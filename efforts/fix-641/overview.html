保持现有 UI，修读取性能与状态一致性

本轮只处理任务板性能、现有状态的一致性，以及整个 MMW 的 GitHub API 调用。保留现有布局、控件、字段、状态词和操作路径。

左列是已读源码反映的现状，右列是优化方向。读取频率、缓存时效及批量大小由当前复现和性能基线决定，本轮尚未实施。

三个改动目标

目标本轮先解决什么
任务板性能核实并减少重复刷新、多标签页重复读取及排队等待，在现有进程与 HTTP 路径内复用工作。
状态一致性修复卡片与连线不同步、合入后更新遗漏、详情最新阶段矛盾和刷新无效。保留关闭、通过、合入及依赖放行的真实区别。
MMW 的 API 调用先删掉汇总等确认重复的读取。核查任务板、relay、status 与 dispatch 的调用链，复用分页与条件请求，并按服务器要求处理限流。

按 MMW 执行的准备顺序

顺序方法与产出
复现、测基线Develop a change 统筹，复用已有 how 调查；bug-fix 交回原缺陷的重复反馈循环，perf-issue 交回当前 trace、固定工作量和可重跑基线。
定最小改动从测量指向的无用和重复工作开始。现有代码能回答的直接决定，有事实分歧才做最小实验，不预定缓存时效或全量读取频率。
先准备验收使用 prepare-ui-acceptance 的 Repair 与 Preserve behavior，以实际产品和已复现需求为基线。回归与行为保留验证直接操作现有 UI，不需要设计原型或 UI 签收。
形成工作、交付to-tickets 选最小可验证单元，必要时才用 spec。你给实施 Go 后派 worker，完成 review、产品验证和同条件性能复测，再交你验收。

验收分别看页面等待、数据滞后、GitHub 请求和额度。前后数据必须同样完整、同样新鲜；保留必要的写后核对和结果通知，不能以漏读换速度。

已有源码与 API 调查及受影响功能清单。当前产品的缺陷复现和性能基线尚待补齐，本轮没有承诺未经测量的提速。
