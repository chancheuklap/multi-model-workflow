## 已取得的证据

本轮实际运行了当前任务板后端和原页面。GitHub 输入由仓库现有隔离层替代，没有写真实票据。命令和结果见 [复现与基线](evidence/diagnosis.md)。

| 问题 | 本轮观察 |
| --- | --- |
| 手动刷新不核对 tracker | GitHub 替身已返回 closed，刷新读到了 landed 事件，回答却仍是 state=open、blocker_hold=open；原页面显示 landed 卡片和一条红色阻塞线 |
| landed 后永久停读 | 加入 ticket.regressed 后再次刷新，该票的评论读取次数是 0，事件仍止于 landed |
| 详情阶段落后 | 原页面卡片和详情头部为 working，Events 最后一块仍为 review |
| 标签页重复消耗 | 12 票受控重放中，一次 GET 读 12 次评论，两个同时 GET 读 24 次，后一个请求排队再做同样的工作 |
| MMW 总结重复读取 | print_summary 先读取全部任务票，再由 batch_children 读取同批票。N 票、C 个独立子 issue 时为 2N+C 次 read_ticket；这是源码调用计数，尚非真实 HTTP 测量 |
| 首次打开的根查询 | 真实 GitHub 上，原来的仓库身份和两类根列表需 3 次 gh 调用。合并查询实验保持回答相同，降至 1 次。各 5 轮交替测试，根查询阶段中位 5.93 秒变为 1.54 秒，未测候选整页提速 |

当前真实仓库没有打开的 map 或 spec，不能把隔离重放当成正在运行一夜的现场测量。#641 的历史性能数字也不作为今天的基线。

## 任务板采用一轮完整核对和一份已发布结果

现状是每个页面请求各做一轮 GitHub 读取，评论与 tracker 分别以 60 秒和 600 秒更新，landed 后评论永久冻结。改为 BoardStore 管理当前仓库的一轮刷新及上一份成功结果。

1. 普通 GET 在上次完整核对完成后 60 秒内复用结果。同页、同时或错开打开的标签页共用这个窗口。过期后由第一个请求刷新，重叠请求共用该轮结果。删除“等锁后每个请求再读一轮”的行为。使用现有服务进程，不增加后台常驻任务。
2. 每轮都核对正在展示的根、结构、依赖、tracker 状态及票据评论。把仓库身份、open map 和 open spec 合并为一次 GraphQL 查询，替代现有三个命令，完整遍历根列表分页。其余结构和评论继续复用已有读取机制及逐页条件请求。删除 600 秒结构缓存与 landed 永久停读的组合，也删除因此不再需要的结构事件补读分支。已落地票只要仍在展示范围内，就继续参与核对。
3. 手动刷新跳过 60 秒复用窗口，等待完整核对结束。正在进行的完整核对可以共用，未核对 tracker 的旧式评论读取不能满足刷新。刷新失败显示现有读取失败提示，保留上一份成功结果。
4. 一轮成功后整体替换结果、缓存验证信息和读取时间。任何必要来源读取失败都不发布半份结果。顶栏现有读取时间表示最近一轮完整核对的完成时间，失败不会让旧数据看起来刚刚成功刷新。
5. 同页只保留一个在途读取，避免定时器、切回页面和手动刷新相互覆盖。成功响应后按已有 read_at 安排这一份结果的下一次核对，不能收到缓存后又重新等足 60 秒。切回可见页面立即请求 GET，隐藏页面继续跳过定时读取。手动刷新所需的强制核对不能被普通缓存响应吞掉。失败按正常重试间隔及服务器限流暂停处理，不因旧 read_at 立即连环重试。

GitHub 多次读取没有跨接口的原子快照保证。本方案消除人为制造的十分钟年龄差和永久冻结，不承诺读取期间 GitHub 自己也停止变化。60 秒是结果复用窗口，实际变化可见时间还包括下一轮网络读取耗时。

## 页面各处共用状态解释，保留业务区别

保留 GitHub 开关状态、验收结果、是否合入、依赖是否放行、会话占用和当前阶段这些不同事实。继续使用 events.py 的事件及依赖放行规则，不用 landed 事件伪造 tracker 已关闭。

卡片、灯、计数、线和详情头部从同一份已发布数据取得这些事实。当前阶段与事件分块使用同一套阶段转换规则，删除独立事件映射和“claim 永远粘在前一块”的例外。验收覆盖 review 结束再认领、非阶段事件、关闭先于 passed、合入后回归及恢复。历史事件仍显示其实际含义，修复不得改写早先 review 的事实来凑齐当前阶段。

只修正现有字段的结果。本轮不增加阶段时长、夜进度、事件种类、默认选择策略或页面设计。

## 整个 MMW 的 GitHub 调用按职责减量

- **status 和 summary。** 同次总结传递已经读到的任务票，复用现有 batch 和 ticket map，把 2N+C 次 read_ticket 减至 N+C。跨命令不缓存，写入后的下一次决策仍重新读取。
- **任务板。** 60 秒内复用完整结果，合并在途刷新，停止多标签页倍增读取。先保留现有逐票条件读取，不同时维护仓库增量流和逐票历史两套通路。当前证据尚未证明仓库增量流值得其合并、删除核对和恢复成本。
- **relay。** 保留现有增量评论、重叠区间、去重和重启完整读取。relay 的增量不作为任务板全部历史，也不依赖页面是否打开。单纯两个进程读过同一张票，不足以删除一次具有不同职责的读取。
- **公共读取工具。** 复用 ghlist 的逐页 ETag、完整分页和错误处理。在现有读取实例内遵守 GitHub 返回的限流暂停时间，交给任务板和 relay 的现有调用循环处理。暂停期间不因手动刷新或固定轮询立即再请求。没有服务器明确时间的二级限流按官方退避规则处理。普通权限错误不冒充限流。
- **认领、路由和合入。** 保留写后以及关键判定前的必要重读。events 已支持消费调用方读到的 comments，只有同一操作中确实已有完整且适用的数据才复用，不引入跨进程缓存。

304 仍有网络和 gh 子进程成本。REST 请求数、GraphQL 点数、主要额度和等待时间分别报告，不能把它们当作一个“API 节省率”。本轮不改模型配置、不设全局额度服务、不用并发冲 GitHub。

## 实施与验收边界

这是一次有共同读取契约的优化，按以下可验证顺序实施，避免一边提速一边漏事件。

1. 先锁定原缺陷的回归：手动刷新清除已关闭上游的阻塞，landed 后新增事件仍进入结果，review 结束后详情最新阶段与卡片一致。保留现有布局、选择、详情打开、缩放和配置操作的行为证明。
2. 在 BoardStore 替换刷新计划和结果复用，再补同页刷新顺序。受控 12 票 workload 中，成功核对后的 60 秒内重复 GET 应新增 0 次 GitHub 读取；过期时重叠请求只执行一轮完整核对；手动刷新必须真实核对所有必要来源。不能靠永久缓存满足性能目标。
3. 修正状态解释，再删除同次 summary 的重复读取。summary 内容、子 issue 归属、路由和写后判定保持原有语义，增加观察 GitHub I/O 的针对性证明。
4. 在已有读取工具落实限流暂停，分别证明任务板保留旧结果和 relay 恢复后不漏、不重复唤醒。复用现有分页、编辑、满页追加和重启用例，只补受影响的失败场景。
5. 同条件交替复测至少五轮，分别报告冷启动、已有结果的页面响应、需要刷新的等待、单页与多页请求数及输出完整性。冷启动和单次完整核对仍须读真实来源，本方案不预先宣称它们有固定倍数提速。
