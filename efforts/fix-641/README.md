## 推荐改动方向

| 目标 | 先处理什么 | 保留什么 |
| --- | --- | --- |
| 任务板性能 | 查明同页重叠刷新、多标签页与错开请求的重复读取，在现有 BoardStore 和 HTTP 路径内复用工作，减少排队和等待 | 现有分页、条件缓存及失败时保留上次结果 |
| 状态一致性 | 复现卡片已合入但线仍阻塞、合入后停读、详情最新阶段矛盾；核实手动刷新和切回页面。消除不同龄数据拼接及重复判定 | 关闭、通过、合入和依赖放行的真实区别，历史事件的原有含义 |
| MMW 的 GitHub 调用 | 核查任务板、relay、status/dispatch 的调用链。先删同次汇总重复读票等确认的浪费，复用仍有效的完整结果，遵守限流暂停 | 写后必要重读，认领/路由/合入所需的新鲜证据，以及 relay 唤醒、去重与重启恢复 |

缓存范围、读取批量与频率由当前 trace 和基线决定，不预定“一分钟全量重读”。先删不该做和重复做的工作，不新增共享后台服务、跨进程缓存、自动策略选择器或全局检查体系。

合入后由现有字段表达的更新仍须读取。修复现有显示所依据的数据，不增加新的收口、复跑或回归界面。手动刷新完成已承诺的必要核对，失败继续使用现有失败显示。

## 按 MMW 推进

1. **复现与基线。** 复用已有 how 调查与受影响功能清单；用 verify-task-board 的独立环境及 control-ui 操作原有页面。状态缺陷走 bug-fix Diagnose；性能走 perf-issue Diagnose/Prepare，按 benchmark-checklist 交回 trace、固定工作量及可重跑命令。
2. **定最小改动。** 从测量支持的无用和重复工作开始。源码及现有机制能回答的直接决定，确有事实分歧才用 prototype 的 EXP 做最小实验。交回准确变更范围和由基线支持的目标。
3. **先准备验收。** 使用 prepare-ui-acceptance 的 Repair 和 Preserve behavior，以实际产品和已复现需求为 baseline。准备原缺陷的回归及既有界面行为的保留证明；API 与性能在对应边界验证。
4. **形成工作并交付。** to-tickets 选最小可验证单元，需要协调才用 to-spec。主人给实施 Go 后派 worker，完成 review、verify-task-board 与同条件性能复测，再由主人验收。触及 MMW 技能脚本时带入 Authoring 的标准及隔离证明。

本轮不进入 Design a UI，不要求原型 winner 或 UI 设计签收。Repair 与 Preserve behavior 明确允许从实际产品及已复现需求准备验收。

## 验收边界

- 同样数据和网络条件下，分别比较页面等待、数据到显示的滞后、真实 GitHub 请求、额度及 gh 子进程。覆盖冷启动、重复刷新和多标签页。
- 保持现有 UI 与操作路径，现有卡片、连线、计数、详情的状态自洽。不能靠漏读或增加滞后来换速度。
- 同次命令减少重复读取，写后重新判定和 relay 通知仍正确。304 仍是网络请求，一次 gh 调用也可能包含多个 HTTP 请求。
- 复用已有工具，只补本次改动所需的证明。安装版本保持冻结，候选运行控制代码只在隔离环境证明；发布仍由主人决定。
