## 按 MMW 推进的工作

### 1. 补当前产品证据

复用已有源码调查。用 verify-task-board 的现有环境工具启动独立任务板，经 control-ui 操作真实页面，复现卡片、依赖线与详情的状态变化，以及刷新、切回、多标签页、合入后阶段。

性能部分调用 perf-issue 的 Diagnose 和 Prepare，先记录代表性工作量、trace 和同一条可重跑命令，按 benchmark-checklist 核对。分别观察页面等待、数据到显示的滞后、GitHub 请求及额度。没有测量不确定瓶颈，不从旧 issue 的秒数确定今天的目标。

先核实 #641 原定分层改造的发布及验收记录。磁盘代码已经迁移不能替代这份记录。此项不会修改安装版本。

产出是本分支上的复现材料、性能基线、候选减法及必须保留的现有行为。仅对改到的 feature 准备证明，不启动任务板全量验证资产维护。

### 2. 用可操作页面和必要实验决定方案

UI 走 Design a UI。通过 prototype 的 UI 分支，在本产品界面中试当前阶段时间、按阶段的详情、夜的收口复跑和回归显示、活跃夜选择。沿用现有任务板结构，每轮只解决一个设计问题，主人在真实页面选择和修改。

读取或状态语义确有未决事实问题时，按 prototype 的对应分支做最小实验。例如同样完整性和新鲜度下，哪种读法减少了等待和重复请求。能由当前源码或已有机制解决的事情直接处理，不为它另开实验或框架。

原型界面涉及数据或错误表现的决定在设计期间解决，其余实现问题回到本准备。实验产出要记录尝试、排除理由和准确结论。图示、advisor 建议和假设不能替代这些结论。

产出是主人选择的可运行 winner、已记录的决定和必要实验的 verdict。主人选择 UI 之前，布局和新阶段显示仍未冻结。

### 3. 先准备验收，再写可执行工作

按 Design a UI 记录确认后的 feature 行为并提交。再用 prepare-ui-acceptance 从相应 baseline 准备新增设计验收、已复现缺陷的回归和需要保留的行为。测试从真实界面或既有 I/O 边界观察，证明能抓住目标失败。

API 读取、分页和限流的证明放在相应后端边界。性能标准来自已经固定的工作量与基线。复用已有测试与工具，不另建全局检查体系。

产出是可运行验收、完整命令及真实证据。不能运行的范围要明确记录，不能标为已通过。

### 4. 再裁切 tickets 与执行

按 Develop a change 在证据和设计确定后选最小可验证单元。一张独立 ticket 足够就不扩成批次。需要协调的多个结果再由 to-spec 和 to-tickets 记录成 spec 与依赖图，按可演示的用户路径切分，不预先按“状态层、后端层、UI 层”排施工票。

本仓库的任务板是产品。若选中的改动触及 MMW 技能、playbook 或其脚本，按 Authoring or modifying a skill 把相应写作、脚本和行为证明标准带入共同准备及对应 ticket。运行中的已安装版本始终是控制方，候选版本只在隔离环境证明。

主人给出实施 Go 后，由现有执行流程派 worker，复用准备好的 baseline 和验收。最终经产品验证、review 和主人验收交付。发布沿用现有主人决定，不由本方案另设流程。

## 简单性的取舍

先找能删除的重复读取、重复状态判定和过时假设。已有主路能覆盖的失败不再加补偿层。新机制必须有当前复现或明确新需求支持，并且不能由既有路径完成。读取频率、缓存范围和事件改动均在证据后决定。
