### Diagnosing bugs

**You own the diagnosis of a reported defect.** Reproduce the user's exact symptom and confirm the mechanism with runtime evidence. For a repair, the original reproduction is the acceptance check.

1. **Build a feedback loop.** Reproduce it yourself on the surface where the failure occurs. Use a failing test, a CLI fixture, a replayed request, or a script that drives the real app. Run one command that goes red on this specific bug and keep its output. For an intermittent bug, loop the trigger and record the failure rate. If the failure remains out of reach, stop and report what you tried and the capture or access you need. Redact secrets in commands, output, and artifacts you share.
2. **Minimise the reproduction.** Cut inputs, callers, config, data, and steps one at a time, re-running the loop after each cut. Keep the smallest case that still produces the same failure. Save the original scenario for verification.
3. **Test competing explanations.** Use **how** when you need to understand the affected subsystem. For a hard bug, generate 3–5 ranked hypotheses and state what each predicts. Share the ranking so the user can contribute facts while you investigate. Each pass, take the split that cuts the most remaining problem space. Change one variable at a time. Use a debugger or a targeted probe where the predictions diverge. For a timing regression, establish a measured baseline, then bisect. When delegating an experiment, give the subagent the reproduction and the prediction to test. Check the returned evidence yourself.
4. **Establish the cause.** Point to the runtime observation that distinguished the surviving mechanism from the alternatives. Remove temporary probes after capturing their output. If the decisive observation is unavailable, return the strongest supported hypothesis and the evidence still missing. For diagnosis alone, return the finding and evidence here.
5. **Agree on the repair and record it.** Propose the smallest change the evidence justifies. Settle any open choice about the intended behavior with the user. Once the problem and solution are agreed, record them on the implementation ticket with the failing command, the observed output, and the expected behavior. For a ticket-only request, return the ticket here.
6. **Verify the repair on the same surface.** When implementation is authorized, delegate the agreed ticket to an implementation subagent through the common development workflow. Where a regression test can exercise the real bug, have the implementer turn the minimised reproduction into a failing test before the fix. If no suitable test seam exists, record why. Review the change and rerun the original scenario yourself. For an intermittent failure, compare failure rates under the same conditions and report an inconclusive result when the runs cannot distinguish them.

**Reply:** the observed failure, its cause and the evidence that distinguishes it, or the evidence still missing. For a ticket, include its link. For a completed repair, show the original reproduction's before-and-after output.
