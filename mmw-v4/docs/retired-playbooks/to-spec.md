### To spec

**You own the spec, not the decisions in it.** Do NOT interview the user for facts; just synthesize what you already know.

Takes the current conversation context and codebase understanding, or a reference the user passes, and produces a spec, published as a GitHub issue. A spec is the last text a person checks before agents build from it unattended: whatever it leaves open, a worker decides alone at night, and whatever it states is built as written, including what nobody decided. So record decisions rather than make them. An engineering call the sources leave open (a module's seam, a data shape, the seam a test observes at) is yours: make it and mark it "this spec's decision". Apply **principle-never-block-on-the-human** to the decisions the sources leave open; put an unresolved owner decision to the user before publishing. That, and the division in step 1, are the only things you ask them. The template is `../references/spec.md`; the `gh` commands are in `../references/github-issues.md`.

1. **Read the sources**, per **Reading the sources** below, and judge whether they make one spec or several. Done when every source the reference leads to has been read and you know which one spec this run writes.
2. **Explore the repo** to understand the current state of the codebase, if you haven't already. Use the project's domain glossary vocabulary throughout the spec, and respect any ADRs in the area you're touching. Find the affected existing features as `../references/feature-map.md` says, and put that list in Implementation Decisions. In each UI subsection, name the winner's exact path as the source of its tickets' baselines. For UI work, use the API fake as the draft interface contract and finalize it through **grilling**. Testing Decisions covers only the repository's own tests, not e2e tests. Done when you know which existing modules and ADRs each decision touches, or that none exists yet, and each affected existing feature has its behaviour decision and each UI subsection its winner's path and final interface contract.
3. **Sketch out the seams** at which you're going to test the feature, per **Seams** below. Done when every state this feature's behaviour turns on has a seam where a test observes it, and either a way a test puts the system into it through that seam or a named mechanism that would.
4. **Check that nothing load-bearing is undecided.** First run the **sharpen** skill on the work the spec will describe. Treat the winner and recorded decisions as settled sources, not questions to ask the owner again. For the UI, the outside check is the same tests passing on both `design` and `product`, plus the Spec reviewer's screenshot-pair comparison. Propose other outside checks only for questions the prototype cannot answer, listed in the **prototype** skill's `UI.md` `### 5. Hand it over and iterate`. Give its conclusions and this step's questions to the user in one batch. Write only the conclusions the user agrees to into the spec, with the source marked "owner, date". Put the agreed outside check in `## Testing Decisions`; To tickets turns it into acceptance commands. A code shape the spec rests on that meets the conditions of the **prototype** skill's sketch branch has not been settled, and a spec that states it records a decision nobody made: stop instead of writing the spec around it, and take it back to where it came from. From Grill with docs, settle it there; from a map, add a `prototype` ticket for it to the map as Work through the map step 5 says, and tell the user to run Work through the map. An unresolved owner decision goes to the user now. Done when the user has answered `sharpen`'s conclusions and each decision the spec will state either has a source, is an engineering call marked "this spec's decision", or has the user's answer.
5. **Write the spec** using `../references/spec.md`, then draw it for the owner as one page with the **diagram-design** skill: each flow a user goes through once it is built, what they do and see at each step and where it branches, named as the spec names them. Use the feature map's feature names in the diagram. Done when every section of the template is filled, and every decision names where it came from. Write it for agents who were not in this conversation (**principle-write-for-where-it-is-read**), and copy every settled answer and chosen artifact into it (**principle-baseline-is-the-contract**).
6. **Publish it**: write the spec to a file and run `verify-ticket.py --publish --spec-body <file> --title "<title>"` of the `verify-ticket` skill, adding `--map <map>` when the reference is a wayfinder map; for any other reference, give it no parent. It gives the spec the `mmw:spec` label and no queue label: a spec is a container for the tickets underneath it, not a piece of work, and a queue label would put it in a queue somebody has to sort back out. Done when the command exits 0 and prints the spec's number.
7. **Cut the tickets.** Run the To tickets playbook (`playbooks/to-tickets.md`) on the published spec, in this same session. Done when To tickets has started on this spec's issue number.

#### Reading the sources

If the user passed a reference (an issue number, a URL, a file path), read its full body and comments before anything else. When the reference is a published spec and one of its sections has to change, run the Revising a spec playbook (`playbooks/revising-a-spec.md`) instead of these steps. When the reference is a wayfinder **map**: read the map body; then walk **Decisions so far** and read each closed ticket's **resolution comment**; where a ticket links a prototype or a research file, read that through to its conclusion. The map's **Out of scope** carries into the spec's Out of Scope unchanged.

Then judge whether what you have read is one spec or several. Decisions that share a **seam** belong in one spec. Split only where a part needs a different **seam** and lands and demos on its own; where it can stay one spec, keep it one spec. A part may depend on a part before it: a product delivered in stages (a server registration, then the client that logs into it, then the work the client does) has no reading under which the later stages depend on nothing, and forcing it into one spec produces one nobody can read. What the dependencies may not do is run backwards or in a circle: every one points at a part earlier in the order, and the `## Specs` section writes that order down.

One spec: write it. Several, or a reference that already carries a **spec division** (a map's `## Specs` section, or a spec whose `## Further Notes` lists several specs): follow **Several specs from one reference** in `../references/spec.md`.

#### Seams

Existing seams should be preferred to new ones. Use the highest seam possible. If new seams are needed, propose them at the highest point you can. The fewer seams across the codebase, the better. The ideal number is one.

A seam says where a test **observes**. Ask the other half in the same breath: for each state this feature's behaviour turns on, can a test put the system into that state through the seam you picked? Where the seam does not reach, say what would, and whether that thing ships.

The seam is yours to decide, not the user's: they are not asked to confirm it. What they see of it is the plain-words opening sentence of Testing Decisions, which says where a test looks at the result.

**Reply:** the spec by name with its link, and where its page is; each "this spec's decision" and each answer the user gave; and, when the work divides, the division and which spec this run wrote.
