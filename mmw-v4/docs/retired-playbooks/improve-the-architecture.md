### Improve the architecture

**You own one architecture review: the deepening opportunities in the codebase, drawn as one page for the owner, and the strongest of them carried into Refactoring; an explorer subagent walks the codebase.** A **deepening opportunity** is a refactor that turns shallow modules into deep ones; the aim is testability and AI-navigability. This playbook changes no code. Which candidate goes first, and every question of module, interface and seam, is an engineering decision and yours; whether the change is worth doing now is the owner's, answered at Refactoring's hand-back. Distinct from Refactoring, which starts from one structural change already named, and from the `codebase-design` skill, which answers one design question in its vocabulary.

1. **Scope before you scan: YAGNI.** Deepening a module pays off by making future changes to it easier, so put extra weight on the parts of the codebase that have recently changed. Decide *where* to look before you look. If the owner named a direction (a module, a subsystem, a pain point), take it, and skip the inference below. Otherwise, walk back a good stretch of the commit history (`git log --oneline`) to find the codebase's hot spots, the files and areas that keep coming up, and let those paths pull your attention first. If the changes are scattered with no clear hot spot, widen the net. Done when you can name the paths the review will walk, and why those.
2. **Explore.** Read the project's domain glossary (`CONTEXT.md`, or each one its `CONTEXT-MAP.md` names for these paths) and any ADRs in the area first: an ADR records a decision this review does not re-litigate. Then send one subagent on the `default` row, the architecture explorer, as the `mmw-mode` skill's `## Subagents` says; its piece is `follow its references/architecture-explorer.md over <the paths of step 1>, because <why those>, reading the glossary <its path>, and hand back that file's report as your last message`. Check each friction point it reports against the code, using **principle-minimize-reader-load**, including its deletion test. Done when the explorer has returned and each friction point it reports has been checked.
3. **Draw the report.** Draw one page for the owner with the **diagram-design** skill, named `architecture-review-<timestamp>.html` so each run gets a fresh one; `../references/architecture-report.md` says what goes on it. A candidate that contradicts an existing ADR is on it only when the friction is real enough to warrant revisiting the ADR, marked in its card (e.g. _"goes against ADR-0007, but worth reopening because…"_); do not list every theoretical refactor an ADR forbids. Done when the page is drawn and its link or path is in your message.
4. **Carry the top recommendation into Refactoring.** Run Refactoring (`playbooks/refactoring.md`) on the page's top recommendation, with what hurts now under `## Problem`, as its card says it, and the page's link or path beside it; the deepened shape is what Refactoring's step 4 names as the target. In the ticket, use the **codebase-design** skill's vocabulary for the architecture (module, interface, depth, seam, adapter, leverage, locality) and the glossary's names for the domain. Done when Refactoring's hand-back is done.
5. **Record a candidate the owner turned down.** When the owner turns it down at the hand-back with a reason a later review would need, so that it is not suggested again, record that reason as an ADR with the **domain-modeling** skill. Skip passing reasons ("not now") and self-evident ones. Done when the ADR is written, or there is none to write.

One candidate goes into Refactoring per run; the page's link or path is how the others are picked up later.

**Reply:** the page's link or path; the candidates, each with its recommendation strength; the one carried into Refactoring and why it goes first; then Refactoring's reply; the ADR recorded, if any.
