### Feature

**You own the design and the ticket that carries it. A worker writes the code, and you verify it on the product.**

1. **Open the ticket.** Open a ticket and its `fix-<n>` as `../references/ticket.md` `## Opening a ticket` says, with `Playbook: Feature` and the owner's words under `## Problem`. A ticket already open, such as one Grill with docs opened, keeps its number and opens only the `fix-<n>` it lacks. Done when the ticket is open and `fix-<n>` is on origin.
2. `how` over the affected subsystem. Read the files the change touches per **principle-read-before-you-conclude**, and follow **principle-start-from-what-exists** before designing. Find the affected existing features as `../references/feature-map.md` says.
3. Settle the throughput checkpoint, one answer per dimension. A dimension that genuinely does not apply (single file, no fan-out) is answered `n/a: <reason>` rather than dropped:
   - **Blocking first steps.** Gates run before fan-out.
   - **Independent workstreams.** Disjoint files, services, or layers parallelize. Shared writes serialize.
   - **Shared mutable state.** Follow **principle-separate-before-serializing-shared-state**.
   - **Smallest safe decomposition.** If one ticket can carry it, name why.

   The checkpoint decides the size. One ticket can carry the change: go on to step 4. It cannot, or its independent workstreams should run in parallel: go to step 6 now and say so, and the owner's word sends it to To spec, as `../references/ticket.md` `## Handing it back` says for a change too big for one ticket. Done when the checkpoint names one ticket or To spec.
4. For new or changed UI behavior, run the **prototype** skill's UI branch on `fix-<n>`. Record the owner's answers to questions that change the interface on this ticket during iteration. For the code shape, run the **prototype** skill, whose `## Pick a branch` decides whether a sketch is drawn; commit what it writes on `fix-<n>`. Done when the code shape is settled and any UI prototype has reached design freeze.
5. **Write the ticket.** Finalize the interface contract. For new or changed UI behavior, use the prototype's API fake as its draft and update it to match the final contract before writing tests. For new or changed UI behavior, read the product's `verify-<product>` skill's Read first, Rules, Drive and Evidence, then write those tests as the `create-verification-skill` skill's `references/tests-from-prototype.md` says. For UI work, put the winner's exact path and the affected feature files under **Read first** as baselines. Turn each owner answer recorded during iteration into its own numbered **What to build** point. Use step 2's existing-feature list to prepare pins or rewrite cases as To tickets' **Acceptance criteria** says (`playbooks/to-tickets.md`), keeping the acceptance tests in this ticket's own new file registered on the feature file's `Tests:` line. Use Cleanup after starting a product. Commit the tests and feature files on `fix-<n>` and push them before the worker starts. Fill it in as `../references/ticket.md` `## Opening a ticket` says. **What to build** sets the scope the worker writes to: the named data shape and its organizing structure per **principle-model-the-domain**; surgical edits, re-grounded against the source for upstream-derived files; a shared-primitive improvement ported to every consumer and verified in each. When the **prototype** skill's sketch branch produced a sketch, it is a baseline under **Read first**, and **What to build** says the sketch is the contract: its `not implemented` bodies become code and its pseudocode becomes logic, a deviation from it is surfaced as a `contract` child rather than absorbed, and it can land as its own commit first (**principle-foundational-thinking**), with breakage while its bodies are filled in governed by **principle-outcome-oriented-execution**. Every other baseline the code must follow is under **Read first** too (**principle-baseline-is-the-contract**). For a UI ticket, follow To tickets' **Vertical slices** for mount-point removal and its **Acceptance criteria** for any back-end test CHECK. The acceptance criteria cover the behavior the sketch and the owner's words describe: the repository's own tests at the ticket's **Seam**, and UI e2e tests prepared here. Done when every section below `## Problem` is filled and the prepared tests and feature files are on origin's `fix-<n>`.
6. **Start or hand it back.** For a ticket with a prototype, the owner's approval of that prototype is Go: run One ticket (`playbooks/one-ticket.md`) without asking again, unless the ticket adds scope beyond the prototype and recorded decisions. In that case, or without a prototype, hand it back as `../references/ticket.md` `## Handing it back` says. Done when the owner has said go and One ticket runs, or the ticket is in `needs-triage` or closed.

Parent-level fan-out is for slices that produce independent artifacts (audits, cross-subsystem investigations, competing experiments), not for writing the change.

**Verify on the matching surface.** One ticket step 4 runs this once the ticket passed: drive the new behavior in `.worktrees/issue-<n>` the way its user meets it, through the matching control skill. "Inconclusive" or wrong-surface is not a pass. Flag it. Run tests per **principle-run-the-smallest-test-set**.

**A ticket that came back.** When a ticket its worker handed back (a `ticket.returned` event) is picked from `needs-triage`, read why on the ticket and go back to step 3 with that evidence.

**Reply:** what the change does for its users, the design chosen and why (tables for design alternatives), the throughput checkpoint, the criteria, what the ticket leaves out, open decisions.
