### Authoring or modifying a skill

**You own one change to the skill set, from the owner's words to its proof on a real task.**

A skill change is a project like any other, with its own standards and its own proof: it runs the general flow for its size, held to the skill set's standards, and is proven once. Every agent that loads the changed text acts on it in cases its writer did not foresee, with no one to ask: a rule written in a second place drifts from the first, and a rule without its reason fails in the case nobody listed. The temptation is to answer each slip with one more sentence; every sentence costs attention on every run that loads the file, so the change deletes before it adds.

1. **Open the ticket.** Open a ticket and its `fix-<n>` with the **to-tickets** skill's opening entry, with `Playbook: Authoring or modifying a skill` under `## Problem`. Record which source the change comes from: the owner's words; a registered problem or retrospective proposal reached through Session pickup; an upstream release; a doubt about a part of the set. Keep the owner's words when they are the source. A ticket already open keeps its number and opens only the `fix-<n>` it lacks.

   Done when the ticket records its source and `fix-<n>` is on origin.
2. **Gather the evidence.** Pick the row for the source recorded under `## Problem`.

   | Source | Evidence to gather |
   | --- | --- |
   | The owner's words | Search the set for the meaning. A meaning the text already states as asked needs no change: tell the owner where it says so and whether the installed checkout (the one `~/.mmw/installed-root` names) carries it yet, close the ticket with that answer, and stop. |
   | A registered problem or retrospective proposal | Open the issue's evidence and confirm it still holds on the project branch. |
   | An upstream release | Follow the `writing-for-agents` skill's `UPSTREAM.md` `## Carry a newer upstream version`. |
   | A doubt about a part of the set | The scoped text is the skill, file or section the source names, and nothing wider; a source that names a whole skill scopes that skill's own directory. Map every entry of the scoped text to a task as the `writing-for-agents` skill's `WALKING-A-SKILL-SET.md` `### List the tasks` says. Measure its use with that skill's `scripts/usage.py <skill name or file>`. Test each passage in scope against its `SKILL-SET-RULES.md` `## Checks`. The findings have one table row per finding: the passage (path and heading), its evidence, the check or design intent it concerns, and the action (remove, merge, move, simplify, add, or none). When no finding calls for a change, tell the owner with the findings comment's link, close the ticket as answered, and stop. |

   Post the findings as one comment on the ticket. Each finding names evidence the owner can open, such as a path and line, a command and its output, a session count or an issue, and the check or intent it concerns.

   Done when every finding carries evidence the owner can open, or the meaning is already stated and the owner has heard where.
3. **Judge it against the design.** Read the `writing-for-agents` skill's `DESIGN-INTENTS.md` and name the intent each change serves. A change that would break an intent, or bring back one of its departures, is not made: tell the owner which intent and why, and wait for their word.

   A change to a workflow first reads the bounded context it touches (`CONTEXT-MAP.md`, then that context's `CONTEXT.md`), the ADRs those entries cite, and the research intents and rejected options those ADRs cite; the plan states how the change goes in each case the workflow serves, for a product workflow at least a new project without code, an existing product, a product across several repositories, and each surface the `create-verification-skill` skill's `Surface` row names. A page that draws MMW itself takes its legend's component kinds from the `writing-for-agents` skill's `SKILL-SET-COMPONENTS.md`.

   Done when each change names its intent and any conflict has the owner's decision.
4. **Plan the fix.** Follow **principle-encode-lessons-in-structure** before deciding to add prose. Apply the `writing-for-agents` skill's `SKILL-SET-RULES.md` `## Editing`: remove, merge, move or simplify before adding, name the run a new mechanism would have prevented, and fix at the level of the finding. A rule a script could check becomes a check, in `SKILL-SET-COMPONENTS.md` `## The method` item 5's order. Use that file to give each passage one component and one file. Write text by the skill's `SKILL.md` and the sections of `SKILL-SET-RULES.md` `## Checks` that govern each passage. For an upstream copy, follow `SKILL-SET-RULES.md` `### Upstream skills` and, for a newer release, `UPSTREAM.md`'s four cases. Change upstream text only where it conflicts with a design intent and connecting text outside it cannot resolve the conflict.

   Done when each finding has a planned fix at its own level, and each passage has one component, one file and its governing standards.
5. **Write it, by kind and size.** Skill text is written once, by you; a script is written by a worker.
   - Skill text one ticket can carry: write each passage yourself in `.worktrees/fix-<n>`, as planned, before any worker starts. Search the set again for every passage that still states the old meaning, and change it too. Commit and push on `fix-<n>`. The ticket keeps its `## Problem` and the findings comment, and the sections below `## Problem` stay unwritten for this text. When no script changes, run **Prove it, once** now, on `fix-<n>`.
   - A script change one ticket can carry, alone or beside skill text: use the **to-tickets** skill's independent entry for the script. **What to build** names each change, the file it goes in, and the standards it keeps to. **Read first** names, for each, the file and section of the `writing-for-agents` skill that governs it, marked as a baseline, not whole files. The worker and reviewer read only **Read first**, so this list is how these standards reach them. A change to a script's output that an agent reads to choose its next step says so in **What to build**, because **Prove it, once** walks it. The acceptance criteria are the checks of **Prove it, once** below that a command decides; the skill text you wrote is not in **Owns**.
   - A larger one: carry the findings, settled scope, assets and governing standards into Develop a change (`playbooks/develop-a-change.md`) for its missing shared preparation, using the existing authority. That preparation calls **to-spec** and **to-tickets**; it does not restart this Authoring task. Each Implementation Decisions subsection that changes the skill set cites, for each passage, the file and section of the standards that governs it, so To tickets copies them into its tickets' **Read first**. State which changes alter what an agent does in a task. Testing Decisions turns each check of **Prove it, once** that a command decides into an acceptance criterion of every ticket that changes a file the check reads, and names the required pre-acceptance behavior proof for the batch executor. The spec states decisions; the night's tickets write the text, from the files as they stand.

   Done when the text is on `fix-<n>` on origin and, with no script, **Prove it, once** has run; or a script ticket's sections below `## Problem` are filled; or the larger change has been handed to Develop a change with its findings, standards and existing materials.
6. **Hand it back.** Apply the mode's preparation authority rules, adding `needs-triage` while the owner's decision remains, and quoting each sentence you wrote or changed, since the owner reads sentences, not a diff. With no script, the owner's go changes the ticket's kind label to `mmw:ticket` (`gh issue edit <n> --remove-label mmw:problem --add-label mmw:ticket --remove-label needs-triage`) and runs Opening a PR (`playbooks/opening-a-pr.md`) from `fix-<n>` in place of One ticket.

   Done when the owner has said go and One ticket or Opening a PR runs, or Develop a change runs, or the ticket is in `needs-triage` or closed.

**Prove it, once.** For skill text alone, step 5 runs this on `fix-<n>`. For a ticket with a script, One ticket step 4 runs it once the ticket passed, in `.worktrees/issue-<n>`; for a larger change, Run a night **Open the pull request** runs it on the candidate delivery version before the owner accepts or `finish` merges it. From the supplied result checkout, run each applicable check, reusing its evidence when already proven on this same candidate version:
- When a script changed, the suites **test-audit** picks (`bash mmw-v4/tests/<name>/run.sh`).
- `scripts/check` exits 0.

Then, when the change alters what an agent does in a task, have one fresh agent walk one real task the change touches, on the changed text read from that checkout, as the `writing-for-agents` skill's `WALKING-A-SKILL-SET.md` `### List the tasks` and `### A fresh agent's walk` say. A wording-only fix needs no walk. A change to a script's output that an agent reads to choose its next step alters what an agent does. Its record of the walk is the task's load. Post the record as a comment on the ticket and link it from the pull request. A required walk without that record fails the check. A place where the agent ended wrong, stopped short of the completion criterion, or guessed at a sentence this change wrote, you fix in the text yourself on the current delivery branch (`fix-<n>` after `land` for an independent ticket, or the night branch for a batch), following the current execution flow's repair rules for script changes, then one more fresh agent walks the same task. Never reopen the ticket or send a worker for it. What the second walk still finds goes to the owner: an end that is wrong or short holds the change until the owner decides, and a guess goes into the Reply. Every other guess goes into the Reply as a finding for a later change: each fresh agent finds a new guess somewhere, and fixing each one adds a sentence that raises the next.

**A ticket that came back.** When a ticket its worker handed back (a `ticket.returned` event) is picked from `needs-triage`, read why on the ticket and go back to step 2 with that evidence.

When in doubt, delete. Keep only prose that changes a decision. Match tone to scope. Delegate to other skills by name. Don't restate. A workflow you keep hitting but isn't captured → propose a new skill. A skill follows **principle-files-describe-the-present**.

**Pure deletion.** When the owner names skill text to delete and nothing replaces it, this session works directly on the project branch without a ticket. Delete every passage that cites what went, run `scripts/check`, and commit with the owner's words quoted. Quote each deleted sentence in the reply. A deletion that needs replacement text, a script or a test follows the numbered steps above.

**Reply:** the intent the change serves; each sentence you wrote or changed, quoted, and the component it goes to; what it deletes; the walk's job, load and result; for a script, the criteria; for a larger change, the shared preparation and spec continuation it needs and why; when a skill's `description` changes, that it takes effect in a new session. The checks and the walk of **Prove it, once**, with their commands, results and the walk's load, are what One ticket reports.
