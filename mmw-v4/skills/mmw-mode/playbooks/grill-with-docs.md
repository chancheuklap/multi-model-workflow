### Grill with docs

**You own the interview and the glossary and ADRs it writes.**

A relentless interview to sharpen a plan or design, which also creates docs (ADRs and glossary) as we go.

1. **Interview.** Use the **grilling** skill and the **domain-modeling** skill. When the owner must compare alternatives or confirm a design, first draw a page with the **diagram-design** skill and point each question to a numbered mark on that page, so the owner sees what the question concerns. Update the page throughout the interview to show the current design. Done when every branch of the plan the user brought has been walked to a decision or to one of the forks of step 2.
2. **Route each fork by whose decision it is.** Apply **principle-never-block-on-the-human** to identify which decisions go to the user. A fact goes to the Investigation playbook, as the **grilling** skill says. An answer you could observe by running something goes to the **prototype** skill, and so does a question of what shape the code should take, which its sketch branch settles when that branch's conditions hold; the user is not asked either. Done when every fork is either answered by the user, or settled by the Investigation or prototype it was handed to.
3. **Write the docs as you go.** Opened by the user directly, before the first doc write, open a ticket and its `fix-<n>` as `../references/ticket.md` `## Opening a ticket` says, with the design being sharpened under `## Problem` and its `Playbook:` line left for step 6. Write each resolved term into the glossary as it resolves, and offer an ADR as the **domain-modeling** skill describes, committing each on the branch that skill names; opened by the user directly, that is `fix-<n>`, and the docs land with this ticket's pull request. These writes are part of the session, not the acting on it that **grilling** holds back. Done when every term resolved in this session is in the glossary and every hard-to-reverse decision has an ADR or the user declined one.
4. **Watch the size.** When the plan turns out too big to settle in one session, propose switching to the Chart the map playbook (`playbooks/chart-the-map.md`); the user decides. Opened from a ticket of a map, what does not fit becomes new tickets or fog on that map instead, as Work through the map step 5 says. Done when the plan fits this session, the excess is on the map, or the user has chosen to keep going or to chart a map.
5. **Hand back to whoever opened it.** Opened from a grilling ticket on a wayfinder map, the decisions go back to that map: Work through the map (`playbooks/work-through-the-map.md`) records them. Opened by the user directly, go on to step 6. Done when the map's ticket has its resolution, or this session is the user's own.
6. **Name the next step.** When the session settles a change one ticket cannot carry, the next step is the To spec playbook (`playbooks/to-spec.md`), in this same session; close this ticket with a comment linking the spec, and `fix-<n>` stays. When one ticket can carry it, give the user two options. Build it now: write the `Playbook:` line for Feature or Refactoring, as the change calls for, and run that playbook, which keeps this ticket and its `fix-<n>`. Or stop here with the decisions recorded: write the `Playbook:` line for the playbook that will build it, and label the ticket `needs-triage`. With no ticket open yet, that playbook's first step opens one. Done when the user has the next step, or both options.

**Reply:** the decisions reached; each glossary term and ADR written, by name; whether the prototype skill's sketch branch ran or was skipped, and why; the next step, or the two options.
