### Hillclimb

**You own the metric and the experiment's integrity. A worker makes the attempts, on one ticket.** For sustained, iterative improvement of one measurable thing against a target. A one-off fix is Bug fix or Perf issue. This is the loop.

Core discipline: one change, one measurement, keep or revert. Never stack untested changes, and never claim a win from code inspection (**principle-prove-it-works**).

1. Open the ticket. Open a ticket and its `fix-<n>` as `../references/ticket.md` `## Opening a ticket` says, with `Playbook: Hillclimb` and the owner's complaint and target in their words under `## Problem`. A ticket already open keeps its number and opens only the `fix-<n>` it lacks. Done when the ticket is open and `fix-<n>` is on origin.
2. Ground the workload and architecture before choosing the metric. Run the **how** skill over the target, name the realistic workload dimensions that can move the result (data size, history, state, concurrency), and select a case that reproduces the user's complaint. If no case reproduces it, fix the repro instead of hillclimbing. Then fix one metric, the direction that counts as better, and a checkable stop predicate that pairs a target with a floor on attempts so a lucky early win can't end the run (the example "at least 50% better than baseline and at least 10 iterations" is this shape). Use the user's numbers when given, otherwise agree them. Done when the metric, its direction and the stop predicate are written down.
3. Build the measurement harness, prove its sensitivity, then freeze it (**principle-build-the-lever**). Run contrasting realistic workloads and confirm the target case reproduces the symptom while easier cases separate as expected. If the harness cannot distinguish them, revise the workload or metric. Vet the harness with the **benchmark-checklist** skill before you freeze it, and make it print its error count and a count of the work done. Once frozen, one repeatable command emits the metric, sampled enough to clear the noise (median of N, not a single run). Record the baseline metric and a green run of the regression gate (the tests that must keep passing) before any change. Commit the frozen harness on `fix-<n>`. Done when the harness is frozen and committed, with the baseline and a green gate recorded.
4. Keep the decision log as comments on the ticket, one per attempt, opening `Attempt <id>:` with hypothesis, change, before, after, delta, tests, verdict (kept or reverted) and note; the baseline is `Attempt 0`. The worker posts each attempt, the reviewer reads them, and a criterion counts them with `gh api`. Done when the ticket holds its baseline comment.
5. Ground each hypothesis in the architecture model from step 2, so it names a specific mechanism ("defer X off the boot path because it blocks first paint"), not "try memoizing something". For a perf metric, order hypotheses by the performance mantras in step 2 of the Perf issue playbook (`playbooks/perf-issue.md`). Borrow only their order, not that step's stop rule. Done when the hypotheses are ranked.
6. Write the ticket. Fill it in as `../references/ticket.md` `## Opening a ticket` says. **Read first** lists the frozen harness, the Attempt comments, the workload and architecture model of step 2, and the hypotheses of step 5 in order. **What to build** carries the loop, which the worker runs:
   - Read the Attempt comments before each attempt. One hypothesis per iteration. Measure before and after with the frozen harness, and run the regression gate.
   - Accept only when the metric moves past noise and the gate stays green. Otherwise revert the change in full. A tweak that "might help" is not kept.
   - One commit per accepted fix, staging only the files changed (`git add <files>`, never `-A`). Post the Attempt comment either way, kept or reverted. Iterate per **principle-sequence-verifiable-units**.
   - Push past the first plateau. On a stall, several rejects in a row, pivot category, combine near-misses, re-read the source, or try something more radical before concluding the hill is climbed. Correctness and simplicity outrank the number. Revert a win that breaks behavior, and keep a simplification that holds the number (**principle-subtract-before-you-add**).
   - Stop when the predicate is met. Don't relax the predicate to meet it, and don't quit while cheap untried hypotheses remain. When the remaining ideas are marginal and the target is not met, abandon the target criterion with what each round tried.
   The acceptance criteria are three: the frozen harness, printing a line only a run that meets the target prints; the regression gate; and at least the predicate's floor of Attempt comments, each with a before, an after and a verdict, counted with `gh api`. Done when every section below `## Problem` is filled.
7. Hand it back. As `../references/ticket.md` `## Handing it back` says. Done when the owner has said go and One ticket runs, or the ticket is in `needs-triage` or closed.

**Check the climb.** One ticket step 4 runs this once the ticket passed: run the frozen harness yourself in `.worktrees/issue-<n>` and compare it with the baseline Attempt comment, then read the Attempt comments: each kept attempt has its commit on the branch, and a reverted attempt left nothing behind. A win claimed without a measured Attempt comment is not a win. A target the worker did not reach is reported as missed, with what it tried.

**A ticket that came back.** When its worker handed it back (a `ticket.returned` event) with the target missed, tell the owner first the final number, what each round tried, and that the kept commits stay on `issue-<n>`. When the owner picks it from `needs-triage`, go back to step 5 with those Attempt comments.

**Reply:** the metric, its target and the stop predicate; the baseline number and the harness that measures it; the hypotheses in order; the criteria; what the ticket leaves out. The final number, the iterations kept and reverted, and the next idea to try are what One ticket reports from **Check the climb**.
