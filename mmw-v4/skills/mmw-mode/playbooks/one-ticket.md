### One ticket

**You own one ticket outside a night, from the owner's go to its pull request.** An upstream playbook wrote the ticket in its `fix-<n>` and handed it back, and the owner said go; or the owner handed this session a ticket that already has acceptance criteria and no `Playbook:` line, which is their go. The ticket belongs to no spec, so no `advance` will ever collect it: `land <n>` is its whole ending. Distinct from Run a night, which runs a spec's batch. What you do on a wake is the dispatch skill's `## On waking`.

A ticket the owner handed in has no `fix-<n>` yet: open it first as `../references/ticket.md` `## Opening a ticket` says, then start at step 1.

1. **Ready.** On the owner's Go, change the kind label to `mmw:ticket`. For `mmw:lesson` or `mmw:problem`, include `--remove-label <original kind> --add-label mmw:ticket` in the `gh issue edit` below. For `mmw:child`, first read the original ticket number from the body's opening ``A `<kind>` child of #<n>`` line, where `<kind>` is its child kind, then run the **dispatch** skill's `dispatch.sh route <original ticket> <child> became-ticket <child>`. Use `route`, not `gh issue edit`, to change a child's kind label, because it also moves the parent and records the resolution on the original ticket. Add `ready-for-agent` and one worker label (`junior-worker`, or `senior-worker` for silent-failure work), removing the other worker label and `needs-triage` when the ticket has them: `gh issue edit <n> --add-label ready-for-agent --add-label <worker label> --remove-label needs-triage`, creating any label the repository lacks as `../references/github-issues.md` says. Then run `verify-ticket.py <n> --lint` of the **verify-ticket** skill and fix every `ERROR`; a fix that changes what the ticket delivers goes back to the owner first, as `../references/ticket.md` `## Handing it back` says. Done when the kind is `mmw:ticket`, the ready labels are on, and `--lint` reports no `ERROR`.
2. **Send the worker.** From `.worktrees/fix-<n>`, `dispatch.sh send worker <n>`: this session becomes the ticket's orchestrator, and the worker starts in `.worktrees/issue-<n>`. When the line it prints names a task board, hand its URL to the owner. Then end your turn. A repository with no executable `scripts/check` is refused: run Set up code checkers (`playbooks/set-up-code-checkers.md`) first, then `send` again. Done when `send` exits 0.
3. **Each wake.** You are woken with `#<n> ticket.passed` or `#<n> ticket.returned`, or with one of the events below. Read that event on the ticket and `dispatch.sh ack <n> <that event>`, then act on it.
   - `#<n> worker.lost`: the worker's session stopped. `dispatch.sh send worker <n>` starts another in the same workspace; it first commits tracked edits and pushes the ticket branch to origin.
   - `#<n> ticket.refused`: the worker refused to claim the ticket, and the event's `reason` says why. Fix that, then `dispatch.sh send worker <n>` again.
   - `#<n> child.opened`: a `fault` stopped the worker. For a fault in this repository's environment, fix what the child names, then `dispatch.sh resume <n> "<what you fixed>, then: continue"` and close the child with `dispatch.sh route <n> <child> fixed`. Leave the running pipeline's own scripts unchanged. Hand that `fault` to the owner using the third finding branch of **Open the pull request** below, preserving its opening ``A `fault` child of #<n>`` line. A `decision` is for the owner, and the worker carries on.
   - `#<n> child.opened` of kind `contract`: when it names a wrong e2e test, this session corrects the test on `fix-<n>`. When the prototype is wrong, run a new round of the **prototype** skill's UI branch and design freeze on `fix-<n>`. When the sketch is wrong, run the **prototype** skill's sketch branch again on `fix-<n>`, post the new verdict on the ticket and point the ticket's **Read first** at it. Then commit and push. For a sketch correction, the resume text names the new verdict comment and tells the worker to read it and rebuild against it. Run `dispatch.sh resume <n> "<what changed and its commit>, then: continue"` so the worker still holding the ticket continues and receives the correction at Work a ticket's **Integrate and run every criterion**. Close the child with `dispatch.sh route <n> <child> fixed`. For other contracts, act as Run a night's **3. Each time something wakes you** says (`playbooks/run-a-night.md`), reading `events.py fold <n>` where it says `status`.
   - A `watchdog:` line or an `MMW turn guard:` line: act as Run a night's **3. Each time something wakes you** says (`playbooks/run-a-night.md`), reading `events.py fold <n>` where it says `status`.

   Tell the owner what woke you and what you did; they are here. Done when the wake is `ticket.passed` or `ticket.returned`.
4. **Check it.** Once the ticket passed, run the verification section of the playbook its `## Problem` `Playbook:` line names, the first bold section after its numbered steps, in `.worktrees/issue-<n>`. A ticket the owner handed in has no playbook verification. A sentence that verification, or the owner, finds to fix in skill text does not stop landing: you write it on `fix-<n>` after `land`, and never reopen the ticket or send a worker for it. Run `scripts/check --all` once in `.worktrees/issue-<n>`. It includes each product's whole e2e suite through its `e2e-<product>` step. A red test belonging to a ticket still open, returned or not yet worked, is expected: record it under that ticket in the page's Not done and left over block and let landing proceed. Any other red result stops landing: tell the owner what it showed, and that the ticket, `fix-<n>` and `.worktrees/issue-<n>` stay as they are for their call. All green results allow landing. The owner's own UI inspection is not a landing gate; their acceptance happens before the PR merges. A ticket that came back skips this step. Done when the checks passed or only tests belonging to a ticket still open are red, the owner has any other failure, or the ticket came back.
5. **Merge the latest project branch, then land.** For a ticket that passed, in `.worktrees/fix-<n>`, `git fetch origin`, merge `origin/<project branch>` and push. `fix-<n>` holds only this session's records (a reproduction, a harness, a sketch, a glossary or ADR) and this ticket's e2e tests and feature files, so a conflict is in them, and you resolve it with the **resolving-merge-conflicts** skill. Then run `dispatch.sh land <n>` from any checkout of this repository. A ticket that came back goes straight to `land`, which closes its watch and leaves it in `needs-triage`. `land` prints what it did; stderr names anything it left standing. Exit 1: tell the owner each line stderr names. Exit 2: nothing landed and the ticket is still passed, because `scripts/check` could not run on the merge (a missing tool, service or dependency) or is missing; fix what stderr names, then run `land` again. A merge conflict or a red `scripts/check` counts as `bounced` on its summary line, and `land` leaves that ticket in `needs-triage`: tell the owner which ticket and what the `ticket.bounced` event names. When the owner picks it again, start at step 1; the worker merges the new `fix-<n>` in at its integration and resolves the conflict there. Done when `land` exits 0, or the owner has its lines.
6. **Open the pull request.** Handle findings before the retrospective, so its gather does not mistake this step's pending work for orphaned children. Only for a ticket `land` merged, first handle its open `finding` children, the entries in `events.py fold <n>`'s `children` whose `kind` is `finding` and which have no `resolution`. Judge each in order, first match wins:
   - Apply **Step 0, before you classify at all** under Run a night's **4. The closing pass** (`playbooks/run-a-night.md`). Run `dispatch.sh route <n> <child> stale invalid` for a finding that never held, or `dispatch.sh route <n> <child> stale fixed-elsewhere` for one resolved elsewhere.
   - If an already-open ticket covers the same problem, run `dispatch.sh route <n> <child> became-ticket <that ticket>`.
   - Otherwise, hand the child to the owner. Keep its opening ``A `<kind>` child of #<n>`` line and finding evidence, and write `## Problem` with `Playbook: <name>` as its first line, omitted when the kind is unclear. Add `needs-triage` with `gh issue edit <child> --add-label needs-triage`. Keep its `mmw:child` kind and leave it unrouted. The owner's Go runs **Ready**, which changes its kind and records the route.

   Fix no code here. Every change outside a night goes through a worker on the owner's go, as `../references/handling-a-request.md` `## Playbooks` says. For each route, exit 1 means run the same command again; exit 2 means nothing was done and stderr says why.

   After handling the findings, run Retrospective (`playbooks/retrospective.md`) with `--ticket <n>` before opening the PR. Run it also when the ticket came back or bounced and will open none. Resume the retrospective on its brief wake and carry its result or failure into the PR or reply.

   Then run Opening a PR (`playbooks/opening-a-pr.md`) from `fix-<n>`, putting each open child, including findings awaiting the owner, in the page's Not done and left over block and in the record. A ticket that came back or bounced opens none: tell the owner what it tried, where its commits are, and that it waits in `needs-triage`. Done when every finding has a route or awaits the owner in `needs-triage`, and Opening a PR is done, or the owner knows the ticket came back or bounced.

**Reply:** the pull request's link, or what came back and why; each line `land` left on stderr; anything that failed and is not on the page.
