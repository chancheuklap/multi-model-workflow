### Retrospective

**You own the retrospective of one run, from its gathered evidence to analyst conclusions recorded on registrations.** Run after a night or one ticket, or on the owner's request for a named spec or ticket. Every registration and signal must have a recorded conclusion. This playbook executes none of those conclusions.

This playbook investigates a run's unresolved problems and records the analysis for a separate owner-approved backlog review. Opening a PR shows the recorded-row counts and links the receipt.

On re-entry, read the run's retrospective progress comment for its material directory and batch identifier before starting again. Use `dispatch.sh brief show <batch>` on an existing batch. If analysts are still running, end your turn and wait for its wake; if all have reported or been lost, continue at **Check and apply the answers**. If a send was interrupted before its identifier was recorded, inspect the existing batch records described by the `dispatch` skill's `scripts/briefs.py` header, matching the sender and the run's material path in its briefs, and adopt that batch. Start no second batch for the same unfinished retrospective. A recorded batch that is absent with no preserved answers is a failure, not a fresh run.

`retro.py` below is the `retro` skill's `scripts/retro.py`; `dispatch.sh` is the `dispatch` skill's `scripts/dispatch.sh`. Pass the product and MMW repository slugs once each to gather, removing duplicates. When the product repository is MMW itself, pass its slug only once. Use the installed skills. In a self-hosted run, the repository's `AGENTS.md` `## Self-hosting boundary` keeps that runtime frozen.

1. **Gather the run.** From the product checkout, run `retro.py gather --spec <spec> <distinct owner/repo>… --out <material directory>` for a night, or replace `--spec <spec>` with `--ticket <n>` for one ticket. Preserve the generated `context.json` and comment on the run with the material directory before dispatch. If every angle has no material, go to **Record the outcome** with zero recorded rows.
   Done when the material paths and counts are available, or the failure goes to **Record the outcome**.
2. **Send the analysts.** Write one brief for each angle with material. Its `## Task` opens with the corresponding sentence below, then asks for that angle's sorting. `## Known` names the material file, the generated context path, and the run's circumstances. `## For` says each analyst row will be recorded on its registration, without executing its conclusion.

   | Angle | First sentence of `## Task` |
   | --- | --- |
   | 判断 | Follow the retro skill's references/judgement.md. |
   | 环境 | Follow the retro skill's references/environment.md. |
   | 流程 | Follow the retro skill's references/process.md. |

   Send all these briefs in one batch with `dispatch.sh send retro-analyst --follow "the brief" <brief>…`, record the returned batch identifier in the run's retrospective progress comment, then end your turn. The dispatch footer tells each analyst how to report its answer.
   Done when the batch is started and your turn has ended, or the failure goes to **Record the outcome**.
3. **Check and apply the answers.** On `brief <batch> done`, follow steps 1 through 3 of the dispatch skill's `## On waking` to read the answers and ack the wake. Leave `## Problems` registration to apply, which registers these as `retro-signal`; running the generic waking step's add first would register each occurrence twice and undercount new registrations. Open every row's evidence and check its conclusion against it. Keep each validated row as written. Return invalid or conflicting rows to the analyst for correction; do not rewrite the analyst's conclusion. Account for each gathered signal, including new registrations in `## Problems`, before running `retro.py apply <answer file>… --context <material directory>/context.json`. If a session was lost without an answer, record the missing angle as a failure rather than treating it as empty material. Close the brief batch with `dispatch.sh brief close <batch>` once its answers are preserved and no longer needed there.
   Done when every registration and signal has a checked conclusion and apply records each accepted row, or the failure goes to **Record the outcome**.
4. **Record the outcome.** Read the `spec.retroed` or `ticket.retroed` receipt apply wrote. For a gather with no material, write an empty answer table in the material directory with the retro skill's `## Analyst instructions` columns and `## Problems` set to `None`, then run apply with that answer and the generated context to record zero rows. Keep the receipt's evidence limits, row counts by conclusion and problem list in the result. These counts describe recorded analysis, not executed merges, rejections or proposals.

   If any step failed, record the command and concrete reason. Use the `verify-ticket` skill's `scripts/events.py emit` to build the run's `spec.retroed` or `ticket.retroed` with `result=unrecorded` and `reason`, then post its comment body to the spec or ticket with `gh issue comment --body-file <file>`. If recording also fails, put both failures in the reply or PR. A retrospective failure does not block merging. Before returning the result, run `retro.py backlog <distinct MMW and product owner/repo>… --out <material directory>/backlog`. When its printed count of assessments since the last merge reaches 20, include a suggestion to run **Merging the lesson backlog** in the result for the calling playbook. Do not start that playbook without the owner's approval. If backlog fails, report the failure instead of guessing its count. Return the receipt to the calling playbook for its page, without a reply of this playbook's own; a standalone retrospective ends with its reply below.
   Done when every registration and signal has a recorded conclusion in the receipt, including a zero result, or the failure and its missing coverage are recorded for the owner.

**Reply:** the number of recorded rows by conclusion and the receipt link; the count of new registrations; each recurrence after the owner's refusal; any failure or unreadable evidence. State that analyst conclusions were recorded, not executed, and that the owner decides what to do in a separate backlog review.

Run `retro.py backlog` for the distinct MMW and product repositories as **Record the outcome** specifies. When it reports at least 20 assessments since the last merge, suggest an owner-approved batch review using **Merging the lesson backlog**, `playbooks/merging-the-lesson-backlog.md`.
