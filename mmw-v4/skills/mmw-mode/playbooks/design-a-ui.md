### Design a UI

**You own the design decision. The prototype skill builds it; the owner confirms it on the running page.**

A direct request returns the confirmed winner and feature description. Called during development or contract correction, return to that calling step on its existing issue and effort branch. Design confirmation settles appearance and interaction; implementation authority remains the caller's recorded scope.

1. **Establish the UI question.** Read the requested pages, actions, states and settled constraints. Keep the supplied issue, effort branch and affected-feature result. For a direct request missing its record or branch, use **to-tickets**, **Open the preparation record**, with `Playbook: Design a UI`; opening it authorizes design assets. If relevant current features are unidentified, call **maintain-verification-skill**, **Find affected features**. With no product verification skill, use the actual product and sources without starting whole-product maintenance.
   Done when the UI scope, preserved behavior, sources and working branch are known.
2. **Construct the runnable alternatives or current winner.** Read the **prototype** skill and follow its **UI** branch with the scope, checkout, settled decisions and prior candidates or winner. That method prepares a missing local environment and returns runnable pages, variant URLs, files and unanswered UI questions. Give the owner the page to operate.
   Done when the owner can operate the alternatives or current winner in their product context.
3. **Iterate with the owner.** The owner selects the base or combination. Follow the prototype UI method to fuse the selected parts into `winner/`, retaining `candidates/<n>/`. Keep arena's synthesis note on the requesting ticket or in the reply. Continue on the same winner, one owner question per round, committing each round. A settled direction needs no fresh set of designs; a remaining uncertain component may use a small arena.

   Walk each action and API fake call to establish its visible result, permissions, errors and recovery. For an owner decision, read **grilling**; for a settled term or qualifying decision, read **domain-modeling**. Use research or the prototype's LOGIC / EXP method for facts or runnable questions. Reach these methods only when the answer changes what the owner sees or does. Record those answers on the existing ticket, or in decision tickets on the existing map. Return other data, storage, business-rule, security, integration and performance questions to the development caller as unanswered preparation. Their presence alone does not expand a design-only request.
   Done when the selected winner demonstrates the settled UI rules. While an owner response is pending, preserve the issue and same prototype, return the question and stop this step until the response arrives.
4. **Reconcile and freeze the design.** Merge the latest project-branch code so the winner runs on the current product. Read the closed decision tickets or the existing ticket's answers and cited spec sections. Demonstrate each visible rule, including states reached through a state URL when actions cannot create them. Decisions govern rules, the glossary governs names, and the prototype governs appearance and interaction; update a lagging prototype. Resolve any remaining UI-changing question by the preceding iteration step.

   Read **create-verification-skill**'s `references/feature-map.md` for the feature-file format. Write this design's account of demonstrated behavior from the winner, closed decisions and glossary, in the UI's language with the prescribed English headings. The owner confirms the real running winner once. Until that confirmation, return the running winner for their trial and remain at this step. Commit the feature description before tests on the effort branch.
   Done when the owner has confirmed the running winner and its feature description is committed before acceptance tests.
5. **Return this design to its caller.** Return the winner's exact path, feature-file paths, recorded UI decisions, API fake as a draft interface, and the unanswered non-UI questions. The development or ticket-writing caller finalizes the interface contract and aligns the fake before preparing acceptance. Prototype mount points stay for implementation; ticket slicing owns their removal. A direct design-only request ends here. A call inside Develop a change or a contract correction resumes that calling step, without opening a new preparation.
   Done when the caller has the confirmed design and its remaining preparation, or the owner has the pending response needed to finish it.

**Reply:** the runnable checkout and page, confirmed winner or pending owner response, feature-file paths, this round's changes, and the non-UI questions handed back.
