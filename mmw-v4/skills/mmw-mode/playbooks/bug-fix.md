### Bug fix

**You own the diagnosis and the ticket that carries it. A worker writes the fix, and you prove it on the product.**

Be scientific. Every shipped line traces to runtime evidence. Belt-and-suspenders that "might help" is a hypothesis, not a fix. It does not ship. When evidence refutes a hypothesis, revert what it motivated. The smallest change the evidence justifies ships, nothing more. Skip a step only with a stated reason.

1. **Open the ticket.** Open a ticket and its `fix-<n>` as `../references/ticket.md` `## Opening a ticket` says, with `Playbook: Bug fix` and the symptom in the owner's words under `## Problem`. A ticket already open keeps its number and opens only the `fix-<n>` it lacks. Done when the ticket is open and `fix-<n>` is on origin.
2. **Build a feedback loop.** A tight pass/fail signal that goes red on this bug is what finds the cause: bisection, hypotheses and instrumentation all consume it, and no amount of reading code replaces it. Spend most of the effort here. Find the affected existing features as `../references/feature-map.md` says. For a product with a `verify-<product>` skill, first check the affected feature file's `Gotchas`, then read Launch and Drive to reproduce. Reproduce it yourself on the matching surface via the control skill, even when a debug or instrumentation protocol says to ask the owner to reproduce. A loop never reaches a real customer, real money or production data: it drives a test account, a sandbox or a copy. A UI bug in a product with no `.agents/skills/verify-<product>/` stops here: ask the owner to name the `create-verification-skill` skill for that product, since generating it starts only when the owner names it; do not generate it yourself, and do not write the ticket without its e2e criteria. For a UI bug, read the `verify-<product>` skill's Read first, Rules and Evidence, and turn the loop into a failing e2e test in a new file belonging only to this ticket under `tests/e2e/<product>/`. Register that file on the affected feature file's `Tests:` line in the feature map, creating the feature file if missing, and commit and push the test and registration together on `fix-<n>`. This loop is AC2, after AC1, the worker's regression test; when step 6 finds no seam, it is AC1, the only criterion. Use Cleanup when you finish with a product you started. Ways to build the loop, roughly in this order:
   1. A failing test at whatever seam reaches the bug: unit, integration, end to end.
   2. A curl or HTTP script against a running dev server.
   3. A CLI invocation with a fixture input, diffing stdout against a known-good snapshot.
   4. A headless browser script that drives the UI and asserts on the DOM, the console or the network.
   5. A replay of a captured trace: a real request, payload or event log saved to disk and replayed through the code path in isolation.
   6. A throwaway harness: a minimal subset of the system (one service, mocked dependencies) that runs the bug's code path with one function call.
   7. A property or fuzz loop: for "sometimes wrong output", run a thousand random inputs and look for the failure.
   8. A bisection harness: when the bug appeared between two known states (a commit, a dataset, a version), automate "boot at state X, check" so `git bisect run` can drive it.
   9. A differential loop: the same input through the old and the new version, or two configurations, outputs diffed.
   10. A human in the loop, last: when a person must click, drive them with `scripts/hitl-loop.template.sh`, so the loop is still structured and its output feeds back to you. Ask the owner only with a stated, specific reason the control surface cannot reach the target, and only after driving it as far as it goes.

   Then tighten it: faster (cache setup, skip unrelated start-up, narrow the scope), sharper (assert the exact symptom, not "did not crash"), more deterministic (pin time, seed randomness, isolate the filesystem, freeze the network). For a bug that comes and goes, the goal is a higher reproduction rate, not a clean repro: loop the trigger a hundred times, run it in parallel, add stress, narrow timing windows, until the rate is high enough to debug against. When no loop can be built, stop and say so, with what you tried, and ask the owner for access to an environment that reproduces it, a captured artifact with its secrets redacted, or leave to add temporary production instrumentation. Do not go on to hypotheses without a loop. Commit the loop on `fix-<n>`. Done when you can name one command, already run at least once with its output shown, that drives the bug's code path and asserts the owner's exact symptom, gives the same verdict every run, finishes in seconds for a non-e2e loop, and runs unattended.
3. **Reproduce + minimise.** Run the loop and watch it go red. Confirm it shows the failure the owner described, not a nearby one, that it reproduces across runs, and capture the exact symptom (the error, the wrong output, the timing) for the check after the fix. Then cut inputs, callers, configuration, data and steps one at a time, running the loop after each cut, and keep only what the failure needs: a minimal repro leaves fewer parts to suspect and becomes the regression test. Done when every remaining element is needed, so removing any one turns the loop green.
4. **Hypothesise.** Before testing any, list possible sources and narrow them as **principle-fix-root-causes** says; seed them with the **how** skill over the affected subsystem and the **why** skill for regression history. Each hypothesis states its prediction: "if X is the cause, changing Y makes the bug disappear, and changing Z makes it worse". One with no prediction is sharpened or dropped. Show the ranked list to the owner and go on without waiting: they may know one is already ruled out. Done when every hypothesis left carries a prediction and the list is ranked.
5. **Instrument.** Test the predictions by binary search: each pass, take the split that cuts the most remaining problem space, get runtime evidence, eliminate. Change one variable at a time. Prefer a debugger or REPL to logs, and targeted logs at the boundaries that tell hypotheses apart to logging everything; tag every debug log with one prefix, such as `[DEBUG-a4f2]`, so cleanup is one `grep`. Before naming a cause, read the code on the path per **principle-read-before-you-conclude**. When the host can schedule its own wake-up, use it to keep a long or stubborn hunt going. A slowness rather than a wrong result is the Perf issue playbook's. Done when one hypothesis survives and runtime evidence confirms its mechanism.
6. **Plan the fix.** A question of code shape goes to the **prototype** skill's `## Pick a branch` first. When the fix needs new code beyond the bug itself, follow **principle-start-from-what-exists**. Find the seam where a regression test exercises the bug as it happens at the call site. When no such seam exists, that is itself a finding: the structure keeps this bug from being locked down. Register it with the **register-problem** skill, its suggested direction a Refactoring, and this ticket goes on with the step 2 command as its criterion. Done when the fix is planned and its seam is named, or the missing seam is registered.
7. **Write the ticket.** First clean up after yourself: remove every tagged debug log (`grep` its prefix), and delete each throwaway script that is not the step 2 loop. Then fill the ticket in as `../references/ticket.md` `## Opening a ticket` says. **What to build** states the symptom, the cause with its runtime evidence, the hypothesis that held, and the fix planned in step 6; a sketch from the **prototype** skill is a baseline under **Read first**. **Seam** is the seam of step 6, or says there is none. The first acceptance criterion is a regression test the worker writes at that seam from the minimised repro of step 3, which must fail on the project branch; the second is the step 2 command. With no seam, the step 2 command is the only one. **What to build** asks for the failing test to be committed before the fix (**principle-sequence-verifiable-units**), which the worker does with the **test-audit** skill. Done when every section below `## Problem` is filled.
8. **Hand it back.** As `../references/ticket.md` `## Handing it back` says. Done when the owner has said go and One ticket runs, or the ticket is in `needs-triage` or closed.

**Verify on the same surface.** One ticket step 4 runs this once the ticket passed: the step 2 loop on the original scenario, not the minimised one, in `.worktrees/issue-<n>`. The original repro no longer reproduces. "Inconclusive" or wrong-surface is not a pass. Flag it. Unit tests show branch behavior, not bug absence.

**A ticket that came back.** When a ticket its worker handed back (a `ticket.returned` event) is picked from `needs-triage`, read why on the ticket and go back to step 4 with that evidence.

**Reply:** the symptom and the loop that reproduces it, its red output verbatim; the ranked hypotheses and the one the evidence left; the root cause with its runtime evidence; the planned fix and its seam, or the Refactoring ticket opened for a missing one; the criteria; what the ticket leaves out.
