### Bug fix

**You own the diagnosis, the ticket that carries it, and the proof on the product. A worker writes the fix.**

Be scientific. Every shipped line traces to runtime evidence. Belt-and-suspenders that "might help" is a hypothesis, not a fix. It does not ship. When evidence refutes a hypothesis, revert what it motivated. The smallest change the evidence justifies ships, nothing more.

1. Reproduce it yourself on the matching surface via the control skill (Non-negotiables), even when a debug or instrumentation protocol says to ask the user to reproduce. Ask the user only with a stated, specific reason the control surface cannot reach the target, and only after driving it as far as it goes. If it won't reproduce directly, synthesize the trigger, tighten conditions, or instrument until it fires.
2. Binary-search the cause. Form the candidate hypotheses, then rule them out until one survives. Seed them with `how` over the affected subsystem and the **why** skill for regression history. Each pass, take the split that cuts the most remaining problem space, get runtime evidence, eliminate. When program state is unclear, add instrumentation or logging and read it as the code runs. Don't guess. When the host can schedule its own wake-up, use it to keep a long or stubborn hunt going. Confirm the surviving *mechanism* with runtime evidence before the step-3 architect fan-out. Read the code on the path before naming a cause (**principle-read-before-you-conclude**).
3. Plan the fix. If it crosses a function boundary, `architect` first. When the fix needs new code beyond the bug itself, look for what already does it (**principle-start-from-what-exists**).
4. Write the ticket and send it. Write one ticket in the shape of `../references/ticket.md`, with `None` under **Parent**. **What to build** states the symptom, the cause with its runtime evidence, and the fix planned in step 3; an `architect` sketch is a baseline under **Read first**. **Seam** is where a regression test exercises the bug as it happens at the call site; when there is no such seam, say so there, since that is itself a finding. The first acceptance criterion is that regression test, which must fail on the project branch; when the step 1 reproduction runs unattended and gives the same verdict every run, it is the second. With no seam there is no regression test, and the step 1 reproduction, made to run unattended with the same verdict every run, is the first. **What to build** asks for the failing test to be committed before the fix, so the failing repro lands before the fix in git history: the canonical **sequence-verifiable-units** principle skill, the failing test first and the fix on top, which the worker does with the **tdd** skill. Publish it with `gh issue create`, with the labels `mmw:ticket`, `ready-for-agent` and one worker label (`junior-worker`, or `senior-worker` for silent-failure work), creating any the repository lacks as `../references/github-issues.md` says, then run `verify-ticket.py <n> --lint` of the **verify-ticket** skill and fix every `ERROR`. Then run **One ticket** of the Run a night playbook (`playbooks/run-a-night.md`) on it: it cuts the ticket's own branch, sends the worker, and ends your turn. Done when the ticket is published with no `ERROR` and the worker is sent.
5. Verify on the same surface. Woken by `#<n> ticket.passed`, run the step 1 reproduction on the original scenario, not the minimised one, in the ticket's worktree (`.worktrees/issue-<n>`). The original repro now passes. "Inconclusive" or wrong-surface is not a pass. Flag it. Unit tests show branch behavior, not bug absence. When the repro still fails, the ticket did not capture the cause: land nothing, tell the user what the repro shows, and go back to step 2 with that evidence (**principle-fix-root-causes**). Woken by `#<n> ticket.returned`, the worker handed it back: read why on the ticket, tell the user, and go back to step 2. Done when the repro passes in the ticket's worktree, or you are back at step 2.
6. Deliver it as **One ticket** steps 4 and 5 say: `land`, then one pull request, merged on the user's yes.

**Reply:** what was broken, root cause, the fix (the ticket and the pull request), how you verified. Paste failing-then-passing repro output verbatim.
