### Opening a PR

**You own one pull request, from its text to its merge on the owner's yes.**

Run by One ticket step 6 and Run a night step 6, once the change has landed on its branch: `fix-<n>` for one ticket, the night's branch for a night. The pull request opens from that branch on origin as it stands. Its commits are the workers' and the merges `land` recorded, so nothing here rebases or rewrites them. Use GitHub CLI (`gh`) for every operation.

1. **Write it.** Choose the title as **Titles** below says. Draw the page with the **diagram-design** skill as **The owner's page** says, then write the body as **The record** says. The summary sentence and the page's words follow `references/owning-a-task.md` `## Writing the reply` and the **unslop** skill. Done when the title is chosen, the body is in a file, and the page is drawn.
2. **Open it and give the owner its link.** `gh pr create --base <project branch> --head <fix-<n> or the night's branch> --title "<title>" --body-file <file>`. Open it ready, never as a draft: omit `--draft`. Run `gh pr view <number>` before you refer to its state. Add the pull request's link to the page's Links block. Done when it is open, the page links back to it, and the owner has its link.
3. **Before merging, read its checks and comments.** Read the head SHA with `gh pr view <number> --json headRefOid` before checking. Run `gh pr checks <number>`; wait for a check still running with `gh pr checks <number> --watch`. Then settle each of these:
   - **A red check.** Tell first whether it is a flake, a project branch that moved on, or this change. A flake fails on a commit where the same check passed before, or passes when run again once: run the failed job again (`gh run rerun <run> --failed`). A project branch that moved on: `git merge-base --is-ancestor origin/<project> origin/<branch>` fails; merge `origin/<project>` into the branch as the **resolving-merge-conflicts** skill says and push it. This change: a fix that needs code, as below.
   - **A review thread or a comment.** Check its claim against the code first, as `../references/bugbot-triage.md` sorts it. One that holds needs a fix, as below; once it is pushed, reply with the commit and resolve the thread. One that does not hold you answer with the specific evidence that disproves it, and resolve the thread. One the reference sends to the owner you put to the owner.

   A fix that needs code is never written here. By day, open a ticket for it as `../references/ticket.md` says, its `## Problem` quoting the check or the comment, but no `fix-<m>` of its own: run One ticket steps 1 to 5 on it from `.worktrees/fix-<n>`, so it lands on `fix-<n>` and this pull request shows it. For a fix ticket that `land` merged, handle its open `finding` children using the three finding branches of One ticket's **Open the pull request** step (`playbooks/one-ticket.md`). Skip that fix ticket's retrospective and its own PR. Put findings awaiting the owner in the page's What the owner decides and Not done and left over blocks and in **The record**. At night, the closing pass fixes it, as Run a night step 7 says.

   Whenever this step changes the pull request, including a pushed fix, a routed finding or a body edit, update the same page at the same address and refresh **The record** with `gh pr edit <number> --body-file <file>`.

   Read `headRefOid` again after settling the checks and comments. If the head changed, repeat this step against the new head. Carry the checked head SHA into the owner's approval and **Merge on the owner's yes** below. Done when every check is green, every thread is answered, each merged fix ticket's finding has a route or awaits the owner in `needs-triage` and on its page, and the checked head SHA is recorded, or the owner has what is left.
4. **Merge on the owner's yes.** By day, follow the repository's merge rules in `AGENTS.md` or the rules file it names. Use the checked head SHA from **Before merging, read its checks and comments**, the version the owner approved. First `git worktree remove .worktrees/fix-<n>`, since every commit on it is on origin and a branch still checked out cannot be deleted. When the repository specifies a merge subject, run `gh pr merge <number> --merge --delete-branch --subject "<repository-required title>" --match-head-commit <checked head SHA>`. Otherwise run `gh pr merge <number> --merge --delete-branch --match-head-commit <checked head SHA>`. If the head changed, return to **Before merging, read its checks and comments** and obtain the owner's approval for that version. Then close each issue the ticket's `## Problem` quotes with a comment linking the pull request. The body's `Closes` lines close nothing: GitHub closes an issue by them only on a merge into the repository's default branch, and each ticket closed when it passed. At night, `finish` merges it, as Run a night step 7 says. Merge with `--merge`, never a squash: each ticket's commits and the merge `land` recorded stay in the history. Done when it is merged, or the owner has its link and has not said yes.

**Titles.** Follow the PR title format in the repository's `AGENTS.md` or the rules file it names. For example, a repository may require a strictly increasing `vMAJOR.MINOR.PATCH` title and that version as the merge subject. When the repository specifies no title format, use these defaults. By day, use Conventional Commits `type(scope): subject`, no trailing period. Type such as `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, or `perf`. Use the changed area, such as `dispatch` or `mmw-mode`, as the scope. Subject is short, imperative, and names a real symbol when one carries the change, for example `fix(dispatch): refuse a finish whose pull request has an open thread`. A night's pull request is titled `Night #<spec>: <the spec's title>`.

**The record.** The body identifies the change and preserves links to its evidence. The owner reads the page, not a briefing for a code reviewer. Write fixed lines in this order, with no prose sections:

- Line 1: the owner's page address or local path.
- One sentence in the owner's language saying what the change does.
- One `Closes #<n>` per ticket carried by the pull request, so GitHub lists it on each ticket.
- Per ticket, its closing verdict, `ALL MET` or `HANDOFF REQUIRED`, met of total, and the baseline run's met count, with a link to its closing comment.
- Each landing's recorded compare link.
- The calling playbook's check summary lines: a night's `scripts/check --all` line and each product-target e2e summary line, including storage assertions.
- Each open child, handed-back ticket or finding awaiting the owner, with its number and state.
- The retrospective receipt's link and count of new proposals, or its recorded failure.
- At night, the `NIGHT SUMMARY` verbatim.

**The owner's page.** One page is the owner's reading and decision place for this pull request. Publish it as the **diagram-design** skill's `SKILL.md` `### Where the page goes` says. Keep its address on line 1 of **The record**. Use the same seven blocks, in this order, on every pull request:

1. **What the owner decides.** One card per decision, each with a one-line recommendation. Cover merging itself, each new retrospective proposal, each child, finding or ticket waiting on the owner, each rejected alternative the owner would otherwise ask about, and any consequence that cannot be undone.
2. **What changed.** Before and after side by side at one scale. When a screen changes, show both screenshots. Start the product as the `verify-<product>` skill's Launch says and capture with the **control-ui** skill: before in a project-branch checkout, after in the `fix-<n>` or night-branch checkout. Do not run e2e again for the screenshots: the acceptance test is red before the change, and e2e captures only the failing step. Otherwise draw the flow or structure before and after.
3. **What the merge touches.** Draw the product's parts with the touched ones marked, beside whether the change can be taken back.
4. **Evidence.** Show each acceptance criterion as one mark, red before from the baseline run and green after from the final run, read from the tickets. Preserve actual results, including criteria already green before work or still red after it. For a performance change, show one primary number with its unit, before → after. Give the command the owner starts the product with, from the `verify-<product>` skill's Launch in the `fix-<n>` or night-branch checkout. For a desktop product, state that this is Mac development mode and real-device acceptance is separate. Use the e2e results and `trace.md` as evidence.
5. **Not done and left over.** Each open child, handed-back ticket and red test belonging to an open ticket, each with its number and state. When the spec or ticket says that another product's e2e test intercepts the landed interface with `browser.route`, include the follow-up to invoke **maintain-verification-skill** after landing for that product's `verify-<product>`. Link the full night ticket map from Links rather than repeating it here.
6. **Retrospective.** Draw the result named by `playbooks/retrospective.md` `**Reply:**` as numbers. Its new proposals are the cards in What the owner decides. Preserve the receipt's links, evidence limits, reminders and any failure beside the relevant number.
7. **Links.** The pull request, the tickets and the task board.

No file, function or code on the page, apart from the product launch command in Evidence. For UI labels, use the feature names in the product's feature map. Let pictures carry the content. Outside labels inside figures, the page's sentences total about 300 characters of the owner's language at most, so the owner can read the whole page without a long text report. Keep explanations beside what they explain, per **principle-everything-at-hand**.

**Reply:** the pull request's link; how each check and thread of step 3 was settled; that the merge waits for the owner's yes, or that it is merged. It goes into the reply of the playbook that ran this one.
