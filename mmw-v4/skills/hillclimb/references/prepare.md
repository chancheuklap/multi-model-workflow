# Prepare the climb

Keep the caller's issue and effort branch. A long experiment is not by itself a spec; return the workload, frozen harness, target and hypotheses to the caller's preparation.

1. Ground the workload and architecture before choosing the metric. Reuse the established target model; call **how** only for missing understanding needed to choose the workload. Name the realistic workload dimensions that can move the result (data size, history, state, concurrency), and select a case that reproduces the user's complaint. If no case reproduces it, fix the repro instead of hillclimbing. Then fix one metric, the direction that counts as better, and a checkable stop predicate that pairs a target with a floor on attempts so a lucky early win can't end the run (the example "at least 50% better than baseline and at least 10 iterations" is this shape). Use the user's numbers when given, otherwise agree them. Done when the metric, its direction and the stop predicate are written down.

2. Build the measurement harness, prove its sensitivity, then freeze it (**principle-build-the-lever**). Run contrasting realistic workloads and confirm the target case reproduces the symptom while easier cases separate as expected. If the harness cannot distinguish them, revise the workload or metric. Vet the harness with the **benchmark-checklist** skill before you freeze it, and make it print its error count and a count of the work done. Once frozen, one repeatable command emits the metric, sampled enough to clear the noise (median of N, not a single run). Record the baseline metric and a green run of the regression gate (the tests that must keep passing) before any change. Commit the frozen harness on the supplied effort branch. Done when the harness is frozen and committed, with the baseline and a green gate recorded.

3. Record the baseline as Attempt 0 in the supplied preparation record, using this skill's **Attempt record** format. The ticket writer carries that baseline to the execution ticket when it is published. Done when the baseline comment and its source are available.

4. Ground each hypothesis in the workload and architecture model, so it names a specific mechanism ("defer X off the boot path because it blocks first paint"), not "try memoizing something". For a perf metric, order hypotheses by the performance mantras in the **perf-issue** skill's `references/diagnose.md`. Borrow only their order, not that step's stop rule. Done when the hypotheses are ranked.

5. **Supply the executable plan.** Read first names the frozen harness, Attempt comments, workload and architecture model, ranked hypotheses, and this skill's implement / verify entries. The criteria are the frozen harness printing its target-only success marker; the regression gate; and the attempt floor counted from comments with `gh api`. Return those materials for the caller to write the independent ticket or spec tickets.
   Done when every required baseline and command is available on the supplied effort branch and the ticket holds Attempt 0.
