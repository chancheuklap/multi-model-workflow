# Diagnose the slowdown

Use the caller's permitted observation surface and return evidence. A diagnosis does not authorize durable product edits or an implementation ticket. Retain the same workload for comparable results.

1. **Capture a baseline trace** via the matching control skill. Vet the baseline, and each later number, with the **benchmark-checklist** skill. Done when the baseline number is vetted and its command and artifact are recorded.

2. **Find the cause.** `how` to ground hypotheses. Don't claim a perf ceiling without running it first. Before naming a cause, read the code on the hot path per **principle-read-before-you-conclude**.
   Use the performance mantras to rank trace-grounded opportunities, cheapest first. A diagnostic call returns those opportunities; applying one belongs to authorized implementation:
   1. Don't do it. Stop work whose result nothing uses rather than cheapening it.
   2. Do it, but don't do it again.
   3. Do it less.
   4. Do it later.
   5. Do it when they're not looking.
   6. Do it concurrently.
   7. Do it cheaper.

   When preparing an authorized change, stop at the earliest mantra that meets the supplied target; a diagnosis does not invent an optimization target. Done when the trace shows where the time goes and which mantra answers it.

Return the workload, vetted baseline, trace, mechanism and the mantra supported by the evidence.
