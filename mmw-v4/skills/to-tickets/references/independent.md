# Independent ticket

Use this entry for one prepared change outside any spec. Keep the supplied issue, Problem, effort branch, decisions and execution authority. The full format and criterion-classification method are in `references/ticket-format.md`; read them before writing.

1. **Read the prepared work.** Read its goal, settled decisions, method results, baselines, glossary and relevant ADRs. Reuse the supplied affected-feature list; when relevant existing features are not identified, call the **maintain-verification-skill** skill's **Find affected features** entry and return here with their names, paths and changed or preserved behavior. For a directly requested ticket missing its problem record or branch, use this skill's Open entry and return here. Record an actual calling playbook only when one exists. A called entry returns a missing prerequisite to that caller. A change needing coordinated units returns that sizing prerequisite to its preparation caller. For a directly requested ticket, return the needed spec and its reason to the owner; this entry does not expand that request into a batch.
   Done when this independent change's scope, sources and remaining prerequisites are known.
2. **Write the plan and tests.** For a new UI design, take the final interface contract from the governing spec when present; for an independent change, finalize it from the settled requirement and API fake here, using **grilling** only for unresolved decisions. Align the API fake before calling generation or acceptance. Reuse an already finalized contract. Read the relevant project-local product method and prepared evidence. For a supported product that must be exercised, call **create-verification-skill**, **Generate and prove**, only when its reusable skill or required launch and drive capability is missing. Supply the product, checkout, scope and actual baseline. Return here with its actual method, command, evidence and any pending product proof. For UI work on a supported surface, reuse matching prepared acceptance. If this UI acceptance is missing, call **prepare-ui-acceptance** with the product method and this ticket's baseline. CLI and unsupported surfaces keep their matching control or native-test method rather than requiring an e2e engine. A missing capability returns its prerequisite instead of an executable plan claimed ready.

   Read project-local formal methods covering the intended code. If a relevant check skipped updates and no current correspondence evidence was supplied, call **maintain-formal-verification-skill** for that check and baseline before relying on it. When this work has an agreed important rule with material harm and a concrete ordinary-test gap, record that rule and gap in the spec's Testing Decisions or the independent ticket's Seam. When no adequate check covers that rule, call **create-formal-verification-skill** when real implementation exists. Return here with the actual local method, fixed command and evidence. A reported product bug stays in the ticket only when its repair is already agreed; otherwise return the scope decision. A blocked method returns its prerequisite.

   When such a formal check is needed but its implementation does not exist, assign creation to the implementing ticket instead. Specify the agreed rule, selected tool, output paths and executable CHECK, include the verification paths in Owns and name the generator under Read first. Do not cite a future file as an available baseline. If the prepared design cannot determine the tool and command, return that missing preparation before publication.

   Fill every section below the unchanged Problem, with `None` under Parent. Put each owner answer in its own numbered What to build point. Record review judgements as unnumbered constraints in What to build or in a marked baseline under Read first. Numbered implementation points still name their machine criteria as the existing lint requires. Seam names the repository test layer, directory, precedent and how tests reach the needed states; Owns includes any mechanism this ticket builds. Read first names the actual project-local SKILL.md paths for the worker and executor, with their baselines; copy complete commands into CHECK. A new-design UI ticket uses the prepared design/product proof and removes its mount point in its final implementation commit. Repairs and behavior-preserving changes use their prepared real-product baseline, without inventing a winner or mount point. Apply the criterion five questions; put an unresolved owner choice to the preparation caller, or directly to the owner for an independent request, rather than creating a batch quiz.
   Done when every section is filled, all test preparation required by the shared format is committed and pushed, and no review judgement masquerades as a command-decided criterion.
3. **Publish and read back.** Write the full body with `gh issue edit <n> --body-file <file>`, preserving the child preamble when present. Run the **verify-ticket** skill's `verify-ticket.py <n> --lint`, fix every ERROR, and read every WARN once, fixing it or keeping it on purpose. Keep the current kind and queue until the caller applies its authorized handoff; the worker is not started here. Fetch the published body and confirm it holds the prepared plan and test evidence. For a directly requested result without execution Go, add needs-triage after read-back and return, keeping its actual kind. A calling workflow owns its own authorized handoff. A product-scope change returns to the owner through the caller when one exists, otherwise directly.
   Done when the published ticket matches the prepared independent result and its lint has no ERROR.

Return the ticket's name and link, scope, baselines, verification sources, criteria and unresolved owner choices. This entry returns to the caller without opening a watch or PR.
