# Failures and cost

Use the shared judgments in the test-audit skill and apply **principle-fix-root-causes**. A green retry is an observation, not a repair. Keep the original command, inputs, revision, environment and failure visible while diagnosing it.

For an order-dependent failure, reproduce the original shard or predecessor order before running the case alone. Distinguish product behavior, fixture or shared-state leaks, missing completion signals, environment, credentials and platform limitations. Repair the producer or resource owner supported by that evidence. Choose repeat counts from the reproduced failure mode rather than a fixed clean-run quota.

For excessive cost, identify the contract, setup, process or dependency causing it. Measure comparable runs under **principle-explain-the-number** and the benchmark-checklist skill. First remove repeated setup or duplicate proof without losing distinct contracts. Do not import a universal time or line-count budget; the project's actual workload determines what is expensive.

Return repairs within the current authorized task to its normal validation and review. Put work that cannot be completed there into the existing tracker through the caller's route, with original evidence, responsibility and the next executable action. Frozen product acceptance uses the existing contract correction route. A whole-product maintain-verification-skill pass remains owner-requested.

Any exceptional quarantine or deferred proof stays explicit in that existing record, with its exit condition. It cannot establish the deferred acceptance behavior. The caller's approved delivery policy decides what unfinished work permits; diagnosis alone changes no gate or landing authority.

Done when the caller receives the evidenced cause and repair proof, or the unresolved failure, attempted diagnoses, proof limits and durable next step.
