# Diagnose the defect

Be scientific. Every proposed change traces to runtime evidence. A hypothesis is tested, and evidence that refutes it discards what it motivated. Use the caller's permitted runtime or scratch surface. A read-only investigation returns evidence without durable product edits; a preparation caller may authorize temporary instrumentation on its effort branch. Retain a completed loop and diagnosis rather than recreating them.

1. **Build a feedback loop.** A tight pass/fail signal that goes red on this bug is what finds the cause: bisection, hypotheses and instrumentation all consume it, and no amount of reading code replaces it. Spend most of the effort here. Reuse the caller's affected-feature result, or obtain the missing list with the **maintain-verification-skill** skill's **Find affected features** entry. For a product with a `verify-<product>` skill, read the complete project-local SKILL.md and the affected feature file's `Gotchas`, then use Launch and Drive to reproduce. Reproduce it yourself on the matching surface via the control skill, even when a debug or instrumentation protocol says to ask the owner to reproduce. A loop never reaches a real customer, real money or production data: it drives a test account, a sandbox or a copy. Ways to build the loop, roughly in this order:
   1. A failing test at whatever seam reaches the bug: unit, integration, end to end.
   2. A curl or HTTP script against a running dev server.
   3. A CLI invocation with a fixture input, diffing stdout against a known-good snapshot.
   4. A headless browser script that drives the UI and asserts on the DOM, the console or the network.
   5. A replay of a captured trace: a real request, payload or event log saved to disk and replayed through the code path in isolation.
   6. A throwaway harness: a minimal subset of the system (one service, mocked dependencies) that runs the bug's code path with one function call.
   7. A property or fuzz loop: for "sometimes wrong output", run a thousand random inputs and look for the failure.
   8. A bisection harness: when the bug appeared between two known states (a commit, a dataset, a version), automate "boot at state X, check" so `git bisect run` can drive it.
   9. A differential loop: the same input through the old and the new version, or two configurations, outputs diffed.
   10. A human in the loop, last: when a person must click, drive them with the **mmw-mode** skill's `scripts/hitl-loop.template.sh`, so the loop is still structured and its output feeds back to you. Ask the owner only with a stated, specific reason the control surface cannot reach the target, and only after driving it as far as it goes.

   Then tighten it: faster (cache setup, skip unrelated start-up, narrow the scope), sharper (assert the exact symptom, not "did not crash"), more deterministic (pin time, seed randomness, isolate the filesystem, freeze the network). For a bug that comes and goes, the goal is a higher reproduction rate, not a clean repro: loop the trigger a hundred times, run it in parallel, add stress, narrow timing windows, until the rate is high enough to debug against. When no loop can be built, stop and say so, with what you tried, and return the missing access or captured artifact to the caller; temporary production instrumentation needs the owner's permission. Do not go on to hypotheses without a loop. Done when you can name one command, already run at least once with its output shown, that drives the bug's code path and asserts the owner's exact symptom, gives the same verdict every run, finishes in seconds for a non-e2e loop, and runs unattended.

2. **Reproduce + minimise.** Run the loop and watch it go red. Confirm it shows the failure the owner described, not a nearby one, that it reproduces across runs, and capture the exact symptom (the error, the wrong output, the timing) for the check after the fix. Then cut inputs, callers, configuration, data and steps one at a time, running the loop after each cut, and keep only what the failure needs: a minimal repro leaves fewer parts to suspect and becomes the regression test. Done when every remaining element is needed, so removing any one turns the loop green.

3. **Hypothesise.** Before testing any, list possible sources and narrow them as **principle-fix-root-causes** says; seed them with the **how** skill over the affected subsystem and the **why** skill for regression history. Each hypothesis states its prediction: "if X is the cause, changing Y makes the bug disappear, and changing Z makes it worse". One with no prediction is sharpened or dropped. Show the ranked list to the owner and go on without waiting: they may know one is already ruled out. Done when every hypothesis left carries a prediction and the list is ranked.

4. **Instrument.** Test the predictions by binary search: each pass, take the split that cuts the most remaining problem space, get runtime evidence, eliminate. Change one variable at a time. Prefer a debugger or REPL to logs, and targeted logs at the boundaries that tell hypotheses apart to logging everything; tag every debug log with one prefix, such as `[DEBUG-a4f2]`, so cleanup is one `grep`. Before naming a cause, read the code on the path per **principle-read-before-you-conclude**. When the host can schedule its own wake-up, use it to keep a long or stubborn hunt going. A slowness rather than a wrong result is the **perf-issue** skill's. Done when one hypothesis survives and runtime evidence confirms its mechanism.

Return the original loop and output, minimal reproduction, ranked predictions, surviving mechanism, and the evidence and access limits. Clean up temporary instrumentation within the authority that permitted it.
