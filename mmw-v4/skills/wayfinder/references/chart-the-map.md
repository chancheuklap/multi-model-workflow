### Chart the map

**You own the map, not the answers. Charting resolves no ticket by hand.**

A loose idea too big for one agent session, with the way to the destination not yet visible. Use the map body and ticket types in this skill's `SKILL.md`. Never resolve more than one ticket per session, with the exception of research tickets.

1. **Name the destination.** Use the **grilling** skill and the **domain-modeling** skill to pin down what this map is finding its way to: the spec, decision, or change. The destination fixes the scope, so it is settled with the user before you go on. Copy the scope the owner set in their own words when opening the topic into Destination and **Out of scope** verbatim; a scope the owner set is never listed as an open question. Done when the user has agreed the destination.
2. **Map the frontier.** Grill again, **breadth-first** this time: fan out across the whole space rather than deep on any one thread, surfacing the open decisions and the first steps takeable now. **If this surfaces no fog** (the way to the destination is already clear, the whole journey small enough for one session), you don't need a map: stop and propose the Grill with docs playbook of the **mmw-mode** skill (`playbooks/grill-with-docs.md`) instead; the user decides. Done when the open decisions and first steps are listed, or the user has chosen Grill with docs.
3. **Create the map** (labels `wayfinder:map` and `mmw:map`): Destination and Notes filled in, Decisions-so-far empty, the fog sketched into **Not yet specified**. Run `git fetch origin`. Then cut the map's effort branch from the project branch: `git worktree add .worktrees/map-<map number> -b map-<map number> origin/<project branch>`, then `git -C .worktrees/map-<map number> push -u origin map-<map number>`, and name the branch in the map's `## Notes` beside the effort's directory name. Done when the map issue exists with both labels and its effort branch is pushed.
4. **Create the tickets you can specify now** as child issues of the map, then wire blocking edges in a **second pass** (issues need ids before they can reference each other). Write cross-references in that pass too, with real ids: a placeholder `#<n>` auto-links to an unrelated issue. Wiring sorts them into the frontier and the blocked; everything you can't yet specify stays in the fog: the **Not yet specified** section. Done when every ticket is a child of the map with its blocking edges wired.
5. **Answer the research tickets.** Answer each `research` ticket you just created as **Research** in `## Ticket Types` of this skill's `SKILL.md` says, and start them all before you end your turn, so they run at once. As each answer comes back, post its resolution comment as that type says and close the ticket, and append its context pointer to the map's Decisions-so-far, one ticket at a time. Done when every research ticket is closed with its resolution comment and its pointer on the map.
6. **Stop.** Charting is one session's work; it hand-resolves nothing. Tell the user the next move: this skill's resolve entry in a fresh session, with the map's number. Done when the user has it.

**Reply:** the map and every ticket by name, which tickets sit on the frontier and which are blocked, the research tickets resolved with their gists, and what stays in Not yet specified.
