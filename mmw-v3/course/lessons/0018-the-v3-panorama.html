第 18 课 · v3 现状

v3 现状：全部组件，和它们怎样运转

这一页只讲 v3 现在是什么样。下面一张图放下 v3 的全部组件：每一列是一种角色，每条线是一种关系。点任一个组件，右边给出它的原文、步骤和前后连线；点一条「典型路径」，图上亮出那条路径，右边一步步讲它怎样跑。

一段话看懂 v3 怎样运转

你开一个会话。它先读 mmw-mode：Claude Code 和 Codex 在有 .mmw/ 的仓库里由钩子 mode-hook.py 让它读，别处由你输入 /mmw-mode。mode 的路由行按任务把会话分到 24 份 playbook 之一；会话把那份 playbook 的步骤抄进待办清单，一步步做：调用技能、跑脚本、开出别的会话或子代理、读写 GitHub 和 git 上的记录。只有你能定的事，停在你的决定点。每个会话只拿到它这一步要用的上下文：白天讨论的结果写成 spec 和票，几方共享；干活的指引只给干这件活的角色（图 1）。

夜里那一段由脚本调度：dispatch.sh 在 runner 里开出 worker 和 reviewer 会话，它们的第一句话点名 Work a ticket 或 Review a ticket；每一步写成票上的事件，relay.py 读到事件就叫醒等它的会话。15 条原则不单独执行，做某个决定时才读。

你开会话→mmw-mode 路由→playbook 的步骤→技能 · 脚本 · 会话 · 子代理→GitHub 与 git 上的记录→你：决定点 · 验收

图里有什么

全景网

从左到右大致是时间顺序：入口、路由、playbook、你的决定点、干活的会话与子代理、技能、程序、留下的记录，最右是原则。形状和左上角的小标签说明它以什么形态存在，颜色同课程里各类组件的颜色。默认只显示路由、交接、等你、开出、照着做、叫醒、拿到七类连线；点一个组件会显示它的全部连线。「拿到」从一个会话或子代理连到它拿到的上下文，线上写着哪一步。

上下文：谁共享、谁独有、哪一步拿到

v3 给每个 agent 的上下文按两条线分。白天讨论定下的东西写成记录，几个角色共享；怎样干活的指引只交给干这件活的角色，而且到它要用的那一步才给。图 1 把每一份上下文和每一个会话、子代理排成格子：格子里写它在哪一步拿到，以及是读全文、只读一部分，还是由它写出。全景网里同样的关系画成「拿到」连线，三条以「上下文」开头的典型路径分别走白天、worker 和评审。

（后来：图里 CODING_STANDARDS.md 那一格写的是 code-review 技能里的通用规则表。它已挪进 setup-mmw 技能当模板，审查读的是仓库根目录那一份，Tests 轴还读 TESTING.md。见 ADR 0039。）

从图里读出的

  1. 代码规则只给评审，tdd 只给 worker，这是写明的。通用的 CODING_STANDARDS.md 原文写着「The author of a change does not read this file」，它随轴文件写进 Standards 和 Tests 两个轴的 prompt。仓库根目录那份，manage-agents-md 写着「Only the review reads it」。tdd 只有 Work a ticket 第 2 步和 Make a small change 点名。
  2. 代码规则只有一份。Work a ticket 第 2 步只留流水线自己的规则：基线怎样遵守、不在屏幕上提问、Owns 的边界、跑哪些测试，以及它们点名的五条原则。改函数先改全部调用方、先找现成的 helper、简化时不丢安全检查、只提交票要的测试，这几条只写在 CODING_STANDARDS.md 和它指向的原则里。原则的触发条件在 mmw-mode 的原则索引里，每个会话从头带着；评审按 CODING_STANDARDS.md 判。worker 只保留一条记录的义务：加了文件、依赖或配置，就在 Decisions I made on my own 写一行为什么现有的不够，因为评审的 Unexplained addition 要读它。
  3. spec 和票用指针，不摘抄。票的 Parent 指向 spec 的节，Read first 指向来源和 TESTING.md 的行，Seam 指向 spec 的 Testing Decisions 里的测试层和让系统进入状态的办法。spec 引用 TESTING.md 只写行号；从地图写出的 spec，Out of Scope 链接地图的 Out of scope。照抄的只剩验收标准里的确切数值，因为机器要靠这些值判对错；改 spec 时由 Revise a spec 把票一起改掉。
  4. TESTING.md 有三个读者。写 spec 的会话第 3 步读全文，在 spec 里只按行号引用它依据的行，不重写。票的 Read first 把这几行作为指针列出，worker 第 2 步打开原文读这几行。Tests 轴读全文。
  5. worker 读的共享记录，评审一侧几乎都读。票，每个轴都读。spec 里票点名的节、基线、屏幕契约的行、已合入的票，由 Spec 轴读。CONTEXT.md 由 Standards 轴读，TESTING.md 由 Tests 轴读，设计包由 UI 轴看截图对比。不读的有两样：Memory，Review a ticket 明文不许作为发现的依据；Read first 里不算基线的参考材料，Spec 轴只读标了基线的。
  6. reviewer 顺着票里的指针找 spec。票的 Parent 写着 spec 的编号和节号，Read first 列着基线。Review a ticket 第 4 步按「the spec section the ticket names」等六样东西把发现分成票内和票外。
  7. worker 第 2 步给的东西最多。这一步现在 815 个英文词，是 worker 所有步骤里最长的：要读的清单和流水线的规则都在这一步。读和写在同一步发生，所以这符合「哪一步用就在哪一步给」。
  8. 白天写 spec 和拆票都不读 Memory。Write a spec 和 Cut tickets 没有读 Memory 的步骤。worker 存下的经验，经 start prompt 里的索引交给后面的 worker。
  9. 没查证的。子代理（四个审查轴、歧义扫描）会不会载入用户级提示词，取决于宿主怎样开子代理，我没有查。

现在在哪

  • v3 写完了，在分支 mmw-rebuild 上。图里的技能、playbook、原则和程序都在这个分支的 mmw-v3/ 下；mode 的路由行、原则索引，以及每一步点名的技能、文件和脚本都存在，由 check_wiring.py 核对。图的数据在每次生成课程时从这些文件重新读出，有技能或 playbook 没放进图里，生成就失败。
  • 本机跑的仍是 v2。~/.mmw/installed-root 记的是已安装 checkout 里的 mmw-v2。换成 v3 要你授权一次 install.sh，而且要在没有开着的夜时做。
  • 两件等你定。任务看板上的「waiting for a slot」已经不会再出现，删不删；Nowledge Mem 停着时现在关不了夜，保持还是放宽。两件的细节在第 19 课第 7 节。

哪个组件、哪条连线和你理解的不一样，直接问我。图里组件的中文名和一句话说明是我写的；每个组件的原文、步骤和出处都来自仓库里的文件，点开就能看到。
