迁移之后，v2 的原则还在不在

你担心迁移把 v2 时期精心设计的原则和路由弄坏。我从 Nowledge Mem 里读了 825 条记忆，归纳成 96 条 v2 要防的问题，分九组。九个只读 agent 各查一组，对照 v2 和 v3 的原文；它们报回的每一条，我都回到原文核过，并且只留下仓库用 setup-mmw 配置好、按设计使用时仍会发生的。结论是没有一条 v2 的守卫整条消失。8 条变弱，2 处两份文字说法相反，每一处都是一两句话的事。

依据本分支 0e866710e；v2 是 mmw-v2/，与本机已安装的 checkout 逐字节相同。清单来自 Nowledge Mem 两个 Space 的 69 次检索。每条发现写着 v2 和 v3 的文件与行号，我逐条重读过。没跑真的一夜；凭读代码得出的后果标了 推断。
主要来源，建议先读mmw-v3/skills/mmw-mode/playbooks/work-a-ticket.md 第 2、3 步。这一课五处要改的地方里，有两处在这两步，第 3 节那件要你确认的也在第 2 步。

1　96 条各自的结论

九组是本课的分法：A 提示层与 mode，B 路由，C spec 与切票，D worker，E reviewer，F 夜，G 界面链，H 记忆与复盘，I 技能集文字。每一条写的是 v2 要防的问题，不是 v2 的写法。v3 换了做法、问题照样被防住，就算「还在」。

「按决定改了」是有记录的改动，记录在 ADR、imports.tsv 的 J 记录或前面的课里。A 组蓝色最多。v2 用户层提示里的规则 2 到 15，按第 4 课的决定搬进了 mmw-mode 和原则技能。MMW 工作的仓库都先由 setup-mmw 配置，会话再经三条路读 mode：Claude Code 和 Codex 上的钩子、worker 和 reviewer 的 start prompt、Grok 和 Cursor 上你输入的 /mmw-mode（第 17 课第 5 节）。F 组的蓝格之一是「排队等槽位」：它在 715 次叫醒里一次没发生，第 19 课删掉了。

「v2 时就缺」不是迁移带来的，第 4 节单列。黄色和红色的 10 格，第 2、3 节按出错的时刻讲。

2　配置好之后仍会出错的五个时刻

五个时刻都出现在正常使用里，不需要先做错什么。第一行每次验收都可能碰到，因为夜里交回的票本来就会留着，而 orchestrator 读 stderr 时两句相反的话同时在眼前。第二行是 v2 写过的一句判断，搬的时候只搬到了「有冲突」那一支。v2 的 implement 写着，合并干净但检查变红时，这是合并造成的，先读合进来的票。

第三行是 推断：每个仓库的头一夜 Memory 索引都是 none，v3 还没真跑过一夜。第四行在你把一个 map 分成几份 spec 时出现；下一次写 spec 的会话看得到 map 下已有那份 spec 的子 issue，多半会察觉，所以后果是可能、不是一定。第五行已经发生过两次：提交 a8f54a30f 和 1f1fe087c 改了有 J 记录的拷贝文件，没加新的 J 记录，check_imports.py 仍印 IMPORTS OK 186 rows。两处都是 MMW 自己写的文字，本身无害；同样的漏记落在 mattpocock 或 pstack 的拷贝上，下次拉上游就会被盖掉。

3　我上一批改动带出的三处

上一批（0e866710e）把 spec 和票里的摘抄改成指针，代码规则只留一处。指针本身是对的。问题是我只改了被指的地方，没有回头找依赖原写法的句子。

那一批改了什么

Work a ticket 第 2 步删了三句：改函数前 grep 所有调用方；写 helper 前先在仓库里找；简化时保留安全检查、防丢数据的错误处理、可访问性。理由是它们在 CODING_STANDARDS.md 和它指向的原则里，mode 的索引把原则的条件带进每个会话。

现在缺了什么

这个前提一半不成立。「Fix at one caller」指向 principle-migrate-callers-then-delete-legacy-apis，它在索引里的条件是「引入新的内部 API」，修共享代码里的缺陷时不触发。「Lost safeguard」那一行没有原则。principle-start-from-what-exists 写明不管就地修 bug。三句现在只有评审读得到。
后果有先例：第 15 课记着 #592 那一夜，一条只有评审读得到的规则，让 8 张票里 6 张多修了一轮。这三条也会这样，worker 写完才被 Standards 轴指出。第 5 节第 1 件要你确认。

那一批改了什么

票的 ## Seam 改成按名字指向 spec 的 Testing Decisions，不再自己写可抄的先例。

现在缺了什么

ticket-format.md 的定档句还写着「Seam 已点名可抄的先例就留 junior-worker」，字面上再也满足不了。
后果：钱或崩溃恢复路径上、有先例可抄的票被定成 senior-worker。夜里用更贵、更慢的模型，不会做错。改法：那一句改成看 Testing Decisions 里那一层有没有先例。

那一批改了什么

spec 的 Out of Scope 不再照抄 map 的 Out of scope，改成链接过去。

现在缺了什么

切票时扫歧义的子代理，提示里写着只读 spec 和票草稿，不跟链接。
后果 推断：map 已经排除的事，它可能当成没定，放进 Choices 问你。改法：ambiguity-scan.md 那一句加上「和 spec 链接的 map 的 Out of scope」。

4　v2 时就有的缺口，和几处小的

下面四处 v2 就这样，不是迁移带来的，列出来是因为这次核到了。

  • story 判官不比较边框颜色，尺寸差 2 px 以内不报。1 px 的红色报错框做成灰色，照样 STORY OK（图 1 的 G5）。Memory 里记着这一点。
  • 夜外跑一张票（Run one ticket）时 relay 停了，没有东西重启它。夜里由 advance 重启。
  • retro 提案的去处 toolbox-memory（把一条经验复制给所有仓库）没有哪一步执行（H4）。
  • 夜里 orchestrator 的 Memory 写进个人的 Default，第二天注入你开的每个会话（H5）。

小处，各是一两行字，都不会让东西做错：

  • 五处用步骤编号引用别的 playbook，例如「Chart a map step 5」。今天都指对；skill-set-rules.md 规定按标题引用，被引用的那份插进一步就会指错。
  • codebase-design 的 description 原样留着 v2 的触发词，和 Improve the architecture 的路由行说同一句。会话按 mode 的路由走，不会走错；但 skill-set-rules.md 把两份 description 认领同一件事算作冲突。
  • integrate 退出 3 时 stderr 说跑合并涉及的仓库检查，Work a ticket 第 3 步说跑覆盖冲突文件的测试。
  • 词汇表过时五行。docs/contexts/tickets/CONTEXT.md 三行还写着照抄和 PR，docs/contexts/night/CONTEXT.md 两行还写着已删的 reviewer Rule。
  • imports.tsv 的 J100 还说 ## Writing the reply 开头有一段，那段已移回 shared.md。
  • test_dispatch.sh 有 6 处逐字钉住 start prompt 的第一句，和 TESTING.md 第 7 行相反。
  • Authoring or modifying a skill 要求宿主名的 grep 一无所获，但有两个文件必须写宿主名或 runner 名。
  • 根目录 CODING_STANDARDS.md 没有规则名，Standards 轴只能临时起名，retro 数不到一起（第 15 课第 9 节已列）。

5　要你定的

  1. Work a ticket 第 2 步那三句。这三条管的是共享代码只修一处、不重复造 helper、简化时不丢安全检查和防丢数据的处理。现在 worker 写代码时看不到，只有评审在写完之后指出。我推荐按「代码规则只有一处」来修：放宽 principle-migrate-callers-then-delete-legacy-apis 的条件并补「共享代码只修一次」；给 principle-laziness-protocol 加一条，删减时保留安全检查、防丢数据的错误处理、可访问性；给 principle-start-from-what-exists 加「先在本仓库找」。另一种是三句原样放回第 2 步，代价是同一条规则又有两处。
  2. 第 19 课带来的两件还没定：看板上永远不会出现的「waiting for a slot」删不删；Nowledge Mem 停着时夜能不能关。
  3. 夜里 orchestrator 的 Memory 写进 Default（第 4 节第四条）：要不要每个仓库分开。

其余都是工程修改：图 2 每一行的改法，第 3 节后两处，第 4 节的小处。你说开始我就一起改；改完照 Authoring or modifying a skill 走一遍真实任务，再跑 check_wiring.py、check_imports.py、check-interfaces.py 和受影响的测试套。

6　怎样查的，没查的

一步做了什么
记忆69 个主题在两个 Space 各检索一次，去重后 825 条。偏好、决定、经验三类读完全文，其余读标题，再挑着读全文
清单归纳成 96 条，每条写 v2 要防的问题、v2 的做法和出处记忆的标题
九个 agent各查一组，只读。每条要给 v2 和 v3 的行号与原句，只报说得出「哪个会话、在做什么时会做错」的问题
核对agent 共报 30 多条。我回到原文逐条读过，再去掉前提不成立的：仓库没配置、机器没装、没按设计的入口进来、你在别的仓库做 MMW 的事，以及历史上一次没发生过的情形
只读检查WIRING OK、INTERFACES OK、IMPORTS OK 186 rows；后者为什么不够，见图 2 第五行

没查的：没跑真的一夜。Grok 和 Cursor 上用 /mmw-mode 打开一个禁止模型调用的技能，是设计好的入口，但这条机制没在这两家实测过。Codex 压缩上下文后会不会再读 mode，没核。mode 的 ## Non-negotiables 让「Nontrivial change」去用 how，而 how 会开研究会话、结束回合等叫醒；worker 在一张大票上会不会触发它，要在真的一夜里看。

7　自测

1．早上你接受了这一夜，orchestrator 跑 finish 退 2，因为还有被交回的票开着。照 Run a night 第 10 步，它该怎么做？

第 10 步写着这些票由你定，一张都不自己关；dispatch.sh 的 stderr 却说「close them」，这正是图 2 第一行要改的。

2．合并干净，但仓库检查变红，票被退回。v2 让 worker 先做什么？

v2 的 implement 写着这是合并造成的，先读合进来的票和关票评论，保留已落地的行为；v3 只在有冲突那一支写了这句（图 2 第二行）。

3．为什么 IMPORTS OK 不能证明对上游拷贝的每一处改动都记了 J？

check_imports.py 只对没有任何改动记录的行逐字节比对；一行有了 J 记录，之后再改它就看不见（图 2 第五行）。
