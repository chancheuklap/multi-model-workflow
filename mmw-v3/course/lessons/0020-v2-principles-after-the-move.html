迁移之后，v2 的原则还在不在

你担心迁移把 v2 时期精心设计的原则和路由弄坏。我从 Nowledge Mem 读了 825 条记忆，归纳成 96 条 v2 要防的问题，派九个只读 agent 逐条对照 v2 和 v3 的原文，只留下仓库用 setup-mmw 配置好、按设计使用时仍会发生的。没有一条 v2 的守卫整条消失。迁移后变弱的 8 条和两处说法相反的，连同你定的三件，这次都改完了。96 条里 2 条是 v2 时就缺的，还缺着。

依据本分支 mmw-rebuild 上这一课所在的提交；v2 是 mmw-v2/。每条发现我都回到 v2 和 v3 的原文核过。改动只在分支上：本机已安装的 checkout 没动，夜里跑的仍是旧版本。没跑真的一夜；凭读代码得出的后果标了 推断。
主要来源，建议先读mmw-v3/skills/mmw-mode/playbooks/work-a-ticket.md 第 2、3 步，和 mmw-v3/skills/mmw-mode/playbooks/run-a-night.md 第 7、8 步。这次的改动多数落在这四步里。

1　96 条现在的结论

九组是本课的分法：A 提示层与 mode，B 路由，C spec 与切票，D worker，E reviewer，F 夜，G 界面链，H 记忆与复盘，I 技能集文字。每一条写的是 v2 要防的问题，不是 v2 的写法。v3 换了做法、问题照样被防住，就算「还在」。

「按决定改了」是有记录的改动，记录在 ADR、imports.tsv 的 J 记录或前面的课里。A 组蓝色最多：v2 用户层提示里的规则 2 到 15，按第 4 课的决定搬进了 mmw-mode 和原则技能。「这次补回」的 11 格，是迁移后变弱的 8 条、两处说法相反的 2 条，和 H5（夜里的 Memory 写进哪个 Space）。虚线的两格 G5 和 H4 v2 时就缺，第 5 节列着。

2　五个会出错的时刻，现在怎样

五个时刻都出现在正常使用里，不需要谁先做错什么。第一行每次验收都可能碰到，因为夜里交回的票本来就会留着；现在 orchestrator 读到的 stderr 和 playbook 说的是同一件事。第二行补回的是 v2 implement 的一句判断：合并干净但检查变红，是合并带进来的东西造成的，先读进来的票。

第五行的新检查第一次跑就报了 12 处：12 个文件在它那一行最后一次改动之后，又被提交改过，没有补 J 记录。12 处都是 MMW 自己写的文字，每处我都看了改动，补了 J 记录。同样的漏记落在 mattpocock 或 pstack 的拷贝上，下次拉上游时这处改动会被盖掉而没人知道；现在漏记的那次提交过不了 check_imports.py。我这次的改动它也查出 6 处，都已补上。

3　你定的三件怎样落地

1　按推荐改：三句进原则

principle-migrate-callers-then-delete-legacy-apis 现在管每一次改动别处会调用的代码，修 bug 也算：先 grep 所有调用方，共享代码里的缺陷在共享代码里修一次。principle-laziness-protocol 加了 Keep the safeguards：删减时保留安全检查、防丢数据的错误处理、可访问性和需求明确要的东西。principle-start-from-what-exists 先在本仓库和票的 Read first 里找 helper，这一条在就地修 bug 时也适用。

worker 什么时候读到

mode 的 ## Principles 索引里，三行的条件改成写 helper、简化、改动别处会调用的函数时触发，每个会话都带着这几行。CODING_STANDARDS.md 的「Lost safeguard」一行现在指向 principle-laziness-protocol，评审和 worker 读的是同一条。
走查发现一处冲突：Work a ticket 第 2 步原来只在验收条件非改不可时才允许改 Owns 以外的文件，和「共享代码修一次」相反。现在那一条把共享代码的修复也算进去，照样记在 Outside Owns: 下。

2a　删看板的「waiting for a slot」

看板的代码、样式、屏幕契约、docs/contexts/task-board/CONTEXT.md、DESIGN.md 和看板测试里都删了。status.py 的说明也不再提等槽位。看板测试套 all passed。

设计包也删了

设计包只有 Claude Design 自己能改。我把要改的 15 处先在本地副本上做完、核过，写成项目里的 task.md，你说「开始」后那边的 agent 照着改，我再拉回来。拉回来的文件和我核过的版本逐字节相同；屏幕契约删掉最后那条 Component · 详情.ticket-waiting 声明。
示例里原来画成在等槽位的两张票 #136、#225，现在照产品真实的显示画成 worker 在跑。设计和产品逐元素比对是 STORY OK 46/46；删之前是 52 行差异。

2b　Nowledge Mem 不可用时，夜能关

memory-list 退 2 时，Run a night 第 8 步改跑 dispatch.sh summary <spec> --memory-unavailable。spec.closed 里记一个空的决定列表和原因，NIGHT SUMMARY 写一行「Memory closing: not done」。退 2 的两种情形都算：Nowledge Mem 没回应，或只返回了部分记录。

防止误用

Nowledge Mem 能把记录列全时，--memory-unavailable 被拒绝，什么都不发；这时照常逐条决定。走查查出原来的写法会让夜在两步之间来回（只列出部分记录时），已改成两处用同一个判断。
代价：这一夜的记录原样留着，仍带 mmw-experience 标签，后来的 worker 照样会看到它们，其中可能有已经过时的。没有哪一步回头处理它们。

3　每个仓库分开

dispatch.sh open、open-ticket 和 check 现在先看本会话的 NMEM_SPACE：不是本仓库的 Space（例如 chancheuklap__multi-model-workflow）就拒绝，什么都不推、不开。brief 开出的研究会话也带上本仓库的 Space；Space 核不到时照样开，stderr 说它们会写进 Default。

你会看到什么

你在本仓库的终端里开的会话，~/.zshrc 已经按仓库设好了这个变量，检查直接通过；那段设置只在有终端（TTY）的 shell 里运行。不经过它开的会话会在 check 那一步停下，Run a night 第 2 步让 orchestrator 告诉你重开会话。推断：哪些启动方式不经过 ~/.zshrc，我没有逐个试。
为什么是拒绝、不是警告：orchestrator 写 Memory 用的是它自己会话的环境，会话开起来以后脚本改不了；放它开夜，这一夜学到的就进了 Default。拒绝发生在推送和开夜之前，重开会话就能继续。

4　其余的修改

  • ticket-format.md 的定档句：票的 Seam 指向的那一层，spec 的 Testing Decisions 给了可抄的先例，就留在 junior-worker。
  • ambiguity-scan.md：扫歧义的子代理也读 spec 链接的 map 的 Out of scope，map 已经排除的事不再当成没定。
  • 按步骤编号引用别的 playbook 的地方，实际有 16 处，不是我上次说的 5 处，分布在 9 个文件里。现在都按步骤的粗体标题引用。
  • codebase-design 的 description 只留它自己那一份（一个模块的接口、seam 放哪、给别的技能用的词汇）；找加深机会、让代码好测，归 Improve the architecture 的路由行。这一条要等发布后的新会话才生效。
  • integrate 退出 3 时的提示，和 Work a ticket 第 3 步一样，说跑覆盖冲突文件的测试。
  • 词汇表五行改成现在的说法；本仓库 docs/agents/issue-tracker.md 里没人再读的「PR 也走 triage」一节删了，setup-mmw 的模板早已没有它。
  • imports.tsv 的 J100 改成实情：## Writing the reply 没有开头那段，那段在 shared.md。
  • test_dispatch.sh 里 5 处逐字钉住 start prompt 第一句的断言，改成只查它带的事实：mode 的路径、playbook 名、票号、base commit。
  • 宿主名的 grep：照原来的写法它永远查得到东西（CLAUDE.md、Claude Design、普通词 cursor）。skill-set-rules.md 现在写明哪些命中算合格，并让两个以宿主或 runner 为主题的文件整份通过。
  • 根目录 CODING_STANDARDS.md 改成和 code-review 那份同样的表，12 条规则各有名字，评审可以按名字报，retro 可以按名字数。规则内容不变；和 code-review 的 Silent pass 重复的那一句，只在出处一栏留下 ADR 0008。

5　还没做的

v2 时就缺、这次没动的三处：story 判官不比较边框颜色，尺寸差 2 px 以内不报（G5）；夜外跑一张票时 relay 停了没有东西重启它；retro 提案的去处 toolbox-memory 没有哪一步执行（H4）。

走查看到、留给以后的（不会让这次改的东西做错，各自是一处没写到的情形）：

  • 仓库检查红了而修不好时，Work a ticket 没有停下的规则；ABANDON: 只管验收条件。
  • 修的是合进来那张票的代码时，算 Outside Owns: 还是开 contract 子票，没写。
  • 票留给你「下一夜再跑」时，这一夜的 finish 怎样才能通过，没写；第 10 步的 Done when 也不管退 2。
  • docs/agents/issue-tracker.md 说 mmw:spec 标签由 to-spec 加，Write a spec 说由 --publish 加；--publish 退 1 时怎么办也没写。

没发布：改动在分支 mmw-rebuild 上，已提交，没推送，本机已安装的 checkout 没动。发布要走 AGENTS.md 的四步，等你说。

7　自测

1．早上你接受了这一夜，orchestrator 跑 finish 退 2，因为还有被交回的票开着。它该怎么做？

Run a night 的 Finish once the owner accepts 写着这些票由你定，一张都不自己关；现在 dispatch.sh 的 stderr 也这样说（图 2 第一行）。

2．夜要收尾，memory-list 退 2，因为 Nowledge Mem 没回应。orchestrator 该跑哪一个？

你定了这时夜能关：summary <spec> --memory-unavailable，记录原样留着，NIGHT SUMMARY 写明没做（第 3 节 2b）。

3．orchestrator 的会话没有设 NMEM_SPACE，它跑 dispatch.sh check。会发生什么？

会话开起来以后，脚本改不了它的环境；放它开夜，这一夜的 Memory 就进了 Default。所以 check、open 都拒绝（第 3 节第 3 件）。
