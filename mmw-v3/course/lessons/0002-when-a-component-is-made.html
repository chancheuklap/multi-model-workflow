第 2 课 · 组件为什么存在

每种组件在什么情况下才该有一个新的

第 1 课讲了每种组件长什么样。这一课讲它为什么存在：在 pstack 里，什么情况会让人新写一个 playbook、一条原则、一个技能、一个脚本，由谁来写，怎么写。最后对照两次迁移：我们当时定的放置规则，有几条和 pstack 自己的做法相反；照它们搬家之后，坏了什么。

这一课回答
  1. 什么情况触发创建，由谁、怎样创建
  2. 每种组件的意义：什么情况才值得有一个新的
  3. 两次迁移的放置规则错在哪，造成了什么
依据pstack 原文（e43c7ee）和它的提交历史；第一次迁移的 ADR 0032 与 issue #874–#891；第二次迁移的 components.md。后两者在 tag archive/mmw-migration-1、archive/mmw-migration-2。
主要来源，建议先读reflect/references/synthesizer.md：pstack 判断「一条经验该落到哪里」的标准，只有一屏。

1　什么情况触发创建，由谁来做

从图 1 能看出的三件事
  1. 默认是改已有的，不是新建。reflect 的判断标准写着：「propose new skill via create-skill: only when no existing skill is a real home, the pattern recurs, and the topic deserves its own skill」。新技能要同时满足三条：没有现成的家、会反复出现、值得单独成为一个技能。
  2. 能写成检查的，就不写成文字。correct 的修复顺序是架构、类型、lint 或 CI、测试，文字规则排最后：「Nothing fails when an agent skips them」。reflect 也一样：「Skill prose is for things mechanisms cannot enforce」。
  3. 没有一行是「把已有的内容按类型重新归类」。每一种创建都由一件具体的事触发：一个任务、一次纠正、一句写了两遍的指令。

2　每种组件的意义

每张卡片四行：这种组件回答什么问题；原文说什么情况该有一个新的；原文说什么情况不该；pstack 里的实例。原文没有直接写、由实例归纳出来的，标了 归纳。

mode skill一个人一份

回答
这个人的工作方式：什么情况用什么，一个任务走哪份 playbook。
该有
要让 agent 照你一贯的方式工作时。automate-me 从你的聊天记录里找出至少两段都出现过的偏好，只为「specific, non-default rule」开一节。Cut ruthlessly. A mode skill is not a manual.
不该
只是一个具体任务、或一种窄的流程（例如怎么写提交信息）：那是普通技能，不是 mode。模型配置也不放进 mode：pstack 加 setup-pstack 时，专门把配置表从 mode 里删掉，只留一句指向（提交 6605d7a）。
实例
poteto-mode；automate-me 为你生成的 <名字>-mode。

playbook一种任务一份

回答
这一种任务从头到尾怎么做、谁负责什么、交回什么。
该有
出现一种新的任务：它要交回的东西和已有的每一种都不同。归纳 例：加 Hillclimb 时，作者写明它和 Perf issue 的区别是「sustained」对「one-off fix」，并让 Perf issue 遇到长期优化时指向它（提交 b64f02a）；mode 的路由行对 Runtime forensics 和 Trace forensics 都写着「The deliverable is a diagnosis, not a fix」。每份 playbook 都有自己的 **You own** 和 **Reply:**，这两行不同，任务就不同。
不该
任务只出现一次：用 figure-it-out 为这一次设计流程，不存成文件。只是把一件事交给一个技能：直接点名那个技能就行。归纳
实例
23 份。新加一份时，作者同时做三件事：写文件、在 mode 的 ## Playbooks 加一行路由、需要时在 setup-pstack 加一个模型角色（b64f02a）。

principle一条判断一个

回答
遇到某种情况时，某个决定该怎么做。
该有
同一个判断在许多任务里都要用。Route to the right layer. One-off -> brain note. Recurring fix -> skill or lint rule. Systemic issue -> principle.新加一条原则时，作者写一份原则技能、在 mode 索引加一行，再把它的名字写进每个用得到它的步骤：Sequence work into verifiable units 一加进来，就写进了 6 处（提交 27daaa3）。现有 24 条，每条都至少被 mode 索引之外的 2 份文件点名。
不该
只在一个任务里有用的判断，留在那份 playbook 的步骤里。重复出现的修正，先看能不能做成 lint 或脚本。
实例
principle-prove-it-works 被 13 份文件点名，最多。

skill一件事一个

回答
一件事怎么做，交回什么。
该有
一件反复要做、又没人管的事。A workflow you keep hitting but isn't captured → propose a new skill.这件事要么被许多步骤用到（how 被 7 份 mode 或 playbook 文件点名），要么值得你自己直接调用（teach、recall、bro、correct 没有一份 playbook 点名它们）。
不该
已有技能能装下：改那个技能。Existing-skill-first
实例
25 个。how、architect 主要由步骤调用；teach、bro 只由你调用。

references/ 里的文件属于一个技能

回答
某一步才用的材料。
该有
材料只在某个分支、或只给某个子代理用。how 的探索提示词只在复杂问题时交给子代理；why 按可用的数据源，只把对应的那一份 references/sources/<源>.md 交给调查者。
不该
每次都要用的内容。Templates and references used on every invocation belong in the skill file, not in separate files that cost a read each time.
实例
9 个技能有，共 31 份。poteto-mode/references/bugbot-triage.md 同时被 4 份 playbook 和 mode 的一行触发打开。

scripts/ 里的程序属于一个技能

回答
每次结果都一样、程序能做或能检查的那部分。
该有
同一句指令写到第二遍（Encode Lessons in Structure），或工作不是一眼能做完的（Build the Lever：「The tool is the artifact a reviewer can rerun」）。If the fix is structural, only use the structural fix. The instruction is the symptom.
不该
需要判断的事。那就留在文字里，写醒目，配一个失败的例子。
实例
Worktree cleanup 第 1 步跑 worktree-audit.sh，并写明依据 build-the-lever；Multi-phase plan 跑 check-plan.mjs，依据 encode-lessons-in-structure。

subagent一个固定角色一份

回答
开出来的子代理是谁、开工前先读什么。
该有
某个角色每次被开出来，都必须带着同一份提示词。poteto-agent 存在，是因为用通用子代理会跳过读 mode：Substituting `generalPurpose` skips that read and drifts.Comment Sicko 是一个固定口径的注释审阅者。
不该
Cursor 文档：一次就能做完的单一用途任务，用技能，不用子代理。
实例
2 份。多数技能开子代理时用通用子代理，把 references/ 里的提示词交给它。

rule一台机器一份

回答
每个角色用哪个模型。
该有
某个选择因人而异、又要在每个会话里生效。由 setup-pstack 写出，每个技能仍带着自己的默认值，没有这份 rule 也能跑：Skills read the configured model per role and fall back to the inline default when the rule is absent, so nothing breaks with no setup.
不该
写死在 mode 或某个技能的正文里。
实例
~/.cursor/rules/pstack-models.mdc，1 份。

3　两次迁移定的规则，和 pstack 自己的做法

第二次迁移的 components.md 写了一套放置规则，第一次迁移的 ADR 0032 写了一条搬家判据。它们都自称是在照 pstack 做。下面四对，左边是我们写的，右边是 pstack 原文实际怎么做。

我们写的

A capability skill names no playbook.
components.md ## How one component reaches another

pstack 原文

benchmark-checklist 点名了 Opening a PR、Perf issue、Hillclimb 三份 playbook；recall 点名了 session-pickup。The Perf issue playbook finds and fixes slowness, and the performance mantras in its step 2 generate the fixes.

我们写的

Nothing names a step number inside another component.
同上

pstack 原文

mode 的触发行写「write the throughput checkpoint (Feature step 3)」、「the narrow Bug fix step 1 exception」；上一格的 benchmark-checklist 也引了 Perf issue 的 step 2。

我们写的

A principle named on a step every run takes is read on every run, so it is no longer working as a principle … drop the name.
同上

pstack 原文

Bug fix 第 5 步、Feature 第 6 步每次都会走到，都点名 sequence-verifiable-units。作者加这条原则时，就是有意把它写进这些步骤：Reference the principle where it applies: … the commit-staging steps of bug-fix, feature, and refactoring

我们写的

A reference that steps of several playbooks open: what several tasks share is a principle or a capability skill, not a reference.
components.md ## Signs a passage is in the wrong component

pstack 原文

bugbot-triage.md 是 mode 的 reference，被 Babysit、Autopilot-full、Autopilot-stack、Multi-phase plan 四份 playbook 和 mode 的一行触发共同打开。
这一条造成了实际的搬家：两份 playbook 共用的检查材料，就是依据它从 mode 搬进了能力技能 writing-skill-sets，接着两份 playbook 的步骤顺序也跟着搬了过去，直到你在旧课程第 2 课指出来才搬回（提交 dccdc899c）。

第一次迁移的判据更进一步。ADR 0032：「每段内容默认搬到按类型该在的层。留在原处必须写明是 H1–H6 或 S 中的哪一条。『没有收益』『现在能跑』『改动面大』不作理由。」pstack 没有这样的规则。它的默认方向相反：reflect 要求先找已有的家，一条修改要让「a future agent does something different」；Authoring a skill 写的是「When in doubt, delete. Keep only prose that changes a decision.」

4　按类型搬家之后，坏了什么

从这一节能看出的
  1. 两次迁移问的是「这段文字属于哪一类」。按类别把一段话从原处搬走，原处和新处往往各留一份，或者搬走一半，于是同一个情况有了两种说法（图 2 第 1、2 行），旧的引用指向了不存在的地方（第 3 行）。
  2. pstack 问的是另外几件事。谁在哪一刻需要它，有几处要用它，它改不改变一个决定，能不能做成检查。它的默认是改已有的、删掉不改变决定的，不是重新归类。这一条是由第 1、2、3 节的原文归纳出来的结论，不是 pstack 的原话。
  3. 有些问题 pstack 没写。什么时候该新写一份 playbook，原文没有规则，第 2 节的说法是从 23 份 playbook 和提交历史归纳的。迁移 MMW 时遇到这类地方，要说明是归纳，并拿给你定。

5　自测

1．一次长任务里，你两次纠正 agent「改完要跑格式化」。pstack 首先会怎么处理？

同一类错误出现两次，correct 从最高一层修起：能用架构、类型、lint 或 CI 挡住的，就不写文字。Encode Lessons in Structure 也说：「If the fix is structural, only use the structural fix.」

2．Hillclimb 为什么是一份新的 playbook，而不是 Perf issue 里加一步？

Perf issue 的 **Reply:** 是「baseline number, post-fix number, delta, artifact path」，一次修复。Hillclimb 的是指标与目标、跑了几轮、保留几个撤回几个、每个被接受的改进一行、decision.tsv 的路径：对一个指标的持续改进。交回的东西不同，所以分成两份（提交 b64f02a）。

3．四份 playbook 都要用同一张判断表。按 pstack 的做法，这张表放在哪？

bugbot-triage.md 就是这样：它是 mode 的一份 reference，四份 playbook 和一行触发都指向它。第二次迁移的规则说这种情况要改成能力技能或原则，那条规则和 pstack 的做法相反。
