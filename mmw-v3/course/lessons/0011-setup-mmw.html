第 11 课 · 接入仓库

setup-mmw：一个仓库要配的东西，一次查齐、一次配齐

流水线在一个仓库上跑之前，要有几份说明文件、一整套标签、一个 Memory Space、几条检查命令。v2 没有一步把它们配齐，几个脚本在第一次用到时各建一部分，其余靠手。setup-mmw 是你在要接入的仓库里叫的技能：先用一个只读脚本把每一项查一遍，能配的配上，配不了的告诉你在哪里动手，最后再查一遍。重跑不坏事，所以它也是已接入仓库的体检。这一课写它现在的样子、它的三个脚本、它和 pstack、mattpocock 两个同类技能的对照，以及第 6 课给它定的计划哪几处没照做、为什么。

1　setup-mmw 管什么

它管的是「每个仓库一次」的东西。你开口叫它，或者别的 playbook 碰到仓库没接入时点名它：mmw-mode 的 ## Non-negotiables 有一行「A repository not set up for the pipeline (a docs/agents/ file, a label or the Memory Space missing), or the owner asks to set one up or check it → the setup-mmw skill.」。Write a spec、triage、wayfinder 找不到 docs/agents/ 的文件时都说「仓库没接入」并停下，脚本缺标签或 Space 时也这样说，这一行把这些停下的地方接到同一个技能。它的 description 是只在被点名时运行的那一句，因为它会写仓库、建标签、建 Space，什么时候开始由你或点名它的地方决定。

# Set up MMW

Sets a repository up for the landing pipeline: every file, label and Space the pipeline needs once per repository, checked, created where this skill can create it, and reported where only the owner can act. It hands back the check's table from before and after, what it wrote and created, and what is still missing with who has to act. Re-running it is safe, so it is also the check-up of a repository already set up: `scripts/check.py` writes nothing, and every write below keeps what is already there.

What you write here is read at the moment of acting by every playbook that publishes or triages an issue, by every script that puts a label on one, and by every worker and reviewer of every night. A wrong command or a missing section is repeated by each spec, ticket and night after it, without an error. So make each file true of this repository rather than filling in a template: check a command against the repository before you write it down.

This skill is the only thing that creates the pipeline's labels and the repository's Memory Space. The scripts that use them only ask, and refuse when one is missing.

## Start

Open a todolist with one item per step below.

## Steps

1. **Check.** From the repository root, run `python3 scripts/check.py` of this skill. It prints one line per item, `ok`, `missing`, `note` or `unchecked`, under the layers `repository` and `machine`, then `SETUP OK` or `SETUP INCOMPLETE <n> missing`.
   Done when you hold its table.
2. **Stop if the tracker is not GitHub.** The pipeline's store is GitHub Issues with sub-issues and issue dependencies, reached through `gh`; nothing else works. When the `tracker` row or the `sub-issues and dependencies` row is `missing`, tell the owner what the row says to do, set up nothing, and stop.
   Done when both rows are `ok`, or `sub-issues and dependencies` is `unchecked` because the repository has no issue yet.
3. **Write `docs/agents/`.** Write `docs/agents/issue-tracker.md`, `docs/agents/triage-labels.md` and `docs/agents/domain.md` from this skill's `issue-tracker.md`, `triage-labels.md` and `domain.md`. A file already there is this repository's own record and the seed only where it started: add what the seed has and the file lacks, change a line only where it is wrong for this repository, and leave every other line as it stands; tell the owner the other differences instead of resolving them. Keep the triage labels at their defaults, since the pipeline's scripts write the default strings. For `domain.md`, describe the layout the repository has: one root `CONTEXT.md` (single context) unless a root `CONTEXT-MAP.md` exists or the repository is a monorepo (`pnpm-workspace.yaml`, a `workspaces` field in `package.json`, packages under `packages/` with their own `src/`).
   Done when the three files exist and `issue-tracker.md` has `## Three label sets` and `## Wayfinding operations`.
4. **Point `AGENTS.md` and `CLAUDE.md` at them.** Add one row per `docs/agents/` file to the `## External References` table (`| Need | File |`) of the root `AGENTS.md`, creating the file or the section when it does not exist; a row already pointing at the same file is updated, not duplicated, and a pointer to it in another shape (an `## Agent skills` block, an `## Issue tracker` section) is replaced by the row. `CLAUDE.md` holds the line `@AGENTS.md`: create it with that line when it is missing, and add the line when it exists without it, leaving the rest of the file as it is.
   Done when `AGENTS.md` names all three files and `CLAUDE.md` has the line `@AGENTS.md`.
5. **Create the labels.** Run `python3 scripts/labels.py`. It creates every label of the pipeline the repository lacks, with the colour and description `verify-ticket.py` defines, and leaves the ones the repository has as they are.
   Done when it printed `LABELS OK <n>`.
6. **Create the Memory Space.** Run `python3 scripts/space.py <owner/name>`, with the owner/name the `tracker` row printed. It creates the repository's Space, or repairs one in the wrong shape, and reads it back.
   Done when it exited 0.
7. **Ignore the pipeline's directories.** Add `.worktrees/`, `.scratch/` and `story-shots/` to the root `.gitignore` when the `.gitignore` row says they are not ignored: ticket worktrees are cut under the first, prototype evidence is written under the second, and the story oracle writes its screenshots under the third when a criterion runs it with no `--out`.
   Done when `git check-ignore` reports all three as ignored.
8. **Record the repository's checks.** The `checks` array of `.mmw/target.json` is run on the merge result before a ticket lands (`advance` in a night, `land` outside one) and before the orchestrator pushes a fix of its own, and it is the one check a commit made with `--no-verify` still passes through. Find the commands this repository already uses to lint, type-check and test: its manifest's scripts, a `Makefile`, the `## Commands` table of `AGENTS.md`, its CI workflow. Run each once from the repository root on the branch nights are cut from; a command that fails there would fail every ticket, so it does not go in, and you tell the owner which one failed and its first failing line. Write the passing ones into `checks`, adding the key and leaving every other key of `.mmw/target.json` as it is, creating the file when it does not exist. When the repository has no such command, write no `checks` and tell the owner the repository has nothing to check its code with; `.mmw/target.json` is still created, because a `.mmw/` directory is what marks the repository as onboarded, and a session started in it is told to read the mode only then.
   Done when `checks` lists every command that passed, or the reply says there is none.
9. **Write `TESTING.md`.** When it is missing, write it at the repository root from what the tests do now: where they live, how one is run, which layers there are, which external boundaries are stubbed and how, and how a test puts the system into a state it needs. Each line states a fact the code already shows, with a file that shows it. Its readers are whoever writes a spec, whose seam and `## Testing Decisions` draw on it, whoever writes a ticket outside a spec, and the review's Tests axis; a worker gets what it needs from the spec and the ticket. How code should be written does not go here or anywhere this step writes: the review applies the `code-review` skill's general `CODING_STANDARDS.md`, and a rule only this repository holds enters its own root `CODING_STANDARDS.md` through a retro proposal the owner approved.
   Done when `TESTING.md` exists, or it already did.
10. **Commit and push.** Commit every file steps 3 to 9 wrote, in one commit on the branch checked out, and push it: a night's worktrees are cut from `origin`, so a file only on this machine is one no worker reads. A push the remote refuses goes into the reply with its reason.
    Done when the commit is on `origin`, or the reply says why it is not.
11. **Check again.** Run `python3 scripts/check.py` again.
    Done when you hold its second table.

**Reply:** the second table's summary line; each item that changed between the two tables; what was written and created; each row still `missing` or `note`, with who acts on it: the owner for a GitHub setting or a branch rule, the machine's installer for a `machine` row, nobody yet for missing checks; and the commit and branch of step 10.

3　一样东西只有一处建

第 10 课结束时你定下：整套标签由 setup-mmw 一次建好，别处不建。Memory Space 原来也是这样分散的：dispatch.sh 的 ensure_repository_memory 在每次 open 和 start 时，Space 不在就建、形状不对就修。归纳我把你的规则推到了 Space 上：那段代码搬进 setup-mmw/scripts/space.py，dispatch.sh 只跑 space.py --check，不在或形状不对就拒绝开夜、拒绝开会话，话里点名 setup-mmw。好处是「这个仓库接入了没有」只在一处回答；代价是一个从没跑过 setup-mmw 的仓库，第一夜会被拒绝，而不是悄悄建好继续。如果你不想要这个代价，改回去只动 ensure_repository_memory 一处。

三个脚本：

  • check.py 只读，什么都不写。每项一行：ok、missing（流水线用不了，后面写怎么补）、note（在了，但有要你看的，比如保护分支）、unchecked（问不了，比如仓库还没有一张 issue 可以拿来试 sub-issue）。最后一行 SETUP OK 或 SETUP INCOMPLETE <n> missing，退出码跟着它。
  • labels.py 从 verify-ticket.py 那张表读出全部 16 个标签：层四个、队列五个、分级两个、wayfinder:* 五个。缺的建，已有的一律不动，颜色或说明和表不同的只打印一行。归纳不覆盖，因为没有一个脚本读颜色和说明，仓库自己的选择没有理由被改掉；搜到的几个同类工具（下面）默认会覆盖或删掉多余的标签。
  • space.py 不带 --check 时建或修，带 --check 时只读；两种都要给仓库的 owner/name。服务连不上时一律报「不可用」，从不拿「建一个」顶替，这条是 v2 原来就有的。

建标签照规矩先搜了现成的：GitHub 上 gh-label-sync、gh-labeler、github-label-sync、PaulRBerg/github-labels 都能从一份 YAML 同步标签。我读了最后一个的 scripts/sync-labels.sh：它先 gh label list --limit 1000，缺的 gh label create，不同的加 --force 覆盖。决定自己写：用它们要多一份标签定义文件，和 verify-ticket.py 那张表重复，正是「一样东西一处定义」要避免的；而要做的只是「缺的建」，二十几行。

5　和两个同类技能对照

setup-pstack 配的是每个角色用哪个模型：查出你有哪些模型，问你预算，整份重写一个规则文件。MMW 里这件事已经是 ~/.mmw/models.json 和改它的 models.py（第 5 课），属于机器不属于仓库，所以 setup-mmw 只查这个文件在不在。取它的三样：先查出现状再动手；整份可重跑；最后一步看项目有没有办法驱动真实的应用来证明改动。最后这一样在 MMW 里是产品层（判官、journey、harness），不归 setup-mmw：一个仓库要不要被驱动，看它的一批票有没有 screen contract；contract 票建它，开夜时 Run a night 第 2 步用 target_config.py --check 查（第 13 课）。

setup-matt-pocock-skills 写 tracker 的三份说明，是第 3、4 步的底子。它一节一节问你：哪种 tracker、要不要默认标签、单个还是多个 context。setup-mmw 一个都不问：前两个在流水线的仓库里只有一个答案，第三个从仓库里有没有 CONTEXT-MAP.md 和 monorepo 的迹象就能定，是工程判断。它在写之前把草稿给你看；setup-mmw 不给，因为三份文件是给 agent 读的说明，不是你要拍板的东西。

9　自测

1．一个从没接入的仓库，你让会话开一夜。dispatch.sh open 现在会怎样？

Space 只由 setup-mmw 的 space.py 建，dispatch.sh 只查（图 3）。查不到就退出 2，话里说 setup-mmw 会建它。

2．仓库里已有 needs-triage，颜色是你自己挑的红色。跑 labels.py 以后呢？

已有的一律不动，颜色或说明不同只打印一行（第 3 节）。没有脚本读颜色，没理由改你的选择。

3．你的仓库放在 GitLab 上。叫 setup-mmw 会怎样？

第 2 步：流水线只经 gh 和 GitHub Issues 说话，选别的什么都跑不起来，所以不问、不配，告诉你并停下。

4．仓库的 npm test 在 main 上本来就有两个测试失败。第 8 步怎么处理它？

基线上就失败的命令会让每一张票都过不了，所以不进 checks；回报里说是哪一条、第一行失败是什么，修不修由你定。

5．setup-mmw 跑完，check.py 还剩一行 note … protected branches main。这说明什么？

note 不算 missing，总结仍是 SETUP OK。它提醒你：夜里会推送的分支若有保护规则，推送会被拒；main 本身夜里不推，看一眼即可。
