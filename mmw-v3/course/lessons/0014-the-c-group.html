第 14 课 · 剩下的七个技能

C 组：四个其实是 playbook，两个留作技能，一个不搬

第 6 课图 4 把七个 v2 技能放在 C 组，理由是它们路由很少，多是自己内部的先后。这一课把它们搬完。搬之前我先答过一次「这七个难在哪」，答的是要不要重跑测试、两个接入仓库会不会坏，没有拿第 6 课的规矩去判；你指出 exe-release 本身就是一份 playbook，grill-with-docs 不用搬。按规矩判下来，七个里有四个和 exe-release 一样：做法成为 playbook，还管着一样东西的技能留下那样东西。

这一课回答

  2. 每个文件去了哪

  4. 补回的句子，改正的事实

依据第 6 课第 3 节「拆的规矩」，mmw-v3/skills/mmw-mode/playbooks/README.md；v2 在 9df1ab67d 的七个技能（词数见图 1）、mmw-v2/merge-notes/ 的 codebase-design.md、improve-codebase-architecture.md、wizard.md；mmw-v3/upstream-pstack/ 的 architect 和 Refactoring、Shipping；本分支现在的文件。本课自己的判断标了 归纳。
主要来源，建议先读John Ousterhout，A Philosophy of Software Design，第 4 章「Modules Should Be Deep」和第 11 章「Design it Twice」。codebase-design 的词汇（深模块、接口、seam）和 Improve the architecture 找的「深化机会」都出自这两章。

1　按规矩判

判一个技能是不是 playbook，看第 6 课规矩 1：**You own …** 和 **Reply:** 两行和已有的每一份都不同，它就是另一种任务。再看规矩 4：几份都写的格式，放进管那件东西的技能。

v2 技能它交回什么结论
improve-codebase-architecture一份架构报告，和你挑中的一个候选问出来的决定规矩 1：成为 Improve the architecture。它只交出决定，不改代码，决定交给 Write a spec。技能删掉，因为它除了这套做法不管别的东西
code-checkers一个仓库装好的检查工具、一条检查命令、一个提交钩子规矩 1：成为 Set up code checkers。三份语言参考只有这份 playbook 读，进 mmw-mode/references/；技能删掉
manage-agents-md一组按同一格式写的 AGENTS.md 和 CLAUDE.md规矩 1：做法成为 Write AGENTS.md。规矩 4：这个格式还有两处在写，Set up code checkers 第 8 步和 setup-mmw 第 4 步按它的标题加行，所以格式和 check.sh 留在技能里
exe-release每个受影响产品的安装包，出自同一个提交，交到你手上试装规矩 1：做法成为 Ship a release。发布清单的格式、出包引擎和九个脚本只有它管，和 design-pages 一样留在技能里
codebase-design不交东西；它是一套词汇（module、interface、depth、seam、adapter、leverage、locality）规矩 6：留作技能，原样。tdd、Improve the architecture 和两份 reference 点名它
wizard一个给人跑的 bash 脚本，带人做只有人能做的几步留作技能，原样。用到它的时机散在别的任务里（配凭证、做一次迁移），由那件任务或你点名，像 B 组的动词 归纳
grill-with-docs只有一句：读 grilling 和 domain-modeling，照两者做不搬，你定的。和第 6 课删掉的 grill-me 一样；需要这一句的地方，Chart a map 第 1 步、triage、wayfinder 已经直接写着

四份新 playbook 各加了一条路由，写在 mmw-mode 的 ## Playbooks，每条写明它和最容易混的那一份怎样不同。两份 playbook 和一个技能派子代理：Improve the architecture 派探查代码库的，Write AGENTS.md 派调查仓库的，codebase-design 的 design-it-twice 派设计接口的。三个子代理的名字、提示词和交回什么登记在 dispatch/roles.json。

mmw-mode 的四条新路由
- **Improve the architecture.** Finding the deepening opportunities in a codebase, shown as an HTML report, and grilling the one the owner picks into a decision ("improve the architecture", "find refactoring opportunities", "make this more testable", "make this easier for agents to navigate"). Distinct from the `codebase-design` skill, which answers one design question in its vocabulary, and from Write a spec, which this playbook hands its decision to. `playbooks/improve-the-architecture.md`.
- **Set up code checkers.** Installing a repository's linter, formatter and type checker, one checker command and a commit hook: when it has none, a language was added, a checker was superseded (pyright, eslint, tsc --noEmit, black, isort), or commits should run them. Distinct from the `setup-mmw` skill, which records a passing checker command as `checks` and installs nothing. `playbooks/set-up-code-checkers.md`.
- **Write AGENTS.md.** Creating, or rewriting to one format, a repository's `AGENTS.md` and `CLAUDE.md` files, root and nested, `AGENTS.override.md` included ("create AGENTS.md", "rewrite CLAUDE.md", "migrate the agent instructions"). Distinct from the `setup-mmw` skill, which only adds the pipeline's rows to the file as it stands. `playbooks/write-agents-md.md`.
- **Ship a release.** Building an install package from the code on the current branch for every product the change touched, and handing it to the owner to install ("ship", "package it", "build an installer"). Distinct from Run a night and Run one ticket, which land code and ship nothing. `playbooks/ship-a-release.md`.

2　文件去了哪

搬法和第 12 课 design-pages 一样：做法改成 playbook 的样子（You own、立场一段、编号步骤各带 Done when、Reply），步骤之外的判断成为加粗命名的一节。原文逐句搬，只换三类字：v2 的文件名换成 v3 的名字（「SKILL.md step 3」换成「the Ship a release playbook's step 3」），user（指你）换成 owner，以及下面第 4 节那两处事实。几处具体的：

  • Write AGENTS.md：v2 分「新建」「重写」两份文件各写一段准备，再跳回 SKILL.md；现在第 1 步判是哪种，第 2 步一起准备，重写才有的 Migrate 成为一节。v2 写的「用宿主的通用子代理，不点名模型；不能派就自己一组一组做」不再写，mmw-mode 的 ## Subagents 对每个子代理都这样规定。
  • Ship a release：driving.md 成为 Drive one product、Pause: missing context、Close、An interrupted build 四节。两个脚本的注释里写着「driving.md 的那一节」，改成指向这一节，脚本本身一个字没动。
  • Improve the architecture：v2 的第 1 步「Explore」既定范围又派子代理，拆成两步；子代理的问题清单原样进 architecture-explorer.md，加上它要读的词汇和交回什么（最多十处，每处带文件、证据和删除测试的结果）。
  • Set up code checkers：v2 有五步没有 Done when，补上；v2 末尾那句总的 Done when 留在步骤之后，作为整件事的完成条件。

v2 的 improve-codebase-architecture 设了 disable-model-invocation，merge-note 写的理由是：worker 在夜里查 bug 时若自己触发它，它要问你挑哪个候选，夜里没人答。playbook 不能被调用，只经 mmw-mode 的路由打开，而 worker 的开工提示点名它要跑的 playbook、不再选路，所以这个理由在 v3 由结构保证 归纳。

3　pstack 有没有现成的

照规矩，先看 mmw-v3/upstream-pstack/ 里有没有做同一件事的。

  • architect（skills/architect/SKILL.md）：先画类型和签名，再看着实现填进去，分 Ground、Sketch、Agree、Implement、Scrap 五段。它既设计又实现，Sketch 一段用 arena 让几个模型各出一版。MMW 的代码只经 spec 和票落地，所以 Improve the architecture 停在决定，交给 Write a spec；多版设计由 codebase-design 的 design-it-twice 在本机开子代理做。不用 architect。
  • Refactoring（skills/poteto-mode/playbooks/refactoring.md）：「You own the contract. The structure changes. The behavior does not.」它交回的是改好的代码，Improve the architecture 交回的是报告和决定，按规矩 1 是两种任务。MMW 里真正改结构的那一步是 spec 切出的票。
  • Shipping（skills/poteto-mode/playbooks/shipping.md）：讲的是逐个验证、落地 PR，不是打安装包。pstack 里没有写 AGENTS.md 的、没有装检查工具的，setup-pstack 也不管这两件。

四份 playbook 都照 v2 原文搬，不另写。

10　自测

1．为什么 manage-agents-md 留下技能，code-checkers 却删掉？

规矩 4：几份都写的格式，放进管那件东西的技能。AGENTS.md 的格式由 Write AGENTS.md、Set up code checkers 第 8 步、setup-mmw 第 4 步写；三份检查工具参考只有一份 playbook 读（第 1 节）。

2．Improve the architecture 的候选你挑定了，问完了。接下来谁改代码？

它只交出决定，第 5 步交给 Write a spec；在这里重构会绕开票和验收检查（第 1、3 节）。

3．出包时 where 打印 PAUSED:needs-context，原因是一处配置写错。先做什么？

构建机只拿 git archive HEAD，不提交的改动到不了构建机，下一轮会同样失败；提交以后才 resume（Ship a release 的 Pause: missing context）。

4．仓库的 checks 在什么时候跑？

在合并结果上、票落地前跑，另外 orchestrator 推自己的修正前也跑；verify-ticket.py 不跑它们（第 4 节）。每次提交跑的是提交钩子，不是 checks。
