第 9 课 · 设计

写产品代码的四份 playbook：做票、审票、小改动、修 bug

v3 里写产品代码的路有四条：夜里的 worker 做一张票（Work a ticket），reviewer 审这张票（Review a ticket），白天你在场时不开票做一处小改动（Make a small change），你报来一个缺陷时诊断它、写成一张票、落地（Bug fix）。前两份现在只有骨架，后两份还没有。这一课定下每一步写什么、从哪段原文来、改了什么，写代码的规矩放到哪里，新写的文字直接给出草稿。这一课只是设计，还没有改 v3 的任何文件；第 11 节列出落地时要改的文件。

这一课回答
  1. 四份现在是什么样，缺什么
  2. 一张票从认领到合进 base，worker 和 reviewer 各做哪几步，票上留下什么
  3. Work a ticket 每一步写什么
  4. 写代码的规矩各放哪：三条新原则，两条从 pstack 引进的原则，留在步骤里的
  5. Review a ticket 的五步和三条轴
  6. Make a small change 的六步，和夜里的一张票差在哪
  7. Bug fix 的五步，和 pstack 的 Bug fix 差在哪
  8. 新写的文字：两份 playbook 和三条原则的草稿
  9. 要引进什么技能，不引进什么
  10. 这一课不做的：界面验收
  11. 落地时改哪些文件

第 4 步的三条规矩来自 v2 收尾时 orchestrator 自己修小问题的那一段，原文是：

1. One commit per finding, or per group of findings with one cause; the commit message names them by number.
2. It touches only what the finding's cause requires, and the tests that prove it; anything more is a ticket after all.
3. It runs the affected test suites, and the commit message quotes the line it saw (`ran 188 skipped 0`, not "the tests pass").

A fix that exceeds those three is a ticket after all.

playbooks/make-a-small-change.md

### Make a small change

**You own one change the owner asked for while here, from their words to a commit on the base branch; a reader who did not write it reviews it.** No spec, no ticket and no night stand behind it: no criteria a script runs, no reviewer in a session of its own, no closed ticket as the record. What this session misses reaches the owner unless that reader finds it first. The temptation is to call the change too small for that reader; run **Get a second reading** however small it is. Distinct from Bug fix, which starts from a defect the owner reports, and from Run one ticket, which runs a written ticket.

1. **Write down the change and judge its size.** Paste the owner's request word for word into a file: it is this change's spec, and the request the review reads. The change is small when one session can finish it and it needs no product decision from the owner. When it is not, tell the owner it needs a spec, with what you found; this playbook ends here.
   Done when the file holds the request and the change is judged small, or the owner has heard why it is not.
2. **Write it test-first.** Run the `tdd` skill. With no ticket, write the seams under test into the request file and confirm them with the owner. A test counts as red only when it fails because the behaviour is absent (**principle-a-check-must-be-able-to-fail**). A change with no behaviour to test, such as wording or configuration, writes down instead the check that will prove it. Write the code under **principle-start-from-what-exists**, **principle-migrate-callers-then-delete-legacy-apis** and **principle-laziness-protocol**, and, when the request names something already settled, **principle-baseline-is-the-contract**. Keep, for the Reply, one sentence per new file, dependency or configuration entry on why the existing one is not enough.
   Done when every behaviour the change adds or alters has a test that failed before its code was written and passes now, or the check that proves it is written down.
3. **Prove it on the product and run the checks.** Show, on the product, that the change does what the owner asked, in their words (**principle-prove-it-works**); while the product runs, the `ui-acceptance` skill's **Five rules while the product is running** hold. Then run the checks **principle-run-the-smallest-test-set** picks. A red check is answered by **principle-fix-the-product-not-the-check**.
   Done when the proof and the checks pass on the final code, with their output kept for the Reply.
4. **Commit it.** One commit per cause. It touches only what the cause requires and the tests that prove it. Its message quotes the line the test run printed (`ran 188 skipped 0`, not "the tests pass"). A change that exceeds those three is a ticket after all: tell the owner it needs one.
   Done when the change is committed on the base branch under those three rules.
5. **Get a second reading.** Run the `code-review` skill with the axes Standards, Spec and Tests, the commit this change started from as the base, and the request file as the request: its axes cannot read this conversation. Do not tell it which parts you believe are right. Check each finding as Review a ticket's **Verify every finding** says; fix what holds, in the commit of the cause it belongs to, and keep what does not, with its refutation, for the Reply. On a host that cannot run subagents the second reading is not done: the Reply says so and gives the command for a new session. Reading the change again in this session is not a second reading.
   Done when every axis has reported and each finding is fixed or refuted, or the Reply lists the second reading as not done.
6. **Push to the base branch.** When the push is rejected, fetch, merge the new base into your commit, run the affected tests again, and push again.
   Done when the commit is on the base branch on origin.

**Reply:** what changed, and why each new file or dependency was needed; the failing-then-passing test output and the proof from step 3, verbatim; each review finding and what became of it; what the owner should check by hand; and, when it was not done, that the second reading is outstanding.

playbooks/bug-fix.md

### Bug fix

**You own the diagnosis, the ticket that carries it, and the proof on the product; the fix is a worker's, landed through Run one ticket.** Be scientific: every line of the ticket traces to runtime evidence, and a change that "might help" is a hypothesis, not a fix. Distinct from Make a small change, which changes behaviour the owner wants different, and from Investigation, which answers and changes nothing.

1. **Reproduce it yourself.** Follow the `diagnosing-bugs` skill's Phase 1 and Phase 2 on the surface where the owner saw the bug; while the product runs, the `ui-acceptance` skill's **Five rules while the product is running** hold. Drive it yourself even when a debugging protocol says to ask the owner to reproduce; ask the owner only with a stated reason the surface cannot reach the bug, and only after driving it as far as it goes. When no loop can be built, tell the owner what you tried and what you need, as Phase 1 says; this playbook ends here.
   Done when one command, already run, shows the owner's exact symptom on a minimised scenario, or the owner has heard what you tried and what you need.
2. **Find the cause.** Follow `diagnosing-bugs` Phase 3 and Phase 4. Seed the hypotheses with the `how` skill over the affected subsystem and the `why` skill for the change that brought the bug in. Show the ranked list to the owner and carry on without waiting. Confirm the surviving mechanism with runtime evidence, then remove every tagged debug line. When the code does what was asked and the owner wants it otherwise, it is not a bug: tell the owner it is a change, for Make a small change or a spec; this playbook ends here.
   Done when one hypothesis survives on runtime evidence, the others are ruled out, and no debug line is left.
3. **Write the ticket.** Write one ticket in the format of the `verify-ticket` skill's `references/ticket-format.md`, with `None` under **Parent**. **What to build** states the symptom, the cause with its evidence, and the smallest change that evidence justifies. **Seam** is where a regression test exercises the bug as it happens at the call site (`diagnosing-bugs` Phase 5); when there is no such seam, say so there, since that is itself a finding. The first criterion is the regression test at that seam; when the step 1 command runs unattended and gives the same verdict every run, it is the second. Publish it with the labels `mmw:ticket` and `ready-for-agent`, and the worker label the format's rule gives; then run `verify-ticket.py  --lint` and fix every `ERROR`.
   Done when the ticket is on the tracker and `--lint` reports no `ERROR`.
4. **Land it.** Run **Run one ticket** on this ticket.
   Done when its `land` has exited 0.
5. **Prove it on the same surface.** On the base branch, with the fix landed, run the step 1 command on the original scenario, not the minimised one. "Inconclusive", or a check on another surface, is not a pass (**principle-prove-it-works**): say so.
   Done when the original repro runs green where it ran red, or the Reply says why that could not be shown.

**Reply:** what was broken, the root cause, the fix (the ticket and the commit `land` made), and how you verified it; paste the failing and the passing repro output verbatim.

principle-fix-the-product-not-the-check/SKILL.md

# Fix the Product, Not the Check

A check that fails is answered by fixing the product, or by recording that the criterion was not met. It is never answered by changing the check, its harness, its test, its expected output or the baseline it compares against until it passes.

**Why:** The checks exist so the owner can trust finished work without reading its code. An honest "not met" costs the owner one look; a false pass lands broken behaviour under a green mark, and everything built on it inherits it.

- A check that is itself wrong (it tests the wrong thing, names the wrong file, expects the wrong value) is reported where its owner sees it, with what it should be; on a ticket that is a `contract` child. The work it judges does not correct it.
- Loosening an expected value, adding a retry, a sleep or a skip, or widening a timeout until red turns green is changing the check.
- When no fix is in sight, stop and record what each round tried. That record is the whole account of the trying.

principle-baseline-is-the-contract/SKILL.md

# The Baseline Is the Contract

A baseline is a decision someone already paid for: the owner's answer, the prototype that won, the page they signed, the section of a spec. Copy its values, wording, states and interface shapes from it. Do not write them again from memory, and do not improve them.

**Why:** Rewriting a baseline from memory, or improving it, reopens that decision where nobody who made it can see. Raising the problem where its owner sees it lets them decide again.

- When a baseline does not hold (it lacks a state, a field or a case, contradicts another source, or cannot be built as written), keep working on what does not depend on it, and say so where its owner sees it: quote what does not hold, and state what in the same source still holds and must be kept. On a ticket that place is a `contract` child.
- Never quietly change a baseline, and never quietly add around one.
- A reviewer reads the baseline itself, not the account of it given by whoever built against it.

12　自测

1．worker 跑判据，AC2 一直红。查下来，是 AC2 的 CHECK: 本身写错了一个文件名。worker 该怎么做？

判据写错也是一种 baseline 不成立。worker 不改票上的判据（principle-fix-the-product-not-the-check），也不能硬凑；它开 contract 子票，点名这条判据，引用写错的地方，写出它应该是什么。子票叫醒 orchestrator 去改票。

2．Spec 轴报「AC3 的空列表状态没实现」。reviewer 到代码里看，列表为空时页面显示的正是 AC3 要的那句话。reviewer 该怎么做？

Review a ticket 第 3 步：坏结果不会发生，结论是 refuted，写出推翻它的事实，放进 ## Withdrawn。原样转过去会让 worker 白修一轮，还可能把对的代码改坏；直接删掉，worker 和你都看不到它被核过。

3．你报来「导出的文件少了最后一行」。Bug fix 第 2 步查下来，代码照 spec 只导出已确认的行，最后一行是草稿。接下来怎么做？

代码照要求在做，你想要的是不同的行为，那是一处改动，不是缺陷。Bug fix 在第 2 步停下告诉你，改动走 Make a small change，要你做产品决定（草稿该不该导出）就走 spec。

4．Make a small change 第 5 步，这个宿主开不了子代理。该怎么做？

同一个会话再读一遍不算第二个读者。这一步记作没做，交回里写明，并给你在新会话里要跑的那句话。
