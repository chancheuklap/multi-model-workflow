任务看板搬进 v3：设置页跟着角色表走

看板是一个独立的产品，不是给 agent 读的技能：一个本机网页，从 GitHub 读票，画出每张票走到哪；设置页改 models.json。它的代码和测试几乎原样搬进 mmw-v3/board/ 和 mmw-v3/tests/board/。你定了三件事，这一课讲每件做成了什么，以及搬的时候找到的三处问题。

依据v2 在 9df1ab67d 的 mmw-v2/board/、mmw-v2/tests/board/ 和 test_dispatch.sh；v3 的 roles.json、models.py、dispatch.sh；本仓库根目录的 .mmw/ 和 docs/specs/task-board/screen-contract.yaml。本课自己的判断标了 归纳。
主要来源，建议先读mmw-v3/board/AGENTS.md：看板由哪几个程序组成，进程怎样在代码变了之后自己重启。

1　你定的三件事

决定做成了什么在哪
设置页显示 7 个角色，角色列表从 roles.json 来设置页的行就是 models.json 的行，而 models.py 只认 roles.json 里每个开会话的角色一行。新加的三行中文说明照 roles.json 的 what 写第 2 节
brief 会话这次不上看板没改。看板的 screen contract 本来就写着「advisor consultations … are never shown」第 3 节
切换放在 v3 整体替换 v2 那一步；之前加一个可选参数后来作废了，见第 17 课：本机跑哪一份只由显式安装决定，用不着另排一次切换。.mmw/ 的三个程序和 screen contract 直接指向 mmw-v3/board，那个可选参数删掉了第 4 节

顺序那一问已经不用定：C 组的七个技能第 14 课搬完了，所以先搬看板，下一课是安装入口。

2　设置页的行从哪来

为什么用 models.json 的行，不另给一张角色表。v3 的 models.py 已经保证了两件事：安装时给缺的角色补一行，保存时多一行少一行都拒绝。所以 models.json 的行就是角色表，网页再拿一份只会多一处要对齐的地方。服务器的回答格式不用改，screen contract 也就不用改（options: hosts, runners, sources 那一行照旧）。

代价。一台机器的 models.json 还没补上新角色时，设置页少那一行，保存会被拒绝，拒绝的理由列出缺哪个角色。补行是安装入口的事，dispatch.sh check 每晚开夜前也会跑一次安装检查，能修就修。

为什么还要动 codeversion.py。看板进程只在启动时读一次 Python 代码，codeversion.py 盯着这些文件，变了就让进程自己重启。v3 的 models.py 在启动时还读一次 roles.json，v2 没有这个文件。不把它加进去，加了角色以后，正在跑的看板要等下次登录才会显示。

3　brief 会话为什么不上看板

advisor、researcher、explainer、synthesizer 由 dispatch.sh brief 开，不挂在任何票上。看板只从 GitHub 读票和票上的事件，所以看不到它们在跑。要让它们上看板，就要给 brief 一个看板能读的记录，并且在 screen contract 里加一种界面状态，这是一个新功能，不是搬家。screen contract 第 283 行写着顾问会话从不显示，这次不改它。

4　这台机器和本仓库，各用哪一份看板

常驻的看板。com.mmw.board 跑的是 ~/.mmw/installed-root 记下的那个 checkout 里的 supervisor.py，今天是 v2 的。在已安装的 checkout 里跑一次 mmw-v3/install.sh，plist 改成 v3 的路径，安装器先停掉旧任务再装上新的；v3 的 supervisor 用同一份 ~/.mmw/boards.json，各仓库的端口不变。为什么只有这一步会换，是第 17 课。

本仓库的 .mmw/。它是看板作为产品的配置：harness/target.py 在一个租来的端口上开看板，harness/board_server.py 是它开的那个进程，stories/serve.py 给组件故事页交出看板的网页代码。三处原来写死 mmw-v2，所以 v3 的看板测试其实在测 v2 的代码。现在三处都直接写 mmw-v3/board；docs/specs/task-board/screen-contract.yaml 里 77 处网页代码的路径，和 #553 设计包里两个读产品代码的工具（build_scenes.py、bundle_logic.py），也一样。#546 到 #553 的决定记录、示例数据和从 Claude Design 拉下来的文件是当时定下的内容，没改。

start 多做的一件事。看板的私有 models.json 的行不是 roles.json 的角色表时（比如上一次留下的是 v2 的四行），start 按 hosts.json 的默认值重写一份。

5　搬的时候找到的

找到什么后果怎样处理
v3 当初删看板时，把 test_dispatch.sh 里 6 个看板场景和两个辅助函数（fresh_board_registry、board_registry_port）一起删了放回场景后，其中两个先报「通过」：缺的函数只让 shell 打一行「command not found」，场景照样往下走。这正是 principle-a-check-must-be-able-to-fail 说的那种假通过两个函数照 v2 放回；6 个场景照 v2 放回；另外 4 个开夜场景的输出照 v2 改回带看板地址。我用脚本查了整个文件，没有别的被调用却没定义的函数

8　还没做的

  1. 让 com.mmw.board 常驻跑 v3 看板，就是在已安装的 checkout 里跑一次 mmw-v3/install.sh。安装入口和 v2 的两个安装场景 installboardagent、installcheckboardagent 在第 17 课回来了；跑不跑、什么时候跑，由你定。
  2. 设计包 prototypes/task-board/ 的设置页场景仍是四行。设置页的测试用它当数据，四行也能测出行为，所以这次没动；要让设计稿画七行，是改设计稿，归你定。

9　自测

1．往 roles.json 加一个开会话的角色，设置页要改哪里才会多一行？

行取自 models.json，models.py 保证它和 roles.json 一致；正在跑的看板由 codeversion.py 重启。只有中文说明要在 ROLE_WHAT 加一句，不加也有行（第 2 节）。

2．本仓库的 .mmw/harness/target.py start 发现看板的私有 models.json 只有 v2 的四行，会怎样？

行不是 roles.json 的角色表，start 就按 hosts.json 的默认值重写（第 4 节）。

3．这台机器上常驻的看板跑哪一份代码，由什么决定？

com.mmw.board 的 plist 写的是安装时那个 checkout 的路径，~/.mmw/installed-root 记下它；别的 checkout 怎么改都碰不到（第 4 节，第 17 课）。
