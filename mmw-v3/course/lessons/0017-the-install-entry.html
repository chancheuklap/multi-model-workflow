第 17 课 · 安装入口

安装入口：本机跑哪一份，只由显式安装决定

你指出我总在列「切换之前、切换之后」的清单。查下来，根子在 v3 没有安装入口：v2 靠 install.sh 保证除非你在已安装的 checkout 里显式安装，否则本机跑的那一份不会变；v3 把安装入口删了，这一层空着，我就拿清单和一个环境变量去补。这一课把 v2 的安装入口搬进 mmw-v3/install.sh，讲清这个保证由什么组成，以及顺带找到的一处真毛病：第 5 课定的 start prompt 第一句，在 Claude Code 上开不了 mode。

1　我错在哪，根子在哪

第 11、13、14 课的结尾都写「替换 v2 是一次切换，所有块都搬完再切，只切一次」；第 16 课更进一步，给本仓库的 .mmw/ 加了一个环境变量 MMW_TOOLBOX_DIR，让 v2、v3 两份看板并存，还提醒你「两个 supervisor 会争同一张登记表」。这些都把「换成 v3」当成一件要另外安排、要列清单守着的事。

v2 早就把这件事设计好了：本机跑哪一份，只由一次显式安装决定；仓库里别处的代码怎么改、合进哪个分支，都碰不到正在跑的那一份。v3 一直没有 install.sh：搬 dispatch 的测试时，安装场景也一起删了（imports.tsv 的 J160 记着），打算最后再做，这个保证就跟着没了。我没有先把它搬回来，而是在每一处用清单去补，所以清单越列越长。

现在 mmw-v3/install.sh 照 v2 搬回，保证原样还在。仓库里的东西因此可以直接写落地后的样子：.mmw/ 直接指 v3 的看板，MMW_TOOLBOX_DIR 删掉（第 6 节）。

2　v2 的保证由哪几件东西组成

全部指向一个 checkout。技能是软链，不是拷贝；hook 的命令写的是 ~/.agents/skills/dispatch/scripts/tool-guard.py 这种经过技能软链的路径；两个 launchd 任务的 plist 写的是安装时那个 checkout 的绝对路径。所以「本机跑哪份」等于「软链和 plist 指向哪个 checkout」，只有安装器会改它们。

~/.mmw/installed-root。安装器装完，把自己所在的目录记在这里。别的程序靠它分辨「我是不是已安装的那一份」。

--check 转交。从别的 checkout 跑 install.sh --check，它不核对自己，而是直接执行 installed-root 那一份的 install.sh --check。所以在票的 worktree 里查安装状态，看到的永远是正在跑的那一份，也不会写任何东西。

dispatch.sh check 只在自己是已安装的那一份时修补。每晚开夜前它先跑一次安装核对；缺东西时，只有自己所在的 checkout 就是 installed-root，才跑 install.sh 修；否则只把缺的报出来。

剩下一条靠规矩。如果有人直接跑一份不是已安装的 dispatch.sh 去开夜，它会开它自己那份的看板和会话。这没有机制挡，靠的是根 AGENTS.md 的 Self-hosting boundary：一个 watch 期间，只用已安装的那一份。

已安装的 checkout 移到新提交（根 AGENTS.md Gotchas 里四步发布的第三步），host 下一次调用读到的就是新提交里的文件；这一步也是你决定什么时候做。

4　装在 v2 上面时，接管什么、不碰什么

换成 v3 就是一件事：在已安装的 checkout 里跑一次 bash mmw-v3/install.sh。这是你要授权的一步。它做的事，由新加的场景 installtakesover 在一个看起来装过 v2 的临时家目录里逐条核对：

装之前装之后
指向 v2 的技能软链，名字在 v3 也有（dispatch、tdd）原地改指 mmw-v3/skills/
指向 v2、v3 没有的技能（implement）摘掉
别的工具装的技能软链一个字不动
CLAUDE.md 指 v2 的 shared.md；mmw-claude.md 指 v2 的 hosts/claude.md前者改指 v3 的 shared.md；后者摘掉
v2 登记的 tool-guard.py hook，旁边有一条别人的 hook原地换成 v3 的那一条，别人的留着；另加一条 SessionStart
installed-root 记的是 v2记的是 v3；接着跑 --check 返回 0，打印 HOOKS-INSTALLED

两个 launchd 任务的 plist 内容变了，安装器先停掉旧任务再装上新的（v2 就是这样写的）；测试里只写 plist、不碰 launchctl，所以这一步在真机上的效果是读代码得出的 归纳。v3 的 supervisor 用同一份 ~/.mmw/boards.json，各仓库的端口不变。

反过来不是一条命令。装完 v3 之后再跑 v2 的 install.sh，它认不出指向 mmw-v3/ 的软链是「本仓库装的」，会报「冲突」并跳过（mmw-v2/install.sh 第 220、916 行）。这是读代码得出的，没跑 归纳。要能一条命令退回 v2，得另做；做不做由你定（第 9 节）。

5　mode 怎样进会话

找到的毛病。第 5 课决定 2 定的 start prompt 第一句是 Use the mmw-mode skill.，理由是「v2 开每个会话都用 Use the X skill，在五个宿主上都有效」。这对 v2 的 implement、code-review 成立，它们模型可以调用；mmw-mode 不一样，它的 frontmatter 有 disable-model-invocation: true。Claude Code 的文档对这种技能说得很清楚：Claude can't invoke the skill on its own，它的 Description not in context，模型硬调时 Claude Code blocks the call。所以 Claude Code 上的 worker 和 reviewer，按那一句开不了 mode。

现在。dispatch.sh 算出它旁边 mmw-mode 的 SKILL.md 路径，第一句改成「Read the mmw-mode skill's SKILL.md in full before any work: 路径。」。读文件不受 disable-model-invocation 限制，五个宿主都一样。pstack 的 poteto-agent 本来就是这样写的：先读 poteto-mode 的 SKILL.md。

钩子也是这次才有。第 5 课定了「SessionStart 钩子在有 .mmw/ 的仓库里替你开的会话载入 mode」，但 v3 一直没有写这个钩子。现在 mode-hook.py 在 mmw-mode 的 scripts/ 里，由安装器挂到 Claude Code 和 Codex 上：会话所在的 git 仓库根目录有 .mmw/，就往上下文加同一句话；没有就什么都不说；Cursor 读到这个钩子时自己退下。Grok 不能注入上下文（第 5 课 U-2 测过），所以 Grok 上靠你输入 /mmw-mode。

9　还没做的

  1. 在已安装的 checkout 里跑 bash mmw-v3/install.sh，就是换成 v3。跑不跑、什么时候跑，由你定；前提是那个 checkout 已经移到含 v3 的提交。
  2. 退回 v2 现在不是一条命令（第 4 节）。要做的话，是让 v2 的安装器也认得指向 mmw-v3/ 的软链，并摘掉 SessionStart 那条钩子；要不要做，由你定。
  3. mmw-v2/ 在 v3 装上之前不能从仓库里删：已安装的 checkout 一移到没有 mmw-v2/ 的提交，本机所有软链就断了 归纳。
  4. 根目录的 AGENTS.md 还在描述 v2。

10　自测

1．在主工作区改了 mmw-v3/skills/tdd/SKILL.md 并合进 dev。本机的 Claude Code 下一次用 tdd，读到的是哪一份？

软链指向已安装的 checkout；合进 dev 不移动它（第 2 节）。

2．在一张票的 worktree 里跑 mmw-v3/install.sh --check，会怎样？

它执行 installed-root 那一份的 --check，只核对，不写（第 2 节）。

3．start prompt 第一句为什么不再写 Use the mmw-mode skill.？

mmw-mode 有 disable-model-invocation: true，Claude Code 上模型调不了；读文件不受这个限制（第 5 节）。
