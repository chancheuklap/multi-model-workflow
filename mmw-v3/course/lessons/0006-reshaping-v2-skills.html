一个会话做完的一件事是一份 playbook，一个技能只是一个动词

2　v2 技能里的六种路由，各去哪

「路由」在这一课指技能里决定「接下来读哪份、做哪步」的文字，按它在问什么分六种。分法是本课的。

分界只有一个问题：这个分支由谁决定？由技能手上的输入决定的，留在技能里。由谁在调用、调用方走到哪、之后轮到谁决定的，搬到调用方那边：④ 写成调用方最后一步的「Run 下一份」，⑤ 的每一种进度是一份触发不同的 playbook，③ 由打印那一行的脚本写明去哪读（lease.py 的拒绝在 v2 里已经这样做）。对照 pstack：一个子代理逐行读了它 25 个技能的 54 份 .md，①到⑤一处也没有；按角色分路的 20 处，全是技能把提示文件分给自己开的子代理，就是图 5 右边的做法。

3　拆的规矩

六条。前五条管 playbook 怎样划，最后一条管技能。

规矩
  1. 交付不同，才是另一份 playbook。这是 playbooks/README.md 已有的标准：看 **You own …** 和 **Reply:** 两行，两行都和已有的一份一样，就是同一种任务，改那一份。只发生一次的事不开一份；只是交给一个技能的事也不开，在步骤里点名那个技能。
  2. 一个会话从开始做到交付的，是一份，叫醒和等你开口都不切开。夜里的机器就是这样：一个 orchestrator 会话从 open 守到 finish，一个 worker 会话从认领做到关票，#<n> reviewer.reported 叫醒的就是同一个 worker（第 5 课决定 8）。换上来的 worker 照 verify-ticket.py --preflight 打印的 RESUME: 那一行接着做，那一行写的是步骤标题，所以前后的步骤必须在同一份里。v2 night.md 的 ## 6. Merge the accepted night 写的也是同一个会话：Only after the user has accepted the result, the orchestrator runs对照 pstack：Orchestrate 一份 2,636 词，处理所有叫醒；Autopilot-full 等你明确说开始，也写在它自己的步骤里。
  3. 几种任务都要走、你也可能单独叫的一段做法，单独成一份，用名字调用。MMW 里只有一段是这样：Revise a spec，改已发布 spec 里的一个决定。Cut tickets、Write the screen contract 和 Run a night 的 contract 子票一节都要做它，你也可能直接要求改 spec。pstack 的 Opening a PR、Babysit、Shipping 分成三份，是同一个理由：每一段你都可能单独要求，Opening a PR 被 8 份 playbook 点名。
  4. 几份都写的格式，放进管那件东西的技能。票的格式（to-tickets 第 4 步怎样写判据、<issue-template>、person-ticket.md）由 Cut tickets 写，也由 Run a night 收尾时给 finding 写票，由 verify-ticket 的 --lint 查，所以进 verify-ticket。只有一份 playbook 写的模板留在那一份里：spec 的模板在 Write a spec 里，像 pstack 把 PR 正文的格式写在 Opening a PR 里。
  5. 同类兄弟按节借，不另拆。playbooks/README.md 写着 A playbook may name a step of another playbookRun one ticket 是夜外的一张票，叫醒和 contract 子票两节照 Run a night 的做，像 pstack 的 Autopilot-stack 写 per Autopilot-full step 4
  6. 技能只做一件事，不写谁在用它。图 1 的①到⑤删掉，⑥留下。

5　轻的路径：Make a small change，以及 Investigation 和接入仓库

v2 里产品代码只有一条路：写 spec，切票，夜里跑。小到改一行字的事也要走完。v3 要有一条轻的路。先看 pstack 怎么做。

pstack 的轻路径

pstack 根本没有「票」和「夜」。它的单任务 playbook（Bug fix、Feature、Refactoring）都在你的会话里一次做完，最后一步都是 Run Opening a PR。它轻在没有 spec 和票，不轻在检查上。读这三份原文，安全靠五样东西：

靠什么pstack 原文
先钉住行为，再动代码Pin the behavior contract first.Reproduce it yourself on the matching surface
写代码的和看代码的分开Mandatory: no skip-with-reason escape, and Laziness Protocol does not override it (the gain is review separation, not lines saved).You own every subagent's work. Review the diff and write your own summary
在真实的界面上验证"Inconclusive" or wrong-surface is not a pass. Flag it.
失败的测试先进历史，修复在上面Stage the commits so the failing repro lands before the fix in git history.
外面还有一道审Opening a PR 开出的 PR 由 bugbot 和你再看；合不合由你说了算（Babysit、Shipping 要你开口）。

另外，真正的闲聊和一句话的小事，pstack 连 mode 都不进：mode 的 frontmatter 写着 Casual turn or user opts out -> don't.

MMW 的 Make a small change

MMW 没有 PR，夜里的票由 land 直接合进 base 分支；orchestrator 收尾时自己修的小问题，也是直接提交、推到 base 分支（v2 night.md ## 4. The closing pass 的 The ones you fix）。所以 MMW 的轻路径照这个先例交付，把 pstack 的五样换成 MMW 已有的东西：

  1. 说清要改的行为，判断够不够小。用你的原话写下要变的行为。要你做产品决定、或一个会话做不完的，停下，交给 Write a spec（还模糊就 Chart a map）。你报来的缺陷不走这里，走 Bug fix（你已定）。
  2. 先写一个会失败的测试。用 tdd。只改文案或配置、没有行为可测的，写下改完以后用来证明的那条检查。
  3. 写代码。
  4. 在真实的产品上验证，再跑仓库自己的检查。照 principle-prove-it-works；页面有 screen contract 的，用 ui-acceptance 的判官；仓库的检查命令由接入仓库时配好。
  5. 请一个没写这段代码的读者看一遍。用 code-review，从改动开始前的那个提交审到 HEAD，把你的原话原样当作 spec 给它。每条意见回到代码上核实，成立的改，不成立的留理由给你。这一步对应 pstack 的「写和看分开」加 bugbot。
  6. 提交，推到 base 分支，告诉你。照 night.md 那一段的三条：一个原因一个提交；只碰原因要求的部分和证明它的测试；提交信息引用测试输出的那一行。原文接着写 A fix that exceeds those three is a ticket after all.这也是轻路径的上限。

交回你的：改了什么，验证的证据（失败再通过的输出原样贴），你该亲手看哪里，审出的意见各自怎么处理。归纳：这六步是我按 pstack 的五样和 layering 分支那份 make-a-small-change.md 拼出来的，写它的那一课再逐条对原文。

它和夜里的路差在哪：没有票，所以没有脚本跑的判据、没有单独会话的 reviewer、没有关票记录。补上的是第 2 步的测试、第 4 步的验证和第 5 步的第二个读者。差的那一截，就是第 5 步交回里「你该亲手看哪里」。

Investigation：照抄 pstack，连同 how、why

你问一个问题，会话只读不改，交回一个带出处的答案。比如「这个功能现在怎么工作」「当初为什么这样做」「我们确定吗」「X 和 Y 选哪个」。你定了照抄 pstack 的 Investigation（145 词），连同它点名的三个技能一起引入。名字也照抄，不叫 Answer a question：少一层翻译，以后对照 pstack 原文时一眼对得上。原文的核心两句：Investigation requests are read-only. They produce a cited explanation or a recommendation, not a code change.If it does, hand back to the user and re-route to Bug fix or Feature.

接入仓库：setup-mmw

pstack 的接入是一个技能 setup-pstack：你叫它，它查出你有哪些模型，问你预算，写一份配置；Overwrite the whole file so re-runs stay idempotent.最后一步看项目有没有办法驱动真实的应用来证明改动，没有就提出替你生成一个。MMW 照这个样子做一个 setup-mmw：你在要接入的仓库里叫它，它把下面每一项查一遍，能配的配上，配不了的告诉你在哪里点什么，最后再查一遍，交回一张全绿或标明还差什么的清单。重跑不坏事，所以它也是已接入仓库的体检。做成技能不做成 playbook，是因为你会直接叫它的名字，它还要带一个只读的检查脚本，pstack 也是这样做的。这是工程上的决定。

9　从「MMW 导论」借了什么，没借什么

MMW 导论

多会话的 playbook 开头有一张 Where you are 表，每个会话从 tracker 上的状态进到对应的一步。

这一课

Run a night 的第 1 步已经这样做，Work a ticket 的第 1 步靠 RESUME: 那一行做同一件事。白天的地图则拆成触发不同的两份（Chart a map、Resolve a map ticket），由 mode 的路由行按地图有没有、清没清送到其中一份。

MMW 导论

「Research a question」是一份 playbook。

这一课

pstack 有对应的一份：Investigation，只读，点名 how、why、unslop，要改代码时交还你重选。所以它不是「只交给一个技能」，规矩 1 管不到它。你定了照抄它，名字也用 Investigation（第 5 节）。

MMW 导论

「Make a small change」：会话当场改产品代码，自己验证，再请一个子代理读一遍。

这一课

借，按 pstack 的单任务 playbook 和 night.md 自己修的规矩改写（第 5 节）。你报来的缺陷不走它，走 Bug fix。

MMW 导论

writing-skill-sets 的 SKILL.md 有一张「哪一刻打开哪份」的时刻表。

这一课

不借。这正是图 1 的②。

11　以后各课的顺序

顺序由你定。我的建议是先夜里，再白天：

  1. 第 7 课：上一节的改动和那道检查，包括引入 Investigation、how、why。
  2. 第 8 课：Work a ticket、Review a ticket，连同 code-review 的几条轴、ui-acceptance 的判官，以及前三条原则候选；Make a small change 用的是同一套，放在这一课。
  3. 第 9 课：Run a night、Run one ticket、Bug fix，连同 retro 和 triage 处理交回的票。
  4. 第 10 课：setup-mmw，在隔离目录里接入一个假仓库验证，再给 agentflow 和 xiaohuangya 各跑一次。夜里的几份要它配好的东西，所以紧跟在夜里之后。
  5. 第 11 到 13 课：Write a spec、Revise a spec、Cut tickets 和票的格式进 verify-ticket；Chart a map、Resolve a map ticket；四份设计。
  6. 最后：C 组和 exe-release。

先夜里的理由：夜里的四份填完，v3 就能在隔离的测试目录里把一张票从开工跑到关票；v2 写的票格式相同，夜里不用等白天那几份。

12　自测

1．worker 读完 reviewer 的报告，要修两处、驳回一处，再关票。v3 里这一段写在哪？

reviewer.reported 叫醒的是同一个 worker 会话（第 5 课决定 8）；换上来的 worker 照 RESUME: 那一行写的步骤标题接着做，所以前后的步骤要在同一份里。交付也没变，还是这张票关上（规矩 1、2）。

2．票的格式（判据怎样写、<issue-template>）由 Cut tickets 写，Run a night 收尾时也写。它放在哪？

几份都写的格式，放进管那件东西的技能（规矩 4）。票由 verify-ticket 的 --lint 查，格式和查它的规则在一处。它不是一段你会单独叫的做法，所以不是 playbook；它也不是一条判断，所以不是原则。

3．早上你读完 NIGHT SUMMARY，说验收，然后跑 finish。为什么这不是单独的一份 Accept a night？

v2 写的是 orchestrator 在你验收后跑 finish，同一个会话从 open 守到 finish。等你开口不切开（规矩 2），就像 pstack 的 Autopilot-full 在自己的步骤里等你说开始。交回的票由你用 triage 处理，那是一个动词，不需要一份 playbook。

4．manage-agents-md 按仓库里有没有 AGENTS.md 分成 create 和 rewrite。v3 里它去哪？

图 1 的⑥：分支由技能手上的输入决定，同一件事，交回同一种东西，调用方不变。

5．Make a small change 做到一半，发现要动三个模块、还得你定一个产品上的取舍。接下来呢？

轻路径的上限照 night.md：超出「一个原因、只碰原因要求的部分」就是一张票。要你做产品决定的，更是 spec 的事。拆小提交和第二个读者都补不上缺的那个决定。
