第 1 课 · pstack 的组件

pstack 由哪些组件组成，每种文档怎么写

pstack 是一个 Cursor 插件。里面给 agent 读或运行的东西分八种，每种有固定的文件形状、固定的被读时机、回答固定的一个问题。这一课先把八种认全，再逐种看文档结构，最后逐节读 poteto-mode/SKILL.md。

这一课回答
  1. pstack 有哪些组件，每种由什么文件组成
  2. 一次任务里，每种在什么时候被读
  3. 每种文档的结构，每一部分写什么
  4. poteto-mode/SKILL.md 每一节写什么
依据的原文cursor/plugins 提交 e43c7ee（2026-10-03），pstack 0.15.9。同一版已作为子树放在 mmw-v3/upstream-pstack/。下文每个文件名都链到这一版的原文。
主要来源，建议先读pstack guide（作者写给使用者的 10 章指南），然后 poteto-mode/SKILL.md 原文。

1　pstack 里有什么

从图 1 能看出的三件事
  1. playbook 不是技能。23 份 playbook 是 poteto-mode/ 里的普通文件，没有 frontmatter，不能用 /名字 调用，只有 mode 能打开它们。
  2. 原则是技能，而且一条原则一个技能。24 个 principle-* 目录各只有一份 SKILL.md。README 说这样做是为了「other skills can reference a principle by name」。
  3. references/ 和 scripts/ 总是挂在某一个技能下面。pstack 里没有全插件共用的 reference 目录。

「八种组件」是本课的分法，不是 pstack 原文的说法。原文对它们的叫法：mode skill（README 也叫 routing skill）、playbook、principle、skill、references/、scripts/、subagent、rule。后文都用这些原名。

2　一次任务里，每种在什么时候被读

从图 2 能看出的三件事
  1. 每次都读的只有 mode。原则每次只读索引里的一行，要应用时才读全文；playbook 只读匹配上的那一份；技能、reference、脚本都要等某一步点名。
  2. 模型不会自己挑技能。50 个技能里有 49 个在 frontmatter 写了 disable-model-invocation: true，唯一没写的是 setup-pstack。Cursor 文档说，写了这一行的技能「only included when explicitly invoked via /skill-name」。所以在 pstack 里，一个技能会被用到，只有三条路：你输入 /名字，mode 的某一行点名它，或者某份 playbook 的某一步点名它。
  3. 同一条规则有两个读的时机。Non-negotiables 的触发行和原则全文都不挂在某一步上：情境一出现就用，不管当时在跑哪份 playbook。

3　每种组件的文档结构

每张卡片是一份文件从上到下的样子：左边是文件里的原样标记，右边是这一部分写什么。mode 单独放在第 4 节。逐份的细节、各部分的字数和例外，在参考页。

playbook23 份，127–2,636 词例：poteto-mode/playbooks/bug-fix.md　回答：这一种任务从头到尾怎么做
### Bug fix没有 frontmatter

标题，就是 mode 路由行里的名字。

**You own …**

第一行粗体：这一次你负责什么，什么交给子代理。

You own this task. Plan, review, verify.
一段话

整份 playbook 的做事态度。

Be scientific. Every shipped line traces to runtime evidence.
1. … 6.

编号步骤，一步一件事，点名这一步用的技能、原则或脚本。这些步骤会被逐字抄进 todolist。

3. Plan the fix. If it crosses a function boundary, `architect` first.
一段话

对所有步骤都成立的规则。例：Feature 末段说，耦合的代码交给一个 owner。

**Reply:**

这份 playbook 的回复里独有的内容。通用写法不在这里，在 mode 的 ## Writing the reply。

Reply: what was broken, root cause, fix, how you verified.
最大的两份（Orchestrate、Multi-phase plan）在里面用 #### 分小节。Opening a PR 没有编号步骤，也没有 **Reply:**。

name: principle-<名>。description 以 Apply 开头，先写条件，再写规则，24 份都是这样。disable-model-invocation: true。

# Attack the Premise

标题，下面一两句规则。

**Why:**

一句理由。24 份里 17 份有。

Why: Each failure under a shared premise is evidence about the premise.
**Pattern:** 等

能照着检查的做法，一条一个要点。标签各份不同：Pattern、The test、Rule……

**Stop:**

什么情况下停下，不再往前做。

This principle is distinct from …

和容易混的另一条原则划清边界，链到那条原则。

mode 技能2,971 词poteto-mode/SKILL.md　回答：这个人的工作方式下，什么情况用什么，一个任务走哪份 playbook
frontmatter

description 写风格和触发说法。disable-model-invocation: true：只有你输入 /poteto-mode 才载入。icon、color 是它当 Custom Mode 时的徽章。另有 mode: true 和 reminder 两个字段，Cursor 文档的字段表里没有。按字面看，reminder 是每一轮提醒 agent 判断这一轮要不要套用 mode（推断，未见官方说明）。

## Non-negotiables691 词
何时用任务进行中任何时刻，情境一出现就用

开头一段：原则支撑每一条触发；回复里点名每条影响了决定的原则，以及它改变了哪个选择；只点名这次会话读过全文的原则。接着 18 行「Remaining triggers」，每行是「情境 → 用什么」，指向一个技能、一份 playbook、一条原则或一份 reference。大多数行只点名、不写做法；问用户之前先分类的那一行是例外，把判断规则写在行里。

Before commit → the `deslop` skill from the `cursor-team-kit` plugin (`/deslop`).
## Principles694 词
何时用任务开头读索引；某条的条件出现时读它的全文

开头两句用法，然后分五组共 24 行：Core、Architecture、Verification、Delegation、Meta。每行三样东西：名字和技能名、条件、一句规则。

Prove It Works (principle-prove-it-works). After a task, before declaring done. Verify against the real artifact, not a proxy or "it compiles".
## Autonomy106 词
何时用要不要先问你、能不能直接做的时候

四段，各以粗体开头：Just do it（可撤回的事直接做）、Always pause（不可撤回的写操作先停）、Session overrides（「going to bed」之类的话让它一直做下去）、No is an acceptable answer（被问意见时给真实判断）。

## Subagents392 词
何时用开子代理之前

开子代理用哪种 subagent_type；每次 Task 调用的默认设置（后台、文件指针而非贴全文、按角色选模型）；你对子代理的产出负责；默认开新的子代理，什么情况才复用旧的。

## Writing the reply243 词
何时用写回复时

所有回复共用的写法：短句、不用长破折号、给谁看、每个结论带证据或标明是推断。最后说明分工：每份 playbook 的 **Reply:** 只写它独有的内容。

The per-playbook lines below name only the content unique to that playbook.
## Comments67 词
何时用写代码注释时

注释和回复同一个标准：只留代码表达不了的 why。

## Playbooks699 词
何时用任务开头选 playbook

先写用法：把匹配上的 playbook 的步骤逐字抄进 todolist，不做的步骤写 skip: <reason>。再写两条路由例外：大型或没有合适的走 figure-it-out，长期的整个项目走 Orchestrate。最后 23 行路由，每行：名字、什么任务（容易混的写出区别）、文件路径。

Hillclimb. … Distinct from Perf issue, which is a one-off fix. `playbooks/hillclimb.md`.
从这张图能看出的两件事
  1. 各节是按「什么时候用」分的，不是按主题分的。每一节对应一个时刻：开头选路、情境出现、要决定、要问之前、开子代理之前、写的时候。
  2. mode 里几乎只有点名，没有做法。做法在别处：触发行指向技能，原则行指向原则全文，路由行指向 playbook。mode 自己写全文的只有对每个任务都成立、又没有别的去处的几件事：Autonomy、Subagents、Writing the reply、Comments。

5　自测

先不看上文，凭记忆选。

1．「提交之前，先跑 deslop。」这一句在 pstack 里写在哪？

在 mode 的 ## Non-negotiables：「Before commit → the deslop skill」。提交可能发生在任何一份 playbook 里，所以它不挂在某一步上。

2．Prove It Works 的全文，agent 什么时候读？

任务开头只读索引里的那一行。它的条件是「After a task, before declaring done」，## Principles 开头要求应用哪条原则就读哪条的全文，所以到宣布完成之前才读。

3．Bug fix 的回复里要贴「先失败、后通过的复现输出」。这一句写在哪？

写在 playbooks/bug-fix.md 的 **Reply:**。所有回复共用的写法在 mode 的 ## Writing the reply；只属于这一种任务的内容在这份 playbook 自己的 **Reply:**。

4．pstack 的 50 个技能里，有几个是模型不经点名、自己就能挑来用的？

只有 setup-pstack。另外 49 个都写了 disable-model-invocation: true，只能经你输入 /名字、mode 点名或 playbook 点名才用到。
