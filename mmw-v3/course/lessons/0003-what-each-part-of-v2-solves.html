第 3 课 · MMW v2 的每个部分解决什么问题

v2 为一件事而建：你不读代码，也能信任一张关掉的票

根 AGENTS.md 的第一句：「MMW is the user's toolbox of skills shared across hosts, repositories and machines, together with the landing pipeline behind them (spec → ticket → a worker dispatched for the night → closed ticket) and a local task board.」它的中心是那条流水线；流水线要做到的事，implement 技能写得最直接：The checks exist so the user can trust a closed ticket without reading its code.这一课先看一个需求在 v2 里怎么走，再看每个部分各自解决这件事里的哪一个问题、依赖什么假设，最后看 v2 和 pstack 在结构上的差别。

这一课回答
  1. 一个需求在 v2 里从头到尾怎么走
  2. v2 的每个部分解决什么问题，依赖什么假设
  3. v2 把一个任务的顺序放在哪，和 pstack 差在哪
依据MMW v2 现役版本，dev 分支提交 0bff6b1：技能原文、docs/adr/ 的 31 份设计决定、docs/contexts/night/how-it-works.md。原文没有直接写、由本课归纳的，标了 归纳。
主要来源，建议先读docs/contexts/night/how-it-works.md：夜里的机器怎么运转，start 和 advance 做什么、事件、叫醒、判活。

1　一个需求在 v2 里怎么走

从图 1 能看出的三件事
  1. 白天和夜里的分界决定了一切。夜里没有人可问，所以需要你决定的事，都在白天当面问完，写进票里。to-tickets 的第 4 步用五个问题给每条规则找去处：能让机器比对的，写成 CHECK: 命令和 EXPECT:；要判断的，交给另一个会话的 code review；要看一个人反应的，单独开一张给人的票；机器本可判定、只是够不着的，先造够得着它的工具；是选择而不是检查的，The user is here now, so ask them。
  2. 一张票关掉，要经过三道互不相信的检查。脚本跑判据，另一个会话审代码，审完改完再跑一次全部判据。--closeout 只认最新那一次运行（ADR 0026）。
  3. orchestrator 只在被叫醒时动作。它起完 worker 就结束回合；叫醒它的是票上的事件，经 relay 送到。

2　每个部分解决什么问题

下面八张卡片和图 2 的八组一一对应。每张四行：这一组解决的问题；v2 的做法；做法依赖的假设，假设不成立时这一组就不起作用；出处。

1 白天写票把想法变成夜里能无人执行的票

问题
夜里的 worker 遇到没说清的地方，没人可问：要么停下，要么自己猜。
做法
白天当面把决定问完（grilling；一次会话装不下的大工作用 wayfinder，拆成一张张决策票逐个解决），写成 spec（to-spec），再切成票（to-tickets）。每张票有固定的几节：## Parent、## What to build、## Read first、## Seam、## Owns、## Acceptance criteria。夜里第一次 advance 之前，verify-ticket.py <spec> --lint 检查整批票。
假设
需要你决定的事，白天都能问到；判据能写成一条机器能跑的命令。做不到的，to-tickets 的五个问题把它分到判据以外的去处。
出处
to-tickets 的 ### 4. Write each acceptance criterion；wayfinder、to-spec 的 description。

2 界面定稿的设计原样落进产品

问题
界面做得对不对，agent 看一眼截图说「看起来对」不可信；设计在仓库和设计工具两边各改一份，就不知道哪份算数。
做法
设计只在 Claude Design 里定稿，仓库里的设计包只由 design-pages 的 pull 写入（ADR 0029）。write-screen-contract 把每个控件该发什么请求写进 screen-contract.yaml。界面是否和设计一致，在组件级离线比对 accessibility tree 和像素；控件发不发请求，在 API client 边界断言，并配一道「跳过点击必须变红」的 negative control（ADR 0011）。
假设
展示组件能拿同一份场景数据单独渲染；设计稿在 Claude Design 里已经签字。
出处
ADR 0011、0028、0029；ui-acceptance 的 SKILL.md。

3 一张票你不读代码，也能信它关得对

问题
写代码的 agent 自己说「做完了」不可信，而你早上不读代码。
做法
worker 按 implement 的 ## Closing steps 八步收尾：合进最新 base，跑全部判据；把自作主张的决定贴到票上；起 reviewer，按 code-review 的四个轴审；修 finding 之后再跑一次全部判据；--closeout 关票。A criterion passes only when its CHECK exits 0 and its output matches EXPECT.手动关票由 tool-guard.py 拦住：`gh issue close` skips all of that and leaves a closed ticket nobody can read in the morning.
假设
判据本身写对了。判据已经是绿的、它要检查的东西却坏着，这种情况 closing pass 的第 2 步专门把它开成新票，并要求一道 negative control。
出处
implement 的 ## Closing steps；ADR 0026；dispatch/references/night.md 的 ## 4. The closing pass。

4 编排没人看着，不停也不乱

问题
夜里几个 agent 并行，你不在：谁开下一张票，谁发现某个 worker 已经死了，一道检查没跑却看起来像通过了怎么办。
做法
票的状态写在票上：每条协议评论末尾有一个 <!-- mmw {...} --> 事件块，状态是从头重放这些事件算出来的，叫 fold（ADR 0019）。agent 之间不轮询：「一个 agent 起了另一个 agent 之后就结束回合」，由事件叫醒（0010）；夜里没有定时器（0017）；relay.py 读票上的事件，叫醒等它的会话。判活分三层，都不是 agent，不花 token：turn-guard.py、watchdog.py、只由 watchdog 写的 worker.lost（0021）。脚本只做工具，判断归 orchestrator（0009）。每道闸口都要回答「它跑了一遍却什么都没做，有人会发现吗？」（0008）
假设
GitHub 一直可用，因为事件存在票上；runner（orca、paseo、herdr）能起会话、能回答会话还在不在。归纳
出处
ADR 0008、0009、0010、0017、0019、0021、0022。

5 合并并行的票合在一起不坏

问题
几张票同时改一个仓库，各自都绿，合在一起可能冲突，或者互相弄坏。
做法
每张票的 ## Owns 写明它改哪些文件，能并行的两张票不改同一个文件。落地以 GitHub 上的 origin/<base branch> 为准：先合，再跑仓库检查，再 fast-forward 推送；合不进去就是 ticket.bounced，第一次退回 worker 队列，第二次交给早上的 triage（ADR 0023、0027）。整批做完后，reverify 在合并后的 base 上把每张已落地票的判据重跑一遍。review 发现的、不属于这张票的问题，closing pass 按四步定去向，默认 orchestrator 自己改，不开新票（0012）。
假设
切票时 ## Owns 切对了。切漏了，worker 开一张 contract 子票：one file has one writer at a time and the cut missed an edge
出处
ADR 0012、0023、0027；implement 写代码的规则。

6 早上几分钟看懂这一夜，再收尾

问题
你醒来，要很快知道这一夜做成了什么、哪里要你看、要你做什么。
做法
summary 贴出 NIGHT SUMMARY，同一个会话紧接着用 retro 复盘，贴出 NIGHT RETRO。你验收之后，orchestrator 跑 finish，把 base branch 合回 project branch 并清理（ADR 0025）。合进默认分支是你的发布决定，不归 MMW。任务板 mmw-v2/board/ 在本机网页上显示这一批票的状态。
假设
你会读总结并做验收；没有验收，finish 不跑。
出处
dispatch/references/night.md 的 ## 5、## 6；ADR 0025。

7 工具箱本身一套技能在五个宿主上都能用

问题
同一套技能要在 Claude Code、Codex、Cursor、Grok、Pi 五个宿主、多个仓库、多台机器上都能用，而且改一处处处生效。
做法
不打包成插件，由 install.sh 散装到中性目录（ADR 0003、0006）；skills.txt 一处决定装哪些技能。不交付自定义 subagent，用宿主自带的通用 subagent（0015）。用户级提示词的源在仓库里：prompt/shared.md 就是你现在的 ~/.claude/CLAUDE.md，render.py 为其他宿主生成 AGENTS.md（0007）。改了上游技能的，理由写进 merge-notes/。
假设
各宿主读同一种 SKILL.md 格式，都提供通用 subagent 和 hook。归纳
出处
mmw-v2/install.sh 开头的注释；ADR 0003、0006、0007、0015。

8 单件事不属于流水线

问题
各自不同：给仓库配 linter（code-checkers）、按固定格式写 AGENTS.md（manage-agents-md）、打安装包（exe-release）、讲课（teach）、写交接文档（handoff）……
做法
每个技能做一件事，靠 description 被调用，不在流水线的顺序里。
假设
这件事的说明能放进一份 SKILL.md 和它的 references。
出处
各技能的 description。
从这一节能看出的
  1. 第 3、4、5 组占了 v2 大部分的机制，它们都在回答同一个问题：你不在场时，凭什么相信结果。回答的方式都是把要信任的东西做成程序能核验的：判据是命令，状态是事件，叫醒是脚本发的，关票只有一条路。归纳

3　v2 把一个任务的顺序放在哪

从图 3 能看出的
  1. v2 没有 mode，也没有 playbook，但有和它们形状相同的内容。implement 的 ## Closing steps 和 references/night.md 是编号步骤、一种任务一份、写明交回什么，形状和 pstack 的 playbook 一样。归纳
  2. v2 一直在上下文里的那一层，内容和 pstack 不同。prompt/shared.md 讲谁做决定、怎么汇报；pstack 的 mode 讲用什么、走哪份 playbook。归纳
  3. 迁移时要问的，是第 2 课那几个问题，不是「这段该搬到哪一层」。例如 implement 的八步收尾有几处在用、谁在哪一刻需要它、哪些已经由脚本强制。

4　自测

1．夜里一张票的 worker 写完代码、跑过判据，觉得全绿了。它能直接关票吗？

还要起 reviewer、修 finding，再对最终提交跑一次全部判据，然后经 --closeout 关票；手动 gh issue close 被 tool-guard.py 拦住。你的验收在整夜结束之后，针对的是整批，不是单张票。

2．夜里一个 worker 的会话突然没了。是什么让这件事被发现？

判活分三层，都不是 agent（ADR 0021）：turn-guard.py 保证看门进程活着，watchdog.py 发现一张被占着的票长时间没有新事件就去问 runner，会话没了就写 worker.lost，叫醒 orchestrator。夜里没有定时器（ADR 0017）。

3．切票时有一条规则：「错误提示要告诉调用方下一步做什么」。它应该写成什么？

这是一个判断，不是比对。to-tickets 第 4 步第 2 问举的例子正是它：「whether an error message tells the caller what to do next」，由另一个会话的 code review 判断，规则写进 spec 的 ## Implementation Decisions，不写成判据。

哪张卡片的说法和原文对不上，或者标了「归纳」的结论你不同意，直接说。
