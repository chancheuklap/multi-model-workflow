1　pstack 是什么

pstack 是 Cursor 的插件仓库 cursor/plugins 里的一个插件，作者 poteto 在 Cursor 工作，也是 React 核心团队成员。它是一套给 AI 编程 agent 读的说明文字，目的写在它的 README 第一段：少写代码，但写的代码质量高、经过验证，这样才敢同时开几个 agent 并行干活。装进 Cursor 以后，你输入 /poteto-mode，agent 就照这套说明工作。

这套说明分成八种组件。下表是每种是什么、什么时候被读；第 1 课有每种的文档结构。

组件是什么什么时候被读
mode 技能一份总说明：工作方式，和每种任务该照哪份 playbook 做。pstack 的叫 poteto-mode会话一开始读一次，之后一直在上下文里
playbook一种任务从头到尾的步骤，比如修 bug、回答一个问题mode 的路由选中它时才打开
principle一条判断规则，写成一个独立的技能，比如「验证要对着真实的东西」mode 里只有一行索引；情况出现时才读全文
技能一件具体事情的做法，比如解释一段代码、删掉文字里的 AI 腔mode 或 playbook 的某一步点名时
references/技能或 playbook 某一步要用的材料，比如派给子代理的提示词模板那一步才读
scripts/程序：能交给程序做或检查的部分某一步运行它
subagent子代理定义：开出来的子代理是谁、先读什么开子代理时
rule配置，pstack 用它记每种角色用哪个模型每个会话自动带着

2　组织方式：一个会话怎样用它

v3 拿的第一样东西不是某个文件，是这套安排。它要解决 v2 的一个问题，ADR 0032「要修的是什么」写着：v2 的规则分在用户层提示、35 个技能和 merge-notes 里，同一条规则有几种说法，一个会话读哪些，全靠各技能的 description 能不能被触发。前两次迁移都卡在说不清每样东西什么时候被读。

这套安排让每条规则按三种时机进入会话。第一种一直生效：## Autonomy 等四节，读了 mode 就在。第二种在某个时刻生效：## Non-negotiables 写「遇到这种时刻，用这个技能」，例如任何要写的文字都过一遍 unslop。第三种在某种情况出现时生效：## Principles 只放 16 行索引，每行写什么情况下用、规则一句话；情况出现时会话才去读那条原则的全文，并在回复里说用了哪条、改变了哪个决定。不用钩子程序，规则也在用到的那一刻才进来。

任务的顺序只有一个家，就是它的 playbook。会话打开 playbook 后，先把步骤逐字抄进 todolist（一张待办清单），不做的一步也留着，写一行 skip: 原因。这样跳过一步会被看见，不会悄悄漏掉。

它依赖两个前提。一是会话真的读了 mode：所以有图 2 上面的三条入口；在 Grok 上只能靠你输入 /mmw-mode。二是路由行彼此分得开：v3 每条路由行都写一句「Distinct from …」，说明它和最容易混的那一份差在哪。它也有管不到的地方：技能派出去的子代理不读 mode，只读派它时写的那份说明；脚本开的会话绝不能做的事（手动关票、把问题放到屏幕上、结束进程）由 tool-guard.py 在宿主执行命令前拦下，不靠它读没读到哪一行。

3　mode 的七节，各从哪来

mmw-mode/SKILL.md 的七节和 poteto-mode 同名同序。下面这张卡是它从上到下的样子，右边写每一节说什么、哪些是 pstack 原文、哪些是 MMW 改的或加的。

mmw-mode/SKILL.md七节，和 poteto-mode 同名同序回答：MMW 的工作方式，和每种任务照哪份 playbook 做
frontmattername、description、disable-model-invocation

disable-model-invocation: true 照 pstack：mode 只有人能开，模型不能自己调用它。pstack 另外四个字段 mode、reminder、icon、color 只有 Cursor 认，没拿。

## Non-negotiables

开头两句照抄：回复里点名每条影响了决定的原则；只点你这次读过全文的。触发留了 pstack 的三条（how、unslop、technical-writing），把 Cursor 自带的 create-skill 换成 writing-for-agents，加了 MMW 的两条（ui-acceptance、setup-mmw）。点名 v3 没有的组件的触发（architect、swarm、Babysit 等）没拿。

Any prose surface → the **unslop** skill. Your reply is a prose surface.
## Principles

两句用法照抄，分组照 pstack（Core、Architecture、Verification、Delegation），加了 Writing 一组。16 行里 7 行是 pstack 的原则，9 行是 MMW 自己的规则，照 pstack 原则的写法改写（第 4 节）。

Read the leaf skill in full for any principle you apply. Each entry names when it applies.
## Autonomy

骨架是 pstack 的四段加粗：Just do it（可撤销的事直接做）、Always pause（收不回的事停下）、Session overrides（你说「别停」就一直做）、No is an acceptable answer（可以说不）。MMW 往里加了只有你能做的决定、在没人看着时怎么办（Unattended 一段）。pstack 另一节里的两句也挪到这里：能跑出来的事实就去跑，不问人；你用自己的话回答，不让你打一个暗号。

## Subagents

只留 pstack 一句：子代理做的你负责，核对后自己写总结。pstack 其余的规定（一律用 poteto-agent，每次指定模型）换成 MMW 的：用宿主自带的通用子代理，不点名模型；要别的模型就开一个会话（第 7 节）；会话开不成时自己做，并说明。

## Writing the reply

pstack 的七条都在：短句、不用破折号、句中不用冒号连接、简短不等于丢内容、先说对用户和接手者的影响、不编链接、每个说法带证据或标「推断」。MMW 把你的用户层提示规则 4、5、6、9 并进来，加了「用通用词」和「列表和表格」两条。

Every claim carries its evidence or its label in the same sentence. Measured, inferred, or guess.
## Comments

照抄，一字未改：代码注释只写代码看不出的「为什么」，测试脚本不写「第一阶段」这类旁白。

## Playbooks

开头一段照抄（开 todolist，步骤逐字抄进去）。路由表换成 MMW 的 27 条；其中 Investigation、Pause safely、Runtime forensics、Trace forensics 四行是 pstack 的原句稍改，Bug fix 一行重写。pstack 的「没有合适的就用 figure-it-out」换成：说哪份最接近、哪里不合，照 mode 的其他节做；太大的想法走 Chart a map。

Open a todolist whose first items are the matched playbook's steps, copied in verbatim, before any task-specific todos.

4　三种文档的写法

v3 的 27 份 playbook 和 16 条原则，不论内容从哪来，都照 pstack 的写法写。写法固定，agent 每次都知道去哪一行找什么：这份 playbook 让我负责什么、做完要回什么。imports.tsv 里写着「the pstack playbook shape」或「pstack's principle format」的 J 记录，就是照这个写法改写的。

playbook 的写法例：playbooks/investigation.md
### 标题

就是 mode 路由行里的名字。

**You own …**

第一行粗体：这一次你负责什么。

You own the answer. Plan, route, write.
一段话

整份的做事态度。

1. … n.

编号步骤，一步一件事，点名用的技能、原则、文件或脚本。v3 多数步骤后面加一行 Done when，写这一步怎样算完；这一行来自 v2 的 implement，不是 pstack 的。

**Reply:**

这份 playbook 的回复里独有的内容；通用写法在 mode 的 ## Writing the reply。

原则的写法例：principle-prove-it-works/SKILL.md
description

一律是同一句：只在被点名时用，不要自己调用。原则靠 mode 的索引行找到，条件写在索引行里。

# 标题 + 规则

规则一两句。

**Why:**

一句理由。

Unverified work has unknown correctness.
**Pattern:** 等

能逐条检查的做法，一条一个要点。

**Stop:**

做到哪里为止。

末行

和最容易混的那条原则怎样分开。

技能也有 pstack 的写法（README 里列了 swarm、how、figure-it-out 三个样板）：标题和一段话说它做什么、交回什么；要派子代理就写清给它的提示词，长的放进 references/；然后是步骤；最后是交回什么、什么格式。v3 的规定写在 mmw-v3/skills/README.md。

5　拿来的 5 份 playbook

Investigation：只读的问题

你问「这个功能现在怎么工作」「当初为什么这样做」「我们确定吗」「X 和 Y 选哪个」，或者问仓库外面的事（某个库怎样用、某个标准怎么规定、某个服务的接口），会话走这一份。它只读不改，交回一个带出处的答案，或一份带利弊表的建议。原文的核心一句：

Investigation requests are read-only. They produce a cited explanation or a recommendation, not a code change.

三步。第 1 步分流：关于本仓库的问题交给 how（问动机时也交给 why）；关于仓库外面的问题，开一个 researcher 会话，它照 research 技能去查一手资料（官方文档、源码、标准），交回带出处的答案。第 2 步写成 how 的五节、核对过出处的 researcher 答案，或一份利弊表。第 3 步过一遍 unslop。how 和 why 怎样工作在第 7 节，图 6。v3 改了这几处：删掉 pstack 第 2 步（它属于 pstack 的 Feature，v3 没有）；加了仓库外问题交给 researcher 的一支；开了会话就结束这一轮、等 relay 叫醒；「不开 PR」改成「不提交、不开票」，要改代码就交回你，转 Bug fix、Make a small change 或 Write a spec；回复要写给你：它做什么、为什么、对产品意味着什么，而不是带你走一遍代码，因为 how 写给的是工程师。

Pause safely：干净地停下

你明说要暂停、要下线、宿主要重启、或上下文快满要被压缩时，会话走这一份。你说「继续」「我去睡了，接着做」时不走。目标是留下一个从零开始的 agent 也能接着做的检查点。

v3 改了两处。第 2 步：pstack 说「不开 PR，不推」，v3 没有 PR，改成「分支原本没推过，这时也不推」。第 4 步：pstack 把续做说明要写哪几项列在这里，v3 改成调用 handoff 技能，并把这张清单（意图、在做什么、进度和已验证的、现状、下一步、关键文件、坑）作为一句加进了 handoff（J5）。一夜因为流水线出故障要停，走的是 Run a night 第 11 步 Suspend the night，不是这一份。

Bug fix：你报的缺陷

你说某处坏了、报错、失败或变慢，会话走这一份。pstack 和 v3 的态度一样：做实验的人的态度，每一行改动都要有运行时的证据；一个「可能有用」的改动只是假设，不是修复。差别在代码由谁写、怎样合进去。

为什么改：pstack 在你的会话里修完，开一个 PR，让 bugbot 和人在合并前再看一遍。MMW 没有 PR，代码只经票落地。所以 v3 的会话只负责诊断、写票和最后的证明；代码交给 Run one ticket：一个 worker 先写会失败的测试再修，一个看不到这次对话的 reviewer 审，land 合进 base 分支。写代码的和看代码的分开，这件事在 pstack 靠 PR 评审，在 v3 靠 worker 和 reviewer 是两个会话。v3 还加了两个出口：复现不了，就告诉你试了什么、还要什么，到此为止；代码照要求做了而你想要别样，那不是 bug，转 Make a small change 或 Write a spec。还有一个分支：症状不报错、只在运行中的产品里出现（内存越涨越高、CPU 空转、卡死、画面花屏），第 1 步不去建复现循环，改走 Runtime forensics；你交来一个已经抓好的文件，改走 Trace forensics。两者的诊断都接回 Bug fix 的「写票」。

Runtime forensics 和 Trace forensics：只诊断，不修

有一类问题不会报错：变慢、内存越涨越高、CPU 空转、卡死、界面花屏。看代码猜不出原因，要从运行中的进程或它留下的文件里取证据。这两份 playbook 管的就是这件事，交回的是一份带出处的诊断：原因在哪个文件、哪个函数、哪一行，证据是什么。修复照常由 Bug fix 写票、交给 Run one ticket。

Runtime forensics 的五步。第 1 步自己起一个实例，按你描述的用法一直跑到症状出现（内存慢慢涨的要跑几个小时），先找出是哪个进程在涨，再抓一份真实的证据文件：CPU 一直很高就抓 CPU 剖析，内存涨就抓堆快照（某一刻内存里所有对象和它们之间引用关系的记录），画面问题就录一段 trace，卡死就抓所有线程此刻停在哪一行。第 2 步把文件缩小到原因：最耗时的那条调用路径，或者从泄漏的对象一路追到「谁还拉着它不放」的那条引用链。第 3 步在自己起的实例上注入探针，验证这个原因确实成立。第 4 步对应到源码的哪一行。第 5 步停掉自己起的实例；仓库没写停止命令的，告诉你哪个实例还在跑、在哪台机器上。

Trace forensics 的五步。文件已经有了（你交来的，或来自够不着的机器，比如客户电脑），只读，不重跑。先认格式、载入，文件没写是哪个版本打出来的就问你（源码对应要用那个版本的 source map）；再变成能查询的形式，然后才去读：trace 用 SQL 查，堆快照用 memlab 的分析命令；找出最耗时的调用或泄漏的引用链；对应到源码；手上有修之前和修之后两份时对比，只有一份时只算「最可能的原因」，不算确认。只有一张堆快照时同理：一张只看得出什么大，看不出什么在涨。

四条安全规定，都是 MMW 加的。第一，在别的机器上启动任何东西之前先问你，并说清这次启动会停掉什么、会连到哪些服务：比如在 Win-PC 上起一个开发版，可能先把你正在用的那份关掉，也可能连上生产环境、花真钱。第二，只在本会话自己起的实例上动手（注入探针、热改代码）；症状只在别人的实例上出现时，比如你正在用的产品，抓证据之前先问你，改它永远不做。第三，证据文件可能带客户数据和密钥，放在仓库外面；tracker 和票上只写文件路径，引用里只出现函数名、产品自己的文件路径和数字。第四，堆快照离开本机之前先用 memlab anonymize 去掉用户数据。用到的工具都写在一份清单 references/forensics-tools.md 里，第 9 节有它替换了什么。

6　拿来的 7 条原则

每条原则在 mode 的索引里有一行，一直在每个会话的上下文里；情况出现时会话读全文，照里面的做法检查自己。下面每张卡写规则本身、在 MMW 里的一个例子、哪些 playbook 在步骤里点名它、v3 加了什么。规则的中文是我的转述，原文在各自的 SKILL.md。

Laziness Protocol偷懒守则，Core 组

规则
用最少的代码和复杂度得到结果。先找能删的再加；调用层次保持扁平，回答一个问题要追过 3 个文件或层就该压平；同一个选择只做一次；改动越小越好；有人要你把一个新信号穿过层层类型和流程时，先找更直接的路。If a human developer would find the code exhausting to maintain, it is a bad solution.
何时
重构、简化、估改动大小，或想加抽象、加层的时候。
谁点名
Make a small change；审查规则 CODING_STANDARDS.md 的 Unexplained addition 和 Lost safeguard 两行，reviewer 按它判。
v3 加了
Keep the safeguards：删减时保留安全检查、防丢数据的错误处理、无障碍支持和需求明说要的东西（你在第 20 课定的）。

Migrate Callers Then Delete Legacy APIs先迁调用方，再删旧接口，Architecture 组

规则
决定换成新接口后，同一波改动里把所有调用方迁过去，删掉旧接口，不留兼容层。前提是没有外部用户依赖旧接口。两套并存会让代码只增不减。
例子
worker 发现缺陷在一个多处共用的函数里：在那个函数里修一次，所有调用方一起好，记在关票评论的 Outside Owns: 下；不在碰到它的那一处绕过去。
谁点名
Work a ticket 第 2 步，Make a small change，Cut tickets，CODING_STANDARDS.md。
v3 加了
改任何被别处调用的代码前，先 grep 出全部调用方；修 bug 也算。

Separate Before Serializing Shared State先拆开共享，再谈排队，Architecture 组

规则
几个同时运行的执行者可能写同一个文件、分支或键时，先问它们是不是真要写同一个东西；不是，就让每个写自己的那份，读的时候再合。真要共享，才用结构保证一次只有一个写：锁文件、分阶段、单一写者。写在说明里的约定不算并发控制。
例子
一夜里几个 worker 同时干活。Cut tickets 第 5 步保证能同时跑的两张票不写同一个文件：给它们加先后（Blocked by），或先切一张票把共用的清单文件拆成每张票一个。每张票有自己的 worktree issue-<n>，每个合并目标一把锁。
谁点名
Cut tickets，Run a night（落在别的票 Owns 里的修复，开一张排在它后面的票），Work a ticket。
v3 加了
没改，只换了 description。

Prove It Works证明它能用，Verification 组

规则
对着真实的东西验证，不信代理指标：文件时间、输出是不是新的、agent 的自述、缓存的截图、「能编译」。验证失败时先怀疑观察的方法。最强的证明是一段能重跑的脚本，留下它的输出给别人重跑。Acting on a wrong inference costs far more than checking the source.
何时
一件事做完、宣布完成之前。
谁点名
Bug fix 第 5 步，Work a ticket，Make a small change，Write AGENTS.md，Ship a release；还有三条 MMW 自己的原则引用它。
v3 加了
两句来自你的用户层提示规则 4：能编译、能部署不等于能用，证明是打开的页面、跑通的流程或第一行失败输出；对自己工作的保留意见是没满足的判据，不是脚注。

Explain the Number说清这个数字，Verification 组

规则
一个测出来的数字是对系统的一个说法。信它、报它、照它做之前，先说清是什么限制了它（「为什么不是快一倍？」），再一一排除它其实测的是别的：请求失败了、命中了缓存没干活、一边没调好、噪声、改的部分小到对整体没影响。A run that went wrong still prints a plausible number.
何时
信、报或照着一个测出来的数字做之前：提速、变慢、吞吐、延迟。
谁点名
mode 的索引行，每个会话都带着。它点名 benchmark-checklist，性能数字照那份清单走完。
v3 加了
没改内容，只换了 description，两处链接改成按名字点名。

A Check Must Be Able to Failpstack 名 Test Behavior, Not Implementation，Verification 组

规则

7　拿来的 5 个技能

how 和 why：解释代码怎样工作、为什么是这样

how 回答「X 怎样工作」，深度是资深工程师刚接手一个子系统时需要的：够建立正确的心智模型，不到逐行注释源码。why 回答「它为什么是这个样子」：哪些力量把代码推成现在的形状，是需求、事故、性能还是一次评审里的讨论。两个都把活分给几个 agent，图 6 是它们怎样分。

how 怎样工作。先判断问题：单个模块、一个函数，会话自己边读边写，不开别的会话；跨多个文件或服务的子系统，先开 2 到 4 个 researcher 会话，每个查一个角度，全部答完后再开一个 explainer，读它们的答案文件，写成一份说明。交回五节：Overview（概述）、Key Concepts（关键概念）、How It Works（怎样运转）、Where Things Live（东西在哪）、Gotchas（容易踩的坑）。拿不准时走简单的路。

why 怎样工作。第一步建「代码锚点」：用 git blame、git log 找到最后改动这段代码的提交，用 gh 读这些提交对应的 PR 描述和评审讨论。第二步列出会话能用的 MCP 服务（MCP 是让 agent 连接外部工具的协议，比如连 Linear、Slack、Sentry），把每个归到七类证据之一：源码历史、工单、长文档、团队聊天、基础设施监控、报错追踪、产品数据仓库。每类开一个 investigator 会话，只查这一类；某类不查，要写下理由，例如「没有能连 Slack 的 MCP，聊天记录查不到」。最后一个 synthesizer 会话把结果合起来，按 references/epistemics.md 的把握程度分开写：查到的、合理推断的、几种可能的解释、不知道的。如果问「为什么」是为了接着改这段代码，它再写一组约束：要保留什么、可以改什么、要避开什么、风险在哪。

v3 改了什么。pstack 里这些 agent 是子代理，每个由一份配置指定模型。v3 里每个都是 dispatch.sh brief 开的独立会话，模型照 ~/.mmw/models.json 里它的角色（researcher、explainer、synthesizer）。理由在 mode 的 ## Subagents：要给不同的 agent 不同的模型，不是每个宿主都让子代理换模型，会话却可以开在任何宿主上。代价是发起的会话要结束这一轮，等 relay 叫醒，所以简单问题不开会话。会话要在 Orca 或 Paseo 里才能被叫醒；不在里面时 dispatch.sh brief 拒绝开会话，mode 的 ## Subagents 规定这时会话自己把活做完，并在回复里说明。另外两处：每份给会话的说明结尾加一行「只读，不改仓库里任何文件」，因为不是每个宿主都有只读开关；why 的 investigator 不进宿主的只读模式，因为那会拿掉 MCP，而且说明里写明它该查哪个 MCP 服务，连不上就在答案里说，因为它跑在自己的宿主上，那里能连的 MCP 可能不同。

谁用它们。mode 的一条触发：非小的改动、架构决定、或有人问「我们确定吗」时用 how。Investigation 第 1 步。Bug fix 第 2 步：how 看出问题的子系统，why 查把 bug 带进来的那次改动。

benchmark-checklist：报一个性能数字之前

一份清单：开测前写下你打算怎样说这个结果，读一遍测量脚本，看机器忙不忙；然后答七个问题，每个都要用一次运行的证据回答，不能凭读代码猜。

问题要查什么
1 为什么不是快一倍说出限制它的东西：一个 CPU 核、一把锁、磁盘、网络，还是压测程序自己先满了
2 调好了吗两边都照生产的设置跑；一边用默认设置，比的是配置，不是做法
3 超出物理极限了吗算一算：去掉一个占 10% 的部分，整体最多快约 11%；超过极限说明测的是别的
4 出错了吗数失败次数，核对输出是对的，不只是有输出
5 能重现吗每边至少 5 次，两边交替跑，报中位数和范围
6 要紧吗同时测用户真正等待的整条路径
7 真的干活了吗确认工作在计时的那段时间里真的发生了

谁用：原则 Explain the Number 遇到性能数字时点名它。v3 改了几处：命令补上 macOS 和 Windows 的对应写法（原文的 nproc、pidstat、strace -c 只在 Linux 上有）；「PR 描述只放一个主要数字」改成关票评论或回复；删掉点名 Perf issue 和 Hillclimb 的一节，因为 v3 没有这两份。

8　没拿的，和为什么

判断的规矩写在 mmw-v3/skills/README.md「The method」第 2、9 条：只有 pstack 有、MMW 没有对应物的组件，要等某个任务需要它才拿，因为它会点名别的组件，拿一个就要连带一串；一句话只要和 v3 已有的不冲突、不重复，可以单独拿。按这个规矩，没拿的分四组：

  • PR 流程：Opening a PR、Babysit、Shipping、Autopilot-full、Autopilot-stack，和 bugbot 评论的处理。MMW 不开 PR，代码由夜里的机器（dispatch.sh、事件、relay、watchdog）落地；ADR 0032 否决了「连 pstack 的脚本和 PR 流程一起照搬」。
  • 长时间、多步的运行：Orchestrate、Autonomous run、Multi-phase plan、Session pickup、figure-it-out。这些事在 MMW 由 Run a night、Run one ticket 和票的事件记录承担，那套机器已经在真实运行里跑过（第 8 课）。
  • 子代理定义和模型配置：poteto-agent 存在，是因为通用子代理会跳过读 mode。MMW 不带子代理定义（ADR 0015）：要读 mode 的 worker 和 reviewer 由起始提示词第一句读，模型记在 ~/.mmw/models.json，只能用 models.py 改。
  • 性能修复和长期调优：Perf issue（带着测量修慢的地方）和 Hillclimb（反复改进一个指标）。Perf issue 要先定「性能数字能不能当夜里票的验收判据」，数字每次跑都有波动；Hillclimb 要在会话里连续提交，MMW 的代码只经票落地。两个技能 create-verification-skill、maintain-verification-skill 给仓库生成「怎样启动、操作、取证」的说明，MMW 已由 setup-mmw 写的 .mmw/、ui-acceptance 和各仓库的运维技能覆盖。原则 Guard the Context Window 在 MMW 只有两份 forensics 用到，写进了它们的步骤。
  • 其余 17 条原则和 20 个技能：没有任务需要，或 MMW 已有做得更多的。例如 architect 既设计又实现，而 MMW 的代码只经 spec 和票落地（第 14 课）；bro 的位置由 v2 的 wait-what 占着；tdd、teach 用的是 mattpocock 的版本。

另有几句 pstack 原文散在 v3 别的文件里，imports.tsv 都记了出处：handoff 里续做说明的清单（来自 Pause safely 第 4 步）；mode ## Autonomy 里「能跑出来的事实就去跑」「你用自己的话回答」「前提错了就说」三句；原则里那段「钉住不变的行为」（来自 Refactoring 第 1 步）。Make a small change 没有拷 pstack 的文字，但它的安全措施是照 pstack 的单任务 playbook 设计的（第 6 课第 5 节）。

9　Cursor 专属的东西换成了什么

pstack 是写给 Cursor 用的，这一批文件里有 7 处只有 Cursor 或 pstack 自己才有的东西。每一处都换成了 MMW 在任何宿主上都能用的做法，imports.tsv 的 J579 到 J582 逐条记着。

10　自测

1．一个会话里，原则 Prove It Works 的全文什么时候被读？

mode 里只有它的一行索引，写着「After a task, before declaring done」。情况出现时会话才读全文，并在回复里说用了它（第 2 节，图 2）。

2．你在 v3 里报了一个 bug。代码由谁写？

v3 的 Bug fix 只负责诊断、写票和最后证明；票交给 Run one ticket，worker 先写会失败的测试再修，reviewer 审（第 5 节，图 4）。

3．v3 的 how 为什么把 researcher 开成独立会话，而不是像 pstack 那样开子代理？

每个角色的模型记在 ~/.mmw/models.json；不是每个宿主都让子代理换模型，会话能开在任何宿主上（mode 的 ## Subagents，第 7 节）。

11　怎样查的，没查什么

查了：imports.tsv 里上游是 pstack 的 28 行，逐个文件和快照比对，确认改动都在 J 记录里；在 mmw-v3/skills/ 里搜每个拿来的组件被哪些文件点名。没查：没有运行任何一个技能或 playbook，「谁点名它」只说明文字里写了，不说明运行时一定走到；pstack 在 Cursor 里实际怎样运行，没试；各条原则的中文是我的转述，不是逐句翻译。
