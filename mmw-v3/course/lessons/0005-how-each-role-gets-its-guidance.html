第 5 课 · 每个角色从哪里拿到指引

MMW 的 agent 由脚本开、被事件叫醒，它们怎样拿到指引

pstack 里只有一个和你对话的会话，别的 agent 都是它当场开的子代理，提示词也由它当场写。MMW 不一样。worker 和 reviewer 由脚本在另一个宿主进程里开，任务说明是前一天写好的票，开了别的 agent 就结束回合，等票上的事件把它叫醒，夜里没有人可问。这是 MMW 和 pstack 最大的不同。每个 agent 都由派发方按工作流派出，所以每个角色要有两份东西：一份教派发方什么时候派、给它什么、回来怎么办；一份教这个 agent 去哪里拿规则做事。这一课先画出 v2 现在每个角色从哪里拿到指引，再给出 v3 的设计：agent 那份怎样到它手上（开工时读什么、怎样选路、怎样知道走到哪一步、被叫醒时读什么），派发方那份由什么组件承担，两份怎样保证对得上。设计只用 v3 已有的组件种类，意图取自 v2，做法参考 pstack，两边都不照抄。

1　MMW 的 agent 和 pstack 的子代理差在哪

五处不同，每一对左边是 v2，右边是 pstack，底下一行是它对 v3 的要求。

谁开它 · v2

dispatch.sh start 让 runner（paseo、orca 或 herdr）在另一个宿主进程里开会话，开工时读到的文字由脚本拼出：The text a session is given when started: which skill to use on which ticket, the standing sentences for working with nobody watching, and the Memory indexes or reviewer Rules for its role.

pstack

只有和你对话的那个会话开 agent，用宿主的 Task 工具，提示词由它当场写。脚本从不开 agent：Agents are spawned, resumed, and drained only through the Task tool. … The CLI never spawns, waits, or wakes anything.
对 v3 的要求：指引不能指望派发方当场写进提示词。它要能由脚本给出，并且在五个宿主上都成立。

任务说明 · v2

白天由 to-tickets 写成票，夜里第一次 advance 之前由 verify-ticket.py --lint 查整批票。worker 开工时读的就是票。

pstack

协调者当场写 brief，字段写不全就不开：The brief is the product. A vague brief fails quietly, because a worker cannot ask you a question.Missing fields are a refuse-to-spawn condition.
对 v3 的要求：夜里的 brief 已经有了，就是票，第 5 节逐个字段对照。技能派出的 agent（advisor、researcher、轴），brief 的规矩已经写在派它的技能里，不另造格式。

走到哪一步 · v2

Where you are is what the ticket's events say, not what this session remembers.implement：重新被开到一张票上，先 --preflight 认领，从它打印的 RESUME: 那一步接着做。

pstack

进度存在 orch 的文件里，重启后重读：Re-read the standing orders and units.tsv, recompute the frontier
对 v3 的要求：两边一致，进度存在会话之外。开工的那段话不写走到哪一步，由 playbook 的第一步去票上读。

等待与叫醒 · v2

一个 agent 开了另一个 agent 就结束回合（ADR 0010）。relay.py 读票上的事件，按 WAKES 表叫醒等它的会话，叫醒行只有 #n 事件。worker 被 reviewer.reported 叫醒后，在原来的会话里接着做。

pstack

默认开新的子代理，只有新工作必须用到旧 agent 身上的状态才续用：its local checkout, its uncommitted changes, or a process it still runs续用时：Every spawn and every resume carries the standing orders verbatim.
对 v3 的要求：被叫醒是 MMW 独有的一种开工，要有自己的指引。worker 续用旧会话正是 pstack 说的例外：它的工作区里有没提交的改动。

有没有人可问 · v2

夜里没有。弹出提问由 tool-guard.py 拦下，改变交付的问题开 decision 子票，先取默认值做下去。

pstack

你一天看两次：the human checking in twice a day instead of every five minutes
对 v3 的要求：脚本开的每个会话都按无人值守工作。这条规则要在它们都会读到的地方，只写一次。

2　v2 现在，每个角色从哪里拿到指引

从图 1 能看出的
  1. 每个角色的指引来自开工那句话点名的技能。技能里的 ## Find your moment 表再按角色选一份 reference：dispatch 有六行，code-review 有两行，advisor 有两行。按角色选路的规则散在这几个技能里，没有一处总的。
  2. 所有角色共用的只有 shared.md，外加脚本里的 AUTONOMOUS 一句。v2 没有 mode，pstack 放在 mode 里的那层工作方式（原则索引、什么时候问你、怎么写回复），worker 和 reviewer 都没有。「没人看着时怎么做」这条规则写在 dispatch.sh 的一个变量里，不在任何技能里。
  3. v2 的 research 不在图里。它去一手来源（官方文档、源代码、规范、第一方 API）查一个工作区以外的事实，写成一份注明出处的研究文件。它现在有固定的时机：wayfinder 画图时，为每张 research 票各开一个宿主的后台子代理，并行去查；它把结论贴到票上并关票。worker 不派它。它不经 dispatch.sh，没有 models.json 的行。
  4. 开工那句话里，规则和数据混在一起。票号、base commit、Memory 索引、reviewer Rules 是这一次的数据；AUTONOMOUS 和 PRODUCT_RULES 两句是每次都一样的规则。

3　v3 的设计

图 2 从一个会话或子代理开始，到它交回结果或被叫醒为止。每个菱形是一个判断，四个判断依次回答：它的指引文字从哪来，是跑一份角色 playbook，还是由某个技能派出；mode 怎样到它手上；它走哪份 playbook；它走到了哪一步。右下角那一圈是被叫醒。

从图 2 能看出的
  1. 跑角色 playbook 的会话载入 mmw-mode；由技能派出的 agent 不载入。前者是 orchestrator、worker、reviewer，以及你白天开的会话；后者是 advisor、researcher、code-review 的轴，以及 to-tickets 的歧义扫描、manage-agents-md 的分组这类子代理。它们只读技能给自己的那一份。v2 派子代理的地方全是这一种，pstack 实际也这样分：Routed workflow skills … set their own `subagent_type`
  2. mode 到手有两条路，都不靠宿主的特殊能力。你开的会话由钩子载入；派发方用 dispatch.sh 开的会话，由 start prompt 第一句 Use the mmw-mode skill. 载入，这句话在五个宿主上都有效。
  3. 角色就是 playbook。开它的那段话点名了 playbook 就照走，没点名才由 ## Playbooks 按任务选。orchestrator 不是脚本开的，它是你的会话选了 Run a night（一夜一批票）或 Bug fix（单张票）。worker 和 reviewer 只由派发方派出，你不会自己去接一张票。
  4. start prompt 只有路由和数据，没有规则。无人值守的规则在 ## Autonomy 的 Unattended 一段，走到哪一步在票上。叫醒行照 v2 只有 #n 事件，醒来先做什么在 dispatch 技能的 ## On waking，由结束回合的那一步点名。

4　每个角色的两份东西

图 2 只画了 agent 那一份。每个 agent 都由派发方派出，派发方也要有一份：什么时候派、给它什么、它交回之后怎么办。图 3 把两份并排列出，中间是开工那段话，两份在这里接上。

从图 3 能看出的
  1. 派发方那份，写在派发方自己 playbook 里派发的那一步。那一步写什么时候派、交回之后怎么核实、等哪个事件。pstack 也这样：how、why 开子代理的那一步写明子代理类型、模型和交给它的提示词。这对图 3 上半的「固定时机」成立：工作流的某一步派它，派发说明就写在那一步。researcher 现在也在这一组，由 wayfinder 发起调查的那一步派；其他技能派出的子代理，派发说明就在派它的那个技能里。
  2. 自由人的派发说明，在它自己的技能里。advisor 是自由人：任何 agent 走到任何一步，遇到难撤回的决定、或一个问题连败两次，就派它。没有哪一步能替它写派发说明，所以何时请教写在 advisor 技能的 description 里，怎么写 brief 写在技能请教的那部分。description 每个宿主、每个会话都会扫到，派发方任何时候都看得到（ADR 0014 就是为此把它放在 description）。mode 不再另写一行，否则同一个时机写两处。researcher 以后要成为自由人，只需把它的调用时机写进 research 的 description，派发说明从 wayfinder 那一步移到技能里；在那之前，它的 description 写成只在被点名时运行。
  3. 派发里每次都一样的部分，交给脚本。开工那段话的措辞、模型行、工作区、必须带的数据由 dispatch.sh 生成，数据缺了就拒绝开工，对应 pstack 的「Missing fields are a refuse-to-spawn condition」。派发方没有机会把开工那段话写错；它要判断的只剩什么时候派、brief 里写什么。
  4. agent 那份，是它的角色 playbook 加上 mode。由技能派出的 agent 例外，只读技能给自己的那一份。
  5. 两份之间的接口由检查脚本守着，不靠记得。开工那段话点名的 playbook、agent 交回的事件、派发方收到事件后的做法，三处任何一处改了另两处没跟上，检查就报错。第四处是 agent 被重新开到票上时从哪一步接着做：verify-ticket.py --preflight 的 RESUME: 行按标题点名 Work a ticket 的一步，检查核对每个标题都在。这是第 2 课说的「能写成检查的，就不写成文字」。
  6. worker 派 reviewer，reviewer 派轴，不是全由 orchestrator 派。这是 v2 现在的做法，我保留它：审查之后的修复和重跑判据都在 worker 自己的工作区里做，由 worker 直接派少一次叫醒，orchestrator 的上下文也不随票数增长。归纳

5　夜里的任务说明就是票

从图 4 能看出的
  1. 票覆盖了 brief 的七个字段，还多做了两件。FORBIDDEN 不写成文字，由钩子拦下；REPORT 的格式由脚本检查。这正是第 2 课说的「能写成检查的，就不写成文字」。
  2. 只有 TIMEBOX 没有对应，也不补。v2 让 worker 自己判断修几轮，watchdog 在一张票长时间没有新事件时提醒 orchestrator；v2 没有出现过需要时限的问题。

6　每个决定的依据

每张卡片五行：决定是什么；v2 的设计意图；pstack 给的启发；前几课的哪条结论支持它；没选的做法和原因。

跑角色 playbook 的会话都载入 mode决定 1

决定
你开的会话、orchestrator、worker、reviewer，开工时都载入 mmw-mode。mode 的 ## Autonomy 原本为你在场的会话写，例如 Always pause 要停下来问你；所以 Unattended 一段要写明夜里遇到这些情况怎么做，不让 worker 读到互相矛盾的指令。
v2 意图
规则经 agent 载入的技能到达它，不经开工那句话；同一条规则只写一处。v2 的 worker 和 reviewer 没有共用的工作方式，AUTONOMOUS 只能写进脚本。
pstack
Reads the `poteto-mode` skill's `SKILL.md` in full before any work … Substituting `generalPurpose` skips that read and drifts.
前几课
第 1 课：mode 在任务开头读全文，之后一直在。第 4 课图 6：## Autonomy、## Writing the reply 对每个任务都成立，worker 和 reviewer 也是任务。
没选
每个角色只载入自己的技能（v2 现状）：原则、问不问你、怎么写，这几层 worker 就没有。为每个宿主写一份子代理定义（pstack 的 poteto-agent）：ADR 0015 已经否决，五个宿主的格式各不相同。

第一句点名 mode，钩子只管你开的会话决定 2

决定
start prompt 的第一句是 Use the mmw-mode skill.。SessionStart 钩子在有 .mmw/ 的仓库里替你开的会话载入 mode（已经由你定了）。
v2 意图
宿主和 runner 中立。v2 开每个会话都用「Use the X skill」，这句话在五个宿主上都有效；钩子不是每个宿主都有。
pstack
poteto-agent 的正文只有一句：先读 mode。v3 把这一句写进 start prompt，不需要子代理定义文件。
前几课
第 2 课：subagent 这种组件在「某个角色每次被开出来，都必须带着同一份提示词」时才有。v3 的这份提示词由脚本拼，不需要单独的文件。
没选
第二次迁移的做法：钩子挂在 SessionStart、SubagentStart、UserPromptSubmit 三处，给所有会话注入 mode。依赖宿主的钩子，没有钩子的宿主上 worker 就拿不到 mode。脚本开的会话在有 .mmw/ 的仓库里也会触发钩子，同一份 mode 读两遍，多占上下文，不改变行为；这个代价先接受，未测量。

角色就是 playbook决定 3 归纳

决定
每个角色的流程各是一份 playbook：Run a night（orchestrator 跑一夜一批票）、Bug fix（orchestrator 只跑一张票）、Work a ticket（worker）、Review a ticket（reviewer）。start prompt 第二句点名 playbook，## Playbooks 开头一句写：start prompt 点名了 playbook，就照它走，不再选。代价有二：worker 和 reviewer 的路线由 start prompt 定死，mode 的路由对它们没有用处；implement 和 code-review 来自 mattpocock 上游，改成 playbook 后要在 imports.tsv 重新登记对应关系。
v2 意图
这三份的步骤 v2 已经有了，形状就是 playbook（第 3 课图 3）：night.md、implement 的 ## Closing steps、code-review 的 session.md。它们各自经一张 ## Find your moment 表被找到。
pstack
只有一个路由，mode 的 ## Playbooks。Orchestrate 里的协调者就是和你对话的会话，跟 v2 的 orchestrator 一样。
前几课
第 2 课：**You own** 和 **Reply:** 不同，任务就不同。orchestrator 管一夜、交 NIGHT SUMMARY；worker 管一张票到关票、交收尾评论；reviewer 管一份审查报告。Bug fix 也管一张票，但它是 orchestrator 的那一份：开 worker、处理叫醒、dispatch.sh land 落地，交回落地结果，没有 NIGHT SUMMARY 和复盘，所以和 Run a night 分开。单张票一般就是修 bug，所以这份 playbook 就叫 Bug fix，路由行写「修一个 bug」，对应 pstack 同名 playbook 的触发；这是你定的。
没选
第二次迁移的 roles.json 加步骤锚点（开工那句写「mode 的某份 playbook 第几步」，由 locations.py 维护）：步骤一挪锚点就断，而走到哪一步本来就在票上。保留各技能的 ## Find your moment 表：路由散在几处，和 mode 的路由重复。保留 implement、code-review 两个技能，start prompt 写 Use the implement skill：代价更小，但 v2 的 implement 收尾八步几乎全是 MMW 自己的，它是一种任务，不是被多处复用的能力。

开工那段话只放路由和数据决定 5

决定
start prompt 是两句路由加数据。AUTONOMOUS 那句的内容进 ## Autonomy，成为 Unattended 一段：开工那段话来自脚本，就按无人值守工作。PRODUCT_RULES 那句成为 ## Non-negotiables 的一行触发：要起停或访问产品，而别的票也在跑，就读 ui-acceptance 的五条规则。票号、base commit、Memory 索引、reviewer Rules 留在 start prompt 里。
v2 意图
start prompt 带数据，规则经技能到达。v2 自己在 AUTONOMOUS 和 PRODUCT_RULES 两处没做到。
pstack
它把常设指令原样贴进每次开工，因为通用子代理不读 mode。v3 的会话读 mode，常设指令就在 mode 里，不必再贴。
前几课
第 2 课：几份 playbook 共用的内容放在 mode 这一层（bugbot-triage.md 被四份 playbook 共用）。Unattended 一段被三份角色 playbook 共用，所以放 ## Autonomy，不放某一份 playbook。
没选
第 4 课原来的安排：脚本起的会话那段移进「夜里的 playbook」。夜里有三份 playbook 都要它，放进其中一份，另两份就读不到。

夜里的 brief 是票，技能派出的 agent 由技能定 brief决定 6

决定
夜里不另造 brief：票就是 brief，由 to-tickets 写、verify-ticket.py --lint 查。技能派出的 agent，brief 的规矩写在派它的技能里，例如 advisor 的五部分、code-review 轴的一句话。## Subagents 只写 v2 已有的通用规则：用宿主自带的通用子代理，不指定模型；brief 写明交回什么、多长；宿主不能开子代理，就自己按顺序做；派发方对它的产出负责。
v2 意图
需要你决定的事白天当面问完，写进票（第 3 课第 1 组）。子代理的规则已经在 v2 的技能规则里：A subagent's brief states what it returns and its length
pstack
派发方对子代理的产出负责：You own every subagent's work. Review the diff and write your own summary, don't pass through what it said.
前几课
第 4 课把 ⑤ 任务说明和 ⑥ 交回的报告留到这一课。图 4 是 ⑤ 的答案；⑥ 用上面 pstack 那一句。
没选
照 pstack 造一个「委托子代理」：先载入 mode、替派发方做一步，并在 ## Subagents 给它一份 brief 格式。v2 所有派子代理的地方都是技能派、只给技能的提示词，没有谁会用它。为夜里的 worker 再写一份 brief 模板：和票的各节重复。

由技能派出的 agent 不载入 mode决定 7 归纳

决定
分界看 agent 的指引文字从哪来：跑角色 playbook 的会话载入 mode；由技能派出的 agent（advisor、researcher、code-review 的轴、其他技能的子代理）不载入，只读技能给它的那一份。researcher 和 advisor 同一种做法：派发方写 brief，dispatch.sh 开一个独立会话，models.json 有它自己的一行。不同在问的问题和时机：advisor 回答「我的判断对不对」，读本仓库，交答案、不写文件，是自由人；researcher 回答「外面的事实是什么」，读工作区以外的一手来源，交一份研究文件，现在只由 wayfinder 派。reviewer 载入 mode：它是一个无人值守的会话，要开轴、核实发现、在票上写报告。
v2 意图
轴：Nothing else: the skill is what they read, and the axis word picks their file in the skill's table.advisor 的价值是一个没被你的思路影响过的会话：the value is a session that has not spent the last hour convincing itselfresearcher 的意图在 v2 research 里：Investigate the question against primary sources … Follow every claim back to the source that owns it.
pstack
技能派出的子代理由技能自己定类型和提示词：Routed workflow skills … set their own `subagent_type` for diverse-model review. Respect what the skill prescribes
前几课
第 1 课：references/ 里放给子代理的提示词模板，how、why 就是这样用的。
没选
按「带着你的工作方式，还是给独立意见」分界：to-tickets 的扫描、manage-agents-md 的分组并不给独立意见，同样不载入 mode，那个分界解释不了它们。researcher 照 v2 用宿主的后台子代理：它就跑在派发方的模型上，换不了模型，也没有 advisor 那样的独立会话。让轴也载入 mode：每个轴多读一份 mode，换来的只是它本不需要的规则。让 reviewer 不载入 mode：它就没有 Unattended 和写报告的规则，又得把规则写回开工那句话。

叫醒是同一个会话接着做决定 8

决定
叫醒行照 v2，只有 #n 事件。醒来先做的四步留在 dispatch 技能的 ## On waking：重跑被打断的命令；到票上读这个事件；dispatch.sh ack；照自己的 playbook 做。由结束回合的那一步点名它，例如 Work a ticket 起完 reviewer 那一步写：结束回合；#n reviewer.reported 叫醒你时，先做 dispatch 的 ## On waking，再读报告。每个事件对应做什么，留在各自 playbook 的那一步里，例如 Run a night 的事件表。
v2 意图
agent 被叫醒，不轮询（ADR 0010）；叫醒行不带票上没有的东西。v2 已经由那一步点名：night.md 第 3 节第 1 步写「Do steps 1-3 of ## On waking in ../SKILL.md」。

保留 dispatch 技能决定 9

决定
dispatch 技能装三样。一是夜里机器的脚本，位置不变：dispatch.sh、relay.py、watchdog.py、turn-guard.py、tool-guard.py、runner 适配器、models.py、statedir.py、status.py、ghlist.py，以及核对两份接口的检查脚本；playbook 用到时写「dispatch 技能的 dispatch.sh advance」。二是你会直接要求的事：改某个角色的宿主、模型、推理强度或 runner（references/editing-models.md，由 models.py 改）；description 只写它的时机。打开任务板（dispatch.sh board）也是这一类，但任务板是一个独立的产品，这一课不搬，搬它的那一课再把它写回 description。三是 ## On waking（决定 8）。v2 的 ## Find your moment 表删掉：第 1 行（worker）进 Work a ticket，第 3 行（orchestrator）进 Run a night，第 2 行（自己接的票）删掉，第 4 行（只跑一张票，references/one-ticket.md）成为 playbook Bug fix。verify-ticket 仍是一个技能。
v2 意图

pstack

8　照这个设计，这一课搬什么

这一课只搬派发系统：谁派谁、开工那段话、叫醒、看守，以及每个角色派发方的那一份。agent 怎么做事不在这一课，包括角色 playbook 里做事的步骤、轴和 advisor 怎么审怎么答、researcher 怎么查、bug 怎么修。这些先建空壳文件，在派发系统里占好位置、能被点名、检查脚本有东西可查，内容由以后的课来填。

这一课要搬的
  1. 写 ## Subagents。只写决定 6 列的 v2 通用规则：用宿主自带的通用子代理、不指定模型；brief 写明交回什么、多长；宿主不能开子代理就自己按顺序做；派发方对产出负责。
  2. 补 mode 的两处。## Autonomy 加 Unattended 一段，写明它和 Always pause 的关系；## Playbooks 开头加「start prompt 点了名就照走」，再加四份角色 playbook 的路由行。
  3. 搬 dispatch 技能。脚本照搬，dispatch.sh 拼 start prompt 的地方改成两句路由加数据，去掉 AUTONOMOUS 和 PRODUCT_RULES；改模型和 ## On waking 留在技能里；删掉 ## Find your moment；models.json 加 researcher 一行，dispatch.sh research 开 researcher；写核对两份接口的检查脚本。它依赖的一起搬：verify-ticket 整个搬（记事件、读走到哪一步都靠它），ui-acceptance 只搬 lease.py、refusal.py 和「五条规则」一节，其余是空壳。任务板和安装器不搬：dispatch.sh 找不到它们时照常开夜，在错误输出里说一句。四套测试（dispatch、relay、liveness、verify-ticket）一起搬，在隔离的目录里跑。

9　自测

1．夜里一个 worker 起完 reviewer 结束回合，被 #n reviewer.reported 叫醒。它先做什么，这件事写在哪？

叫醒行只有 #n 事件。结束回合的那一步写明了等哪个事件、醒来先做 dispatch 的 ## On waking：重跑被打断的命令，读事件，ack，再回到 playbook 里等这个事件的那一步（决定 8）。

2．reviewer 开的 Standards 轴子代理，开工时读什么？

它由技能派出，不载入 mode。开它的只有一句话，点名 code-review、票、base commit 和轴名，技能按轴名把 references/standards-reviewer.md 交给它（决定 7）。

3．pstack 默认给新工作开新的子代理。v3 里 worker 被叫醒，为什么在原来的会话里接着做？

pstack 写明的例外：新工作必须用到旧 agent 身上的状态，例如它的工作区和没提交的改动。worker 的修改都在 issue-<n> 工作区里，这正是那种情况（决定 8）。

4．worker 的 start prompt，措辞由谁定？

措辞、模型行、必须带的数据每次都一样，交给脚本，数据缺了就拒绝开工。orchestrator 要判断的只有什么时候派；任务说明是票，白天由 to-tickets 写（决定 10）。

5．一个 worker 撞上一个难撤回的接口设计。何时该请教 advisor，这条规则写在哪里？

advisor 是自由人，没有哪一步能替它写派发说明。何时请教写在它技能的 description 里，每个会话都扫得到；怎么写 brief 在技能请教的那部分。写进 mode 会让同一个时机写两处。
