1　你定的六件各落在哪

第 1、2 件是同一处。选 runner 的程序 models.py 原来有好几层，其中票级指定、tmux 和 lody 这些运行时列表，服务的是没有适配器的 runner，走不到。现在只剩三级：环境变量 MMW_RUNNER，models.json 的 runner，写 auto 或都没写时读当前会话所在的 runner（先 Herdr，再 Orca），最后是 orca。Paseo 和 Herdr 的适配器没动。

第 4 件不用改任何一张票。改票是对 GitHub 的外部写入，所以先只读扫了一遍：agentflow 开着的 49 张，本仓库 7 张。带事件的 3 张 v3 都读得懂，spec.opened 都带 into 和 project。读事件的程序因此不留任何为旧格式写的分支（ADR 0034 记着扫描结果）。

第 6 件改了 16 个文档文件。写的过程中查出两个技能文件和代码对不上：product-answers.md 和 target_config.py 都说仓库检查由收尾的 --closeout 跑，实际在合并时由 dispatch.sh 跑，失败就把票退回 worker。两处都改成了实际的样子（imports.tsv 的 J524 到 J526）。

3　你用的时候会看到哪些不同

情形以前现在
本机的产品槽位全被占（默认 8 个）worker 排队，等别的票交还槽位后被叫醒worker 开一个 fault 子票报受阻，停下；orchestrator 被叫醒处理
开夜前的 dispatch.sh check 发现安装不全在已安装的 checkout 里自己跑 install.sh 修只印警告；装不装由你
reverify 之后又往 base branch 推了修复summary 认回执文件，照样关夜summary 拒绝，要先在新的提交上再跑一次 reverify
关夜时 Nowledge Mem 不响应Memory 决定记成「未核对」，夜照样关memory-list 退 2，夜关不了，直到 nmem 恢复
Pi第五个宿主不再是宿主；装 v3 时摘掉 v2 给它装的东西

第四行是这一批里唯一让一种故障更难过去的改动。理由是：「未核对」那套结构在 11 夜里一次没出现，而为它写的 345 行代码每次都要维护 归纳。代价是 Nowledge Mem 停着的那天早上，这一夜要等它恢复才能关。要不要退回「未核对也能关」，由你定（第 7 节）。

4　代码少了多少

产品脚本净少约 3,100 行，测试净少约 1,650 行。少得最多的是 gate-check（少了一大半）和 install.sh（少了三分之一），两处都是给不存在的调用方或已完成的迁移留的代码。

原来的为什么错现在

8　自测

1．本机 8 个产品槽位都被别的票占着，这时一个 worker 要跑判据，会怎样？

这次运行什么都不跑、退 2，worker 照 ui-acceptance 的第 4 条开 fault 子票报受阻（第 2、3 节，ADR 0033）。

2．reverify 跑完以后又往 base branch 推了一个修复，接着跑 summary，会怎样？

summary 要每张已落地的票最新一次 reverify 在 origin/<into> 当前的提交上全绿（第 3 节，ADR 0034）。

3．开夜前 dispatch.sh check 发现本机安装缺了一样，会怎样？

它只跑 install.sh --check，把缺的印成警告；本机装哪一份只由你决定（第 1 节，你的第 5 个决定）。
