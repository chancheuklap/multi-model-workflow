# Upstream intents

The design intents of the two skill sets MMW is built from: Matt Pocock's skills (`mattpocock/skills`, subtree `mmw-v3/upstream-mattpocock/`) and pstack (`cursor/plugins`, subtree `mmw-v3/upstream-pstack/`). MMW is Matt's skills placed into pstack's frame, with MMW's own additions. Every id below appears in [`DESIGN-INTENTS.md`](DESIGN-INTENTS.md), either under the MMW intent that takes it or among the departures with the reason; an id in neither is a gap, to be brought in or given a reason.

## Reading an upstream for its intents

- A **design intent** is why a set is built the way it is: the problem a design solves, the means it uses, and what it deliberately does not do. pstack's `principle-*` skills are rules an agent follows, one kind of mechanism; they are not its intents.
- **Written**: a sentence in an upstream file states it, and the source names that file. **Implied**: no sentence states it; it is inferred from which components exist, where they sit and how they call each other, and the source names that structure. Both kinds are listed.
- Read two layers: how the set works on a task, and the architecture of the set itself. Read the architecture along ten dimensions: the kinds of component and what each is for; loading and triggering (when, and by whom, a text is read; the load an always-present text puts on context, and the load a person-invoked one puts on the person); orchestration and control flow; state and the shape of each hand-off; one home per fact; how each component is written; what a program enforces and what text asks; distribution, install and upgrade; how the set's own skills are tested and kept up; how sessions and models are organised.
- Read the whole repository, the root and the hidden directories included (`.agents/`, `.changeset/`, `.out-of-scope/`, `automations/`, `docs/`), not only `skills/`.
- A source below names a file of the subtree, or a skill by name (its directory under the subtree's `skills/`).
- After an upstream pull, the changed files are read against this list, as the `### Upstream skills` bullets of [`SKILL-SET-RULES.md`](SKILL-SET-RULES.md) say.

## Matt Pocock's skills

Written for an engineer at the keyboard who reads the code. They answer four failures of agent coding: misalignment, verbosity, code that does not work, and code that decays into a mess.

| --- | --- | --- | --- |
| M1 | written | Align before acting. Before a change, grill: walk the design tree a round at a time, each question with a recommended answer; the agent looks facts up, the person makes decisions; work starts once the questions run out and the person confirms the shared understanding. | `README.md` (failure mode 1); `grilling` |
| M2 | written | A shared language. The glossary and the ADRs are written when a decision takes shape; an ADR records only a decision that is hard to reverse, surprising without context, and a real trade-off. | `README.md` (failure mode 2); `domain-modeling` |
| M3 | written | The speed of the feedback loop caps the speed of development: type checks, the browser, automated tests; a failing test before the code, in small steps. | `README.md` (failure mode 3); `tdd` |
| M4 | written | Care for the design every day. Deep modules, a small interface over much behaviour; few, high seams; survey for deepening every few days. | `README.md` (failure mode 4); `codebase-design`; `improve-codebase-architecture` |
| M5 | written | Control stays with the user. Skills are small, editable, composable and not tied to a model; a framework that takes over the whole process makes its errors hard to correct. | `README.md` opening |

## pstack

Written by poteto for an engineer who reads the code and runs many agents at once on Cursor. Its aim is less code written well, well enough to trust many agents in parallel.

| Id | Kind | Intent | Source |
| --- | --- | --- | --- |
| P1 | written | Quality before quantity: to go fast, go deep first; write less code and write it well; against bulk low-quality AI output. | `README.md` opening |
| P2 | written | Parallelism you can trust: trust one agent to write verifiable code before running many; each agent gets its own working directory, and each place has one writer. | `README.md`; `docs/guide/02-poteto-mode.md`; `skills/principle-separate-before-serializing-shared-state/SKILL.md` |
| P3 | written | Models by strength: code to a fast code model, the hardest changes, prose and judgement to the strongest; a second opinion is the same prompt on another model; a verifier runs on another vendor's model. | `README.md`; `poteto-mode` `## Subagents`; the Orchestrate playbook |
| P4 | written | One front door: the person states the goal and what done means, not the process; `poteto-mode` matches a playbook and calls the other skills step by step; the mode stays in effect once entered. | `README.md`; `docs/guide/01-setup.md`, `02-poteto-mode.md` |
| P5 | written | A rule enters the session when it applies: non-negotiables map situations to skills; a principle is one index line, read in full when applied and named in the reply with the decision it changed; a principle's name is also the word a person uses to correct course. | `poteto-mode` `## Non-negotiables`, `## Principles`; `docs/guide/08-principles.md` |
