### Cut tickets

**You own one batch: a published spec broken into the tickets the owner approved, published under it with their labels and blocking edges; the ambiguity scan goes to a subagent.** Each ticket is read by agents who were not in this conversation and cannot ask it anything: a worker at night, a reviewer in another session. This session is the last one that holds the spec, the codebase and the owner at once, so settle here what can be settled: a choice left open is made at night by a worker who cannot ask. Distinct from Write a spec, which decides what is built and runs this playbook at its end, and from Bug fix, which writes one ticket outside any spec. Every ticket is written in the format of the `verify-ticket` skill's `references/ticket-format.md`.

1. **Read the spec.** Read the spec's full body and comments. A plan or a conversation with no published spec goes through **Write a spec** first.
   Done when you hold the spec's issue number and have read its full body and comments.
2. **Explore the codebase.** Explore it until you know the current state of what each ticket touches. Ticket titles and descriptions use the project's domain glossary vocabulary and respect the ADRs in the area. Look for a prefactor that makes the implementation easier: "Make the change easy, then make the easy change."
   Done when you know the module or directory each ticket will write to.
3. **Draft vertical slices.** Break the work into **tracer-bullet** tickets. Each slice cuts a narrow but complete path through every layer (schema, API, UI, tests), not a horizontal slice of one layer; a completed slice is demoable or verifiable on its own; any prefactor goes first. Split where the parts can run at the same time, or where one part's criteria can fail without the other's; keep together what would write the same files, since splitting that only adds an edge. When the spec has a screen contract, read the `mmw-mode` skill's `references/cutting-interface-tickets.md`. When the spec's `## Feature map changes` names a feature file, that file goes under the **Owns** of the ticket that changes it. A ticket that changes a feature file already on the base branch lists that file under **Read first**. A section that reads `none` adds neither.
   **A wide refactor is the exception.** One mechanical change (rename a column, retype a shared symbol) whose **blast radius** fans across the whole codebase breaks thousands of call sites in one edit, so no vertical slice of it can land green. Do not force it into a tracer bullet; sequence it as **expand–contract**: expand, adding the new form beside the old so nothing breaks; migrate the call sites in batches sized by blast radius (per package, per directory), each batch its own ticket blocked by the expand and green on its own because the old form still exists; contract, deleting the old form once no caller remains, in a ticket blocked by every migrate batch (**principle-migrate-callers-then-delete-legacy-apis**). When even the batches cannot stay green alone, they share an integration branch that all block a final integrate-and-verify ticket, and green is promised only there.
   Done when the work is drafted as slices, each one vertical or one step of an expand–contract sequence.
4. **Write each acceptance criterion.** Write each one as the format's `## Each acceptance criterion` says, and ask its five questions of everything you want to say about the work. A ticket that changes a feature file already on the base branch carries the pin that section names for a feature file. A rule question 2 sends to the spec's `## Implementation Decisions` is written there through **Revise a spec**. A choice question 5 finds is carried to step 6. Where no command exists because the spec's `## Testing Decisions` never decided how the thing is verified, settle that in the spec through **Revise a spec** first; do not invent a command.
   Done when every criterion on every ticket carries a number, a `CHECK:` and an `EXPECT:`, each `CHECK:` aimed at behaviour its ticket adds has failed on the base branch, and everything that stopped at question 2, 3, 4 or 5 has landed where that question sends it.
5. **Give each ticket its blocking edges.** A blocking edge names a ticket that must complete before this one can start. The edges are the night's schedule: every ticket whose blockers have landed starts at once, so a missing edge sends two workers into one file or onto work not built yet, and an edge that gates nothing makes the night wait for no reason.
   **What a ticket creates is put in service by an edit to something it did not create**: the registry, router, parent template, index, story adapter or stylesheet that has to name it. Until one does, no criterion of that ticket can see it; and when several tickets that can run at the same time each make that edit, all but the first to land bounce on a merge conflict. For each path a ticket marks `(new)`, `grep` the nearest existing file of its kind twice, once for its file name and once for the one identifier it declares for others (its root class, exported symbol or route path), and put every file that answers under this ticket's **Owns**, whoever created it. Where that sibling is still to be built in this batch, its ticket's **Owns** is the same list.
   **What a ticket changes is also stated in files it does not change**: a reference or playbook that teaches the old shape, a template another repository is set up from, a glossary entry, a course lesson. For each name, path, format or printed output a ticket retires or changes, `grep` the repository for the old form, and put every file that still teaches or uses it under the **Owns** of that ticket, or of a later ticket of the batch that rewrites it. A record of the past (an ADR, a review, a prototype's README, a judgement entry of `imports.tsv`) stays as it was written.
   What overlaps there decides the shape of the batch. Two tickets that can run at the same time get the **Blocked by** edge the **Owns** section calls for. Several tickets on the same registration files, where chaining them would make much of the night run one ticket at a time, get a **prefactor ticket** ahead of them, which owns those files and lands in one pass every entry, route, include and export, each naming a placeholder the ticket behind it fills; where a shared file is only a list of independent entries (a stylesheet, a registry, a bundle index), the prefactor splits it into one file per ticket that the shared one includes once. Each of those tickets is then blocked by the prefactor alone, and they run together. A shared file that is one body of logic, such as a route module several tickets add handlers to, is neither pre-landed nor split, because what each ticket writes there is its own work; those tickets keep their chain. Every shape keeps one rule: no two tickets that can run at the same time write the same file (**principle-separate-before-serializing-shared-state**). Two tickets can run at the same time when neither blocks the other, directly or down a chain.
   Done when every path marked `(new)` has the files that put it in service under the same ticket's **Owns**, every file a `grep` for a retired or changed form returns that still teaches or uses it is under some ticket's **Owns**, and no two tickets that can run at the same time write the same file.
6. **Scan for ambiguities, then put the breakdown to the owner.** Write the spec body and the drafted tickets to a file `mktemp` makes, and send out one subagent, the ambiguity scanner, restricted to reading and searching where the host allows it, with one sentence: "Read the `mmw-mode` skill's `references/ambiguity-scan.md` and scan spec #<spec> and the drafted tickets in <file> for ambiguities." Its questions belong in each ticket's **Choices** when the owner first sees it. Then present the breakdown as a numbered list. For each ticket an agent works:
   - **Title**: a short descriptive name.
   - **Blocked by**: which other tickets must complete first, if any.
   - **What it delivers**: the end-to-end behaviour this ticket makes work.
   - **Worker**: `junior` or `senior`, by the format's `## Labels` rule, and the one-line reason.
   - **Choices**: every choice question 5 sent here and every question the scan returned that only the owner decides (what the customer sees, money, scope, the order things are delivered), one line each: the options, and the one you would take. A question the scan returned that is an engineering call is yours: decide it and write it into the ticket's **What to build**. Omit the line when there are none.

   Then the `ready-for-human` tickets in the same list, each with its **Title**, **Blocked by**, its kind (*reaction* or *reach*) and what is to be looked at. Ask the owner which option each choice takes and whether the order of delivery is right. The granularity, the edges between tickets and the worker grades are engineering calls you have made: they are in the list for the owner to read, not questions put to them. Iterate until the owner approves the breakdown. Write each answered choice that changes only what one ticket delivers into that ticket's **What to build**; write each that changes a decision in a spec section through **Revise a spec**, then into the tickets.
   Done when the owner has approved the breakdown, every answered choice is written into a ticket's **What to build** or the spec, and step 5's Done when still holds for the approved breakdown.
7. **Lint and publish the batch.** Write each approved ticket as one draft in a directory `mktemp -d` makes, as the `verify-ticket` skill's `references/linting.md` describes a draft, with the labels the format's `## Labels` gives it. Run `verify-ticket.py <spec> --lint --drafts <dir>` and fix every `ERROR` in the drafts; then publish them as they stand with `verify-ticket.py <spec> --publish --drafts <dir>`, which ends by linting the published spec. Close no parent issue.
   Done when every approved ticket is published as a sub-issue of the spec, with its labels and its blocking edges.
8. **Read the batch back.** Read the lint `--publish` ran on the published spec as the `verify-ticket` skill's `references/linting.md` says: no `ERROR`, and every `WARN` read once and either fixed or kept on purpose. The drafts run of step 7 does not stand in for it: only this run sees the tracker's labels, sub-issues and blocking edges. Fix each `ERROR` on its ticket and run `verify-ticket.py <spec> --lint` again. Check that each `ready-for-human` ticket holds all of **the five things** in the `verify-ticket` skill's `references/person-ticket.md`, because no agent can repair one.
   Done when the lint reports no `ERROR` and every `ready-for-human` ticket holds the five things.

**Reply:** the batch: each ticket's number, title, worker grade and blockers; each `ready-for-human` ticket and what the owner is to look at; each choice the owner settled and where it was written; and that the batch runs when the owner starts its night, through Run a night.
