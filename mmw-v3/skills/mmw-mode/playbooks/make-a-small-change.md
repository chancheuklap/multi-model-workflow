### Make a small change

**You own one change the owner asked for while here, from their words to a commit on the base branch; a reader who did not write it reviews it.** No spec, no ticket and no night stand behind it: no criteria a script runs, no reviewer in a session of its own, no closed ticket as the record. What this session misses reaches the owner unless that reader finds it first. The temptation is to call the change too small for that reader; run **Get a second reading** however small it is. Distinct from Bug fix, which starts from a defect the owner reports, and from Run one ticket, which runs a written ticket.

1. **Write down the change and judge its size.** Paste the owner's request word for word into `.scratch/request-<slug>.md` of the repository, which git ignores, `<slug>` the request in a few lowercase words joined by `-`: it is this change's spec, and the request the review reads. The change is small when one session can finish it and it needs no product decision from the owner. When it is not, tell the owner it needs a spec (Write a spec), with what you found; this playbook ends here.
   Done when the file holds the request and the change is judged small, or the owner has heard why it is not.
2. **Write it test-first.** Run the `tdd` skill. With no ticket, write the seams under test into the request file and confirm them with the owner; the repository's `TESTING.md` says which test layers there are, which external boundaries are stubbed and how tests run. A test counts as red only when it fails because the behaviour is absent (**principle-a-check-must-be-able-to-fail**). A change that must keep a behaviour as it is writes a pin before the structure moves (**principle-a-check-must-be-able-to-fail**). A change with no behaviour to test, such as wording or configuration, writes down instead the check that will prove it. Write the code under **principle-start-from-what-exists**, **principle-migrate-callers-then-delete-legacy-apis** and **principle-laziness-protocol**, and, when the request names something already settled, **principle-baseline-is-the-contract**. Keep, for the Reply, one sentence per new file, dependency or configuration entry on why the existing one is not enough.
   Done when every behaviour the change adds or alters has a test that failed before its code was written and passes now, every behaviour it keeps has a pin you have seen go red, or the check that proves it is written down.
3. **Prove it on the product and run the affected tests.** Show, on the product, that the change does what the owner asked, in their words (**principle-prove-it-works**); while the product runs, the `ui-acceptance` skill's **Five rules while the product is running** hold. Then run the tests **principle-run-the-smallest-test-set** picks. A red test is answered by **principle-fix-the-product-not-the-check**.
   Done when the proof and the tests pass on the final code, with their output kept for the Reply.
4. **Commit it.** One commit per cause. It touches only what the cause requires and the tests that prove it. Its message quotes the line the test run printed (`ran 188 skipped 0`, not "the tests pass"). A change that exceeds those three is a ticket after all: tell the owner it needs one.
   Done when the change is committed on the base branch under those three rules.
5. **Get a second reading.** Run the `code-review` skill with the axes Standards, Spec and Tests, the commit this change started from as the base, and the request file as the request: its axes cannot read this conversation. Do not tell it which parts you believe are right. Check each finding as Review a ticket's **Verify every finding** says; fix what holds, in the commit of the cause it belongs to, and keep what does not, with its refutation, for the Reply. On a host that cannot run subagents the second reading is not done: the Reply says so and gives the command for a new session. Reading the change again in this session is not a second reading.
   Done when every axis has reported and each finding is fixed or refuted, or the Reply lists the second reading as not done.
6. **Push to the base branch.** Before pushing, run the repository's checks: each command `.mmw/target.json` lists under `checks`, from the repository root, with `MMW_BASE_REF=origin/<base branch>`. A red check is answered by **principle-fix-the-product-not-the-check**. When the push is rejected, fetch, merge the new base into your commit, run the affected tests and the checks again, and push again.
   Done when the commit is on the base branch on origin, and the checks passed on that commit or the repository declares none.

**Reply:** what changed, and why each new file or dependency was needed; the failing-then-passing test output and the proof from step 3, verbatim; each review finding and what became of it; what the owner should check by hand; and, when it was not done, that the second reading is outstanding.
