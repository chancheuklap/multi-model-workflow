### Make a small change

**You own one change the owner asked for while here, from their words to a commit on the base branch; a reader who did not write it reviews it.** No spec, no ticket and no night stand behind it: no criteria a script runs, no reviewer in a session of its own, no closed ticket as the record. What this session misses reaches the owner unless that reader finds it first. The temptation is to call the change too small for that reader; run **Get a second reading** however small it is. Distinct from Bug fix, which starts from a defect the owner reports, and from Run one ticket, which runs a written ticket.

1. **Write down the change and judge its size.** Before you change the product, read the feature file for this feature under `docs/features/<product>/`. Take the entries from `## How to get to it (user POV)`, the steps from `## Driving it`, and the traps from `## Gotchas`. A product with no such directory has no feature map. Go on, say so in the Reply, and tell the owner to run the `setup-mmw` skill for this product. When no feature file covers the feature, write that file in the shape of the `mmw-mode` skill's `references/feature-map.md`, with `source` `existing <YYYY-MM-DD>`, before you go on. The path you follow is the one that file states. Paste the owner's request word for word into `.scratch/request-<slug>.md` of the repository, which git ignores, `<slug>` the request in a few lowercase words joined by `-`: it is this change's spec, and the request the review reads. The change is small when one session can finish it and it needs no product decision from the owner. When it is not, tell the owner it needs a spec (Write a spec), with what you found; this playbook ends here. Then search the design packages (`efforts/*/claude-design/`) and the screen contracts (`efforts/*/screen-contract.yaml`) for what the request changes: a copy, a control, a state. When one holds it, the change moves a signed baseline, and a code change alone would not last: the story oracle compares the product's text and elements with the design page, so the next ticket on that page goes red and its worker turns the code back. Tell the owner the baseline changes first, through Design in Claude Design and Pull a design, or Write the screen contract for a behaviour, and run that playbook once they agree, since the owner signs a baseline off; this playbook ends here, and runs on the code once the new baseline is on the base branch.
   Done when the file holds the request and the change is judged small and held by no baseline, or the owner has heard why it is not small or which baseline holds it. The feature file was read, or written when none covered the feature. When the product has no feature map, the Reply says so.
2. **Write it test-first.** Run the `tdd` skill. With no ticket, write the seams under test into the request file and confirm them with the owner; the repository's `TESTING.md` says which test layers there are, which external boundaries are stubbed and how tests run. A change to how the tests run (a test layer, a stubbed boundary, a way a test puts the system into a state) changes the root `TESTING.md` in the same commit. A test counts as red only when it fails because the behaviour is absent (**principle-a-check-must-be-able-to-fail**). A change that must keep a behaviour as it is writes a pin before the structure moves (**principle-a-check-must-be-able-to-fail**). A change with no behaviour to test, such as wording or configuration, writes down instead the check that will prove it. Write the code under **principle-start-from-what-exists**, **principle-migrate-callers-then-delete-legacy-apis** and **principle-laziness-protocol**, and, when the request names something already settled, **principle-baseline-is-the-contract**. Keep, for the Reply, one sentence per new file, dependency or configuration entry on why the existing one is not enough.
   Done when every behaviour the change adds or alters has a test that failed before its code was written and passes now, every behaviour it keeps has a pin you have seen go red, or the check that proves it is written down.
3. **Prove it on the product and run the affected tests.** Show, on the product, that the change does what the owner asked, in their words (**principle-prove-it-works**); while the product runs, the `ui-acceptance` skill's **Five rules while the product is running** hold. Prove it with the `verify-this` skill, on the surface the owner named. Bring the product up and drive it as the `ui-acceptance` skill's `references/control-ui.md` or `references/control-cli.md` says. Run one proof for each entry `## How to get to it (user POV)` lists, following `## Driving it`. When the product has no feature map, that one proof is the surface the owner named. The entry the owner named claims the change is in effect. Each other entry claims that entry still works. A verdict other than `VERIFIED` on any entry means the change is not shown. Do not commit. Leave the change in the worktree. The Reply states each verdict and the path under `.scratch/verify/`. Then run the tests **principle-run-the-smallest-test-set** picks. A red test is answered by **principle-fix-the-product-not-the-check**.
   Done when every such entry is `VERIFIED` and the tests pass on the final code, with their output kept for the Reply, or the change is still in the worktree and the Reply states each verdict and the path under `.scratch/verify/`.
4. **Commit it.** Commit only when every entry proved in **Prove it on the product and run the affected tests** is `VERIFIED`. When **Write down the change and judge its size** wrote a feature file, or the change alters a behaviour, an entry, or `## Driving it`, that same commit updates the feature file. Before the commit, run `feature_map.py lint` from the repository root. The program is the `verify-ticket` skill's `scripts/feature_map.py`. A lint that does not pass is not committed. When `docs/features/` is absent, there is nothing to lint, and the commit still proceeds. One commit per cause. It touches only what the cause requires and the tests that prove it. Its message quotes the line the test run printed (`ran 188 skipped 0`, not "the tests pass"). A change that exceeds those three is a ticket after all: tell the owner it needs one.
   Done when the change is committed on the base branch under those three rules, every proved entry was `VERIFIED`, and `feature_map.py lint` passed before the commit or `docs/features/` is absent.
5. **Get a second reading.** Run the `code-review` skill with the axes Standards, Spec and Tests, the commit this change started from as the base, and the request file as the request: its axes cannot read this conversation. Do not tell it which parts you believe are right. Check each finding as Review a ticket's **Verify every finding** says; fix what holds, in the commit of the cause it belongs to, and keep what does not, with its refutation, for the Reply. On a host that cannot run subagents the second reading is not done: the Reply says so and gives the command for a new session. Reading the change again in this session is not a second reading.
   Done when every axis has reported and each finding is fixed or refuted, or the Reply lists the second reading as not done.
6. **Push to the base branch.** Before pushing, run the repository's checks: each command `.mmw/target.json` lists under `checks`, from the repository root, with `MMW_BASE_REF=origin/<base branch>`. A red check is answered by **principle-fix-the-product-not-the-check**. When the push is rejected, fetch, merge the new base into your commit, run the affected tests and the checks again, and push again.
   Done when the commit is on the base branch on origin, and the checks passed on that commit or the repository declares none.

**Reply:** what changed, and why each new file or dependency was needed; the failing-then-passing test output and the proof from step 3, verbatim, with each entry's verdict and the path under `.scratch/verify/`; each review finding and what became of it; what the owner should check by hand; when the product had no feature map, that it had none; and, when it was not done, that the second reading is outstanding.
