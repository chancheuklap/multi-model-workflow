### Bug fix

**You own the diagnosis and the ticket that carries it; the fix and its proof on the product are a worker's, landed through Run one ticket.** Be scientific: every line of the ticket traces to runtime evidence, and a change that "might help" is a hypothesis, not a fix. Distinct from Make a small change, which changes behaviour the owner wants different, and from Investigation, which answers and changes nothing.

1. **Reproduce it yourself.** Before you drive the product, read this feature's file as the `mmw-mode` skill's `references/feature-map.md` `## Using it in a task` says. Follow the `diagnosing-bugs` skill's Phase 1 and Phase 2 on the surface where the owner saw the bug; while the product runs, the `ui-acceptance` skill's **Five rules while the product is running** hold. Bring the product up and drive it as the `ui-acceptance` skill's `references/control-ui.md` or `references/control-cli.md` says. Drive it yourself even when a debugging protocol says to ask the owner to reproduce; ask the owner only with a stated reason the surface cannot reach the bug, and only after driving it as far as it goes. When the symptom throws no error and shows only in the running product (a leak, a spin, a hang, a glitch), run **Runtime forensics** instead of building the loop; when the owner hands over a captured artifact, run **Trace forensics**. Either one's diagnosis takes the place of this step and **Find the cause**: go on at **Write the ticket**. When no loop can be built and neither applies, tell the owner what you tried and what you need, as Phase 1 says; this playbook ends here.
   Done when one command, already run, shows the owner's exact symptom on a minimised scenario, reached by an entry that feature file states, a forensics playbook has handed back its diagnosis, or the owner has heard what you tried and what you need. When the product has no feature map, that command was still run, and the Reply says there is none.
2. **Find the cause.** Follow `diagnosing-bugs` Phase 3 and Phase 4. Seed the hypotheses with the `how` skill over the affected subsystem and the `why` skill for the change that brought the bug in. Confirm the surviving mechanism with runtime evidence, then remove every tagged debug line. When the code does what was asked and the owner wants it otherwise, it is not a bug: tell the owner it is a change, for Make a small change or Write a spec; this playbook ends here.
   Done when one hypothesis survives on runtime evidence, the others are ruled out, and no debug line is left.
3. **Write the ticket.** Write one ticket in the format of the `verify-ticket` skill's `references/ticket-format.md`, with `None` under **Parent**. **What to build** states the symptom, the cause with its evidence, and the smallest change that evidence justifies; evidence from a forensics artifact is cited by the artifact's path, quoting only function names, the product's own file paths and numbers. **Seam** is where a regression test exercises the bug as it happens at the call site (`diagnosing-bugs` Phase 5); when there is no such seam, say so there, since that is itself a finding. The first criterion is the regression test at that seam. The second is the step 1 command, on the original scenario, whenever it runs unattended, gives the same verdict every run and needs no file only this checkout holds: it goes red on the base branch before the fix, and the worker's run of it is the proof on the surface the owner saw, so nothing proves the fix again after it lands. When the fix changes what the feature file says, the ticket carries that change as `references/feature-map.md` `## Using it in a task` says. Publish it with the labels `mmw:ticket` and `ready-for-agent`, and the worker label the format's rule gives; then run `verify-ticket.py <n> --lint` and fix every `ERROR`.
   Done when the ticket is on the tracker and `--lint` reports no `ERROR`.
4. **Land it.** Run **Run one ticket** on this ticket. Its closing comment holds the worker's run of every criterion, the reproduction included; whether the fix landed is what `land` printed.
   Done when its `land` has exited 0.

**Reply:** what was broken, the root cause, the fix (the ticket and the commit `land` made), and the proof: the reproduction's red run from **Reproduce it yourself** and its green run from the ticket's closing comment, verbatim. When the product had no feature map, say so.
