### Bug fix

**You own the diagnosis, the ticket that carries it, and the proof on the product; the fix is a worker's, landed through Run one ticket.** Be scientific: every line of the ticket traces to runtime evidence, and a change that "might help" is a hypothesis, not a fix. Distinct from Make a small change, which changes behaviour the owner wants different, and from Investigation, which answers and changes nothing.

1. **Reproduce it yourself.** Before you drive the product, read the feature file for this feature under `docs/features/<product>/`. Take the entries from `## How to get to it (user POV)`, the steps from `## Driving it`, and the traps from `## Gotchas`. A product with no such directory has no feature map. Go on, say so in the Reply, and tell the owner to run the `setup-mmw` skill for this product. When no feature file covers the feature, write that file in the shape of the `mmw-mode` skill's `references/feature-map.md`, with `source` `existing <YYYY-MM-DD>`, before you go on. The path you follow is the one that file states. Follow the `diagnosing-bugs` skill's Phase 1 and Phase 2 on the surface where the owner saw the bug; while the product runs, the `ui-acceptance` skill's **Five rules while the product is running** hold. Bring the product up and drive it as the `ui-acceptance` skill's `references/control-ui.md` or `references/control-cli.md` says. Drive it yourself even when a debugging protocol says to ask the owner to reproduce; ask the owner only with a stated reason the surface cannot reach the bug, and only after driving it as far as it goes. When the symptom throws no error and shows only in the running product (a leak, a spin, a hang, a glitch), run **Runtime forensics** instead of building the loop; when the owner hands over a captured artifact, run **Trace forensics**. Either one's diagnosis takes the place of this step and **Find the cause**: go on at **Write the ticket**. When no loop can be built and neither applies, tell the owner what you tried and what you need, as Phase 1 says; this playbook ends here.
   Done when one command, already run, shows the owner's exact symptom on a minimised scenario, reached by an entry that feature file states, a forensics playbook has handed back its diagnosis, or the owner has heard what you tried and what you need. When the product has no feature map, that command was still run, and the Reply says there is none.
2. **Find the cause.** Follow `diagnosing-bugs` Phase 3 and Phase 4. Seed the hypotheses with the `how` skill over the affected subsystem and the `why` skill for the change that brought the bug in. Show the ranked list to the owner and carry on without waiting. Confirm the surviving mechanism with runtime evidence, then remove every tagged debug line. When the code does what was asked and the owner wants it otherwise, it is not a bug: tell the owner it is a change, for Make a small change or Write a spec; this playbook ends here.
   Done when one hypothesis survives on runtime evidence, the others are ruled out, and no debug line is left.
3. **Write the ticket.** Write one ticket in the format of the `verify-ticket` skill's `references/ticket-format.md`, with `None` under **Parent**. **What to build** states the symptom, the cause with its evidence, and the smallest change that evidence justifies; evidence from a forensics artifact is cited by the artifact's path, quoting only function names, the product's own file paths and numbers. **Seam** is where a regression test exercises the bug as it happens at the call site (`diagnosing-bugs` Phase 5); when there is no such seam, say so there, since that is itself a finding. The first criterion is the regression test at that seam; when the step 1 command runs unattended and gives the same verdict every run, it is the second. When **Reproduce it yourself** wrote a feature file, or the fix changes a behaviour, an entry, or `## Driving it`, **What to build** names that file and puts it in the same commit as the fix. It also says to run `feature_map.py lint` from the repository root before that commit, and not to commit when the lint does not pass. When `docs/features/` is absent, the ticket says there is nothing to lint. The program is the `verify-ticket` skill's `scripts/feature_map.py`. Publish it with the labels `mmw:ticket` and `ready-for-agent`, and the worker label the format's rule gives; then run `verify-ticket.py <n> --lint` and fix every `ERROR`.
   Done when the ticket is on the tracker and `--lint` reports no `ERROR`, and any feature file this fix needs is named there in the same commit as the fix.
4. **Land it.** Run **Run one ticket** on this ticket.
   Done when its `land` has exited 0.
5. **Prove it on the same surface.** On the base branch, with the fix landed, run the step 1 command on the original scenario, not the minimised one; after a forensics diagnosis, capture the same signal the same way and compare it with the first capture. Prove that run with the `verify-this` skill. The baseline is the reproduction from **Reproduce it yourself**. The treatment is that same command after the fix, on that same surface. Run one proof for each entry `## How to get to it (user POV)` lists, following `## Driving it`, and drive the product as the `ui-acceptance` skill's `references/control-ui.md` or `references/control-cli.md` says. When the product has no feature map, that one proof is the surface the owner saw. The entry the owner reported claims the bug is fixed. Each other entry claims that entry still works. A verdict other than `VERIFIED` on any entry means the fix is not shown. Do not commit anything still uncommitted. Leave that work in the worktree. The Reply states each verdict and the path under `.scratch/verify/`. "Inconclusive", or a check on another surface, is not a pass (**principle-prove-it-works**): say so.
   Done when every such entry is `VERIFIED` and the original repro runs green where it ran red, the second capture no longer shows the cause the forensics diagnosis named, or the Reply states each verdict and the path under `.scratch/verify/` and nothing further was committed.

**Reply:** what was broken, the root cause, the fix (the ticket and the commit `land` made), and how you verified it; paste the failing and the passing repro output verbatim. State each entry's verdict and the path under `.scratch/verify/`. When the product had no feature map, say so.
