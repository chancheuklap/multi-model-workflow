### Work a ticket

**You own one ticket, as its worker, from its claim to its closing comment; its reviewer is dispatched from here.** A script started you on it and nobody is watching, so the mode's **Unattended** paragraph holds from the first step. Distinct from Review a ticket, which judges this work and writes nothing but its report.

Commands of the `verify-ticket` skill's `verify-ticket.py` and the `dispatch` skill's `dispatch.sh` are named bare below. Every `--sub-issue` run is in the `verify-ticket` skill's `references/sub-issues.md`. A fault in the pipeline itself (its own scripts, a hook, or `.mmw/target.json`): `verify-ticket.py <n> --sub-issue fault <file>`, whose body is the command you ran and the output you saw, then stop.

1. **Claim the ticket and find your step.** Run `verify-ticket.py <n> --preflight`. On `NOT_READY`, stop: the reason is already on the ticket, as a `ticket.refused` event that wakes the orchestrator. A `RESUME:` line names, by its title, the step below to carry on at; where you are is what the ticket's events say, not what this session remembers (**principle-progress-is-what-the-record-says**). With no `RESUME:` line, go on to the next step. The branch may already carry the commits of an earlier worker of this ticket whose session ended, among them a `wip(#<n>): uncommitted work of …` commit holding what it left uncommitted. They are this ticket's work: carry on from them.
   Done when `--preflight` claimed the ticket and you are at the step its `RESUME:` line names or the next one, or it printed `NOT_READY` and you stopped.
2. **Read yourself in and write the code.** Read until you know what this ticket delivers, what it must not contradict, and the words the repository uses for them: the ticket in full, comments included, and its own open sub-issues (`gh api --paginate repos/{owner}/{repo}/issues/<n>/sub_issues?per_page=100 --jq '.[] | select(.state=="open")'`), as a supplement to **What to build** (whether you do them goes under `Decisions I made on my own`); then every item under its **Read first**, each through to its conclusion: the part of a research file that answers its question, an ADR's decision in the untitled paragraph under its title, a design package pulled into the repository, a prototype's leaf `README.md` read to its verdict. A baseline in **Read first** is anything there that records a settled conclusion, and it is a contract, not a reference. A design package is copied exactly; a prototype is rewritten to production standard, keeping the shape its verdict settled on. Then follow **Parent** to the spec: read its Problem Statement and Solution, the few lines that say who uses this and why, then only the Implementation Decisions sections the ticket names, plus its Testing Decisions and Out of Scope (with the map's **Out of scope** when it links one), not the whole spec. Where the ticket is silent, choose what serves the person the Problem Statement names. Then the domain glossary (the root `CONTEXT.md`, or the `CONTEXT.md` of each context `CONTEXT-MAP.md` lists that this ticket touches): where it has a term for the thing you name, use that term. When **Read first** lists a screen contract, read the `ui-acceptance` skill's `references/writing-interface-code.md`. Read `references/memory.md` whatever your start prompt's Memory indexes hold, `none` included: open the records they list that bear on this ticket, and from here to the last step save each fact its `## Save` conditions name.   Write the code test-first with the `tdd` skill, at the seams the ticket's **Seam** names. Where an acceptance criterion's `CHECK:` names a test case, that case is your first red test: run it before writing the code it covers and read why it fails (**principle-a-check-must-be-able-to-fail**). A criterion that is a pin is run green before the structure moves, and broken once by hand to see it red. No later step does this for you: the claim-time baseline ran before the test existed, and the review reads tests without running them. While writing:
   - Every baseline under **Read first**, and every spec section **Parent** names, is followed as **principle-baseline-is-the-contract** says; a prototype is rewritten to production standard, keeping the shape its verdict settled on. Where one does not hold, or an acceptance criterion lacks a state, field, interaction or case or contradicts another such source, keep going and run `verify-ticket.py <n> --sub-issue contract <file>`. When the rest of the ticket depends on the answer, end your turn: the child wakes the orchestrator, which corrects the source and resumes you, or leaves the question to the owner. A wrong `CHECK:` is a `contract` child too: name the acceptance criterion, quote what is wrong, and state what it should be. Once a batch is published, only its orchestrator or the owner edits a spec, ticket body or acceptance criterion.
   - Put no question on the screen (**principle-never-block-on-the-human**). Take the option the ticket, its baselines and the spec make most likely, write one line for it under `Decisions I made on my own`, and keep going. A question whose answer would change what the ticket delivers gets `verify-ticket.py <n> --sub-issue decision <file>` instead, and the rest of the work carries on. Write each line for the reviewer, who judges it, and for the owner, who reads it in the morning without your context: a choice the owner would notice in the product (a label, a default, what a page shows or hides) is the one most worth a line. A file, a dependency or a configuration entry you add gets a line there saying why the existing one was not enough: the review asks for it.
   - A file outside **Owns**: change it when a criterion cannot pass otherwise, or when the defect sits in shared code that is fixed once for every caller (**principle-migrate-callers-then-delete-legacy-apis**), and it lands under `Outside Owns:` in the closing comment; when the change is merely convenient, leave it and run `verify-ticket.py <n> --sub-issue deferred <file>`. A file owned by a ticket that can run beside this one (neither blocks the other, directly or down a chain) is never changed from here, whatever needs it: run `verify-ticket.py <n> --sub-issue contract <file>`, because one file has one writer at a time and the cut missed an edge (**principle-separate-before-serializing-shared-state**).
   - Run typechecking and single test files regularly, and, once at the end, the tests the repository's own instructions name for what this ticket changed (**principle-run-the-smallest-test-set**); the repository's `checks` run when `advance`, or `land` outside a night, merges the ticket into the base branch. Verify your work however you like; scratch scripts and quick checks need not be kept.
   Done when every point under **What to build** has its code and the tests the ticket asks for, committed to the ticket's branch.
3. **Integrate and run every criterion.** Integrate `origin/<base branch>` first: `dispatch.sh integrate <n>`, from this ticket's worktree. Exit 3 leaves a conflicted merge in the tree. The incoming side is closed tickets whose criteria the closing pass's `reverify` runs again on the base branch, so read each incoming ticket and its closing comment before you resolve, and keep what landed: a resolution that drops their behaviour reopens their ticket hours later, and after a bounce no reviewer sees this merge. Where theirs and yours cannot both hold, the cut missed an edge: keep what landed and run `verify-ticket.py <n> --sub-issue contract <file>` naming both tickets. Note each trade-off under `Decisions I made on my own`, run the tests that cover the files the merge conflicted in, commit the merge, and run `dispatch.sh integrate <n>` again. Exit 2 names the condition that prevented integration; a pipeline failure becomes a `fault` sub-issue, then stop. Never rebase, abort or push from this integration. When the ticket came back with a `ticket.bounced` event whose line names `Failed checks:`, the repository's checks failed on its merge result, and a merge with no conflict can still cause that: read the incoming tickets `integrate` names and their closing comments, as for a conflict, and keep what landed; then run each named command from this worktree after the integration and fix the product until it exits 0. Then run every criterion: `verify-ticket.py <n>`. A criterion passes only when its `CHECK:` exits 0 and its output matches `EXPECT:`. A run that exits 2 ran nothing and its stderr says why; with every product slot of the machine held, report the ticket blocked by rule 4 of the `ui-acceptance` skill's **Five rules while the product is running**. How many rounds a criterion gets is your judgement: keep fixing the product while a fix is in sight (**principle-fix-the-product-not-the-check**), and when none is, give it the line `ABANDON: AC<n> failed <what each round tried>` (the `verify-ticket` skill's `## ABANDON lines`), which step 10 puts in the closing-comment draft, and carry on with the rest.
   Done when `verify-ticket.py <n>` has recorded a run of your own after the integration.
4. **Post the decisions comment.** Once: `verify-ticket.py <n> --decisions <file>`. The file is two sections, each opened by its `## ` heading: `## Decisions I made on my own`, with every line written so far, one per line, in the shape the closing comment uses; and `## Outside Owns`, with the `Outside Owns:` line of your newest run (its `ticket.checked` event, run `self`), followed by one sentence per file saying which criterion could not pass without it; `None` when that line is `None`. It is posted here, before the reviewer starts, so the review judges every line of it, and once: the review's fix round adds nothing to it, and the closing comment carries the final version.
   Done when `--decisions` exits 0.
5. **Start the reviewer.** Run `dispatch.sh start <n> reviewer`, then end your turn. One reviewer per round. Exit 2 whose stderr says to start again: run it once more. Any other exit 2, or a second one: the pipeline is at fault, so open a `fault` child as the `verify-ticket` skill's `references/sub-issues.md` says, and stop.
   Done when `start` exited 0 and your turn has ended, or the `fault` child is open.
6. **Read the review.** When `#<n> reviewer.reported` wakes you, do the `dispatch` skill's `## On waking`, then read the report: `dispatch.sh wait <n> reviewer` prints the event with the two commits it read. When `#<n> reviewer.lost` wakes you instead, the reviewer died with no report: do `## On waking`, then go back to **Start the reviewer**. The in-ticket round is first: fix the in-ticket findings once, under the rules that governed the first write in **Read yourself in and write the code**, and run **Integrate and run every criterion** again. An in-ticket finding you do not fix is answered `refuted:`, which says you checked and the bad outcome does not happen at the cited location. Write what disproves this specific claim; a true fact about nearby code that does not disprove the claim does not count. Then, for each out-of-ticket finding whose body the in-ticket round has not made untrue, run `verify-ticket.py <n> --sub-issue finding <file>`.
   Done when the review report is read and its wake acked, each in-ticket finding is fixed or `refuted:`, and each out-of-ticket finding still true has its `finding` child.
7. **Run every criterion one final time.** `verify-ticket.py <n> --reverify --actor worker`. It runs after the last step that writes a commit, including the review fix, and includes criteria earlier runs already ticked. If anything still fails, write `ABANDON: AC<n> failed` for each failure and close out `HANDOFF REQUIRED`; this final run gets no fix round.
   Done when the final run is on the ticket at `HEAD`.
8. **Audit.** Read the ticket once more against the branch, the way the owner will read your closing comment. Each point under **What to build** holds in the product, not only in a test (**principle-prove-it-works**), and each baseline under **Read first** is followed where it applies. A point that does not hold is said in the closing comment; nothing is committed after the final run.
   Done when you can name, for each point and each baseline, where the branch follows it or the line of the closing comment that says it does not.
9. **Tell the tickets whose files you changed.** `verify-ticket.py <n> --touched`.
   Done when `--touched` exits 0.
10. **Write the closing-comment draft.** First cut loose what only a person can settle: a criterion that waits only on one sentence from a person gets `ABANDON: AC<n> decision <question, options, and the default if nobody answers>` **and** `verify-ticket.py <n> --sub-issue decision <file>`; the ticket does not stop. Then `verify-ticket.py <n> --draft`, which prints the path it wrote as `DRAFT: wrote <path>`; give that run no path of your own. Fill every `<fill>`: `skipped:` as `[X], add when [Y]`; each review finding as `fixed <commit>` or `refuted: <what actually happens at path:line>`; each criterion under `Green before work:` with the landed ticket that did that work, with the fact that it is a pin for behaviour this ticket keeps, or with the fact that this `CHECK:` cannot see this ticket's behaviour (then also a `contract` child); `Decisions I made on my own` with every line written so far. Put each `ABANDON:` line under its criterion.
    Done when the closing-comment draft has no `<fill>` left.
11. **Close the ticket.** Run `verify-ticket.py <n> --closeout <draft>`. It posts the closing comment and puts `ticket.passed` or `ticket.returned` on the ticket, which wakes the orchestrator to land it. Never close the ticket or swap its labels yourself: a hook blocks the command. Open no pull request, and do not run `land` from this session: it stops every session the ticket's events name, this one included.
    Done when `--closeout` exits 0.

**Reply:** the closing comment `--closeout` posted is this run's reply; this session's own last message is read by nobody.
