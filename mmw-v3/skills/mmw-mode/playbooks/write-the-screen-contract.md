### Write the screen contract

**You own one effort's screen contract, `docs/specs/<effort>/screen-contract.yaml`: every control of the design package bound to the backend decision behind it, every gap settled with the owner, and the file linted clean and committed.** The design package is the decided look and the decisions are the decided behaviour; this file joins them and decides neither. What the file is, its rules and its scripts are the `write-screen-contract` skill; read its `SKILL.md`, and its `references/screen-contract-format.md` before step 3. Distinct from Write a spec, which reads this file and stops on any row it leaves unaligned.

Work in a `<scratch>` directory this run created, as the skill's `## Scripts` says. Steps 3 to 6 are four passes over the same rows; go back and forth between them as the rows fill. Step 2 comes first because the skeleton needs its keys, and step 8 comes last because nothing reaches `docs/specs/` until the owner has settled the gap list.

1. **Gather the inputs.** The design package directory (`<package dir>`) as Pull a design wrote it, read-only. The backend decisions: on a map, its **Decisions so far** in the issue body and, through each link, the closed tickets' resolution comments, with each ADR, research file or domain document a resolution names; when the decisions were settled in conversation, those conclusions. The backend contract as it exists today, `openapi.json`: from the repository's own exporter when it covers this product; otherwise from the skill's `scripts/dump_openapi.py` for a FastAPI app factory; otherwise written by hand in `<scratch>`, describing exactly the routes, methods, fields and status codes the server's routing code implements. The effort name `<effort>`: the directory under `prototypes/` that holds `<package dir>`, which is also its directory under `docs/specs/`.
   Done when you hold all four.
2. **Declare the rendering inputs and extract the skeleton.** Start `<scratch>/screen-contract.yaml` with the top-level `effort`, `baselines`, `locale` and `viewports`. `locale` is the locale the design must render under: the product's own `<html lang>` when it has one, otherwise the owner names it; the package names none. The package `README.md` lists each page's `$preview` size under `## Viewport and size source`: `viewports` holds the size most pages share, and a page drawn at another size gets that size as its own `pages.<page>.viewports`, written now. Then run the skill's `scripts/extract_skeleton.py`.
   Done when `<scratch>/skeleton.json` is written.
3. **Declare pages, name components and split preconditions.** For each page in `scenes.json`, write one `pages` entry with its **`mount`**, the short stable id the product will serve as the story page (`?page=<mount>`). `mount` is your declaration, not a derivation: a page holds several components' rows, and the one with most rows can be a shared control borrowed from another page. For a `Component · ` page also name the **`component`** the implementation will own it under: the repository's existing feature directory or module file when there is one, otherwise the page name; every row of that page's controls uses the same value. An `App · ` page is a whole-surface root and names no component. Then a control whose behaviour differs by state gets one row per state, told apart by `precondition`. A disabled state is a row (`calls: [none]`, `next: stay`). A state the design package never shows is still a row when the backend decisions reach it, with `scenes: []`, so the gap is on record. A placeholder or hint the accessibility tree folds into a name is an accessibility defect of the design package: note it for the reply, not in the file.
   Done when every page has its entry and every skeleton control that is clickable or editable has its rows.
4. **Fill the behaviour columns and the scene declarations from the backend sources.** For every row: `calls`, `shows`, `next`, `on_failure`, `source`, `gap`, by the format reference's column rules. The ones people get wrong: `shows` names fields, never values, and the literals and counts in a page's data file under `data/` are seed data for tests, not copy; `calls` names what the control does to the system, and a control that only changes local view state is `none` and still a row; `source` cites the Implementation Decisions subsection that carries a story's conclusion, not the story, and a row whose sources are all `code:` and README is a `design-only` candidate, so check the decisions again before marking it. Where an operation under `proposed_operations` is new or changed and other products share this backend, note it for the spec. Then one `scenes` entry per scene of `scenes.json`: its `page`, and its `input` when the page draws that scene from a data file in the package (read the page's script for the file it loads, the value it reads for the scene, and anything it sets on top).
   Done when every row has every column and every scene has its entry.
5. **Write each cross-component row from the App-page wiring.** A behaviour that crosses regions belongs to no Component page's ticket: the App row is the only place it gets an owner, so a link left out here is one nobody builds. Read every `App · ` page's wiring, the callbacks and state passed between its `dc-import`s; each place region A's action affects region B is one cross-component row on that App page, as the format reference's **A cross-component row** says. An App page whose wiring passes nothing from one region to another goes on the gap list.
   Done when every App page has its cross-component rows or a gap-list entry.
6. **Sweep in reverse.** The forward passes find only what the design draws; this one finds what the backend decided that the design forgot, while the owner is still here to settle it. The lint sweeps `openapi.json`; you sweep the decisions: every decision line an end user could notice (a value shown, a state reached, a failure seen) lands in a row's `source`, becomes a `backend-only` row, or gets one line under `backend_without_ui` saying why the UI has no place for it.
   Done when every such decision line is in one of the three places.
7. **Write the gap list and settle it with the owner.** Collect every row whose `gap` is `design-only` or `backend-only`, every scene the owner has judged cannot be captured, and every App page step 5 found no cross-component row for, into `<scratch>/gap-list.md`: one entry each, with the row id or scene, what the design shows, what the backend decides, the options, and the one you would take. Put the list to the owner: this is the one judgement in this playbook that is theirs, and it is a grilling, not a form, so read the `grilling` skill's `SKILL.md` first. Expect a handful of entries; dozens means a decision was skipped upstream, and that goes back to the map or the conversation. A gap list does not carry an implementation that today does less than the decisions say (a finding for the ticket that will own the code, for the reply), nor an accessible name the shipped product will render differently from the design package.
   Done when the owner has answered every entry and each answer is in its row, cited as `conversation <YYYY-MM-DD>`.
8. **Lint and commit.** Run the skill's `scripts/lint_screen_contract.py` on `<scratch>/screen-contract.yaml`, `<scratch>/skeleton.json` and the `openapi.json`, from inside the repository, to zero errors. Copy the file to `docs/specs/<effort>/screen-contract.yaml` and commit it.
   Done when the lint exits 0 and the file is committed.

**Re-runs.** A re-run makes a new `<scratch>`, copies `docs/specs/<effort>/screen-contract.yaml` into it as `<scratch>/screen-contract.yaml`, and runs step 2's command against that copy. After a pull whose `pull-report.md` `改动分类` is `增删控件或改流转`, edit only the rows those controls belong to; a control whose `data-ui` id is unchanged keeps its bindings, and new disagreements go to the owner. After a spec decision changed, edit the rows that cite it and put the changed rows through step 7. Either way, finish with step 8.

**Reply:** the file's path and its row count; each gap-list entry and the owner's answer; the accessibility defects and implementation findings noted along the way; the operations under `proposed_operations` other products share; and the next run: on a map's alignment ticket, **Resolve a map ticket** step 4 records the resolution; otherwise, after a first contract, **Write a spec**; after a re-run, **Revise a spec**, with the tickets already cut corrected against the new text.
