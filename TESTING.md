# Testing

How this repository's tests run. Whoever writes a spec or a ticket draws the seam from it, and the review's Tests axis reads it as facts. The rules for what makes a good test are in the principles, not here.

## Where the tests live, and their layers

- A skill's tests live in `mmw-v4/tests/<name>/`, which exists only in a checkout and climbs two levels to `mmw-v4/` and down into `skills/<name>/scripts/` to reach the script under test. gate-check's own tests are in `mmw-v4/tests/verify-ticket/gate-check/`, and the `verify-ticket` suite runs them. The prompt renderer's tests are in `mmw-v4/prompt/tests/`.
- `mmw-v4/tests/session-start/` runs `session-start.py` as a process with both hosts' SessionStart payloads. It checks the startup and compaction context, one-line JSON output, and that malformed input exits 0 without context. Real-host payload and context checks are recorded in `session-start.py`'s header.
- `mmw-v4/tests/reply-check/` runs `reply-check.py` as a process with each host's Stop payload, temporary repositories with tracked and untracked nested glossaries, git-ignored files and excluded directories, a non-repository working directory with an unrelated child glossary, MMW's own checkout glossary, and a test `MMW_HOME`. Open briefs are written through `briefs.py`; a fake runner answers `self`, and a fake `gh` refuses tracker calls. It checks exit codes, reported hits and replacement terms, and that exemptions leave the state unchanged. Real-host payload and block checks are recorded in `reply-check.py`'s header.
- `mmw-v4/tests/relay/test_runner_screen.py` runs the real runner adapters as processes. A fake `orca` supplies successive screens and turn probes for `start` and `state`. Its read timestamps check the two-second confirmation interval. Fake `herdr` and `paseo` supply status lists for `state`. The tests check output, exit codes, and refused-start terminal closure.
- `mmw-v4/tests/relay/test_orca_send.py` runs the real `runners/orca.sh send` as a process, with a fake `orca` first on `PATH` and a temporary `MMW_HOME`, and checks its exit code and the calls the fake logged.
- The install tests live in `mmw-v4/tests/install/test_install.py`; they need `mmw-v3/` beside `mmw-v4/`, because `--back` and the takeover of a v3 machine run its `install.sh`.
- `mmw-v4/tests/lib/` holds the four shared checks every suite runs first (`check_module_paths.py`, `check_wiring.py`, `check_host_neutrality.py`, `check_skill_frontmatter.py`), and its own `run.sh` tests `check_wiring.py` and `check_host_neutrality.py`.
- Four layers:
  - **unittest** (`test_*.py`): a script loaded as a module by its file path and called with fixed input (`mmw-v4/tests/verify-ticket/_load.py` loads `verify-ticket.py` and `events.py` this way).
  - **end to end** (`test_*.sh`, and the `test_*.py` that run a script as a process): the real script run as a process, with the external boundaries below replaced by fakes (`mmw-v4/tests/dispatch/test_dispatch.sh`, `mmw-v4/tests/relay/test_relay.sh`, `mmw-v4/tests/liveness/test_guard.sh`, `mmw-v4/tests/install/test_install.py`).
  - **node** (`*.test.mjs` under `mmw-v4/tests/board/`, and gate-check's `run-tests.mjs` and `lint-tests.mjs`): the board's page modules and gate-check's engine.
  - **browser**: the board suite drives the real board in a headless Chromium through Playwright.
- `mmw-v4/tests/register-problem/test_register.py` tests the registration command as a module and as a process. Its fake `gh` holds issues, labels, parents, closing links, and event comments. The concurrency case holds one fake issue read at a file gate until the test releases it, while a second registration runs. The tracker fixture locks each request rather than a whole registration. Git repositories, process identities, and locks run for real in temporary directories, with `MMW_HOME` pointing at the test home.
- `mmw-v4/tests/retro/test_retro.py` calls gather, apply, backlog, and merge-apply as commands against a paginated fake `gh`, with process cases using that fake on `PATH`. The gather replays use selected real start, suspension, and contract event comments and child bodies from #1165, agentflow #1618, and agentflow #1418 in `mmw-v4/tests/retro/fixtures/`, before their retrospective receipts. The settlement case uses the real opening and closing comments for #1358, whose closing event stores the child number as a string. Run histories and occurrences are dated event comments. Gather runs against real temporary git commits and reverts. Fixed analyst answer tables drive apply without starting sessions, including a gather-to-apply case using the generated context. Assessment and receipt write failures are injected to test replay from the material directory's `.retro-apply` journal; comment markers prevent duplicate writes. Registration lookup failures are injected before writes and retried with the same answer. New-problem entries exercise multiple evidence sources and missing files; unreadable sources appear in partial receipts. Missing or empty Problems sections refuse before writes. The apply process tests log fake `gh` calls, check each cross-repository write destination, and compare registration state before and after mixed answer tables; separate rows about one registration remain separate assessment events, including conflicting conclusions. Loose analyst codes identify registrations; free-text conclusions and proposals stay verbatim in assessment events. Mixed answers include unresolved targets in receipts and malformed problem entries alongside readable registrations. Backlog fixtures include open and closed registrations, multiple repositories, and assessment and merge events with equal timestamps and out-of-order comments. Decision JSON drives merge-apply; the fake tracker persists copied occurrences, closure reasons, duplicate destinations, and merge events across process retries. Lost responses after each write test recovery without duplicate comments. `MMW_HOME` points at a test home.
- `mmw-v4/tests/writing-for-agents/` and `mmw-v4/tests/worktree-audit/` test the comparison and audit scripts as processes. The comparison fixtures commit baseline upstream and local copies, then a separate upstream update, in real temporary repositories; local-copy variations stay in the working tree. The audit fixtures use a bare origin and clone with `dev` ahead of `main`, `origin/HEAD` pointing to `dev`, and a worktree merged into `dev`. Only `gh` is faked on `PATH`; neither suite reaches GitHub or the machine’s session records.
- `mmw-v4/tests/writing-for-agents/test_usage.py` runs the evidence command as a process against a temporary skill tree and synthetic session records. `--repo`, `--claude`, and `--codex` keep every read inside those fixtures.
- `mmw-v4/tests/dispatch/test_parallel_runner.sh` runs the scenario runner against fixture scenarios with overlapping execution and a deliberate failure. It checks grouped output, failed-scenario diagnostics, successful-scenario PASS lines, unknown names, the concurrency override, and exclusive port use across simultaneous suite runs, and cancellation without starting queued scenarios.
- `check-interfaces.py`, beside `dispatch.sh`, checks that the dispatcher's side and the agent's side of every role meet; the dispatch suite's `test_check_interfaces.py` tests the checker itself.

## How to run them

- One suite: `bash mmw-v4/tests/<name>/run.sh`; the prompt renderer's: `bash mmw-v4/prompt/tests/run.sh`. There is no aggregate runner of the suites; `scripts/check` runs the ones a change needs, and `scripts/check --all` every one. Each `run.sh` header names what it tests and the tools it needs; every suite needs `uv` for the shared frontmatter check.
- A passing suite's last line is `all passed` (`全过` for `exe-release`).
- `diagram-design` and `verify-ticket` take `-k <pattern>`, the substring or glob `python3 -m unittest -k` accepts (`mmw-v4/tests/lib/parse_k.sh`); under `-k` the `verify-ticket` suite skips its node half. `setup-mmw` takes a bare name pattern.
- One dispatch scenario: `bash mmw-v4/tests/dispatch/test_dispatch.sh <scenario>`, `all` for every one; several names run as separate processes. `MMW_TEST_JOBS` overrides the CPU-count concurrency. Interrupting the runner stops its active process groups and discards queued scenarios. Board-command scenarios run serially after the others. A machine-wide per-user lock covers supervisor allocation and startup so concurrent watch-opening scenarios receive distinct board ports across suite runs. Board-command scenarios hold that same lock through their cleanup. An unknown name lists the names discovered from its scenario functions, and a passing scenario's last line is its EXPECT string. `mmw-v4/tests/relay/test_relay.sh` takes the same argument.
- `scripts/check --step <name>[,<name>…]` runs only the named steps without selecting by changed paths. An unknown name exits 2 and lists the known names.
- `python3 mmw-v4/skills/dispatch/scripts/check-interfaces.py` prints `INTERFACES OK`.

## Stubbed boundaries

- **Research browsers.** `test_briefs.py` puts a logging fake `playwright-cli` on `PATH` and starts sleeping processes named for its batches. It advances the relay clock past the abandoned-parent deadline and checks cleanup, process isolation, and removal despite cleanup errors. A failing fake `ps` supplies the cleanup-error case. `test_dispatch.sh` puts a fake `playwright-cli` on `PATH`. Its `open` starts a test-owned daemon whose command line contains `cliDaemon.js` and the session name, with a child process. Both ignore SIGTERM, and its `close` only logs the call. Tests inspect real process liveness to check forced cleanup and isolation from another batch. The exit trap cleans up fixture processes.
- **The tracker.** No test reaches GitHub. `test_dispatch.sh` and `test_relay.sh` put a fake `gh` on `PATH` that logs every call, one per line with fields joined by ` :: `; `test_dispatch.sh`'s answers from environment variables and a JSON file of ticket rows (`FAKE_GH_TICKETS_FILE`). The board suite has its own fake under `mmw-v4/tests/board/github/`. `mmw-v4/tests/setup-mmw/test_setup.py` answers every `gh` command with a fake inside the test. Most cases also fake git, while the environment-probe cases run real git worktrees and a committed fixture `scripts/env`. The verify-ticket suite runs against fixed ticket bodies, and `_load.py` makes `ticket_spec` answer `None`, so no module it loads asks the tracker which spec a ticket sits under.
- **The runners.** `test_dispatch.sh` puts fake `paseo`, `herdr` and `orca` on `PATH`, each logging every call. `test_relay.sh` delivers through the real `runners/paseo.sh` adapter to a fake `paseo`. The liveness unit tests use a fake board, recorded `liveness` and `send` verbs, and temporary runner scripts answering `state`. `mmw-v4/tests/dispatch/test_status.py` reads a fixed `paseo ls`/`inspect` snapshot.
- **The hosts' model catalogs.** `mmw-v4/tests/dispatch/catalog.json` and `catalogs/` stand in for each host's catalog through `MMW_HOST_CATALOG`. `test_catalog.py` instead writes fake `claude`, `codex`, and `paseo` executables into a temporary `HOME/.local/bin`; they log calls and answer the control-request or app-server line protocol. Its missing-command case restricts the search folders so it cannot select a machine's real binary. `test_settings_api.py` reuses those host fakes to drive background reads through the real board process, and seeds `MMW_HOME/catalog.json` to test stored catalogs. Its `MMW_HOST_CATALOG` fixture uses `fixture-catalog.json`, separate from that cache.
- **The machine's install targets.** `test_install.py` puts fake `orca` (its setups in a JSON file the test writes), `gh`, `node`, `nmem`, `paseo` and `launchctl` on `PATH`; the case for missing base tools runs `--check` on a `PATH` of only `python3`, `uv`, `git`, the fake `gh`, `/usr/bin` and `/bin`.
- **What runs for real:** git (bare origins and clones made in a temporary directory), processes and the state directory's locks (`statedir.py`'s lock is tested against real processes, a recycled pid among them), `node`, and the headless Chromium (board suite).

## How a test puts the system into a state

- **Pull request CI.** `test_dispatch.sh` writes workflow trigger declarations into its temporary repository. Its fake `gh` opens a PR, returns green, red, missing or delayed checks from `FAKE_GH_PR_CHECKS`, and records workflow dispatches. A workflow dispatch returns a run URL or adds a new run to a list containing an older run. `MMW_PR_CHECKS_GRACE_SECONDS` shortens the wait for missing checks in tests. A persisted fake PR tests a retry after the PR opens but its checks cannot be read. No workflow runs on GitHub.
- **A closed brief batch.** `test_briefs.py` creates batches through `briefs.create`, removes one through `briefs.remove`, and runs the reference-check command against brief files pointing at open, closed and nonexistent batches. `test_dispatch.sh` sends a brief and closes its batch through dispatch, then sends a follow-up that references the deleted answer path. References to an open batch are accepted. References to a closed or nonexistent batch are refused without starting a session.
- **Machine state.** Every suite that touches it points `MMW_HOME` at a temporary directory (`mmw-v4/tests/board/run.sh`, the relay and liveness suites, `test_dispatch.sh`'s `$TMP/mmw-home`, and `test_status.py`'s `Plans.setUp`); none touches `~/.mmw`. `MMW_INSTALL_HOME` is a test seam for `install.sh` and `render.py` only: it moves the whole install target to a throwaway directory and skips `launchctl` and `paseo reload`.
- **Worktree activity and waiting tickets.** `test_liveness.py` commits in a temporary git repository with fixed commit dates and sets file modification times with `os.utime`. Its fake runner answers `state` from a per-session file. `child.opened` and `child.closed` comments create and route children on the fake parent ticket. A delivered JSONL row in the temporary state directory creates an unacked wake, and removing the row acks it. A fake clock advances idle, stuck and nudge thresholds without waiting.
- **A repository.** `mmw-v4/tests/setup-mmw/test_setup.py` commits a fixture `scripts/env` in a temporary git repository. Its `setup`, `up`, and `down` log their calls, `up` prints fixed or worktree-specific resource names, and chosen subcommands can fail. The tests check the reported row, teardown calls, and remaining worktree registrations. `test_dispatch.sh` and `test_preflight.py` commit executable `scripts/env` fixtures that log subcommands, absolute worktree paths and working directories. Their setup and up create readiness files checked by dispatch assertions, merge checks and baseline criteria. Chosen subcommands fail to check preparation refusals and non-blocking teardown. The baseline fixture emits non-UTF-8 bytes from every subcommand so output decoding cannot bypass teardown. `test_lint_drafts.py` runs draft CHECKs against a detached base checkout of a temporary clone with a bare origin. Committed scripts print chosen output and exit codes. The runner-expect tests call static per-ticket lint directly when checking draft wording, without executing those CHECKs. `test_dispatch.sh` makes a bare `origin.git` and a clone under `mktemp -d`, and remakes them for a scenario that needs a fresh pair. Research destination scenarios check out `map-<n>` or `fix-<n>` in that clone to reach an effort branch. They seed evidence alone, then an answer file beside it, to check that another send cannot reuse either saved result. Rejected-runner cases leave the new empty question directory in place and retry into it.
- **The installed checkout.** `test_dispatch.sh` writes a temporary checkout's `mmw-v4/` path to `$MMW_HOME/installed-root`. It invokes dispatch from that checkout and from another git worktree of the same repository, including a path with spaces. The installed checkout is independent of the skill directory running the command.
- **Failed finish cleanup.** `test_dispatch.sh` uses a nonexistent local origin path, a real branch-reference lock on the night or project branch, or a bare-origin update hook that rejects deletion. The project-branch lock covers creation, an unchecked branch update, and a fast-forward in a checked-out worktree. A temporary git wrapper refuses only `git -C <repo> worktree list --porcelain`; its other commands use the real git binary. The retry removes that failure and runs `finish` against the same recorded merge.
- **A missing project worktree.** `test_dispatch.sh` deletes a fixture worktree directory without removing its git registration. It checks that `finish` names the missing path and gives inspection and pruning commands without pruning automatically, then prunes the fixture registration and retries.
- **Issue closing and reopening.** `test_dispatch.sh`'s fake `gh` records issue state changes in `gh-issue-states.json`, separate from the ticket rows. Later `gh issue view --json state --jq .state` reads those changes. A refused close changes nothing. `reset_log` clears the recorded states between scenarios.
- **A ticket's history.** `_load.py`'s `event` writes a comment the way the pipeline's scripts post one, and `checked` writes one `ticket.checked` event; the fake `gh` serves ticket rows from `FAKE_GH_TICKETS_FILE`.
- **Historical ticket text.** The build-point lint replay reads the saved bodies of erp-frontend #65, #66 and #68 from `mmw-v4/tests/verify-ticket/fixtures/`. `erp-frontend-build-points.json` records the last GitHub `userContentEdits` edit before each worker opened its contract child. The tests never fetch that history.
- **An old design directory.** `mmw-v4/tests/setup-mmw/test_setup.py` creates `design/notes/` without a verification skill in its set-up repository fixture. This directory does not prevent `SETUP OK`.
- **Label migration.** `mmw-v4/tests/setup-mmw/test_setup.py` supplies issue pages, parents and comments through its fake `gh`; comment bodies are built with `events.py` and served as paginated REST objects. Label and issue edits update that same fake repository so retries and a second run observe the previous writes.
- **An open night.** Every `test_dispatch.sh` scenario runs with the night on spec 76 open: a stand-in process holds the relay's lock in the run's state directory and records that it watches spec 76. A scenario about opening, acking or refusing clears it first (`no_relay`).
- **A broken landed criterion.** The dispatch scenarios first land a ticket whose criterion names a shell test, then commit a rename of that test on another ticket branch. The plural-bounce fixture lands a second ticket naming the same script. A script move or deletion exercises missing commands, and a harmless test edit and a root-file edit exercise selected and unselected criteria. The selected-criterion timeout test runs the real gate-check engine with a one-second timeout in its temporary test configuration.
- **Checks red on the base.** The dispatch and worker fixtures commit an executable `scripts/check` that reports named steps red on both trees, green only on the base, partly red on the base, or unsupported through `--step`. Worker tests run the real criterion engine and repository check against temporary commits and check that the detached base checkout is removed. Closeout fixtures put a finding before or after the base-red record. The landing fixture supplies a worker's base-red record and checks that landing runs its own merge and base checks. The landed-criterion scenarios commit a root configuration file after a ticket lands. That file makes the landed criterion red before another ticket changes, moves, or deletes its named test script. Both `advance` and `recheck` compare that failure with the base without changing the landed ticket's state. A candidate-only runner marker makes a criterion start and fail on the candidate but fail to start on the base.
- **A broken skill set.** `test_check_wiring.py`, `test_check_host_neutrality.py` and `test_check_interfaces.py` run on a copy of `mmw-v4/skills/` broken one way per case. The host-neutrality fixtures link the read-only upstream tree and copy the checker with a temporary exceptions file to test stale rows. `test_status.py` copies the dispatch and verify-ticket scripts to a temporary skill tree with a missing or corrupt `roles.json`. The `diagram-design` suite edits the skill's shipped example pages one way per case.
- **An Orca recipient.** `test_orca_send.py`'s fake `orca` logs every call to `calls.jsonl`. Its `terminal list` row carries an `agentIdentity`, an empty or absent one; its `terminal wait --for tui-idle` answers satisfied, not satisfied, a timeout, or something unreadable, with the exit code the test sets. Its `terminal read` returns the supplied screen, empty by default. Its `terminal send` answers with prompt stages or an error envelope. Successive sends read a sequence of answers, counted in a file in the test's temporary directory.
- **A host's process tree.** `test_tool_guard.py` copies the running Python executable into a temporary directory as `claude` or `codex`. The named executable starts a child, a grandchild and the real guard, while the test starts a neighbor outside that host's tree. On macOS the fixture copies the executable reported by `ps`, not Python's launcher, which starts another executable. An ancestry-failure case puts a failing `ps` first on `PATH`. The guard reads real process ancestry in every other process-tree case; no test sends a kill signal.
- **Skill usage.** `test_usage.py` writes JSONL records with invocations, file reads, bare mentions, and parent and subagent transcripts into temporary host directories. Session timestamps supply the date-filter boundary.
- **The board's data.** The board suite starts the real `mmw-v4/board/server.py` through `mmw-v4/tests/board/board_process.py`, its fake `gh` answering from the test's fixture; a node test writes a page module's input inside the test.

## Traps

- A suite runs from inside a runner's session as easily as from a terminal. `test_dispatch.sh` and the board suite unset `PASEO_AGENT_ID`, `ORCA_TERMINAL_HANDLE`, `HERDR_PANE_ID` and every `NMEM_*` variable first: a scenario says which session it stands in, and nothing else may answer `self`.
- A skip is a failure. `mmw-v4/tests/lib/run_unittests.py` exits 1 on a skip count other than 0 or a run count of 0, and the suite then withholds `all passed`; the `verify-ticket` suite fails without `node` rather than passing on half its tests.
- The task board loads verify-ticket's `events.py` and `issue_tree.py` and dispatch's `ghlist.py`, `models.py`, `statedir.py` and `roles.json` by file path (`mmw-v4/board/codeversion.py` lists them): a change to one of them is a change to the board.
- The board suite takes the newest Playwright `uv` resolves (no pin, no upper bound: it follows global upgrades) and runs `mmw-v4/tests/lib/ensure_chromium.py` first, which installs the Chromium build that Playwright needs when it is absent and never deletes another build. When Chromium still cannot start, the suite exits 2 before any test runs, and `scripts/check` reports it as `ENV` and ends `CHECK CANNOT RUN` rather than red. A suite's `run.sh` exits 2 for nothing else. With Playwright cached, the board suite runs `uv` offline, on the newest cached release.

## Which suites a change needs

The map from a changed path to the suites it needs is `MAP` in `scripts/check`, its only copy; `scripts/check` with no flag runs the suites it selects for the paths changed against the base.

## Tests written this way on purpose

- No test asserts the wording of a skill's `SKILL.md`, a playbook, a reference, a refusal, or a start prompt's standing sentences. Tests assert exit codes, the strings a program reads (event names and fields, labels, output tokens), the facts a behaviour produces (a number, a path, an issue number, a session id, the data rows of a prompt), and the effect on files, the tracker fake or git; a refusal is checked by its exit code, by what it did not do, and by the fact it names.
- The liveness suite does not prove that a real host calls the turn guard with the payloads it feeds, or honours its answer: that is checked by hand against each host and recorded in `turn-guard.py`'s header (`mmw-v4/tests/liveness/run.sh`).
- `exe-release`'s two PowerShell checks (`check-generated-powershell.sh`, `check-template-behaviour.sh`) are in no suite and no tier of `scripts/check`: they need a Windows build machine, and `scripts/check` names them on its `not run here:` line.
