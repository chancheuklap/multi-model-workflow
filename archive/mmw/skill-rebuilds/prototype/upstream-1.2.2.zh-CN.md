# Prototype

Prototype 是**能够回答一个问题的一次性代码**。问题决定它的形态。

## 选择分支

根据用户的提示、周围的代码，或者在用户在线时直接询问，找出要回答的问题：

- **“这套逻辑或状态模型感觉正确吗？”** → 使用 [LOGIC.md](#logicmd)。构建一个可分享的单一 HTML 文件，其中包含 `free-play` 按钮和使用标签页切换的 `guided walkthrough`；它会让状态机经过难以在纸面上推理的情形，而且非开发者也能操作。
- **“它应该是什么样子？”** → 使用 [UI.md](#uimd)。在单一路由上生成若干个截然不同的界面变体；通过 URL 查询参数和底部悬浮栏切换。

两条分支会产生非常不同的产物；选错分支会浪费整个 prototype。如果问题确实含混，而且无法联系用户，就默认选择与周围代码更匹配的分支，例如后端 module 使用逻辑分支，页面或组件使用 UI 分支；并在 prototype 顶部说明这项假设。

<!-- source: vendor/mattpocock-skills/skills/engineering/prototype/SKILL.md:19-26 -->

## 两条分支共同适用的规则

1. **从第一天起就是一次性的，并明确标记。** 把 prototype 代码放在接近实际使用位置的地方，例如放在所模拟的 module 或页面旁边，使上下文显而易见；但命名必须让普通读者看出它是 prototype，不是生产代码。对于一次性界面路由，遵守项目现有的路由约定；不要自创新的顶层结构。
2. **运行极其简单。** UI prototype 通过项目任务运行器中的一条命令启动，例如 `pnpm <name>`、`python <path>` 或 `bun <path>`。逻辑 demo 是用户双击即可打开的单一 HTML 文件。无论哪一种，启动时都无需思考。
3. **默认不持久化。** 状态保存在内存中。持久化是 prototype 正在**检查**的对象，不应成为 prototype 依赖的对象。如果问题明确涉及数据库，就使用临时数据库，或者使用名称中明确写着 `PROTOTYPE — wipe me` 的本地文件。
4. **跳过润色。** 不写测试；除了让 prototype **能够运行**所需的错误处理，不写其他错误处理；不写抽象。目的是快速学到东西。
5. **呈现状态。** 每次执行逻辑动作后，或者每次切换界面变体时，打印或渲染完整的相关状态，使用户能看到变化。
6. **完成后保存。** 把经过验证的决定吸收到真实代码中；随后把 prototype 本身作为**一手来源**保存：把它提交到 main 之外的一次性分支，并在实施 issue 上留下指向该分支的上下文引用。还要保存答案，也就是结论及它所解决的问题；把答案写进 issue 或 commit。main 分支只保留经过验证的决定。

# Logic Prototype

一个独立、自包含的 HTML 文件，也就是一份**可分享 demo**；任何人都能点击按钮来驱动状态模型。当问题涉及**业务逻辑、状态转移或数据形状**时使用，也就是在纸面上看似合理、经过真实情形后才会感觉不对的内容。

因为它只有一个文件，也无需安装任何内容，你可以把它交给非开发者，例如 designer、PM 或领域专家，让他们亲自感受这套模型。因此，它使用他们的语言，不使用代码语言。

## 适合这种形态的情形

- “我不确定这台状态机能否处理先发生 X、再发生 Y 的边界情况。”
- “这个数据模型真的能让我表示这种情形吗……”
- “我想在编写 API 前先感受一下它应该是什么形态。”
- 任何人想要**按下按钮并观察状态变化**的情形。

如果问题是“它应该是什么样子”，说明选错分支。使用 [UI.md](#uimd)。

<!-- source: vendor/mattpocock-skills/skills/engineering/prototype/LOGIC.md:16-33 -->

## 流程

### 1. 说明问题

编写代码前，写下要模拟的状态模型和问题。用一个段落写在 demo 顶部；必须放在可见的介绍中，不能只写成注释。回答错误问题的逻辑 prototype 完全是浪费。明确写出问题，使它以后可以被检查，无论用户现在正在观看，还是之后才以 AFK 方式回来查看。

### 2. 把逻辑隔离到一个可移植 module 中

把真正的逻辑，也就是回答问题的部分，放进单一 `<script>` 块。把它写成一个小型纯 module，使它以后能够被取出并放进真实代码库。周围的页面是一次性的；这个 module 不是。

正确形态取决于问题：

- **纯 reducer**——`(state, action) => state`。当动作是离散事件，而且状态是单一值时适用。
- **状态机**——明确的状态与转移。当“当前究竟允许哪些动作”也是问题的一部分时适用。
- 在普通数据类型上运行的**一小组纯函数**。没有隐式当前状态、只有数据转换时适用。
- 当逻辑确实拥有持续存在的内部状态时，使用具有清晰方法集合的**类或 module**。

选择最适合当前问题的形态，**不要**选择最容易接到页面上的形态。保持纯粹：不要使用 DOM，不要使用 `document`，按钮处理器也不能伸进 module 内部。页面调用 module；任何内容都不能反向流动。这使 prototype 在自身生命周期结束后仍然有用：问题得到回答后，经过验证的 reducer、状态机或函数集合可以独立移入真实 module。

<!-- source: vendor/mattpocock-skills/skills/engineering/prototype/LOGIC.md:35-50 -->

### 3. 构建可分享的 HTML 文件

只使用一个文件和原生 HTML、CSS、JS；没有框架、打包器或服务器；全部内联，使它能通过双击打开，也能在邮件转发后继续运行。任何人打开文件就能运行。

面向非开发者编写。每个标签都使用**领域语言**，不使用代码语言；按钮和状态都要读起来像业务，不像 reducer。用直白文字解释正在发生什么。

从上到下按照清晰层级布局：

1. **标题和一行说明**，说明这个 demo 允许用户探索什么，也就是第 1 步中的问题。
2. **当前状态**——把完整的相关状态渲染为可读面板，使用带标签的字段，不要原样倾倒 JSON。每次点击后重新渲染，使变化可见。在有助于非开发者理解时，指出刚刚发生了什么变化。
3. **`free-play` 按钮**——每种动作一个按钮，始终可用，使任何人都能以任意顺序探索模型。每次点击都派发对应动作，并重新渲染状态。
4. **`guided walkthrough`**——一组**场景**，每个标签页一个。每个标签页包含对场景的简短直白说明，也就是它建立的情形和需要观察的内容；下方是该场景中应当依次**按下的按钮**。每一步都是一个真实按钮：点击会执行对应动作，并进入下一步。开始走查时重置到已知初始状态，使场景每次都以相同方式运行。

选择能够展示棘手情形的场景，例如正常路径、困难边界情况、尝试执行不应合法的操作；也就是难以在纸面上推理的情形。

保持美观但克制：干净的排版、宽松的间距、一种强调色。不要动画，不要花招；任何内容都不能与状态和按钮争夺注意力。

<!-- source: vendor/mattpocock-skills/skills/engineering/prototype/LOGIC.md:52-58 -->

### 4. 交给用户

把文件发给用户，或者替用户打开。他们可以在方便时完成 `guided walkthrough` 和 `free-play`；有价值的时刻是他们说“等等，这不应该发生”或“原来如此，我原以为 X 会不同”。这些是**想法**中的 bug，这正是 prototype 的意义。如果他们需要新的动作或场景，就加入。Prototype 会持续演进。

### 5. 保存答案和 prototype

Prototype 回答问题后，先保存答案，然后按照 [SKILL](#skillmd) 的说明保存 prototype。逻辑专属映射如下：经过验证的 reducer、状态机或函数集合会移入真实 module，也就是决定被吸收；HTML 外壳则随 prototype 一起进入一次性分支，并在那里作为一手来源保留。由于它是单一自包含文件，在该分支上重新运行仍然极其简单。

<!-- source: vendor/mattpocock-skills/skills/engineering/prototype/LOGIC.md:60-67 -->

## 反模式

- **不要添加测试。** 需要测试的 prototype 已经不再是 prototype。
- **不要连接真实数据库。** 除非问题明确涉及持久化，否则使用内存状态。
- **不要泛化。** 不要考虑“如果以后需要支持 X 怎么办”。Prototype 只回答一个问题。
- **不要把逻辑和页面混在一起。** 如果纯 module 引用了 DOM、`document` 或按钮处理器，它就无法再被移出。让页面成为纯 module 上的一层薄外壳。
- **不要使用框架、打包器或服务器。** 接收者应当双击一个文件；React 应用或开发服务器会破坏“可分享”这一属性。
- **不要把 HTML 外壳发布到生产环境。** 页面为人工点击走查而优化。后面的逻辑 module 才是值得保留的部分。

# UI Prototype

在单一路由上生成**若干个截然不同的界面变体**，并通过底部悬浮栏切换。用户在浏览器中切换变体，选出一个，也可以从每个变体中取走一部分，然后丢弃其余变体。

如果问题涉及逻辑或状态，而不是某项内容的外观，说明选错分支。使用 [LOGIC.md](#logicmd)。

## 适合这种形态的情形

- “这个页面应该是什么样子？”
- “我想在作出决定前先看这个仪表盘的几个选项。”
- “为设置页面尝试一种不同布局。”
- 任何用户原本需要花一天时间在脑中三个含混界面草图之间作选择的情形。

## 两种子形态——强烈优先选择子形态 A

当 UI prototype **紧贴应用的其他部分**时，更容易判断；真实页头、真实侧边栏、真实数据、真实密度。孤立的一次性路由是真空环境：每个变体单独看都没有问题。只要存在一个合理的现有页面可以承载这些变体，默认使用子形态 A。只有 prototype 确实没有邻近归宿时，才使用子形态 B。

<!-- source: vendor/mattpocock-skills/skills/engineering/prototype/UI.md:18-32 -->

### 子形态 A——调整现有页面，首选

路由已经存在。变体在**同一路由**上渲染，并由 `?variant=` URL 查询参数控制。保留现有取数、参数和鉴权；只替换渲染。这是默认方案；除非存在具体理由，否则选择它。

如果 prototype 对应的内容还没有页面，但**自然会位于某个现有页面内**，例如仪表盘的新区块、设置页面的新卡片，或现有流程的新步骤，它仍属于子形态 A。把变体挂载到宿主页面内。

### 子形态 B——新页面，最后手段

只有被模拟的内容确实没有现有页面可以容纳时才使用，例如全新的顶层界面，或无法合理嵌入任何位置的流程。

按照项目现有路由约定创建**一次性路由**；不要自创新的顶层结构。命名必须明显表明这是 prototype，例如在路径或文件名中包含 `prototype`。使用相同的 `?variant=` 模式。

决定采用子形态 B 前，快速检查：真的不存在可以嵌入它的现有页面吗？空路由会隐藏已有内容充实的页面能够暴露的设计问题。

两种子形态使用完全相同的底部悬浮栏。

<!-- source: vendor/mattpocock-skills/skills/engineering/prototype/UI.md:34-54 -->

## 流程

### 1. 说明问题并选择 N

默认使用 **3 个变体**。超过 5 个后，它们不再截然不同，只会形成噪声；上限为 5 个。

在 prototype 所在位置或文件顶部注释中，用一行写下计划：

> “设置页面的三个变体，位于现有 `/settings` 路由上，可通过 `?variant=` 切换。”

无论用户是否在场并提出异议，这项规则都有效。

### 2. 生成截然不同的变体

起草每个变体。每一个都必须符合：

- 页面的用途及其可访问的数据。
- 项目的组件库或样式系统，例如 TailwindCSS、shadcn、MUI、原生 CSS 等。
- 清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须在**结构上不同**，包括不同布局、不同信息层级、不同 primary affordance，不能只有不同颜色。三个只经过轻微调整的卡片网格不算 UI prototype，只算墙纸。如果两个草稿过于相似，使用明确的“不要使用卡片网格”指令重做其中一个。

<!-- source: vendor/mattpocock-skills/skills/engineering/prototype/UI.md:56-75 -->

### 3. 把它们接在一起

在路由上创建一个切换器组件：

```tsx
// 伪代码——适配项目使用的框架
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于子形态 A，也就是现有页面：把所有现有取数逻辑保留在切换器上方；每个变体只改变渲染的子树。

对于子形态 B，也就是新页面：`/prototype/<name>` 下的一次性路由挂载相同的切换器。

<!-- source: vendor/mattpocock-skills/skills/engineering/prototype/UI.md:77-92 -->

### 4. 构建悬浮切换器

在屏幕底部中央放置一个小型固定定位栏，其中包含三个部分：

- **左箭头**——循环切换到上一个变体，到头后回到末尾。
- **变体标签**——显示当前变体键；如果变体导出了名称，也显示该名称，例如 `B — 侧边栏布局`。
- **右箭头**——向前循环切换，到头后回到开头。

行为：

- 点击箭头会更新 URL 查询参数。使用框架的路由器，例如 Next 使用 `router.replace`，React Router 使用 `navigate`，使变体可以分享，并在刷新后保持不变。
- 键盘：`←` 和 `→` 方向键也会切换。当焦点位于 `<input>`、`<textarea>` 或 `[contenteditable]` 时，不要拦截方向键。
- 在视觉上与页面明确区分，例如使用高对比度药丸形和细微阴影，使它明显不属于正在评估的设计。
- 在生产构建中隐藏；通过 `process.env.NODE_ENV !== 'production'` 或等价检查控制，使意外合并的 prototype 不会把该栏发布给用户。

把切换器放在单一共享组件中，使两种子形态都能复用。把它放在项目存放共享界面的位置。

<!-- source: vendor/mattpocock-skills/skills/engineering/prototype/UI.md:94-105 -->

### 5. 交给用户

呈现 URL 和 `?variant=` 的取值。用户可以在方便时切换查看。通常最有价值的反馈是：**“我想要 B 的页头和 C 的侧边栏。”** 这才是用户真正想要的设计。

### 6. 保存答案并清理

一个变体胜出后，保存答案，也就是哪个变体胜出及其原因；然后按照 [SKILL](#skillmd) 的说明保存 prototype。把获胜变体吸收到真实代码中，并把其余内容移到一次性分支，不要放进 main：

- **子形态 A**——把获胜变体吸收到现有页面；从 main 删除落选变体和切换器。
- **子形态 B**——把获胜变体提升为真实路由；从 main 删除一次性路由和切换器。

完整变体集合是一手来源，因此应放在一次性分支，不要丢进垃圾桶。留在 main 分支中的变体组件和切换器会很快腐化，并使下一位读者困惑。

<!-- source: vendor/mattpocock-skills/skills/engineering/prototype/UI.md:107-112 -->

## 反模式

- **只在颜色或文案上不同的变体。** 这只是调整，不是 prototype。真正的变体会在结构上存在分歧。
- **在变体之间共享过多代码。** 共享 `<Header>` 没有问题；共享 `<Layout>` 会违背目的。每个变体都应当能够丢弃现有布局。
- **把变体接到真实写操作上。** 只读 prototype 没有问题。如果变体需要写入，就把它指向桩；问题是“它应该是什么样子”，不是“后端是否运行”。
- **直接把 prototype 提升到生产环境。** 变体代码按照 prototype 约束编写，没有测试，错误处理也很少。把它吸收进去时，要以正确方式重写。
