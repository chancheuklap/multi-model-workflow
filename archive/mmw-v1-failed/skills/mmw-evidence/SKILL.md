**取证不判定**：只提供证据和出处，改法、路线、设计结论不在这一步确定。查不到就说查不到，不要用推测填补。

记录一条事实：一行一句陈述，不是判断也不是建议。出处给 `文件:行号`、链接，或者一条已经执行过的命令连同它的输出；给不出出处的那条不算数。信心填 高 / 中 / 低——亲眼读到写高，靠推断写中，只是看着像写低。没查清的单独记录，连同它阻塞了什么。

**只打开与你这一步对应的那一份。**主线程自己动手的三份在这里：

| 这次做什么 | 读哪一份 |
| --- | --- |
| 查清代码结构、边界、数据流 | [主线程：查代码结构](references/main-structure.md) |
| 确定一个 bug 的根因 | [主线程：查一个 bug 的根因](references/main-bug.md) |
| `scout` 的三节已经交回来 | [主线程：回执收回来之后](references/main-verify.md) |

`scout` 不查这张表——它按提示词第一行的任务名，照自己角色文件里那张表走。

## 线下 · 不是技能内容

**为什么单独一份技能，而不住在某一个阶段里**：探路解一个查证类决策、查清现状答一批题目、`mmw-fix` 定一个根因，用的是同一门手艺。写在其中一处，另外两处要用就得跨文件引用，很快会漂成好几套。

**先按角色劈，再按这一步干什么劈**：主线程和 `scout` 能干的事不一样——造一个会变红的信号要改文件、切版本，`scout` 没有改文件的手，又跟主线程共用一棵工作树（`mmw-dispatch`：只读角色不建树），切版本会砸掉主线程脚下的代码；收回执、向用户开口，`scout` 也做不了。合成一份就得在正文里反复交代「这一段是谁的活」，读的人每段都要先判断管不管自己。两边再各按这次干什么切成三份：主线程来收回执时，不该把造信号那四十行一起装进上下文；`scout` 被派出来查外部来源时，也不该装上查代码结构那六个词。派它出来那一句已经点明了方向，让它进门先读一份三个方向的合集，是拿注意力换整齐。

**重复照留，但只留在开不到的地方**：六个词、三个判据在主线程那一份与 `scout` 那一份里各有一版，因为读其中一份的人永远不会打开另一份。反过来，取证不判定与事实写法只写在这里——主线程进门都装这一份，再抄进三份支撑文件就是纯浪费。

**这一份 `SKILL.md` 做两件事：把取证的两条底线摆出来，再把主线程分到它这次要用的那一份。**它本身要足够短。外面的阶段技能一律点名到具体那一份，这张表是主线程找不准时的兜底。`scout` 走另一条路：它的分流住在自己的角色文件里，那张表按提示词第一行的任务名指到它那三份中的一份。

**回哪儿靠 `phase`，不靠这一份点名**：探路、查清现状、`mmw-fix` 三处都会进来，这一份认不出这次是谁调的；主线程查完一轮，会话里已经堆了几十条工具回执，也未必还记得。`phase` 是盘上现成的锚点，读一下就知道回哪一份。这句话在主线程那三份的末尾各写一遍，因为它们各自都可能是主线程读的最后一份。

**为什么「查外部来源」是 `scout` 的一份，不是给探路单开一份**：查证类决策里查的人是 `scout`，主线程只有怎么派、回执回来怎么办两件事。缺的是 `scout` 出门时没有第一方来源那条判据，它交回二手综述，主线程才在 `main-verify` 里降级或丢弃，白跑一轮。判据下发到采集那一侧，探路的查证决策与查清现状的外部方向同时受益。上游做成独立的 `research` 技能，是因为那边研究票有一次性分支与资产挂载；我们落查证笔记，不需要那一层。

**外面的技能点名到具体那一份，不只点技能名**：分流表按「这次做什么」分，而调用方进门时的状态未必对得上表里的措辞。探路那边曾经写成「怎么查……读 `mmw-evidence`」，主线程带着「怎么查」进门，表里没有一行是它——查的人是 `scout`。表留着给找不准的主线程兜底，调用方直接点名少一跳。

**为什么不给 `scout` 开写权限，好让它也能造信号**：一个 bug 只需要一个信号，派几个人各造一个是白费；`scout` 的结论本来就要主线程逐条亲验，让它改代码得逐行验，比自己写还贵；派发那边还规定每个能写文件的角色单独一棵工作树，并行几个就是几棵树要收拾。

**来源**：上游 `vendor/mattpocock-skills/skills/engineering/diagnosing-bugs`——Phase 1 整节（这一步就是手艺本身、造信号的办法、磨它的三个方向、非确定性 bug 提高复现率的手段、一条已经跑过的命令当完成判据、造不出来时向用户要哪三样），加上它 `scripts/hitl-loop.template.sh` 原样搬进本份 `scripts/`；Phase 3 的可证伪假设与一次提 3 到 5 个。上游十种造法里，浏览器脚本与 property/fuzz 循环没单列——前者并进「搭一次性最小环境」，后者在「时有时无的 bug」那段里。`codebase-design` 的 `SKILL.md`（词汇表、深浅、三个判据）与 `DEEPENING.md` 的依赖四类。旧插件两份 investigate workflow 提示词里的回执要求。上游 `research`（12 行）的第一方来源判据，落进 `scout` 查外部来源那一份。

**上游把 Phase 1 称作「这份技能本身」，这里照搬这个分量**：先造信号、再提假设的先后不能倒过来，没有信号就编假设是它最要防的事。曾经把这一步写成「判断这个 bug 能不能稳定复现」，主动造成了被动判断，理由是「取证只读做不到」——真正不该干这件事的只有 `scout`。也曾经按「只读做不做得到」把这套办法劈成两半、重的那半搬去 `mmw-fix`，结果主线程要跨两份文件才拼得齐一套办法。现在按角色分：主线程那一份整套都有，`scout` 查根因那一份直说这不是你的活。

**没摘的**：`codebase-design` 的深浅示意图与「设计接口时问自己能不能减少方法数」（设计动作）；`DEEPENING.md` 除依赖四类之外的部分——怎么把浅模块合深、接缝纪律、replace-don't-layer 的测试策略（都是重构动作，归 `mmw-design` 与 `mmw-build`）；`DESIGN-IT-TWICE.md` 整份（派几个子代理各设计一版接口再比，是设计动作，归 `mmw-design`）。`diagnosing-bugs` 的 Phase 2 最小化、Phase 4 插桩、Phase 5 修复与回归测试、Phase 6 收尾——都要写盘或反复改，归 `mmw-fix` 与 `mmw-build`。`improve-codebase-architecture` 整份不用：它产出重构建议，撞取证不判定；且它 `disable-model-invocation: true`，子代理调不动。
