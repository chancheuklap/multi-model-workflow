# Design · 取证战役（设计中的大事实缺口时读这一份）

> 用于选供应商、选模型、定并发上限、验证第三方 API 合同、比较开源方案等需要计划、多候选或真实运行的大缺口。几次读码或网搜能坐实的小缺口就地完成，不开战役。
>
> 取证战役回答“事实是什么”；prototype 迭代回答“这套状态、流程或界面是否成立”。两者资产和状态分开，不把测试计划、供应商探测数据塞进 `prototype/`。

## 缺口 → 计划 → 实测 → 台账 → 回填

1. **登记冻结面**：把待坐实假设和它冻结的决定写进设计草稿 Open Decisions。只暂停依赖该事实的分支。
2. **立计划**：写 `docs/design/<slug>/evidence/<日期>-<对象>-test-plan.md`，列对象、口径、通过判据和真实环境需求。
3. **真实测**：探测脚本与原始产物放 `docs/design/<slug>/evidence/runs/<战役名>/`；浏览器验证用已装的 `playwright-cli` skill。涉及凭证、真机或生产环境时，动手前先获用户确认。
4. **记台账**：结论写 `docs/design/<slug>/evidence/<日期>-<主题>.md`，逐条标证据等级（一手实测 > 官方文档 > 二手评论），并指向原始产物。被否决候选也保留否决理由和证据。
5. **回填设计**：正文只写结论和台账路径，不内联长输出；解除对应 Open Decisions 后回原话题继续。

成规模的多候选、多轮实测按对象并行派调查工人，主线程亲验后汇总；量小自己完成。每固化一个结论提交一次。引不出原始产物的结论只能标“待验”。旁路问题用 `mmw spinoff` 登记，不扩大战役。

若取证结果产生了需要用户逐轮走查的状态模型或 UI 候选，回 `prototype-mockup.md`，用 `mmw prototype start` 登记新循环；已有候选文件则按 `mmw where` 给出的 `start --adopt` 接管，不手工混写 prototype 状态。
