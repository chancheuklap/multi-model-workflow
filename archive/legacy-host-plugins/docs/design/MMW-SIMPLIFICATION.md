# MMW 精简改造 · 方案与实施计划

配套图解：Artifact「MMW 精简形态」。本文是权威规格，图解是同一份内容的可视化。

## 一、目标状态

### 为什么改

两个原因，第二个更要紧。

**一是迁移成本。**同一套东西在四个宿主上各实现一遍，适配耗时且容易出错漏。

**二是代理卡在流程正确性上推不动。**不论在哪个宿主，代理都过分看重流程走没走全，停在某一格不往前走。最典型的是在最复杂的那条路径里改一两行代码或几句话，代理也坚持要跑完全量终审才肯往下走。根源是流程写死了：闸绑在阶段上，不绑在改动大小上。

**改造要同时解决这两件事。**只解决第一件，代理照样卡；只解决第二件，四份实现照样各自漂移。

### 形态

一句话：**阶段之间由人敲命令推进，阶段之内代理自己转到收敛。**

三件套是整套的骨架：

| 件 | 是什么 | 谁控制它 |
| --- | --- | --- |
| 技能 | 某一个阶段怎么干的方法论 | 用户敲命令时加载 |
| 命令 | 把代理推进下一个阶段，并加载那一阶段的技能 | 用户敲 |
| 子代理 | 阶段之内完成某一项工作的角色 | 技能或命令派它，不自行发起 |

这样每个阶段的要求与边界清晰，阶段之内保持灵活，不靠脚本捆住代理。

三条支柱：

1. 删掉推进引擎。机器不再计算「下一步是什么」，那个决定权交回用户。
2. 保留全部阶段内收敛循环。它们是 MMW 的价值本体，且天然不跨阶段，不需要引擎驱动。
3. 迁移靠意图清单加共享验收测试，适配实现由该宿主里的 agent 自己写，不靠把同一套代码抄成四份，也不靠一个替所有宿主预判字段的生成器。

| D1 | 阶段推进改成用户敲命令，删除推进算法 | 现在的算法有六种输出、多重守卫，全部为了替用户做一个用户自己能做的决定 |

| D39 | 安装脚本只写自己的文件，不读也不改用户自己的规则文件 | 用户的全局规范是用户的；插件需要什么就自带什么，卸载才干净 |

| D41 | 仓库层只写本仓库事实，通用测试权威一个字都不重述 | 重述既费 token 又会各自漂移；实测某仓库把八行禁止表压成一句名词罗列，禁令还在但为什么禁和替代做法全没了 |
| D42 | 角色登记七条，条数由模型或权限是否不同决定，不由职责数量决定 | 现状十二到十三条，多出来的是把「这次审什么」当成了角色；那句话派发时说一遍即可 |

| D44 | 顾问只能由主线程调用 | 子代理调顾问会出现嵌套派发，责任链断掉 |
| D45 | 技能按「一件事一份」拆开；一条命令指向且只指向一份自足技能，读完直接干，不再跳转 | 现状是主线程要读编排技能再跳场景文件再跳阶段方法论，而阶段契约表在四个场景文件里各抄一份 |
| D46 | 引用任何技能一律用名字，不用路径；插件内部技能之间也是 | 各宿主把技能装在不同位置，路径必然失效；名字是唯一跨宿主稳定的标识 |
| D47 | 点名的外部技能不在时不卡住：照本阶段自己的方法做，并在回执里说明它不在 | 外部技能缺失是环境问题，不该让流程停下来 |
| D48 | 钩子只留出站发布拦截一条，且是选配 | 记提交的接收方已删（进度改从 git 推导），开场分诊由用户敲的第一条命令代劳 |
| D49 | 原型方法论自写，不调外部原型技能，只吸收其中可用部分 | 外部那份要求原型提交到一次性分支、不进主分支，与本流程「原型是设计的证据、随设计提交」直接冲突 |
| D50 | 场景预设取消。只有一条主干九格，敲命令任意跳格 | 「选了完整开发这条路的规矩就全套适用」正是两行改动也要跑全量终审的根源 |
| D51 | 取消场景不为此新造方法论技能：修缺陷吸纳外部那份的纪律，改一点小东西直接用测试驱动循环技能 | 外部修缺陷技能 134 行六阶段，比自写的粗方法论好；流程侧的事本来就与走哪几步无关 |
| D52 | 外部技能有与本流程冲突的条款就吸纳重写，不引用；无冲突的继续按名字引用 | 引用一份带冲突条款的技能会让代理在两套规矩之间困惑，代价高于重写 |
| D53 | 状态目录四家共用同一个名字，位置在任务工作树内部，加进仓库忽略清单 | 换宿主接着做同一个任务；任务结束工作树一删状态自动消失 |
| D54 | 断点续传不靠会话记忆，靠盘上三样：状态文件、阶段产物本身、提交流水 | 设计与原型可能跑几周到一个月，一句现场注记接不上 |
| D55 | 并行派多个子代理不做任何专门设计，就是把派发接口的第一步连着调 N 次 | 参考实现有原生编排工具、另三家用五百行脚本，但两边干的是同一件事；派发接口本来就返回编号，连派天然成立 |
| D56 | 旁路发现本地随手记，收尾一次性开成远端 issue | 每发现一条就外发一次太碎，且落地阶段发现的东西常在后面几轮自己消解 |
| D57 | 阶段产物的目录形状写成约定，尤其是原型 | 长周期阶段的产物是断点续传的主要依据，散了就接不上 |
| D58 | 所有命令统一以 `mmw` 开头；不跑引擎子命令的那条不做壳，直接用技能名当命令 | 通用词做命令名在用户几十条命令里搜不到也容易撞名；而只写一句「去读某技能」的壳是纯冗余 |

D29 的判据：一个机制若满足下列任一条，即判为过度设计并删除。

- 它守的事实在提交流水、审查记录、状态文件或阶段产物里本来就有。
- 它的输入在方法论里没有任何一步指示谁去生成，实际长期走空分支。
- 它的注释或文档已承认防不住它要防的东西。
- 它是为少于十个字段的数据建立的投影层、缓存层或传输合同。

## 四、核心机制规格

### 4.1 阶段与推进

阶段是一组可跳的格子，不是固定序列。主干顺序：探路（可选）、查清现状、给方案、做设计、切片、写计划、落地、出包、收尾。

`/next` 只做四件事，全程无判断：

1. 读状态文件取当前格
2. 目标格 = 参数指定的格，未指定则主干下一格
3. 写回状态文件
4. 打印目标阶段的技能路径与本任务的约定路径

唯一拒绝点：当前在设计阶段时拒绝，提示敲 `/approve-design`。

`/back` 同理，方向相反，不校验。

### 4.2 状态文件

| 字段 | 用途 |
| --- | --- |
| 任务名 | 贯穿工作树、分支、文档目录 |
| 当前格 | 断点恢复 |
| 起点提交 | 推导落地范围 |
| 现场注记 | 一句话，跨会话接现场；无人值守时代理替用户推进的决定与理由也追加在这里，不另设字段 |
| 设计已过门 | 一个标记加过门时间与所认可的文档清单 |

五个字段。不存阶段序列（主干固定）、不存产出路径（约定推导）、不存返工与掉头计数（无接收方）、不存任何指纹或哈希（4.6、4.7）、不存审查基准（在审查记录里，4.3）、不存执行步账（从盘上工作区与提交推导，D11）。

**位置：任务工作树内部，四家共用同一个目录名，加进仓库的忽略清单。**由此推出四件事：

- 开任务的顺序固定为先建工作树再写状态——状态没有地方存之前不能开任务。
- 主仓库里不需要任何在飞任务索引，`git worktree list` 即是答案（原「列全队在管工作区」的命令因此更没有存在理由，X10）。
- 任务结束、合并回主分支、删掉工作树，状态随之消失。这是对的：任务结束了状态就该消失。
- 同一个任务可以换宿主接着做——同一个工作树、同一份状态，哪个宿主打开都读得到。这是共用目录名的全部意义。

**往仓库忽略清单加一行，是本插件唯一一处往用户仓库写内容的地方。**用 git 的本机忽略机制可以避开，但那份配置只在本机、换台机器就没了，且合并回主分支后他人仍会误提交。这个例外写明在此。

**同目录下的第二份文件：旁路清单**

干活途中撞到本次范围外的问题，记在这里，不改主流程。

| 时点 | 动作 |
| --- | --- |
| 工人交活、主线程审这一份时 | 把工人报的范围外发现记一行：一句话、在哪个文件、谁报的 |
| 收尾 | 把清单摊给用户，由他挑哪些开成远端 issue，一次性开完 |

不每发现一条就开一条 issue：往远端写是出站动作，逐条弹确认太碎；且落地阶段发现的东西常在后面几轮自己消解，攒到收尾再看，剩下的才是真该留给下次的。开 issue 走出站红线那道确认（4.7）。

清单随工作树一起删掉。该开的已经开成 issue，本地这份没有留存价值——这与状态文件同理。

### 4.3 审查循环

一套循环体，四个调用点，两个参数。循环体：起审 → 收回发现 → 主线程逐条亲验取舍 → 改 → 只重审改动部分 → 收敛。

| 调用点 | 审什么 | 谁来审 | 命令 |
| --- | --- | --- | --- |
| 设计写完 | 设计文档 | 第二模型，两路视角 | `/mmw-review` |
| 计划写完 | 计划文档 | 与写者不同的模型，两路视角 | `/mmw-review` |
| 一个工人交活 | 该工人的改动 | 主线程自己 | `/mmw-review 这份` |
| 全部落地 | 全量改动 | 第二模型，两路视角 | `/mmw-review 全量` |

不变量是**写者与审者不能是同一个**，不是「审者必须是第二模型」。计划由第二模型写，所以那道审的审者是主线程这一族；代码由工人写，所以主线程审即满足不变量。

**四个调用点都在一个任务内部。**几个分支一起合回主分支是任务之外的一件事，走 4.12 的合并技能；那里也会起一道审，由合并技能驱动。

**全量审读全部改动，不因主线程已自审而略读。**它的两路视角是：一路对着设计与计划逐条核，一路不看计划、以全新眼光读全部改动。第二路的价值就在于不受任何在先判断影响，任何形式的略读都会抹掉它。主线程自审的记录只用于给第一路省力，不给第二路设边界。

主线程自审因此定位为「工人交活当场发现问题比攒到最后便宜」，不承担减少终审工作量的作用。

**「这份」的指向**：等于最近一个交活的工人。多个工人同时交活时逐个审，不引入第三种变量。

**增量审的基准**：审查记录里写一句「本轮审到哪个提交」。下次起审时代理读记录加提交流水，自行判定增量范围。不算哈希、不存文件清单——历史被改写导致对不上时代理会发现，退回全量审并告知用户即可。

停止规则：无新的高置信承重发现即收敛；主线程读两轮审查记录判定同一批发现连转两轮，或满三轮，停下写卡点等用户。

### 4.4 命令与变量

| 命令 | 作用 |
| --- | --- |
| `/mmw <需求>` | 开任务：起名、准备工作区、进去 |
| `/mmw`（不带参数） | 报现状：现在在哪一格、盘上产物说到哪、上次为什么停（4.9） |
| `/mmw-next [阶段]` | 往下走，不填走下一格 |
| `/mmw-back [阶段]` | 回上游，不填回上一格 |
| `/mmw-review [范围]` | 起一道审，不填按当前阶段取默认范围 |
| `/mmw-approve-design` | 设计过门，唯一硬人闸，代理无权代敲 |
| `/mmw-done` | 合并回主分支、把旁路清单摊给用户挑哪些开成 issue、清工作区、收尾 |

变量只有两种：阶段名（就是主干九格的名字）、审查范围（「这份」/「全量」，仅落地阶段需要填）。

**上面说的是用户敲进来的参数。技能与命令自己的定义面另有一组字段，同样要配，不能只写名字与描述。**至少这四类：

| 配什么 | 为什么必须显式配 |
| --- | --- |
| 谁能调用 | 只由用户敲的技能要关掉代理自动调用。描述常驻上下文，一份纯手敲的技能白占一份常驻开销 |
| 描述怎么写 | 代理能自动调用的，描述只写触发条件；关掉自动调用的，描述写给人看 |
| 工具白名单 | 只读角色的技能不给写工具 |
| 模型与思考档 | 承重的那几份钉死，不跟随会话当前设置漂移 |

**各宿主的字段名不同，这是适配区的事**（6.3、6.8）；核心区只声明每一份技能属于哪一类、要什么权限。

**写之前先读该宿主已装好的技能怎么写。**宿主自带与用户已装的技能就是现成样本，字段用法看一眼即知，不要凭想象填。

**全部以 `mmw` 开头**（D58）。`next` `back` `done` `review` 这些词太通用，混在用户几十条命令里既搜不到也容易与别的插件撞名；统一前缀后敲 `mmw` 就能把整套列出来。

**审查那条不做命令壳。**它不跑任何引擎子命令，壳里除了「去读技能 mmw-review」没有别的内容。宿主允许直接敲技能名调用技能，那层壳就是纯冗余。这是 D45「一条命令指向且只指向一份自足技能」的极限形态：命令即技能。

### 4.5 无人值守

同一条命令，代理有权调用，每次替用户推进都把决定与理由追加进现场注记，不另设字段。三处无权代敲：设计过门、缺用户才能给的输入、往远端推送。

退出不另设机制：用户打断即停，这是宿主自带行为。不引入边界字段、不做到界判定。

### 4.6 收敛循环与停止规则

打转守卫从推进引擎移到各循环自身。每个循环自带停止规则，触发即停并写卡点。

| 循环 | 停止规则 |
| --- | --- |
| 解雾 | 决策清单清空 |
| 原型 | 用户认可 |
| 审查返工 | 无新承重发现 / 同一批发现连转两轮 / 满三轮 |
| 打包自愈 | 出包成功 / 修复轮次用尽 |

「同一批发现」由主线程读两轮审查记录直接判断，不做签名比对。每轮审查记录都在盘上，主线程手里有两轮全文，判「是不是上一轮那批问题又回来了」是它做得了的判断。判定结果写进本轮审查记录一句话。

不引入缺陷签名算法。原实现从审查记录行里抠严重度、文件名与前两个英文单词拼签名，在中文审查记录下会退化成「严重度加文件名」，把同一文件里两个不同缺陷判成重复，反而误停健康迭代。

### 4.7 机器硬检查（只剩一道）

**出站发布**：推送到远端前弹权限框，由用户亲批。该拦截靠钩子；钩子是选配（D15），宿主没有钩子面时退回该宿主自身的推送权限机制。

设计文档过门后是否被改动，不做机器比对：改动会在 git 历史里留下提交，代理开场读提交流水即可看见并告知用户。`/approve-design` 只记「已过门」这个事实与所认可的文档清单，不算哈希。

### 4.8 测试规则的归属

**通用权威在插件，本仓库事实在仓库根，两边不重复一个字。**

| 层 | 放哪 | 写什么 |
| --- | --- | --- |
| 通用测试权威 | 插件技能内，随插件走，任何仓库生效 | 测试名怎么起、断言对象是什么、mock 边界、每行为在权威层测一次、数据构造方式、退役与 skip、禁止形态清单（含为什么禁与替代做法）、准入问题 |
| 本仓库事实 | 目标仓库根 `TESTING.md` | 目录分层、哪些边界算外部可 mock、权威源指针、套件门控与入口 |

**固定路径，不再是「任意位置」。**现行插件写的是「可以指向任意位置的仓库测试治理文档，不得按固定文件名推断」——这句话是散掉的根源。实测的经过是：目标仓库先把根 `TESTING.md` 挪进测试目录（动机是进那个目录才自动加载、不必每会话固定加载），插件两周后跟着放宽了路径约束。

**配套设计：这份文件放根目录，但不被目标仓库的项目指令链自动引用。**由插件在需要写测试的时点提醒代理去读。这样既固定了位置，又不付每会话的常驻成本，同时满足了当初把它挪走的那个动机。与检索工具那套「常驻压到最小、要用时才展开」是同一个思路。

三个读取时点：

| 谁 | 什么时候 |
| --- | --- |
| 计划撰写者 | 写测试规划前 |
| 写码工人 | 写测试前 |
| 终审者 | 核测试质量时 |

**仓库没有这份文件时**，结论不是「这个仓库没有测试规则」，而是「只有插件这份通用权威，缺本仓库事实」，并在收工回执里标出来。这个语义原来就有，保留。

**通用权威补一条**：测试名不使用流程编号（计划号、切片号、迭代号、修复号）。这些编号是本编排流程自己产生的，任何用它的仓库都会碰到工人拿计划编号当测试名；现行第一条只堵了「复述函数名」，没堵住这个。

**核对结论**：插件现有的通用权威与目标仓库那份退场前的根文档逐条比对，写作规范 8 条全在、另多 3 条，禁止形态 8 行一一对应无缺失，准入问题在——**没有被改坏，是超集**。改动史印证：共用片段自建立起未改，方法论文件从 8 行增至 36 行，只增不减。

**连带的仓库侧动作**（不属本仓库，单独做）：目标仓库把测试治理文档移回仓库根目录并改名为 `TESTING.md`；它里面与插件通用权威重复的那几条**直接删掉，不再重述一遍**，只留本仓库自己的事实。

### 4.9 断点续传

设计与原型阶段可能跑几天到一个月。跨会话恢复靠状态文件就够，**跨月恢复靠一句现场注记接不上**——那时用户自己也不记得讨论到哪了。

**恢复只读盘上三样，不依赖任何会话记忆：**

| 来源 | 回答什么 |
| --- | --- |
| 状态文件 | 在哪一格、从哪个提交开始改的、设计过没过门 |
| 阶段产物本身 | 讨论到哪了、原型当前是第几版、用户上一轮说了什么 |
| 提交流水 | 实际做了什么 |

现场注记只补一句「上次为什么停在这」，不承担记录进度的职责。

**入口**：`/mmw` 不带参数即报现状，不新增命令。它把上表三样合起来报一遍。

**长周期阶段的产物必须自解释**，这是断点续传成立的前提，不是可选的文档习惯：

- 设计文档里有一块「待拍板」，讨论到哪写到哪。用户每提一个新顾虑、每拍一次板，当场更新。
- 原型目录里有一份逐轮账本，每轮写清这轮要验的问题、用户看了之后说了什么、据此改了什么、验证结果与结论。目录形状见 5.3。

这两样现行插件都有，但没被当作断点续传的组成部分登记，精简时容易被顺手删掉。

### 4.10 技能拆分与渐进式加载

**一条命令指向且只指向一份技能，那份技能自足，读完直接开干。**这正是本方案最初的构想：命令推动代理进入下一阶段并调用相应技能。

现状的毛病很具体：主线程先读编排技能，再跳到场景文件，再跳到阶段方法论，中间还要回头看阶段契约表——而那张契约表在四个场景文件里各抄了一份。

**「自足」指的是不必跳到别的技能去补方法，不是把所有材料塞进一个文件。**这两件事必须同时成立：

- **一份技能只讲一件事。**代理干这件事的时候只读这一份，不在文档之间来回跳。
- **一份技能里不要求代理做很多件事。**需要多插一份技能就多插一份，不搞大杂烩。

**主文件之外用附属文件承载分支材料。**判据是分支：每一条分支都要的内容留在主文件，只有部分分支会走到的内容推进附属文件，主文件里留一句话说明什么时候去读它。

**附属文件放在这份技能目录下的 `references/` 子目录里**，主文件用 `references/<文件名>.md` 指过去。这是旧插件已经在用的形状，照用。主文件开头写一句「本文件是总纲，某某在 `references/`，到那一步再读」。

技能之间的引用一律用名字不用路径（D46）；技能内部指自己的附属文件用相对路径——它们是同一份技能的一部分，跟着技能一起装，路径不会失效。

审查技能是最典型的例子：设计审、计划审、终审、多路合并审是四条分支，一个审者只走其中一条。四份材料焊进一个主文件，等于每个审者都被迫读完另外三路。旧插件的做法是对的——主文件四十行讲共同纪律，四条分支各一份附属文件。

**主文件控制在一百行以内。**超出就说明分支材料没推下去，或者这一份在讲不止一件事。

技能拆成二十二份，按「谁在什么时候读」组织：

| 谁在什么时候读 | 份数 | 具体 |
| --- | --- | --- |
| 主线程按阶段读 | 11 | 开任务、探路、查清现状、给方案、做设计、做原型给用户看、切片、写计划、落地、出包、收尾 |
| 主线程按动作读 | 2 | 起一道审查（四个调用点共用，范围作参数）、几个分支一起合回主分支（4.12） |
| 子代理被派发时读 | 3 | 写码工人怎么干、计划撰写者怎么干、审者怎么干 |
| 三方共读 | 1 | 测试权威（工人写测试前、计划撰写者做测试规划前、审者核测试时） |
| 按需读 | 5 | 诊断缺陷、符号检索、结构检索、外部文档检索、迁移指南 |

现状是 5 份技能带 33 个文档。份数看着相近，性质完全不同：现状那 33 个是一个大技能下面的碎片，靠路径互相跳；新形态的 22 份每一份都是入口。

**诊断缺陷为什么归在「按需读」而不是某一格**：它的六个阶段跨越查清现状与落地两格——先造一个能稳定复现的检查回路、复现并把场景缩到最小、一次生成三到五个可证伪的假设、打点验证、先写回归测试再改、清理与复盘。拆开塞进两格会破坏它的核心纪律（没有红回路之前不许跳到假设）。主线程遇到缺陷时整份加载，跨格使用。

**「做原型给用户看」从设计里拆出来**，因为它的方法与写设计文档完全不同：一个是把结构想清楚，一个是做一版让用户看了能说「不对，应该这样」。合在一起就是大杂烩。产物目录约定（5.3）写进这一份，不另开技能。

场景预设已取消，开任务那一份因此很薄：起名、建工作树、进去、写状态，没有分类也没有入口证据。

**引用技能一律用名字**

- 只写技能名字，让代理按名字去调。各宿主把技能装在哪里是各宿主的事，语料不关心。
- 插件内部技能之间也用名字。现状是用相对路径互相引用（例如工人技能里写「读上级目录里的测试规则文档」），既是跳转又是路径依赖，两个毛病一起犯。
- 点名的技能不在时不卡住：照本阶段自己的方法做，并在收工回执里说明它不在。

**引用还是吸纳，判据是有没有冲突条款**（D52）：

- **无冲突的按名字引用。**技能名要写准确的那个名字，不写「代码库设计类技能」这种描述——代理按名字调，描述调不出东西来。八份：

  | 技能名 | 在哪一格用 |
  | --- | --- |
  | `tdd` | 落地：测试驱动循环 |
  | `codebase-design` | 做设计：代码库层面的结构设计 |
  | `domain-modeling` | 做设计：第一次和用户谈之前先对齐领域 |
  | `improve-codebase-architecture` | 做设计、查清现状：架构改进 |
  | `to-tickets` | 切片：切工单 |
  | `triage` | 做设计：外部反馈进来时先分诊 |
  | `grilling` | 给方案、做设计：追问把想法逼实 |
  | `playwright-cli` | 做原型、落地：浏览器操作与界面验证 |

  `playwright-cli` 自带的规则文件放在哪、要不要存在，本次不处理，维持现状。

- **有冲突的吸纳重写，不引用**。引用一份带冲突条款的技能，会让代理在两套规矩之间困惑，代价高于重写。目前两份：
  - `prototype`——它要求原型进一次性分支不入主分支，与本流程「原型是设计的证据、随设计提交」冲突。
  - `diagnosing-bugs`——它让代理去读一个固定文件名的上下文文档，与本流程「按目标仓库的项目指令链读」冲突。

吸纳时把对方的手艺完整搬过来，只改冲突那一条，并在本份技能里说明改了哪一条。

**场景预设取消后不新造技能**（D50、D51）：修缺陷用上面吸纳的那一份；改一点小东西直接用测试驱动循环技能。流程侧的事——建工作树、跳到哪一格、审多大范围、怎么收尾——本来就在主干技能里，与走哪几步无关。

**原型那份自写，不调外部原型技能。**外部那份的手艺部分值得吸收：先判断在回答哪个问题——「这个逻辑对不对」就做个能跑的小程序把状态机推过那些纸上想不清的情况，「这东西该长什么样」就做几个差异很大的界面变体让用户切着对比；判错这个问题整个原型就白做。另加五条：一次性代码明确标出来别让人误当生产代码、一条命令能跑起来、默认不落数据库、不做打磨（不写测试不做抽象，错误处理只做到能跑）、每一步把状态显示出来让用户看见变了什么。

**不采纳它的资产存放**：外部那份要求原型提交到一次性分支、不进主分支、在实现工单上留指针。本流程按自己的来——原型放设计目录下随设计提交，因为设计文档要长期保存，原型是这份设计的证据，证据与设计放在一起才找得到；外部那条的前提是没有设计文档这个载体。

现状那份原型方法论 108 行里绝大部分是状态机（三种状态、轮次编号、接管旧产物），而状态机已在待删清单（X3）。删掉之后剩十几行：资产放设计目录下、一个循环只验一个能判真假的问题、用户认可后把结论回灌设计文档。

**点名外部技能时若有冲突条款，在本份技能里明写哪一条不采纳。**这个模式适用于日后碰到的所有外部技能。

### 4.11 钩子

**只剩一条，且是选配。**

| 钩子 | 处置 | 理由 |
| --- | --- | --- |
| 拦出站发布 | 留 | 推送到远端前弹权限框由用户亲批。这是唯一一件必须在代理动手前拦住的事 |
| 记提交进度 | 删 | 落地进度已改成从 git 推导——工作区在不在就是派没派，有没有提交就是干没干（D11） |
| 会话开场分诊 | 删 | 开场回报由用户敲的第一条命令代劳，那条命令本来就要报现在在哪一格、上次做到哪 |

**钩子的唯一价值是在代理想做某件事之前拦住它。**除出站发布外，其余事情代理都可以在方法论里自己做，不需要机器在旁边盯着。

必须是选配：有的宿主没有钩子这个面，那就退回该宿主自身的推送权限机制，流程照跑。

### 4.12 几个分支一起合回主分支

**独立入口，不走九格主干，不开任务工作树，主线程在主仓库做。**原插件把它单列为一个场景，这个判断保留；本次只把入口从场景预设改成一份技能，用户按名字发起。

触发条件是：同一个项目上跑了几个任务，各自的分支都过了终审，现在要一起合回主分支。

**它与审查循环的四个调用点不同**：那四处审的是一个任务内部的产物；这里审的是几个分支之间的交互。每个分支自己都对，合起来可能语义打架——同一条业务流被从不同环节改、领域假设不一致、迁移顺序错、一个分支依赖了另一个分支改掉的行为。git 能干净合上不代表设计不冲突。

六步：建合并说明（本次唯一权威源，落状态目录）→ 七个维度扫冲突 → 冲突分三级路由 → 根因不明的先查清 → 按序逐个合并、每合一个就验 → 全合完起一道集成审。

集成审复用审查循环那一套循环体，范围填「多路合并」，**不信各分支自己的终审结论**，独立验组合行为。修复软上限一轮，不收敛就停下交用户。

**只合已过终审的分支**，没跑完的先别合。合并序拿不准、或者两个分支的目标本身矛盾，停下来交用户拍方向。

一个任务内部多份计划合回任务分支不走这一份：那些计划同时落完，紧接着的全量审读的就是合并后的全部改动。

### 4.13 插件里所有文档的写法

技能、命令、角色登记这些都是**写给代理执行的指令**，不是写给人读的说明文。按高密度电报体写。

| 要求 | 说明 |
| --- | --- |
| 只写指令 | 写做什么、怎么做、什么时候停。不写为什么这样设计、不写这一步的价值 |
| 一个东西一个词 | 同一个概念从头到尾一个叫法，不换近义词 |
| 一句话一件事 | 讲操作的句子控制在二十个词以内 |
| 主动语态 | 写「打开开关」，不写「开关必须被打开」 |
| 一段一个主题 | 不把两件事塞进一段 |

**禁止的写法**：「不是 A，也不是 B，而是 C」这类句式；口号式小结；为强调而加的粗体；举例说明设计意图；复述上一段已经讲过的话。

**判据**：逐句问「删掉这句，代理的行为会变吗」。不变就删整句，不要改写。

**长度不是靠压缩句子达成的，是靠删内容。**该给代理的信息一条都不能少；不影响它行为的话一句都不留。

## 五、工作树规格

### 5.1 为什么存在

**第一层，任务级并行。** 一个任务一个工作树，多个任务同时推进、互不干扰。跨会话续跑是副产品，不是目的。

**第二层，落地级并行。** 互不依赖的计划各开一个子工作树，多个写码工人同时干，各自提交到各自分支，最后合并回任务分支。

两层都建立在 git 的多检出能力上。建、删、开子沙箱四个宿主用完全相同的 git 命令，**工作树本身零适配**。

### 5.2 硬要求：子代理必须真正进入它的工作树

不是「把路径写进提示词就行」。子代理不真正进入工作树，长时间工作下必然发生下列漂移：

| 漂移 | 后果 |
| --- | --- |
| 相对路径写操作 | 文件落进主仓库而不是它的工作树 |
| 跑测试与构建 | 读到的是主分支的代码，绿了也不算数 |
| `git commit` | 提交落到当前分支，污染主分支 |
| 多工人并行 | 几个工人在同一个目录上互相覆盖 |
| 边界检查 | 只改源码禁碰文档的检查是对该工作树的差异做的，工人在别处改就检查不到 |

**迁移到新宿主时，必须在该宿主里找到让子代理的工作目录钉在指定路径的办法。**这是迁移工作的必做项，不是可选项。若该宿主确实没有这个能力，则必须补一道派发后校验：核对该工人的提交确实落在指定工作树的分支上，不符即打回，且校验失败必须非零退出。仅靠提示词要求不算数——提示词正是长时间工作中最先失效的东西。

### 5.3 产物目录约定

产出登记已删除，路径改为约定推导（D10），所以约定本身必须写死。四类产物随分支提交，过程产物不永久存档、随工作树消失。

| 产物 | 位置 |
| --- | --- |
| 设计文件夹 | `docs/design/<任务名>/`，主文档与文件夹同名 |
| 切片 | `docs/issues/` |
| 计划 | `docs/plans/` |
| 领域背景 | `docs/context/`（项目级资产，不随任务删） |
| 审查留痕、终审报告 | 过程产物，不提交 |

**原型目录的形状要写死**（D57），因为它是长周期阶段的主要产出，也是隔一个月回来接上的主要依据。

| 位置 | 放什么 | 不担什么 |
| --- | --- | --- |
| `prototype/OVERVIEW.md` | 当前结构、每个子目录担什么、怎么复跑 | 不讲业务理由（那在设计文档里） |
| `prototype/README.md` | 逐轮账本：这轮验什么、用户说了什么、改了什么、验证结果、结论 | 不是方案正文 |
| `prototype/<子系统>/` | 现役链路，一个子系统一个目录 | |
| `prototype/runs/<轮次>/` | 每轮的验证证据 | 不作为当前方案入口 |
| `prototype/archive/` | 被取代的东西，按原分区保持结构 | 不是事实来源 |

三条硬规矩：

- 外层只放现役链路，被取代的立刻挪进归档。
- 现役代码不从归档里取任何东西。
- 每轮证据落到轮次目录，正文只引用不内联。

那份逐轮账本就是 4.9 说的原型逐轮记录。现行实现由原型状态机维护，正文里埋着会话、轮次、载荷三种哈希锚点；状态机在待删清单（X3），**账本内容全部保留，锚点与哈希全删，改成人写的 markdown**。

## 六、迁移架构

### 6.1 三层划分

| 层 | 谁负责 | 是否共享 |
| --- | --- | --- |
| 意图清单（角色要什么能力、命令什么语义、状态什么形状） | 本仓库定义 | 共享，各宿主一字不改 |
| 适配实现（怎么把意图落成该宿主认的定义面与派发方式） | 该宿主里的 agent 自己写 | 不共享，各写各的 |
| 验收测试（适配有没有达成意图） | 本仓库定义 | 共享，各宿主一字不改 |

写适配的人不得同时判定适配是否通过。理由见 6.6。

### 6.2 仓库形状

**插件只由五种东西组成**（D37）：技能、命令、子代理、MCP、钩子。落不进这五类的不做——这既是简化的判据，也是日后新增功能的准入门槛。四家对插件机制的支持程度差别很大，但这五类各家都认。

**核心区 · 零空白 · 四家共用一字不改**

| 类别 | 内容 |
| --- | --- |
| 技能 | 方法论语料（不含任何宿主名、宿主专属工具名、宿主状态目录名）、出包发布整块（6.11）、三份检索工具技能（6.10） |
| 命令 | 六个命令的语义规格 |
| 子代理 | 角色意图清单（写意图不写字段） |
| MCP | 三条检索工具接入配置与那份收窄代理（6.10） |
| 钩子 | 出站红线一条，选配 |

另有两样不属于这五类，但它们是被上面五类调用的实现，随插件本体走：状态文件规格与推进脚本（纯 bash 加 git，本身不触碰宿主）、共享验收测试。

**适配区 · 全空白 · 每宿主一个目录**

目录里只放产出合同，不放实现步骤。Claude Code 那一份作为参考实现，作用是对照「一份完整的适配交出来长什么样」，不是拿来抄。

**只统一资产，不统一装法**（D38）。宿主原生插件机制能覆盖多少就用多少，覆盖不到的由安装脚本补；有的宿主必须把整套拆开复制到用户级目录才生效，那就复制，这不是缺陷。验收不看用了什么机制，只看三条：装完之后用户根目录下没有任何需要手工维护的本项目文件；脚本可重复跑，改完仓库重装一次即同步；脚本能卸载干净。

**安装脚本只写自己的文件**（D39），不读也不改用户自己的规则文件。插件需要什么纪律就自带一份，作用域限在插件内，别处不留第二份。

宿主确实没有对应面的（实机已知一处：某宿主的顾问能力是用户级扩展，模型与思考档配在扩展自己的配置里，插件无处声明），写进能力声明的降级一档，并由安装脚本在结束时打印一份「需要手工做一次」的清单，逐条给出做法与验证方式。不假装能自动化，但要保证这类事一次性、有清单、装完能核对。

### 6.3 适配区产出合同

每个宿主的适配必须交出五样，缺一不可：

| # | 产出 | 验收 |
| --- | --- | --- |
| A1 | 安装脚本：把核心区语料与自己生成的定义面装到该宿主认的位置；卸载写在同一个脚本里，与安装共用同一份路径列表 | 装完宿主能加载，技能与命令可见；卸载后用户目录零残留。不另建「装了哪些文件」的清单——写清单的和装文件的是同一段代码 |
| A2 | 能力声明：对意图清单每一条表态——支持 / 降级 / 不支持 | 覆盖检查，缺项即失败 |
| A3 | 派发与收回两个函数的实现 | 冒烟派发通过 |
| A4 | 跑通共享验收测试 | 全绿 |
| A5 | 检索工具接入：把收窄代理按本宿主的 MCP 格式注册，装好三份技能 | 三个工具各实测可调用，缺一即失败（6.10） |

模型与思考档不在这五样里，它们改由用户装完确认一次，理由与代价见 6.6。

### 6.4 角色意图清单规格

清单描述角色需要什么能力，不描述用什么字段表达。五个维度，不多不少：

```
角色：设计审者 · 内容
  只读        必须
  本地检索    必须（含结构化检索，宿主有就用，没有退普通检索）
  外部检索    必须
  模型选取    本宿主可用模型中推理最强的一档；与设计撰写者不同族，无第二族时降级并声明
  思考投入    该模型可设的较高档
```

不设「可并行」维度——并行是派发时的决定，不是角色属性。不设「轮次上限」维度——轮次归各收敛循环的停止规则管（4.6）。

**模型与思考档写相对要求，不写绝对档次。**各宿主可用的模型集合不同，且有的宿主模型标识由用户自行注册（见 6.9），绝对档次无法映射，相对要求才有据可依。

适配层负责翻译。同一条意图在不同宿主的落法可以完全不同：「只读」可能是一个宿主级开关，也可能是一份不含写工具的白名单；「推理能力最强的一档」可能是内置别名，也可能要读用户自己注册的模型表再排序取头。

**清单一共七条。**现状是各宿主十二到十三条，多出来的部分是把「这次审什么」当成了角色。审设计、审计划、审代码这三件事，模型和权限完全一样，差别只在派发时交代一句话，不需要为它各存一份登记。查资料、把多份调查合成一份、单点查一个符号同理，共用一条。

**登记的条数由「模型或权限是否不同」决定，不由职责数量决定。**职责说明在共享语料里，派发时作为提示词传入（D14）。

| 角色 | 为什么必须单独一条 | 派发时用提示词传什么 |
| --- | --- | --- |
| 工人 | 唯一能改代码的 | 哪份计划、哪个切片 |
| 工人（高风险档） | 同样能改代码，但用更强的一档模型 | 同上 |
| 计划撰写者 | 能改文件，但只准改自己那份计划与对应 issue | 哪个 issue |
| 审者甲 | 只读；模型要与被审内容的写者不同族 | 审什么、哪一路视角、增量基准 |
| 审者乙 | 只读；模型还要与甲不同族，无第二族时降级并声明 | 同上 |
| 只读劳力 | 只读，常规档 | 查什么问题，或把哪几份合成一份 |
| 顾问 | 只读，本宿主推理最强的一档加高思考投入 | 交接包五项 |

工人那两条能否并成一条，取决于该宿主允不允许派发时临时指定模型：允许的并成一条，不允许的保留两条，写进能力声明的降级项。

**角色不一定以定义文件的形式存在。**实机看到三种形式，同一宿主内还会并用：

| 形式 | 实机样本 |
| --- | --- |
| 一份定义文件（名字、模型、思考档、工具权限） | 四家的审者 |
| 派发命令行的参数（无文件，模型与思考档写在那条命令里） | 参考实现的写码工人跑的是外部命令行 |
| 宿主自带的扩展配置 | 某宿主的顾问 |

因此真正的要求不是「有一份定义文件」，而是**派它出去的那一刻，模型、思考投入、工具权限、工作目录四样都已钉死**。用什么形式钉死不重要。

这条带来一个验收后果：定义文件形式钉死的东西可核对，文件在那儿一目了然；命令行参数形式钉死的东西只存在于那一次调用，写错、漏传或被宿主静默忽略都不会有东西提醒，只表现为「这个子代理产出的质量莫名其妙地不对」。所以冒烟派发不可省（6.6）。

**顾问的行为规格**（它与其余六条不是一类：其余六条是流程的零件由主线程按阶段编排，顾问是卡住时的出口，不进流程）：

| 项 | 规格 |
| --- | --- |
| 谁能调 | 只有主线程。子代理调顾问会出现嵌套派发，责任链断掉 |
| 什么时候调 | 条件触发：几个方向的取舍彼此接近、证据互相矛盾、或这一步会锁死难以回头的架构或数据权威。开工前例行确认与收工前再保险都不算，每阶段最多一次 |
| 给它什么 | 交接包五项：目标、已有证据（带定位）、暂定结论、未决问题、约束。它只读工具齐全，把交接包里每一句都当作未经验证的说法回源码核 |
| 它给回什么 | 三选一——照这么走、走错了往回拐、停下交给用户。简报不足时用一行说清缺什么然后停，不写交付物 |

宿主原生就有这个能力的直接用原生的，插件不为它造壳。交接包一律要给——依赖宿主自动转发上文，等于把顾问的输入质量交给宿主的实现细节。

### 6.5 能力声明规格

对每条意图三选一表态：

- **支持**：给出该宿主的具体落法。
- **降级**：说明退到什么程度、代价是什么。示例：宿主无法给角色钉模型，则跨模型审查退化为同模型两路视角，交叉验证效果下降。
- **不支持**：语料中依赖该能力的分支据此关闭，并在会话开场如实告知用户。

禁止静默填默认值。声明缺项即安装失败。

### 6.6 共享验收测试规格

**冒烟派发是核心，静态校验不够。**静态校验挡不住这种失败：字段名写对了但该宿主并不认这个字段，于是静默忽略——配置文件看起来完全正确，运行不报错，实际跑的是默认模型与默认权限。这类错误通常要很久之后以「审查质量莫名其妙变差」的形式才暴露。

**验收分两类，不能都指望代理自报。**

**代理可自报项**——安装后真的派一个最小角色出去，让它回报并当场试：手上有哪些工具、能否写文件、能否访问外部检索、当前工作目录在哪。这四项代理看得见、试得出，自报可信。

**由用户装完确认一次的项**——模型与思考档。代理对自己跑在什么模型上的报告不可靠，思考档多数宿主根本不告知代理。这两项不做机器验证：安装脚本在完成时提示用户派一个角色看一眼实际模型，确认一次即可。**代价要写在安装回执里：模型与思考档没有机器保证，宿主日后改了默认行为不会有东西提醒你。**

验收测试至少覆盖：

| 测试 | 判据 | 类别 |
| --- | --- | --- |
| 意图覆盖 | 能力声明对清单每条都有表态 | 静态 |
| 工具与权限 | 角色回报的工具清单、写权限、外部检索与意图一致 | 代理自报 |
| 工作目录 | 角色回报的工作目录等于派发时指定的路径 | 代理自报 |
| 隔离 | 并行派两个角色，各自写操作只落在各自工作树的分支 | 行为 |
| 只读约束 | 声明只读的角色尝试写入被拒 | 行为 |
| 语料洁净 | 核心区方法论语料中零宿主名 | 静态 |

不测钩子失败语义：钩子已是选配，为它构造异常场景的成本高于收益。

**部分测试只能在装有该宿主的机器上跑，进不了持续集成。**这是既定事实，安装脚本须在本机跑完并留下结果文件，不得因为持续集成里跑不了就省略。

### 6.7 迁移指南（skill）编写原则

**它的内容就是本节三样东西的技能化**：产出合同（6.3）、分叉点清单（6.8）、这里的编写原则。不另列内容清单。

- 每个分叉点先写**目的**：这个设计要达成什么。迁移者理解目的后自行选路，不照抄某个宿主的做法。
- 再写**为什么会分叉**：分叉来自宿主能力差异还是设计选择。
- 再写**有几条路**，每条给出适用条件与代价，按自动化程度排序。
- 明确写出：清单里列举的宿主差异是**已知样本，不是穷举**，遇到清单外的形状按目的自行判断。
- 指南本身与适配区说明必须点名宿主，**核心区语料的宿主名黑名单不扫这两处**。

### 6.8 分叉点清单

**分叉点 1 · 主线程怎么进任务工作区**

- 目的：任务级并行。
- 分叉来源：宿主对代理会话工作目录的控制权不同。
- 三条路：代理自建自进（需宿主有切换会话工作目录的工具，无代价）；用户在界面建悬空工作树、代理就地绑分支（需宿主界面能针对目录开会话，代价是开任务要人动手、无人值守起不了新任务）；代理建但不进、全程带显式路径（需脚本与 git 都接受目录参数，代价是易漏带路径、编辑工具相对路径基准会落在主仓库，方法论须强制绝对路径）。

**分叉点 2 · 子代理怎么进它的工作树**

- 目的：落地级并行，且防止第 5.2 节列出的五种漂移。
- 分叉来源：宿主派发机制是否支持钉住子代理的工作目录。
- 三条路：派发命令自带工作目录参数；会话内子代理工具支持指定隔离工作目录；两者都没有时补派发后校验并 fail-closed。
- 无论走哪条，都不得只靠提示词。

**分叉点 3 · 怎么派一个子代理**

- 目的：起一个干净上下文干一件事，不污染主线程上下文。
- 三条路：会话内子代理、外部无头命令行、两者混用。
- **收敛成同样的两步，各家实现不同但对外一模一样**：第一步「派出去」，给三样——用哪条角色登记、这次干什么、要不要放后台跑，返回一个编号；第二步「收回来」，凭编号取结果。方法论里只写「派一个审者去审这份设计」，不写任何宿主的工具名与参数写法。换宿主时把这两步重新实现一遍，方法论一个字不用改。
- **并行不是第三条路**（D55）。查清现状阶段要同时派几个调查员，就是把第一步连着调几次拿几个编号，再逐个收回。宿主自带编排工具的直接用它，没有的连着派——两边干的是同一件事。参考实现为此有一份原生编排脚本、另三家有一份五百多行的自建脚本，落地时都不再需要。
- 七条角色全走这两步，没有例外分支。所有角色的工作目录都要钉死，包括只读的——只读角色不污染分支，但它跑测试与构建时若读到的是主分支代码，绿了也不算数。

**分叉点 4 · 角色壳**

- 目的：把模型与思考档钉死在角色上，让不同角色跑不同模型。
- 两条路：宿主支持角色注册则写三字段壳；不支持则退化成派发时在提示词里说明角色，模型只能全局一个（能力下降，需在清单里显式声明）。

**分叉点 5 · 命令壳**

- 目的：让用户能敲斜杠命令推进阶段。
- 两条路：宿主支持斜杠命令则写薄壳；不支持则退化成用户打一句话、代理识别意图。

**分叉点 6 · 决策点咨询（更强模型顾问）**

- 目的：卡在承重决策上时，向一个更强的只读模型问一次，拿到「照这么走」「你走错了」「停下交给用户」三选一。它是卡住时的出口，不是例行多加一道审。
- 分叉来源：**有的宿主原生提供这个能力，有的没有。**原生提供的宿主直接用，插件不为它造壳；没有的宿主要自己注册一个只读角色，钉更强的模型与高思考档，派发时带一份交接包（目标、已有证据、暂定结论、未决问题、约束），因为这类宿主不会自动转发上文。
- 无论哪条路，触发都是条件触发不是节拍。完整行为规格见 6.4 末尾。

**照抄点 A · 发布清单**：让宿主认出这是插件并加载，照该宿主格式写，无选择。

**照抄点 B · 安装生效**：改完的语料能被宿主读到，照该宿主机制写，无选择。

钩子面：

| 项 | 差异 |
| --- | --- |
| 事件名 | 两家用同一组三个事件名；一家用四个完全不同的名字；一家在扩展里自行注册 |
| 注册位置 | 用户级与插件级是两套；同一宿主内两处位置的行为不同 |
| 失败语义 | 一家有显式的失败即拦标志；一家靠返回值；一家靠退出码。**钩子脚本自身异常时是放行还是拦住，三家不一致**，直接决定出站红线守不守得住 |

上一版方案曾把这些差异判定为「同一件事的不同写法，可由生成器按模板吐出」。实机核对后该判定不成立：四家的能力集合只是部分重叠，只读开关与工具白名单不是同一件事，服务器级授权与工具级授权粒度不同，后台在一家是角色属性、在另一家是调用属性。这是采用意图层（6.4）而非生成器的直接依据。

### 6.10 检索工具接入规格

三个工具：符号检索（找定义、找引用、找实现、看文件符号概览）、结构与影响面检索（模块关系、调用链、反向影响、跨语言数据流）、外部库文档检索（库与框架的当前用法和配置）。目标是跟着插件走、换宿主不重配，并且把常驻上下文开销压到最低。

**实测：直接挂上游的代价**

| 工具 | 上游工具数 | 工具清单载荷 | 估算 token |
| --- | --- | --- | --- |
| 符号检索（已收窄到四个只读工具后） | 4 | 8 508 字符 | ≈ 2 430 |
| 结构与影响面检索 | 10 | 6 041 字符 | ≈ 1 726 |
| 外部库文档检索 | 2 | 5 003 字符 + 632 字符握手说明 | ≈ 1 610 |
| 合计 | 16 | | **≈ 5 765** |

这近六千 token 每次请求都在，哪怕这一轮既不查符号也不查文档。单个工具的说明最长的接近 3 900 字符。结构检索那家的上游启动参数里没有任何工具过滤能力，而宿主级过滤四家粒度不同，因此收窄只能自己做。

**做法：一份收窄代理 + 三条配置 + 三份技能**

代理把每个上游服务器收成一个工具，参数透传。每条配置写三项：

| 配置项 | 符号检索 | 结构与影响面检索 | 外部库文档检索 |
| --- | --- | --- | --- |
| 上游怎么连 | 本地进程 | 本地进程 | 远端地址 |
| 动作映射 | 找定义 / 找引用 / 找实现 / 看概览 | 关系查询 / 反向影响 / 两点路径 / 节点解释 | 认库 / 查文档 |
| 工具描述 | 一行 | 一行 | 一行 |

**三条不能省的约束**

- **参数透传，代理不重新定义参数集。**最长那个工具的说明接近 3 900 字符，说明它参数很丰富；重定义一套参数是最容易把上游能力包没了的地方。
- **外部库文档检索的两步不合并。**先认库、再查文档是有意义的：库名经常有歧义，同一个名字对应多个候选，要让模型自己挑。自动取第一个会在冷门库上悄悄查错文档，而这种错很难发现。
- **符号检索的只读白名单内建进代理。**上游默认暴露 29 个工具，其中包含任意命令执行、一整套写工具（覆写文件、替换符号体、前后插入、重命名、删除、跨文件替换）和一套会往仓库里落文件的记忆系统。这三类分别绕过本方案的编辑纪律、安全边界和状态文件权威，必须挡住。

**提示词只写在技能里**

MCP 声明里不写纪律，上游上下文的提示词字段留空，不改上游自己的全局提示词模板，不往用户的规则文件写任何东西。每个工具一份技能，讲清楚：什么时候用、几个动作各解决什么问题、参数怎么给、结果只是候选必须回当前源码亲验、什么情况转交给另一个工具。技能的描述常驻、正文按需加载，与常驻的工具清单正好互补。

**图的新鲜度**

结构检索依赖一张关系图，上游只读图不建图。建工作树时跑一次建图，失败不阻断；方法论里加一句：代码刚大改又要查影响面时再跑一次。不做自动检测，也不做每次调用前重扫——原自建版本那套每次调用前重扫的超时上限设到 900 秒，隐藏成本大于它挡的风险。

**账**

| 项 | 现在 | 之后 |
| --- | --- | --- |
| 自建代码 | 1 010 行 | 约 250 至 300 行，一份代理 |
| 常驻 token | ≈ 5 765 | 约 750 |
| 提示词落点 | 6 处 | 3 处技能 |
| MCP 工具数 | 16 | 3 |

**新增第四个工具**：配置加一条（怎么连、动作映射、一行描述），写一份技能。代理不改。

**代价，写明**：外部库文档检索原本可以零安装直连远端，经代理后要多起一个本地进程。这是全套设计里唯一一处包装引入了新依赖的地方。

**冒烟不可省**：装完逐个实测工具可调用，缺一即安装失败。现状已出现过它要挡的失败——配置在、工具名在工具列表里、直到真正调用才报错。

### 6.11 出包发布归属与版本对齐

**它属于核心区，不属于任何宿主。**实测依据：

| 组成 | 单宿主行数 | 四家差异 |
| --- | --- | --- |
| 自愈引擎 | 1 310 / 1 389 | 旧两家与新两家差 79 行；同代之间差 3 行（状态目录解析写法新旧不同） |
| 打包阶段脚本 | 353 | 只有参考实现那份用旧写法，差 3 行 |
| 合同校验 | 257 | 四家一字不差 |
| 脚本组装 | 357 | 四家一字不差 |
| 方法论 | 150 | 旧两家与新两家差 10 行 |

引擎内搜不到任何宿主名、子代理工具名或模型名。它是纯 shell 加 JSON 处理的状态机，靠仓库登记的一份适配清单认项目；唯一与派发沾边的一步是调本项目统一入口的另一个子命令，不直接调宿主。**它被复制四遍是组织方式问题，不是能力差异。**

**它与阶段编排的耦合只有一处**：主干里的打包那一格。拆成独立技能后，编排侧只剩一句「走到打包那一格就调出包技能」。

**那 79 行修的是一个真实的坏行为。**出包失败的真实原因常常在构建机而不在代码——产品的开发版还在运行导致端口或文件占用，或者缺少远端主机与目录的环境变量。旧版本把这类失败归进待修复派发，于是派一个代码修复工人去改代码，而代码没有问题，工人只能空转，转完再失败，直到熔断停机。新版本给根因加了环境类标记，识别出来立刻暂停并做三件事：状态查询多输出一行处置句，直接说该干什么；回执带根因摘要，从诊断结果抽出每条失败的名字、根因、处置办法与摘录；环境类失败不派代码修复工人。

落地三步，有先后：

| 步 | 内容 | 规模 |
| --- | --- | --- |
| 1 | 把那 79 行回填到参考实现与另一个旧版宿主，四家版本对齐 | 79 行，机械操作 |
| 2 | 整块提到核心区只留一份 | 删掉三份复制，约 7 300 行 |
| 3 | 从阶段编排里拆出成独立技能 | 编排侧只剩一句调用 |

第二步与第三步是同一件事的两面：它能只留一份，正因为零宿主耦合；它零宿主耦合，正说明它与阶段编排没有真正的绑定。

**版本只有一个：整个仓库一个号，核心区与四份适配区同进同出。**适配区不单独发版——它没有独立于核心区的用户，为它设计一套独立版本线是给一件不存在的事做机制。现状是四家各维护自己的清单版本，那是四份复制品各自为政的产物，本次改造之后没有理由保留。

## 八、验证方式

| 项 | 判据 |
| --- | --- |
| 推进 | 在落地那一格改两行，敲 `/next` 直接进下一格，不触发任何审查 |
| 增量审 | 全量审通过后回落地改两行，再敲 `/review`，审者只收到这两行的改动范围 |
| 跨会话 | 关掉会话重开，只读状态文件、阶段产物与提交流水即可续跑，无需会话记忆 |
| 跨月 | 一个月前停在设计或原型阶段的任务，敲 `/mmw` 能报清在哪一格、讨论到哪、上次为什么停 |
| 产物形状 | 原型目录里外层无被取代的东西，每轮证据在轮次目录，逐轮账本读得出每轮验了什么、用户说了什么 |
| 无人值守 | 授权后代理自行走到出包，现场注记里逐条可读它替用户做的决定，三处禁区未被代敲 |
| 子代理隔离 | 并行派两个工人，各自提交只出现在各自分支，主分支无改动 |
| 终审覆盖 | 全量审的独立审计一路读到了全部改动，不因主线程已自审而缩范围 |
| 增量审退化 | 提交流水与审查记录对不上时，代理主动退回全量审并说明原因 |
| 去宿主名 | 黑名单扫描核心区语料，零命中；迁移指南与适配区不在扫描范围 |
| 意图覆盖 | 能力声明对角色意图清单五个维度都有表态，无缺项 |
| 工具与权限 | 派出的角色回报的工具清单、写权限、外部检索、工作目录与意图一致 |
| 模型与思考档 | 安装回执提示了确认动作并写明「无机器保证」 |
| 迁移 | 按迁移指南在一个新宿主上完成接入，只看产出合同与参考实现，不抄其他宿主的适配代码，最终通过全部共享验收测试 |

## 九、责任边界

- 本次改造只动阶段编排与迁移面。审查方法本体不在范围内，原样保留。检索纪律的内容不变，但它的接入方式纳入本次范围（6.10）。测试质量权威的内容只补一条（流程编号不进测试名），改的是它与仓库层的分工与路径约定（4.8）。
- 归档目录不参与改造。
- 四个宿主不同步改造：Claude Code 那份先落地并稳定，再按迁移指南推其余三份。
- 测试规模不承诺净减。引擎测试减少，但新增共享验收测试且验证面变宽（四宿主一致行为、冒烟派发、运行事实回读），预计落在 3000 至 4000 行，且其中一部分只能在装有对应宿主的机器上跑。不得把这部分测试因为进不了持续集成而省略。
