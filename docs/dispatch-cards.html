卡因此怎么写

谁发命令在哪跑写进卡里的正文云端自己能读的
Coordinator 派 Worker 这台 Mac 工单和 spec 的正文、评论、night branch、开工提交、ticket/issue-N、RUNTIME_COMMIT。角色一句：去读 dispatch，按 worker 做。 已经推送的 ticket/issue-N。读不到这台机器上的路径。
Worker 派第一个 verifier Worker 那份云端检出 票号、分支、ticket head、feature file、上面那份正文。角色一句：去读 dispatch，按 verifier 做。环境留空，所以还在这份检出里。 这份检出里的 HEAD，包括还没推送的提交。读不到 Coordinator 的夜记录。
Coordinator 派三个轴和第二个 verifier 这台 Mac spec、已 land 的票、两个提交、diff 用的命令、标准文件名、feature file。三个轴和第二个 verifier 各一张卡。第二个 verifier 的检出从已推送的 night branch 打开。 night branch 上已经推送的提交。两个提交都在这条历史上，diff 才能在那边重算。
researcher 这台 Mac 问题本身。模型从 researcher 那一行来。不进 night 的云端检出。 不靠云端。

发送者仍只填脚本在自己这台机器上读不到的那一项：开夜时的 host、project 名、spec 号或票号；之后每张票的票号；researcher 的问题。工单正文由这边的命令读好，写进卡，不把磁盘路径交给云端。
