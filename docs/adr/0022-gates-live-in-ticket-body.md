# 验收关卡写在票正文里，不建独立账本文件

落地流水线的完成定义是「票的全部验收关卡通过且留有证据」。关卡放哪里有两个候选：票（issue）正文的验收小节，或仓库里独立的账本文件（参考项目 unlazy 的形态：每个工作单元一个 `gates/*.md`）。

选票正文。to-tickets 产出的票本来就有 `- [ ]` 验收条目小节，关卡是把这些条目磨利：可跑的条目补上检查命令与期望输出（写法取 unlazy「Author gates that can fail」一节中与可跑检查相关的五条（意译）：直接观测结果物、只在全部断言通过后打印成功标记、否定断言先过正例、给定数字独立测量、证据取最小决定性输出；该节的第六条「按后果复核人工关卡」由人工项标注承接），写不成命令的条目显式标为人工项并指定裁决人。票就是工人收到的完整简报（unlazy 的简报封闭清单四项：共享契约、该单元的归属与依赖、它自己的账本、完成规则），关卡放在票里意味着简报天然自足；放独立文件则每次派发都要做一次票与文件的连接，且两处必然漂移。

每条检查命令必须无交互，通过与否按双条件判定：退出码为 0 且输出含约定的成功标记（继承 unlazy 的判定，堵住「报错文本里碰巧含成功词」）。这样的命令将来可原样搬进任何 CI。

## Considered Options

- **独立账本文件（unlazy 形态）。** 否决。unlazy 的账本是给它自己的 checker 运行时解析的；本流水线不引入该运行时（约 1600 行运行时代码、连测试约 2900 行，仓库无 CI 养不起），账本文件失去了机器消费者，只剩漂移成本。它的格式纪律（双条件判定、证据回写、勾选不算数）以散文规则的形式继承进关卡写法。
- **关卡放仓库、票里放链接。** 否决。等于独立文件加一跳间接，两个缺点都保留。

## Consequences

- to-tickets 需要精确修改：验收条目升级为关卡（含检查命令、期望输出、人工项标注），改动写 merge-note——它是上游技能。
- 完成判定「勾选不算数、证据才算数」：工人勾选条目时必须附检查输出的决定性片段作为证据，复验者重跑全部检查、不信工人写的证据。
- 判决绑定代码版本：复验判决以票号加 commit 为键记录在票的评论里，代码再变则判决作废。
