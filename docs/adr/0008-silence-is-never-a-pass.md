# 流水线里每一道闸口，拒绝要点名事实、给唯一出路，且不许靠什么都不做通过

改动或新增流水线的任何一道闸口时，要问它的问题不是「坏情况它抓不抓得住」，而是：**它跑了一遍却什么都没做，有人会发现吗？** 一道既没干活也没出声的闸口，读起来和一道通过了的闸口完全一样。

所以凡是能拒绝的东西——`hook.py` 的 pretool 与 question 两道、`lease.py` 的 claim 与 release、`verify-ticket.py` 的 preflight 与 closeout、`.mmw/target.json` 的 `start`、`board.py` 的空 frontier 解释——都要同时满足三条：

1. **点名它查的那个事实。** 一个 pid、一个路径、一个计数、一个票号，读的人能自己去看。没有事实的拒绝跟猜没有区别。
2. **说出唯一那条出路。** 不是列选项：给了选项的 agent 会自己发明第六个。没有出路的拒绝是一句正确的死锁，两个这样的拒绝互相顶着，一夜就停在那里。
3. **绝不靠什么都不做而通过。** 跑不动的时候——没数据、没应答、没网络——它要大声说跑不动并失败。「查不了」和「查过了，没问题」是两个答案，其中只有一个是沉默。

拒绝这三条讲的是闸口的行为；一条拒绝消息本身的三段结构（发生了什么、为什么、下一步做什么）写在 `mmw-v2/skills/verify-ticket/scripts/refusal.py`。

## 这条规则是从哪一批故障里得出的

2026-09-05 一夜里出的故障是同一个形状，而且不是大家预期的那个形状：**没有一处说谎**。每一道闸口都处在既没干活也没出声的状态。

- 批次检查读错了批次，于是「防止两张票认领同一块屏」那道检查跑在一个两张票都不在的集合上，什么都没打印；
- `advance` 一张票都没派出去，五张票停在不可启动的状态，而它打印的总结行，和「本来就没事可做」时打印的是同一行；
- 一道类型检查红了三天，每个 worker 都绕开它走；
- 一套测试写进了本机真实的租约注册表，直到有一个运行被锁在自己的端口外面，才有人发现；
- 一个已经不再应答的应用仍然占着自己的地址，而唯二能处理它的两条命令都拒绝了，每一条都拒绝得对。

## Considered Options

- **写进 `verify-ticket/SKILL.md`。** 否决。这条规则的读者是改流水线的维护者，不是跑验收的 worker 与 verifier；放在 SKILL.md 里，每个 worker 每一次开工都要把它读进 context，而它对手上这张票没有一句可执行的内容。
- **只写进 `CONTEXT.md` 的 `### Working discipline`。** 否决。`CONTEXT.md` 开头写明自己是镜子不是源（「这份和那份不一致时，以那份为准」），一条只存在于 `CONTEXT.md` 里的原则没有 `_Home_` 可指。现在 `CONTEXT.md` 里有一条 `**silence is never a pass**` 词条，`_Home_` 指向本文件。
- **写进 `refusal.py` 的模块 docstring。** 否决。`refusal.py` 的主题是一条拒绝消息的三段结构，是给写消息的人看的；闸口该不该存在、怎么验它，是设计判断，不是那个函数的说明。`refusal.py` 的 docstring 指向本文件。

## Consequences

- 新增闸口时多一步自检：把它的失败路径跑一遍，确认它在「跑不动」时会红，而不是静默放行。
- 已经按这条改过的地方：`board.py` 的 `herdr_strict`（Herdr 答不上来时抛错，不当成「工作区里没有会话」）与 `explain_empty_frontier`（空 frontier 逐票说明被什么挡住），`lease.py` 的 `release`（有进程还在监听就拒绝并报出 pid），`hook.py` 的三道拒绝（每一条都带下一步）。
- 测试套件自己也在这条规则之下：verify-ticket 的测试用自己的租约注册表与端口段，并有守卫反向验证守卫本身没有失效。
