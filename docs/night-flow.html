流程是下面这一条。Worker 和 verifier 的卡由 spawn 印出。三个审查轴由 Coordinator 在自己这场按 dispatch-reviewer 派出。

顺序

每张 ticket 走 1 和 2。全部 land 之后才走 3。research 不在这个 night。

1 · Coordinator 派 Worker 实现，写 drive script，提交，推送，把 PR 开成 draft 2 · Worker 派 verifier 跑 verify
通过Worker 交回 CoordinatorCoordinator 做 land。这一步没有卡。
没通过Worker 修修好、推送，用修好后的 ticket head 再跑第 2 步。
3 · 全部 land 之后 Coordinator 按 dispatch-reviewer 派三个轴，同时派第二个 verifier 审的是整条 night branch。怎么备材料、怎么派轴，在 dispatch-reviewer。verifier 仍由 spawn 印卡。
没有卡有问题，Coordinator 自己修好改在 night branch 上。改完不再派一轮。

1. Coordinator 派 Worker

这张卡的活是实现。verify 是下一张卡，由 Worker 按卡上的固定句去派。

python3 models.py spawn worker --host cursor --at RUNTIME_COMMIT --role junior-worker --ticket 18 --spec docs/spec.md --into night/spec-76 --start <night branch 开工时的提交> --sources ticket-18.md

Coordinator 交

--role
junior-worker 或 senior-worker

ticket 上的 worker grade。两个都在或都没有，命令停下。

--at / --start
RUNTIME_COMMIT 锁模型。--start 是 night branch 开工时的提交。
--ticket / --spec / --into
18，docs/spec.md，night/spec-76

76 是这场 spec 的 issue 编号。没有 spec 就不交 --spec，night branch 写成 night/ticket-N。

--sources
Coordinator 已经读过的正文
命令填 仓库名、模型、ticket/issue-18。这条要先从 night/spec-76 的尖端推上去。

印出 1 张

命令填 模型 grok-4.7-high-fast。senior 换成 grok-4.7-xhigh-fast。
固定 环境 cloud，从 ticket/issue-18 开。等它做完。种类 generalPurpose。名称 Implement ticket #18。
Coordinator ticket、spec、night/spec-76、开工时的提交、正文、RUNTIME_COMMIT。
命令填 Repository、ticket/issue-18。
固定 实现，写好 drive script 并跑到通过，提交，推送，把 PR 开成 draft。
固定 然后跑 spawn verifier，把印出的卡交给 Task。没通过就修好再跑。通过后把 work report 交回 Coordinator。
固定 不派 Standards、Spec、Tests。
Codex：同一份提示词。gpt-6.1-sol，junior 的 effort 是 medium，senior 是 high。没有环境，没有后台。

实现中 Worker 问问题：Coordinator 用原来的 Agent ID 做 resume，不跑 spawn，不换模型。

2. Worker 派第一个 verifier

PR 已经开成 draft。这张卡只跑 verify-<app>，不改 drive script。项目没有 verify-<app>，或这张 ticket 不改人会用到的界面：不印卡，Worker 直接交回。

python3 models.py spawn verifier --host cursor --at RUNTIME_COMMIT --ticket 18 --branch ticket/issue-18 --head <ticket head> --features features/login.md --sources ticket-18.md

Worker 交

--head
ticket head
--branch / --ticket
ticket/issue-18，18
--features
这张 ticket 点名的 feature file
--sources / --at
ticket 正文，和 RUNTIME_COMMIT
命令填 verifier 那一行的模型。verify-<app> 的目录 .cursor/skills/verify-…/

印出 1 张

命令填 模型 = verifier 行的 slug
固定 环境留在 Worker 这场，所以仍在 ticket/issue-18 上。等它做完。种类 generalPurpose。名称 Verify ticket #18。
固定 调用 verify-<app>。先 Doctor，再跑点名的 feature file。不改 drive script，不改 feature map。脚本断言的句子是 expected result，原样抄来的。
Worker ticket 18，ticket/issue-18，ticket head，feature file，正文。
固定 向 Worker 交回通过或没通过，以及实际跑过的命令和结果。
Codex：同一份提示词。模型按 verifier 行拆成 model 和 effort。

没通过：Worker 修好并推送，再跑下面这一条。--head 换成修好后的 ticket head。这是一张新卡。resume 只接实现途中的问题。

python3 models.py spawn verifier --host cursor --at RUNTIME_COMMIT --ticket 18 --branch ticket/issue-18 --head <修好后的 ticket head> --features features/login.md --sources ticket-18.md

谁写哪一份

文件它负责
dispatch这夜的顺序。两个提交各是什么。何时派 Worker、何时派 verifier、何时 land。审查在派轴前停下时，verifier 仍跑。审查之后改在 night branch 上。Worker 卡和 verifier 卡。
code-review 的 dispatch-reviewer一次完整审查怎么做。把 spec 和已 land 的 ticket 收成 sources，找出标准文件，对上 diff，然后派出 Standards、Spec、Tests，核对它们的报告并汇总。
Standards、Spec、Tests各自怎么判断。Tests 不跑 verify-<app>。
verifier跑 verify-<app>。不改 drive script，不改 feature map。

3. 整晚收口

全部 ticket 都 land 在 night branch 上。Coordinator 定下 pinned comparison、night branch 全部 land 之后的提交、这晚的 spec、已经 land 的 ticket，并读 review-axis 那一行。然后在自己这场按 dispatch-reviewer 做。sources 怎么写、标准文件怎么找、diff 怎么对、三个轴怎么派，都在那一份里。

派轴的同一轮，Coordinator 用那份 sources 跑下面这一条，把 verifier 的卡和三个轴一起交给 Task。verifier 用 verifier 那一行。环境是 cloud，从 night/spec-76 开。三个轴留在 Coordinator 这场，也在 night/spec-76 上。

python3 models.py spawn verifier --host cursor --at RUNTIME_COMMIT --branch night/spec-76 --features features/login.md --sources <dispatch-reviewer 写成的 sources> --for night

dispatch 交给这场审查

pinned comparison
night branch 切出来时的提交
要审的提交
night branch 全部 land 之后的提交
交给审查的
这晚的 spec，加上已经 land 的 ticket。标准文件和 sources 由审查自己收。
命令填 review-axis 的模型。models.py row，不印轴卡。

dispatch-reviewer 自己做

文件里 先把 spec、ticket、testing decisions、expected results 写成 sources。标准文件里要有仓库里的 CODING_STANDARDS.md 和 CONTRIBUTING.md。
文件里 再对上两个提交，写出 diff 和提交列表。对不上或 diff 是空的，就停在这里。sources 留着。
文件里 三个轴一起派，等它们回来。只交报告，不改代码。没有 spec 时跳过 Spec。
文件里 核对报告，汇总成 Standards、Spec、Tests 三节，留在 Coordinator 这场。
Codex 同一份做法。review-axis 是 gpt-6.1-sol，effort high。模型仍从那一行读。

审查在派轴前停下：原因写在 dispatch-reviewer 里。verifier 仍用那份 sources，在那个 night branch 提交上跑。要改的，Coordinator 自己改在 night branch 上。改完这场审查结束。

落在这些地方

地方现在这样
spawn只印 Worker 和 verifier。
云端 Coordinator全部 land 之后，交出两个提交、spec 和已 land 的 ticket。按 dispatch-reviewer 派三个轴，同一轮 spawn 第二个 verifier。然后自己改 night branch。
dispatch-reviewer写 sources，找标准文件，对 diff，派三个轴，汇总。
本地暂停。本地 reviewer 仍走 main reviewer。
云端 Worker只派 verifier。

verifier 和 Standards、Spec、Tests 不占 max_workers。max_workers 只数 Worker。失败的 verifier 是一张新卡。Worker 的 Agent ID 仍由 Coordinator 留着，只接实现途中的问题。
