事实就是推上去的分支、PR，和 GitHub 上的 issue。云端自己读。first verifier 在 Worker 同一个分支上跑 verify-<app>。没有要另外登记的一份。

整场顺序

例子用 spec 76、ticket 18。N 是 issue 号。project 名是 owner 授权的那个名字。

  1. 1
    open · Coordinator · 云端

    发送者打 host、project 名，以及 spec 号或这一张 ticket 的号，两样里打一样。夜班已存在，这场从那条 night branch 开始；还没有，就从 project branch 开始，project branch 也没有就从 dev 开始。命令把 project branch 按 dev 的提交推上去（缺了才推）。然后把当前分支改名为 night/spec-76 或 night/ticket-N，推上去。

    起点就是这两条分支的 merge-base。pinned comparison 和 RUNTIME_COMMIT 都是这一个提交。命令现算，不另存。

  2. 2
    spawn worker --ticket 18 · Coordinator · 夜班分支

    eligible 的 ticket 一起派。命令不自己挑。它读标签，正好是 junior-worker 或 senior-worker 才印卡。模型用那一行。

    命令不建 ticket/issue-18。origin 上已有这条分支，卡就从它打开；还没有，卡从 night branch 打开。Coordinator 留在 night branch。Worker 自己把分支改名为 ticket/issue-18。

  3. 3
    Worker 实现 · 云端 · 改名为 ticket/issue-18

    步骤在 Worker reference 里，不在卡上。第一次推送前把当前分支改名为 ticket/issue-18。票上写了 feature file 的路径和要原样出现的那一句，Worker 才在 verify 技能里写 drive script，跑到通过，和那一页一起提交。票上没写，就不写。然后推送，开 PR：head 是 ticket/issue-18，base 是 night branch，保持 draft。这张 PR 就是这张 ticket 的记录。

  4. 4
    spawn verifier · Worker 那份检出 · 发送者不用打参数

    先把当前 night branch 合进 ticket/issue-18。冲突时，Worker 把合并前的提交和冲突文件交回，Coordinator 解决后 resume 这个 Worker。合入改了人会用的表面，就先改 drive script 并跑过，再派 verifier。

    verifier 在同一个检出、同一个分支，卡不带 environment。它核对 HEAD，跑 verify-<app>。feature file 是这条分支相对 PR base 改过的那些。

    不通过。 Worker 修好，提交并推送新的 head，再跑 spawn verifier。这是一张新卡，不 resume。通过的只算它跑过的那一个提交。

    通过。 PR head 还是这个提交，才把结果写进 PR，并写明这个提交。通过之后又有新提交，再派一张新卡。

    不派。 没有 verify-<app>，或这张 ticket 不改人会用的表面。结果直接写进 PR。

  5. 5
    land · Coordinator · 夜班分支 · 没有卡

    Worker 是 Coordinator 的 cloud subagent。这一轮结束，Coordinator 读这张 PR。land 只打 PR 号，要合进去的提交就是 PR 现在的 head。派过 verifier 的，PR 里通过的那个提交必须就是这个 head。没做完的留着 draft。

    scripts/check 不过。 命令带上检查的输出。resume 原来的 Worker。它修好、推送，再派一张新的 verifier。通过的提交成为 PR head 之后，再 land。

    合入 night branch 时冲突。 Coordinator 自己解决，再 land。

    second verifier 不通过。 Coordinator 稍后在 night branch 上改。不叫回 Worker。

  6. 6
    spawn review · Coordinator · 夜班分支 · 不用打参数

    每一张会 land 的 ticket 都 land 了，而且没有 Worker 还在跑，才到这里。没做完的留下，不挡住这场审查。三个轴和 second verifier 各自从夜班提交打开一条临时分支，自己用 gh 读 issue，不改名，不推送。命令把起点和当前尖端两个 SHA 写上卡。核对和汇总由 Coordinator 做。

  7. 7
    改 night branch，然后交付 · Coordinator · 夜班分支 · 没有卡

    硬问题，包括 second verifier 的失败，改在这条 night branch 上，提交并推送。这一改结束这场 night 的审查。judgement call 不改代码：Coordinator 写下判断和建议，放进 delivery PR，再在对话里汇报。delivery PR 是 night branch 到 project branch。retro 在这张 PR 出现之后，提交仍在这条 night branch 上。并回 dev branch 做测试、再并回 main branch 做部署，仍是另一次授权，用 gh，不把这场检出切过去。

实现中途的提问，resume 原来的 Worker。verifier 不通过不是提问：修好，新卡，再跑。eligible 的 ticket 一起派。

命令是 dispatch.sh。它印出卡。发送者把印出的对象交给 Task。三个轴和 verifier 不再往下派。本地版的完整审查仍由 main reviewer 做。spec 这个 issue，和 Spec 这个轴，是两个词。

dispatch-reviewer.md 让 Coordinator 做的事

  1. 1
    跑 spawn review。命令快进 night branch，算出它和 project branch 的 merge-base，把起点、尖端、spec 号、已 land 的 ticket 号写上卡。
  2. 2
    同一个回合把 Standards、Spec、Tests、second verifier 的卡交给 Task。等它们回来。
  3. 3
    Coordinator 核对每条发现。对不上的删掉并写下原因。
  4. 4
    按 Standards、Spec、Tests 分栏汇总。不合成一个高低。然后回到 coordinator.md。

命令

命令印 JSON，自己不启动 agent。谁印出卡，谁把 cards 里的每一张交给 Task。skipped 是这回没有印的卡。Cursor 的卡带 description、prompt、model、subagent_type、run_in_background，有的话再带 environment 和 cloud_base_branch。Codex 的卡带 description、prompt、model、effort。除了 researcher，都是前台。

命令谁，在哪发送者打的命令自己读的
open Coordinator，云端 --host --project，外加 --spec 或 --ticket 缺了才从 dev 推出 project branch。把当前分支改名为 night branch 并推送。夜班已在 origin 上就先快进到它。
spawn worker --ticket N Coordinator，当前分支是 night branch ticket 号 当前 night branch、ticket 的 worker grade、gh 上这张 issue 的号。origin 已有 ticket/issue-N 就从它发卡，否则从 night branch 发卡。
spawn verifier Worker，它的云端检出 没有 当前分支、已推送的 HEAD、这张 PR 的 base。模型读 night branch 起点上的 verifier 那一行。
spawn review Coordinator，夜班分支 没有 当前 night branch、它和 project branch 的 merge-base、status 里已 land 的 ticket 号。印出最多四张卡。
spawn researcher --question FILE Coordinator 这场，不另开云端 --question，以及 --host 问题文件的正文。模型读 researcher 那一行。印一张后台卡。
show Coordinator，night branch 检出 没有 night branch 起点上的模型配置。cloud 这场不再使用 max_workers。
status Coordinator，夜班分支 没有 当前分支名里的 spec 号或 ticket 号。已 land 的判定和现在一样。
land PR Coordinator，夜班分支 PR 号 这张 PR 的 head，和当前 night branch。PR 必须指向这个仓库和这条分支。
board Coordinator，night branch 检出 可以带端口 和现在一样。没有卡。

row ROLE HOST --at COMMIT 仍给 night 以外、需要单独读一行模型的技能。一场 night 里，--at 就是 night branch 和 project branch 的 merge-base。

dispatch 的 SKILL.md 留什么

每个 night 角色都读这一个文件，然后只打开自己那一行。派卡、land、实现、审查判断，都不堆在这里。

# Dispatch

Read this file, then the one reference for the assigned role in your first message.
That role is yours for this run. The sender keeps its own.
A later result or question does not start you over, and it does not give you the sender's role.

The installed runtime is the runtime of this night. Run its skills and this dispatch.sh.
A commit that changes those files in the repository does not become the runtime until a later run.

Resolve ../../tools/dispatch/scripts/dispatch.sh from this file, and run it in the consuming repository.
The command prints JSON. It does not start the subagent.

When that JSON contains cards, hand each object to Task as printed.
Wait, unless the object has run_in_background set.
skipped names a card that was not printed. That role does not run, and the step continues without it.
On Codex, hand the same object to the host's subagent tool.

Return the result the reference names, with the evidence it names.
A question returns to the sender and ends the turn.
The sender answers by resuming that same Agent ID.
A returned result continues the step that sent it.
A missing or incomplete result is a limitation of that step, not a success.

When no assigned role is named and the request is to review a branch, a PR, or since a commit, stop.
The only review is the Coordinator's night-branch review, and it runs once.
It reviews the night branch, not the named PR.

Dispatch reviewer 不是卡上的角色。Coordinator 的那一节打开 references/dispatch-reviewer.md。命令印出的卡已经填好。发送者把那个对象交给 Task。
