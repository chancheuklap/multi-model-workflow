# 领域文档

技能探索代码前该怎么读本仓库的领域文档。

## 开工前先读这两处

- **`CONTEXT.md`**（仓库根）——术语表。项目自己的话怎么说。
- **`docs/adr/`**——架构决策记录。只读跟本次要动的地方相关的那几份。

**文件不存在就默默继续。** 不要提它们缺失，不要建议先建。术语和决策是等真的解决了一个才由 `domain-modeling` 顺手写下来的，不是开工前的填表作业。

## 布局

单上下文，一份根 `CONTEXT.md` 加一个 `docs/adr/`：

```
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-<kebab-标题>.md
│   └── 0002-<kebab-标题>.md
└── ...
```

决策记录编号四位、从 `0001` 起、只增不改。

## 用术语表里的词

输出里提到一个领域概念时（issue 标题、重构提案、假设、测试名），用 `CONTEXT.md` 里定下的那个词，不要漂到它明确避开的近义词。

要用的概念还不在术语表里，这本身是信号：要么你在发明项目不用的语言（重新想），要么是真缺一条（记下来交给 `domain-modeling`）。

## 撞上既有决策要摆到明面

输出跟某份决策记录矛盾时说出来，不要默默覆盖：

> 与 ADR-0007（事件溯源的订单模型）矛盾——但值得重开，因为……

## 两者留在仓库里，跟代码同一个提交演进

术语表和决策记录不上 Wiki。理由：agent 每次开工前都要读，本地文件不用联网；改了实现就该在同一个提交里改决策记录，脉落才不会分家。设计和计划文档走的是另一条路（落地后上 Wiki，见 `issue-tracker.md`）。
