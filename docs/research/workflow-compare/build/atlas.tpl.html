一句话看懂 pstack 的运转

人给一个目标和完成条件；常驻的 poteto-mode 把它分到 23 条 playbook 之一；playbook 是一份分步说明，每一步调用技能、派出子 agent、读写产物；需要人的地方停在人的决定点；最后多半经 PR 交付，由人（或事先给的授权）决定合并。

人：目标→poteto-mode 路由→playbook 步骤→技能 · 子 agent · 脚本→PR / 报告→人：授权 · 复盘

真正的程序只有 poteto-mode/scripts/ 与 show-me-your-work/scripts/ 下那几个（orch、watch-pr、check-plan、worktree-audit、log.sh 及其实现）；其余都是给 agent 读的文字：技能正文、reference、提示词。pstack 没有 hook、没有常驻进程：唤醒靠 Cursor 的 /loop 与子 agent 完成通知。50 个技能里 49 个设了 disable-model-invocation: true，模型不会凭描述自己选用，只能由人敲 /名字或由 poteto-mode 点名调用。原则不单独执行，而是在做某个决定时被读取、约束那个决定。

全局规则：不管走哪条 playbook 都成立

来自 poteto-mode/SKILL.md。黄边的是「总要停下来问人」的事。

怎样在 23 条 playbook 里选

把 poteto-mode 的路由条件整理成一棵树：先看请求属于哪一类，再在组内按顺序逐条判断，第一条「是」就选它。分组是我为阅读整理的；组内顺序照调查员按原文判别条件排的检查顺序。点绿色块在全景网里定位。

单任务 playbook：同一副骨架，不同的第一步和证据

每条单任务 playbook 都走「先做什么 → 怎样分工 → 拿什么证明 → 产出什么 → 交给谁」。差别集中在第一步和算完成的证据。

PR 的一生：谁把它推到下一个状态

每条箭头上的标签是推动这一步的组件：Babysit 只负责把 PR 推到 merge-ready；过了 merge-ready 的每一步都归 Shipping；watch-pr 只观察和报告，不推动。

五种长时模式：按「一次处理多少」和「谁合并」区分

左图定位，右表逐项比较。选哪一种，原文给的判别条件在表的最后一行。

同一套生命周期，五种做法

并行技能的拓扑：派几个、什么模型、谁评判、谁合成

同一种画法：左边是主 agent 派出的角色（方块里是数量，颜色是默认模型，锁形表示只读），中间是评判，右边是合成与产出。

证明手段：各自证明什么、不能代替什么

按它在工作中出现的时点分四栏。红字是原文明说它不够证明的东西。

经验怎样回流到下一次

一次运行留下的记录，经审阅和 reflect，变成技能修改或结构化检查；recall 在下一次开工时把近期状态取回来。

会话的暂停、接手与清理

三条互不相同的线：明确暂停 → 接手这一个会话；跨会话回顾近期工作（recall）；清理磁盘（worktree-cleanup）。

23 条原则，以及谁点名引用它

行是原则（按它约束的工作阶段分组），列是点名引用它的 playbook 或技能。圆点越多，这条原则越贯穿全流程。点原则名在全景网里定位。

谁用什么模型

默认值来自 setup-pstack 写的规则模板；人可以在 pstack-models.mdc 里改。panel 表示一个角色同时派三个不同模型。

容易混的成对组件

名字或用途相近，一句话分清。
