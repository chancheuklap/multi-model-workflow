# 界面验收设计的设计意图（从主人在整段对话里的原话整理）

## 要解决的问题

1. 主人在 Claude Design 里设计产品的 UI/UX，把设计拉回仓库，再通过 map 和 grilling 和 agent 讨论定稿。要的是一套工具：能被不同的 agent 在不同的时候使用，保证落地的产品和设计一致。范围是自动化的 UI/UX 验收，甚至是产品验收。
2. 做法的顺序：以 pstack 的 verify 系统（create-/maintain-verification-skill、verify-<产品>、feature map）为底座，引入 e2e（tester-army/e2e）加强它，再和 mmw v4 已有的工作流接起来，最后按 agentflow、ERP 两个仓库的实际情况调整。
3. 一直没解决的核心问题：一个项目已经设计好、还没有落地时，它的验收怎么提前准备好。
4. 项目不会只设计一次、落地一次：设计会更新，产品会改，要有维护和更新的路径。
5. agentflow 是多产品 monorepo：不能写死一个 app，每个产品一个 verify 技能。桌面产品（parrot、hedgehog）也必须能排进夜里真测；不排进夜里，v4 做出来就没有用。

## 主人定死的规矩（方案不越过）

- mmw v4 是技能集合，agent 通过被点名来调用技能。不能像 pstack 那样靠 agent 自觉触发 verify；需要它的步骤明确写出来。
- e2e test 和仓库其他测试不一样：不进 TESTING.md、scripts/check、spec 的 Testing Decisions、票的 Seam；不归开夜流程管，不由 worker 生产，也不由 reviewer 判对错。
- verify-<产品> 和 e2e test 在开夜前生成并提交：现有功能照已有代码写，新项目、新功能照 Claude Design 的设计包写。夜里只读。
- 「去掉 pending」这一步的答案是 `verify-ticket.py --closeout`，不新发明机制。
- 不新增 verifier。worker 写完代码自己跑验收直到通过，然后只 review 一次、返工一次，不允许两个 agent 来回返工。
- 验收用的 e2e test 只用固定步骤。
- 不碰生产；本地测试只用假账号、测试账号。
- 不录像；完全不用 bug bash。
- 维护只在主人要求时做。
- 给仓库接上这个系统是 setup-mmw 的工作，不另起流程。
- 不设测试耗时的硬上限；不反复跑测试，不动不动跑全量。
- 单张票（One ticket）和开夜（Run a night）的验收要一致，不设计成两套。
- v4 删掉的东西不加回来。
- 新方案落地后，项目仓库里旧流水线留下的东西全部删掉、重新 setup，不兼容它们。
- verify-<产品> 和它的 feature map 一旦生成，就必须被充分利用：每一部分都要有具体步骤读它，该读它的步骤都要读；没有人读的部分就不该生成。同时不让 agent 读得过多：每一步只读它要的那一部分。
- 测试账号、测试许可证、本地测试服务器和数据库、PC 测试机都是测试资源，哪里需要就在哪里用；外部收费 API 照调。唯一禁区是生产服务器（ssh 读也算）和主分支代码。本机的数据库、服务器、应用实例每个任务单独一套、互不干扰，设一个合理的上限控制并发。
- `.mmw/target.json` 在 v4 已拿掉，不加回来；它原来负责的事由 verify-<产品>、e2e、scripts/check 和仓库目录结构接住。

## 设计包的地位

- 设计包是主人在 Claude Design 里定稿、拉进仓库 `design/<产品>/` 的页面，是界面的标准答案：屏幕长什么样、写什么字、怎么交互。
- 设计包里的数据是假的，只用来画图。数据长什么样，由数据库表和代码决定，写在 spec 里。
- 主人在 Claude Design 里当场做的决定，由那边的 agent 临时记下，拉取设计包时由本地 agent 按固定步骤登记回特定的地方。不一定登记回 spec，因为设计一般在 map 阶段，那时 spec 还没有。
- Claude Design 不支持自定义技能：给那边 agent 的工作要求靠上传的 `CLAUDE.md`，设计规范（design system）是 Claude Design 自带的东西。
- v3 的三个设计 playbook 应该是一个三合一的技能（design-pages 的 A、B、C 三段）；重组时要读原文、按技能的思路重组，不能盲目照抄。
- 主人更新设计包后，不需要重跑 setup-mmw；要说清楚之后谁在哪一步更新 e2e test 和 verify-<产品>。

## 已经否决的（不要再提回来）

- v2/v3 的界面验收那一套：screen contract、`data-ui` 和 `ui-ids.md`、`state-list.md`、逐元素比对、拉取报告。正常的 Claude Design 代码里没有 design system 类名、`data-ui` id、每个状态的数据，那些是按 v2 工作流写出来的。
- 新增 verifier；让 reviewer 的 Tests 轴去管界面验收；测试去测确切值的垃圾测试。
- 录像；bug bash；e2e 的额外订阅服务（e2e 是本地套件，用现有 agent 跑）。
- 「种子数据」那一套：专门的种数据命令、每张票一份数据文件、CHECK 里灌数据的空位、前置重构票、返回内容文件。主人的判断是「设计又变得越来越复杂了」；改成测试自己通过产品入口建数据。
- 「真实路径测试」这类和 e2e test 并列的第二套测试。
- 夜里截住产品发给后台的请求、换成设计包里的假数据。
- 把白天的事（To spec、To tickets）画进夜里。

## 从技能合集的角度，主人一直强调的

- 每一步放在哪个组件（技能、playbook、参考文件、脚本、mode），通过组件里的哪一步或哪个命令串起来，输入什么、输出什么，谁在哪一步读写什么、格式是什么，都要设计清楚。
- 找最短路径、最优解；不照搬 v2、v3、pstack、e2e 任何一方，从设计意图出发重新设计。
- 不过度设计、不过度防御、不重复、不冗余；一个东西只负责一件事；每个字都是 token。
- mode 只点名；规矩写在动手的 agent 当时读的那一行；能用机制（脚本、检查、`.gitignore`）解决的，不写成文字规矩。
- 用已有的术语，不造词，不用指代。
- 只改本仓库；`~/agentflow`、`~/ERP` 只读。
