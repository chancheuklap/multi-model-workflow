MMW v2 · landing pipeline · 2026-09-01

MMW v2 landing pipeline 蓝图

一张票从 spec 到关票要走 14 步。每一步在这页上都是一张图；图里出现的每样东西按它的机制画：技能、脚本、hook、subagent、会话、票、评论、label、文档、外部系统——十种，各一种固定画法，下面十张小卡是全页的图例。图里的 Sn 是本页的步号：一张票从开工到关票经过 S5 到 S12，白天与早上各占两头。

词汇全部取自根 CONTEXT.md（一个概念一个英文正名）。这页只说 landing pipeline 现在是什么样；每一句的出处是技能自己的正文（mmw-v2/skills/ 与 mmw-v2/upstream/skills/engineering/）、mmw-v2/merge-notes/ 里那份技能的逐段意图，以及 spec #105 的 Implementation Decisions。图的画法用 diagram-design 默认样式（paper #f5f5f5、ink #2d3142、accent #eb6c36），未按品牌定制。

技能 SKILL

多个 agent 复用的做法。白底、实线、名字用正体。

symlink 进 ~/.agents/skills 与 ~/.claude/skills 两处，都指向source directory；正文改完下一次调用即生效。脚本住在技能目录里，装了技能就是拿到脚本。

脚本与子命令 SCRIPT

固定操作，模型不逐步照做。白底、实线、名字用等宽字。

verify-ticket.py 五个子命令、dispatch.sh 四个子命令、board.py 四个形态、visual-parity.py、gate-check。

每个脚本都住在一个技能里（外框），由拿着那份技能的 agent 从它的 SKILL.md 就地解析——caller 只点技能名，不写安装路径。怎么走见下面那张图。

hook HOOK

host 强制，模型绕不过。橙色虚线边界。

两个：hook.py pretool 装五个 host、守 closeout；rule-at-moment.py 只装 Claude Code、把 ~/.claude/CLAUDE.md 的条目在动作那一刻送到模型眼前，不碰票。idle 而 phase 未到 closed/handoff 的 worker 由 board.py re-prompt（4b），不是 hook。

会话 SESSION

经 Herdr 起在自己 pane 里的 host 进程。灰底、实线。

main agent、worker（junior / senior）、reviewer。

subagent AGENT

在派它的会话里面跑，Herdr 看不见。灰底、虚线。

verifier、advisor、claim-checker；模型在 models.md，assembled subagent file 由 assemble.py 装出。

票与 spec TICKET

GitHub issue，唯一的事实与状态存放处。淡灰底、灰实线。

spec 是票的容器，不打状态 label。

ticket comment COMMENT

脚本或 agent 落到票上的一条评论，以 first line 为名。方角、first line 用等宽字。

NOT_READY: self-run reverify VERDICT REVIEW ALL MET HANDOFF REQUIRED。

label LABEL

只表达票在哪个 queue。小方片。

五个：needs-triage needs-info ready-for-agent ready-for-human wontfix。

文档 DOC

事实，只给指针不抄写。折角页。

CONTEXT.md、models.md、AGENTS.md、ADR、handoff package。

外部系统 EXT

landing pipeline 用而不改的东西。极淡底、淡边。

Herdr、GitHub 网页、Claude Design。

1 全局：一天三段共 14 步

全天只有一个 main agent（Claude Code 会话）：白天与你讨论、出 spec、出票；晚上敲一条 dispatch.sh run <spec> 开起 board.py，紧接着敲一次 dispatch.sh advance <spec> 派出第一批；此后每次 board.py 发来一行 mmw board: ADVANCE 就再敲一次 advance。派发权在 main agent 手上，board 只做 repair：re-prompt idle 而 phase 未到 closed/handoff 的会话、关掉 form、redispatch 死掉的会话、到上限 hand back 到 needs-triage、写 NIGHT SUMMARY（4b）。你只讨论、拍板、改 models.md、早上看网页。图里只画一张票的路径。

2 白天：出票前（S1 → S4）

主线走 to-spec；只有含 UI acceptance criterion 的票才走下面那条支线，它的产出（下载回来的 handoff package）和 spec 一起喂进 to-tickets。

4 夜间总览：一张票从开工到关票（S5 → S12）

worker 永远是 main agent 经 Herdr 派出的会话，跑同一份 implement；main agent 派完只读票。两张图看同一段的两个面：图 4 是谁做什么、什么落到票上，图 5 是三个关卡与三个循环。

4b night：票与票之间，会话停下之后

图 4、图 5 画的是一张in-ticket部；这一节画票与票之间和会话停下之后。两个角色分工：派发归 main agent——它敲 dispatch.sh advance <spec>，那一条命令先把关掉的票的分支按关闭时间并回来，再把 frontier 上的票逐张派出去；repair 归 board.py——它在 monitor tab 里常驻，每次 pane 事件或每 SNAPSHOT_INTERVAL 做一轮 wakeup loop，并在 frontier 变了时发一行 mmw board: ADVANCE 给 mmw-main。判据是「repair 归 board，下一步归 main agent」：一次 repair 把已经派出去的会话扶回原位，一次派发决定下一张票从哪个 HEAD 切分支。三张图：图 4b 是一夜的分工，图 4c 是派发那一半——一条 issue-<n> 分支从切出去到并回来，图 4d 是 repair 那一半——一条会话停下之后怎么被扶回原路。方案全文 #105，词汇见 CONTEXT.md 的 Dispatch 节。

re-prompt 谁发什么为什么
idle 而 phase 未到 closed/handoff、或关掉 form 之后的 workercontinue会话还活着，还握着它在读的技能与它在做的票；停在哪一步由票上的 self-run / VERDICT / REVIEW 评论与 phase 写着。implement 收尾段有一句「票上已有这些评论的，从最新那条之后续」（merge-notes/implement.md「Closeout: resume after a re-prompt」）
关掉 form 之后的 reviewercontinue同一套动作；到 WAKE_LIMIT 就停手，不碰票
main agent（mmw-main）mmw board: <case> #<n> — run <命令>五个 <case>：ADVANCE 与 night over 结尾是 dispatch.sh advance <spec>，因为两者都留着要并的分支；WAKEUP LIMIT / REDISPATCHED / TIME LIMIT 结尾是 board.py --once <spec>，board 已经评论并换过 label，main agent 读一眼、不动手
常量（board.py 顶部）值依据
COOLDOWN_SECONDS120host 回合间隙的 idle 常见于几十秒内
WAKE_BACKOFF · WAKE_LIMIT120 → 240 → 480 s · 3 / 会话递增有上限；3 与 three-round cap 同档
REDISPATCH_LIMIT1 / 票第二次死交 /triage 判
MAX_HOURS4 / 票只 hand back 到 needs-triage，不杀会话
SNAPSHOT_INTERVAL60 s事件丢了一分钟内补上；不持状态所以重连无损
TOKEN_TTL_MS86400000（一天）一夜的运行不该活得比它自己的元数据久

没有并行上限：派发不再归 board，PARALLEL 常量与 --parallel 参数一并退场。一次跑几张票由 main agent 敲 advance 时决定，而 --lint 已经保证同一 frontier 上的票 ## Owns 不相交。

一个 board 管谁怎么划的
会话只收 workspace_id 与自己 HERDR_WORKSPACE_ID 相同的；读不到自己的 workspace 时全部收进来，那是单 board 的情形
Herdr 名字三种名字都带 workspace id 小写前缀：w2q-issue-61、w2q-issue-61-review、w2q-mmw-main。Herdr 的 agent 名字在全服务器的活 agent 之间唯一，两个仓库各有一张 #100 会撞车。git 分支名仍是 issue-61——前缀是 Herdr 的名字，不是分支名
monitor tabdispatch.sh run 开在敲它的那个 workspace 里，tab 标题 mmw board #<spec>；每个 workspace 一个，几个项目可以同一夜各跑各的

S5 · 派发：dispatch.sh <n> <role>

caller 只给ticket number与角色（junior-worker / senior-worker / reviewer）；票上没有一个字说这张票该给哪一档 worker。开 worktree 与 Herdr 那一串固定操作全在脚本里；每个 agent 的 host、模型、effort、launch arguments 只在 models.md 一处。夜里这条命令由 main agent 的 dispatch.sh advance 逐张调（4b）。

S6 · 开工：--preflight 守卫，然后读入

worker 在票上动任何东西之前先跑守卫；六项全过才 claim。被拒时脚本自己把 NOT_READY: 评论到票上——否则早上看这张票和从没派过一样。

S7 · writing rules：contract、不问、两档

implement 的 While writing code 段共八条，放在「state the seam」之后、Use /tdd 之前。措辞全是动作加票上的字段，不写原则散文。三栏各管一种自我发挥。

S8 · self-run：verify-ticket.py <n>

票是唯一的状态。每次运行都从票上重新取标准，交给 vendor 来的 gate-check 跑，把更新后的 ledger 贴回票上一条 self-run 评论。

S9 · verifier：只收ticket number，只写一行

在 code-review 之前跑。由 worker 会话派出，提示词只有 verify #<n>；四步的顺序、可动环境的边界、那一行怎么写，全在 mmw-v2/agents/verifier/body.md，不由 worker 转述。

S10 · code-review：一轮，不复审

worker 用同一条 dispatch.sh 起 reviewer session；code-review 的 SKILL.md 是 dispatcher 那一份，它起三个子代理，把三份报告写成票上一条 REVIEW 评论。三个子代理跑在 reviewer session所在 host 的默认子代理模型上，models.md 里没有它们的行。Spec axis读票 ## Read first 里标为 baseline 的条目，diff 偏离 baseline 算它的 Built wrong 一类；handoff package 是唯一不打开的那件，由 visual-parity 判。裁决不在这里：一轮上限与修哪些写在 implement 收尾段。

S11 · Audit 与 closing comment 草稿

草稿先写到文件，由 S12 的脚本核过再贴。图里每一层是草稿的一段；右侧写谁填它、--closeout 核它什么。

S12 · --closeout closeout 与 hook 兜底

landing pipeline 上唯一能关票或换 label 的地方。绕过它的命令被 host hook 拒绝，拒绝话里指回 --closeout。

5 三种「做不下去」：只有两种让票停下

标准层三个 kind，每一个机器都据它做不同的事：failed 是跑了没过，stuck 是跑不起来，两者都不看轮次；decision 不挡关票。

6 label 状态机：五个 label 只表达「在哪个 queue」

一个新 label 都不加；spec 不打状态 label；bug / enhancement 只属于外来件。每条迁移都写着是谁做的。

7 早上：人接手（S13 → S14）

一页看完。票都是 spec 的原生 sub-issue，面板本身回答「夜里关了哪些、新开了哪些、还卡着哪些」；label 维度用两个书签补上。凡是「你检查」的制品都在 GitHub 网页上打得开。

8 词汇指针：这页用到的词在 CONTEXT.md 的哪一节

定义不在这里抄；根 CONTEXT.md 每一节对应 landing pipeline 的一段。凡是文件里出现的字面串只有一个名字，就是那个串；角色与做法只写英文正名。每个词条底下的 _Avoid_ 一行列的是它的死词——写文档或写票时撞上其中一个，换成正名。
