# mmw 该怎么组织：一场讨论的交接

2026-09-06 凌晨。这份文档只写一件事：**mmw 的技能结构该怎么改**，以及这场讨论已经走到哪、
哪些方案已经被证据否掉了。拿它继续讨论，不要重走已经走过的弯路。

仓库 `/Users/cheuklapchan/multi-model-workflow`，分支 `main`。

## 一、触发这场讨论的具体问题

一个 agent 要完成「给一个仓库接上验收流水线的两个判官」——产出 `.mmw/target.json`——
它需要的材料散在两个技能里：

- 九个问题与三份分产品答卷：`mmw-v2/skills/verify-ticket/references/targets/`
- 合同 `target` 段的格式：`mmw-v2/skills/align-screens/references/contract-format.md`

为此提出建一个新技能把人带过去。用户的反应是这场讨论的起点：

> 一个新技能如果本质上只是一份指向三个地方的目录，说明问题不在缺一个目录。

## 二、已经被否掉的方案，以及否掉它们的证据

新 agent 若重新提出下面任何一条，是在重走弯路。

### 方案 A：新建 `target-setup`，把三份分产品答卷搬进去

**先被一个理由否掉，那个理由后来查明不成立**：说每份 `screen-contract.yaml` 的
`target.adapter` 是字面路径、`align-screens/scripts/lint_contract.py:136` 按它做存在性检查，
搬走会让所有合同 lint 变红，属于跨仓库数据迁移。

反证成立：`screen_driver.py` 的 `adapter_for()` 按 `target.kind` 选适配器，**全文一次都没读过
`target.adapter`**；读它的只有 `lint_contract.py:132-136` 的存在性检查；磁盘上的合同只有一份。
所以那不是数据迁移。

**但方案 A 仍然被一个更强的理由否掉**：那三份文件是**驱动器代码的说明书**。
`electron.md:5` 直接点名 `ElectronAdapter`，`web.md:3-5` 点名 `WebAdapter`/`WebSpaAdapter`，
七问的每条答案都在描述那个类的行为；加一种新产品要同时加一份文件**和一个适配器类**。
把说明书搬到另一个技能，以后每改一次适配器就要跨两个技能改，**永久成本**；而「取材料跨技能」
是一次性的路径问题。

而且搬了也消不掉跨技能：合同格式仍在 `align-screens`。**一处交叉换成两处。**

### 方案 B：`advance` 在 `.mmw/target.json` 没有 `instance` 键时扣住整批

前提「没有 `instance` 则并发闸门整个不生效」**不成立**。`dispatch.sh:446` 每派一票就
`lease.py claim`，`lease.py` 的 `SLOTS`（默认 8）在第 9 个 claim 时拒绝。`instance` 缺席的含义是
「产品可隔离，机器上限说了算」，见 `dispatch.sh:232-243` 的注释，`CONTEXT.md` 的 **instance**
词条也写成可选。

（真正的缺陷只有一个，且与结构无关：`dispatch.sh:246` 的 `except Exception: print("")`
把 JSON 语法错误吞成「没声明」。）

### 方案 C：「九问没有任何时刻会被读到」

**不成立。** `mmw-v2/upstream/skills/engineering/to-tickets/SKILL.md` 的
`### 3. Draft vertical slices` 明写 contract ticket 交付 `.mmw/target.json` 并指向分产品文件；
`CONTEXT.md` 的 **contract ticket** 词条同；`screen_driver.py:281,1504` 在文件缺失时也会拒绝并指路。

真实的缺口窄得多：**那个指针指向分产品文件，而分产品文件只答七问**，所以做 contract ticket 的
worker 永远碰不到第 8 问（instance）和第 9 问（什么会离开这台机器）。

### 方案 D：把原则写进 `mmw-v2/AGENTS.md`

`mmw` 是技能的**源码仓库**；真正生效的是 `~/.agents/skills/<技能>` 这些指向
`mmw-v2/skills/<技能>` 的软链。写进仓库根 `AGENTS.md` 的东西**只有在 mmw 仓库里干活的 agent
读得到**。`AGENTS.md` 第 3 行本来就写着「仓库里的技能是交付物，不是你的工作指南」。

## 三、讨论目前的结论

来自 advisor 的独立判断（它读了全部提交与仓库自身的撰写原则）：

> **技能边界没划错，缺了一层。**

八个技能是按「agent 所处的时刻」划的——每份 `description` 都是 "Use when …"，host 据此在某个
时刻把它装进上下文。这个划法对，而且是 skill 这种交付物唯一说得通的划法：skill 是按时刻触发的
**路由单元**，不是代码模块。

`docs/adr/0003-no-plugin-packaging.md` 当年把交付面收成「技能 + subagent」两种，退掉了 CLI 与
runtime。于是所有**不属于任何时刻**的东西——驱动器和它的适配器类、租约、两个 hook、
gate-check——没地方去，全塞进 `verify-ticket`，别的技能再按相对路径伸手过去拿。

**三处硬耦合是证据，都只因为「这两个技能恰好装在一起」才成立**：

| 位置 | 伸手去拿什么 |
|---|---|
| `mmw-v2/skills/align-screens/scripts/extract_skeleton.py:47` | import `verify-ticket/scripts/screen_driver.py` |
| `mmw-v2/skills/dispatch/scripts/dispatch.sh:39` | 调 `verify-ticket/scripts/lease.py` |
| `mmw-v2/install.sh:376-377` | 从 `verify-ticket` 取 `hook.py`，从 `dispatch` 取 `turn.py` |

后果：`verify-ticket` 的 1574 行 `screen_driver.py` 与 `lease.py` 是全管线的共享库，却挂在一个
票工技能名下；`dispatch` 名下的 `turn.py` 是 host 生命周期 hook，与「派发」这个时刻无关，
只是无处可放。**「接判官要跨技能取材」是这一层缺位的下游症状**，不是独立问题。

### 建议的结构

**新增第三个交付面 `mmw-v2/runtime/`**，与技能同样用软链安装。放：`screen_driver.py`（含各适配器
类）、`lease.py`、`hook.py`、`turn.py`、`gate-check/`，以及跟着适配器类走的九问与三份分产品答卷。
各自的测试一起搬。

**技能仍按时刻切，六个边界都对**，加一个 `target-setup`——「让一个仓库能被判官驱动」是独立时刻，
每个仓库做一次，由 contract ticket 的工人做，不是拿着票跑判据的人。`verify-ticket` 瘦回票工该有
的样子，`turn.py` 从 `dispatch` 搬走。

**明确不做两件事，理由要一起带走**：

- 不拆 `verify-ticket` 的五个时刻（preflight / self-run / reverify / closeout / lint）。它们共用
  一份账本格式和一个脚本，工人与核验者必须读同一套规则，拆开会漂移。**它「大」是对的，
  大在基础设施才是错的。**
- 不把 `code-checkers` / `manage-agents-md` / `target-setup` 合并成一个「配仓库」技能。三者由不同
  的人在不同时刻触发，合并只是把路由再散一次。

### 两步，顺序不能倒

**第一步（收益最大、纯机械）**：建 `mmw-v2/runtime/`，搬那五样基础设施及其测试。连带改
`install.sh:376-383`、`dispatch.sh:39`、`extract_skeleton.py:47-49`、
`verify-ticket.py`/`wiring-check.py`/`visual-parity.py` 的 import、`CONTEXT.md` 里这些文件的
`_Home_`、各技能 `tests/run.sh` 的路径。**要写一份新 ADR 修正 `0003` 与 `0006` 的「两个交付面」**
（这是记录决定，不是请示，但按仓库规矩必须有）。
验收：各技能 `tests/run.sh` 全绿、`install.sh --check` 退 0、`dispatch.sh run` 的前置检查通过。

**第二步**：九问与三份答卷随驱动器进 runtime，`target.adapter` 降为可选并由 `kind` 推导，
新建 `target-setup`。连带改动：`screen_driver.py:9,281,1504`；`verify-ticket/SKILL.md:65,99`；
`verify-ticket/references/wiring-check.md:13`（相对链接，搬走即断）；`electron.md:4-5` 与
`chrome-extension.md:6-7` 的自引用；`align-screens/SKILL.md:18`、`contract-format.md:16,77`、
`lint_contract.py:134,136`；三个测试夹具 `test_screen_driver.py:42`、`test_screen_contract.py:39`、
`align-screens/tests/test_lint_contract.py:38,138`（第 38 行对真实 skills root 做存在性检查，
会真的失败）；`CONTEXT.md:697-737` 六处 `_Home_`；`mmw-v2/skills.txt`。
**最容易漏且代价最高的两处**：`mmw-v2/upstream/skills/engineering/to-tickets/SKILL.md:38` 与
`to-spec/SKILL.md:87` 在 subtree 里，改动会与上游产生合并冲突，按
`mmw-v2/merge-notes/README.md` 写 merge-note。

**顺序不能倒**：先有 runtime 层，`target-setup` 才有一个「不属于任何票工技能」的地方可指；
先建技能再搬文档，得到的就是第一节里那个被否掉的「目录技能」。

## 四、还没裁的一个矛盾（它决定第二步的内容）

`verify-ticket/references/targets/README.md` 说九问是**每一类产品**答的；
`CONTEXT.md` 的 **target** 词条说第 8、9 问是**每个仓库**在 `.mmw/target.json` 里答的。两者打架。

- 若按仓库答：三份分产品文件只答七问就是对的，「补齐」这件事不存在。
- 若分产品文件也要答：那是三段具体内容（Electron 的调试端口如何从 `MMW_PORT_BASE` 派生、
  chrome-extension 的 persistent context 目录怎么落到 `MMW_DATA_DIR` 等），不是机制问题。

**先裁这个，再做第二步。**

## 五、用户在这场讨论里立下的判据

新方案要拿这几条去检验，不是拿「看起来更整齐」去检验：

1. 技能是**交付物**，不是 mmw 仓库自己的工作指南。
2. 技能里每一个字都重要：**需要被读的，要在技能里安排好什么时候去读；不需要被读的，
   就不该写在技能里。**
3. 一道只会拒绝的闸门不是「教」。拒绝的出路必须是一个能直接执行的动作（例如「调用某技能」），
   不是「去读某文档」。
4. 不要修修补补，要最根本的最优解。
5. 文件只描述现状，不写自己的历史；事故经过属于提交信息。
