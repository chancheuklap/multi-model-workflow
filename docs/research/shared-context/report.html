Project Context 调研与 MMW 方案

2026-09-13 第二轮九份调研：Cursor、13 个商业产品、22 个开源实现、理论文章、Nowledge Mem、Factory Missions、BMAD 与 Anthropic、monomind/Devin/Augment、降返工专题

先读这里

  1. MMW 最强的地方不用改。九份调研里没有一个对象同时做到这几条：验收由命令判定且判官自带负对照、落地后在合并结果上重跑、票状态只由脚本写事件、agent 靠事件唤醒、合并前先查。Factory、BMAD、Anthropic、Copilot 在这几点上都比 MMW 松。
  2. 返工的主要入口里，MMW 有三处缝。①worker 发现 spec、基线或本票验收标准不成立时，contract 子票谁也不叫醒，同一 spec 小节下没开工的票照常派出，写错的 CHECK 由 worker 只在本票上改；②落地合并冲突变成 ticket.bounced 后当夜没人接手，要等早间 triage；③一夜里学到的操作性知识，同一夜别的 agent 读不到——写入大部分已由 Nowledge Mem 自动完成，缺的是按任务取回。
  3. Nowledge Mem 适合做经验库，不适合做账本。agent 用 nmem m add 写入后立即可检索；会话结束时插件自动采集，每个 space 有 Working Memory 在会话开头注入，所以跨夜的写与读它都已经在做。它做不到的是同一夜内按这张票检索：会话开头注入的内容不含检索结果。MMW 只补这一处，由 dispatch.sh start 起 worker 时查一次放进 prompt。票状态、唤醒、闸口仍然只在 tracker 事件里。
  4. 方案分三个阶段。阶段一优化现有流水线，不需要新基础设施：补上面前两处缝，让 main agent 当夜处理而不是登记后停下；取消作用过小的 verifier；发布前检查 spec 有没有被票完整覆盖、开工前先在基线上跑一遍验收。阶段二以 Nowledge Mem 自带机制为主做经验层，MMW 只补当夜检索。阶段三做跨夜复盘，把重复出现的问题变成检查或技能修改。
  5. 现在就有一个与方案无关的风险：你的 Nowledge Mem Working Memory 里 MMW 和客户产品的内容混在一起，会在任何仓库、任何 host 的会话开头注入，夜里的 worker 会话也已经被自动存进你的个人记忆库。第 9 节已定。

我自己回到 MMW 仓库核实过的推断（其余来自 subagent，报告里注明出处）：

  • 写错的验收标准由 worker 在本票上改：mmw-v2/skills/verify-ticket/references/running-criteria.md 写 "A wrong `CHECK` is fixed on the ticket: comment saying what is wrong with it, edit the criterion, run again." 这条改动只修本票；同一个错误如果来自 spec，或也写在兄弟票里，别处不会跟着改。有一个实例：MMW 仓库 #162（2026-09-06），verifier 判 AC1 failed 后，worker 没改代码，把 AC1 的 CHECK: 换成绕开失败的命令，自跑变绿，在同一个 commit 上关票；#205 之后关票检查会比对 verifier 那次运行的标准指纹，这条路在 verifier 之后已堵上，在 verifier 之前没有。
  • contract 子票不叫醒任何人：mmw-v2/skills/dispatch/scripts/relay.py 的 WAKES 表里 child.opened 只在 kind 为 fault 或 decision 时叫醒 main agent；how-it-works.md 的 Results, watches and wakes 一节写明 "A finding, a contract or a deferred child is written on its ticket and wakes nobody, by design"。
  • 五种子票在 agentflow 仓库的实际数量（按正文首行 "A `<kind>` child" 搜索，含已关闭）：finding 73、fault 5、contract 3、decision 2、deferred 2。三张 contract（#821、#828、#860）都是真实的基线问题：缺一条兼容下发路径、两份合同的到期锚点互相冲突、屏幕合同一行的 shows 抄错了对象。
  • 合并冲突的第一道处理已经在 worker 手里：implement/SKILL.md 收尾步骤第 1 条要求跑验收前先 dispatch.sh integrate <n> 把 origin/<base branch> 合进本票分支，冲突时报出是哪几张已落地的票，用 resolving-merge-conflicts 技能解决。所以落地时的 bounce 只发生在"worker 合入之后、本票落地之前，另一张票先落地"的那段时间里。bounce 之后 ticket.bounced 谁也不叫醒，当夜不再试（ADR 0023 的 Consequences）。
  • 两条规则打架：to-spec/SKILL.md 第 5 步要求 spec 修订后 "Tickets already cut from the section are checked against the new text and corrected"，docs/contexts/tickets/CONTEXT.md 的 ticket 条目写票正文 "not edited once the batch has been reported to the user as published"。
  • verifier 修环境的办法并非无处可写：mmw-v2/skills/verdict/SKILL.md 规定结论行第三段写 "What you repaired"，随 verifier.passed/verifier.failed 留在票上；只是没有别的票会读它。
  • 跨票协作已有一条：code-review/references/spec-reviewer.md 的 Read tickets already integrated into the base branch 从组合行为、契约一致、迁移完整、共享状态四个角度审已合入 base branch 的票。
  • ADR 0001（docs/adr/0001-tracker-repo-authority.md）：权威副本在"生产这份内容的那一侧"，另一侧是索引。它管的是票状态这类有程序读取的内容；经验没有程序读取、不进任何闸口，所以阶段二不套用它，agent 直接写 Nowledge Mem。

2取舍的标准：MMW 的设计意图

每条借鉴都先过这几条。不符合的，即使别家做得好也不搬；符合的，改成 MMW 自己的形状再用。

  1. 事实只由脚本写，模型打字不算（ADR 0019）。新机制产生的记录也要经脚本写成事件。
  2. tracker 是权威，别处是索引（ADR 0001）。任何外部系统只能是副本。
  3. 沉默不算通过（ADR 0008）。查不了要说查不了，不能读起来像"没问题"。
  4. agent 靠事件唤醒，不轮询；夜里没有时钟（ADR 0010、0017）。
  5. 写入单线程、验证独立：worker 一人写一张票，reviewer 是另起的会话，只报告不改。
  6. 回环有上限：一轮评审修复，失败交回人（implement/SKILL.md）。
  7. 技能文本对所有 host 一样，能力差异写成能力，不写 host 名。
  8. 并行换吞吐，冲突靠 ## Owns 与 blocking link 预防；worker 落地前先把 base branch 合进本票并解冲突，落地时仍冲突变 ticket.bounced（ADR 0023；1.3 改为当夜回到 worker 一次）。

4参考对象里值得学的

每个对象只写对 MMW 有用的部分，以及它比 MMW 弱的地方。

Factory Missions

和 MMW 最像的大任务编排：orchestrator 不写代码，每个 feature 一个全新上下文的 worker，每个里程碑结束自动插入两道验证。

  • 值得学：先写验收断言清单（validation-contract.md），经至少两轮对抗评审，再做"每条断言恰好被一个 feature 认领"的覆盖检查，然后才拆 feature。原文理由："If it had created the features first, the contract would be influenced by the implementation it had already planned." 真实 mission 里 96 条断言、0 条遗漏。
  • 值得学：验证者分两种。scrutiny 读 diff 与 worker 轨迹，只许直接写"事实性、低风险"的共享知识（命令、环境），对 AGENTS.md 与技能只能提建议；user-testing 黑盒跑跨 feature 的用户流程。
  • 值得学："已知的无关老问题"登记在固定小节，后续 worker 不重复排查。
  • 8 月新研究：验证者先建完成标准且对实现者保密，同一模型在 gdal 重写上行为一致性从 36% 到 90%，代价 14 倍花费。原话："The single agent didn't lack skill. It lacked a standard of completion."
  • 比 MMW 弱：验证结论由 LLM 读截图给出；交接记录是 worker 自述，7 份里 5 份没写 commit；需求变了但契约没跟着改时，validator 把正确的新实现判失败；validator 的系统性建议没人执行，连续两个里程碑重复出现；顶层串行，吞吐低。

BMAD-METHOD v6

  • 值得学：评审发现先核实再处置，结论只有 high / medium / low / false / maybe-false，判 false 必须写反驳，每条都进 Review Triage Log。
  • 值得学：spec 错误的处理。bad_spec 先记下哪些做对了（KEEP），回滚代码，改 spec 并写进 Spec Change Log，再重做；intent_gap（人批准的意图本身不完整）回滚后交人。
  • 值得学：retro 的规矩——每条发现必须有出处，否则丢弃；每条给两个处置："本例怎么办"和"怎样防下一次"；下一轮先按证据核上一轮的行动项落没落地；只提议不执行。
  • 值得学：一个只描述不提议的"意图对账"评审层：列出用户原话的几种合理读法、这次实现了哪种、用户期望的"表面"与测试观察的表面是否一致。
  • 比 MMW 弱：状态同时存在两处；评审强制报满 N 条发现（与 ADR 0012 记录的"每票约 3 条、循环不会自己停"冲突）；回环上限 5 轮。

Anthropic 工程文章

  • 值得学：写代码前 generator 与 evaluator 协商"完成的定义"（sprint contract）。MMW 已经做得更彻底（标准由别人事先写好、可执行、你批准），剩下可取的一半是"开工前确认标准在基线上是红的"。
  • 值得学：把 evaluator 调严的方法是读它的日志，找它"发现问题又说服自己放行"的例子，然后改提示词；一次只拿掉一个脚手架组件。
  • 值得学：会话开头先验证已有功能没坏，再做新的。

planning-with-files

它的价值主要是一个反例：同一作者早期的 planning-with-teams 让所有 agent 写同一组文件，后来自己退回到"只有 orchestrator 写计划，每个 worker 写自己的日志"，并写明原因："The later write silently discards the earlier one's work, and nothing notices." 另外两条值得记：注入给模型的只放结构化摘要、不放磁盘上的自由文本（防提示注入）；Stop 钩子阻止提前结束时有次数上限，且"上次阻止后没有进展就放行"。

monomind project-context

  • 值得学：采集与提升分两步。"Capture has to be cheap enough to happen during the work, or it does not happen at all." 是决策、经验还是无用，提升时再判断。
  • 值得学：证据写成 path@commit，用 git diff --quiet <commit> HEAD -- <path> 判断引用后文件变没变，变了就报 evidence-drift。"A link that still resolves proves the cited file exists, not that it still says what it said when it was cited."
  • 值得学：检索按"这次要改的文件"做路径前缀匹配，不用向量检索；超预算的条目列成链接而不丢弃。agent 不得批准自己提出的条目。
  • 局限：只有 3 颗星、作者自用，没有并发多 agent；价值在设计理由写得清楚。

Devin 与 Augment

  • Devin：Knowledge 按触发描述检索，没有版本、没有过期、写入时不查冲突；陈旧只能事后在 Session Insights 的 "Misleading Knowledge" 里发现，且只给建议。会话记录用了哪些知识条目（"Accessed Knowledge"），这点可审计性值得学。Cognition 2026-04 自己的结论："writes stay single-threaded and the additional agents contribute intelligence rather than actions"。
  • Augment：记忆加载时对照现状，有冲突就报出来，而不是过期删除。评审记忆在合并时从评审结果学习：明确的人工反馈直接生效，弱信号要重复出现才晋升；按改动路径加载，用来压低已知误报。进 AGENTS.md 的两条准入："undiscoverable"（读代码推不出）且 "universal"（每个任务都适用）。

降返工专题里的其他对象

  • GitHub Copilot Memory：每条记忆带 path:line 引用，使用前核对引用，核对不上就不用；投毒测试里 agent 会发现矛盾并改正记忆。注意核对是提示词驱动，不是脚本。
  • OpenAI：失败归因于环境而非模型——"what capability is missing, and how do we make it both legible and enforceable for the agent?"；lint 错误信息里直接写修复指令；"When Codex makes the same mistake twice, ask it for a retrospective and update AGENTS.md"。
  • Kiro：bug 类 spec 固定三段，第三段是"SHALL CONTINUE TO [现有行为]"，把防回归写成显式标准。
  • Claude Code agent teams：现行文档里 teammate 的计划已改为不经 lead 审阅自动批准——说明"LLM lead 审计划"的价值官方没有坚持。

space 与身份space 可设 strict / shared / all 检索模式；agent identity 通过 NMEM_AGENT_ID 选择，只决定 agent 级 rules 和默认 space，检索本身不按 agent 过滤。本机 spaces 未启用、只有 default 一个身份、51 条 rules 全是草稿每个客户仓库一个 strict space、一个共享的工具箱 space 可以做到隔离，需要你同意启用

已经在发生的事agentflow 仓库 issue-900 worktree 里的 worker 与 reviewer 会话已被自动存入你的记忆库；Working Memory 里 MMW 与客户监控产品的决策混在一起，每个会话开头都会注入客户上下文正在跨仓库、跨 host 流动，与方案无关，已定（第 9 节）

它该承担什么、不该承担什么

该承担：没人会写进票、但下一个 agent 很需要的东西——怎么起产品、哪个测试不稳、上次为什么失败、某个目录的已知坑、本仓库评审中反复出现的误报与真缺陷。

不该承担：票状态、认领、依赖、唤醒、## Owns 重叠检查、验收证据、spec、ADR、决策结论，以及任何闸口的通过条件。理由：这些都要求确定性或可审计的历史，而 Nowledge Mem 的检索是语义的、写入没有版本、后台会自动合并改写，且失败时静默。

位置的一句话表述：tracker 事件是账本，仓库文件是规章，Nowledge Mem 是经验库。经验不是票状态，直接写进 Nowledge Mem，不在票上留第二份。

6方案

三个阶段按"证据强、改动小、先堵漏"的顺序排。每项写明它解决的缝、做法、你在产品上会看到的变化、依据和风险。第 9 节列出由你定下的产品决定；其余是工程决定，按 MMW 惯例由我判断。所有新名字都是暂名，落地时按 CONTEXT-MAP.md 的词表规则定名。

阶段一 · 优化现有流水线 · 不需要新基础设施

当夜处理问题、取消 verifier、发布前查覆盖、开工前查基线

这一阶段的共同原则：worker 发现问题就正式交出去（开子票、或落地失败），main agent 被叫醒，能引用已写下的依据的就当夜解决并恢复派发；引用不到依据时，才真正停掉相关的票等你。

先把层次说清楚

worker 照着做的东西是一条从上到下派生的链。错可能出在任何一层，改要改在出错的那一层，再把下游派生出来的一起改掉：

层写在哪里面有什么
基线ADR、决策票的结论、交接包、屏幕合同、领域文档已经定下的结论；票的 ## Read first 逐行列出并标明是基线
spec一个 mmw:spec issue## Implementation Decisions、## Testing Decisions 等小节；没有验收标准
票spec 下的子 issue## Parent 指回 spec 小节；## What to build、## Owns；## Acceptance criteria 里一条条验收标准，每条由 CHECK:（要跑的命令）、EXPECT:（输出必须出现的文字）、EVIDENCE: 组成

1.1照做的东西不成立：contract 叫醒 main agent，改在出错的那一层已定：第 9 节

缝
两处。worker 发现基线或 spec 不成立时开 contract 子票后继续做，谁也不被叫醒（relay.py 的 WAKES 只对 fault、decision 叫醒），同一小节还没开工的票照常派出，基于同一个错误写代码。发现本票的 CHECK 写错时，running-criteria.md 让 worker 在本票上直接改，同一个错误若来自 spec 或也在兄弟票里，别处不跟着改。
做法
这两种合成一条路：worker 开 contract，写明哪一处不成立、它认为应该是什么，照常做不受影响的部分。relay 的 WAKES 表里 child.opened 的叫醒种类加上 contract。main agent 被叫醒后顺着链往上找出错的那一层，然后二选一：
  • 能引用已写下的依据 → 自己改。依据是比出错处权威更高或更具体的文件、仓库规则（如 AGENTS.md），或基线当初照抄的实物（交接包、已上线的代码）。改出错的那一层：tracker 上的 spec、决策票、票正文与验收标准直接编辑（GitHub 保留编辑历史）；仓库里的基线文件经一个新的 dispatch.sh 命令在 merge-<branch> worktree 提交并 fast-forward 推到 origin/<base branch>，与落地同一把锁。再改从它派生、还没落地的票。关子票时写明依据是哪份文件、改了哪些地方，然后 resume 受影响的 worker，照常 advance。main agent 每次被叫醒是先处理再跑 advance，改好之前不会有同小节的新票派出。
  • 引用不到 → 停下等你。三种情况：没有任何文件说过怎么办；修法会推翻你做过的决定（决策票结论、ADR、spec 的 User Stories 与 Out of Scope）；需要 spec 范围之外的新工作。把同小节未开工的票从 ready-for-agent 移到 needs-triage，开一张 decision 写明选项与推荐，已开工的照常。NIGHT SUMMARY 列出被停的票。
要先补的一张表
MMW 现在没有写下"依据互相冲突时谁优先"，只有"交接包管外观、屏幕合同管行为"这一条分工（docs/contexts/tickets/CONTEXT.md 的 contract 条目）。草案：你的决策票与 ADR > spec > 交接包或屏幕合同（各管各的领域）> 领域文档 > 票正文。
拿实例试
agentflow 的三张 contract：#860 屏幕合同四行 shows 抄错，交接包与代码一致——能引用交接包，自己改。#828 票与 #587 要求的到期起算时刻和领域文档冲突——按草案"spec 优先于领域文档"能引用，自己改（当时的实际处理也是收窄领域文档）。#821 缺一条下发路径——修法方向能引用 AGENTS.md 的 "Contracts and evolution"，是否属于 spec 范围内的工作没有核对。
怎样观察到叫醒
每次叫醒 relay 在 ~/.mmw/state/<owner>__<name>/relay.log 写 queued <序号> #<n> child.opened for main <session> 与 delivered … 两行，main agent 的会话收到 #<n> child.opened。relay 测试套件加一个场景：五种子票各开一张，断言只有 contract、fault、decision 进队列。
顺带解决
running-criteria.md、to-spec 第 5 步、tickets/CONTEXT.md 三处关于"发布后票能不能改"的矛盾统一为：发布后 spec、票正文与验收标准只由 main agent 或你改。
风险
main agent 夜里改基线，等于在你不在时改设计意图。约束是每次必须点名依据；早上看子票关闭评论就能逐条核对，依据站不住的可以改回。

1.2五种子票各自的边界，写成一个判定顺序

缝
verify-ticket/references/sub-issues.md 的表写了每种记录什么，没有写"两种都像时选哪个"。1.1 让 contract 叫醒 main agent 之后，选错种类的代价变大。
做法
在那张表前加一个按顺序问的判定，第一个答"是"的就是种类，每种写一个"不是它"的例子：
顺序问种类不是它的例子
1流水线本身坏了吗——脚本、钩子、driver、.mmw/target.json？fault产品端口被旧进程占着，杀掉就能跑：这是环境，修掉并记一条经验（2.1）
2照做的东西不成立吗——## Read first 的基线、spec 小节、本票的验收标准缺状态、字段、情形，或互相矛盾？contract这些写得清楚，只是自己的实现没做对：本票里修
3它们都没说，而这是只有你能做的选择吗？decision（取默认继续）没说、但怎么做都不影响结果（内部命名、数据结构）：worker 自己定，写进 DECISIONS 评论
4评审报告指出的缺陷在本票 ## Owns 之外吗？finding在 Owns 之内：本票修
5Owns 之外有顺手想改、但验收不需要的地方吗？deferred不改就过不了验收：直接改，列在 Outside Owns
顺带
tickets/CONTEXT.md 的 contract 条目写进"spec 小节或本票验收标准不成立"两种情形。
实际数量
agentflow 已开的 85 张子票：finding 73、fault 5、contract 3、decision 2、deferred 2。落地后开始统计早间 triage 改种类的次数。

1.3落地冲突当夜回到这张票的 worker

缝
worker 跑验收前已用 dispatch.sh integrate <n> 合入 base branch 并解冲突；但在它合入之后、本票落地之前，另一张票可能先落地。这时 advance 合并失败，写 ticket.bounced，谁也不叫醒，票等到早上（ADR 0023）。
做法
relay 的 WAKES 加上 ticket.bounced，叫醒 main agent。main agent 用 start <n> worker 在保留的 worktree 起 worker，开场指令固定：再跑 integrate，冲突按 resolving-merge-conflicts 技能读两边的票与 spec 解决，重跑验收，关票；之后照常落地。每张票每夜只回一次，第二次 bounce 才交早间 triage。当夜重试时，bounce 不再把票移到 needs-triage、不释放认领。修订 ADR 0023 的 Consequences。
为什么是 worker 解
①两个并行 spec 各有自己的 main agent，每个只持有自己那一半的背景；worker 的 integrate 会报出冲突来自哪几张票，技能会去读它们，两边都拿得到。②解冲突写出新代码，要重跑本票标准，走 worker 路径自然有；ADR 0023 否决"main agent 当晚修"正是因为会绕过验证。③main agent 的上下文要撑一整夜。main agent 负责时机：被叫醒就立刻派回去。
你会看到
同文件的并行票不再过夜；NIGHT SUMMARY 的 Bounced: 行只剩第二次仍冲突的票。
代价
每次 bounce 多一次 worker 的花费。

1.4评审发现先核实再上报，处置逐条入账

缝
in-ticket 发现修没修、为什么不修，票上无法逐条对账；假发现会被照改，真发现会被略过。
做法
两处。reviewer 会话（code-review/references/session.md 第 3 步分拣之前）逐条打开发现所指的 file:line 核对，不成立的放进报告末尾的撤回列表，不进入 In-ticket / Out-of-ticket。worker 的关票草稿增加一节，每条 in-ticket 发现一行：fixed <commit> 或 refuted: <file:line 上实际发生什么>；--closeout 逐条核对都有一行；Spec 轴判为 should not 的不允许 refuted。
你会看到
每张票的评审结果可以一行一行追到代码提交或反驳理由；收口轮里被判 stale 的 finding 应该变少（现在 ADR 0012 记录约 24%）。
依据
BMAD Review Triage Log；Anthropic 要求附证明后实质评论从 16% 到 54%；Claude Code Code Review 与 Uber 的"先对照代码验证再上报"。
风险
核实本身也是 LLM 做，会误撤真问题。MMW 的 in-ticket 修复只有一轮，误报代价高，偏向精度是合适的。

1.5取消 verifier（先做）

现在的作用
mmw-v2/skills/verdict/SKILL.md：在 worker 的同一 worktree、同一 commit 上用 --reverify 把票上标准再跑一遍，发一行 VERDICT（怎么跑的、结果、修了环境里的什么）；不改文件、不加标准、不评代码。--closeout 要求 VERDICT 的 commit 等于 HEAD。
实际效果
relay 日志（2026-09-12 起）：agentflow 49 次、MMW 8 次 VERDICT，失败 0 次。worker 刚在同一 commit 上跑过同一组命令，那次运行本身由脚本记成事件，所以重跑几乎只能抓到环境差异。MMW #162 的 AC1 failed 是 worker 自跑已经看到的失败。
参考来源对照
设计来自 pstack（skills/poteto-mode/playbooks/autopilot-full.md）与 unlazy（--reverify）。pstack 的验证分三条线，在 MMW 里都已有人做：
  • 在要合并的 commit 上重跑检查——worker 自跑，由脚本记成 ticket.checked；夜后 main agent 的 reverify 再在合并结果上跑一遍。
  • 在真实界面上证明关键行为——MMW 的界面验收是 story-parity.py、boundary-check.py、journey.py 这些写在票上的标准，由 worker 在自跑里执行，判官自带负对照，结论由命令给出。它们的目的是让 worker 自己发现实现与设计的明显差别并修正：DIFF 行点名差在哪个节点，implement 收尾步骤第 1 条要求 worker 只修 DIFF 行点名的地方（drive-target/references/story-parity.md 的 Exit codes 一节）。
  • 不信 PR 描述，审证据与 diff——这是 reviewer 的三轴评审，一个独立会话，默认与 worker 不同模型家族；取消 verifier 不影响它。
pstack 自己在 playbooks/orchestrate.md 写道："A verifier agent whose entire product would be rerunning one command is ceremony, not verification."
做法
删除 verdict 技能；implement 去掉第 4 步与状态表里的 verifier 行；--closeout 的条件改为"脚本记录的 worker 自跑在 HEAD 上全部通过"；--verdict、dispatch.sh start … verifier、models.json 的 verifier 行、relay WAKES 里的 verifier.*、events.py 与任务板对这些事件的读取、docs/contexts 的词条一并删除；写一份 ADR 记录取消的理由。与本阶段其他项改同一批文件，放在最前面做。
剩下的风险
worker 在关票前改了 CHECK:，关票前没有第二个会话看到；夜后 reverify 跑的也是改过的标准。防线是 1.1 的规则（发布后只有 main agent 或你改标准）、GitHub 的正文编辑历史、以及复盘（3.1）列出关票前标准被改过的票。三者都能发现，不能阻止。

1.6spec 覆盖检查进 --lint

做法
verify-ticket.py <spec> --lint 新增两项：spec 的每个 Implementation Decisions 编号小节至少被一张票的 ## Parent 点名；Testing Decisions 的 How a test arrives at a state 下每个机制都被某张票的 ## Owns 覆盖（to-tickets 第 8 步现在是人工检查，改为机器）。未被认领的报 WARN 并点名小节号。
你会看到
发布时就知道 spec 里哪一条决定没有任何票去做，而不是验收时才发现少了一块。
依据
Factory 的覆盖检查（"Unclaimed assertions = planning gap"）；spec-kit analyze 的覆盖率。
后续
Factory 的做法是给每条行为断言编号并要求"恰好被一个 feature 认领"。先做小节级覆盖，看 retro 里"spec 有、票没做"的案例多不多，再决定要不要细到断言级。

1.7发布前一次只读的"找漏"会话

做法
to-tickets 第 6 步请你批准切分之前，起一个 host 原生 subagent（与 code review 的轴 subagent 同一做法，工作指引写成一份单独的 reference），只读 spec 与票草稿，找会改变交付内容的模糊、冲突与遗漏，最多 5 条，每条引用 spec 原句并带推荐选项，并入你已经在看的 Choices 行，不另开一轮对话。
依据
Factory 契约的对抗评审（"It is very likely that important assertions are missing, even if the contract looks good on the surface"）；Ambig-SWE（模型分不清规格是否完整）；spec-kit clarify 的"最多 5 题、带推荐"。
风险
过度规格化（Böckeler 批评小 bug 被扩成 16 条验收）。只收会改变交付的问题，其余照 implement "Put no question on the screen" 由 worker 取默认。

1.8认领后先在基线上跑一遍验收

做法
--preflight 认领成功后，在 worker.started 的 base commit 上把全部标准跑一遍，写一条 run 为 baseline 的 ticket.checked。没写代码就已经通过的标准，--closeout 要求草稿逐条说明：已被别的票做掉，还是这条 CHECK 测不到本票的行为（后者走 contract）。不阻止开工。
依据
Anthropic "run through a basic end-to-end test before implementing a new feature"；PLANS.md "the new test fails before the change and passes after"；MMW 的 boundary-check.py 已证明负对照可以机械化。
风险
开工变慢，带长 TIMEOUT: 的标准要跑两次，可以只对不需要产品槽位的标准做。测试文件还不存在时标准必然是红的，这种红不证明任何事，所以只对"基线已绿"下结论。更强的版本（worker 自跑时把本票新增的测试放到旧代码上跑、要求失败，即负对照）需要单独设计，放到这一项跑一段时间之后。

1.9批次级流程验收票（仅对能起整机的仓库）

做法
spec 声明跨票的用户流程时，to-tickets 切一张验收票，Blocked by 流程涉及的所有票，## Owns 只含 .mmw/journeys/<flow>/，标准是 journey.py run <flow>。它自然在最后被派出，由新 worker 在已合并的 base branch 上跑；失败走现有的 finding 路由。
依据
Factory user-testing validator 是发现问题最多的环节；SpecBench 的组合差距。
适用范围
需要 .mmw/target.json 能起整机并登录；MMW 自身这种没有界面的仓库不适用。
阶段二 · 共享经验层 · Nowledge Mem 自带机制优先

让每个 agent 开工时读到别的 agent 学到的东西

经验不是票状态：没有程序汇总它，也没有闸口依赖它，所以不经票事件，agent 直接写 Nowledge Mem。能交给 Nowledge Mem 自带机制的都交给它，MMW 只补它做不到的一处——同一夜内按票检索。下面的每个结论标明是本机实测、读源码确认，还是推断。

需要Nowledge Mem 现成的够不够MMW 要补的
agent 记一条nmem m add（可带标题、label、unit type、space、agent id），或 MCP memory_add；写入后立即可检索（服务端接口说明，搜索 0.52 秒为实测）够implement、verdict 技能文本各加一句何时记、怎么记
条目与会话记录落到本仓库space。2026-09-14 实测，spaces 已启用：设了 NMEM_SPACE 的 nmem m add 与 Claude Code、Codex、Grok、Pi 四个 host 的会话记录都落进指定 space，Default 检索不到；经 orca 交互启动（Claude Code、Codex、Grok）、经 paseo 启动（Claude Code、Codex）、直接命令行启动都一样。Cursor 未测够派发时给会话设 NMEM_SPACE、NMEM_AGENT_ID：orca 在启动行前加 exec env …、paseo 用 --env，两种都实测传进了会话
跨夜读到会话结束自动采集并蒸馏；每个 space 一份 Working Memory，会话开头由插件注入（Grok 不注入）够，蒸馏内容由模型决定不补
同一夜、按这张票读到没有。会话开头注入的 Context Bundle 不含检索结果；每回合只提示"主动去搜"不够dispatch.sh start 起 worker 时检索一次，结果写进开场 prompt（2.2）
reviewer 常驻的指南agent 级 rules，脚本可直接写成 active，按 NMEM_AGENT_ID 进入 bundle（读 CLI 帮助确认）够（Grok 除外）给 mmw-reviewer 维护一组 rules
reviewer 不读 worker 的经验检索不能按 agent 过滤不够，只能在 prompt 层做它们的开场 prompt 不放检索结果；它们自己去搜挡不住

2.1写：agent 直接写，会话落到本仓库

做法
implement 技能文本加一段：撞到别的票大概也会撞到的坑（不稳定的测试、工具的怪行为），或者为了让命令跑起来修过环境，就用 nmem m add 记一条，写事实、证据（命令与输出首行，或 path:line）、label 带上 ticket-<n> 与种类。不强制，关票时不查。space 不写进技能文本，由环境变量决定。
派发时设环境变量
runner adapter 起会话时设 NMEM_SPACE=<owner>__<name> 与 NMEM_AGENT_ID=mmw-<角色>。paseo 有 --env；orca 的启动行是 shell 执行的 exec <launch line>，前面加 env。这样 agent 的 nmem m add 与插件的会话采集都落进本仓库 space。
实测
2026-09-14 在一个临时 space 里验证（验证后已删除）：见上表"条目与会话记录落到本仓库"一行。另发现 NMEM_AGENT_ID 指向一个不存在的身份时，Nowledge Mem 会自动建一个同名身份，所以派发用的身份名要固定，不能每次生成。Cursor 本机 cursor-agent 未登录，没有测。
Nowledge Mem 不可达
nmem 报错，agent 照常继续；不影响任何闸口。

2.2读：跨夜交给 Nowledge Mem，当夜由派发脚本查一次

跨夜
不加代码。会话开头插件注入本仓库 space 的 Working Memory；worker 也可以按技能文本自己搜。
当夜
dispatch.sh start 起 worker 时，用本票标题与 ## Owns 路径跑一次 nmem --json m search … --space <repo> --time today，取前几条放进开场 prompt 的固定小节，失败时写"经验库未查询"。与 host 无关，估计几十行。
角色
reviewer 的开场 prompt 不放检索结果；它需要的常驻内容写成 mmw-reviewer 的 agent 级 active rules，由 bundle 注入。
过期
Nowledge Mem 有取代、弃用与矛盾检测，但不会比对代码是否变过。条目里写了 path:line 的，由读的 agent 自己核对。
依据
monomind 按文件路径取回；Cognition 与 LangChain：验证者用干净上下文；Nowledge Mem 各插件钩子源码。

2.3提升：重复才进规章已定：第 9 节

做法
收口轮里 main agent 检索今夜本仓库带 ticket- label 的条目，逐条三选一：留着（本来就在检索里，不用动）；提名进规章（同类出现两次以上，或一次就让票卡住的，提议写进 .mmw/target.json、仓库脚本、消费仓库 AGENTS.md 的 Gotchas、reviewer rules，或 MMW 技能文本）；弃用（用 Nowledge Mem 的 deprecate，写原因）。NIGHT SUMMARY 加一行计数。
谁批准
"进规章"会改变之后所有 agent 的行为，默认做成早上给你看的提案。
依据
Augment 与 OpenAI 的"同一错误两次再回写"；ETH 研究（上下文文件写多了有害，只放读代码推不出的）。
布局（第 9 节已定）：spaces 已于 2026-09-14 启用，目前只有 Default 一个 space，所以现有会话的行为不变。还要定的是布局：每个消费仓库一个 strict space，另建一个工具箱 space 共享给各仓库。现有 1883 条记忆留在 Default，不会自动迁移，仓库 space 起初是空的。
阶段三 · 跨夜学习

同一类失败出现第二次时，提议一条自动检查或一处技能修改

现在每夜结束，早间 triage 把被退回、bounce、子票逐张处理掉，处理完就结束了；同一个原因下一夜再出现，再逐张处理一次，没有谁去看"这是第几次"。例子：#748、#750、#751 三张票都因为改同一批文件而 bounce，每次都是单独处理。"改同一批文件的票要串行"这条结论最后记进了你的 Nowledge Mem，并开了 MMW #408，是人看出来的，不是流程自己数出来的。

夜后复盘（retro）做的就是"看第几次"：读完票事件，把失败按原因归类，某一类跨票或跨夜出现第二次，就开一张 issue，提议把它变成一条机器检查（例如 --lint 里多查一项）或一处技能文本修改，附上那几次的出处。它只提议，不改；你早上批准或拒绝。

3.1夜后复盘（retro）已定：第 9 节

做法
summary 之后跑，只用票事件与 git log 作证据，产出一条由脚本写成事件的 spec 评论：
  • 每条发现带事件或 commit 出处，无出处的丢弃；
  • 每条两个处置：本例怎么办（开票 / 接受）、怎样防下一次（改哪个技能的哪一节、加哪个检查、改哪条规章）；
  • 跨票或跨夜出现两次以上的同类问题（bounce 原因、HANDOFF REQUIRED 原因、finding 类别、同一环境问题被反复修）列成候选，属于工具箱的开到 MMW 仓库，属于消费仓库的开到该仓库；
  • 先核上一次 retro 的行动项，按证据写"已落地"或"没找到证据"；
  • 一节只描述不提议的意图对账：整批交付与 spec 的 Problem Statement、User Stories、Out of Scope 对一次，列出用户期望的表面与测试实际观察的表面是否一致；
  • 评审结果写成"本仓库评审指南"候选：同一路径被判 stale 两次的发现提名为已知误报，同类缺陷成立两次的提名为反模式或 lint 规则。
需要补的字段
review comment 的每条发现加一个类别字段（现在是自由文本，无法聚合）；route 的 stale 区分"本来就不成立"和"被别的票修掉了"。
是不是技能
MMW 现在没有复盘技能，mmw-v2/skills.txt 里也没有；这是新提议，落地时写成一个新技能加一个脚本命令。mattpocock 上游有一个 mmw-v2/upstream/skills/in-progress/retro/SKILL.md，上游 README 标注 "STUB: design notes only, not functional yet"，针对单个会话，把改进候选分成 Navigation、Automated checks、Coding standards、Global AGENTS.md、Tool economy、No-ops、Information access 七类；它的分类可以直接借用，对象从单个会话换成一夜的票事件。
依据
BMAD skills/bmad-retrospective（workflow.md、references/evidence-gathering.md、references/retro-document.md）的出处规则与双处置；OpenAI Codex best practices "When Codex makes the same mistake twice, ask it for a retrospective and update AGENTS.md"；Devin Session Insights 的事后归类；Anthropic "a discovered bug class never makes it back into CLAUDE.md … the whole structure degrades"；OpenAI "promote the rule into code"；Augment 评审记忆的强弱信号；ADR 0012 自己的数据（每票约 3 条发现、三代不降）。
风险
提议太多没人看。每次只列重复两次以上的，并跟踪上一次提议的落地率。

其他值得做的小项

  • worker 的回合结束守卫。现在 worker 过早结束回合，要等 watchdog 一小时沉默才发现。照 planning-with-files 的教训做：票上没有等待中的 reviewer/槽位、也没有结果事件时拦一次，有次数上限，自上次拦截后票上没有新事件就放行，理由用固定句子。
  • reviewer 与 worker 同一模型家族时，install.sh --check 给一行 WARN。Copilot Rubber Duck 与 Factory 都把"验证者用不同家族"作为默认；MMW 的 hosts.json 默认已经这样配，但没有检查。
  • bug 类票至少一条"现有行为保持"标准。来自 Kiro bugfix spec 的 "SHALL CONTINUE TO"。

7不采纳的做法

做法来源不采纳的理由
顶层全串行Factory并行本来就会冲突，冲突由有背景资料的 worker 在落地前 integrate 时解决，落地时再冲突当夜回到 worker（1.3）；串行换来的是整夜吞吐下降
每批生成专用 worker 技能Factory技能是交付物、对所有 host 一样；实物显示 mission 专用技能会与仓库事实脱节
票级验收标准对 worker 保密Factory 8 月研究MMW 的 CHECK 是精确规格而非稀疏抽样，worker 需要自测；只在 1.9 的流程验收票上可以试"持有者不是实现者"
验证失败自动修到收敛Factory、BMADMMW 的一轮上限是有意防止无限循环；Factory 修复占实现量 34%、首轮从不通过
评审强制报满 N 条BMAD与 ADR 0012 的数据冲突，会放大子票膨胀
共写一个共享笔记文件Cursor 默认、planning-with-teams并行分支改同一文件会 bounce；同作者已退回单写者；LLM 整体重写会塌缩
把项目上下文整份注入每个会话Cline memory bankETH 研究：上下文文件平均降低成功率、成本升 20% 以上；MMW 按票收窄读取范围。Nowledge Mem 注入的 Working Memory 是每个 space 一份、上限 4 KB 的简报，不在此列
Nowledge Mem 承载状态、唤醒或闸口—检索语义化、无版本、后台改写、失败静默，违反 ADR 0001、0008、0019
从一次纠正自动保存用户偏好Cursor、DevinCursor 自己禁止 worker 保存偏好；一次性意见固化为全局规则是污染
reviewer 读 worker 的完整会话记录Factory scrutiny上下文暴涨、各 host 记录格式不同；先观察 1.4 与 3.1 的效果

8怎么判断有没有用

两篇 2026 研究表明上下文文件主要省时间、不直接提高正确率，所以每一项都用它针对的那个成本来衡量，不笼统看通过率。这些数都能从票事件与 git 里算出来，放进 3.1 的复盘。

项看什么方向

9决定

已经定了的（来自你在本页的评论与对话）

  • 验收标准不用脚本锁定。发布后 spec、票正文与验收标准只由 main agent 或你改；worker 发现照做的东西不成立，一律开 contract（1.1）。
  • main agent 有权当夜修改出错的那一层并恢复派发，只在需要你选择时才停掉后续的票（1.1）；五种子票的边界要写清（1.2）。
  • 不做并行 spec 之间的 ## Owns 重叠检查；落地冲突当夜交回这张票的 worker，每票每夜一次，修订 ADR 0023（1.3）。
  • 取消 verifier（1.5）：它的三条验证线在 MMW 里已由 worker 自跑、界面判官与 reviewer 承担；接受"关票前改标准无人拦"的剩余风险。
  • 阶段一与原阶段三合并为"优化现有流水线"。
  • 经验不经票事件，agent 直接写 Nowledge Mem；能用 Nowledge Mem 自带机制的不另写代码（阶段二）。

第 9 节原待定四条，按推荐定案

  • main agent 能否当夜改基线：能引用一份已写下的依据就自己改，并在子票里点名依据；引用不到、会推翻你做过的决定、或需要 spec 范围外的新工作，就停下等你。依据冲突时的优先顺序：你的决策票与 ADR > spec > 交接包或屏幕合同（各管各的领域）> 领域文档 > 票正文（1.1）。
  • Nowledge Mem 布局：spaces 已启用；每个客户仓库一个互不可见的 strict space，另建一个共享的工具箱 space；夜里流水线会话的采集与条目进仓库 space，不进你的个人 Default；你自己的会话保持现状（阶段二）。
  • 复盘：每夜收尾自动跑；它开出的工具箱 issue 先进 needs-triage（3.1）。
  • 经验进规章：夜里只出提案，早上由你批准（2.3）。
  • 发布前找漏（1.7）用 host 原生 subagent，和 code review 的轴 subagent 一样，工作指引单独写成一份 reference。
