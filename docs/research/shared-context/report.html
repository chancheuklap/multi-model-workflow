Project Context 调研与 MMW 方案

2026-09-13 第二轮九份调研：Cursor、13 个商业产品、22 个开源实现、理论文章、Nowledge Mem、Factory Missions、BMAD 与 Anthropic、monomind/Devin/Augment、降返工专题

先读这里

  1. MMW 最强的地方不用改。九份调研里没有一个对象同时做到这几条：验收由命令判定、独立 verifier 在同一 commit 重跑、票状态只由脚本写事件、agent 靠事件唤醒、合并前先查。Factory、BMAD、Anthropic、Copilot 在这几点上都比 MMW 松。
  2. 返工的主要入口有四个，MMW 各有一处缝。①验收标准在 verifier 开跑之前可以被 worker 改弱，关票门不会发现；②worker 发现 spec 或基线错了（contract 子票）谁也不叫醒，同一 spec 小节下没开工的票照常派出；③并行的 spec 之间没有 ## Owns 重叠检查；④一夜里学到的操作性知识没有地方沉淀，别的 worker 读不到。
  3. Nowledge Mem 适合做"经验索引"，不适合做"账本"。显式写入后 0.5 秒可检索，能按仓库、类型、metadata 过滤，有 space 做客户隔离；但会话开始时自动注入的内容不含按任务检索的结果，五个 host 的接入各不一样，自动蒸馏要排队几十分钟。所以"读"要做完整，得由 dispatch.sh 在派发时替每个 agent 查好、写进 prompt；事实本身仍记在 tracker 事件里，Nowledge Mem 是它的检索副本。
  4. 方案分四个阶段。阶段一补上面前三处缝，不需要新基础设施；阶段二用 Nowledge Mem 做跨 agent、跨 spec、跨夜、跨仓库的经验层；阶段三在发布前检查 spec 有没有被票完整覆盖、开工前先在基线上跑一遍验收；阶段四做跨夜 retro，把重复出现的问题变成检查或技能修改。
  5. 现在就有一个与方案无关的风险：你的 Nowledge Mem Working Memory 里 MMW 和客户产品的内容混在一起，会在任何仓库、任何 host 的会话开头注入，夜里的 worker 会话也已经被自动存进你的个人记忆库。第 9 节第 3 条请你定。

我自己回到 MMW 仓库核实过的推断（其余来自 subagent，报告里注明出处）：

  • worker 可以改验收标准：mmw-v2/skills/verify-ticket/references/running-criteria.md 写 "A wrong `CHECK` is fixed on the ticket: comment saying what is wrong with it, edit the criterion, run again."；verify-ticket.py 的关票检查只比对 verifier 那次运行的标准指纹与票上当前标准是否一致（shape_digest），指纹只在每次 ticket.checked 时记录，发布时不记录。
  • contract 子票不叫醒任何人：mmw-v2/skills/dispatch/references/how-it-works.md 的 Results, watches and wakes 一节。
  • 两条规则打架：to-spec/SKILL.md 第 5 步要求 spec 修订后 "Tickets already cut from the section are checked against the new text and corrected"，docs/contexts/tickets/CONTEXT.md 的 ticket 条目写票正文 "not edited once the batch has been reported to the user as published"。
  • 没有跨 spec 的 ## Owns 重叠检查：relay.py 的 overlap() 只比较票号；dispatch/scripts/ 与 status.py 里没有读 ## Owns 做比较的代码；verify-ticket.py 的 --touched 只取同一 spec 的子票（open_children_owns(spec)）。
  • verifier 修环境的办法并非无处可写：mmw-v2/skills/verdict/SKILL.md 规定结论行第三段写 "What you repaired"，随 verifier.passed/verifier.failed 留在票上；只是没有别的票会读它。
  • 跨票协作已有一条：code-review/references/spec-reviewer.md 的 Read tickets already integrated into the base branch 从组合行为、契约一致、迁移完整、共享状态四个角度审已合入 base branch 的票。
  • ADR 0001（docs/adr/0001-tracker-repo-authority.md）：权威副本在"生产这份内容的那一侧"，另一侧是索引。这决定了阶段二里 Nowledge Mem 的位置。

2取舍的标准：MMW 的设计意图

每条借鉴都先过这几条。不符合的，即使别家做得好也不搬；符合的，改成 MMW 自己的形状再用。

  1. 事实只由脚本写，模型打字不算（ADR 0019）。新机制产生的记录也要经脚本写成事件。
  2. tracker 是权威，别处是索引（ADR 0001）。任何外部系统只能是副本。
  3. 沉默不算通过（ADR 0008）。查不了要说查不了，不能读起来像"没问题"。
  4. agent 靠事件唤醒，不轮询；夜里没有时钟（ADR 0010、0017）。
  5. 写入单线程、验证独立：worker 一人写一张票，reviewer 和 verifier 是另起的会话，只报告不改。
  6. 回环有上限：一轮评审修复、一次 verifier，失败交回人（implement/SKILL.md 第 4 步）。
  7. 技能文本对所有 host 一样，能力差异写成能力，不写 host 名。
  8. 并行换吞吐，冲突靠 ## Owns 与 blocking link 预防，合并冲突变 ticket.bounced 交早间 triage（ADR 0023）。

4参考对象里值得学的

每个对象只写对 MMW 有用的部分，以及它比 MMW 弱的地方。

Factory Missions

和 MMW 最像的大任务编排：orchestrator 不写代码，每个 feature 一个全新上下文的 worker，每个里程碑结束自动插入两道验证。

  • 值得学：先写验收断言清单（validation-contract.md），经至少两轮对抗评审，再做"每条断言恰好被一个 feature 认领"的覆盖检查，然后才拆 feature。原文理由："If it had created the features first, the contract would be influenced by the implementation it had already planned." 真实 mission 里 96 条断言、0 条遗漏。
  • 值得学：验证者分两种。scrutiny 读 diff 与 worker 轨迹，只许直接写"事实性、低风险"的共享知识（命令、环境），对 AGENTS.md 与技能只能提建议；user-testing 黑盒跑跨 feature 的用户流程。
  • 值得学："已知的无关老问题"登记在固定小节，后续 worker 不重复排查。
  • 8 月新研究：验证者先建完成标准且对实现者保密，同一模型在 gdal 重写上行为一致性从 36% 到 90%，代价 14 倍花费。原话："The single agent didn't lack skill. It lacked a standard of completion."
  • 比 MMW 弱：验证结论由 LLM 读截图给出；交接记录是 worker 自述，7 份里 5 份没写 commit；需求变了但契约没跟着改时，validator 把正确的新实现判失败；validator 的系统性建议没人执行，连续两个里程碑重复出现；顶层串行，吞吐低。

BMAD-METHOD v6

  • 值得学：评审发现先核实再处置，结论只有 high / medium / low / false / maybe-false，判 false 必须写反驳，每条都进 Review Triage Log。
  • 值得学：spec 错误的处理。bad_spec 先记下哪些做对了（KEEP），回滚代码，改 spec 并写进 Spec Change Log，再重做；intent_gap（人批准的意图本身不完整）回滚后交人。
  • 值得学：retro 的规矩——每条发现必须有出处，否则丢弃；每条给两个处置："本例怎么办"和"怎样防下一次"；下一轮先按证据核上一轮的行动项落没落地；只提议不执行。
  • 值得学：一个只描述不提议的"意图对账"评审层：列出用户原话的几种合理读法、这次实现了哪种、用户期望的"表面"与测试观察的表面是否一致。
  • 比 MMW 弱：状态同时存在两处；评审强制报满 N 条发现（与 ADR 0012 记录的"每票约 3 条、循环不会自己停"冲突）；回环上限 5 轮。

Anthropic 工程文章

  • 值得学：写代码前 generator 与 evaluator 协商"完成的定义"（sprint contract）。MMW 已经做得更彻底（标准由别人事先写好、可执行、你批准），剩下可取的一半是"开工前确认标准在基线上是红的"。
  • 值得学：把 evaluator 调严的方法是读它的日志，找它"发现问题又说服自己放行"的例子，然后改提示词；一次只拿掉一个脚手架组件。
  • 值得学：会话开头先验证已有功能没坏，再做新的。

planning-with-files

它的价值主要是一个反例：同一作者早期的 planning-with-teams 让所有 agent 写同一组文件，后来自己退回到"只有 orchestrator 写计划，每个 worker 写自己的日志"，并写明原因："The later write silently discards the earlier one's work, and nothing notices." 另外两条值得记：注入给模型的只放结构化摘要、不放磁盘上的自由文本（防提示注入）；Stop 钩子阻止提前结束时有次数上限，且"上次阻止后没有进展就放行"。

monomind project-context

  • 值得学：采集与提升分两步。"Capture has to be cheap enough to happen during the work, or it does not happen at all." 是决策、经验还是无用，提升时再判断。
  • 值得学：证据写成 path@commit，用 git diff --quiet <commit> HEAD -- <path> 判断引用后文件变没变，变了就报 evidence-drift。"A link that still resolves proves the cited file exists, not that it still says what it said when it was cited."
  • 值得学：检索按"这次要改的文件"做路径前缀匹配，不用向量检索；超预算的条目列成链接而不丢弃。agent 不得批准自己提出的条目。
  • 局限：只有 3 颗星、作者自用，没有并发多 agent；价值在设计理由写得清楚。

Devin 与 Augment

  • Devin：Knowledge 按触发描述检索，没有版本、没有过期、写入时不查冲突；陈旧只能事后在 Session Insights 的 "Misleading Knowledge" 里发现，且只给建议。会话记录用了哪些知识条目（"Accessed Knowledge"），这点可审计性值得学。Cognition 2026-04 自己的结论："writes stay single-threaded and the additional agents contribute intelligence rather than actions"。
  • Augment：记忆加载时对照现状，有冲突就报出来，而不是过期删除。评审记忆在合并时从评审结果学习：明确的人工反馈直接生效，弱信号要重复出现才晋升；按改动路径加载，用来压低已知误报。进 AGENTS.md 的两条准入："undiscoverable"（读代码推不出）且 "universal"（每个任务都适用）。

降返工专题里的其他对象

  • GitHub Copilot Memory：每条记忆带 path:line 引用，使用前核对引用，核对不上就不用；投毒测试里 agent 会发现矛盾并改正记忆。注意核对是提示词驱动，不是脚本。
  • OpenAI：失败归因于环境而非模型——"what capability is missing, and how do we make it both legible and enforceable for the agent?"；lint 错误信息里直接写修复指令；"When Codex makes the same mistake twice, ask it for a retrospective and update AGENTS.md"。
  • Kiro：bug 类 spec 固定三段，第三段是"SHALL CONTINUE TO [现有行为]"，把防回归写成显式标准。
  • Claude Code agent teams：现行文档里 teammate 的计划已改为不经 lead 审阅自动批准——说明"LLM lead 审计划"的价值官方没有坚持。

它该承担什么、不该承担什么

该承担：没人会写进票、但下一个 agent 很需要的东西——怎么起产品、哪个测试不稳、上次为什么失败、某个目录的已知坑、本仓库评审中反复出现的误报与真缺陷。

不该承担：票状态、认领、依赖、唤醒、## Owns 重叠检查、验收证据、spec、ADR、决策结论，以及任何闸口的通过条件。理由：这些都要求确定性或可审计的历史，而 Nowledge Mem 的检索是语义的、写入没有版本、后台会自动合并改写，且失败时静默。

位置的一句话表述：tracker 事件是账本，仓库文件是规章，Nowledge Mem 是检索索引。按 ADR 0001，同一条经验的权威副本在产生它的票事件里，Nowledge Mem 里的那条是索引，丢了可以从事件重建。

6方案

四个阶段按"证据强、改动小、先堵漏"的顺序排。每项写明它解决的缝、做法、你在产品上会看到的变化、依据和风险。标 要你定 的项依赖第 9 节的决定；其余是工程决定，按 MMW 惯例由我判断。所有新名字都是暂名，落地时按 CONTEXT-MAP.md 的词表规则定名。

阶段一 · 补闸口 · 不需要新基础设施

先把验收、spec 错误、并行冲突、评审处置这四处缝堵上

1.1验收标准发布即锁定要你定：第 9 节第 2 条

缝
worker 在起 verifier 之前改弱一条 CHECK，verifier 跑的就是改弱后的标准，关票门放行。
做法
发布读回（to-tickets 第 8 步）或开夜前的批次 lint（night.md 第 1b 步）通过时，脚本在每张票写一个记录标准指纹的事件（复用 verify-ticket.py 已有的 shape_digest）。--closeout 增加一条：票上当前标准的指纹必须等于最近一次发布或修订事件里的指纹，否则拒绝，并点名变了哪条 AC、给出唯一出路。running-criteria.md 的 "A wrong CHECK is fixed on the ticket" 改为：标准写错走 --sub-issue contract，由 main agent 或你修订后重发指纹事件。
你会看到
"ALL MET" 的票，验收标准一定是你批准切分时的那一版，或者有一条记录谁在什么时候为什么改过。
依据
ImpossibleBench（给出口 54%→9%；只读测试挡住改测试）；METR（改判定器，不是改提示词）；MMW 自己的 #162 已经堵住了"verifier 之后改"。
风险
如果很多票的 CHECK 本身写错，HANDOFF REQUIRED 会变多。那说明问题在切票质量，由 3.1、3.2 处理。

1.2contract 子票叫醒 main agent，暂缓同小节未开工的票要你定：第 9 节第 1 条

缝
worker 发现 spec 或基线本身不成立，开 contract 子票后继续做；谁也不被叫醒，同一 Implementation Decisions 小节下还没开工的票当夜照常派出，第二天一组票按改后的 spec 返工。
做法
relay 把 child.opened 的 contract 加进叫醒 main agent 的种类。main agent 只做一件事：对 ## Parent 指向同一小节、且还没有 worker.started 的票暂不派出，已开工的继续。NIGHT SUMMARY 的 "Not dispatched" 行写明被哪张 contract 挡住。contract 子票正文增加一节"哪些照原样成立"（BMAD 的 KEEP），早上修订 spec 时照着保留。
你会看到
发现 spec 错误的那一夜，受影响小节少派几张票；第二天返工只限已开工的票。
依据
BMAD 的 bad_spec 与 intent_gap 分流：spec 层面的修正比在错 spec 上打补丁更可能产出一致的代码。
风险
worker 把实现 bug 误开成 contract，会让同小节的票停一夜。只冻结同小节、未开工的票，影响有上限且在 summary 里可见。

1.3并行 spec 之间的 ## Owns 重叠检查

缝
两个 spec 并行开夜时，各自的票可能改同一批文件，直到合并时才 bounce。
做法
advance 派出每张票之前，把它的 ## Owns 与同仓库其他开着的 watch 下"已开工且未落地"的票的 ## Owns 求交集；有交集就本轮不派，stderr 点名挡住它的票（沿用 how-it-works.md 里 "When no ticket can start … stderr names each condition" 的格式）。挡住它的票落地后，下一次 advance 自然派出。relay 已持有同仓库所有 watch（ADR 0022），不需要新进程。
你会看到
并行 spec 的同文件 bounce 消失，代价是这类票自动变成先后执行。
依据
你记忆里的 #748、#750、#751；Factory 与 Anthropic C 编译器文章记录的同一失败模式。三份调研独立指出这个缺口。
风险
## Owns 写成整目录 glob 时会误挡本可并行的票。stderr 会报出被挡的数量，据此收紧 to-tickets 的 glob 粒度。

1.4评审发现先核实再上报，处置逐条入账

缝
in-ticket 发现修没修、为什么不修，票上无法逐条对账；假发现会被照改，真发现会被略过。
做法
两处。reviewer 会话（code-review/references/session.md 第 3 步分拣之前）逐条打开发现所指的 file:line 核对，不成立的放进报告末尾的撤回列表，不进入 In-ticket / Out-of-ticket。worker 的关票草稿增加一节，每条 in-ticket 发现一行：fixed <commit> 或 refuted: <file:line 上实际发生什么>；--closeout 逐条核对都有一行；Spec 轴判为 should not 的不允许 refuted。
你会看到
每张票的评审结果可以一行一行追到代码提交或反驳理由；收口轮里被判 stale 的 finding 应该变少（现在 ADR 0012 记录约 24%）。
依据
BMAD Review Triage Log；Anthropic 要求附证明后实质评论从 16% 到 54%；Claude Code Code Review 与 Uber 的"先对照代码验证再上报"。
风险
核实本身也是 LLM 做，会误撤真问题。MMW 的 in-ticket 修复只有一轮，误报代价高，偏向精度是合适的。
阶段二 · 共享经验层 · Nowledge Mem 作检索索引

让每个 agent 开工时读到别的 agent 学到的东西

这是你这一轮要的"读"的自动化。设计原则：写入由脚本经票事件完成（账本在 tracker），脚本同时写进 Nowledge Mem（索引）；读取由 dispatch.sh 在派发时替 agent 查好放进 prompt，不依赖各 host 的钩子；按角色给不同的内容，保住 reviewer 和 verifier 的独立性。

2.1采集：随时可记，关票时必须交代

做法
给 verify-ticket 加一个采集子命令，worker、reviewer、verifier 在工作中任何时候都能记一条，脚本立即写成票事件并同步写入 Nowledge Mem 该仓库的 space。每条固定四段：事实一句；证据（跑过的命令与输出首行，或 path:line）；适用条件；种类（环境 / 不稳定测试 / 工具坑 / 假设）。出处字段（仓库、spec、票、角色、commit、涉及文件、哪一夜）由脚本填，不让模型填。关票草稿与 verifier 结论增加固定行 Learned:，列本票记下的条目，或写 none — 评估过什么；缺这一行 --closeout 拒绝。verifier 结论里现有的"修了什么"自动作为一条环境类条目。
为什么随时可记
关票要几个小时，并行的另一张票等不到那时。显式写入后 0.5 秒可检索，同一夜就能传到。
Nowledge Mem 不可达
事件照常写在票上，事件里标"未索引"，stderr 说一行；恢复后脚本从事件补写索引。不影响任何闸口。
依据
monomind "Capture has to be cheap enough to happen during the work"；Copilot Memory 的引用字段；ADR 0008 在知识上的应用（"没什么可记"也要显式说）。

2.2读取：派发时由脚本组装"开工包"

做法
dispatch.sh start 在给 worker、reviewer、verifier 写开场 prompt 时，调用一个脚本组装一个有篇幅上限的固定小节，按角色不同：
角色从 tracker 取从 Nowledge Mem 取不给
worker并行 spec 里 ## Owns 与本票重叠的活票（号、标题、状态）；本票直接 blocker 已落地后的 DECISIONS 评论本仓库已接受条目中涉及文件与 ## Owns 路径前缀重叠的；今夜本仓库新记的条目（标"未审"）；工具箱 space 里与流水线相关的条目Working Memory（避免客户产品上下文串入）
reviewer—只取"本仓库评审指南"类已接受条目，按 diff 文件路径匹配worker 记的任何条目（保住评审不被实现者的推理带偏）
verifier—只取环境类条目其余一切（它只判定标准，不判断代码）
细节
每条已接受条目带 path@commit 锚，组装时跑 git diff --quiet <commit> HEAD -- <path>，文件变过就标"依据已变，先核对"；超篇幅的列标题不丢弃；查询失败时小节里明说"经验库未查询"。worker 发现取回的条目与现状不符，写进 DECISIONS 评论一行，收口轮据此取代旧条目。开工包列出的条目 id 写进 worker 的运行事件，事后可查哪条经验帮了忙、哪条误导了。
为什么放在派发时
五个 host 的钩子行为不一致（Grok 丢弃输出、钩子失败静默、bundle 不含检索结果）；派发脚本是 MMW 唯一对所有 host 一样、且能按角色区分的位置。
依据
monomind 按文件路径取回；Augment 按改动路径加载评审记忆、加载时核对冲突；Cognition 与 LangChain：验证者用干净上下文；Devin "Accessed Knowledge" 的可审计性。

2.3提升：main agent 单写，重复才进规章要你定：第 9 节第 4 条

做法
收口轮里 main agent 逐条处理今夜的条目，和现在处理 finding 一样有唯一出口、写事件：去重后三选一——接受（在 Nowledge Mem 标为已接受并补齐 path@commit 锚，之后按路径被取回）；提名进规章（同类出现两次以上，或一次就让票卡住的，提议写进 .mmw/target.json、仓库脚本、消费仓库 AGENTS.md 的 Gotchas，或 MMW 技能文本）；丢弃（写原因）。NIGHT SUMMARY 增加一行计数；有未处理条目时 summary 拒绝，与未路由的 finding 一致（ADR 0008）。
谁批准
"接受"只影响检索，main agent 可以做。"进规章"会改变之后所有 agent 的行为，默认做成早上给你看的提案，由你决定（第 9 节第 4 条）。
依据
planning-with-files 的反例（共写一个文件会静默丢失）；ACE 论文（LLM 整体重写共享笔记会塌缩）；Factory scrutiny 的权限分层；Augment 与 OpenAI 的"同一错误两次再回写"；ETH 研究（上下文文件写多了有害，只放读代码推不出的）。

四层 context 怎样流转

层要传的东西载体谁写谁读、何时读
跨 agent（同一张票）评审报告、verdict、决定、环境修法票事件（已有）＋ 2.1 的条目worker、reviewer、verifier，经脚本被事件唤醒时读票（已有）；verifier 的环境修法进入下一个开工包

阶段三 · 把设计意图传到代码

发布前查覆盖，开工前查基线

3.1spec 覆盖检查进 --lint

做法
verify-ticket.py <spec> --lint 新增两项：spec 的每个 Implementation Decisions 编号小节至少被一张票的 ## Parent 点名；Testing Decisions 的 How a test arrives at a state 下每个机制都被某张票的 ## Owns 覆盖（to-tickets 第 8 步现在是人工检查，改为机器）。未被认领的报 WARN 并点名小节号。
你会看到
发布时就知道 spec 里哪一条决定没有任何票去做，而不是验收时才发现少了一块。
依据
Factory 的覆盖检查（"Unclaimed assertions = planning gap"）；spec-kit analyze 的覆盖率。
后续
Factory 的做法是给每条行为断言编号并要求"恰好被一个 feature 认领"。先做小节级覆盖，看 retro 里"spec 有、票没做"的案例多不多，再决定要不要细到断言级。

3.2发布前一次只读的"找漏"会话

做法
to-tickets 第 6 步请你批准切分之前，另起一个会话只读 spec 与票草稿，找会改变交付内容的模糊、冲突与遗漏，最多 5 条，每条引用 spec 原句并带推荐选项，并入你已经在看的 Choices 行，不另开一轮对话。
依据
Factory 契约的对抗评审（"It is very likely that important assertions are missing, even if the contract looks good on the surface"）；Ambig-SWE（模型分不清规格是否完整）；spec-kit clarify 的"最多 5 题、带推荐"。
风险
过度规格化（Böckeler 批评小 bug 被扩成 16 条验收）。只收会改变交付的问题，其余照 implement "Put no question on the screen" 由 worker 取默认。

3.3认领后先在基线上跑一遍验收

做法
--preflight 认领成功后，在 worker.started 的 base commit 上把全部标准跑一遍，写一条 run 为 baseline 的 ticket.checked。没写代码就已经通过的标准，--closeout 要求草稿逐条说明：已被别的票做掉，还是这条 CHECK 测不到本票的行为（后者走 contract）。不阻止开工。
依据
Anthropic "run through a basic end-to-end test before implementing a new feature"；PLANS.md "the new test fails before the change and passes after"；MMW 的 boundary-check.py 已证明负对照可以机械化。
风险
开工变慢，带长 TIMEOUT: 的标准要跑两次，可以只对不需要产品槽位的标准做。测试文件还不存在时标准必然是红的，这种红不证明任何事，所以只对"基线已绿"下结论。更强的版本（verifier 把本票新增的测试放到旧代码上跑、要求失败）需要单独设计，放到这一项跑一段时间之后。

3.4批次级流程验收票（仅对能起整机的仓库）

做法
spec 声明跨票的用户流程时，to-tickets 切一张验收票，Blocked by 流程涉及的所有票，## Owns 只含 .mmw/journeys/<flow>/，标准是 journey.py run <flow>。它自然在最后被派出，由新 worker 在已合并的 base branch 上跑；失败走现有的 finding 路由。
依据
Factory user-testing validator 是发现问题最多的环节；SpecBench 的组合差距。
适用范围
需要 .mmw/target.json 能起整机并登录；MMW 自身这种没有界面的仓库不适用。
阶段四 · 跨夜学习

让重复出现的问题变成检查，而不是每夜重犯

4.1夜后 retro要你定：第 9 节第 5 条

做法
summary 之后跑，只用票事件与 git log 作证据，产出一条由脚本写成事件的 spec 评论：
  • 每条发现带事件或 commit 出处，无出处的丢弃；
  • 每条两个处置：本例怎么办（开票 / 接受）、怎样防下一次（改哪个技能的哪一节、加哪个检查、改哪条规章）；
  • 跨票或跨夜出现两次以上的同类问题（bounce 原因、HANDOFF REQUIRED 原因、finding 类别、verifier 修环境）列成候选，属于工具箱的开到 MMW 仓库，属于消费仓库的开到该仓库；
  • 先核上一次 retro 的行动项，按证据写"已落地"或"没找到证据"；
  • 一节只描述不提议的意图对账：整批交付与 spec 的 Problem Statement、User Stories、Out of Scope 对一次，列出用户期望的表面与测试实际观察的表面是否一致；
  • 评审结果写成"本仓库评审指南"候选：同一路径被判 stale 两次的发现提名为已知误报，同类缺陷成立两次的提名为反模式或 lint 规则。
需要补的字段
review comment 的每条发现加一个类别字段（现在是自由文本，无法聚合）；route 的 stale 区分"本来就不成立"和"被别的票修掉了"。
依据
BMAD retrospective 的出处规则与双处置；Anthropic "a discovered bug class never makes it back into CLAUDE.md … the whole structure degrades"；OpenAI "promote the rule into code"；Augment 评审记忆的强弱信号；ADR 0012 自己的数据（每票约 3 条发现、三代不降）。
风险
提议太多没人看。每次只列重复两次以上的，并跟踪上一次提议的落地率。

其他值得做的小项

  • worker 的回合结束守卫。现在 worker 过早结束回合，要等 watchdog 一小时沉默才发现。照 planning-with-files 的教训做：票上没有等待中的 reviewer/verifier/槽位、也没有结果事件时拦一次，有次数上限，自上次拦截后票上没有新事件就放行，理由用固定句子。
  • reviewer、verifier 与 worker 同一模型家族时，install.sh --check 给一行 WARN。Copilot Rubber Duck 与 Factory 都把"验证者用不同家族"作为默认；MMW 的 hosts.json 默认已经这样配，但没有检查。
  • bug 类票至少一条"现有行为保持"标准。来自 Kiro bugfix spec 的 "SHALL CONTINUE TO"。

7不采纳的做法

做法来源不采纳的理由
顶层全串行FactoryMMW 用 ## Owns 重叠检查（1.3）把真正冲突的票串起来，其余保持并行
每批生成专用 worker 技能Factory技能是交付物、对所有 host 一样；实物显示 mission 专用技能会与仓库事实脱节
票级验收标准对 worker 保密Factory 8 月研究MMW 的 CHECK 是精确规格而非稀疏抽样，worker 需要自测；只在 3.4 的流程验收票上可以试"持有者不是实现者"
验证失败自动修到收敛Factory、BMADMMW 的一轮上限是有意防止无限循环；Factory 修复占实现量 34%、首轮从不通过
评审强制报满 N 条BMAD与 ADR 0012 的数据冲突，会放大子票膨胀

9需要你拍板的

下面五条会改变每夜交付多少、客户数据流向、或你每天要做的事。其余都是工程决定，已在第 6 节给出理由。阶段一的 1.3、1.4 不依赖任何一条，可以先做。

  1. spec 有疑点时当夜少派票。1.2 会让同一 spec 小节下未开工的票在出现 contract 子票后停一夜。我建议接受：返工限于已开工的票，影响可见且有上限。
  2. 验收标准发布后谁能改，以及它和"spec 修订后更正票"怎样并存。现在 running-criteria.md 允许 worker 改，to-spec 第 5 步要求更正已切出的票，tickets/CONTEXT.md 却说票正文发布后不改，三处互相矛盾。我建议：worker 永远不改；标准或票要改，只由 main agent 或你经 contract 子票修订，修订时脚本写一个带新指纹的修订事件，票正文可改但每次改都有事件记录。
  3. Nowledge Mem 的布局与现有数据流。四件事一起定：启用 spaces，每个客户仓库一个互不可见的 space、一个共享的工具箱 space；流水线会话停止注入 Working Memory；夜里的 worker、reviewer、verifier 会话是否继续自动存进你的个人记忆库（我建议停掉，只保留脚本显式写入的经验条目，因为会话原文含客户代码与 issue 内容）；将来云端或别的机器上的 worker 是否可以持有全权 API key。
  4. 经验提升进规章由谁批准。2.3 里"接受进检索"由 main agent 做；写进消费仓库 AGENTS.md、.mmw/target.json 或 MMW 技能文本会改变之后所有 agent 的行为。我建议夜里只出提案，早上由你批准，代价是知识晚一天进入规章（检索当夜就生效）。
  5. 你每天多做的事。早上看 retro 提案和经验提升提案，并从 ALL MET 票里抽 2–3 张实际验收，估计每天 10 分钟左右。retro 每夜自动跑还是你点名跑；它开出的工具箱 issue 是直接进 ready-for-agent 还是先进 needs-triage（我建议后者）。

10更正与原始报告

本页前几版里已更正的说法

  • "前一夜的结果不流回下一个 spec"——错。一夜的遗留问题经早间 triage 分流进 spec 或票；而且 MMW 的多个 spec 本来就是并行开夜，没有"上一个、下一个"之分。
  • "verifier 修环境的办法无处存放"——不准确。它写在 verdict 结论行里，缺的是别的票会读它。
  • "coordinator 独写 notes.md 是 Cursor 官方设计"——官方博客没这么写，是 Arslan 的做法；Cursor 客户端提示词里确实也有 worker 不得写 notes.md 的规则。

Cursor Projects 要点（第一轮）

Project Context 是挂载到每台机器的共享文件夹：notes.md 放状态（只有 coordinator 写，只允许复选框行），docs/、plans/、media/ 给人看，internal/ 放 agent 报告（worker 只能改带自己 subagentId 的文件）。文件内容不注入 prompt，只告诉 worker 路径和规则。同步按文件后写者赢，输的一方存成冲突副本。coordinator 之间不能通信，Arslan 用 git 里的收件箱文件绕过。细节见原始报告一。
