# 界面 QA 技能 spec

> 这份 spec 来自 2026-08-12 的一次 `/mmw-grilling` 访谈。访谈从「MMW 缺少 UI/UX 自动化检查」这个需求开始，经七轮问答形成共同理解，用户在最后确认。访谈期间的事实调查全部由主 agent 当场完成并验证，没有保存 research 目录，也没有产生 prototype 资产，因此 `artifact_refs` 为空。
>
> 访谈引用的外部一手来源在 Further Notes 一节逐条列出。

## Problem Statement

用户在 prototype 阶段迭代界面时，必须亲自逐项指出问题，agent 才能修改。每一个元素、每一条流程、每一个步骤都要用户点出来。这个循环很慢，而且它浪费了前置工作——在 prototype 之前，`/mmw-grilling` 或 `/mmw-wayfinder` 已经把这个产品要什么样的界面谈清楚了，agent 本来就具备判断依据。

项目完整落地之后，问题换了一种形式。这时 spec 已经固定，后端是真实代码，是最适合完全自动化的时机，用户却仍然要一项一项盯。

MMW 现在没有任何技能承担这件事。`/mmw-prototype` 管的是用户本人走查，`/mmw-review` 管的是六道审，两者都不检查界面本身。

用户的目标用户看重可用性和贴合真实工作流，不看重美观和品味。所以需要的是最基本的审美保障加上用户体验优化，不是一套设计品味体系。

## Solution

新增独立技能 `/mmw-ui-qa`。它按已经谈定的判据自动检查界面，产出两类结果：确定性检查判定成立的**违规项**直接修改，模型判断产出的 **finding** 只报告、等用户裁决。

**它是交互式技能，不是跑完才见面的批处理。** 用户在开发迭代过程中随时喊起来，技能在正常流程里该问的时候停下来问。它承担三件事：

1. **建立这个产品的判据** — 第一次运行时用 intake 问卷把判据和接线建起来，然后接着往下跑。
2. **对刚刚完成的那一块做检查** — 默认范围就是本次改动，用户一个字都不用多说。这是主场景。
3. **对完整应用做全流程检查** — 挂一个标签切到全量，用在初版落地和去 Windows 那一次。

**用户的批注次数随轮次下降**，靠的是每条裁决存一个指纹：下一轮指纹全等的条目根本不出现在报告里，只差一个字段的条目只问一句「是不是同一件事」。裁决不论结论都长期保存，判成不成立的也记住，所以同一件事不用说第二次。

技能自带方法，不依赖任何界面 QA 工具的运行时。运行时依赖有三个：浏览器自动化框架、可访问性规则引擎、设计系统格式校验器，具体选型见 Further Notes。

## Current State

**MMW 侧。** 技能源在 `mmw/skills-src/`，通过 `mmw skills materialize` 物化成 Pi、Claude Code、Codex 三个宿主的技能产物。Cursor 只物化原生 subagent，不在技能物化的目标里。技能之间的引用、技能源不写产物落点字面值、技能物化三件事各有一份已存在的机械校验。产物落点数据在 `mmw/cli/artifacts.json`，路径由 `mmw artifact path` 回答，形状由 ADR-0003 和 ADR-0006 规定。角色表里已有 `designer`，只读、独立上下文，当前只有 `/mmw-codebase-design` 的 design-it-twice 在用。派 subagent 使用 `[[mmw-launch:…]]` 与 `[[mmw-launch-group:…]]` 动作块。

**目标仓库侧（agentflow，主要使用场景）。** 三个 Electron 桌面应用共用同一套技术栈：Electron 41、electron-vite、Tailwind 4、daisyUI，`src/renderer/` 下是 TypeScript 直接操作 DOM，没有前端框架。变色龙应用在 worktree 中开发，将使用 React，尚未合入主干。三个应用都装了 `@playwright/test`，`node_modules` 里实际版本是 1.61.0，因此 ARIA snapshot 可用。其中两个应用有 `playwright.config.ts`，`desktop` 已经在用 `_electron` 启动应用做集成测试。

`desktop/tests/integration/launch.spec.ts` 里已经有四个确定性界面断言：读计算光标断言可点击元素是手型、注入探针元素断言全局光标规则、比较按压前后的 `transform` 与 `filter` 断言按压反馈、读 `getBoundingClientRect` 与 `overflow` 断言进度条没被裁掉。它们由三次 `fix` 提交引入（`91a6948bf`、`89c293888`、`e0782ca0a`），每次都是先发现缺陷、修改样式、再补一条断言防回归。它们证明界面规范可以用零截图的确定性断言表达，但它们锁住的每一条都是人先发现的，不构成发现机制。其中两个断言注入假元素测全局 CSS 规则，测不到被更具体选择器覆盖的真实元素。

仓库根有 `DESIGN.md`，由 Impeccable 生成，人持续维护，13 次提交。它的 YAML frontmatter 有 `colors`、`typography`、`rounded`、`spacing`、`components`，正文有六条具名规则和 Do's/Don'ts 各九条。它没有可执行的阈值——`≥4.5:1` 全文出现五次，全部在注释和散文里；也没有任何一条「用户必须能做到什么」形式的判据。

`ENGINEERING-RULES.md` 记着一条铁律：Windows GUI 与 Electron 必须在交互式用户会话启动，SSH 前台拉起会静默失败。两份历史 plan 重复了同一条：Mac agent 不能跨 SSH 启动 Windows GUI。

Impeccable 在 agentflow 已经不是现役工具，规则文件与技能目录都不在，只剩未进 Git 的本地缓存。

## User Stories

### 起步与时机

1. 作为产品负责人，我希望在 prototype 迭代的任何一轮随时发起界面 QA，以便不必等到某个固定关卡才能拿到反馈
2. 作为产品负责人，我希望在项目初版完整落地后发起一次界面 QA，以便在最适合自动化的时机拿到全面结果
3. 作为产品负责人，我希望在已有项目的新功能完整落地后发起界面 QA，以便新功能与既有界面用同一套判据衡量
4. 作为产品负责人，我希望界面 QA 不占用六道审的任何一道，以便它在不走审查流程的 prototype 阶段也能用
5. 作为主 agent，我希望界面 QA 是独立技能而不是某个流程步骤，以便 `/mmw-prototype` 和 `/mmw-review` 都能点名调用同一份方法
6. 作为主 agent，我希望技能启动时先要求工作区干净，不干净就停下来让用户提交，以便技能自己的修改可以直接提交、也可以被整轮退掉
7. 作为主 agent，我希望技能探测到判据或接线文件缺失时进入建立模式而不是停止，以便新仓库第一次运行能走完
8. 作为产品负责人，我希望技能是交互式的，在正常流程里该问我的时候停下来问，以便它不是跑完才见面的批处理
9. 作为产品负责人，我希望日常发起时一个字都不用多说，以便我在迭代中随手就能喊起来
10. 作为产品负责人，我希望需要改范围时只挂一个标签，以便我不必描述一遍我想查什么
11. 作为主 agent，我希望用户挂了标签就直接用不再推断，以便行为可预期
12. 作为主 agent，我希望技能在检查判据之前先判定产品，以便按产品分的判据和接线文件找得到
13. 作为产品负责人，我希望只做一个应用的仓库永远不被问是哪个产品，以便我不回答只有一个答案的问题
14. 作为产品负责人，我希望多个产品时看到的是产品名而不是目录名，以便我不必记住目录叫什么
15. 作为产品负责人，我希望一次运行只检查一个产品，以便我裁决时不会分不清在答哪个应用的事

### 判据建立

16. 作为产品负责人，我希望技能通过一轮 intake 问卷建立初始判据，以便新项目从零起步时也能用
17. 作为产品负责人，我希望 intake 问卷只问我能答、而技能查不到的事，以便我不重复回答仓库里已有的信息
18. 作为产品负责人，我希望技能从共同理解和 spec 里抽取这个产品特有的可用性要求，以便我在 grilling 里说过的话不用再说一遍
19. 作为产品负责人，我希望技能不从现有代码逆向抽取判据，以便当前的缺陷不会被固化成标准
20. 作为产品负责人，我希望阈值表的初始值跟我已有的组件规格对齐，以便技能不会把我刻意做小的徽章判成违规
21. 作为产品负责人，我希望每一条可用性判据都记着它的来源和状态，以便我日后能查到它是从哪次讨论或哪次界面 QA 来的
22. 作为产品负责人，我希望判据文件带版本字段，以便格式变化时技能能认出旧文件而不是静默误读

### 判据读取

23. 作为主 agent，我希望技能读取目标仓库已有的设计系统文件，以便不重复建立一份竞争的设计权威
24. 作为主 agent，我希望技能依赖设计系统的格式规范而不是生成它的工具，以便目标仓库换生成器时界面 QA 不受影响
25. 作为产品负责人，我希望没有设计系统文件时技能提议建一份，以便新产品也能有完整的九种判拒
26. 作为产品负责人，我希望技能建设计系统时从问卷和已有产物取内容而不是从运行页面提取当前值，以便当前的缺陷不会被固化成标准
27. 作为主 agent，我希望技能建完设计系统立刻转为只读，以便它的所有权交回目标仓库
28. 作为产品负责人，我希望技能在用判据之前先校验判据本身，以便一份自己就违规的规范不会把读不清的界面判成合规
29. 作为产品负责人，我希望判据自己的问题被标明是判据的问题而不是界面的问题，以便我不去改界面
30. 作为主 agent，我希望判据校验只用一条命令、不需要启动应用，以便这一步的成本可以忽略
31. 作为产品负责人，我希望 intake 问卷七个问题一次问完、其中大部分我只需勾选或确认，以便我实际打字的地方尽量少
32. 作为产品负责人，我希望从共同理解和 spec 抽取的判据一次性展示、默认全接受、我划掉不要的，以便我既不用逐条确认也不会被塞进我没说过的判据
33. 作为主 agent，我希望技能不修改目标仓库的设计系统文件，以便它的所有权仍然属于目标仓库
34. 作为主 agent，我希望目标仓库没有设计系统文件时技能仍能运行，以便只跑不依赖它的那几种判拒
35. 作为主 agent，我希望认知走查四问、Trunk Test 六问和困惑分量表写在技能正文里，以便任何仓库装了 MMW 就有，不需要配置
36. 作为产品负责人，我希望可用性判据每个产品一份，以便四个产品的差异不会被挤进同一份文件

### 检查范围

37. 作为产品负责人，我希望默认只检查我刚改动的那一块，以便我在迭代中随手发起时不用等全量跑完
38. 作为产品负责人，我希望能指定检查整个任务的改动，以便任务交出去之前查一遍
39. 作为产品负责人，我希望能指定全量检查，以便初版落地和去 Windows 那一次覆盖全部界面
40. 作为主 agent，我希望改动的文件通过界面全图已有的来源文件字段映射成要查的界面，以便这一步是查表而不是再扫一遍代码
41. 作为主 agent，我希望范围推不出界面时逐级降级而不是少跑判拒，以便九种判拒在任何一档上都全部运行
42. 作为产品负责人，我希望报告开头就写清这次查了哪些、没查哪些，以便我不会以为查全了
43. 作为产品负责人，我希望范围因降级变过时报告写明原因，以便我知道它为什么比我预期的大
44. 作为主 agent，我希望范围内没有产物路径时用全图跳转关系拼一条，以便语义层在任何范围下都有路可走
45. 作为产品负责人，我希望拼出来的路径在报告里被标明，以便我知道那几条结论要打折看

### 检查执行

46. 作为主 agent，我希望以结构化数据为主要输入，以便 token 成本可控且判断精确
47. 作为主 agent，我希望用无障碍树快照读取界面结构，以便判断不依赖 class 名、测试标识和包装元素
48. 作为主 agent，我希望批量提取计算样式与布局盒模型数值，以便用数字而不是图像判断间距、尺寸和对比度
49. 作为主 agent，我希望 A3 判定用运行时实际生效的 token 集合而不是文件里的声明，以便过时的声明不会让结果整体失真
50. 作为产品负责人，我希望声明的 token 与实际生效的 token 不一致时被单独报出来，以便我知道文档和实现已经脱节
51. 作为产品负责人，我希望技能给出「从声明生成实现」的建议但不替我改构建流程，以便选型决定仍然在我手里
52. 作为主 agent，我希望截图只在结构化数据判不了时使用，并且裁到局部，以便不为每一步付整屏图像的成本
53. 作为主 agent，我希望调用可访问性规则引擎，以便拿到无障碍树快照查不了的对比度、ARIA 误用、`tabindex` 取值、`aria-hidden` 元素可聚焦、嵌套交互控件和可滚动区域可达性
54. 作为产品负责人，我希望技能明确声明它不验证实际键盘遍历顺序，以便我不误以为焦点顺序已被覆盖
55. 作为主 agent，我希望收集渲染进程的控制台报错，以便运行时错误进入检查结果
56. 作为主 agent，我希望检查方法不依赖前端框架，以便同一套方法覆盖原生 DOM、React 和未来的 Web 应用

### 语义层

57. 作为产品负责人，我希望技能判断界面想表达的功能和流程是否被实现，而不只是组件是否存在
58. 作为主 agent，我希望按认知走查四问逐步评估，以便判断落在意图、注意、联想和反馈四个语义维度上
59. 作为主 agent，我希望每一屏按固定量表单独打困惑分，以便不同轮次的结果可比
60. 作为主 agent，我希望走查过程保留完整会话历史，以便重复运行的结果彼此一致
61. 作为主 agent，我希望技能明确写出「agent 走得通不等于用户走得通」，以便我不把任务完成当成通过判据
62. 作为主 agent，我希望走查任务来自 MMW 已有产物，以便判据和任务不是同一份东西
63. 作为主 agent，我希望走查任务是完整用户路径而不是单个操作，以便自动化的成本换得回价值
64. 作为主 agent，我希望从产物里取到的是单个操作时向上合并到完整路径，以便不把任务拆细去凑数
65. 作为主 agent，我希望 Trunk Test 六问按固定表述提问，以便不同产品的结果可比

### 界面全图与覆盖

66. 作为主 agent，我希望技能先建立界面与状态的全图，以便认知走查能看到当前屏之外的路
67. 作为主 agent，我希望全图从代码抽取打底、运行时探测补充、判据记录补足，以便三种来源各自覆盖对方的盲区
68. 作为产品负责人，我希望空状态、加载态、错误态和权限差异**只要接线文件声明的准备方式能到达**就进入检查，以便 QA 不只跑通顺路径
69. 作为产品负责人，我希望到不了的状态被明确报成覆盖缺口而不是当作已检查，以便我知道覆盖到哪里为止
70. 作为主 agent，我希望全图每次运行重建、不持久化，以便技能不需要记住上次跑到哪
71. 作为产品负责人，我希望覆盖缺口不驱动代码修改，以便它不被误当成界面缺陷

### 平台

72. 作为产品负责人，我希望在 Mac 上对 Electron 渲染层做界面 QA，以便 prototype 阶段不必去 PC
73. 作为产品负责人，我希望应用完整落地后能在真实 Windows 上跑一次界面 QA，以便 DPI 缩放和中文字体回退这类问题被覆盖
74. 作为产品负责人，我希望 Windows 侧启动一次之后检查步骤全自动，以便我不必守着每一步
75. 作为产品负责人，我希望 Windows 侧要改东西之前技能先告诉我有几处、要重启几次，以便我决定这次改还是只报告
76. 作为产品负责人，我希望 Windows 特有的问题在 Windows 上改、在 Windows 上验证，以便不会改完回 Mac 才发现验不了
77. 作为主 agent，我希望连接远程调试端口后先自检能力，以便能力不足时报成缺项而不是当完整结果
78. 作为主 agent，我希望技能明确写出不能跨 SSH 启动 Windows GUI，以便我不做一个会静默失败的动作
79. 作为产品负责人，我希望技能明确列出在 Mac 上测不到的那批行为，以便我不误以为已经覆盖

### 处置与回流

80. 作为产品负责人，我希望 A 类的违规项被直接修改，以便我不必逐条批准显然的修复
81. 作为产品负责人，我希望技能要求我先提交再检查，以便它改的东西可以整轮退掉，也不会跟我没写完的代码混在一起
82. 作为主 agent，我希望回退直接用 git，以便技能不必自造快照机制
83. 作为主 agent，我希望九种判拒全部跑完再统一修改，以便所有检查看到的是同一个界面状态
84. 作为主 agent，我希望每改一条只重跑触发它的那一项检查，以便验证成本不随修改条数膨胀
85. 作为主 agent，我希望全部改完后把四种 A 类检查整体重跑一遍，以便这一轮修改引入的新 A 类问题当场被发现
86. 作为产品负责人，我希望修改导致原问题还在或引入新问题时被自动撤销并降级成 finding，以便技能不会越改越坏
87. 作为主 agent，我希望定位到第三方组件或依赖包里的违规项一律不改只报，以便技能不动它管不了的代码
88. 作为产品负责人，我希望本次全部 A 类修改合成一个提交，以便我要退就 `git revert` 一次
89. 作为产品负责人，我希望报告逐条写明改了哪个文件哪一处、改前改后各是什么，以便我看得出技能动了什么
90. 作为产品负责人，我希望 B 类的 finding 只报告不修改，以便 agent 不按自己的审美改我的界面
91. 作为主 agent，我希望 A 类产出叫违规项、B 类产出叫 finding，以便 `finding` 的既有定义不被改成「已确认缺陷」
92. 作为主 agent，我希望模型产出的 finding 是候选而不是结论，以便我回到源码验证后才采信
93. 作为产品负责人，我希望界面与阈值不一致时默认判实现错，以便可执行下限保持约束力
94. 作为产品负责人，我希望界面与规则或可用性判据不一致时交给我裁决，以便我有意改动设计时不会天天被报红
95. 作为产品负责人，我希望我对 B 类 finding 的每一个裁决都被长期记住，不论我判它成立还是不成立，以便同一件事不用说第二次
96. 作为产品负责人，我希望被采信的设计系统规则违反回流成本产品的可用性判据，以便设计系统保持只读也能沉淀结论
97. 作为主 agent，我希望 finding 使用 MMW 已有的五个处置标记，以便处置方式与六道审一致
98. 作为主 agent，我希望每条裁决存一个指纹，以便下一轮认得出同一件事
99. 作为产品负责人，我希望指纹由技能自动生成，以便我裁决时不用多做一步
100. 作为主 agent，我希望指纹按判拒的天然粒度分四种形态，以便针对一屏或一条路径的判拒不被硬套元素位置
101. 作为产品负责人，我希望指纹全等命中的条目根本不出现在报告里，以便我不重复裁决同一件事
102. 作为产品负责人，我希望界面改动导致指纹只差一个字段时，技能只问我是不是同一件事，以便我答一个字而不是重新裁决一遍
103. 作为主 agent，我希望近似匹配停下来问用户而不是自动判定，以便界面重排不会误压制真问题
104. 作为产品负责人，我希望本轮没命中的旧裁决被列出来提示，以便判据不会积成一份压制着早已不存在问题的文件
105. 作为产品负责人，我希望陈旧裁决只被列出而不自动删除、也不让运行失败，以便它不打断我的迭代

### 报告与产物

106. 作为产品负责人，我希望界面 QA 报告直接交给我看、不写进仓库，以便仓库里不堆积历史噪音
107. 作为产品负责人，我希望长期沉淀的只有判据和裁决，以便积累的是规则不是记录
108. 作为主 agent，我希望判据产物的落点由 `mmw artifact path` 回答，以便技能正文不写路径字面值
109. 作为主 agent，我希望判据产物跨交付累积、不带工作名，以便它不随每次任务改变位置
110. 作为产品负责人，我希望报告按判拒编号组织，以便我一眼看出哪几类出了问题
111. 作为产品负责人，我希望报告分成五节并按「要我做什么」排序，以便我一眼看出哪些要我裁决、哪些只是给我看
112. 作为产品负责人，我希望只要答「是/不是」的那些条目单独成节，以便我不按裁决新问题的强度去想它们

### 跨宿主与跨仓库

113. 作为主 agent，我希望技能在能物化技能的三个宿主上语义一致，以便我换宿主时行为不变
114. 作为产品负责人，我希望技能明确声明 Cursor 不在技能发布面内，以便我不在那里找一个不存在的命令
115. 作为主 agent，我希望目标仓库通过一份薄接线文件告诉技能怎么启动应用，以便技能不猜测环境变量和窗口识别方式
116. 作为产品负责人，我希望接线文件每个产品一份，以便三个应用各自的启动参数不互相干扰
117. 作为主 agent，我希望三个运行时依赖由 MMW 的安装入口提供并固定版本，以便技能不依赖目标仓库碰巧装了什么
118. 作为产品负责人，我希望接线文件写明这次跑在哪个环境，以便技能不会连到我的正式数据上
119. 作为主 agent，我希望语义层的整条路径一次性交给独立上下文的评估者，以便它判得了「操作之后有没有反馈」这一问

## Implementation Decisions
### 1. 技能身份与术语

新增技能源 `mmw-ui-qa`，技能名 `/mmw-ui-qa`。它是方法技能，不占交付工作流的一跳，由 `/mmw-prototype`、`/mmw-review` 点名调用，也可由用户直接调用。先例是 `/mmw-tdd`。

**它是交互式技能，不是跑完才见面的批处理。** 用户在迭代过程中随时喊起来，技能在正常流程里有停下来问用户的点（第 6 节、第 12 节）。这与 `/mmw-tdd` 的形态一致。

**入口沿用 `/mmw-start` 已有的 argument hint 形态**：开头挂可选标签，后面跟自由内容，留空走默认。

```
argument-hint: "[本任务|全量] [产品名；留空自动判定]"
```

标签决定范围档（第 7 节），自由内容给产品名。**挂了标签就直接用，不再推断**，这条规矩照抄 `/mmw-start` 第 1 步。两者都留空时，范围取默认档「本次改动」，产品按第 6 节第三步自动判定。用户不必为一次日常检查多说一个字。

新增两个 canonical 术语：

- **界面 QA**：agent 依据判据自动检查界面，产出违规项与 finding。
- **违规项**：确定性检查直接判定成立的界面问题。它不是候选，不需要裁决。

`finding` 的 `_Avoid_` 里列了「已确认缺陷」。界面 QA 的 A 类结果正是已确认缺陷，因此它不叫 finding，叫违规项。B 类结果是候选，仍然叫 finding，仍然走五个处置标记。

**但 `finding` 的定义必须扩展一处：生产方。** 现有定义是「审查者报告的一个可定位问题候选」。界面 QA 的 B 类由 `designer` 角色产出，它不是审查者。生产方变了，定义就变了——写「不改定义，只增加一个产出它的场景」是自欺，下游 agent 读到一条 `finding` 时将无法判断它来自六道审还是界面 QA。

两个既有术语不动：

- **走查**（`docs/context/delivery-workflow.md` 拥有）：用户本人使用 prototype 并给出接受、拒绝或修改意见。它的 `_Avoid_` 已经列了「自动验收」，本次不改。
- **审查**（`docs/context/review.md` 拥有）：六道审。本次不增删道数。

**`/mmw-domain-modeling` 要做三件事**，实现时必须调用它，不得手改 leaf。它拥有 leaf 归属与 Context Map 的维护权，本 spec 不越过它指定写在哪一份 leaf 里：

1. 登记「界面 QA」与「违规项」两个新术语。
2. **扩展 `finding` 的定义**，把生产方从「审查者」扩展到「审查者或界面 QA」，并在正文里说明两个来源各自的处置去向。
3. 登记本 spec 引入的其余长期对象：**判拒**、**覆盖报告**、**界面全图**、**判据自检结果**。这四个都有稳定结构、明确的生产方与消费方，会出现在技能正文、合同字段与测试名里；不登记，后续 spec 与实现会为同一个对象各起一个名字，也没有 `_Avoid_` 划边界。

**「QA」这个缩写首次出现时给出全称**：质量保证（Quality Assurance）。此后全文固定用「界面 QA」这一个形式。

### 2. 判拒分类：两类九种，外加一份覆盖报告

分类依据是判定性质，不是判据载体。这条线沿用既有决定：确定性检查的结果是事实，模型判断的结果是候选。

**A 类 · 违规项。** 确定性检查判定，违反即成立，不需要用户裁决，直接修改。

| 编号 | 判拒 | 判据来源 |
| --- | --- | --- |
| A1 | 可执行阈值违反 | 阈值表 |
| A2 | WCAG 规则违反 | 可访问性规则引擎自带规则集 |
| A3 | 设计系统 token 越界 | 目标仓库设计系统的机器可读部分 |
| A4 | 运行时错误 | 渲染进程控制台 |

**B 类 · finding。** 模型判断产出的候选，主 agent 回到源码验证后交用户裁决。

| 编号 | 判拒 | 判据来源 |
| --- | --- | --- |
| B1 | 设计系统规则违反 | 目标仓库设计系统的散文规则部分 |
| B2 | 认知走查四问任一不成立 | 方法判据 |
| B3 | 困惑分偏高 | 方法判据 |
| B4 | Trunk Test 六问任一答不出 | 方法判据 |
| B5 | 产品特有可用性判据不成立 | 可用性判据 |

**三类报告项不是判拒。** 它们的共同性质是：确定的事实，但**没有界面上的修复目标**，因此不进 A 类的直接修改，也不进 B 类的用户裁决。

| 报告项 | 陈述什么 | 为什么没有界面修复目标 |
| --- | --- | --- |
| 覆盖报告 | 全图里有、本次没走到的状态 | 它说的是本次 QA 没执行什么，不主张界面有错 |
| 判据自检结果 | 设计系统文件自身的格式问题、跨 token 对比度不足、引用不完整 | 要修的是判据文件，不是界面。而设计系统只读 |
| 声明与实现不一致 | 设计系统声明的 token 与运行时实际生效的 token 对不上 | 修它要么改只读的设计系统，要么改构建配置——后者是产品的选型决定，不是缺陷 |

九种判拒是封闭集合。日后增加一种，必须同时说明它属于 A 还是 B，以及判据来自下一节哪一条。**产生新的确定性事实但没有界面修复目标时，加成报告项，不加成判拒。**

### 3. 判据五种

| # | 名称 | 物理形式 | 生产方 | 产生方式 | 供给 |
| --- | --- | --- | --- | --- | --- |
| 1 | 阈值表 | JSON，仓库一份 | 界面 QA | intake 问卷建立，裁决结果追加 | A1 |
| 2 | 可用性判据 | Markdown，每个产品一份 | 界面 QA | intake 问卷、从共同理解与 spec 抽取、裁决结果回流 | B5 |
| 3 | 设计系统 | 符合 **DESIGN.md 格式规范**的文件：YAML frontmatter 的 token 加正文八个 section 的散文 | 目标仓库 | 已存在时只读不写；不存在时提议建一份，建完转只读 | A3、B1 |
| 4 | WCAG 规则集 | 代码，可访问性规则引擎的依赖包 | 第三方 | 不产生，装依赖即有 | A2 |
| 5 | 方法判据 | Markdown，技能源的 reference 文件 | MMW 技能源 | 本次实现写定，跨项目不变，目标仓库不可配置 | B2、B3、B4 |

第 5 种承载认知走查四问、Trunk Test 六问和困惑分量表，全文在第 9 节写定。它不是目标仓库的配置，任何装了 MMW 的仓库直接具备。

**第 3 种绑格式，不绑工具。** 依赖的是 DESIGN.md 这个开放格式规范（Google Labs，Apache-2.0），不是任何一个生成它的工具。谁生成的都行，格式对就读得了。规范定义 frontmatter 的 `colors`、`typography`、`rounded`、`spacing`、`components` 五组 token（Dimension 只接受 `px`、`em`、`rem`，引用语法 `{colors.primary-60}`），正文八个 section 有固定顺序：Overview、Colors、Typography、Layout、Elevation & Depth、Shapes、Components、Do's and Don'ts。

**规范本身几乎不定义阈值。** 全份规范唯一可校验的数值约束是单位必须是 px、em、rem；WCAG 对比度只以「颜色值内部转成 sRGB 以便做对比度检查」这种处理行为出现，`4.5:1` 只在示例的 Do's and Don'ts 里。**这正是判据 1（阈值表）必须独立存在的原因**——阈值不可能从设计系统里读出来。

**规范严格限于视觉身份。** 没有用户流程、没有任务完成、没有产品需求层。功能与流程那一层由判据 2 与走查任务承担，见第 4 节。

**已存在时只读。** 所有权属于目标仓库，可能由它自己的工具管理。

**不存在时提议建一份，三条硬约束**：用 DESIGN.md 标准格式；内容来自 intake 问卷与 MMW 产物，**不从运行页面提取当前值**——那是逆向抽取，会把当前的缺陷固化成标准；建完立刻转只读，技能此后永不再写它。用户拒绝建立时才跳过 A3 与 B1，其余七种照常运行，报告中声明跳过原因。

**判据自己要先被检查。** 见第 6 节第四步。

### 4. 技能读取的三样非判据输入

| # | 名称 | 物理形式 | 生产方 | 产生方式 |
| --- | --- | --- | --- | --- |
| 6 | 走查任务 | MMW 既有产物 | MMW 流程 | 不新建。按阶段取自 prototype 的 `README.md`、tracer bullet ticket、spec |
| 7 | 接线文件 | JSON，每个产品一份 | 目标仓库 | intake 问卷建立模式时写一次 |
| 8 | 界面全图 | 进程内数据，不落文件 | 界面 QA | 每次运行重建，用完即弃 |

走查任务按阶段选源：prototype 迭代中用 prototype 的 `README.md`（它记录当前问题、逐轮用户走查结论、页面功能与后端行为的精确对应）；spec 已发布、实现进行中用 tracer bullet ticket（它的定义就是端到端垂直切片，天然是一条完整用户路径）；项目完整落地后用 spec。

**取到之后按检查范围筛。** 产物给出的是这个阶段的全部路径，本次要走的是其中经过范围内界面的那几条。一条都不经过时，用全图的跳转关系拼路径。两步都在第 7 节写定。

### 5. 产物落点

**新增两个产物类别**，都写进 `mmw/cli/artifacts.json`。两者都是跨交付累积、不属于任何一次交付的长期产物，因此 `has_name` 为假、`allows_scope` 为假，与 ADR、leaf、Context Map、否决记录同类。

| 类别标识符 | canonical 术语 | 类别根 | `root_kind` | 类别内细分 |
| --- | --- | --- | --- | --- |
| `ui-criteria` | 界面 QA 判据 | `docs/ui-criteria` | `fixed` | `sub_pattern` 同时匹配阈值表的固定文件名与 `products/` 下每产品一份的 Markdown |
| `ui-qa-wiring` | 界面 QA 接线 | `docs/ui-qa-wiring` | `fixed` | `sub_pattern` 匹配每产品一份的 JSON |

两个类别根分开，因为 ADR-0003 规定一个类别根只放一类产物，而判据与接线是两类：判据由界面 QA 生产，接线由目标仓库生产。

`sub_naming` 取 `one-per-concept`，并同时给出 `sub_pattern`。解析器在 `sub_fixed` 为空且 `sub_pattern` 非空时走正则分支，因此一个类别能同时容纳固定文件名与按产品分文件两种形态。

**`sub_fixed` 必须写成 `[]`，不能写 `null`。** 现有 26 个类别全部用 `[]`，解析器有一处 `[.sub_fixed[] | ascii_downcase]` 在 `null` 上会抛 jq 错误——虽然被 `-e` 吞成假值不影响判定结果，但每次调用都往 stderr 打一行错误。

**`scratch` 不动。** 界面全图在进程内构建、用完即弃；界面 QA 报告直接交给用户，不写进仓库。两者都不需要落点，因此不给 `scratch` 的 `sub_fixed` 追加任何取值。

这一条同时决定了技能不需要任务绑定（第 6 节第一步）：`scratch` 的 `has_name` 为真，要工作名；而上面两个新类别 `has_name` 为假，不要工作名。界面 QA 只写这两个类别，所以整条工作名链路都不需要。

**报告不落文件是有意的。** 用户的判断是「报告只会变成历史噪音，是没有用的；如果非要积累的话，需要积累的是规则」。落进 scratch 再随任务清理，等于先写一份没人回头看的文件、再删掉它。直接交给用户看完就完，长期沉淀交给判据。

落点一律由 `mmw artifact path` 回答，技能正文不写路径字面值，遵守 ADR-0006 与 ADR-0009。

**长期沉淀的只有两个新类别里的判据与裁决。**

**两个新类别的精确值**，直接写进 `mmw/cli/artifacts.json`：

| 键 | `ui-criteria` | `ui-qa-wiring` |
| --- | --- | --- |
| `term` | 界面 QA 判据 | 界面 QA 接线 |
| `root` | `docs/ui-criteria` | `docs/ui-qa-wiring` |
| `root_kind` | `fixed` | `fixed` |
| `has_name` | `false` | `false` |
| `allows_scope` | `false` | `false` |
| `sub_naming` | `one-per-concept` | `one-per-concept` |
| `sub_fixed` | `[]` | `[]` |
| `sub_pattern` | `^(thresholds\.json\|products/[a-z0-9][a-z0-9-]*\.md)$` | `^[a-z0-9][a-z0-9-]*\.json$` |

阈值表的文件名固定为 `thresholds.json`；可用性判据每产品一份，落 `products/<产品标识>.md`；接线文件每产品一份，落 `<产品标识>.json`。产品标识用小写字母、数字与连字符，与接线文件里的 `product` 字段一致。

这些字面值必须写进 spec 而不是留给实现者，因为解析器直接执行 `sub_pattern`，而现有测试逐项固定这些值——两边各发明一套，第一次运行就会在 `mmw artifact path` 阶段失败。

### 6. 起步流程：建立模式与运行模式

技能启动时按顺序做五件事。第一件不成立就停止，用户提交之后重新发起；后四件不成立时先补齐再继续。

**第一，检查工作区干净。** 运行 `git status --porcelain`，有输出就停下来，让用户先提交，然后重新发起。

这一条是整个技能的地基，它换来四件事：

| 换来什么 | 怎么换来的 |
| --- | --- |
| 范围定义得出来 | 「刚改完的那一块」= 最近一个提交。工作区脏时这个概念不存在——改了三轮没提交，每次算出来的都是同一堆文件 |
| 回退不用自己造机制 | 技能改坏了就 `git revert` 或 `git reset --hard` 到 QA 前那个提交。提交本来就是逐条可回退的 |
| A 类修改可以正常提交 | 工作区本来是干净的，技能改的就是技能改的，不会把用户没写完的代码一起提交进去 |
| 不需要任务绑定 | 见下 |

**技能不需要任务绑定，也不建 worktree。** 界面 QA 唯一的长期产物是判据与接线，它们落的两个类别 `has_name` 为假，不要工作名。界面全图在进程内构建、用完即弃；报告直接交给用户，不落文件——用户的原话是「报告只会变成历史噪音」，那它本来就不该写进仓库。因此没有任何产物需要工作名，`mmw task state` 这一步整个不存在。用户在主检出还是在任务 worktree 里发起，技能行为一致。

**第二，检查依赖。** 三个运行时依赖由 MMW 的安装入口 `mmw/install.sh` 提供并固定版本，技能通过已安装 runtime 的固定入口定位它们，不使用目标仓库碰巧装了什么版本。浏览器自动化框架缺失时停止——它是全部检查的驱动。可访问性规则引擎缺失时降级，跳过 A2；设计系统格式校验器缺失时降级，判据这一轮不校验。其余照常。

**第三，判定产品。** 判据与接线都是按产品的，所以产品必须先定下来。四级，第一级命中就不往下走：

1. argument hint 的自由内容里给了产品名 → 直接用，不问。
2. 没给，但接线文件只有一份 → 用那一份，不问。只做一个应用的仓库永远不会被问到。
3. 没给，接线文件有多份 → 列出来让用户选一次。**列的是接线文件里 `product` 字段的值，不是目录名**，用户看到的是产品的名字，不必记目录叫什么。
4. **一份接线文件都没有**（全新仓库首次运行）→ 直接问用户这次要检查哪个产品，把答案作为产品标识。这一级不能省：第 2、3 级都以接线文件存在为前提，全新仓库两级都不命中；而建立模式在下一步，它要建的文件本身就按产品分，产品名必须先有。

第 4 级问出来的产品名，就是下一步 intake 问卷建立各文件时用的标识，问卷里不再重复问一遍。

一次运行只检查一个产品。要检查第二个就再发起一次。多个产品的结果混进一份报告，用户在裁决时会分不清在答哪个产品的事，而裁决是这个技能里唯一需要用户逐条参与的环节。

**第四，检查判据与接线。** 阈值表、该产品的可用性判据、该产品的接线文件、设计系统文件，缺任何一份就进入**建立模式**：跑 intake 问卷，把缺的那几份建起来，然后自动转入**运行模式**继续本次检查。缺一份和缺四份走同一条路径，只是问卷问的内容不同。

**intake 问卷只问技能查不到的，七个问题一次问完。** 技能自己能查到的不问：设计系统文件在不在、声明了什么组件规格、应用怎么启动（`package.json` 的 scripts 与构建配置）、界面有哪些（代码抽取建全图）、用户在 `/mmw-grilling` 和 spec 里说过的可用性要求。

| # | 问什么 | 技能先做什么，好让用户少打字 |
| --- | --- | --- |
| 1 | 这个产品给谁用、在什么场景下用 | 从 spec 或共同理解抽一段草稿，用户改 |
| 2 | 哪几条是核心流程 | 列出全图里从主窗口出发的可达路径，用户挑 |
| 3 | 哪些元素是刻意做小的展示型元素 | 扫出所有小于通用下限的元素列成候选，用户勾 |
| 4 | 启动方式对不对 | 从构建配置读出候选命令，用户确认或改 |
| 5 | 这个产品跑在哪个环境：本机起的服务，还是真实服务器上的测试账号 | 无法预填，直接问。两个选项二选一，没有第三个。答案写进接线文件的 `environment` |
| 6 | 登录态与测试数据怎么准备 | 无法预填，直接问；答不上来记为空，相关状态进覆盖报告 |
| 7 | Windows 远程调试端口 | 给默认值，用户改或留空 |

**从共同理解与 spec 抽取的可用性判据一次性展示，默认全部接受，用户划掉不要的。** 不逐条确认——那是「一项一项盯」。也不静默采用——抽取是模型判断，抽错的条目会变成长期判据，每轮都拿它判 B5，代价是第一轮报告混进一堆本不该存在的条目，用户还得为每条做一次裁决，裁决又永久留在判据文件里。抽取结果跟着 intake 问卷一起给用户看，不额外增加一次交互。用户扫一眼就能认出哪条是自己的意思、哪条是模型加的——这比裁决一条陌生的 finding 轻得多。

**判据自己要先被检查。** 判据齐了之后，对设计系统文件跑一次格式校验：把接线文件 `designSystem` 字段指向的路径作为参数传给校验器（语法是 `lint <文件>`，输出 JSON 带退出码）。校验器由 MMW 的安装入口提供并固定版本，不用 `npx` 当场拉取，理由见第 14 节。它做的不只是格式校验，还包括**跨 token 的 WCAG 对比度计算**和**引用完整性检查**，不需要启动应用、不需要浏览器。

这一步不可省略，因为 A3 与 B1 拿设计系统当判据，**判据自己违规时，判得越准越糟**——一份声明了「白字配琥珀色」的规范，会让 A3 把读不清的按钮判成合规。

校验结果进报告，**不进九种判拒**：它说的是判据有问题，不是界面有问题。判据的 finding 没有界面上的修复目标，也不进用户裁决。有 `error` 级 finding 时停止本次运行——文件解析不了，A3 与 B1 无从判起；只有 `warning` 时继续，报告中列出。

**第五，确定范围。** 按下一节的三档判定，含降级链。范围确定后写进报告开头。

**四份缺失的性质不同，拒绝建立时的后果也不同：**

| 缺哪一份 | 性质 | 用户拒绝建立时 |
| --- | --- | --- |
| 阈值表 | 必须建 | **停止**。A1 没有判据，而它是最基础的一层 |
| 该产品的可用性判据 | 必须建 | **停止**。B5 没有判据，而这一层承载「贴合真实工作流」这个核心目标 |
| 该产品的接线文件 | 必须建 | **停止**。应用启动不了，九种判拒一种也跑不了 |
| 设计系统 | 提议建 | **继续**。跳过 A3 与 B1，其余七种照常运行，报告顶部声明跳过原因 |

设计系统单独一档，因为缺了它只影响两种判拒，而缺前三份中任何一份技能都跑不起来。这也是它归目标仓库所有、技能只在不存在时建一次的原因。

因此只有三种情况停止：用户拒绝建立前三份中的任意一份、问卷问出来的信息不足以建立能运行的接线文件、判据自检报出 `error` 级 finding。

### 7. 检查范围：三档

技能的主场景是用户在迭代过程中随时喊起来。这时他刚改完一个东西，要检查的是那一块，不是整个应用。浏览器每往返一次要几秒，全量跑一遍几十个状态，等不起。所以范围必须分档，而且默认档要服务主场景。

**三档，与 MMW 的任务模型对齐**，不按「查几个界面」分档：

| 档 | 范围怎么算 | 什么时候用 |
| --- | --- | --- |
| **本次改动**（默认） | `git diff HEAD~1...HEAD --name-only` | 刚提交完一次改动，随手检查 |
| **本任务** | `git diff $(git merge-base HEAD <父分支>)...HEAD --name-only`，父分支默认 `main` | 一个任务完整落地，交出去之前 |
| **全量** | 界面全图里的全部界面与状态，不看 git | 应用初版落地，或去 Windows 那一次 |

固定点的取法与 `/mmw-review` 第 1 步一致，不新造。

**三档都是无状态的，技能不记「上次跑到哪」。** 起步第一步已经保证工作区干净，所以「刚改完的那一块」就是最近一个提交，`HEAD~1...HEAD` 直接算得出来，不需要在任何地方存一个「上次运行提交」。

这一点很重要，因为反过来的做法走不通：若允许工作区脏、并靠记录上次运行时的 `HEAD` 来划范围，那么用户连续改几轮都不提交时 `HEAD` 始终不变，每次算出来的都是同一堆未提交文件——「只查刚改的那一块」就退化成了「每次重查整个脏工作区」。

`HEAD~1` 在任务分支的第一个提交上不存在。这时降到「本任务」档。

**档位由 argument hint 的标签决定，挂了就直接用，不再推断。** 两个标签取值是 `本任务` 与 `全量`；不挂标签走默认档。

**改动的文件怎么变成要查的界面。** 界面全图的每个界面节点记着 `来源文件`（第 10 节）。改动了文件 F，就取所有 `来源文件` 包含 F 的界面节点。这一步是查表，不是新增一遍扫描——代码抽取建全图时本来就知道自己在读哪个文件。

**降级链，三级。降级只改范围，不减判拒。**

| 情况 | 降到哪 | 报告里写什么 |
| --- | --- | --- |
| 本次改动映射出至少一个界面 | 不降 | 正常 |
| 映射出零个界面（改的是后端、配置或文档） | 本任务 | 本次改动未涉及界面文件，范围扩大到本任务 |
| 本任务也映射出零个界面 | 最小子集：接线文件 `mainWindow` 指向的界面，加它在全图里的直接下一级 | 本任务未涉及界面文件，改为检查主窗口及其下一级 |
| `HEAD~1` 不存在（任务分支的第一个提交） | 本任务 | 无需说明，这是首次提交的自然结果 |

**不因为范围推不出来就少跑判拒。** 九种判拒在任何一档上都全部运行，档位只决定它们作用在哪些界面上。

**走查任务跟着范围走。** 范围给出一组界面，走查任务是从 MMW 产物取到的一组完整路径。两者这样对上：

1. 产物里有经过范围内任意一个界面的路径 → 用那几条，经过多条就都用。
2. 产物里一条都没有 → 用全图的跳转关系自己拼：从主窗口出发到范围内每个界面的最短路径，各拼一条。

第 2 条保证 B2、B3、B4 在任何范围下都有路可走。**拼出来的路径必须在报告中标明是拼的**——它只保证走得到，不保证用户真会这么走，语义层基于它得出的结论要打折看。

### 8. 检查执行：结构化数据为主

主要输入是结构化数据，不是截图。四个来源：

- **无障碍树快照**：读界面结构，只含角色与可访问名，不含 class、测试标识、包装元素与内联样式。因此它对前端框架不敏感，同一套方法覆盖原生 DOM、React 与 Web 应用，不需要按框架做适配。
- **批量提取的计算样式与布局盒模型数值**：供 A1 与 A3 判定。间距、尺寸、对比度、是否在首屏内、是否被遮挡，全部用数值判断。
- **运行时的 CSS 自定义属性**：读 `getComputedStyle(document.documentElement)`，拿到实际生效的 token 集合。
- **渲染进程控制台**：供 A4 判定。

**A3 的 token 集合用声明层。** 设计系统文件是**声明**（人写下的意图），运行时的 CSS 变量是**实现**（实际生效的）。A3 这条判拒叫「设计系统 token 越界」，它判的就必须是「元素用的值在不在设计系统声明的 token 集合里」——改用实现层会让它名不副实：实现层多出一个设计系统没声明的 token 时，用这个 token 的元素反而通过 A3，而那恰恰是越界。

**实现层照样要读，用途是判断判据可不可信。** 两组键值对比一比，成本几乎为零：

| 对比结果 | 怎么处理 |
| --- | --- |
| 实现层有、声明层没有 | 这个 token 未经声明。作为报告项报一条（**按 token 报一条，不按使用它的元素逐个报**）。用到它的元素同时被 A3 判为越界，因为它确实不在声明集合里 |
| 声明层有、实现层没有 | 声明已经过时。作为报告项报一条 |

**不一致的条目多到一定程度时，报告必须明确写出「A3 的结果可能失真」。** 这是「拿过时的声明去判会全是噪音」这个担心的正确解法——把脱节暴露给用户，而不是偷偷换一个判据来源。

目标仓库用 Tailwind 4 时，`@theme` 块编译出的就是 `:root` 上的 CSS 变量，官方文档确认可以用 `getComputedStyle(document.documentElement)` 读到。

报告中同时给出一条建议：设计系统的官方 CLI 支持把 token 导出成构建配置能直接用的形式，目标仓库改成从声明生成实现之后，这类不一致不会再出现。**这只是建议，技能不替目标仓库改构建流程。**

截图只在两种情况下使用，并且裁到相关区域，不截整屏：结构化数据判不了的整体视觉印象，以及需要向用户出示证据时。

**A2 的实际覆盖面。** 可访问性规则引擎覆盖对比度、ARIA 误用、缺 label、缺 alt、`tabindex` 取值、`aria-hidden` 元素可聚焦、嵌套交互控件、可滚动区域可达性、跳过链接。

**它不验证实际键盘遍历顺序。** 引擎里与焦点顺序同名的那条规则是实验规则、默认关闭，而且只检查已在焦点序列中的元素角色是否适合交互内容，不追踪按 Tab 时焦点实际走的次序。技能必须在报告中声明这一点，不得让用户以为焦点顺序已被覆盖。

### 9. 语义层：认知走查、Trunk Test 与困惑分

语义层判断界面想表达的功能、流程与目的是否被实现，不判断组件是否存在。

**认知走查四问。** 每一步问：

1. 用户会不会想要达成正确的那个结果
2. 用户会不会注意到正确的操作是可用的
3. 用户会不会把正确的操作与他想达成的结果联系起来
4. 操作之后，用户会不会看到事情在推进的反馈

四问中只有第 2 问需要视觉信息。它同时使用两种输入：结构化的视觉显著度数值（是否在首屏内、尺寸、对比度、是否被遮挡、层叠次序）与一张裁到相关区域的局部截图。第 1、3、4 问只用结构化数据。

**Trunk Test 六问。** 假设用户被直接放到当前这一屏，没有任何上文，他能否回答：

1. 这是什么产品
2. 我现在在哪一个界面
3. 这个界面有哪些主要区块
4. 我在这一层有哪些可选的操作
5. 我处在整个流程的什么位置
6. 我怎么回到上一层，或者找到我要的东西

第 6 问是对桌面应用的调整。来源的原始表述问的是「怎么搜索」，那假设界面上有搜索框。桌面工作台不一定有，所以改成问导航与查找能力。其余五问按原表述。

六问按上面的固定表述提问，不逐个产品改写，这样不同产品的结果可比。任一问答不出，记一条 B4。

**困惑分量表。** 每一屏单独打分，三档：

| 分档 | 含义 |
| --- | --- |
| 完全不困惑 | 当前该做什么一眼可见 |
| 有点困惑 | 需要停下来读或想一下才知道该做什么 |
| 很困惑 | 读完仍不确定该做什么，或有两个以上看起来都对的选项 |

**「偏高」的判定**：任何一屏被评为「很困惑」直接记一条 B3；连续两屏被评为「有点困惑」也记一条 B3，指向这一段路径而不是单屏。单独一屏「有点困惑」不记。

**两条必须落实的做法。**

- **保留完整会话历史**，把已经走过的屏、做过的动作、给过的理由带进后续每一步。不带历史时重复运行的结果彼此不一致。
- **写死一条判据：agent 走得通不等于用户走得通。** 任务完成不作为通过判据。依据见 Further Notes：同一界面人类评估者找出十个失败点，语言模型多轮合计只找出三个，而语言模型的任务完成率更高。

走查任务分两种来源，要求不同：

- **从 MMW 产物取到的路径。** 必须是用户为达成一个真实目的所走的完整路径，跨多个界面，并且至少包含一条失败路径或边界情况。从产物中取到单个操作时向上合并到它所属的完整路径，不拆细凑数。
- **范围内没有产物路径时，用全图跳转关系拼出来的路径**（第 7 节）。不要求含失败路径，但**必须在报告中标明是拼的**。它只保证走得到，不保证用户真会这么走，基于它得出的语义层结论要打折看。

B2、B3、B4 产出的全部内容是 finding 候选，由主 agent 回到当前源码验证后才进入处置。

### 10. 界面全图与覆盖报告

全图记录界面、每个界面的状态与界面之间的跳转。它是认知走查的前提——没有它，走查只能看到当前这一屏。

三个来源按顺序合并：代码抽取打底（路由表、状态机、条件渲染分支），运行时探测补充（启动应用后遍历可达路径），可用性判据补足（记录探测不到、需要特定条件才出现的状态）。

**全图不落文件，在进程内构建，用完即弃。**

每个界面节点带一个 `来源文件` 字段，是数组，记代码抽取这一步读到的、产生这个界面的文件。第 7 节靠它把改动文件映射成要查的界面。这个字段不需要新增一遍扫描——代码抽取建全图时本来就在逐个文件读路由表、状态机与条件渲染分支，把当时的文件名记下即可。

**没有「上次运行提交」这类跨轮次状态。** 起步第一步保证工作区干净，范围三档全部由 git 当场算出（第 7 节），技能不需要记住上次跑到哪，因此全图也不需要持久化。

代价是每次运行都要重建全图：代码抽取是读文件，运行时探测要跑应用。后者本来每次运行都要做——九种判拒里有七种需要应用跑起来——所以重建全图基本是顺带的，不构成额外成本。

三者是并集，不是互斥选择，因此没有「取哪一个」的冲突。同一个状态被多个来源命中时合并成一条，并记录它被哪几个来源命中。到达性由运行时探测单独决定：探测到过的标为已到达，只出现在代码抽取或可用性判据中的标为未到达。未到达的状态保留在全图里，不删除。

**不做跨轮次的全图比较。** 全图每次重建、不持久化，所以拿不到上一次的图，也就不承诺「发现新增和消失的界面」这类跨轮次结论。需要跨轮次留住的东西写进可用性判据，那里才是长期落点。

这不是能力缺失，是分工：界面新增和消失，`git diff` 看得比全图比对准确，而范围判定本来就在用它。

**能到达什么，取决于接线文件。** 空状态、加载态、错误态和权限差异，只要接线文件声明的准备方式能到达，就进入检查。接线文件声明不了的（例如需要注入故障、切换多个权限身份、或在检查中途复位数据），技能不自己发明办法去制造这些状态——那属于产品自己的测试夹具范畴，不在本技能范围。

到不了的状态进**覆盖报告**，逐条写明状态名与到不了的原因。覆盖报告不驱动修改，也不进入用户裁决。

### 11. 平台与通道

Electron 渲染进程本质是 Chromium，运行 HTML、CSS 与 DOM。因此**按 Web 处理**，不作为第三个平台从头设计。外壳差异单列一份补充说明，明确列出在 Mac 上检查不到的行为：Windows 原生菜单、托盘图标与通知、DPI 缩放、系统中文字体回退导致的行高差异、安装包行为与文件关联、原生文件对话框。

**prototype 阶段在 Mac 上运行。** 对象是 mockup 或开发模式启动的应用。

**项目完整落地后在真实 Windows 上运行一次。** 通道是：用户在 Windows PowerShell 里手动启动应用，启动时带远程调试端口；主 agent 从 Mac 连接该端口接管渲染进程，检查步骤全自动。

**Windows 侧照常修改 A 类违规项，但动手前先报数并等用户点头。** 检查跑完后，技能告诉用户这一轮有几处要改、改完需要重新构建并重启几次，用户说继续才动手。用户可以答「这次先只报告」，那就全部转成 finding 带回。

理由是 Windows 那一趟的全部价值就是覆盖 Mac 上测不到的行为——DPI 缩放、系统中文字体回退导致的行高差异这些，把修复推回 Mac 等于查出来了但改不了也验不了，下次再来可能发现改错了，又推回去。这个来回比多按几次启动贵。报数加点头这一步把代价变成用户可控的：只有一两处就顺手做了，有十几处他可以另约时间。

**连接后必须先自检能力。** 通过调试端口接管已有实例，得到的能力低于自行启动的实例。连接成功不等于四项能力都在。技能依次验证：取无障碍树快照、批量提取计算样式、局部截图、注入可访问性规则引擎。任一项失败，本次结果按缺项处理——报告顶部声明哪几项能力不可用、因此哪几种判拒没有运行，**不把缺项结果当成完整 QA**。

技能正文必须写明：不能跨 SSH 启动 Windows GUI，SSH 前台拉起会静默失败。这是目标仓库 `ENGINEERING-RULES.md` 已经记载的铁律。技能同时写明 Windows 侧的界面 QA 不是 AFK 的：**用户至少启动一次，选择让技能修改时每一轮修复再各启动一次**。技能在报数时把预计次数一并说出来，不含糊说成「一次」。

打包安装后的应用不在覆盖范围。目标仓库已有出包实测工具处理这一层，它测的是启动耗时一类指标，与界面 QA 是两件事。

### 12. 处置与回流

**A 类产出违规项，直接修改。** 不占用用户时间，不使用处置标记——它们不是候选。

**B 类产出 finding，走 MMW 既有的五个处置标记**：`accepted`、`rejected`、`duplicate`、`needs-evidence`、`waived`。技能不自动修改，等用户裁决。五个标记各有去向：

| 裁决 | 谁去修 | 存不存进判据 | 下一轮指纹命中时 |
| --- | --- | --- | --- |
| `accepted` | **主 agent 当场修**，与 A 类的修改一起进本次 QA 那个提交 | 存，状态「已确认」 | **再报一次**，标明「上次已确认并修过，现在又出现了」 |
| `rejected` | 不修 | 存，状态「已裁决不成立」 | 压制，不报 |
| `waived` | 不修 | 存，状态「已搁置」 | 压制，不报 |
| `duplicate` | 跟随它指向的那条 | 不单独存 | 不适用 |
| `needs-evidence` | 不修 | **不存** | 不适用 |

**`accepted` 的裁决是回归标记，不是压制标记。** 这一点容易搞反：`rejected` 和 `waived` 的意思是「这不是问题」，所以下一轮命中要压制；`accepted` 的意思是「这是问题，而且已经修了」，下一轮又命中说明**问题复现了**，压制它等于把已确认的缺陷永久藏起来。

**`needs-evidence` 不进判据**，因为它表示主 agent 没能在源码里验证出这条 finding 的出处——它还不是一个成立的判断，存进长期判据会污染判据文件。它只出现在本次报告里。

B 类的修复没有可重跑的确定性检查可验证，它是模型判断。所以验证方式是下一轮：问题真解决了，下一轮不会再产生这条 finding；没解决，下一轮会按上面那条规则再报一次。

**归属裁决。** 界面与判据不一致时，判据层次决定默认归属：与阈值表不一致默认判实现错，因为可执行下限没有「有意改小」的合理场景；与设计系统规则或可用性判据不一致标为需要用户裁决，因为有意改动设计是正常的。

**裁决全部长期保存，不论结论。** 用户对每一条 B 类 finding 的裁决——`accepted`、`rejected`、`waived` 都一样——当场写进该产品的可用性判据，带状态字段区分。只回流 `accepted` 会让被判不成立的条目每轮重复出现。

下一轮怎么认出「同一件事」，由下面的指纹与两级匹配决定。**这是批注次数下降的落地机制**，没有它，「裁决长期保存」只是把条目堆起来，下一轮仍然全部重报。

#### 12.1 A 类违规项的修改流程

**前提是工作区干净**，由起步第一步保证。这个前提让下面每一条都成立，不需要任何自造的回滚机制。

**先跑完全部九种判拒，收集全部结果，再统一进入修改。** 不边查边改。A 类修改会改变界面：A3 改了 token，B1 看到的就是改后的界面，用户在报告里读到的 finding 描述会对不上他打开界面看到的样子。全部检查跑在同一个界面状态上，结果才自洽。

**逐条修改，逐条验证。** 每改完一条，只重跑触发这条违规项的那一项检查。判据是：这条违规项对应的那条判据现在满足了。通过即算修好。

**全部改完之后，把四种 A 类检查整体重跑一遍。** 逐条验证只看得见自己那一条，看不见「这次修改是否引入了别的 A 类问题」。整体重跑补上这一层，成本很低——A1 读数值、A2 跑规则引擎、A3 比对 token 集合、A4 读控制台，全是确定性检查，不需要模型判断，也不需要重走语义层。

**B 类不重跑。** 用户裁决时看到的是修改前的界面，这一点在报告里写明。A 类改的是阈值、WCAG、token、运行时错误这四类确定性问题，不改变 B 类关心的流程与语义。

**改坏了用 git 退回去。** 整体重跑发现新的 A 类违规项，或某条逐条验证没过，就退回该次修改。工作区在 QA 开始时是干净的，所以退回是 `git checkout -- <文件>` 这一级的操作，不需要快照对象。退回的那条降级成 finding 报给用户，标明「尝试修复失败」。

**改不了源码的一律不改。** 违规项定位到第三方组件内部或依赖包里的文件时，不修改，转成 finding 报给用户。

**本次 QA 的全部 A 类修改合成一个提交。** 提交信息写明这是界面 QA 的修改、改了哪几条违规项。

选一个提交而不是一条一个，理由是回退的实际用法：用户要么接受这一轮修改，要么整轮退掉（`git revert <该提交>`），逐条 revert 不是真实场景。报告第 1 节仍逐条列出改了什么，要单独退某一条，用户在这个提交的基础上自己改。

技能敢提交，是因为起步第一步保证了工作区干净——**这个提交里只有技能改的东西，不可能夹带用户没写完的代码**。这也是「必须先提交」这个前提换来的第三件事。

#### 12.2 指纹：哪条判拒 + 哪个位置

每条 B 类裁决存一个指纹，两截：判拒编号，加位置。位置按判拒的天然粒度取，四种形态。**指纹由技能自动生成，用户不参与。**

**元素级（B1、B5）**

```
判拒：B1
判据：DS-规则3          ← 被违反的是哪一条
界面：main
状态：default
元素角色：button
元素名：同步
```

界面与状态两个字段直接取全图已有的标识。元素角色与元素名取无障碍树快照里的值。

**`判据` 字段不能省。** 同一个元素可能同时违反两条不同的判据——一个按钮既不符合设计系统的间距规则，又不满足某条产品可用性判据。不记被违反的是哪一条，两条 finding 的指纹完全相同，用户对其中一条判 `rejected`，会把另一条真实问题一并压制掉。

取值：B1 取设计系统正文里那条规则的标识，B5 取可用性判据的条目编号。B2、B3、B4 的判据是技能自带的方法判据，由下面各自的 `问` 或 `步骤` 字段区分，不另设 `判据` 字段。

**这里有意不用 CSS 选择器。** 浏览器自动化框架的官方无障碍测试文档给的指纹做法是「规则 ID + 元素选择器」。选择器带 class 名与 `nth-child`，界面一重排就全变。角色加可访问名稳定得多，而且第 8 节已经定了主输入是无障碍树快照，「只含角色与可访问名，不含 class、测试标识、包装元素」——用它做指纹与主输入同源，不引入第二套定位方式。

**步骤级（B2）**

```
判拒：B2
走查任务：新建同步任务
步骤：3
问：2
```

`问` 是认知走查四问的第几问。同一步在第 2 问和第 4 问上失败是两件事，分开记。

**屏级（B4）**

```
判拒：B4
界面：main
状态：default
问：5
```

**屏级或路径级（B3）**

```
判拒：B3
界面：[main]
状态：[default]
```

界面与状态是数组。单屏「很困惑」时长度为 1；连续两屏「有点困惑」记的那一条指向一段路径，长度为 2。

**A 类不记指纹。** 它直接修改，不产生裁决，没有要记住的东西。

#### 12.3 两级匹配

每次运行，把本轮每一条 B 类 finding 的指纹，与该产品可用性判据里已有的裁决逐条比对。

| 级 | 条件 | 结果 |
| --- | --- | --- |
| 第 1 级 · 全等 | 指纹每个字段都相同 | 同一件事。按已有裁决处理，**不报给用户** |
| 第 2 级 · 近似 | 判拒相同，位置字段**恰好只有一个**不同 | 可能是同一件事。报给用户，附上上一轮的裁决，问是不是同一件事 |
| 都不中 | 判拒不同，或两个以上位置字段不同 | 新问题，正常报 |

「恰好只有一个字段不同」是确定性规则，同样的输入永远得到同样的结果，不依赖模型判断。它覆盖的是界面迭代中最常见的三种改动：

| 改了什么 | 哪个字段变 | 落在哪级 |
| --- | --- | --- |
| 按钮文案从「同步」改成「立即同步」 | 元素名 | 第 2 级 |
| 状态从 `default` 拆成 `default` 与 `syncing` | 状态 | 第 2 级 |
| 走查任务中间插一步，原第 3 步变第 4 步 | 步骤 | 第 2 级 |
| 按钮换了界面又改了名 | 界面 + 元素名 | 新问题 |

最后一行是有意的：既换界面又改名的元素已经不是原来那个东西，重新问一次是对的。

**第 2 级命中后的处理。** 用户答「是」，技能把这条裁决的指纹更新成本轮的新值，以后按裁决处理；答「不是」，当新问题，用户重新裁决，判据里多一条。

**为什么不用回退式匹配。** 代码分析工具那边用的是多级回退——位置对不上就退而比对内容或消息，自动判为同一件事。那套在代码上成立，因为代码改一行周围几十行不动。界面改一版可能整屏重排，同样的回退在这里误压制的概率高得多。所以我们在第 2 级停下问用户，而不是自动判定。用户只答「是/不是」，比从头裁决一遍轻得多。

#### 12.4 陈旧裁决：只列出，不自动删

每次运行结束，检查该产品可用性判据里的裁决条目。**只检查指纹落在本轮范围内的那些**：指纹的界面在本轮检查过，而本轮既没有被第 1 级、也没有被第 2 级命中，才列进报告最后一节，标题写明「这几条裁决本轮没有对应的检查结果，可能已经失效」。

**范围外的裁决一律不参与陈旧判定。** 默认档只查本次改动，绝大多数界面本轮根本没被检查，当然不会命中——把它们列成「可能失效」是把「没查」当成了「查过但没发现」，会诱导用户删掉仍然有效的判据。B2 的指纹按走查任务定位，同理只在本轮实际走过的走查任务范围内判定。

因此只有「全量」档会对全部裁决做一次完整的陈旧检查。这也是合理的：那一档本来就是用在初版落地和上 Windows 之前，正是适合清理判据的时机。

**只列出，不自动删除，也不因此让运行失败。** 代码检查工具那边是在问题修好后以非零退出码报错，那套面向持续集成流水线；界面 QA 面向的是用户在迭代中随手发起，报错会打断他。用户看到了想删就说一句。

这一条防的是判据腐烂——裁决只增不减，会长成一份越来越大、且在压制早已不存在的问题的文件。

#### 12.5 报告结构：五节

报告固定五节，按「要用户做什么」排序：

| 节 | 内容 | 要用户做什么 |
| --- | --- | --- |
| 1 · A 类改了什么 | 每条一行：违规项编号、文件与位置、改前值、改后值、验证结果。末尾给出本次修改的提交 SHA | 不做事，看一眼。要整轮退掉就 `git revert` 那个 SHA |
| 2 · B 类新 finding | 第 1 级第 2 级都没中的。标 `已回滚` 的 A 类也出现在这里 | 逐条裁决 |
| 3 · B 类近似匹配 | 第 2 级命中的，每条附上一轮裁决 | 每条答「是/不是」 |
| 4 · 三类报告项 | 覆盖报告、判据自检结果、声明与实现不一致 | 不做事，可选择说一句 |
| 5 · 陈旧裁决 | 指纹落在本轮范围内、却没有对应检查结果的裁决 | 不做事，想删就说一句 |

第 2 节与第 3 节分开，因为第 3 节要的只是「是/不是」，比新 finding 好答得多，混在一起会让用户按同一种强度去想每一条。

第 4、5 节分开，因为两者的性质不同：第 4 节说的是**本次检查的边界**（哪些没查到、判据自身有什么问题），第 5 节说的是**已有判据可能该清理了**。合成一节会让用户以为覆盖缺口也需要他处理。

第 1 节的「验证结果」栏取两个值：`已验证`（逐条重跑该项检查通过，且全部改完后的整体重跑没有引入新的 A 类违规项）或 `已回滚`（任一环节未过，修改已撤销）。标 `已回滚` 的那几条同时出现在第 2 节，作为标明「尝试修复失败」的 finding。

报告开头固定五行，写在五节之前：

```
本次范围：本次改动（未指定，默认档）
覆盖：3 个界面 / 7 个状态
未覆盖：12 个界面 / 31 个状态
判据：阈值表 v1 · 小黄鸭可用性判据 14 条 · 设计系统已读
本次跳过：无
```

范围因降级变过时，第一行写成「本次改动 → 本任务（本次改动未涉及界面文件）」，把降级原因带上。「本次跳过」那一行接既有的降级情况：设计系统文件缺失写「A3、B1（设计系统文件不存在）」，Windows 能力自检有缺项写缺哪几项。

**被采信的 B1 回流到可用性判据，不回流到设计系统。** 设计系统只读，改不了。所以采信的设计系统规则违反，写成该产品可用性判据里的一条，正文记录它是对哪条设计系统规则在本产品上的具体化，来源指向那条规则。

**属于阈值性质的裁决进阈值表。** 例如用户确认某类元素的最小尺寸，写进阈值表，下一轮由 A1 直接判定。

每条回流都写明来源为本次界面 QA 与日期。

### 13. 角色与派发

不新增角色。认知走查的评估者使用既有的 `designer` 角色，只读、独立上下文。派发使用完整动作块，由 `mmw skills materialize` 整块替换，技能正文不按宿主名称分支。

**浏览器由主 agent 独占，`designer` 拿不到它。** 两条理由：A 类检查已经占着同一个应用实例，两边同时驱动会互相干扰；`designer` 是独立上下文，它要自己开实例就意味着应用状态归零，走到第五步才出现的那个界面它到不了。

**派发粒度是一条完整路径一个 `designer`，不是一步一个。** 认知走查四问要带完整会话历史（第 9 节）。一步一派时每个 `designer` 的上下文都是空的，第 4 问「操作之后用户会不会看到事情在推进」根本判不了——判它需要知道操作之前是什么样。

**交接顺序：主 agent 先把整条路径走完，再一次性交付。** 主 agent 按路径逐步操作应用，每一步采集下表的数据，全部走完之后把整条路径的数据包一次交给 `designer`。

**路径包的字段。** 路径级：

| 字段 | 类型 | 内容 |
| --- | --- | --- |
| `产品名` | 字符串 | 本次检查的产品 |
| `路径名` | 字符串 | 这条路径做的事，一句话 |
| `用户目的` | 字符串 | 用户走这条路径想达成什么。认知走查第 1 问判的就是它 |
| `来源` | 枚举 | `产物` 或 `拼的`。`拼的` 时 `designer` 的结论在报告里要标注打折看（第 9 节） |
| `步骤` | 数组 | 见下表，按执行顺序 |

每一步：

| 字段 | 类型 | 内容 |
| --- | --- | --- |
| `序号` | 整数 | 从 1 开始 |
| `界面标识` | 字符串 | 界面全图里的节点标识 |
| `界面标题` | 字符串 | 用户看得到的那个标题 |
| `本步动作` | 字符串 | 这一步做了什么操作。第一步写「到达此界面」 |
| `可操作元素` | 数组 | 每项含 `名称`、`角色`、`是否在首屏内`、`尺寸`、`对比度`、`是否被遮挡`、`层叠次序`。第 2 问用它 |
| `无障碍树快照` | 文本 | 本步执行后的快照 |
| `动作后的变化` | 字符串 | 主 agent 比对动作前后两份快照得出的差异描述。第 4 问用它 |
| `局部截图路径` | 字符串 | 裁到相关区域的那一张。第 2 问用它，其余三问不看 |
| `运行时报错` | 数组 | 本步产生的报错。为空写空数组 |

**截图落临时目录，运行结束删除。** subagent 读不到主 agent 进程里的字节，截图只能走文件。落点用 `mktemp -d` 当场创建的目录，路径随数据包交给 `designer`，本次运行结束时整个目录删掉。**不走 `mmw artifact path`**：它回答的是产物落点，而这些截图在本次运行之后没有任何消费者；而且 `scratch` 类别要求工作名，起步流程已经取消任务绑定（第 6 节），取不到工作名。

**会话历史不落文件。** 整条路径的数据包本身就是完整历史，一次进 `designer` 的上下文。它在一次任务内看得到前面每一步，第 4 问因此判得了。

**`designer` 交回什么。** 一份结构化列表，每条含：`判拒`（`B2`、`B3`、`B4` 之一）、`步序号`、`界面标识`、`元素`（判到具体元素时填，否则留空）、`失败的是哪一问`（认知走查四问或 Trunk Test 六问的编号）、`一句话问题`、`理由`。另交一份困惑分，每步一档，取值是第 9 节那三档之一——B3 由主 agent 按第 9 节的判定规则从困惑分算出，不由 `designer` 直接报。

**交回之后主 agent 做什么。** 按 `/mmw-verifying-agent-output` 回到当前源码验证每一条的出处。验证不出来的不进处置（第 12 节）。

**本版不做跨模型独立审查。** 既有的审查者组动作块是六道审专用——它的展开模板写死了「⓪、①、②、⑤ 每个视角」，两个审查角色也登记为由 `/mmw-review` 派发。把它用在界面 QA 上，各宿主展开后会得到六道审的派发说明，而不是界面 QA 的评估动作。要做跨模型评估必须新增角色与启动组，那是另一件事的规模，不在本 spec 范围。

### 14. 运行时依赖

**三个**，不是两个：

| 依赖 | 用途 | 缺失时 |
| --- | --- | --- |
| 浏览器自动化框架 | 启动 Electron、取无障碍树快照、批量提取计算样式、读运行时 CSS 变量、局部截图 | **停止**。它驱动全部检查 |
| 可访问性规则引擎 | 供给 A2 | 降级，跳过 A2，其余照常 |
| 设计系统格式校验器 | 起步第五步的判据自检 | 降级，报告顶部标明判据这一轮没有被校验过，其余照常 |

第三个是判据自检引入的。早先写「只有两个」是在加入判据自检之前定的，那句话现在不成立。

**三个都由 MMW 的安装入口提供并固定版本。** `mmw/install.sh` 是本机安装的统一入口。技能通过已安装 runtime 的固定入口定位它们，**不用 `npx` 当场拉取**——`npx` 在离线环境下直接失败，在联网环境下取到的版本不受控；而设计系统格式规范目前是 alpha、可能有破坏性变更，版本不固定会让判据自检的结果在两台机器上不一致。

**格式校验命令必须带文件参数。** 它的语法是 `lint <文件>`，不接受省略。技能把设计系统文件的路径显式传进去，路径从接线文件的 `designSystem` 字段取。

三个依赖的安装行为需要在 `mmw/install.sh` 里落地，并由 Testing Decisions 里的安装校验覆盖。

明确不依赖任何界面 QA 工具或技能合集的运行时。目标仓库的设计系统文件按判据 3 只读，不要求生成它的工具在场。

## Failure Paths

| 失败情况 | 触发条件 | 负责处理的边界 | 用户观察到的结果 | 系统行为 |
| --- | --- | --- | --- | --- |
| 工作区不干净 | `git status --porcelain` 非空 | 界面 QA 起步阶段 | 技能列出未提交的文件，说明必须先提交 | 停止本次运行。技能不替用户提交，也不用快照绕过 |
| 一份接线文件都没有 | 接线文件的类别目录不存在，或目录下没有文件 | 起步第三步 | 技能直接问用户这次要检查哪个产品，并给出产品标识的取值规则 | 拿到产品标识后进建立模式；用户答不上来就停止 |
| 判据或接线缺失 | 阈值表、该产品可用性判据、该产品接线文件缺任意一份 | 界面 QA 起步阶段 | 技能提出 intake 问卷，只问缺的那部分 | 进入建立模式，建立后自动转入运行模式继续本次检查 |
| 用户拒绝建立 | 用户不答 intake 问卷 | 界面 QA 起步阶段 | 技能说明缺哪几份、缺了会少跑哪几种判拒 | 停止本次运行 |
| 接线信息不足 | 问卷答完仍拿不到能启动应用的信息 | 界面 QA 起步阶段 | 技能说明还缺哪几项 | 停止本次运行，不猜测启动方式与环境变量 |
| 浏览器自动化框架缺失 | 依赖未安装或入口定位失败 | 界面 QA 驱动层 | 技能说明依赖由 MMW 安装入口提供，指出重装动作 | 停止本次运行，全部检查都依赖它 |
| 可访问性规则引擎缺失 | 依赖未安装或调用失败 | 界面 QA 驱动层 | 报告声明本次跳过 A2 | 跳过 A2，其余照常运行 |
| 设计系统文件缺失 | 接线文件指向的文件不存在，或接线文件未声明它 | 起步第四步 | 技能提议建一份，说明建法与三条约束 | 进建立模式；用户同意就建完转只读，拒绝才跳过 A3 与 B1，其余七种照常 |
| 判据自检报出 `error` | 设计系统文件格式校验有 `error` 级 finding | 起步第四步 | 报告写出全部 error finding | 停止本次运行。文件解析不了，A3 与 B1 无从判起 |
| 判据自检报出 `warning` | 跨 token 对比度不足、引用不完整、缺 `primary` 等 | 起步第四步 | 报告列出全部 warning，标明这是判据的问题不是界面的问题 | 继续运行，九种判拒照常。判据 finding 不进裁决，也不驱动界面修改 |
| 格式校验命令跑不起来 | 依赖拉取失败或命令非零退出且无 JSON 输出 | 起步第四步 | 报告声明判据未经校验 | 继续运行，但在报告顶部标明 A3 与 B1 的判据这一轮没有被校验过 |
| 声明与实现的 token 不一致 | 设计系统声明的 token 与运行时 CSS 变量对不上 | 界面 QA 检查执行 | 报告第 4 节列出不一致的 token，并标明 A3 这一轮的结果可能失真 | A3 仍按声明层判定，不中止，不改构建配置，不拿实现层顶替声明层 |
| 接线文件没写 `environment` | 起步第三步读到的接线文件缺这个字段 | 界面 QA 起步阶段 | 技能说明必须先确定这次跑在哪个环境 | 停止本次运行。不默认连生产环境 |
| 应用启动失败 | 启动命令返回非零，或超时未出现主窗口 | 界面 QA 驱动层 | 报告写出启动命令、环境变量与原始错误 | 停止本次运行，不用部分结果冒充完整 QA |
| Windows 端口连不上 | 主 agent 无法连接用户手动启动时开的远程调试端口 | 界面 QA 驱动层 | 技能说明端口号，并提示应用必须在交互式会话中启动 | 停止 Windows 侧运行，明确不尝试跨 SSH 启动 GUI |
| Windows 已连接但能力不足 | 连接成功，但取快照、提取样式、局部截图、注入规则引擎四项自检有任一项失败 | 界面 QA 驱动层 | 报告顶部声明哪几项能力不可用、因此哪几种判拒没有运行 | 按缺项处理，继续跑能跑的部分，**不把缺项结果当成完整 QA** |
| 全图建不全 | 代码抽取与运行时探测都到不了某些已知状态 | 界面 QA 全图构建 | 覆盖报告列出到不了的状态与各自原因 | 继续本次运行，这些状态进覆盖报告，不驱动修改，不静默略过 |
| 接线文件有多份，用户没点名产品 | 起步第三步 | 界面 QA 起步阶段 | 技能列出各接线文件的 `product` 值，让用户选一次 | 选定后继续，一次运行只检查一个产品 |
| 本次改动映射不出界面 | 改动的文件在全图里没有对应界面（改的是后端、配置或文档） | 界面 QA 范围判定 | 报告第一行写「本次改动 → 本任务」并给出原因 | 降到「本任务」档继续，**不减判拒** |
| 本任务也映射不出界面 | 本任务的改动文件在全图里都没有对应界面 | 界面 QA 范围判定 | 报告第一行写「改为检查主窗口及其下一级」 | 降到最小子集继续，**不减判拒** |
| 范围内没有产物路径 | MMW 产物里没有一条路径经过范围内界面 | 界面 QA 任务取源 | 报告标明本次路径是拼的，结论要打折看 | 用全图跳转关系拼最短路径，B2、B3、B4 照常运行 |
| 走查任务产物完全取不到 | 当前阶段对应的 MMW 产物不存在 | 界面 QA 任务取源 | 技能说明查过哪些产物 | 全部改用拼出来的路径，并标明。**不跳过 B2、B3、B4** |
| finding 无法回到源码定位 | 模型产出的候选在当前源码中找不到对应位置 | 主 agent 验证阶段 | 该条标为 `needs-evidence` | 不进入修改，也不当作已确认缺陷 |
| 修复后验证不通过 | 逐条重跑该项检查原违规项仍在，或全部改完后的 A 类整体重跑发现了新的违规项 | A 类修改流程 | 报告第 1 节该行验证结果写 `已回滚` | `git checkout -- <文件>` 退回该次修改。工作区在起步时是干净的，退回不会碰到用户的东西。该条降级成 finding 进第 2 节，标「尝试修复失败」 |
| 违规项定位到改不了的地方 | 位置落在第三方组件内部或依赖包文件里 | A 类修改流程 | 报告说明该条不修改的原因 | 不修改，转成 finding 报给用户 |
| 语义层 `designer` 交不回结构化结果 | 派发返回空、格式对不上，或中途失败 | 主 agent 验证阶段 | 报告顶部「本次跳过」写「B2、B3、B4（语义层评估未返回结果）」 | 跳过这三种判拒，A 类与 B1、B5 照常。不拿主 agent 自己的判断顶替独立上下文的评估 |
| 截图临时目录创建失败 | `mktemp -d` 非零退出 | 界面 QA 语义层 | 报告说明认知走查第 2 问缺少视觉输入 | 继续跑，B2 的第 2 问只用结构化的视觉显著度数值判定，并在该条 finding 上标明没有截图 |
| Windows 侧用户不同意修改 | 报数后用户答「这次先只报告」 | A 类修改流程 | 报告写明本次未修改及原因 | 全部违规项转成 finding 带回，不修改 |

## Testing Decisions

好测试只验证外部可观察的行为：给定一份技能源与一份配置，命令与物化产出了什么、哪些输入必须当场失败。不测模块内部私有函数，不把当前技能正文的内容当作预期值。

**机械校验的边界。** 技能正文的内容质量不进机械校验。认知走查四问写得对不对、Trunk Test 六问的表述是否合适、判据分层合不合理、Windows 通道说明是否准确，这些属于产物质量、方法选择与语义真实性，由 ① spec 审与 final 终审判断。不用计数、列表形状、固定阈值或豁免清单伪装成机械校验。

**四个既有 seam 复用，加一个新 seam。** 新的那一个是运行时依赖装配——三个依赖由 `mmw/install.sh` 提供并固定版本（第 14 节），而 `mmw/cli/tests/` 下当前一条安装相关的断言都没有，`mmw/test.sh` 的十条也全都不碰 `install.sh`。这是本次真正新增的合同面，不补就没有任何东西挡得住「依赖没装、版本没固定、或者有人改回 `npx`」。

| Seam | 验证的外部行为 | 选择这一层的原因 |
| --- | --- | --- |
| 技能引用校验（`mmw/cli/tests/test_skill_refs.sh`） | 新技能正文里的四类引用都指得到真东西：点名的技能目录存在、同目录 reference 文件存在、指向别的技能「第 N 步」时那一步存在、写出的命令与子命令 CLI 里存在 | 新技能一次引入四类引用，全部是断了不会产生任何运行时报错的那种，读到的 agent 只会自己编一个 |
| 技能落点字面值校验（`mmw/cli/tests/test_skill_paths.sh`） | 新技能正文不写类别根字面值加占位符、不写工作目录根默认值、不按序号从别的命令输出里取值 | ADR-0006 与 ADR-0009 的机械落地。界面 QA 要读写两个新类别，正是最容易写死类别根的地方 |
| 技能物化（`mmw/cli/tests/test_materialize_skills.py`） | 新技能的动作块在三个能物化技能的宿主各展开成什么文本、哪些文件不该出现、哪几种输入必须当场失败；**新技能的 `argument-hint` 在三个宿主的产物里逐字保留** | 发布面最后一道。技能正文写对而这一层错时，各宿主拿到的是错的技能，且正文读起来仍然通顺 |
| 产物落点解析（`mmw/cli/tests/test_artifact.sh`） | 两个新类别的路径形状解析正确：`has_name` 为假时不带名字段、`sub_pattern` 接受阈值表文件名与按产品分文件、拒绝不匹配的取值、两个类别出现在无参用法输出中 | 新增产物类别是可解析的机械事实，必须在数据层锁住。当前解析器直接执行 `sub_pattern`，不加测试就会在第一次运行时才发现 |
| 运行时依赖装配（`mmw/install.sh`，**新增 seam**） | `install.sh` 里每一个界面 QA 依赖的声明都带固定版本、都不是 `npx` 当场拉取；技能正文引用的每个依赖入口名都能在这些声明里找到 | 这是引用完整性检查，与既有的技能引用校验同一家族：静态可判定，不联网、不真装包。装不上或版本漂了，判据自检的结果会在两台机器上不一致，而技能正文读起来完全正常 |

**`argument-hint` 这一项是本次新引入的覆盖面。** 三个宿主的既有产物确实逐字保留了这个字段（对 `mmw-wayfinder` 的四份产物逐一核对过），但 `mmw/cli/tests/` 下当前**没有任何一条断言检查它**。本技能把范围档与产品名全部压在这个字段上，字段丢失或被改写时，用户挂的标签不再生效，而技能正文读起来完全正常。所以这条断言必须补上。它落在既有 seam 内部，不是新 seam。

**保留它的代码路径要认准。** `materialize_skills.py` 里解析并重新序列化 `argument-hint` 的那一段位于 `render_pi_prompt`，只处理 Pi 的用户命令；三个宿主的普通技能走的是 `materialize_host`，它直接保留整个 frontmatter。断言要针对后者，只覆盖 Pi 那条分支会漏掉三个宿主的普通技能产物。

**另需决定**：新技能不设 `disable-model-invocation`。设了它就不会物化到 Pi（`handoff`、`mmw-start`、`wait-what` 三个技能就是这样），而界面 QA 要被 `/mmw-prototype` 与 `/mmw-review` 点名调用，必须对模型可见。

具体测试写法由 `/mmw-tdd` 与目标仓库的 `TESTING.md` 规定。全量校验入口是 `bash mmw/test.sh`。

## Contract Boundaries

**三份跨边界数据**，归属方与消费方如下。三份都是 JSON 或带结构的 Markdown，**都必须带 `version` 整数字段**：格式变化时技能据此认出旧文件并说明，而不是静默误读。界面全图不在其列——它在进程内构建、不跨边界。

`version` 的处理规则：技能认识的版本号写在技能正文里；读到更大的版本号时停止并说明文件由更新版本的技能写成；读到更小的版本号时按当前版本读取，并在报告中留一行提示。文件损坏或不是合法 JSON 时停止，写出解析器的原始错误，不猜测内容。

**未知内容按设计系统规范给出的那张消费者行为表处理**，不另立一套：未知的段落保留、不报错；未知的键，值合法就接受；未知的属性接受但在报告中留一行提示；重复的同名段落报错并拒绝该文件。

这四条不是我们发明的容错规则，是我们已经依赖的那份格式规范自己定义的消费者行为。三份数据用同一套，读设计系统和读我们自己的判据行为一致，实现者不需要记两套规矩。

**接线文件。** 归属方是目标仓库，消费方是界面 QA。每个产品一份。字段与规则：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `version` | 整数 | 是 | 格式版本 |
| `product` | 字符串 | 是 | 产品标识。小写字母、数字与连字符，与可用性判据的文件名一致 |
| `launch` | 对象 | 是 | 见下 |
| `mainWindow` | 对象 | 是 | 见下 |
| `environment` | 对象 | 落地后那一档必填 | 见下 |
| `prepare` | 对象 | 否 | 见下。缺失时相关状态进覆盖报告 |
| `designSystem` | 字符串 | 否 | 设计系统文件的仓库相对路径。缺失时跳过 A3 与 B1 |
| `windows` | 对象 | 否 | 见下。只在 Windows 侧运行时需要 |

五个对象的内部字段：

| 对象 | 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- | --- |
| `launch` | `command` | 字符串数组 | 是 | 启动命令与参数，逐个元素一项，不是待解析的整行 |
| `launch` | `cwd` | 字符串 | 否 | 仓库相对路径。缺省为仓库根 |
| `launch` | `env` | 字符串到字符串的映射 | 否 | 启动环境变量。值可以是凭证引用 |
| `launch` | `readyTimeoutMs` | 整数 | 否 | 等待主窗口出现的上限。缺省 30000 |
| `mainWindow` | `titlePattern` | 字符串 | 二选一必填 | 匹配窗口标题的正则 |
| `mainWindow` | `urlPattern` | 字符串 | 二选一必填 | 匹配渲染进程地址的正则 |
| `environment` | `kind` | 枚举 | 是 | `local-server` 或 `test-account` |
| `environment` | `endpoint` | 字符串 | 是 | 本地服务器地址，或真实服务器地址 |
| `environment` | `account` | 对象 | `kind` 为 `test-account` 时必填 | 测试账号的标识与凭证引用 |
| `prepare` | `steps` | 对象数组 | 否 | 每项含 `name` 与 `command`（字符串数组），按顺序执行 |
| `windows` | `debugPort` | 整数 | 是 | 远程调试端口 |
| `windows` | `host` | 字符串 | 否 | 缺省 `127.0.0.1` |

**`environment` 是数据安全的唯一保障。** 项目完整落地后跑 QA 时，走查任务是完整用户路径且至少含一条失败路径，agent 会真的点下去——真的新建、真的提交、真的触发错误。所以那一档必须声明环境，而且只接受两种：本机起的本地服务器，或真实服务器上的测试账号。两者都与生产数据隔离，因此**技能不需要禁止操作清单，也不需要为不可逆操作逐个停下来问用户**。

`environment` 缺失或 `kind` 不是这两个值时，落地后那一档停止并说明。prototype 阶段那一档不要求这个字段——那时检查的是 mockup 或开发模式启动的应用，本来就不连生产。

**凭证只存引用，不存明文。** 引用的结构是固定前缀加名字：`env:<环境变量名>` 或 `keychain:<条目名>`。技能运行时按前缀取值。写成其他形态的一律当作明文拒绝，并停止运行。必填字段缺失时按 Failure Paths 处理，不填默认值。

**阈值表。** 归属方是界面 QA，仓库一份，文件名 `thresholds.json`。除 `version` 外，顶层是阈值项的映射，每项四个字段：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `value` | 数值 | 是 | 阈值 |
| `unit` | 枚举 | 是 | `px` 或 `ratio`。不接受无单位裸数 |
| `appliesTo` | 枚举 | 是 | `interactive`（可点击元素）或 `presentational`（展示型元素） |
| `compare` | 枚举 | 是 | `min` 或 `max`。决定「小于算违规」还是「大于算违规」 |

`appliesTo` 与 `compare` 两项不能省。前者区分可点击与展示型，后者说明比较方向——同一个数值在缺少比较方向时无法判定，实现者只能猜。初始值必须与目标仓库既有组件规格对齐，不照搬通用值——目标仓库存在高度低于常见触控下限的展示型组件，直接套用通用下限会把它们误判成违规，因此阈值需要区分可点击元素与展示元素。

**可用性判据。** 归属方是界面 QA，每个产品一份。每条判据六项：

| 字段 | 必填 | 内容 |
| --- | --- | --- |
| 编号 | 是 | 条目标识 |
| 正文 | 是 | 判据内容 |
| 来源 | 是 | 从哪次讨论、哪份 spec 或哪次界面 QA 来 |
| 状态 | 是 | 「已确认」「已裁决不成立」「已搁置」之一，对应用户裁决结果 |
| 指纹 | 由裁决产生的条目必填 | 第 12.2 节四种形态之一。技能自动生成 |
| 最后命中 | 由裁决产生的条目必填 | 这条最近一次被第 1 级或第 2 级匹配命中的日期 |

从 intake 问卷或从共同理解、spec 抽取来的判据没有指纹——它们不是从某一次具体检查结果裁决来的，没有对应的界面位置。这类条目每轮都参与 B5 判定，不参与两级匹配。

**界面全图。** 归属方是界面 QA，进程内构建，不落文件，因此不是跨边界数据，没有 `version` 字段。结构如下：

| 位置 | 字段 | 内容 |
| --- | --- | --- |
| 界面节点 | 标识 | 路由或窗口标识 |
| 界面节点 | `来源文件` | 数组。代码抽取读到的、产生这个界面的文件 |
| 状态节点 | 标识 | 界面标识加状态名 |
| 跳转节点 | 标识 | 起点加终点加触发动作 |

**没有「上次运行提交」这类顶层字段。** 全图不落文件，跨轮次留不住任何东西；范围三档也不需要它，全部由 git 当场算出（第 7 节）。

同一状态被多来源命中时按标识合并，并记录命中来源与是否已到达。

**设计系统文件是只读边界。** 界面 QA 读它，不写它。它的所有权属于目标仓库。

## Release Risk

**新技能的发布面同步。** 产品版本号必须按 `AGENTS.md` 的发布表在五处同步：`mmw/.codex-plugin/plugin.json`、`mmw/.claude-plugin/plugin.json`、根 `.claude-plugin/marketplace.json` 的插件版本、根 `.claude-plugin/marketplace.json` 的顶层版本、`mmw/package.json`。根 `.agents/plugins/marketplace.json` 是 Codex 的发布入口，**不是版本号位置**，不要在那里改版本。

**三个宿主的技能登记方式不一样，只有一处要手动加条目。** 逐份核对过：

| 宿主 | 登记文件 | 当前形态 | 新增技能要做什么 |
| --- | --- | --- | --- |
| Claude Code | `mmw/.claude-plugin/plugin.json` 的 `skills` | 29 项的数组，逐个技能列出 | **必须手动追加一条** |
| Codex | `mmw/.codex-plugin/plugin.json` 的 `skills` | 单个字符串 `"./skills-codex/"` | 不动，物化目录后自动取得 |
| Pi | `mmw/package.json` | 只登记技能目录 | 不动，物化目录后自动取得 |

写成「登记进对应宿主的 manifest」会让实现者去改三份文件，其中两份改了反而出错。

**技能只发布到三个宿主。** 技能物化的目标是 Pi、Claude Code、Codex。Cursor 只物化原生 subagent，`mmw agents materialize` 不发布技能，因此 **Cursor 上没有 `/mmw-ui-qa`**。这不是遗漏，是当前发布面的事实；技能与文档都要如实说明，不承诺四宿主。

**部署顺序。** 先落技能源与两个新产物类别，再物化，再同步版本号与 Claude Code 的技能清单，最后跑全量校验。顺序颠倒时物化产物会与源不一致，而 `skills materialize --check` 是发现这一点的地方。

**新的用户交付物。** 用户通过升级已安装的 MMW runtime 取得这个技能，入口是 `mmw/install.sh`。三个运行时依赖也在这个入口安装并固定版本。目标仓库侧不需要新的初始化动作——判据与接线文件由技能第一次运行的建立模式产生。

**设计系统格式规范目前是 alpha。** 规范文件的 `version` 字段当前值就是 `alpha`，官方明确标明可能有破坏性变更。我们把 A3 与 B1 的判据地基押在它上面，所以：技能读取时按规范给出的「未知内容的消费者行为」表容错（未知 section 保留不报错、未知颜色 token 值有效就接受、未知组件属性接受但警告、重复 section 报错拒绝文件）；格式校验命令在 CI 场景下应固定版本；规范出现破坏性变更时，受影响的是 A3 与 B1 两种判拒，其余七种不受影响。这个爆炸半径可控，是选择依赖它的前提。

**不可逆操作。** 无。新增技能、新增两个产物类别，都不改动既有产物，不迁移历史数据。技能在设计系统文件不存在时写一次该文件，那是新建，不覆盖任何东西。

**需要人点头的环节。** 界面 QA 在 Windows 侧运行时，用户必须在场手动启动应用一次。这不是自动化缺陷，是目标仓库铁律带来的固有约束。

## Out of Scope

- **不改六道审。** 界面 QA 不作为新的一道审，`docs/context/review.md` 的六道审定义不动。
- **不改「走查」的定义。** 走查仍专指用户本人使用 prototype 并给出意见。界面 QA 由 agent 执行，不叫走查。
- **不把 `finding` 改成别的意思。** 它仍是「一个可定位的问题候选」，仍需主 agent 验证出处才作数。本次只扩展它的生产方（原定义写的是审查者，现在多了界面 QA 的语义层模型），这一处扩展走 `/mmw-domain-modeling`。A 类结果不叫 `finding`，另立「违规项」承载。
- **不做跨模型独立审查。** 既有审查者组是六道审专用，用它会展开成六道审的派发说明。要做必须新增角色与启动组，不在本 spec 范围。
- **不验证实际键盘遍历顺序。** 可访问性规则引擎不提供这个能力，本版也不自建。
- **不制造需要故障注入、多权限身份或中途数据复位才能到达的状态。** 那属于产品自己的测试夹具范畴。这类状态进覆盖报告。
- **不承诺跨任务的界面全图比较。** 全图每次重建、不落文件，跨任务要留的结论写进可用性判据。
- **一次运行不检查多个产品。** 多个产品的结果混进一份报告，用户裁决时会分不清在答哪个应用的事。要检查第二个就再发起一次。
- **近似匹配不自动判定。** 指纹只差一个字段时停下来问用户，不像代码分析工具那样自动认成同一件事。界面重排比代码改动剧烈，自动判定误压制的概率太高。
- **陈旧裁决不自动删除。** 只列出来提示，由用户决定。
- **不覆盖打包安装后的应用。** 目标仓库已有出包实测工具处理这一层。
- **不做设计生成。** 界面 QA 只检查与修复，不产出新的视觉方案。设计系统文件不存在时提议建一份是例外，且只建一次、建完转只读。
- **不绑定任何生成设计系统的工具。** 依赖的是 DESIGN.md 格式规范，不是生成它的技能或插件。目标仓库换生成器，界面 QA 不受影响。
- **不采纳外部方法论里的 component spec。** 「AI-Ready 设计系统」方法论定义了每组件一份、七个必填字段的规格文件（useCases、antiPatterns、variants、props、accessibility、aiHints、composition）。不采纳，因为它要求目标仓库逐个组件手工维护，而它能供给的 `antiPatterns` 与 `composition` 全在系统合规层，对功能完整性没有贡献。
  **一个例外条件**：其中 `accessibility.keyboard` 是「键到行为的映射」，明确拒绝自由文本。日后某个产品的键盘操作成为核心可用性问题时，可以只引入这一个字段——届时 A2 那条「不验证实际键盘遍历顺序」的限制随之解除。
- **不校验设计系统文件的格式合规性并因此中止交付。** 判据自检的结果只进报告。格式合不合规是目标仓库的责任。
- **不做移动端与 Mac 应用。** 覆盖面是 Electron 桌面应用与 Web 应用。
- **不依赖远程桌面通道。** 远程桌面会话的分辨率由服务端协商，与真实显示器不同，会让 DPI 缩放这类检查得出假结果。
- **不长期保留界面 QA 报告。** 长期沉淀的只有判据与裁决。
- **不从现有代码逆向抽取判据。** 逆向抽取会把当前缺陷固化成标准。
- **Cursor 上不提供本技能。** 当前发布面不支持。

### 判据自检这一步的由来：一次实测

访谈期间对目标仓库现有的 `DESIGN.md` 跑了一次官方格式校验，结果直接产生了「判据自己要先被检查」这条决定。

**67 条 finding，0 条 error。** 格式完全合规——现有文件就是标准 DESIGN.md，不需要重新生成，也不需要换格式。

**3 条对比度不足**，其中两条落在主按钮上：`xhy-button-primary` 的白字配琥珀色底是 1.93:1，`xhy-button-primary-hover` 是 3.19:1，WCAG AA 要求 4.5:1。第三条 `parrot-nav-tab` 的背景是全透明，实际值取决于叠在什么上面，需要真实渲染才能定论。另有 1 条 `missing-primary`。

**62 条孤儿 token**（定义了但没被任何组件引用）。这个数字要谨慎解读：校验器只看文件内部的引用关系，看不到代码，而该文件的 `components` 段只声明了九个组件，颜色 token 有几十个，代码中大概率经由工具类直接引用。它主要说明 `components` 段覆盖面窄，不等于 62 个颜色没在用。

这次实测确认的是一个此前没有预见的层次：**A3 与 B1 拿设计系统当判据，而这份判据自己可能违规**。不先校验判据，一份声明了「白字配琥珀色」的规范会让 A3 把读不清的按钮判成合规——判得越准越糟。同一次实测也证明这条检查的成本极低：一条命令、几秒钟、不需要启动应用。

它同时是「不采纳任何爬取式生成器」这条决定的实证依据。这三条对比度违规现在存在于文件里；用从渲染结果取值的生成器重新生成，会把它们原样固化成标准。

### 目标仓库既有做法的定位

目标仓库 `desktop/tests/integration/launch.spec.ts` 中的四个确定性界面断言，性质是事后补的回归护栏，不是发现机制。它们证明界面规范可用零截图的确定性断言表达，这一点被本方案采纳；但其中两个断言通过注入假元素测全局 CSS 规则，测不到被更具体选择器覆盖的真实元素，这个做法不采纳。

### 术语冲突的处理

`docs/context/delivery-workflow.md` 中「走查」的 `_Avoid_` 已经列了「自动验收」，`docs/context/review.md` 中 `finding` 的 `_Avoid_` 列了「已确认缺陷」。本次不扩展这两条定义，而是新增「界面 QA」与「违规项」两个术语各自承载。这样下游读到「已走查」时仍能确定是用户本人看过，读到 `finding` 时仍能确定它是候选。
