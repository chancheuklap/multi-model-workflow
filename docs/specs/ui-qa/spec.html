02起步：五步。第一步不成立就停，后四步不成立先补齐

1
检查工作区干净

运行 git status --porcelain。有输出就停，你先提交，然后重新发起。

工作区脏 → 停止。技能不替你提交，也不自己造快照绕过
这一条换来四件事：范围算得出来（「刚改完的那一块」= 最近一个提交）、回退直接用 git、技能的修改可以正常提交、整条工作名链路都不需要
2
检查依赖

三个运行时依赖由 mmw/install.sh 提供并固定版本，不用 npx 当场拉取。

浏览器自动化框架缺失 → 停止。它驱动全部检查
可访问性规则引擎缺失 → 跳过 A2，其余照常
设计系统格式校验器缺失 → 判据这一轮不校验，报告顶部标明
3
判定产品

判据与接线按产品分，所以产品先定。四级，第一级命中就不往下走：① 你点名了 → 直接用。② 没点名但接线文件只有一份 → 用那份。③ 有多份 → 列出来让你选一次，列的是产品名不是目录名。④ 一份都没有（全新仓库首次运行）→ 直接问你要检查哪个产品。

第 ④ 级不能省：②③ 都以接线文件存在为前提，而建立模式在下一步、它要建的文件本身就按产品分
4
检查判据与接线，缺了就建

阈值表、可用性判据、接线文件、设计系统，缺任何一份就进建立模式：跑七问 intake 问卷，建完自动转入运行模式接着跑。

拒绝建前三份中任意一份 → 停止。技能跑不起来
拒绝建设计系统 → 继续，跳过 A3 与 B1，其余七种照常
问卷问完仍不足以建立能运行的接线文件 → 停止，不猜启动方式
5
校验判据本身，再确定范围

对设计系统文件跑一次官方格式校验。这一步不可省略——A3 与 B1 拿它当判据，判据自己违规时判得越准越糟。然后按第 04 节确定范围。

校验报 error → 停止。文件解析不了，A3 与 B1 无从判起
只有 warning → 继续，报告里列出，并标明这是判据的问题不是界面的问题

intake 问卷：只问技能查不到的，七个一次问完

#问什么技能先做什么，好让你少打字
1这个产品给谁用、在什么场景下用从 spec 或共同理解抽一段草稿，你改
2哪几条是核心流程列出全图里从主窗口出发的可达路径，你挑
3哪些元素是刻意做小的展示型元素扫出所有小于通用下限的元素列成候选，你勾
4启动方式对不对从构建配置读出候选命令，你确认或改
5这个产品跑在哪个环境：本机起的服务，还是真实服务器上的测试账号无法预填。两个选项二选一，没有第三个。答案写进接线文件的 environment
6登录态与测试数据怎么准备无法预填。答不上来记为空，相关状态进覆盖报告
7Windows 远程调试端口给默认值，你改或留空

不问的：设计系统在不在、声明了什么组件规格、应用怎么启动、界面有哪些、你在 grilling 和 spec 里说过的可用性要求——这些技能自己查得到。实际要你打字的只有第 1、6 两项。

第 5 问是数据安全的唯一保障。项目落地后跑 QA 时 agent 会真的点下去——真的新建、真的提交、真的触发错误。本地服务器和测试账号都与生产数据隔离，所以技能不需要禁止操作清单，也不需要为不可逆操作逐个停下来问你。

抽取出来的判据一次性展示，默认全接受，你划掉不要的。不逐条确认（那是一项一项盯），也不静默采用（抽错的会变成长期判据，每轮都拿它判 B5）。它跟着问卷一起给你看，不多一次交互。

04地基：为什么绑格式不绑工具

依赖的是 DESIGN.md 格式规范，不是生成它的工具

开放格式规范，Apache-2.0。frontmatter 五组 token（Dimension 只接受 px/em/rem，引用语法 {colors.primary-60}），正文八个 section 有固定顺序。谁生成的都行，格式对就读得了。目标仓库换生成器，界面 QA 不受影响。

规范本身几乎不定义阈值

全份规范唯一可校验的数值约束是单位合法性。4.5:1 只出现在示例里。这正是判据 1（阈值表）必须独立存在的原因——阈值不可能从设计系统里读出来。

规范严格限于视觉身份

没有用户流程、没有任务完成、没有产品需求层。同期最成熟的「AI-Ready 设计系统」方法论也明确说自己做的是系统合规审计，不是功能 QA 审计。功能与流程这一层外部是空白的，由判据 2 与走查任务承担——那正是界面 QA 存在的位置。

规范目前是 alpha

version 字段当前值就是 alpha，官方标明可能有破坏性变更。爆炸半径可控：出现破坏性变更时受影响的只有 A3 与 B1，其余七种判拒不受影响。这是选择依赖它的前提。

判据自己要先被检查——这条来自一次实测。 对目标仓库现有的设计系统文件跑官方校验：67 条 finding，0 条 error，格式完全合规。但其中 3 条对比度不足，两条落在主按钮上：白字配琥珀色底 1.93:1，悬停态 3.19:1，WCAG AA 要求 4.5:1。

不先校验判据，一份声明了「白字配琥珀色」的规范会让 A3 把读不清的按钮判成合规——判得越准越糟。同一次实测也是「不采纳任何爬取式生成器」的实证依据：这三条违规现在就在文件里，用从渲染结果取值的生成器重新生成，会把它们原样固化成标准。

05检查范围：三档，默认服务主场景

浏览器每往返一次要几秒。你在迭代中随手喊起来，等不起全量。所以范围分档，而且默认档服务主场景。三档与 MMW 的任务模型对齐，不按「查几个界面」分。

档范围怎么算什么时候用
本次改动
默认		 git diff HEAD~1...HEAD --name-only 刚提交完一次改动，随手检查
本任务 git diff $(git merge-base HEAD <父分支>)...HEAD --name-only 一个任务完整落地，交出去之前
全量 界面全图里的全部界面与状态，不看 git 初版落地，或去 Windows 那一次
改动的文件怎么变成要查的界面

界面全图的每个界面节点记着 来源文件。改动了文件 F，就取所有 来源文件 包含 F 的界面节点。这是查表，不是再扫一遍代码——代码抽取建全图时本来就知道自己在读哪个文件。

降级链：只改范围，不减判拒

映射出零个界面（改的是后端、配置、文档）→ 降到本任务。本任务也映射不出→ 降到主窗口及其直接下一级。HEAD~1 不存在（任务分支的第一个提交）→ 降到本任务。
九种判拒在任何一档上都全部运行，档位只决定它们作用在哪些界面上。

三档都是无状态的，技能不记「上次跑到哪」。 起步第一步已经保证工作区干净，所以「刚改完的那一块」就是最近一个提交。反过来的做法走不通：若允许工作区脏、靠记住上次运行的 HEAD 来划范围，你连改几轮不提交时 HEAD 始终不变，每次算出来的都是同一堆未提交文件——「只查刚改的那一块」就退化成「每次重查整个脏工作区」。
走查任务跟着范围走。 产物里有经过范围内界面的路径就用那几条；一条都没有，就用全图的跳转关系拼——从主窗口到范围内每个界面的最短路径。第二种保证 B2、B3、B4 在任何范围下都有路可走，但拼出来的路径必须在报告里标明：它只保证走得到，不保证用户真会这么走，结论要打折看。 
报告开头固定五行 ——

本次范围：本次改动（未指定，默认档）
覆盖：3 个界面 / 7 个状态
未覆盖：12 个界面 / 31 个状态
判据：阈值表 v1 · 小黄鸭可用性判据 14 条 · 设计系统已读并校验
本次跳过：无

范围因降级变过时，第一行写成「本次改动 → 本任务（本次改动未涉及界面文件）」，把原因带上。

06检查执行与语义层

无障碍树快照
只含角色与可访问名，不含 class、测试标识、包装元素。
因此对前端框架不敏感：原生 DOM、React、Web 应用共用一套方法
计算样式与盒模型数值
间距、尺寸、对比度、是否在首屏内、是否被遮挡，全部用数值判断。
供给 A1 A3
运行时 CSS 自定义属性
读 getComputedStyle(document.documentElement)，拿到实际生效的 token 集合。
A3 判的是声明层——这条判拒叫「设计系统 token 越界」。实现层照样读，但用途是判断判据可不可信：两边对不上就作为报告项报出来，并标明 A3 的结果可能失真
渲染进程控制台 + 局部截图
控制台供给 A4。截图只在结构化数据判不了时用，且裁到相关区域。
认知走查四问里只有第 2 问需要截图
A2 不验证实际键盘遍历顺序 规则引擎里与焦点顺序同名的那条是实验规则、默认关闭，且只检查已在焦点序列中的元素角色，不追踪按 Tab 时焦点实际走的次序。技能必须在报告中声明这一点。

语义层：三套方法判据，全文写在技能源里，任何装了 MMW 的仓库直接具备

认知走查四问 B2

  1. 用户会不会想要达成正确的那个结果
  2. 用户会不会注意到正确的操作是可用的
  3. 用户会不会把正确的操作与想达成的结果联系起来
  4. 操作之后，会不会看到事情在推进的反馈

只有第 2 问需要视觉信息。

Trunk Test 六问 B4

假设用户被直接放到这一屏，没有任何上文：

  1. 这是什么产品
  2. 我在哪一个界面
  3. 有哪些主要区块
  4. 这一层有哪些可选操作
  5. 我处在流程的什么位置
  6. 怎么回上一层或找到我要的

第 6 问是对桌面应用的调整：原表述问「怎么搜索」，那假设有搜索框。

困惑分量表 B3

三档：完全不困惑（一眼可见）、有点困惑（要停下来想一下）、很困惑（读完仍不确定，或两个以上选项看起来都对）。

偏高怎么判：任一屏「很困惑」直接记一条；连续两屏「有点困惑」也记一条，指向这段路径。单独一屏「有点困惑」不记。

写死一条判据：agent 走得通不等于用户走得通。 任务完成不作为通过判据。依据：同一界面，人类评估者找出十个失败点，语言模型多轮合计只找出三个，而语言模型的任务完成率更高。
另一条：保留完整会话历史。 不带历史时，重复运行的结果彼此不一致。

语义层怎么交接：主 agent 走，designer 判

浏览器归主 agent，designer 碰不到

两条理由：A 类检查已经占着同一个应用实例，两边同时驱动会互相干扰；designer 是独立上下文，它自己开实例就意味着应用状态归零，走到第五步才出现的那个界面它到不了。

一条完整路径派一个，不是一步派一个

认知走查第 4 问问「操作之后有没有反馈」，判它需要知道操作之前是什么样。一步一派时每个 designer 的上下文都是空的，这一问根本判不了。

先走完，再一次性交付

主 agent 按路径逐步操作应用，每步采集数据，全部走完后把整条路径的数据包一次交出去。这个数据包本身就是会话历史，不落文件。

07判拒：两类九种，外加三类报告项

分类依据是判定性质，不是判据载体：确定性检查的结果是事实，模型判断的结果是候选。九种是封闭集合。

编号判拒判据来源性质与处置
A1可执行阈值违反阈值表 违规项
违反即成立，不需要裁决，直接修改。不使用处置标记——它们不是候选
A2WCAG 规则违反规则引擎自带规则集
A3设计系统 token 越界运行时实际生效的 token 集合

B2认知走查四问任一不成立方法判据

B4Trunk Test 六问任一答不出方法判据

三类报告项：确定的事实，但没有界面上的修复目标

报告项 覆盖报告
全图里有、本次没走到的状态。它说的是本次 QA 没执行什么，不主张界面有错。
报告项 判据自检结果
设计系统自身的格式问题、跨 token 对比度不足、引用不完整。要修的是判据文件，而它只读。
报告项 声明与实现不一致
声明的 token 与运行时实际生效的对不上。修它要么改只读文件，要么改构建配置——后者是选型决定不是缺陷。
为什么 A 类不叫 finding。 领域文档把 finding 定义为「审查者报告的一个可定位问题候选」，它的 _Avoid_ 列了「已确认缺陷」。A 类结果正是已确认缺陷，所以另立违规项。finding 仍然是候选、仍然要主 agent 验证出处才作数，但它的定义要扩展一处：生产方。B 类由 designer 产出，它不是审查者，这一处扩展走 /mmw-domain-modeling。
产生新的确定性事实但没有界面修复目标时，加成报告项，不加成判拒。

08A 类怎么安全地直接改

前提是工作区干净，由起步第一步保证

这一条让下面每一步都成立，不需要任何自造的回滚机制。早先的设计是「不要求干净、动手前 git stash create 拍快照」，实测走不通：工作区只有未跟踪文件时那条命令返回空字符串——它不处理未跟踪文件，而新建界面文件正是 prototype 阶段最常见的操作。

换成「先提交」之后，退回就是 git checkout -- <文件> 这一级的操作。

本次全部 A 类修改合成一个提交

技能敢提交，是因为工作区本来就是干净的——这个提交里只有技能改的东西，不可能夹带你没写完的代码。

选一个提交而不是一条一个，理由是回退的实际用法：你要么接受这一轮，要么整轮退掉（git revert <该提交>）。逐条 revert 不是真实场景。报告第 1 节仍逐条列出改了什么，要单独退某一条，你在这个提交的基础上自己改。

1
先跑完全部九种判拒，收集全部结果，再统一进入修改

不边查边改。A3 改了 token，B1 看到的就是改后的界面，你在报告里读到的描述会对不上你打开界面看到的样子。全部检查跑在同一个界面状态上，结果才自洽。

2
逐条修改，逐条验证

每改完一条，只重跑触发这条违规项的那一项检查，不重跑全部。

3
全部改完之后，把四种 A 类检查整体重跑一遍

逐条验证只看得见自己那一条，看不见「这次修改是否引入了别的 A 类问题」。整体重跑补上这一层，成本很低——A1 读数值、A2 跑规则引擎、A3 比对 token 集合、A4 读控制台，全是确定性检查，不需要模型判断，也不需要重走语义层。
B 类不重跑：你裁决时看到的是修改前的界面，这一点在报告里写明。A 类改的是阈值、WCAG、token、运行时错误四类确定性问题，不改变 B 类关心的流程与语义。

4
改坏了退回去

整体重跑发现新的 A 类违规项，或某条逐条验证没过 → git checkout -- <文件> 退回该次修改，降级成 finding 报给你，标「尝试修复失败」。

5
改不了源码的一律不改

定位到第三方组件内部或依赖包文件时，不修改，转成 finding。

09裁决怎么被记住：指纹与两级匹配

这是「批注次数下降」的落地机制。没有它，「裁决长期保存」只是把条目堆起来，下一轮仍然全部重报。

元素级 B1 B5
判拒：B1
判据：DS-规则3
界面：main
状态：default
元素角色：button
元素名：同步
步骤级 B2
判拒：B2
走查任务：新建同步任务
步骤：3
问：2
屏级 B4
判拒：B4
界面：main
状态：default
问：5
屏级或路径级 B3
判拒：B3
界面：[main]
状态：[default]
数组。连续两屏时长度为 2

有意不用 CSS 选择器。浏览器自动化框架官方文档给的做法是「规则 ID + 元素选择器」。选择器带 class 名与 nth-child，界面一重排就全变。角色加可访问名稳定得多，而且和主输入同源，不引入第二套定位方式。A 类不记指纹——它直接改，不产生裁决。

级条件结果
第 1 级 · 全等指纹每个字段都相同同一件事。按已有裁决处理，不报给你
第 2 级 · 近似判拒相同，位置字段恰好只有一个不同报给你，附上上一轮的裁决，只问「是不是同一件事」
都不中判拒不同，或两个以上字段不同新问题，正常报

「恰好只有一个字段不同」是确定性规则，不依赖模型判断。它覆盖界面迭代中最常见的三种改动：按钮改文案（元素名变）、状态被拆开（状态变）、走查任务插了一步（步骤变）。既换界面又改名的元素两个字段都变 → 算新问题，这是有意的：它已经不是原来那个东西。

为什么不用自动回退式匹配。代码分析工具那边位置对不上会退而比对内容，自动判为同一件事。那套在代码上成立，因为代码改一行周围几十行不动；界面改一版可能整屏重排，误压制的概率高得多。所以我们在第 2 级停下来问你，你只答「是/不是」。

裁决全部长期保存，不论结论

accepted、rejected、waived 都一样，当场写进该产品的可用性判据，带状态字段区分。只回流 accepted 会让被判不成立的条目每轮重复出现。
被采信的 B1 回流到可用性判据，不回流到设计系统——设计系统只读，改不了。

陈旧裁决只列出，不自动删

只检查指纹落在本轮范围内的那些：指纹的界面在本轮检查过、而两级都没命中，才提示「可能已经失效」。范围外的一律不参与——默认档只查本次改动，绝大多数界面本轮根本没被检查，把它们列成「可能失效」是把「没查」当成了「查过但没发现」。
不自动删除，也不因此让运行失败——代码检查工具那边是非零退出码报错，那套面向流水线；界面 QA 面向你随手发起，报错会打断你。

10报告结构：五节，按「要你做什么」排序

节内容细节要你做什么
1A 类改了什么每条一行：违规项编号、文件与位置、改前值、改后值、验证结果（已验证 / 已回滚）。末尾给出本次修改的提交 SHA不做事，看一眼。要整轮退掉就 git revert 那个 SHA
2B 类新 finding两级都没命中的。标 已回滚 的 A 类也出现在这里逐条裁决
3B 类近似匹配第 2 级命中的，每条附上一轮裁决每条答「是/不是」
4三类报告项覆盖报告、判据自检结果、声明与实现不一致不做事，可选择说一句
5陈旧裁决指纹落在本轮范围内、却没有对应检查结果的裁决不做事，想删就说一句

第 2 节与第 3 节分开，因为第 3 节要的只是「是/不是」，比新 finding 好答得多，混在一起会让你按同一种强度去想每一条。

第 4、5 节分开，因为两者性质不同：第 4 节说的是本次检查的边界（哪些没查到、判据自身有什么问题），第 5 节说的是已有判据可能该清理了。合成一节会让你以为覆盖缺口也需要你处理。

11平台：Mac 与 Windows

Mac 侧 · prototype 阶段

对象是 mockup 或开发模式启动的应用。技能自行启动，全流程自动。

在 Mac 上检查不到的行为（技能必须列出，以免你误以为已覆盖）：Windows 原生菜单、托盘图标与通知、DPI 缩放、系统中文字体回退导致的行高差异、安装包行为与文件关联、原生文件对话框。

Windows 侧 · 完整落地后

1
你手动启动一次

PowerShell 里启动，带远程调试端口。

2
主 agent 从 Mac 连接端口

接管渲染进程。

3
连接后先自检四项能力

取快照、提取样式、局部截图、注入规则引擎。连接成功不等于四项都在。任一项失败按缺项处理，声明哪几种判拒没运行，不把缺项结果当完整 QA。

4
要改东西之前先报数、等你点头

告诉你有几处要改、要重新构建并重启几次。你可以答「这次先只报告」。

不能跨 SSH 启动 Windows GUI

SSH 前台拉起会静默失败。这是目标仓库 ENGINEERING-RULES.md 已记载的铁律。所以 Windows 侧的界面 QA 不是无人值守的。

为什么 Windows 侧照常改，而不是带回 Mac 改

Windows 那一趟的全部价值就是覆盖 Mac 上测不到的行为。把 DPI 缩放、中文字体回退这类问题的修复推回 Mac，等于查出来了但改不了也验不了，下次再来可能发现改错了。这个来回比多按几次启动贵。
启动次数：至少一次，选择让技能修改时每轮修复各再一次。技能报数时把预计次数说出来，不含糊说成「一次」。

13边界：明确不做什么

不改既有定义
  • 不作为新的一道审，六道审定义不动
  • 不改「走查」——它仍专指用户本人使用 prototype 并给出意见
  • 不把 finding 改成别的意思——它仍是候选，仍要验证出处才作数；只扩展它的生产方
  • 设计系统已存在时不修改它
关于设计系统的边界
  • 不绑定任何生成它的工具，只依赖格式规范
  • 不做设计生成。文件不存在时提议建一份是例外，只建一次、建完转只读
  • 不从运行页面提取当前值来建——那会把当前缺陷固化成标准
  • 不因判据格式不合规而中止交付，自检结果只进报告
本版不做的能力
  • 不做跨模型独立审查（既有审查者组是六道审专用）
  • 不验证实际键盘遍历顺序
  • 不制造需要故障注入、多权限身份或中途数据复位才能到达的状态
  • 不承诺跨任务的界面全图比较
  • 一次运行不检查多个产品
  • 近似匹配不自动判定；陈旧裁决不自动删除
不采纳外部方法论的 component spec，但留了一个口子

每组件一份、七个必填字段，要目标仓库手工维护，而它能供给的 antiPatterns 与 composition 全在系统合规层，对功能完整性没贡献。

例外条件：其中 accessibility.keyboard 是「键到行为的映射」，明确拒绝自由文本。日后某个产品的键盘操作成为核心可用性问题时，可以只引入这一个字段——届时 A2 那条「不验证实际键盘遍历顺序」的限制随之解除。
