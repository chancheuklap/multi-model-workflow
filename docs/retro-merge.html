retro 是怎么缝出来的

Matt 的 retro 留下「看什么、怎么报告」。pstack 的 correct 留下「同一类到了第二次就修，并且修到错不再可能发生」。缝在一起之后，Coordinator 在交付 PR 开好时调用它。

顺序缝完的 retroretro 原稿correct 原稿
01

谁来做，什么时候做

你是 Coordinator。交付 PR 已经在，或者你刚纠正了一次重复的错。然后改仓库，让下一个 agent 不能再犯这次已经出现两次的错。

retro等人叫一声 retrospective。只给环境提建议，不改仓库。技能写成模型不能自己调用。

correct等人叫 /correct。改仓库，让下一个 agent 不能再犯。技能同样写成模型不能自己调用。

02

先读什么

读这一次交付的提交、评审、回退、说明文件，和解释绕路的注释。会话还在就读会话。你点名一次纠正，就读那一次。

retro读你指定的那次会话。你没指定，就读当前这次。动笔改说明文件之前，先调用 writing-for-agents。

correct读最近的提交、回退、评审意见、agent 说明文件，和解释绕路的注释。

03

怎么归类

用 retro 的七类去找候选。用 correct 的计数：同一类出现两次，才算一类。

retro七类原句留下：Navigation、Automated checks、Coding standards、Global AGENTS.md、Tool economy、No-ops、Information access。每类后面的 Use when 也留下。

correct把错误分成类。一类要出现两次才计数。

04

七类里改过的两句

Automated checks：先读这个仓库自己的提交钩子和 scripts/check。没有钩子在跑 lint、类型检查、以及 scripts/check 会选中的测试，这本身就是一条发现。Coding standards：机械的错做成 linter 规则，或者一条新的提交钩子，哪个便宜用哪个。

retro先读 package.json 和 CI。没有 pre-commit、也没有跑 lint 的 CI job，就是一条发现。机械的错可以做成 linter 规则、新钩子，或一个新的 CI job。

correct 没有这七类。这一行的改动来自你的规则，不是来自 correct。

05

修到哪一层

出现两次的，现在就修，一类一个提交，提交在交付 PR 已经跟踪的分支上。顺序是 correct 的四层：先结构，再类型和提交钩子，再让行为测试进入 scripts/check 会选中的测试，文档最后。在这台机器上跑新检查。出现一次的只写进报告，仓库不动。

retro不修。把候选按严重程度交给人挑。不自动安装钩子。

correct现在就修最常见的类，一类一个提交。四层：结构，类型或 lint/CI，测试，文档最后。新检查必须在一次真实的旧错上失败。同一条命令在本地和 CI 都跑。例外要有理由、到期日、和人的批准。

06

规则要有执行者

说明文件里留一张表，每条规则对着谁在执行它。你纠正的时候，修好错，并把规则补上。规则已经写着、却没有东西执行它，这就是一次重复，同一次改动里提到更高的层。错不再可能发生，就把这条规则删掉。那份文件自己禁止清单时，这一对写进提交说明和交付报告。

retro 没有这张表。

correct这段原句留下。多出来的一句是：AGENTS.md 禁止把清单写进说明文件时，规则和它的执行者改记在提交说明和交付报告里。

07

怎么回报

每一类都报告，按严重程度，包括已经修掉的。每类给出证据、选中的层、以及更高一层为什么不行。提交推到交付 PR 已经跟踪的分支。这份 PR 仍是交付。另开一个 PR、合并、或再开一轮 dispatch，都在这个技能外面。

retro把候选按严重程度交给人。retro 到这里就停。

correct回复里每一类都有证据、选的层、为什么更高的层不行。

08

整段照抄的参考

Implementation vs Review 和 Files 两节，用 retro 的原文。评审 agent 负责编码标准，因为实现的 agent 上下文最紧。AGENTS.md 只放导航。CODING_STANDARDS.md 在评审时读。文档和技能的用法也留着。

retro这两节没有改字。

correct 没有这两节。

什么时候调用

两版的 Coordinator 都在交付 PR 创建之后调用 retro。

本地版：修在这个 PR 已经跟踪的分支上。云端版：修在 NIGHT 上，这个 PR 跟踪的就是 NIGHT。

本地只做一张工单、并且不开这个交付 PR 的那条路径，不会调用它。

三处接头，各留一句

模型可以自己调用这份技能。两份原稿都写成不能自己调用；v5 的规则是技能保持可调用，所以这两行去掉了。

修，不停留在提议。你要的是交付之后迭代仓库的 agent 可用性，所以用了 correct 的「现在就修」，没有用 retro 的「只提议」。

检查留在本机。correct 写的是本地和 CI 跑同一条命令；retro 把 CI job 算作守卫。这两处都改成提交钩子和 scripts/check。
