## 二、复审标准现在是什么样（`mmw-v2/upstream/skills/productivity/writing-for-agents/SKILL-SET-REVIEW.md`）

它是写技能和审技能共用的规则。写、改、复审一组互相交接的技能时，`writing-for-agents` 的入口句会把 agent 引到这份文件。要点：

- **按"任务"审，不按文件清点。** 这里的任务是：一个 agent 从拿到的第一段文字，一路读、跑脚本、交接，直到把工作做完。
- **每条发现必须说明它在实际使用中怎么发生。** 依据是你的配置、tracker 上的历史，或脚本在正常使用中收到的输入。没人走的路径不算，已会明确拒绝并被处理的失败也不算；历史里查不到的就不记。
- **修法先减后加。** 新增任何机制（检查、字段、退出码、防护句）都必须指出它在哪次运行中真的出过问题。
- **只把四类事交给你决定：** 客户看到的东西、钱、范围、不可撤回的事。其余由 agent 自己定，并写明理由。
- **你的三条裁定写进了规则。**
  - description 只留触发条件。
  - 词表不是权威，和技能文本按同一标准审。
  - 上游技能能不改就不改，只负责把它们接入工作流；为文风而改的地方要恢复原文。
- **写作规则与你全局 CLAUDE.md 一致。** 用领域内的既有术语或普通词，不用比喻，名字照原文抄，文件只写当前为真的内容。

## 三、修了哪些问题

### 1. 会让 agent 走错或卡住的（真实会发生）

| 问题 | 修法 |
| --- | --- |
| review 里"审 worker 自己的决定、审越界改动"这一项，在每张票上都是空的：worker 在 review 之后才发出决定清单 | `implement` 把"发出决定清单"挪到启动 reviewer 之前，重排后续步骤和恢复表；reviewer 的 Spec axis 按新顺序读取 |
| 还没写 screen contract 时修完设计再拉取一次，脚本就不再标"首次"，结果契约一直没人写 | `design-pages` 的 `pull.md` 改为按契约文件是否存在来决定下一步 |
| spec 里"关键流程：`none`"会被 `verify-ticket.py` 当成读不懂的行报错，而 `to-spec` 正是要求这么写 | 脚本把单独一行 `none` 视为"没有关键流程"，补了测试 |
| 路由技能 `ask-matt` 给了两条走不通的路线：直接用 `implement`，以及用 `code-review` 审任意分支 | 改为：发布的票交给 `dispatch` 技能运行；`code-review` 只审一张票的 diff |
| `to-tickets` 声称可以从"计划或对话"直接切票，实际离不开一份已发布的 spec | 没有 spec 时先走 `to-spec` |
| 复验后仍失败、被交回 `needs-triage` 的票，`triage` 技能的说明把它排除在外，也没说怎么处理 | 说明里加上这个触发分支，并写明处理方式：放回 `ready-for-agent`，下一次 `advance` 会重新启动它 |
| 没有审核发现的一夜，会跳过"Memory 收尾"，结果 `summary` 被拒 | 没有发现时也先做 Memory 收尾，再进入第 5 步 |
| 复验仍失败的票，`night.md` 说"留给 triage 也算有效结果"，脚本却拒绝 `summary`（复验重开票在最近两夜都发生过） | 改为：告诉你是哪张票、为什么，然后停下 |
| `resume` 退出码 3 时说"等一下再试"，可夜里没有时钟 | 改为：结束本回合，下次被唤醒时再发一次 |
| worker 中途恢复时，"重新认领"产生的事件让恢复表的最后一行永远对不上 | 把这类事件列入"不改变所处步骤"的清单 |
| reviewer 启动失败时，文字指向一个不存在的"reviewer row"，最坏会被误读成去改模型配置 | 直接指向 `inside-a-ticket.md` 的退出码一节 |
| `advisor` 和 `ui-acceptance` 两个技能的 description 不是合法 YAML；grok 是否严格解析没核实，而 grok 正是你的初级 worker 宿主 | 改写成只含触发条件的合法写法 |

## 四、有意没修的（及理由）

这是第一轮结束时的判断。第二轮已按新标准修掉其中的 `retro` 正文和 em-dash 两项，并逐条复查了其余各项，见第七节。

| 事项 | 理由 |
| --- | --- |
| 复审报告里约 10 条 High 和大部分 Medium、Low | 在你的实际使用中不会发生，或者发生了也会明确报错停下。例如：一张票被两个 worker 同时做、`check` 时安装不完整、调用方读不到 advisor 的回答、发布修复后重发旧代码 |
| `retro` 技能正文 | 正文是设计文档 `docs/notes/stage-two-shared-experience-layer.md` 里锁定的"固定执行 prompt"，retro 测试要求逐字一致。相关问题都只是措辞，8 次 retro 全部正常，所以撤回了修复工作者对它的改动。要改它，得先改那份设计文档 |
| 任务看板上的 "The Night" 标签 | 这是 Claude Design 设计稿里的文字，界面验收会拿产品文字逐项对照设计稿。要改，需先在 Claude Design 里改，再拉取下来 |
| reviewer 规则（Rules）送不到做检查的子 agent | 目前生效的规则为 0 条（65 条都是草稿），没有影响。以后启用规则时再修 |
| 上游子树里本仓添加的文字使用 em-dash（上游仓库的规矩不允许） | 不影响任何运行，改动量大 |
| `models.py` 注释里的 "Tonight's runner" | 改它必须跑看门狗网页的测试（要 Playwright 浏览器），而这只是注释 |
| 其他很少走到的路径：一次性运行的看门狗处理、复验失败时的决定、验收后仍有未关的票等 | 历史记录里没有出现过 |
