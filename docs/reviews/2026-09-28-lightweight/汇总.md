## 一、还要你决定的两件事

### 1. `design-pages` 的两句理由要不要写回技能正文

**背景。** `design-pages` 是和 Claude Design 打交道的技能：在 Claude Design 里画界面页面，再把页面拉回仓库，作为实现和验收的依据。9 月 21 日你定过一条规矩（Nowledge Mem `415f96d0`）：界面技能的正文只留可执行的规则，写给维护者的理由不写进正文，放在 `docs/adr/0029-claude-design-is-the-design-source.md` 和 `docs/adr/0030-design-system-built-by-claude-design-agent.md`。下面两句正是按这条规矩删掉的，我建议写回去。

**第一句**，放在 `mmw-v2/skills/design-pages/references/design-system.md` 的 `## What it is for` 开头。

- 这一节讲"design system（一套统一的颜色、字号、组件）有什么用"。现在只有一句否定的话："没有判官拿页面和 design system 比对，它也不是每个设计都必须经过的一步。"
- 要写回的英文原句的意思：design system 让所有页面是同一个样子，Claude Design 里的 agent 用现成的组件和刻度拼页面，不用每次猜数值，所以下个月画的页面和今天画的一致；从现有产品建 design system 时，它也是统一产品里不一致之处的地方，每统一一个值就在 `Unifications` 表里记一行，页面拉回来后产品代码跟着改。
- 为什么要写回：agent 要判断"这个产品值不值得建一套 design system"。现在这一节只写了它不是什么，agent 只会倾向于不建。补上用途以后，它才能两边权衡。

**第二句**，放在 `mmw-v2/skills/design-pages/references/template-project-claude-md.md` 的 `## Files` 里，接在 "It loads no product code" 之后。

- 这份文件是一个模板，会被写进 Claude Design 项目的 `CLAUDE.md`，读它的是 Claude Design 里画页面的那个 agent。
- 要写回的英文原句的意思：页面的样子只来自 design system 和页面自己的标记。页面如果加载产品自己的代码，验收就变成拿产品和它自己比；产品的样式表还会带进编辑器点不中的选择器。
- 为什么要写回：这个 agent 读不到本仓的 ADR，而"直接引用产品样式表最省事"的诱惑是真实发生过的。spec #445 的第三个问题记录了：抄进来的生产 CSS 带进了 18 条编辑器点不中的选择器，其中一条把指标数值缩成了 13px 灰字。

**两个选项。**
- **写回（我的建议）。** 两句共约 90 个英文词。代价是推翻 9 月 21 日那条规矩在这两处的适用。那条规矩的前提是"执行的 agent 读得到 ADR"，而第二句的读者读不到。
- **不写回。** 维持原裁定。代价是：Claude Design 里的 agent 再遇到"用产品样式表更省事"时，没有理由阻止它；判断建不建 design system 时，只看到反对的理由。

同一条裁定里提到的第三类理由（为什么不用 Claude Design 的 Handoff 导出功能），我按原裁定不写回。原因是它不改变 agent 在技能里做的任何选择。

### 2. `to-tickets` 加不加一句"票怎么拆"的判据

**背景。** `to-tickets` 把一份 spec 切成夜里 worker 做的票。上游原本有一句"每张票要能在一个新上下文窗口里做完"，你之前定过删掉它：票的大小不设机械上限，由切票最后一步的 quiz 问你"粗了还是细了"（`mmw-v2/merge-notes/to-tickets.md` 第 40 行）。现在切票的 agent 自己完全没有拆分的判据，只能等你在 quiz 里纠正。

**提议的句子**，放在 `to-tickets` `SKILL.md` 的 `### 3. Draft vertical slices`。意思是：能同时开工的部分、或一部分的验收标准能独立判成败的，拆开；会改同一批文件的，放在一起，因为拆开只会多一条依赖，让它们排队。

**它和原裁定的关系。** 这句话不设数量或大小上限，只给两条和流水线运作方式挂钩的判据：能不能并行，能不能单独判定。我认为它不违背"不设机械上限"，但它确实碰到了那条裁定。

**两个选项。**
- **加（我的建议）。** 切票 agent 自己先按并行和独立判定来拆，你在 quiz 里要纠正的会变少。
- **不加。** 维持现状，拆分完全靠 quiz 里你来判断。

**models.json 这一条。**
- **原因**：`models.py` 用 Claude Code 自己的 `/model` 选单当作可选模型的目录。这台机器的 Claude Code 升到 2.1.283 后，选单里不再列出带 `[1m]`（100 万 token 上下文）的条目。但命令行仍然接受这两个名字：`opus[1m]` 解析为 `claude-opus-5-5[1m]`，`fable[1m]` 解析为 `claude-fable-5-1`。你的配置没错，是目录的来源变了。
- **修法**（工程决定）：对 claude 这一行，名字带方括号后缀时，去掉后缀在目录里匹配，然后原样交给命令行。
- **没采用**：把你的配置改成 `opus`、`fable`。那等于替你放弃 100 万上下文。
- **剩余风险**：目录里已经看不出哪个模型支持 `[1m]`，后缀写错要到启动时才报错。`fable[1m]` 解析出来不带 `[1m]` 标记，Fable 实际是否按 100 万上下文运行，我没有验证。
- **在修复轮之前**：下一夜开夜时，`dispatch.sh check` 会遇到这个问题。

**wizard 的三处修复。** `wizard` 为需要人动手的配置工作（例如在阿里云控制台开 AccessKey 再填进仓库）生成一个 bash 向导脚本，人照着一步步做。
1. **路径过时。** agent 凭记忆写了阿里云控制台的点击路径，而控制台已改版（"OpenAPI 调用访问"改名成"使用永久 AccessKey 访问"），你两次截图回来问该点哪里。修法：每一步除了路径，还写明这一步要达成什么（开哪个设置、设成什么值、拿到哪个密钥），并标出哪些路径是凭记忆写的。
2. **中文文案让脚本崩溃。** 向导里写了 `"区域：$REGION，下一步"` 这类句子。macOS 自带的 `/bin/bash` 3.2 会把紧跟变量的全角逗号当成变量名的一部分，报"变量未定义"并退出。本会话已复现（`REGION�: unbound variable`，退出码 127），而语法检查和 shellcheck 都查不出来。修法：要求变量一律写成 `${REGION}`。
3. **一个没用到的颜色变量引出误改。** 模板 `template.sh` 里定义了没用到的 `RED`，shellcheck 因此报警告，agent 为了消警告去改了模板里不该手改的公共部分。修法：删掉这个变量。

### 3. 技能文字：补"为什么"，删废话

- **根源先修。** 前几轮修剪之所以把"为什么"删掉，根源在写作标准 `mmw-v2/upstream/skills/productivity/writing-for-agents/SKILL-SET-REVIEW.md`：它只把"做决定"列为技能文字的职责，逐句按字数检验，还把理由送去 agent 读不到的 ADR 和 merge-note。修复轮第一步先改它。新加的第一条要求：讲目的、讲下游、讲立场的句子，必须说得出"一个步骤没覆盖的具体情况，没有这句时 agent 怎么做，有了这句怎么做得不同"；说得出就不因字数删，说不出就是废话。几份写着"理由只写在这里"的 merge-note 同步改。
- **补回的句子。** 每一句都贴在它管的规则旁边，不写成开头的口号。例子：

  - `dispatch` 主 agent 的立场："这一夜的产出是一批你早上能接受的票，不是关掉的票数。"
- **删掉的废话。** 删除集中在复述脚本输出和拒绝信息的段落，例如 `verify-ticket` 的 `references/linting.md` 从 1,431 词减到约 150 词。调查员写的"灵魂"草稿约一半说不出它改变哪种情况，被我拒掉。

保留下来的新增机制，每一项都是把现在写在文字里、要 agent 手工做的事搬进脚本，并删掉对应文字（第三节第 2 小节）；或者是修一个真实故障，而修法本身不增加机制（第三节第 1 小节最后一列）。

## 五、依据

- **官方指南，均为全文阅读，不是摘要。**

  - "Claude is smart enough to generalize from the explanation"（给理由，模型能推广到没写到的情况）；
  - "Skills developed for prior models are often too prescriptive … can degrade output quality"（旧技能规定过细，反而降低质量）；

## 六、没做和没验证的

- 没有改任何技能、脚本或配置，也没有跑测试。修复轮要等你对第一节的两件事做出决定后开始。修复轮不运行 `install.sh`，不发布到安装工作树，不推送，这些都需要你另外授权。
- **只是推断、没有实例的。** 补回的句子里，有几条机制有依据，但没找到出过事的实例，定稿里已逐条标了"推断"。这些句子能不能真的改变 agent 的做法，要等修复轮的双向验证：
  - 让一个新 agent 拿新标准去修剪一个技能，看它会不会删掉该留的；
  - 让另一个新 agent 拿新标准去补文字，看会不会混进废话。
- **models.json。** "下一夜启动不了 reviewer"是从代码路径推出的，没有实际跑一夜验证。
- **产品仓库。** 删除自动修复后端涉及 agentflow 和 xiaohuangya 的文件，要各自开票处理。agentflow 的工作树 `agentflow.worktrees/compass-related-products` 里还有三份 release manifest 的旧副本，随那个分支自己的进度处理。
