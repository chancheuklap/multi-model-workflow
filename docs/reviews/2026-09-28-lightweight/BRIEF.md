# 调查任务书：一个技能的过度设计、过度防御、冗余与"灵魂"

你是只读调查员，负责 MMW 技能集中的**一个**技能（名字和路径在启动你的那段话里）。你查清楚它哪里多余、哪里死板、哪里缺了该有的思想性内容，写成一份报告。你不改任何文件，只写你自己的报告文件。

## 为什么做这件事

MMW 是用户的技能工具箱：一组技能加它们调用的脚本，被 Claude、Codex、Grok 等宿主上的 agent 加载去干活（写 spec、切票、夜里做票、审票、验收、发布等）。前几轮复审已经纠了错、减了重（正文约 113k → 94k 词）。这一轮的目标不同：

**在所有功能完整保留的前提下，让 MMW 回到轻盈灵活。** 充分相信加载技能的 agent 的智力和自主性。一堆条条框框、死板流程和替 agent 预想好的每一种情况，会把 agent 变成照单执行的机器人，反而降低它的表现。这些东西多半是之前构建技能的 agent 自己的设想，没有真实发生过的问题作依据。

但有一类内容**绝对不是冗余**，而且可能是技能的灵魂：让 agent 明白这件事的意义、它背后牵涉什么、对全局有什么影响、应该以什么样的思想、态度和思考方式去做。看 `mmw-v2/upstream/skills/engineering/wayfinder/SKILL.md` 的开头几段和 `## Plan, don't do`、`## Fog of war`：第一眼像是可删的解释句，其实它们让 agent 知道自己承担的是什么责任，该怎么想。技能不是 SOP 或 protocol，它是人把"这件事该怎么做、为什么这么做"交接给 agent 的载体。只有机械步骤的技能，不如直接写成脚本。

整个 MMW 遵循一条分工：

- **不需要 agent 判断、可以直接执行的东西，用脚本做，技能文本里不再复述。**
- **脚本代替不了的东西（判断、取舍、背景、意义、思路）才是技能文本和 reference 里要认真写的。**

## 你要查的三个方向

### A. 该删或该改成脚本的（"废话"）

用户对废话的定义只有三类：

1. **脚本完全可以代替完成的内容**：文本在复述脚本做了什么、它的参数表、退出码表、分支逻辑；或者文本要 agent 手工做一件确定性的事，而这件事应该（或已经）由脚本做。
2. **使用这个技能的 agent 根本不需要知道的内容**：维护者视角的设计理由（该放 ADR）、agent 默认就会做的事（no-op）、"be careful / make sure"这类空态度、只在别的角色或别的分支才用到却放在必读路径上的材料。
3. **撰写技能的 agent 留下的历史记录或碎碎念**：日期实测、"no longer / now / 原来"、改动经过、issue 号、"不要理会 X"之类的注记。

再加上用户点名的另外三种：

4. **过度设计**：为一个本来靠判断就能做好的工作规定了编号流程、if-then 清单、穷举的情况表；为执行一条规则又加一套程序；多余的层级、文件拆分、自造的术语和概念。修法是换成目标 + 完成标准 + agent 最容易判断错的那一两个判断点。
5. **过度防御**：文字或机制在守一条实际不会发生的路径。每一条都按这四问给证据：它触发过吗（tracker 历史、日志、状态文件、测试之外的真实使用）？正常输入能走到它吗？它的前提是实测为真还是推理为真？删掉以后，这种情况由谁处理（脚本的拒绝、agent 的常识、别的机制）？前两问都是"否"才算过度防御。脚本里的过度防御同样算：没人会传的参数校验、互相重复的检查、为想象中的并发或损坏状态写的恢复代码、死代码。
6. **冗余重复**：同一个意思在两处以上出现（包括脚本 `--help`、拒绝信息、脚本生成的启动 prompt、模板、别的技能）；多个脚本里重复的逻辑。说明保留哪一份（acting agent 在行动那一刻加载的那份），删哪几份。

### B. 该保护、该补的（"灵魂"）

站在一个**全新的、刚加载这个技能、手里只有触发它的那段话**的 agent 的角度，逐段读这个技能，回答：

- 它读完能不能清楚知道：自己在做的这件事的**意义**是什么？背后**牵涉**哪些东西（上下游是谁、交给谁、谁会读它的产出）？做错或做浅了对**全局**有什么影响？
- 它知不知道应该以**什么样的思想、态度、工作思考方式**去做（例如 wayfinder 的"找路而不是冲向终点"、grilling 的"事实去查、决定交给人"）？
- 哪些地方只给了步骤没给目的，让 agent 只能机械照做、遇到清单外的情况就没了方向？

对每个缺口，写出**建议补充的文字草稿**（技能正文是英文，草稿用英文），说明放在哪里、为什么能改变 agent 的做法。补充要短而有力，不写空话；不能改变 agent 行为的"意义陈述"同样是废话。

同时列出技能里**现有的**思想性、背景性段落，标明"保留，勿删"，理由一句话，以免下一轮修剪的人把它当废话删掉。

如果你怀疑前几轮减重时删掉了这类段落，可以查该技能文件的 git 历史（例如 `git log -p --since=2026-09-20 -- <技能目录>`），把值得恢复的原文找出来。

### C. 死板的流程

找出那些限制 agent 智力的结构：把本该交给判断的工作写成必须逐条执行的编号步骤、固定模板、硬规则；替 agent 规定了它自己会做得更好的细节。说明应该换成什么（目标、完成标准、判断点，以及 B 里的思路）。区分清楚：流程里真正依赖顺序的（例如脚本依赖的事件、交接顺序）必须留；只是"作者觉得应该这样做"的可以放开。

## 边界

- **功能一个都不能丢。** 每一条删改建议都写明：删掉后这项功能由谁承担（哪个脚本、哪段保留的文字、agent 的常识），剩余风险是什么。说不清的就不提。
- **上游技能**（`mmw-v2/upstream/`、`mmw-v2/upstream-diagram-design/` 下的）：用户的既定裁定是上游原文尽量不改，本仓只负责把它接进工作流。所以：
  - 重点查**本仓加的部分**：对照 merge-note（`mmw-v2/merge-notes/<技能>.md`）和上游原文的 diff（取法见 `mmw-v2/merge-notes/README.md` 开头）。
  - 上游原文只在它**在 MMW 工作流里真的会让 agent 做错**时才报，并单独列出。为了减字数去删上游原文，不提。
  - `code-review`、`implement`、`to-tickets` 三个虽在上游目录，正文几乎全是本仓写的，按本仓自有技能查。
  - 没被本仓改过的上游技能，结论可以是"没有可删的"，这是正常结果，不要硬凑发现。
- **不制造发现。** 没问题就说没问题。每条发现都要有你亲眼读到的证据；你没读到的部分，写明是推断。
- 现有的技能写作标准是 `mmw-v2/upstream/skills/productivity/writing-for-agents/SKILL-SET-REVIEW.md`，其中 `### Redundancy and bloat`（含"These stay, though a trimming pass reads them as noise"那一段）和 `### Scripts and judgement` 可以作为判断参考。但它偏向删减；凡与本任务书关于"灵魂"内容的要求冲突之处，以本任务书为准，并在报告里指出冲突。
- 用户的其他既定裁定（不用重新讨论）：description 只写触发条件；技能正文是英文；技能文本的规则唯一归属是 `SKILL-SET-REVIEW.md`。

## 怎么查

1. 读完你负责的技能的全部文本：`SKILL.md`、每个 reference、模板。大文件分段读完，不要只读开头。
2. 读它的脚本：至少读每个脚本的头部注释、`--help`、主流程和每一个拒绝/报错分支。判断"过度防御"时要读到那段代码本身。
3. 查这个技能在集合里怎么被用：`grep -rn "<技能名>" mmw-v2/ docs/agents/ AGENTS.md`，看谁启动它、谁读它的产出、它交给谁。跨技能的重复只记录，说明哪一边该留。
4. 需要真实使用证据时，可以用只读手段：`gh issue list/view`（tracker 用法见 `docs/agents/issue-tracker.md`），`~/.mmw/` 下的状态文件和日志，`nmem --json m search "<关键词>"` 查过去的决定，`git log`。
5. **只读。** 不改任何文件，不提交，不跑 `install.sh`，不跑会写东西或启动会话的命令；脚本只跑 `--help` 或只读子命令，拿不准就读源码。测试套件不需要跑。

## 报告

写到 `docs/reviews/2026-09-28-lightweight/<技能名>.md`，中文，引用技能原文时保持英文原样。结构：

```markdown
# <技能名>

## 结论
<三到六句：这个技能现在的体量（正文词数、脚本行数）；主要问题是什么；估计能删掉多少词/行而不丢功能；它的"灵魂"是否完整。>

## A. 删除或改成脚本
| # | 位置（文件 + 标题，引用原文开头几个词） | 类别（1–6） | 证据 | 删掉后由谁承担 / 剩余风险 | 建议修法 |

## B. 灵魂
### 保留，勿删
- <位置>：<为什么它是灵魂>
### 缺口与补充草稿
- <位置>：<缺什么，agent 因此会怎么做错或做浅>
  > <英文草稿>

## C. 死板的流程
| # | 位置 | 为什么死板 | 换成什么 |

## 脚本
<脚本里的过度防御、重复逻辑、死代码；每条带文件、函数名、证据。没有脚本就写"无"。>

## 与其他技能的重复或交接问题
<只记录，写明哪边该留。>

## 没查到的
<没读的文件、没能验证的推断。>
```

报告写完后，你的最终回复（给调度你的主 agent）不超过 300 字：报告路径、A/B/C 各几条、估计可删词数或行数、最重要的三条发现、有无需要用户拍板的事（只有涉及客户可见、钱、范围、不可撤回的才算）。
