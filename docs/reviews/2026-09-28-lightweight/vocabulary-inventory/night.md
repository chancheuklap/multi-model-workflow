## Same concept, several names

- **level / effort**: editing-models.md's `<level>` and `models.json`'s `effort` field are stated to be the same value — "`<level>` is the reasoning level, saved as the row's `effort`" (dispatch/references/editing-models.md).
- **pair / offering**: editing-models.md calls one selectable (model, level) combination a "pair" ("offers model-and-level pairs, each pair set per model"); models.py's own code calls the same thing an "offering" (`match_offering`, `fetch_cli_offerings`).
- **`dispatch.sh` / `<dispatch>`**: the script's own name, and the placeholder the advisor and one-ticket/inside-a-ticket references resolve it to.
- **recommendation / "the answer"**: advising.md calls the advisor's output a "recommendation"; consulting.md's own section heading for reading it is "## The answer".
- **task root / `MMW task root:`**: the Ticket-run concept "task root" and its literal rendering as a line in the worker's start prompt (dispatch.sh `worker_memory_packet()`).
- **reverify, several identifiers for one action**: the command `dispatch.sh reverify <spec>` (night.md), the plan-line token `REVERIFY <ticket>` (status.py), and the `ticket.checked` event's `run=reverify` (Ticket-run CONTEXT's "`ticket.checked`") all name one act of re-running a ticket's criteria on the base branch, at three different levels of the pipeline.
- **receipt, two unrelated uses**: retro/SKILL.md and night.md use "receipt" loosely for the confirmation that `spec.retroed` recorded a result ("`finish` needs its `recorded` receipt"); dispatch.sh separately calls its own local marker file (`mmw-reverify-<spec>`, holding green/red counts and the checked commit) the "reverify receipt". These are two different objects that happen to share the informal word — also listed below.

## Same name, several concepts

- **finding**: (a) a code-review axis's **review finding** (Ticket-run CONTEXT), (b) a ticket's child of **child kind** `finding` (Tickets/Ticket-run CONTEXT), and (c) a **watchdog finding** — one thing watchdog.py's second or third layer notices and reports as a `watchdog:` line (this group's own new term, not the same as either ticket-side concept).
- **`HOLD`**: the ticket-run concept **held** (a ticket's fold state showing an agent may still be working it) versus status.py's land-plan output token **`HOLD <ticket> <why>`** (a line meaning "still being worked, or unreadable; do nothing to it yet") — related in sense but distinct identifiers at different levels (fold state vs. printed plan line).
- **row**: the wake queue's **row** (one queued wake, relay.py) versus a **`models.json` row** (one host/model/effort entry for a dispatched agent) — unrelated objects sharing the word.
- **receipt**: dispatch.sh's local **reverify receipt** (the `mmw-reverify-<spec>` marker file) versus the informal use of "receipt" for **`spec.retroed`'s recorded result** in retro/SKILL.md and night.md — two different things.
