## Same concept, several names

- **The reviewer session** vs **the reviewer**. `code-review:SKILL.md` and `code-review:session.md` consistently call the role "the reviewer session" (session.md opens "You are the reviewer session"); `docs/contexts/ticket-run/CONTEXT.md`'s `reviewer` entry, and `implement:SKILL.md`'s own commands (`<dispatch> start <n> reviewer`), just say "the reviewer" or "reviewer". Same session, two names depending on which skill's text you're in.
- **The worker's own run** vs **run `self`**. `implement:SKILL.md` closing step 1 calls it "a run of your own"/"your own run"; `verify-ticket:verify-ticket.py` and `events.py` name it by the machine value `run="self"` (`newest_run(comments, "self")`). The `implement` merge-note explicitly rejects a third candidate name, "self-run" (as a comment's first line), because nothing in the pipeline reads a comment's first line — so the concept has exactly two live names (prose "your own run" / "the worker's own run", and the machine value `self`), with a third name deliberately not adopted.
- **`Counts:`** is computed once by `--closeout`/`draft_summary()`/`tally()` from the draft's own `ABANDON:` lines; `implement:SKILL.md` step 7 never tells the worker to compute or recount it (only to place each `ABANDON:` line under its criterion), while `docs/contexts/ticket-run/CONTEXT.md`'s `Audit` entry still describes Audit as the step that "recounts `Counts:`" — the glossary's name for who produces this fact is stale (see the flagged row above and the note below).
- **The design package binds look** / **the screen contract binds behaviour**: `implement:writing-interface-code.md`'s opening paragraph and `code-review:spec-reviewer.md`'s "What is not yours" section both restate the same jurisdiction split (design package = look/copy, screen contract = calls/shown-values/transitions/failure/timing) in their own words; not a naming conflict, but the same boundary is asserted independently in two files of my group and could drift if edited in only one.

## Same name, several concepts

- **"contract"**: (1) the `contract` sub-issue kind, opened when a baseline/spec-section/AC doesn't hold (`verify-ticket:sub-issues.md`, `implement:SKILL.md`); (2) "the contract" as shorthand for **screen contract** — used in the very same sentence as sense (1) in `implement:writing-interface-code.md` line 3 ("...the two never compete. A `contract` child for a screen-contract row that does not fit also names..."), and again in `code-review:spec-reviewer.md` ("quoted from the contract's `pages` entry"); (3) the more abstract maxim "the baseline is the contract" in `implement:SKILL.md`'s writing rules, meaning a baseline is binding authority, not literally either of the above.
- **"finding"**: the bare word covers any axis's **review finding** (code-review:session.md, all four axis files) — including ones that stay in-ticket and never leave the ticket — while `finding` is also the specific **sub-issue kind** (one of five: `fault`, `contract`, `decision`, `deferred`, `finding`) that only an *out-of-ticket* review finding becomes (`verify-ticket:sub-issues.md` question 4, `implement:SKILL.md` closing step 3). Every `finding` child is a review finding, but most review findings (the in-ticket ones) never become a `finding` child.
- **"decision"**: (1) the `decision` ABANDON kind and the matching `decision` sub-issue kind — both used together for one event: a criterion blocked on a question only a person can answer (`implement:SKILL.md` closing steps, `verify-ticket:sub-issues.md`); (2) "Decisions I made on my own" / the `DECISIONS` comment — the worker's *un*-escalated, autonomous choices, the near-opposite case (a choice the worker made itself rather than one it is asking someone else to make). Both live in the same files and are easy to conflate because both surface on the same ticket during the same round.
- **"draft"**: (1) a ticket or spec body written but not yet published to the tracker, read with `--lint --drafts <dir>` (`verify-ticket:linting.md`); (2) the closing-comment skeleton file `--draft` writes and `--closeout <draft>` consumes (`implement:SKILL.md` step 7, `verify-ticket:verify-ticket.py`). Unrelated concepts, same word, both inside the `verify-ticket` skill.
- **"Shared state"**: (1) the Spec axis's fourth reviewing angle for tickets integrated into the base branch — "both tickets agree on ownership, ordering and lifecycle of persistent or process-wide state" (`code-review:spec-reviewer.md`); (2) the unrelated lint problem tag `shared-state` for a `CHECK:` that mutates shared state without restoring it (`verify-ticket:verify-ticket.py` `lint_check_effects()`). Different concepts (a review judgement vs. a criterion-writing defect), same two words.
- **"the five questions"**: (1) `verify-ticket:sub-issues.md`'s ordered yes/no ladder that picks a sub-issue's kind (`fault`→`contract`→`decision`→`finding`→`deferred`); (2) `docs/contexts/tickets/CONTEXT.md`'s own **the five questions** entry, a *different* ordered ladder belonging to `to-tickets` (deciding whether something becomes an acceptance criterion, a code-review judgement, a `reaction` ticket, a `reach` ticket, or a user choice). Both are five-step, first-yes-wins decision procedures that end in similar-looking labels, which makes them easy to confuse even though sub-issues.md's ladder is not in the tickets glossary's entry.
- **"design-page"**: the UI axis's finding category `design-page` (a design page itself drawn wrong, `code-review:ui-reviewer.md`) is one word away from, and not the same concept as, ui-acceptance's own term **design package** (`prototypes/<effort>/claude-design/`, `docs/contexts/ui-acceptance/CONTEXT.md`). Reviewers reading quickly could misread one for the other.
