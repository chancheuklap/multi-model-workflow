### Bug fix

**You own this task. Plan, review, verify.** Delegate investigation and the fix to subagents, stay in the lead. Pick each subagent's reasoning level and fast or standard speed for the job, per the Subagents section.

Be scientific. Every shipped line traces to runtime evidence. Belt-and-suspenders that "might help" is a hypothesis, not a fix. It does not ship. When evidence refutes a hypothesis, revert what it motivated. The smallest change the evidence justifies ships, nothing more.

Redact every secret from each command, output and captured artifact you show, including the Reply: write `<REDACTED>` in its place. Build loops against environment variables so the credential stays in the environment. Quote only the lines of a captured artifact that carry the signal. If the redacted output is not enough to diagnose the bug, say so and ask the user.

1. Reproduce it yourself on the affected surface using the project's `verify-<app>` ([verify-this](../../verify-this/SKILL.md) only if none matches), even when a debug or instrumentation protocol says to ask the user to reproduce. Ask the user only with a stated, specific reason the control surface cannot reach the target, and only after driving it as far as it goes. If it won't reproduce directly, synthesize the trigger, tighten conditions, or instrument until it fires.
   - Build the reproduction as a **feedback loop**: one command you have already run, shown with its invocation and redacted output. It drives the real bug path and asserts the user's exact symptom, so it can go red on this bug and go green once fixed. It gives the same verdict on every run, finishes in seconds and runs without you. Form no theory of the cause until it exists. The [diagnosis reference](../references/bug-fix/diagnosis-loop.md) covers ways to build one, tightening it and intermittent bugs. Put the reference's path in the investigation delegate's brief.
   - If no loop can be built after that, stop and report what you tried. Ask the user for what would unblock it, such as access to an environment that reproduces it, a redacted captured artifact, or permission to add temporary production instrumentation. Do not start step 2.
   - Once it is red, cut the reproduction down one element at a time, re-running after each cut, until every remaining element is load-bearing. Step 3 takes its test seam from this minimized reproduction.
2. Binary-search the cause. Form the candidate hypotheses, then rule them out until one survives. Seed them with [how](../../how/SKILL.md) over the affected subsystem and the [why](../../why/SKILL.md) skill for regression history. Each pass, take the split that cuts the most remaining problem space, get runtime evidence, eliminate. When program state is unclear, add instrumentation or logging and read it as the code runs. Don't guess. For a long or stubborn hunt, schedule recurring wakes for the diagnostic passes. Confirm the surviving *mechanism* with runtime evidence before the step-3 [architect](../../architect/SKILL.md)/[interrogate](../../interrogate/SKILL.md) fan-out.
   - Write 3 to 5 ranked hypotheses before testing any. Each states a prediction, such as "if X is the cause, changing Y makes the bug disappear". Discard or sharpen one that predicts nothing. Record the ranked list on the work issue before testing any, and keep going, since the user may know one to drop or promote.
   - Tie each probe to a prediction and change one variable at a time. Prefer a debugger or REPL to logs, and log only at boundaries that tell hypotheses apart. Tag every temporary log with a unique prefix such as `[DEBUG-a4f2]`.
   - The investigation hands back the command, the minimized reproduction, each hypothesis with its verdict, and the surviving mechanism with its runtime evidence.
3. Plan the fix. If it crosses a function boundary, [architect](../../architect/SKILL.md) first. Delegate implementation to a subagent using your configured bug-fix model with a specific scope. Name the test seam from step 1's reproduction and have the delegate follow [write-tests](../../write-tests/SKILL.md).
   - A test seam is correct when a test there exercises the real bug pattern as it occurs at the call site. A seam too shallow for that, such as a single-caller test for a bug that needs several callers, gives false confidence. When none is correct, report that as a finding and have the delegate follow "When a failing test is impractical".
4. Verify on the same surface. The original repro now passes. "Inconclusive" or wrong-surface is not a pass. Flag it. Unit tests show branch behavior, not bug absence.
5. Stage the commits so the failing repro lands before the fix in git history. With a cheap local test path, the delegate follows "A bug with a cheap test path" in [write-tests](../../write-tests/SKILL.md). Otherwise it follows "When a failing test is impractical".
   This is the canonical [principle-sequence-verifiable-units](../../principle-sequence-verifiable-units/SKILL.md) principle skill, the failing test first and the fix on top.
   - Before staging, search for the debug prefix and remove every tagged probe and throwaway prototype. If you forced the red by mutating code or a fixture, `diff` against a pristine copy to prove the mutation landed before you trust it. Put the hypothesis that held in the fix commit message so the next debugger learns.
6. Run **Opening a PR**.

**Reply:** what was broken, root cause, fix, how you verified. Paste failing-then-passing repro output verbatim.
Redaction applies to the pasted output. Name the test seam, or say that none was correct.
