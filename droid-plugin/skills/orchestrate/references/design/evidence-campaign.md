# Design · 取证战役(设计中的大缺口,读这一份)

> 设计里的关键决策(选供应商、选模型、定并发上限、验第三方 API 合同、比开源方案)不能靠文档和口碑拍——**真枪实弹测过才能进设计**。小缺口(一次 `rg`/读码/一次网搜)就地做完回去续聊,不用本文;要立计划、跑脚本、多候选横向对比的才叫战役。

## 打法:缺口 → 计划 → 实测 → 台账 → 回填

1. **立计划**:一句话点明要坐实什么假设;取证计划落盘 `docs/design/<slug>/prototype/<日期>-<对象>-test-plan.*`(测哪些对象、什么口径、怎么算过关)。
2. **真实测**:写探测脚本、跑并发实测、开浏览器验证(用已装 `playwright-cli` skill)、调真实 API。脚本与原始产物(运行 jsonl、指标 json、出图样张、探测 tsv)**全部保真落** `docs/design/<slug>/prototype/`,不塞正文。
   - 涉**凭证 / 真机 / 生产环境**的探测,动手前先跟用户确认一句。
   - 成规模(多候选 × 多轮)→ 按对象拆并行调查工人分头测,你亲验汇总;量小自己打。
3. **记台账**:结论进 `docs/design/<slug>/evidence/<日期>-<主题>.md`,**按证据等级标注**(一手实测 > 官方文档 > 二手评论/网文);**被否决的候选也留否决理由 + 证据**——防下周把它翻出来重查一遍。
4. **回填设计**:设计文档正文只引用台账结论(一句话 + 台账路径),不内联长输出。回到原话题续聊。

## 纪律

- **开打先登记冻结面**:战役立项时把「在途取证 + 冻结哪些决定」写进设计草稿 Open Decisions,只暂停依赖它的决策分支、无关分支照常讨论;打完落盘解锁、回灌草稿——不让一场战役冻结整场设计。
- **每固化一个结论 commit 一次**(`docs(<主题>): 固化 <结论>`)——提交流水就是跨天回来时「上次打到哪」的自动记录。
- 结论必须可追溯:台账每条带产物文件指针(prototype/ 内的原始运行数据),引不出原始产物的结论降级为「待验」。
- 战役途中发现的旁路问题照常 `mmw spinoff` 登记,不就地扩战线。
