# ① 设计文档 review

**Source**:源意图(要解决的 issue / 讨论结论 / 目标结果)· 待审产物(设计文档路径)

## 轴 A 设计内容
审设计有没有把问题想清、表达完整、可落地。对照源意图报 Missing / Extra / Misunderstood:
- **挑战前提 / 方向**:先跑 quartet 方向级第一问(源意图本身可疑?)再查一致性;方向可疑用 `needs redirection`,别对着错方向把设计抠完整。
- 目标可测:每条可感知行为有可断言目标,不是"做好体验"。
- 完整性:核心流程走得通;失败 / 边界 / 空态 / 并发覆盖。
- 过度设计:有没有为当前 + 可见未来都不需要的留结构(YAGNI)。
- Mockup / 结构:界面 / 数据结构拆成可实现的样子。
- 解对问题:在解源意图真正的问题。
- Critical(必修才进 plan):核心意图不可测 / 目标含混到 plan 必须猜 / mockup 只写目录没拆视觉规格 / 关键场景缺失 / 新业务对象缺 owner。

## 轴 B 项目对齐 + 质量
审合不合硬约束、踩没踩坑。标准 = 项目领域定义 + 工程规则:
- 术语 / 数据权威:用词和落点对得上项目定义,不跨系统复制 schema。
- 不变量:项目声明的硬约束(违反即数据/钱/权限出错)没被违反(如金额状态机、血缘穿透、单一权威源)。
- 登记:新增的可被外部引用之物设计层面点到要登记(如端口 / 命令 / 收费动作 / capability / migration / ADR)。
- 质量:AI slop / 架构直觉(高频路径常驻复用、抽象边界)/ UI·UX 设计语言硬规则。
- Critical(必修才进 plan):违反不变量 / 依赖不存在的基础设施 / 跨边界合同缺 producer-consumer / 绕过项目的合同·登记·迁移机制 / 未设计生产风险。
