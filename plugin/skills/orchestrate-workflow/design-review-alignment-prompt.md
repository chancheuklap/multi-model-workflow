# Design Review — Project Alignment

Phase 0a 并行组 2：审查设计文档是否符合项目架构约束、工程规则，以及技术可行性。

## 发送给 workflow-auditor 的 prompt

你审查设计文档的**项目对齐与可行性**。另一个 auditor 同时在审查内容逻辑质量——你不需要关注完整性/可测试性/一致性/范围，专注于设计是否适配这个项目。

**Design doc**: [DESIGN_FILE_PATH]

**首先**：读取项目根目录 CLAUDE.md 及其链入的所有规则文档（如 AGENTS.md、ENGINEERING-RULES.md、PROJECT.md）。你需要完整理解项目的架构约束才能做此审查。

每个 finding 必须有：**具体位置**（设计文档哪一节）+ **违反了哪条项目规则**（引用规则原文）+ **为什么这会造成问题** + **置信度（0-100，只报 ≥ 80）**。

---

### 1. 项目架构对齐

逐条对照项目的架构约束和北极星不变量：

- 数据放对了权威源吗？（如该归 Gateway 的有没有放到 Collection？）
- 模块边界是否被破坏？（如跨模块直接依赖而非走合同/API？）
- 依赖方向是否正确？（如 shared → 业务模块的反向 import？）
- 计费/结算设计是否遵守四态收口？
- LINEAGE keys 是否在设计中贯穿？
- 新增的端口/命令/收费动作是否意识到了需要注册到权威位置？

### 2. 可行性

- 设计的技术方案在项目当前架构下是否可行？
- 依赖的外部服务/API 是否存在且可用？（用 Grep 验证项目中是否已有集成）
- 性能假设是否合理？（如"200 视频 80 并发"——项目文档中是否有相关基线？）
- 是否依赖了项目中不存在的基础设施？

---

### 校准

| 级别 | 定义 | 示例 |
|------|------|------|
| **Critical** | 违反项目架构约束，实现时必然撞墙 | 北极星不变量违反、数据权威源错误、模块边界破坏 |
| **Important** | 不直接违反但设计选择与项目惯例不一致 | 未标注需注册的端口/命令、可行但非最优的技术路径 |
| Minor | 不报 | |

### 假阳性排除

- 项目约定中没有明确禁止的做法（不外推规则）
- 设计中明确标注了"与项目约定 X 不同，原因是 Y"的有意偏离
- 超出本次功能范围的已有架构问题

### 报告格式

```
### 设计文档 — 项目对齐审查

**结论**：通过 / 阻塞（N Critical, M Important）

#### Critical
1. [confidence: 93] **节 4.2**：设计将视频审核结果存储到 Collection PG。
   **违反规则**：PROJECT.md §5.3 "视频审核 Local-First"——审核数据应在本地 SQLite。
   **为什么重要**：云端长链路抗不住 200 视频 80 并发的场景。
   **建议**：改为本地 SQLite 存储，仅批级结算结果上传 Gateway。

#### Important
1. [confidence: 82] **节 3.1**：新增 API 端口 8801 但未提及 ports.py 注册。
   **项目规则**：ENGINEERING-RULES §2.2 "新端口先入 ports.py"。
   **建议**：在设计中标注"需在 ports.py 注册 8801"。

### 低置信度观察（< 80，仅供参考）
- ...
```
