# Design Review — Content & Logic

Phase 0a 并行组 1：审查设计文档的内容质量——是否内部自洽、完整、可测试、范围适当。

## 发送给 workflow-auditor 的 prompt

你审查设计文档的**内容与逻辑质量**。另一个 auditor 同时在审查项目架构对齐——你不需要关注项目约束，专注于设计本身的内在质量。

**Design doc**: [DESIGN_FILE_PATH]

每个 finding 必须有：**具体位置**（哪一节/哪一句）+ **问题描述** + **为什么会导致下游出错** + **置信度（0-100，只报 ≥ 80）**。

---

### 1. 完整性与覆盖

- 有无 TODO / 占位符 / "TBD" / 空节？
- 用户旅程是否完整覆盖？（起点 → 操作 → 结果 → 异常路径）
- 边界条件是否考虑？（空数据、并发、权限不足、网络断开、余额不足）
- 错误场景是否有对应设计？（不只是 happy path）

### 2. 可测试性

- **逐条检查**：每条设计意图（"用户应该能 X"）能否用 Bash 命令或具体操作验证？
- 模糊意图（"性能应该好"、"体验应该流畅"）= Critical，除非附带量化标准
- 如果一条意图无法写出具体的 acceptance test 描述 → 标记为不可测试 = Critical

### 3. 内部一致性

- 文档内有无自相矛盾？（A 节说"本地存储"，B 节说"云端同步"）
- 术语使用是否一致？（同一概念是否用了不同名称）
- 数据流方向是否前后一致？

### 4. 范围纪律

- 是否聚焦单个功能/单个目标？
- 有无超出 brainstorming 结论范围的内容？（YAGNI）
- 有无为未来假想需求预设的设计？

---

### 校准

| 级别 | 定义 | 示例 |
|------|------|------|
| **Critical** | 会导致计划方向错误或无法执行 | 意图不可测试、内部矛盾、关键场景遗漏 |
| **Important** | 不影响方向但降低计划质量 | 术语不一致、边界条件未覆盖、量化标准缺失 |
| Minor | 不报 | 格式、措辞偏好 |

### 假阳性排除

- 纯格式/措辞偏好
- 设计文档中明确标注为"有意为之"的选择
- 超出本次功能范围的建议

### 报告格式

```
### 设计文档 — 内容与逻辑审查

**结论**：通过 / 阻塞（N Critical, M Important）

#### Critical
1. [confidence: 95] **节 2.3 第 4 段**："用户应该能流畅操作"——不可测试，无量化标准。
   **为什么重要**：pack-executor 无法为此写 acceptance test，Phase B 无法验证。
   **建议**：改为"操作响应时间 < 500ms"或删除此意图。

#### Important
1. [confidence: 85] **节 3.1**：术语"采集任务"和"抓取任务"混用。
   **为什么重要**：plan 中 task 描述可能因术语歧义被误解。
   **建议**：统一使用"采集任务"。

### 低置信度观察（< 80，仅供参考）
- ...
```
