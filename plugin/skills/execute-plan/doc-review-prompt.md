# Document Review — Phase 0 prompt template

Phase 0：调度 workflow-auditor 审查设计文档和计划文档。这是整条执行链的质量源头——设计不过关，计划建在沙上；计划不过关，代码在错误方向上狂奔。

## 发送给 workflow-auditor 的 prompt

你审查设计文档和实施计划。先查设计（如有），通过后查计划。**设计有 Critical 问题则停止，不审计划。**

### Phase 1：设计文档审查（仅存在时）

逐维度审查。每个 finding 必须有：**具体位置**（文档的哪一节/哪一句）+ **问题描述** + **为什么这会导致下游出错** + **置信度（0-100）**。

#### 1.1 完整性与覆盖

- 有无 TODO / 占位符 / "TBD" / 空节？
- 用户旅程是否完整覆盖？（起点 → 操作 → 结果 → 异常路径）
- 边界条件是否考虑？（空数据、并发、权限不足、网络断开、余额不足）
- 错误场景是否有对应设计？（不只是 happy path）

#### 1.2 可测试性

- **逐条检查**：每条设计意图（"用户应该能 X"）能否用 Bash 命令验证？
- 模糊意图（"性能应该好"、"体验应该流畅"）= Critical，除非附带了量化标准
- 如果一条意图无法写出具体的 acceptance test 描述 → 标记为不可测试

#### 1.3 内部一致性

- 文档内有无自相矛盾？（A 节说"本地存储"，B 节说"云端同步"）
- 术语使用是否一致？（同一概念是否用了不同名称）
- 数据流方向是否前后一致？

#### 1.4 范围纪律

- 是否聚焦单个功能/单个目标？
- 有无超出 brainstorming 结论范围的内容？（YAGNI）
- 有无为未来假想需求预设的设计？

#### 1.5 项目架构对齐

读取项目根目录 CLAUDE.md 链入的工程规则文档（如有），检查设计是否：

- 违反项目北极星不变量？
- 把数据放错了权威源？（如该归 Gateway 的放了 Collection）
- 破坏模块边界？（如跨模块直接依赖而非走合同）
- 与现有架构约束冲突？

#### 1.6 可行性

- 设计的技术方案在项目当前架构下是否可行？
- 依赖的外部服务/API 是否存在且可用？
- 性能假设是否合理？（如"200 视频 80 并发"是否有支撑）

#### 校准

| 级别 | 定义 | 示例 |
|------|------|------|
| **Critical** | 会导致计划方向错误或无法执行 | 意图不可测试、架构约束违反、内部矛盾、关键场景遗漏 |
| **Important** | 不影响方向但降低计划质量 | 术语不一致、边界条件未覆盖、量化标准缺失 |
| Minor | 不报 | 格式、措辞偏好 |

**有 Critical → 停止，不审计划。报告 Critical findings 给编排器修复。**

---

### Phase 2：计划文档审查（仅设计文档通过后）

#### 2.1 设计覆盖度

- 逐条核对：设计文档的每条意图在计划中是否有对应 task？
- 有无设计意图被遗漏？（未出现在任何 task 中）
- 有无 task 超出设计范围？（计划做了设计没要求的事）

#### 2.2 项目工程规则对照

读取项目根目录 CLAUDE.md 链入的工程规则文档（如有）：

- 计划是否违反项目不变量、单一权威源、模块边界？
- 新增的端口/命令/收费动作是否标注了需注册到对应权威位置？
- 涉及跨模块数据的 task 是否标注了合同墙要求？
- 涉及的目录如有 AGENTS.override.md，是否有 task 负责同步更新？

#### 2.3 Grep 验真

**逐条验证**计划中引用的每一个：
- 文件路径 → `grep` 或 `find` 确认存在
- 函数名 / 类名 → `grep -r` 确认存在
- 配置项 / 环境变量 → `grep -r` 确认存在

每个 grep 返回 0 结果 = Critical。**不跳过任何一个引用**。

#### 2.4 Task 质量

- 每 task 粒度 2-5 分钟？过大（> 5 分钟）= Important，需拆分
- 每 task 是否写清了 TDD 验证步骤？（"测试什么、预期什么结果"）
- Task 之间依赖关系是否正确标注？有无循环依赖？
- Section 分组是否合理？（触碰同一文件的 task 是否在同一 section？）

#### 2.5 可执行性

- pack-executor 拿到这个 task 能否直接开始？还是缺少前置信息？
- 是否有 task 的描述模糊到"不知道该改哪个文件"？
- 是否有 task 依赖外部资源但未说明如何获取？

#### 校准

| 级别 | 定义 | 示例 |
|------|------|------|
| **Critical** | pack-executor 会卡住或做错 | 引用不存在的路径/函数、违反项目约束、设计意图遗漏、task 描述无法执行 |
| **Important** | 不卡但降低执行效率 | task 过大需拆分、TDD 步骤缺失、依赖未标注 |
| Minor | 不报 | 措辞、格式 |

---

### 假阳性排除

以下**不要报**：
- 纯格式/措辞偏好（不是审美审查）
- 已在设计文档中明确标注为"有意为之"的选择
- 项目约定中没有明确禁止的做法（不外推规则）
- 超出本次功能范围的已有技术债（不趁机翻旧账）

### 报告格式

```
### 设计文档审查结果（如有）

**结论**：通过 / 阻塞（N Critical, M Important）

#### Critical
1. [confidence: 95] **节 2.3 第 4 段**："用户应该能流畅操作"——不可测试，无量化标准。
   **为什么重要**：pack-executor 无法为此写 acceptance test，Phase B 无法验证。
   **建议**：改为"操作响应时间 < 500ms"或删除此意图。

#### Important
1. [confidence: 85] **节 3.1**：术语"采集任务"和"抓取任务"混用，指同一概念。
   **为什么重要**：plan 中 task 描述可能因术语歧义被误解。
   **建议**：统一使用"采集任务"。

### 计划文档审查结果

**结论**：可执行 / 需修正（N Critical, M Important）

[同上格式]

### 低置信度观察（< 80，仅供参考）
- ...
```

Phase 0 finding 不标注路由——全部返回给编排器（主 session）直接处理。
