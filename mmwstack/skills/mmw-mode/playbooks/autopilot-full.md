### Autopilot-full

**You own the verdicts, never the PRs. One owner carries each PR from build to merge, and nothing merges until an independent verifier has proven the code that lands.**

A verdict covers one patch and green CI covers one head. Step 4 runs full verification once, and again only for a major change. The patch-id rule in `playbooks/shipping.md` can carry a lane's result, and every new head needs its own green CI. If an active plan still directs multiple workers to verify a PR, give its scenarios and existing evidence to one verifier before the next dispatch. Preserve its pass conditions and operator gates. For a multi-PR spec or plan, `trunk` means a dedicated `project/<slug>` branch created off the repository's integration branch before spawning owners; child PRs merge into `project/<slug>`, never directly into `dev` or `main`. For a standalone single-ticket run, `trunk` is the repository's integration branch.

1. **The operator's gates come first.** The grant covers only the queue's items, so items the operator names as theirs and PRs outside the queue stop at merge-ready. A request to state the plan is not a go. For a multi-PR spec or plan, create and push `project/<slug>` from the integration branch first (`git push origin origin/<integration>:refs/heads/project/<slug>`), and use that branch as each owner's base. In a local Home Repo task, pass `--base project/<slug>` to `scripts/worktree start`.
2. **Spawn one owner per PR, and keep its work where a replacement can find it.** Resolve the forge once per `playbooks/opening-a-pr.md` and use it throughout the program. Use the model and settings from the current host’s `coder` entry in `~/.agents/mmwstack-models.md` (or the supplied rule file). On Factory Droid, set `subagent_type` to `mmw-agent-<tier>`, replacing `<tier>` with the tier from this step’s model entry. Give it a separate worktree on the user's computer for a local task or a separate cloud workspace for a cloud task. Replacements inherit the task's execution environment. Give it the execution ticket URL and the PR URL if the ticket already has one. If the ticket calls for writing or changing tests, include the expected behavior and “Invoke [write-tests](../../write-tests/SKILL.md) before writing or changing tests.” An owner who delegates that work passes both to the writer. The owner builds, opens or resumes the ticket's PR per `playbooks/opening-a-pr.md`, proves the change on the real artifact, babysits to green per `playbooks/babysit.md`, and merges once steps 4 and 5 clear it. Where that playbook says to report a rebase, the owner rebases its own branch and publishes it with `git push --force-with-lease` pinned to the SHA it last pushed or took over.

   Open the PR early so CI and bots run alongside the work. The code is ready only after the slop-strip (the [deslop](../../deslop/SKILL.md) skill) and the [no-comments](../../no-comments/SKILL.md) pass, so the verifier checks finished code. Then rebase onto current trunk and report the code-ready head before self-proof, so verification runs on the base the patch lands on. Report every later head, and merge-ready once self-proof, CI, and babysit are done. Fix rounds stay on that base unless trunk conflicts, breaks CI, or lands a known concurrent change to the same files, because each rebase restarts CI. Run the repo's checks for the touched paths on the committed head before the code-ready push and before a later push that needs a verifier.

   Assume the worker environment can disappear. Soon after starting, push and start a decision trail in the root coordinator's artifact store named in the kickoff per the [show-me-your-work](../../show-me-your-work/SKILL.md) skill, then push each finished unit before you start the next. Whoever spawns a subagent records its id, state, and a stuck-after runtime from past runs of its kind there, so the root can probe it if the parent dies. Force-push only your own branch, with `--force-with-lease` pinned to the SHA you last pushed or took over, and on any push you did not make, stop and report to the root.
3. **Run owners in parallel off trunk, never stacked,** so each PR lands on its own.
4. **Verify the code-ready head independently.** Dispatch one fresh agent in a separate worktree or cloud workspace in the task's execution environment. Use the model and settings from the current host’s `verifier` entry in `~/.agents/mmwstack-models.md` (or the supplied rule file). On Factory Droid, set `subagent_type` to `mmw-agent-<tier>`, replacing `<tier>` with the tier from this step’s model entry. Give it the PR URL, code-ready SHA, execution ticket URL and acceptance criteria. It reruns the gates, exercises each required scenario on the real surface and returns the result and evidence for each check. Use the project's `verify-<app>` for each affected surface, or [verify-this](../../verify-this/SKILL.md) where none matches. New behavior, a redesign or a large new diff gets full verification again. For a rebase, conflict resolution or minor fix, dispatch one verifier on the new head to recheck affected behavior and apply Shipping's patch-id rule. A wording-only change gets no new verifier. Check the live evidence and the merge-ready receipts before issuing a verdict. Leave diff-wide Code review to the project branch after its PRs land.

   Block a PR only for a problem you can show, with a failing run at the head or a doc line the PR made wrong. A problem the PR's base already has, whether trunk or the PR below it in a stack, doesn't block unless the PR copies it or newly reaches it. Only a bug a user would hit, a failed gate, or a wrong shipped doc blocks, and everything else goes in a follow-up.
5. **The owner merges only what you verified, tested on the trunk it lands on.** Green CI alone never authorizes a merge. Once the verifier has started, merge prep rebases onto current trunk, reports the new head, and waits for green CI.

   Right before merging, fetch trunk and ask whether its changes can affect the patch, because rebasing for every trunk move never ends. Rebase and wait for CI when the code that would land was never tested, as with a conflict, a file both sides changed, or a change to which checks run for the PR. A lockfile both sides changed needs no rebase when a frozen install passes on the merge result and the packages the PR changes resolve there as on the head, because that install tests the lockfile that would land, and a failing install means the rebase must repair it. When trunk changed a caller of the patch or something the patch depends on, such as code it calls or a dependency version, run the patch's checks on the merge result and merge on a pass. Otherwise merge. If trunk would force a third rebase past merge prep, hold and report to the root, which sequences the colliding work.
6. **Run the root layer.** Anything that loosens a gate, such as a raised budget or an allowlist entry, needs a verifier's proof and then your fresh countersign, because the owner is the one who wants green. Under a grant that covers approvals, that countersign is the approval, and the owner's record of it points at your countersign for the verifier to check. A disabled or soft-failed check always comes out, because it stops guarding every case. Never give or bypass an approval the forge enforces, because no countersign covers it.

   On the operator's go, schedule an hourly audit that can wake the coordinator until no delegated work is left, because long runs drift and agents stall silently. If the host cannot wake the coordinator, report that the hourly audit is unavailable. Each tick re-reads the execution playbook named in the kickoff from trunk and fixes drift, such as an unreported head or an unrecorded agent, by having its owner record it, because drift is a gap in the record, not a stall. It probes every agent, including each owner's delegates, and judges each by its side effects, because status text and summaries can hide a stuck child. An agent is stuck when it errors, cannot start turns, or shows nothing new past its stuck-after runtime, and so is an owner that has neither pushed nor written a trail row by the first tick. One waiting on you or the operator is not stuck, so answer it. Replace a stuck agent at once, without waiting for its stop to land. A tick that changed something for the operator ends by catching them up per the [ketchup](../../ketchup/SKILL.md) skill, and one that changed nothing stays quiet.
7. **Stand down at once on the operator's stop, or once all project-branch PRs land.** Cancel pending audits on stop. A hold reaches every owner as a zero-writes order. Each reports where it stands and keeps its brief until the operator releases it. When running against a `project/<slug>` branch, stop after all child PRs have merged into `project/<slug>` and hand the branch to the operator for `/code-review project/<slug>` and final merge into the integration branch.

**Reply:** catch the operator up per the [ketchup](../../ketchup/SKILL.md) skill, covering each PR's state and verdict, what merged, countersigns and why, open operator gates, and parked follow-ups, with links to each PR and the trails.
