# 处置、指纹与报告

## A 类违规项的修改流程

**前提是工作区干净**，由主文件第 1 步保证。这个前提让下面每一条都成立，不需要任何自造的回滚机制。

1. **先跑完全部九种判拒，收集全部结果，再统一进入修改。** 理由见主文件第 8 步。
2. **逐条修改，逐条验证。** 每改完一条，只重跑触发这条违规项的那一项检查。判据是：这条违规项对应的那条判据现在满足了。
3. **全部改完之后，把四种 A 类检查整体重跑一遍。** 逐条验证只看得见自己那一条，看不见「这次修改是否引入了别的 A 类问题」。成本很低——A1 读数值、A2 跑规则引擎、A3 比对 token 集合、A4 读控制台，全是确定性检查，不需要模型判断，也不需要重走语义层。
4. **改坏了用 git 退回去。** 整体重跑发现新的 A 类违规项，或某条逐条验证没过，就 `git checkout` 那个文件退回该次修改。工作区在开始时是干净的，所以退回不会碰到用户的东西。退回的那条降级成 finding 报给用户，标明「尝试修复失败」。
5. **改不了源码的一律不改。** 违规项定位到第三方组件内部或依赖包里的文件时，不修改，转成 finding 报给用户。

**B 类不重跑。** 用户裁决时看到的是修改前的界面，这一点在报告里写明。A 类改的是阈值、WCAG、token、运行时错误这四类确定性问题，不改变 B 类关心的流程与语义。

**本次全部 A 类修改合成一个提交。** 提交信息写明这是界面 QA 的修改、改了哪几条违规项。

选一个提交而不是一条一个，理由是回退的实际用法：用户要么接受这一轮修改，要么整轮退掉，逐条退不是真实场景。报告第 1 节仍逐条列出改了什么，要单独退某一条，用户在这个提交的基础上自己改。

技能敢提交，是因为第 1 步保证了工作区干净——**这个提交里只有技能改的东西，不可能夹带用户没写完的代码**。

## 五个处置标记的去向

B 类走 MMW 既有的五个处置标记。技能不自动修改 B 类，等用户裁决。

| 裁决 | 谁去修 | 存不存进判据 | 下一轮指纹命中时 |
| --- | --- | --- | --- |
| `accepted` | **主 agent 当场修**，与 A 类的修改一起进本次那个提交 | 存，状态「已确认」 | **再报一次**，标明「上次已确认并修过，现在又出现了」 |
| `rejected` | 不修 | 存，状态「已裁决不成立」 | 压制，不报 |
| `waived` | 不修 | 存，状态「已搁置」 | 压制，不报 |
| `duplicate` | 跟随它指向的那条 | 不单独存 | 不适用 |
| `needs-evidence` | 不修 | **不存** | 不适用 |

**`accepted` 是回归标记，不是压制标记。** 这一点容易搞反：`rejected` 和 `waived` 的意思是「这不是问题」，所以下一轮命中要压制；`accepted` 的意思是「这是问题，而且已经修了」，下一轮又命中说明**问题复现了**，压制它等于把已确认的缺陷永久藏起来。

**`needs-evidence` 不进判据**，因为它表示没能在源码里验证出这条 finding 的出处——它还不是一个成立的判断，存进长期判据会污染判据文件。它只出现在本次报告里。

B 类的修复没有可重跑的确定性检查可验证，它是模型判断。所以验证方式是下一轮：问题真解决了，下一轮不会再产生这条 finding；没解决，下一轮按上表再报一次。

**裁决全部长期保存，不论结论。** `accepted`、`rejected`、`waived` 都一样，当场写进该产品的可用性判据，带状态字段区分。只回流 `accepted` 会让被判不成立的条目每轮重复出现。

## 归属裁决

界面与判据不一致时，判据层次决定默认归属：

- 与阈值表不一致 → **默认判实现错**，因为可执行下限没有「有意改小」的合理场景。
- 与设计系统规则或可用性判据不一致 → **标为需要用户裁决**，因为有意改动设计是正常的。

## 指纹：哪条判拒 + 哪个位置

每条 B 类裁决存一个指纹，两截：判拒编号，加位置。位置按判拒的天然粒度取，四种形态。**指纹由技能自动生成，用户不参与。**

**元素级（B1、B5）**

```
判拒：B1
判据：DS-规则3          ← 被违反的是哪一条
界面：main
状态：default
元素角色：button
元素名：同步
```

界面与状态两个字段直接取全图已有的标识。元素角色与元素名取无障碍树快照里的值。

**`判据` 字段不能省。** 同一个元素可能同时违反两条不同的判据——一个按钮既不符合设计系统的间距规则，又不满足某条产品可用性判据。不记被违反的是哪一条，两条 finding 的指纹完全相同，用户对其中一条判 `rejected`，会把另一条真实问题一并压制掉。取值：B1 取设计系统正文里那条规则的标识，B5 取可用性判据的条目编号。

**这里有意不用 CSS 选择器。** 选择器带 class 名与位置序号，界面一重排就全变。角色加可访问名稳定得多，而且与主输入同源，不引入第二套定位方式。

**步骤级（B2）**

```
判拒：B2
走查任务：新建同步任务
步骤：3
问：2
```

`问` 是四问的第几问。同一步在第 2 问和第 4 问上失败是两件事，分开记。

**屏级（B4）**

```
判拒：B4
界面：main
状态：default
问：5
```

**屏级或路径级（B3）**

```
判拒：B3
界面：[main]
状态：[default]
```

界面与状态是数组。单屏「很困惑」时长度为 1；连续两屏「有点困惑」记的那一条指向一段路径，长度为 2。

**A 类不记指纹。** 它直接修改，不产生裁决，没有要记住的东西。

## 两级匹配

每次运行，把本轮每一条 B 类 finding 的指纹，与该产品可用性判据里已有的裁决逐条比对。

| 级 | 条件 | 结果 |
| --- | --- | --- |
| 第 1 级 · 全等 | 指纹每个字段都相同 | 同一件事。按已有裁决处理，**不报给用户** |
| 第 2 级 · 近似 | 判拒相同，位置字段**恰好只有一个**不同 | 可能是同一件事。报给用户，附上上一轮的裁决，问是不是同一件事 |
| 都不中 | 判拒不同，或两个以上位置字段不同 | 新问题，正常报 |

「恰好只有一个字段不同」是确定性规则，同样的输入永远得到同样的结果，不依赖模型判断。它覆盖界面迭代中最常见的三种改动：

| 改了什么 | 哪个字段变 | 落在哪级 |
| --- | --- | --- |
| 按钮文案从「同步」改成「立即同步」 | 元素名 | 第 2 级 |
| 状态从 `default` 拆成 `default` 与 `syncing` | 状态 | 第 2 级 |
| 走查任务中间插一步，原第 3 步变第 4 步 | 步骤 | 第 2 级 |
| 按钮换了界面又改了名 | 界面 + 元素名 | 新问题 |

最后一行是有意的：既换界面又改名的元素已经不是原来那个东西，重新问一次是对的。

**第 2 级命中后的处理。** 用户答「是」，把这条裁决的指纹更新成本轮的新值，以后按裁决处理；答「不是」，当新问题，用户重新裁决，判据里多一条。

**不用回退式匹配。** 代码分析工具那边用的是多级回退——位置对不上就退而比对内容或消息，自动判为同一件事。那套在代码上成立，因为代码改一行周围几十行不动。界面改一版可能整屏重排，同样的回退在这里误压制的概率高得多。所以在第 2 级停下来问用户，而不是自动判定。用户只答「是/不是」，比从头裁决一遍轻得多。

## 陈旧裁决：只列出，不自动删

每次运行结束，检查该产品可用性判据里的裁决条目。**只检查指纹落在本轮范围内的那些**：指纹的界面在本轮检查过，而本轮两级都没有命中，才列进报告最后一节。

**范围外的裁决一律不参与陈旧判定。** 默认档只查本次改动，绝大多数界面本轮根本没被检查，当然不会命中——把它们列成「可能失效」是把「没查」当成了「查过但没发现」，会诱导用户删掉仍然有效的判据。B2 的指纹按走查任务定位，同理只在本轮实际走过的走查任务范围内判定。

因此只有「全量」档会对全部裁决做一次完整的陈旧检查。那一档本来就用在初版落地和上 Windows 之前，正是适合清理判据的时机。

**只列出，不自动删除，也不因此让运行失败。** 代码检查工具那边是在问题修好后以非零退出码报错，那套面向持续集成流水线；界面 QA 面向用户在迭代中随手发起，报错会打断他。用户看到了想删就说一句。

这一条防的是判据腐烂——裁决只增不减，会长成一份越来越大、且在压制早已不存在问题的文件。

## 报告结构：五节

按「要用户做什么」排序：

| 节 | 内容 | 要用户做什么 |
| --- | --- | --- |
| 1 · A 类改了什么 | 每条一行：违规项编号、文件与位置、改前值、改后值、验证结果。末尾给出本次修改的提交 SHA | 不做事，看一眼。要整轮退掉就 revert 那个 SHA |
| 2 · B 类新 finding | 两级都没中的。标 `已回滚` 的 A 类也出现在这里 | 逐条裁决 |
| 3 · B 类近似匹配 | 第 2 级命中的，每条附上一轮裁决 | 每条答「是/不是」 |
| 4 · 三类报告项 | 覆盖报告、判据自检结果、声明与实现不一致 | 不做事，可选择说一句 |
| 5 · 陈旧裁决 | 指纹落在本轮范围内、却没有对应检查结果的裁决 | 不做事，想删就说一句 |

第 2 节与第 3 节分开，因为第 3 节要的只是「是/不是」，比新 finding 好答得多，混在一起会让用户按同一种强度去想每一条。

第 4、5 节分开，因为两者性质不同：第 4 节说的是**本次检查的边界**（哪些没查到、判据自身有什么问题），第 5 节说的是**已有判据可能该清理了**。合成一节会让用户以为覆盖缺口也需要他处理。

第 1 节的「验证结果」栏取两个值：`已验证`（逐条重跑该项检查通过，且全部改完后的整体重跑没有引入新的 A 类违规项）或 `已回滚`（任一环节未过，修改已撤销）。

**报告开头固定五行，写在五节之前：**

```
本次范围：本次改动（未指定，默认档）
覆盖：3 个界面 / 7 个状态
未覆盖：12 个界面 / 31 个状态
判据：阈值表 v1 · 小黄鸭可用性判据 14 条 · 设计系统已读并校验
本次跳过：无
```

范围因降级变过时，第一行写成「本次改动 → 本任务（本次改动未涉及界面文件）」，把降级原因带上。「本次跳过」那一行接各种降级情况：设计系统文件缺失写「A3、B1（设计系统文件不存在）」，语义层没返回结果写「B2、B3、B4（语义层评估未返回结果）」，Windows 能力自检有缺项写缺哪几项。

## 裁决回流到哪

**被采信的 B1 回流到可用性判据，不回流到设计系统。** 设计系统只读，改不了。采信的设计系统规则违反，写成该产品可用性判据里的一条，正文记录它是对哪条设计系统规则在本产品上的具体化，来源指向那条规则。

**属于阈值性质的裁决进阈值表。** 例如用户确认某类元素的最小尺寸，写进阈值表，下一轮由 A1 直接判定。

每条回流都写明来源为本次界面 QA 与日期。
