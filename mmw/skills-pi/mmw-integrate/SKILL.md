---
name: mmw-integrate
description: 把结果分支集成到当前任务分支。用于合并已完成分支、让未完成分支 rebase 到已推进的目标分支，或处理进行中的 merge 或 rebase 冲突。
---

开始前，遵守目标仓库 `AGENTS.md` 的领域上下文规则。

把几条结果分支集成到当前任务分支。当前任务分支是本轮唯一目标；主 agent 不切换工作目录，也不把结果直接合入仓库的默认分支。

当前已经存在 merge 或 rebase 冲突时，直接进入第 3 步。merge 读 [merging.md](merging.md)，rebase 读 [rebasing.md](rebasing.md)。

## 1. 记录现状

先确认当前在一条任务分支上：`git symbolic-ref --quiet --short HEAD` 有输出，且不在主检出里。记下当前任务分支和 `HEAD`。工作区有与集成无关的未提交改动时停下。

每条结果分支记录四项：

| 项目 | 取得方式 |
| --- | --- |
| 分支与报告 HEAD | 使用执行者交回的分支名和 HEAD SHA |
| 基点 | 使用派发时记录并由执行者交回的基点 SHA |
| 完成状态 | 检查 task 验收、主 agent 验证和终审记录 |
| 合同关系 | 检查一条分支是否提供另一条分支消费的数据模型、interface、迁移或序列化格式 |

先运行 `mmw result verify <结果分支> <HEAD SHA> <基点 SHA>`。任何一项与报告不一致时，不集成该分支。

## 2. 多条分支同时合，先调查

**只有两条以上已完成的结果分支要在这一轮合进来时才做这一步。** 只让一条未完成分支跟上，跳过，直接进第 3 步。

git 说没冲突，不等于这几条分支的意图合到一起是对的。四个角度各走一遍，读各分支的 spec 和它们各自的 diff：

1. **组合行为**——全部分支合在一起，产出的是各份 spec 描述的行为吗。各自对不等于组合对，盯交互、顺序、依赖。
2. **合同一致**——跨分支的数据模型、interface、数据库结构、序列化格式、登记表一致吗。一个分支提供的合同，被另一个正确消费了吗。
3. **迁移完整**——多个分支的数据迁移合并后顺序对吗；有没有漏（这条改了模型，那条没配套迁移）；回滚安全吗。
4. **状态一致**——跨分支对同一份共享状态、缓存、全局配置的假设一致吗；并发访问安全吗。

**不信各分支自己终审的结论。** 那些结论只证明每条分支单独成立。

调查结果就在对话里说，不落盘。说清三样：合并顺序、每处已知取舍点打算怎么定、哪几处你判不了要用户拍板。判不了的那些，停在这里等他，不要先合了再说。

完成判据：四个角度各有一条结论；这一轮要合的每条分支在顺序里都有位置。

## 3. 确定顺序与路线

| 结果分支状态 | 处理方式 |
| --- | --- |
| 已完成并通过终审 | 合入当前任务分支，读 [merging.md](merging.md) |
| 尚未完成，当前任务分支已经推进 | 在拥有该结果分支的任务中 rebase 到当前任务分支，读 [rebasing.md](rebasing.md) |

已完成的分支按合同依赖排序：提供方先合，消费方后合。没有合同关系时，按终审通过时间排序。顺序确定后逐条推进；如果依赖事实发生变化，停止本轮并重新排序。

## 4. 逐条推进

合入已完成分支时，运行：

```bash
mmw result integrate <结果分支> <HEAD SHA> <基点 SHA>
```

命令使用 `git merge --no-ff`，保留结果分支的提交历史。发生冲突时按 [merging.md](merging.md) 继续，不重新运行集成命令。

未完成分支需要跟上当前任务分支时：

**这条结果分支归谁，就让谁推进它。** 它是宿主后台任务产出的，就让那个后台任务在它自己的 worktree 里继续；它是本地 worktree，用 `git worktree list` 找到路径，让它在那棵树里做。无论哪种，**主 agent 不切换自己的工作目录**。

推进它的那一侧按 [rebasing.md](rebasing.md) 操作，做完交回新的 HEAD SHA 和验证结果。

主 agent 拿这两个新值重跑一次 `mmw result verify <结果分支> <新 HEAD SHA> <新基点 SHA>`——**rebase 之后基点变了**，新基点就是它 rebase 到的那个当前任务分支 HEAD，用它，不用旧的。整轮只跑这一次。

冲突处理遵守三条规则：

1. 先读取提交、issue 和 spec，确认双方意图。
2. 逐块保留双方兼容的行为；不兼容时只按本轮已确定的目标取舍。双方 primary source 和既定目标都没有要求的行为不得加入。
3. 每次推进后运行目标项目要求的检查。

冲突解决只组合已有意图，不发明新行为。若必须增加第三种行为才能让代码通过，现有目标不足以决定取舍，停止并交用户判断。

把实质取舍写入下面命令输出的记录。同一天第二轮在日期后加序号：

```bash
mmw artifact path review --sub integration-<日期>[-<序号>].md
```

每条记录文件位置、双方意图、保留内容和理由。

完成条件：没有进行中的 merge 或 rebase；工作区干净；本轮应合入的分支都出现在当前任务分支历史中。

## 5. 合完自查

有三件事合并前查不了，合完当场查，不派审查者：

1. **模块引用**——合并后有没有循环引用；依赖版本一致吗。
2. **回归**——跑目标项目的完整测试套件，报结果。
3. **冲突修复质量**——解过冲突的地方解得正确、完整吗。取舍记录里写了保一边的，保下来的确实是这一轮目标要的吗。

三条里有一条不过，停下报告，不要带着它进终审。

| 情况 | 处理 |
| --- | --- |
| 集成完成，自查三条都过 | 报告已合入的分支和当前任务分支 HEAD。问用户：终审，还是到这里停。终审固定点用集成前记录的当前任务分支 `HEAD` |
| 这次只让一条未完成分支跟上，没有新的已完成分支合入 | 报告已合入的分支、仍在工作的分支和当前任务分支 HEAD |

**不是你建的树就不归你清。** 看这棵树在哪：位于当前仓库 `.mmw.json` 的 `paths.worktrees` 下，等用户批准之后跑 `mmw worktree remove <当前结果分支>`；在别处，是宿主给的，它会在任务归档后自己回收。
