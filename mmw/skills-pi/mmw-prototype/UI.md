# UI Mockup

UI mockup 用可运行页面理顺页面、状态和操作路径。它是 prototype 资产，不是临时预览。用户在浏览器中走查，选择一个方向，或者指出需要组合和修改的部分。

## 1. 确定本轮起点

已有 `README.md`、`mockup/current/` 或变体时，先读取它们。再读取相关文档、讨论结论、真实数据、组件库和样式系统。读完后按下表选择本轮路径：

| 当前情况 | 本轮路径 |
| --- | --- |
| 还没有 `mockup/current/`，而且整体方向不明确 | 生成多个完整 UI mockup 变体，让用户选择或组合一个起点 |
| 已有 `mockup/current/`，而且某一部分的方向不明确 | 保持其他部分不变，只为这一部分生成多个局部变体 |
| 方向已经明确 | 没有当前 mockup 时直接创建 `mockup/current/`；已有当前 mockup 时直接修改它 |

变体是解决方向不确定的手段。方向明确时，直接创建或修改当前 mockup。已有当前 mockup 时，以它为起点继续优化，不重新生成整套界面。

这一节完成时，必须明确本轮是「完整变体」「局部变体」还是「直接创建或修改」。同时写清本轮验证问题和保持不变的部分。

## 2. 选择承载形态

| 项目情况 | 承载形态 |
| --- | --- |
| 已有成熟应用，而且 prototype 天然属于某个页面或流程 | 挂入已有页面。保留真实页头、侧边栏、数据密度、取数、参数和鉴权，只替换正在验证的界面部分 |
| 全新产品、纯后端仓库，或者需要跨前端和后端验证可行性 | 在 [SKILL.md](SKILL.md) 确定的 `mockup/current/` 或对应变体目录中使用独立 HTML。它是正常形态，不是最后手段 |
| 已有应用，但没有任何现有页面能够承载一个新的顶层界面 | 按项目现有路由约定建立明确标记的 prototype 路由 |

挂入已有页面时，prototype 更容易暴露真实密度、数据和流程问题。独立 HTML 适合尚无前端宿主的产品，也适合把前端和后端可行性放在同一份 prototype 中验证。

UI mockup 的持久资产必须保存在 `mockup/`。应用源码中确实需要 route 或挂载文件时，只保留让 mockup 运行所需的薄接线，并在 `README.md` 中记录它与 `mockup/` 内资产的精确对应关系。

## 3. 创建当前 mockup 或变体

直接创建或修改时，只改 `mockup/current/`。它是后续轮次继续优化的唯一当前 mockup。

需要变体时，为本轮验证问题建立 `mockup/variants/<问题 slug>/`。`<问题 slug>` 从本轮验证问题提炼，使用简短的 `kebab-case` 名称。每个变体使用独立子目录，例如 `variant-a/`、`variant-b/`。

完整变体可以改变整页布局、信息层级或 `primary affordance`。局部变体共享当前 mockup 已确认的部分，只替换本轮正在比较的页面、组件、状态或操作路径。每个变体必须存在真实结构差异。只改变颜色或文案不构成新变体。

变体数量由仍待比较的结构方向决定，不使用固定数量。每个变体都遵守页面用途、真实数据和项目现有组件库或样式系统。

用户已经选择方向后，把选中结果或实际组合结果写进 `mockup/current/`。后续轮次继续修改当前 mockup。原变体组保持不变，作为本轮选择的一手来源。

多个结构方向可以独立生成，而且并行能够缩短当前轮次时，可以为每个方向派一个 `prototype-worker`。每份 task 使用以下四栏表：

| 栏 | 内容 |
| --- | --- |
| 目标 | 当前验证问题，以及该 `prototype-worker` 负责的一个结构方向 |
| 读 | 页面或流程的精确路径；真实数据、组件库、样式系统和现有 prototype 资产的精确路径 |
| 约束 | 只实现分配的结构方向；只修改分配给自己的文件；不实现其他变体；不写测试；把 prototype 身份标在页面上 |
| 验收 | 变体可以运行；结构方向与其他变体存在真实差异；交回精确运行方式、走查地址或文件路径，以及结果分支上的 HEAD SHA |

派发前，确认当前任务分支已经提交，而且 worktree 干净。为每个 `prototype-worker` 确定唯一、完整的结果分支名，并记录当前任务分支的 `HEAD` 作为基点 SHA。把结果分支名和基点 SHA 写入对应 task。

启动：先运行 `mmw task new <结果分支> "<目标栏原文>" --from <基点 SHA>`，使用命令返回的 worktree 绝对路径作为 cwd。然后调用原生 `subagent`，agent 设为 `mmw-prototype-worker`，task 传四栏表全文，cwd 设为该绝对路径。

每个 `prototype-worker` 交回后收取结果：

该角色完成后，运行 `mmw result verify <结果分支> <HEAD SHA> <基点 SHA>`。命令通过后，从输出取得结果 worktree 路径；在该路径读取报告与 diff，并运行本技能规定的验收。这一步不合入结果分支。

按 `/mmw-verifying-agent-output` 验证结构差异、项目组件约束和可运行性，再集成通过的结果：

本技能规定的验收全部通过后，运行 `mmw result integrate <结果分支> <HEAD SHA> <基点 SHA>`。命令成功后，结果提交才算进入当前任务分支。

并行没有明显收益时，由主 agent 直接完成。直接创建、直接修改或只有一个方向时，由主 agent 完成，不派 `prototype-worker`。

## 4. 连接和切换变体

每个变体使用清楚的名称，例如 `VariantA`、`VariantB`。变体之间可以共享已经确认的页头等稳定组件，但不能共享正在比较的整体布局或局部结构。

多个变体需要切换时，在同一路由使用 `?variant=` 查询参数和浮动切换器。保留切换器上方的真实取数、参数和鉴权，只切换正在比较的渲染子树。

浮动切换器固定在屏幕底部居中，提供上一个变体、当前变体名称和下一个变体。上一个和下一个按钮在首尾之间循环。点击按钮或按 `←`、`→` 方向键时更新 URL 查询参数，使链接可以分享并在刷新后保持稳定。焦点位于输入框、文本域或可编辑元素时，不拦截键盘方向键。切换器在视觉上与产品界面区分，并在生产构建中隐藏。

只有一个已选方向时，不保留无用切换器。

用户要求组合不同变体时，先完成本轮记录。再把指定部分组合进 `mockup/current/`，形成一份可运行页面并重新走查。不能只用文字宣布组合已经选定。

## 5. 连接后端行为

初轮可以使用桩来验证 UI/UX 流程。流程确定后，为每个功能和按钮补上后端脚本、接口合同或可复用 `module`，并在 `README.md` 中记录精确对应关系。

写操作尚未接入真实后端时，必须清楚显示桩行为。需要验证真实写操作时，先完成对应后端 prototype，再让页面调用它。

每个实际存在的页面状态都应能呈现，包括与当前问题相关的加载、空、错误、成功和部分完成状态。页面变化后显示用户判断当前问题所需的完整相关状态。

## 6. 打开并交给用户

把页面地址和 `?variant=` 取值交给用户。只有一个方向时，直接给出该页面地址。

按 [SKILL.md](SKILL.md)「用户走查」的浏览器规则打开全部页面。宿主有内置浏览器时使用内置浏览器。宿主没有内置浏览器时使用 Playwright。必须让用户和主 agent 同时能够看到并操作同一份 UI mockup。

用户给出任何走查意见后，继续本文件第 7 节。

## 7. 保存结果

这一轮记什么、`README.md` 怎么维护、交回调用方什么，全部见 [capture.md](capture.md)。

用户选中的方向已经把界面这个想法磨清楚时，`mockup/current/` 中的页面结构、组件和交互就是下游可以直接参考或复用的内容。变体组、调试路由和切换器继续作为 prototype 资产保存，不列为可复用内容。
