# 合规交叉审

**谁读**：任务名是「合规交叉审」的审查者。

这个视角看这批 plan 合不合项目的硬规矩，以及它们引用的东西是不是真的存在、几份 plan 之间对不对得上。

## 往哪里看

- **交叉验证**：每份 plan 里引用的每一个夹具、辅助函数、行号、表名、接口，都自己 grep 或读一遍验真存在——**引不出来就是一条 finding**。同一个文件被几块、甚至被几份 plan 同时改的冲突风险；没标出来的隐式顺序依赖。
- **prototype 资产**：plan 引用的资产目录、用户选中版本和逐轮记录都真实存在；落选变体没有被当成当前设计或生产实现的依据。
- **合规**：跨边界的合同改动同步了全部消费方并升了版本；数据的唯一事实来源没被绕开；项目的不变量没被违反；新增的可被外部引用之物入了登记；新的数据库字段配了迁移；辅助函数放在对的边界上；新文件标了是新建。
- **依赖**：依赖图无环；plan 头部 `## Global Constraints` 一节齐全；各块的顺序成立；几份 plan 之间的合同图没有缺提供方或缺消费方，也没有归属冲突。
- **验证规划**：每条行为都有落点——端到端、合同或者单元；修 bug 的那一块带着挡同一个坑的回归测试。

测试本身怎么写在你已装的 `mmw-tdd/tests.md` 与 `mmw-tdd/mocking.md` 里，够不够格进仓库在 `mmw-tdd/quality-bar.md` 里。验证到那一步再读，不在这里重复。

## 每条 finding 标一类

一条 finding 归一类，写在它标题后面：plan 自身的问题、plan 跟 spec 对不上、spec 本身有缺、ticket 跟 plan 对不上、上下文含混、架构摩擦。

## 这几种一定要报

依赖关系错了；出现循环依赖；某一块内部自相矛盾；引用了不存在的路径；违反项目规则；允许弱类型的裸结构当跨边界合同；高风险改动缺迁移或回滚。
