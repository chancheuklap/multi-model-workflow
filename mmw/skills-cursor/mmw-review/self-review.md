## ③ 逐份验收：你自己做

一个 `worker` 交回它写的代码时，你当场亲手验证三关。**三关都过才允许合并回任务分支。**

1. **做漏没有** —— 派给它的那张 ticket（有 plan 那一层的话，还有那份 plan）每条验收标准真达成了吗。跑验收命令、读 diff，不认「我做完了」。
2. **测试有没有证明行为** —— 它自己说测试写好了不算。按 `/mmw-tdd` 检查公开行为、独立预期值和 mock 边界，再执行目标仓库 `TESTING.md` 的规则和命令。测试没有证明 ticket 要求的行为就打回重写。
3. **有没有偏离** —— 落地有没有跑偏 ticket 与 plan 写下的意图、合同、边界。

`worker` 交回的四档怎么读，在 `/mmw-verifying-agent-output`。它卡在 ticket 或 plan 与代码互相矛盾上，这件事交给用户。

### 三关不过时的返工升级策略

有一关不过就写修复指令打回，每一轮修复配一次重新验证——只验证这一轮改动碰到的地方，不重走全部三关。轮次按下表：

| 第几轮 | 派谁 |
| --- | --- |
| 一到三轮 | **恢复原 `worker` 续跑**。本轮修复指令就是这次的 task 正文，句柄用派发时记下的那个 |
| 四、五轮 | 改派全新 `worker-high-risk` |
| 第五轮还没过 | 停止返工，由你判定 |

一到三轮的恢复动作。③ 发生在集成之前，结果 worktree 与任务分支还是同步的，所以不用先把任务分支合进结果分支：
恢复：后台执行 `mmw-cursor-agent --resume <句柄原文>`。把修复 task 正文作为命令的标准输入。句柄是原派发输出里的会话 id。句柄取不到或命令失败时退回重派：按对应的启动动作重派新实例，task 正文带上原 task 全文、原报告全文和本轮修复指令。

句柄失效或恢复失败时，这一轮退回重派：task 正文带上原 task 全文、原报告全文和本轮修复指令。四、五轮是全新派发，上下文不继承，同样按这个形状写 task。

第五轮还没过时先判这一关挡不挡验收：测试写法差一点但行为是对的，不挡；行为不对或者合同破了，挡着。不挡：记入待办，开 issue 打 `needs-triage`。挡着：报是哪一关、五轮各自改了什么，交给用户。**不做第六轮。**

| 情况 | 处理 |
| --- | --- |
| ③ 三关都过 | 把这份代码合并回任务分支，回 `/mmw-implement` 第 5 步关闭这张 ticket，再取下一张 |
| ③ 三关有一关不过，返工还在前五轮内 | 按返工升级策略打回，这一轮不合并。前三轮恢复原 `worker` 续跑，四五轮改派 `worker-high-risk` |

## ④ 合同门：你自己做

每份 plan 对应的代码都合并回任务分支之后跑一次，**只验证一件事**：spec 的 `## Cross-Plan Contract Anchors` 一节里每条跨 plan 合同，在合并后的代码里真兑现了。

- 提供方声明的接口、类型、端点、数据结构真存在——grep 到定义，给出 `文件:行号`。
- 消费方真按那个接口对接，调用点的签名对得上。
- 合同版本号一致；新字段配套的迁移在位；新增的可被外部引用之物入了登记。

**grep 不到行号就不算兑现。** 这一道不做主观代码评审。

上面三样全是机械查找，**合同条数多的时候把取证派出去**：给它合同清单和目标仓库根的绝对路径，让它逐条 grep 定义、抄回 `文件:行号` 加原文，找不到的写「找不到」。派法在 `/mmw-verifying-agent-output` 的「取证可以派，判定不可以」一节。**判「兑现了没有」仍然是你的活**，尤其是「找不到」那几条——它可能只是没搜对名字，你要自己再搜一次才能判成落地漏了。

没有跨 plan 合同（只有一份 plan，或者 spec 的 `## Cross-Plan Contract Anchors` 写明「无跨 plan 共享合同」），把这件事连同你据以确认的位置一起记下来，不要跳过不写。

| 情况 | 处理 |
| --- | --- |
| 每条跨 plan 合同都 grep 到了行号 | 回 `/mmw-review`，从第 1 步起发起 ⑤ final 终审 |
| 有合同 grep 不到行号 | 按 `/mmw-implement` 第 6 步的路由——发回提供方 ticket 的原 `worker`（先做同步前置），恢复不了派修复 ticket；修复仍失败才停，报是哪条合同、提供方或消费方缺在哪 |
