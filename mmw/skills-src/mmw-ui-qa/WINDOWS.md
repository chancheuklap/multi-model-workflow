# Windows 侧

Electron 渲染进程本质是 Chromium，运行 HTML、CSS 与 DOM。因此**按 Web 处理**，不作为第三个平台从头设计。九种判拒在 Mac 和 Windows 上是同一套。

外壳差异不一样。**在 Mac 上检查不到这些行为**，报告必须明确列出，以免用户误以为已覆盖：

- Windows 原生菜单
- 托盘图标与通知
- DPI 缩放
- 系统中文字体回退导致的行高差异
- 安装包行为与文件关联
- 原生文件对话框

## 通道：用户手动启动，主 agent 连过去

**不能跨 SSH 启动 Windows GUI。SSH 前台拉起会静默失败**——不报错，就是不出现窗口。这是目标仓库工程规则里已经记载的铁律，不要试。

正确的顺序：

1. 用户在 Windows 的 PowerShell 里手动启动应用，启动时带远程调试端口。端口取自接线文件 `windows.debugPort`。
2. 主 agent 从 Mac 连接该端口，接管渲染进程。
3. 检查步骤全自动。

连不上时**停止 Windows 侧运行**，说明端口号，并提示应用必须在交互式用户会话中启动。不要尝试自己去启动它。

## 连接后必须先自检能力

通过调试端口接管已有实例，得到的能力低于自行启动的实例。**连接成功不等于四项能力都在。** 依次验证：

1. 取无障碍树快照
2. 批量提取计算样式
3. 局部截图
4. 注入可访问性规则引擎

任一项失败，本次结果按缺项处理：报告顶部声明哪几项能力不可用、因此哪几种判拒没有运行。**不把缺项结果当成完整 QA。**

## 修改前先报数，等用户点头

Windows 侧照常修改 A 类违规项，但**动手前先报数**。检查跑完后告诉用户：

- 这一轮有几处要改
- 改完需要重新构建并重启几次

用户说继续才动手。他可以答「这次先只报告」，那就全部转成 finding 带回，不修改，报告写明本次未修改及原因。

**为什么在 Windows 上改而不是带回 Mac 改。** Windows 那一趟的全部价值就是覆盖 Mac 上测不到的行为——DPI 缩放、系统中文字体回退导致的行高差异这些。把修复推回 Mac 等于查出来了但改不了也验不了，下次再来可能发现改错了，又推回去。这个来回比多按几次启动贵。

报数加点头这一步把代价变成用户可控的：只有一两处就顺手做了，有十几处他可以另约时间。

## 这一趟不是 AFK 的

明确告诉用户：**他至少要启动一次；选择让技能修改时，每一轮修复再各启动一次。** 报数时把预计次数一并说出来，不要含糊说成「一次」。

这不是自动化缺陷，是那条铁律带来的固有约束。
