**提示词第一行永远是 `任务：<任务名>`**，第二行起写这次的活。角色自己按任务名找方法，你不用交代怎么查、怎么审。任务名有哪些，读那个角色文件里的表。

| 角色 | 怎么起 |
| --- | --- |
| `scout`、`reviewer-claude` | Task 工具，`subagent_type` 填角色名 |
| `reviewer-gpt`、`plan-writer`、`executor` | `bash "${CLAUDE_PLUGIN_ROOT}/scripts/dispatch.sh" run --role <角色> --cwd <目录> --brief <文件>` |

无头那条**先把提示词写进一个文件再传路径**：一整段中文塞进命令行参数会被引号和换行咬坏。续接追问同一个角色，把 `run` 换成 `resume` 并加 `--session <会话号>`。

**要交代哪几样，读 `${CLAUDE_PLUGIN_ROOT}/roles/<角色>.md` 那行「开工要拿到」**，逐项填齐。

**派可写角色前先给它一棵工作树**：从任务分支分叉出 `.mmw/worktrees/<任务名>-<片名>`。验收过了 `git merge --no-ff` 合回任务分支，再清掉那棵树。只读角色不建树，在任务工作树里跑。

**一律起在后台。并行就是连着起几个。**

**几个一起起还是串着起，看活与活之间有没有依赖**：互不依赖就一起起；后一个要交代什么取决于前一个的结果，就等前一个回来再起。

## 线下 · 不是技能内容

**这份属于适配层，换一家宿主整份重写。**四家各一份，住 `adapters/<宿主>/`，安装脚本软链对应那一份。

**为什么走哪条路不在运行时判断**：哪个角色本宿主派得了、哪个要起无头，装机时读 `fields.json` 的模型表就定死了。运行时再判一次是把安装期的事拖到每次派活。

**为什么可写角色各一棵工作树**：派发脚本要求首派时工作树干净，几个可写角色挤同一棵会互相顶掉。

**为什么一律后台**：审一轮、落地一份计划都常超前台等待上限。

**为什么无头那侧要抄角色文件正文**：它看不见我们的角色文件。原生那侧靠宿主加载拿得到，无头那侧不抄就一个字都送不到。这件事由派发脚本做，你不用管。
