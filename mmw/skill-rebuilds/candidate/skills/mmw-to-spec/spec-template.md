# spec 模板

本模板记录已经形成的决定。标为条件式的 section 只在当前 spec 确实涉及对应内容时保留；当前 spec 不涉及时，删除整个 section。

节名使用英文原文，正文使用项目的 canonical 术语。

```markdown
# <这次交付什么> spec

> 写明这份 spec 来自哪次讨论、哪张 issue 或哪张 map。存在 prototype 或 research 输入时，写出这份 spec 实际使用的索引和精确文件。

## Problem Statement

从用户角度说明用户正面对的问题。

## Solution

从用户角度说明这个问题的解决方案。

## Current State

这是条件式 section。当前代码、数据、外部合同或既有流程影响本次决定时保留。

记录支撑本次决定的当前事实。为会随代码或外部系统变化的关键事实标注精确出处。

## User Stories

编写一份**很长的**编号 user story 清单。每条 user story 使用以下格式：

1. 作为 <角色>，我希望获得 <功能>，以便 <收益>

<user-story-example>
1. 作为一名手机银行客户，我希望看见自己各个账户的余额，以便对支出作出信息更充分的决定
</user-story-example>

这份 user story 清单必须极其详尽，并覆盖这项功能的所有方面。

## Implementation Decisions

列出已经形成的实施决定，可以包含：

- 将要建立或修改的 module
- 将要修改的 module interface
- 开发者作出的技术澄清
- 架构决定
- schema 变更
- API 合同
- 具体交互

**不要**写入具体文件路径或代码片段。这些内容可能很快过期。

例外：如果 prototype 产生的一段代码比文字更精确地编码了某项决定，例如状态机、reducer、schema 或类型形状，就把它内联到相关决定中，并简短注明它来自 prototype。只保留决定信息密集的部分；不要放入可运行 demo，只放重要片段。

## Failure Paths

这是条件式 section。当前方案存在已经谈定的失败、部分完成或恢复行为时保留。

| 失败情况 | 触发条件 | 负责处理的边界 | 用户观察到的结果 | 系统行为 |
| --- | --- | --- | --- | --- |

## Visual Contract

这是条件式 section。有用户界面时保留。

已有 prototype 时，使用用户选中的产物和对应走查结论。没有 prototype 时，使用已经确认的讨论结论和当前产品界面。

| 页面或组件 | 设计出处 | Viewport | 状态 | 视觉规格 | 交互行为 | 可验收结果 |
| --- | --- | --- | --- | --- | --- | --- |

## Testing Decisions

列出已经形成的测试决定，包含：

- 说明什么样的测试才是好测试，只测试外部行为，不测试实现细节
- 将测试哪些 module
- 测试先例，例如代码库中类似类型的测试

用户已经确认的 seam 用**清单表**列，下游按这张表取：

| Seam | 验证的外部行为 | 选择这一层的原因 |
| --- | --- | --- |

具体测试写法由 `/mmw-tdd` 和目标仓库的 `TESTING.md` 规定。

## Contract Boundaries

这是条件式 section。当前方案涉及 API、跨边界数据、数据库、定时任务载荷、计费或权限时保留。

记录已经谈定的归属方、提供方、消费方、合同形态、版本或迁移要求，以及从公开边界验证合同的方法。

## Release Risk

这是条件式 section。当前方案涉及数据迁移、计费、权限、部署顺序、回滚、功能开关，或者上线过程中需要人点头才能继续的环节时保留。

记录已经谈定的中间状态、部署顺序、回滚方式和不可逆操作。存在新的用户交付物时，说明用户怎样取得它。

## Out of Scope

说明哪些内容不在这份 spec 的范围内。

## Further Notes

记录关于这项功能的其他说明。
```
