# spec 模板

本模板记录已经形成的决定。每个 section 都要写完整；标为条件式的 section 只在当前 spec 确实涉及对应内容时保留。没有真实内容时删除整个条件式 section，不为填满模板编造内容。

节名使用英文原文，正文使用项目的 canonical 术语。

```markdown
# <这次交付什么> spec

> 写明这份 spec 来自哪次讨论、哪张 issue 或哪张 map。存在领域文档、prototype 或 research 输入时，在这个抬头集中写出当前 spec 实际使用的索引、选中产物、走查结论和 research 文件精确路径。

## Problem Statement

从用户角度说明用户正面对的问题。写清角色、触发场景、受阻的行为，以及为什么需要现在解决。

## Solution

从用户角度说明解决方案。写清完成后用户能够怎样做事，不在本节展开实现。

## Current State

这是条件式 section。当前代码、数据、外部合同或既有流程影响本次决定时保留。

逐项记录支撑本次决定的当前事实，并为会随代码或外部系统变化的事实标注精确出处。说明现有能力、已知限制，以及决定复用或替换现有实现的依据。

## User Stories

编写一份**很长的**编号 user story 清单。每条 user story 使用以下格式：

1. 作为 <角色>，我希望获得 <功能>，以便 <收益>

<user-story-example>
1. 作为一名手机银行客户，我希望看见自己各个账户的余额，以便对支出作出信息更充分的决定
</user-story-example>

这份清单必须极其详尽，并覆盖这项功能真实存在的所有方面。写入本次范围内真实存在的成功、失败、空状态、权限和交互边界。不要为了增加长度而编造没有讨论过的场景。

## Implementation Decisions

列出已经形成的实施决定，可以包含：

- 将要建立或修改的 module
- 将要修改的 module interface
- 开发者作出的技术澄清
- 架构决定
- schema 变更
- API 合同
- 具体交互

每项写清决定内容，以及已经形成的相关取舍。**不要**写入具体文件路径或代码片段。这些内容可能很快过期。

例外：如果 prototype 产生的一段代码比文字更精确地编码了某项决定，例如状态机、reducer、schema 或类型形状，就把它内联到相关决定中，并简短注明它来自 prototype。只保留决定信息密集的部分；不要放入可运行 demo，只放重要片段。精确资产路径集中写在 spec 抬头，不写入本节。

prototype 形成决定时，记录用户确认的决定和取舍。落选变体只提供用户已经确认的否定约束，不作为当前设计依据。

prototype 已经记录 UI 与后端的对应关系时，把每项页面功能或按钮对应的后端脚本、接口合同或可复用 `module` 写入相关决定。精确路径继续由 spec 抬头指向的 prototype 资产索引承载。

## Failure Paths

这是条件式 section。当前方案存在需要明确处理的失败、部分完成或恢复行为时保留。

| 失败情况 | 触发条件 | 负责处理的边界 | 用户观察到的结果 | 系统行为 |
| --- | --- | --- | --- | --- |

只记录本次真实存在的失败路径。不要加入包罗万象的兜底处理，也不要把失败静默转换成成功。

## Visual Contract

这是条件式 section。有用户界面时保留。

已有 prototype 时，只使用用户选中的产物和对应走查结论。没有 prototype 时，使用已经确认的讨论结论和当前产品界面作为设计依据。不能只写“参见某个目录”；逐项写出用户可以观察和验收的结果。

| 页面或组件 | 设计出处 | Viewport | 状态 | 视觉规格 | 交互行为 | 可验收结果 |
| --- | --- | --- | --- | --- | --- | --- |

逐项记录每个功能的交互状态：

| 功能 | 状态 | 触发方式 | 用户观察到的结果 | 设计出处 | 可验收结果 |
| --- | --- | --- | --- | --- | --- |

## Testing Decisions

好测试只通过公开 interface 验证外部行为，不验证实现细节。实现可以替换，测试仍应保持有效。具体测试写法由 `/mmw-tdd` 和目标仓库的 `TESTING.md` 规定。

列出将测试哪些 module，以及代码库中可以复用的测试先例。

记录用户已经确认的 seam：

| Seam | 验证的外部行为 | 选择这一层的原因 |
| --- | --- | --- |

已有 seam 优先于新 seam。确实需要新 seam 时，说明现有 seam 为什么无法覆盖目标行为。

## Contract Boundaries

这是条件式 section。当前方案涉及 API、跨边界数据、数据库、定时任务载荷、计费或权限时保留。

逐项写清归属方、提供方、消费方、合同形态、版本或迁移要求，以及从公开边界验证合同的方法。

## Release Risk

这是条件式 section。当前方案涉及数据迁移、计费、权限、部署顺序、回滚、功能开关或人工审批关卡时保留。

写清中间状态、部署顺序、回滚方式和不可逆操作。存在新的用户交付物时，说明用户怎样取得它。

## Out of Scope

说明哪些内容明确不在这份 spec 的范围内。每项记录排除理由，以及已经谈定的后续去向。

## Further Notes

这是条件式 section。记录无法归入以上 section、但已经讨论并需要随 spec 保留的其他说明。没有其他说明时删除本节。
```
