# Prototype

prototype 是在真实代码落地前回答问题的可运行资产。初版可以粗糙；后续轮次继续修改同一份 prototype，直到它接近可以真实落地的状态。最终的前端和后端 prototype 可以共同形成产品雏形，供后续工作直接参考或复用。

## 一轮回答一个问题

开始一轮前，写下这一轮要回答的问题。问题来自已经进行的讨论、现有 prototype 或周围代码。用户走查后必须能够说明哪里正确、哪里需要修改，或者哪个方向成立。

同一份 prototype 可以连续回答多个问题。每一轮只收窄当前问题，不为新问题新建一套 prototype。只有走查事实证明整个方向不成立时，才停止这个方向。

## 选择当前形态

| 当前问题 | 使用形态 |
| --- | --- |
| 一份数据长什么样、接口应该接收和返回什么、转换输出是否正确，而且查看输出就能判断 | 最小可运行后端脚本、合同样例或测试夹具 |
| 业务逻辑、状态转移或数据形状必须由用户手动推动才能判断，而且没有合适的产品界面 | Logic HTML |
| 页面、操作流程或 UI/UX 应该是什么样子 | [UI/UX Prototype](#uiux-prototype) |

这些形态是同一份 prototype 的不同工作面，不是互斥的生命周期。复杂产品逻辑通常先用 UI/UX HTML 理顺页面、状态和操作路径，再为每个功能或按钮补上后端脚本或接口合同。纯后端逻辑简单时，可以直接从澄清后的问题开始编写后端脚本。

问题在两种形态之间含混时，询问用户。用户无法立即回答时，根据当前验证问题和周围代码选择最小形态，并在 prototype 记录中写明假设。

## 后端 prototype

查看一次输出就能判断的问题，不需要额外搭建交互界面。提供最小可运行脚本、合同样例或测试夹具，并把输入和输出一起交给用户。

最小后端 prototype 仍需覆盖与当前问题直接相关的失败、空值和边界输入。不要只展示顺利路径。

复杂逻辑在 UI/UX 流程确定后继续补齐。每个页面功能和按钮必须对应一个可运行后端脚本、接口合同或可复用 `module`。尚未接入真实后端时，可以先使用桩，但必须明确记录它正在替代什么。

## Logic HTML

Logic HTML 是独立、自包含的 HTML 文件。它让非开发者通过 `free-play` 和 `guided walkthrough` 手动驱动状态模型。它适合没有合适产品界面的纯状态模型，也适合需要把状态机单独交给非开发者走查的情况。

prototype 不重复定义 Logic HTML 的制作方法。请求 Logic HTML 时，提供当前验证问题、现有状态模型或后端脚本路径、真实场景和边界，以及 Logic HTML 输出路径。Logic HTML 是当前 prototype 的一项资产，后续轮次继续修改同一文件。

## 共同规则

1. **运行方式清楚。** 使用项目已有的任务入口；自包含 HTML 应能直接打开。把精确运行方式写进 prototype 记录。
2. **默认把状态保存在内存。** 当前问题涉及持久化时，才接临时数据库或明确标记的本地文件。
3. **早期保持轻量。** 初轮只完成回答当前问题所需的代码、错误处理和界面质量。
4. **按复用目标提高质量。** 经过多轮验证、准备交给下游直接复用的纯逻辑、后端脚本、接口合同或组件，需要补齐项目要求的测试、错误处理和必要的本地持久化。
5. **呈现完整相关状态。** 每次逻辑动作、界面状态变化或变体切换后，都显示用户判断当前问题所需的完整状态。
6. **原地迭代。** 后续轮次修改同一份 prototype，保留已经确认的状态、交互和文案。
7. **保存问题和答案。** 每轮记录验证问题、用户原话、修改内容、验证结果，以及下一轮问题或选中的资产。

## 用户走查

把当前可运行产物和运行结果交给用户。用户自己操作并给出意见；agent 不能代替用户选择或接受。

用户要求修改时，继续迭代同一份 prototype，并记录下一轮问题。用户选定结果时，记录选中产物的精确路径。走查事实证明整个方向不成立时，记录击穿方向的事实，并把它交回调用方。

记录用户实际说了什么，以及这句话对下一步产生什么影响。

## 保存与复用

把完整 prototype 保存到仓库，作为 spec、ticket、plan、审查和实现的一手来源。保存可运行资产、完整界面变体、逐轮走查结论和选中产物。过程材料不进入持久 prototype。

正式实现只吸收已经验证的决定和达到项目质量要求的可移植内容。调试外壳、切换器和落选变体继续保留为 prototype 资产，不进入生产路由。经过验证并符合项目技术与质量要求的组件、纯逻辑、接口合同和后端脚本可以直接复用。

## `UI.md`

# UI/UX Prototype

UI/UX prototype 用可运行页面理顺页面、状态和操作路径。用户在浏览器中走查，选择一个方向，或者指出需要组合和修改的部分。

## 适合这种形态的情形

- 页面应该是什么样子。
- 操作流程应该如何组织。
- 复杂产品逻辑需要先通过界面理顺。
- 前端和后端的可行性需要在同一份 prototype 中验证。

## 选择承载形态

| 项目情况 | 承载形态 |
| --- | --- |
| 已有成熟应用，而且 prototype 天然属于某个页面或流程 | 挂入已有页面。保留真实页头、侧边栏、数据密度、取数、参数和鉴权，只替换正在验证的界面部分 |
| 全新产品、纯后端仓库，或者需要跨前端和后端验证可行性 | 使用独立 HTML。它是正常形态，不是最后手段 |
| 已有应用，但没有任何现有页面能够承载一个新的顶层界面 | 按项目现有路由约定建立明确标记的 prototype 路由 |

## 判断是否需要多个变体

只有 UI 结构方向尚未确定时，才生成多个变体。变体必须在布局、信息层级或 `primary affordance` 上存在真实差异。数量由仍待比较的结构方向决定，不使用固定的默认数量。

用户已经选择方向后，继续迭代选中的版本。不要在每一轮重新生成整组变体。

多个变体可以并行生成，也可以由同一 agent 完成。根据复杂度、文件所有权和并行收益决定，不为每个变体强制建立 subagent 或 worktree。

## 生成结构不同的变体

每个变体都遵守页面用途、真实数据和项目现有组件库或样式系统。每个变体使用清楚的名称。变体之间可以共享页头等稳定组件，但不能共享正在比较的整体布局。

多个变体需要切换时，使用 URL 查询参数和浮动切换器，使链接可以分享并在刷新后保持稳定。只有一个已选方向时，不保留无用切换器。

## 连接后端行为

初轮可以使用桩来验证 UI/UX 流程。流程确定后，为每个功能和按钮补上后端脚本、接口合同或可复用 `module`，并记录精确对应关系。

写操作尚未接入真实后端时，必须清楚显示桩行为。需要验证真实写操作时，先完成对应后端 prototype，再让页面调用它。

每个实际存在的页面状态都应能呈现，包括与当前问题相关的加载、空、错误、成功和部分完成状态。页面变化后显示用户判断当前问题所需的完整相关状态。

## 交给用户

把页面地址和变体切换方式交给用户。用户选择一个方向、组合不同方向，或者要求修改时，继续迭代同一份 UI/UX prototype。

## 保存结果

保存选中产物、落选变体和用户给出的理由。落选变体只提供被否定的约束，不进入下游当前方案。调试路由和切换器继续作为 prototype 资产保存，不进入生产路由。

达到项目技术与质量要求的选中组件可以复用。仍使用桩、缺少测试或只为走查编写的界面外壳，不能直接进入生产路由。

## 反模式

- 变体只在颜色或文案上不同。
- 用户已经选定方向后，每轮重新生成整组变体。
- 初轮的桩没有在记录中说明替代对象。
- 页面功能或按钮没有对应后端脚本、接口合同或可复用 `module`。
- 把调试路由、切换器或落选变体接入生产路由。
