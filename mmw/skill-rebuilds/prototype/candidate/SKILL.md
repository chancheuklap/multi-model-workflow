开始前，遵守目标仓库 `AGENTS.md` 的领域上下文规则。

prototype 是在真实代码落地前回答问题的可运行资产。初版可以粗糙；后续轮次继续修改同一份 prototype，直到它接近可以真实落地的状态。最终的前端和后端 prototype 可以共同形成产品雏形，供后续工作直接参考或复用。

## 1. 一轮回答一个问题

开始一轮前，写下这一轮要回答的问题。问题来自已经进行的讨论、现有 prototype 或周围代码。用户走查后必须能够说明哪里正确、哪里需要修改，或者哪个方向成立。

同一份 prototype 可以连续回答多个问题。每一轮只收窄当前问题，不为新问题新建一套 prototype。只有走查事实证明整个方向不成立时，才停止这个方向。

按下表完成适用性判断：

| 当前情况 | 处理 |
| --- | --- |
| 读取文档或源码即可回答 | 主 agent 直接取得事实并结束，不准备 prototype 资产或 worktree |
| 问题无法收敛成可走查的具体问题 | 移交 `/mmw-grilling`，谈清问题后再返回 |
| 问题能够通过走查得到明确答案，而且必须运行产物才能回答 | 继续第 2 节 |

## 2. 确定资产位置

开始本技能时必须已经确定 `产物目录`。来自 `/mmw-wayfinder` 的任务还必须给出当前 decision ticket 的 `issue-<编号>` 子目录。普通任务使用任务 slug 作为 `产物目录`，不加 issue 子目录。

用户直接调用本技能但当前任务还没有 `产物目录` 时，移交 `/mmw-start` 建立任务，并停止本步骤。取得确定的 `产物目录` 后，从本节继续。

运行以下命令，记录 prototype 产物路径和 scratch 路径：

```bash
mmw path prototype <产物目录> [issue-<编号>]
mmw path scratch <产物目录> [issue-<编号>]
```

开始写入前，确认当前任务已有正确的任务 worktree。没有时执行宿主动作：

[[mmw-host-action:prepare-task-worktree]]

使用以下持久目录：

```text
<prototype 产物路径>/
├── README.md              运行方式、逐轮问题、用户结论、选中产物和精确对应关系
├── logic/                 后端脚本、接口合同、可移植逻辑和 Logic HTML
└── mockup/                UI/UX prototype 和完整界面变体
```

过程截图、DOM、console、录屏、临时探测输出和生成中间物写入 scratch 路径，不进入 Git。只有下游长期判断确实需要，而且不能从可运行 prototype 低成本重建的最小证据，才提升为长期证据，并在 `README.md` 中写出精确路径。

已有 `README.md` 时先读取它，再只读取当前问题需要的 prototype 资产。后续轮次继续修改同一份 prototype，不建立版本目录。

## 3. 选择并组合工作面

后端脚本、Logic HTML 和 UI/UX prototype 是同一份 prototype 的不同工作面。复杂产品逻辑通常先用 UI/UX HTML 理顺页面、状态和操作路径，再为每个功能或按钮补上后端脚本或接口合同。纯后端逻辑简单时，可以直接从澄清后的问题开始编写后端脚本。

每轮只选择当前问题需要的工作面：

| 当前问题 | 处理 |
| --- | --- |
| 查看一次数据、接口或转换输出就能判断 | 继续第 4 节，在 `logic/` 中编写最小可运行后端脚本、合同样例或测试夹具 |
| 必须由用户用按钮驱动状态模型，而且没有合适产品界面 | 继续第 5 节，询问用户是否使用 Logic HTML |
| 涉及页面、操作流程或 UI/UX | 完整读取 [UI.md](UI.md) |
| 同时符合两个工作面，而且用户可以回答 | 停止并请用户确认这一轮先回答哪个问题 |
| 同时符合两个工作面，而且用户暂时无法回答 | 根据当前验证问题和周围代码选择最小工作面，并在 `README.md` 中写明假设 |

问题涉及两个工作面时，先完成能够回答当前问题的一个；用户走查后再登记下一轮问题，并继续补齐另一个工作面。

## 4. 后端 prototype

查看一次输出就能判断的问题，不需要额外搭建交互界面。提供最小可运行脚本、合同样例或测试夹具，并把输入和输出一起交给用户。

最小后端 prototype 覆盖与当前问题直接相关的失败、空值和边界输入。不要只展示顺利路径。

复杂逻辑在 UI/UX 流程确定后继续补齐。每个页面功能和按钮必须对应一个可运行后端脚本、接口合同或可复用 `module`。尚未接入真实后端时，可以先使用桩，但必须在 `README.md` 中记录它正在替代什么。

## 5. Logic HTML

Logic HTML 适合没有合适产品界面的纯状态模型，也适合需要把状态机单独交给非开发者走查的情况。

按以下顺序处理：

1. 询问用户是否手动调用 `/wait-what` 生成或更新 Logic HTML。
2. 用户不同意时停止本轮，并报告当前问题缺少可走查形态。
3. 用户同意时，请用户手动调用 `/wait-what`，并提供以下四项输入：

   - 当前验证问题。
   - 现有状态模型或后端脚本的精确路径。
   - 真实场景和边界。
   - `<prototype 产物路径>/logic/` 中的精确输出路径。

4. 停止本步骤，等待用户完成 `/wait-what`。
5. `/wait-what` 交回用户原话、Logic HTML 路径和验证结果后，读取 [capture.md](capture.md) 记录本轮结论。

Logic HTML 的制作方法只由 `/wait-what` 的 Logic HTML 分支定义。Logic HTML 是当前 prototype 的一项资产。后续轮次继续修改同一文件。不要用静态说明冒充运行结果。

## 6. 共同规则

1. **运行方式清楚。** 使用项目已有的任务入口；自包含 HTML 应能直接打开。把精确运行方式写进 `README.md`。
2. **默认把状态保存在内存。** 当前问题涉及持久化时，才接临时数据库或明确标记的本地文件。
3. **早期保持轻量。** 初轮只完成回答当前问题所需的代码、错误处理和界面质量。
4. **按复用目标提高质量。** 经过多轮验证、准备交给下游直接复用的纯逻辑、后端脚本、接口合同或组件，需要补齐项目要求的测试、错误处理和必要的本地持久化。
5. **呈现完整相关状态。** 每次逻辑动作、界面状态变化或变体切换后，都显示用户判断当前问题所需的完整状态。
6. **原地迭代。** 后续轮次修改同一份 prototype，保留已经确认的状态、交互和文案。
7. **保存问题和答案。** 用户给出走查意见后，按 [capture.md](capture.md) 保存本轮记录和下游输入。

## 7. 用户走查

把当前可运行产物和运行结果交给用户。用户自己操作并给出意见；agent 不能代替用户选择或接受。

需要展示界面时执行宿主动作：

[[mmw-host-action:present-ui-review]]

用户走查按 `HITL` 交互处理；调用方继续负责自己的人工审批关卡。
