并行做的几条分支，最后要变成本轮目标分支上的一个状态。这件事有它自己的决定要做：先进哪一条、还没完成的怎么跟上、每一次推进遇到冲突怎么解。

**集成在本轮指定的目标分支上做。** 合入后台任务结果时，目标分支就是当前 Codex App 任务分支。各结果任务的 worktree 留到分支与提交验证完成；当前分支不是本轮目标分支时停下。

`git status` 已经显示有一个进行中的 merge 或 rebase 的，第 1、2 步跳过，直接按第 3 步：merge 走 [merging.md](merging.md)，rebase 走 [rebasing.md](rebasing.md)。

## 1. 认现状

要集成的每条分支，记下四样：分支名、它相对本轮目标分支的分叉点（`git merge-base <分支> <本轮目标分支>`）、终审过没过（`.reviews/` 里有没有它的终审报告）、它跟别的分支有没有合同关系（一条提供数据模型、接口、数据库结构或序列化格式，另一条消费它）。

本轮目标分支的当前 `HEAD` 也记下——第 4 步发起审查要用它当固定点。

**完成判据**：这一轮要处理的每条分支都有这四样，没有一条是「大概还行」。合同关系拿不准的按 `$mmw:mmw-research` 的内部方向派出去查，收回来按 `$mmw:mmw-verifying-agent-output` 验证。

## 2. 定顺序与路线

每条分支归进两类之一，不留悬着的：

| 这条分支的状态 | 这一轮怎么处理 |
| --- | --- |
| 已经完成，终审过了 | 进本轮目标分支，走 [merging.md](merging.md) |
| 还没完成，而本轮目标分支已经被别的分支推进了 | rebase 到最新本轮目标分支跟上，接着在它自己的 worktree 里做，走 [rebasing.md](rebasing.md) |

**终审没过的不进本轮目标分支。** 它属于第二类——先 rebase 跟上，做完终审再等下一轮。

进本轮目标分支的那几条按这个顺序：提供合同的先进，消费它的后进；没有合同关系的按终审通过的先后。**先进的那条会推进本轮目标分支，后面每一条的分叉点都跟着变**，所以顺序定完就不再回头改，要改就整轮重来。

**完成判据**：每条分支都落进上面两类中的一类，且进本轮目标分支的那几条有一个确定的先后。

## 3. 逐条推进

后台 Worktree 任务交回后，先运行与本 `SKILL.md` 同目录的 `scripts/verify-worker-result.sh <结果分支> <报告的 HEAD SHA> <派发前基点 SHA>`；验证通过后再按第 2 步定的顺序，一条一条来。走 merge 还是 rebase 看它归的类，机械差异各在自己那份文件里——`ours` 和 `theirs` 指哪一边、怎么完成、放弃的代价，两者不一样，凭 merge 的直觉做 rebase 会保错边且不报错。

冲突怎么解，两条路共用下面三条：

1. **查清两边各自要做什么**，再动手。读提交信息、PR、原始 issue。按 `$mmw:mmw-research` 的内部方向派出去，一个来源一个 subagent，题目是「这一侧在这几个冲突文件里想做成什么」；收回来按 `$mmw:mmw-verifying-agent-output` 验证。
2. **逐块解，双方的意图都保住。** 确实不兼容的，选符合这一轮集成目标的那一个，**把这个取舍记下来**——第 4 步要连同各分支的 spec 一起交给审查者。不发明新行为。
3. **跑这个项目自己的检查**：类型检查、测试、格式化。这次推进弄坏的当场修。

取舍记录落 `.reviews/integration-<YYYY-MM-DD>.md`，同一天第二轮在日期后加序号。一条记三样：哪个文件的哪一块、两边各自要做什么、保了哪一边加理由。

**完成判据**：`git status` 没有进行中的操作，工作区干净，第 2 步归为「进本轮目标分支」的每一条都在本轮目标分支历史里（`git branch --merged` 查得到）。

## 4. 判要不要发起集成审

| 这一轮做了什么 | 要不要审 |
| --- | --- |
| 几条并行分支合到了一起 | **要**。各自对不等于组合对，交互、顺序、依赖只有合到一起才看得出 |
| 只有一条分支 rebase 跟上本轮目标分支，且冲突全是机械的 | **不要**。它还没完成，终审时自然会审到 |
| 只有一条分支 rebase 跟上本轮目标分支，但解冲突时做过实质取舍 | **要** |

机械冲突和实质取舍这样分：

- 两边改的是**同一个行为**，而你保了一边、舍了另一边——实质取舍。
- 两边改的是**不同行为**，只是落在相邻位置（同一个 import 块、同一个列表各加一项、相邻行）——机械。
- 任何一边碰的是**合同**（数据模型、接口、数据库结构、序列化格式、迁移）——一律算实质，不看位置。

要审的，固定点是集成后的本轮目标分支 `HEAD` 加第 1 步记下的各分支分叉点。

## 下一步

| 情况 | 下一步 |
| --- | --- |
| 第 3 步全部推进完，第 4 步判定要审 | **移交**：`$mmw:mmw-review` 第 1 步，那一道是 ⑥ 合并集成审。把第 3 步的取舍记录和各分支的 spec 一起备进材料 |
| 第 3 步全部推进完，第 4 步判定不用审 | **停**：报这一轮哪几条进了本轮目标分支、哪几条 rebase 跟上了还在做、各自现在在哪。结果提交已绑定分支后，用户可以归档对应 Codex App 任务，由 App 管理 worktree 清理 |
| 当前不在本轮目标分支 | **停**：报当前在哪个分支。切分支归用户 |
| 解冲突时两边意图确实不兼容，而这一轮的集成目标不足以判 | **停**：报是哪个文件的哪一块、两边各自要做什么，让用户定保哪一边。这时候 merge 或 rebase 停在中途，一并告诉他 |
| 项目自己的检查因为这次推进坏了，当场修不好 | **停**：报是哪个检查、哪一处冲突解出来之后开始坏的 |
| 第 1 步发现某条分支终审还没过，而用户要它这一轮进本轮目标分支 | **停**：报它缺终审。要么这一轮先 rebase 跟上，要么先去 `$mmw:mmw-review` 第 1 步跑 ⑤ final 终审 |
