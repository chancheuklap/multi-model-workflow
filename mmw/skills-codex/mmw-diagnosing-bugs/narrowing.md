# Phase 2 到 4 —— 把范围收窄

手上已经有一个 tight 且 red-capable 的 loop。这三个 Phase 全部由主 agent 自己做，不派 `worker`。

## Phase 2 —— 复现 + 最小化

跑那个 loop。看着它变 red，bug 出现了。

确认：

- [ ] 这个 loop 产出的是**用户**描述的那个失败形态，不是旁边碰巧出现的另一个失败。
- [ ] 这个失败多跑几次都能复现（非确定性的 bug：复现率高到足以对着它调）。
- [ ] 你已经把那个确切症状记下来：报错信息、错误输出、慢了多少。

需要落盘的错误输出、最小化输入和测量结果继续写入 Phase 1 取得的任务 scratch。

### 最小化

变 red 之后，把 repro 缩到**还能变 red 的最小情形**。输入、调用方、配置、数据、步骤，**一次去掉一样**，每去掉一次重跑一遍 loop——只留对这个失败关键的部分。

为什么要缩：最小 repro 会把 Phase 3 的假设空间压小，也会在 Phase 5 变成一条干净的回归测试。

**剩下的每一样都是关键的**——去掉任何一样 loop 就变绿——这时候算完成。复现**和**最小化都完成之前不要往下走。

## Phase 3 —— 提假设

在验证任何一条之前，先生成 **3 到 5 条排好序的假设**。

只提一条假设会把后面的验证锚在第一个听起来合理的解释上。先列出几个互相竞争的解释，再按证据排序。

每条假设都必须**可证伪**：把它做出的预测写出来。

> 格式：「如果 <X> 是原因，那么 <改动 Y> 会让 bug 消失／<改动 Z> 会让它更严重。」

预测写不出来，这条假设就只是直觉——丢掉，或者把它写得更精确。

**验证之前把排好序的清单给用户看。** 他可能当场重排，或者知道哪几条他已经排除过。不要停在这里等——用户不在场就照你的排序往下走。

## Phase 4 —— 埋点

每一个探针都要对应 Phase 3 里的某一条具体预测。**一次只改一个变量。**

工具优先级：

1. **调试器／REPL 检查**，只要环境支持。一个断点胜过十条日志。
2. **有针对性地打日志**，放在能区分开各条假设的边界上。
3. 不要「全都打日志然后 grep」。

**每条调试日志都打标记**，用一个唯一前缀，例如 `[DEBUG-a4f2]`，最后清理就是一次 grep。临时埋点产生的输出写入任务 scratch。

埋点由你自己动手，不派 `worker`。这些日志在 Phase 5 开始前全部删掉，一行都不进最终 diff。

**性能分支。** 性能回退的问题，日志通常是错的工具。改成：先建立一条基线测量（计时 harness、`performance.now()`、profiler、查询计划），然后二分。先测量，后修复。

## 下一步

| 情况 | 下一步 |
| --- | --- |
| 某条假设被埋点证实，根因清楚了 | **自己继续**：读 [fixing.md](fixing.md)，把修复派给 `worker` |
| 3 到 5 条假设全部被证伪 | **自己继续**：回 Phase 3 重提一批 |
| 最小化之后 loop 不再变 red | **自己继续**：回 Phase 2，说明你去掉的哪一样其实是关键的，把它加回来 |
| 反复几轮仍然定不到根因 | **停**：报你验证过哪些假设、各自被什么观测否掉，让用户判断是继续挖还是换方向 |
