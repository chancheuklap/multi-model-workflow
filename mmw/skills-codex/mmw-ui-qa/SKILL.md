界面 QA 检查界面本身。它**不是六道审的任何一道**，在不走审查流程的 prototype 阶段也能用。

它是交互式技能，在正常流程里有停下来问用户的点。用户在开发迭代过程中随时喊起来，日常发起一个字都不用多说。

它承担三件事：

1. **建立这个产品的判据** — 第一次运行时用 intake 问卷把判据和接线建起来，然后接着往下跑。
2. **对刚刚完成的那一块做检查** — 默认范围就是最近一个提交。**这是主场景。**
3. **对完整应用做全流程检查** — 挂 `全量` 标签，用在初版落地和去 Windows 那一次。

**入口的两个标签。** 开头挂可选标签 `本任务` 或 `全量`，后面跟产品名，两个都可以留空。**用户挂了标签就直接用，不再推断。**

## 1. 检查工作区干净

运行 `git status --porcelain`。**有输出就停下来**，列出未提交的文件，让用户先提交，然后重新发起。

不要替用户提交，也不要拍快照绕过去。

这一条是整个技能的地基，它换来四件事：

| 换来什么 | 怎么换来的 |
| --- | --- |
| 范围定义得出来 | 「刚改完的那一块」就是最近一个提交。工作区脏时这个概念不存在——改了三轮没提交，每次算出来的都是同一堆文件 |
| 回退不用自己造机制 | 改坏了就 `git checkout` 那个文件，或整轮 `git revert`。提交本来就是可回退的 |
| A 类修改可以正常提交 | 工作区本来是干净的，技能改的就是技能改的，不会把用户没写完的代码一起提交进去 |
| 不需要任务绑定 | 见下 |

**不需要任务绑定，也不建 worktree。** 界面 QA 唯一的长期产物是判据与接线，它们不带工作名。界面全图在进程内构建、用完即弃；报告直接交给用户，不写进仓库。因此整条工作名链路都用不上。用户在主检出还是在任务 worktree 里发起，行为一致。

## 2. 检查依赖

运行 `mmw-ui-qa check`。三个运行时依赖由 MMW 的安装入口提供并固定版本，不要用别的方式临时取。

| 缺哪个 | 怎么办 |
| --- | --- |
| 浏览器自动化框架 | **停止**。它驱动全部检查 |
| 可访问性规则引擎 | 降级，跳过 A2，其余照常 |
| 设计系统格式校验器 | 降级，报告顶部标明判据这一轮没有被校验过，其余照常 |

## 3. 判定产品

判据与接线都是按产品的，所以产品必须先定下来。**四级，第一级命中就不往下走：**

1. argument hint 的自由内容里给了产品名 → 直接用，不问。
2. 没给，但接线文件只有一份 → 用那一份，不问。只做一个应用的仓库永远不会被问到。
3. 没给，接线文件有多份 → 列出来让用户选一次。**列的是接线文件里 `product` 字段的值，不是文件名**，用户看到的是产品的名字。
4. **一份接线文件都没有**（全新仓库首次运行）→ 直接问用户这次要检查哪个产品。产品标识用小写字母、数字与连字符。

第 4 级问出来的产品名，就是下一步建立各文件时用的标识，问卷里不再重复问一遍。

接线文件的落点用 `mmw artifact path ui-qa-wiring --sub <产品标识>.json` 解析，判据用 `mmw artifact path ui-criteria --sub thresholds.json` 和 `mmw artifact path ui-criteria --sub products/<产品标识>.md`。列举现有产品时列出接线类别根这一层的目录内容。

**一次运行只检查一个产品。** 要检查第二个就再发起一次。混进一份报告，用户裁决时会分不清在答哪个应用的事。

## 4. 检查判据与接线，缺了就建

阈值表、该产品的可用性判据、该产品的接线文件、设计系统文件，缺任何一份就进**建立模式**：跑 intake 问卷，把缺的那几份建起来，然后自动转入**运行模式**继续本次检查。缺一份和缺四份走同一条路径，只是问卷问的内容不同。

**问卷、四份文件各自的性质，以及拒绝建立时的后果，完整读 [CRITERIA.md](CRITERIA.md)。**

## 5. 判据自己要先被检查

判据齐了之后，对设计系统文件跑一次格式校验：

```bash
mmw-ui-qa design-lint <接线文件 designSystem 字段指向的路径>
```

文件参数不能省。校验器不只查格式，还做跨 token 的 WCAG 对比度计算和引用完整性检查，不需要启动应用。

这一步不可省略，因为 A3 与 B1 拿设计系统当判据，**判据自己违规时，判得越准越糟**——一份声明了「白字配琥珀色」的规范，会让 A3 把读不清的按钮判成合规。

| 校验结果 | 怎么办 |
| --- | --- |
| 有 `error` 级 finding | **停止**。文件解析不了，A3 与 B1 无从判起 |
| 只有 `warning` | 继续，报告里列出，**标明这是判据的问题不是界面的问题** |
| 命令跑不起来 | 继续，报告顶部标明判据这一轮没有被校验过 |

校验结果进报告，**不进九种判拒**。判据的 finding 没有界面上的修复目标，也不进用户裁决。

## 6. 确定范围

**三档，与任务模型对齐**，不按「查几个界面」分档：

| 档 | 范围怎么算 | 什么时候用 |
| --- | --- | --- |
| **本次改动**（默认） | `git diff HEAD~1...HEAD --name-only` | 刚提交完一次改动，随手检查 |
| **本任务** | `git diff $(git merge-base HEAD <父分支>)...HEAD --name-only`，父分支默认 `main` | 一个任务完整落地，交出去之前 |
| **全量** | 界面全图里的全部界面与状态，不看 git | 应用初版落地，或去 Windows 那一次 |

固定点的取法与 `$mmw:mmw-review` 第 1 步一致，不新造。

**三档都是无状态的，不记「上次跑到哪」。** 第 1 步已经保证工作区干净，所以「刚改完的那一块」就是最近一个提交。反过来的做法走不通：允许工作区脏、靠记住上次运行的 HEAD 来划范围时，用户连改几轮不提交则 HEAD 始终不变，每次算出来的都是同一堆未提交文件。

**改动的文件怎么变成要查的界面。** 界面全图的每个界面节点记着 `来源文件`。改动了文件 F，就取所有 `来源文件` 包含 F 的界面节点。这是查表，不是再扫一遍代码——建全图时本来就知道自己在读哪个文件。

**降级链。降级只改范围，不减判拒。**

| 情况 | 降到哪 | 报告里写什么 |
| --- | --- | --- |
| 映射出至少一个界面 | 不降 | 正常 |
| 映射出零个界面（改的是后端、配置或文档） | 本任务 | 本次改动未涉及界面文件，范围扩大到本任务 |
| 本任务也映射出零个界面 | 最小子集：接线文件 `mainWindow` 指向的界面，加它在全图里的直接下一级 | 本任务未涉及界面文件，改为检查主窗口及其下一级 |
| `HEAD~1` 不存在（任务分支的第一个提交） | 本任务 | 无需说明 |

**九种判拒在任何一档上都全部运行**，档位只决定它们作用在哪些界面上。

## 7. 建界面全图

全图记录界面、每个界面的状态与界面之间的跳转。它是认知走查的前提——没有它，走查只能看到当前这一屏。

**在进程内构建，不落文件，用完即弃。** 三个来源按顺序合并，它们是并集不是互斥选择：

1. **代码抽取打底** — 读路由表、状态机、条件渲染分支。读到哪个文件，就把文件名记进那个界面节点的 `来源文件`。
2. **运行时探测补充** — 启动应用后遍历可达路径。
3. **可用性判据补足** — 记录探测不到、需要特定条件才出现的状态。

同一个状态被多个来源命中时合并成一条，并记录被哪几个来源命中。**到达性由运行时探测单独决定**：探测到过的标为已到达，只出现在另外两个来源里的标为未到达。未到达的状态保留在全图里，不删除。

**能到达什么，取决于接线文件。** 空状态、加载态、错误态和权限差异，只要接线文件声明的准备方式能到达，就进入检查。声明不了的（要注入故障、切换多个权限身份、或在检查中途复位数据），**不要自己发明办法去制造**——那属于产品自己的测试夹具范畴。

到不了的状态进**覆盖报告**，逐条写明状态名与到不了的原因。覆盖报告不驱动修改，也不进入用户裁决。

**不做跨轮次的全图比较。** 全图每次重建、不持久化，拿不到上一次的图。界面新增和消失，`git diff` 看得比全图比对准确，而范围判定本来就在用它。

## 8. 跑检查

**先跑完全部九种判拒，收集全部结果，再统一进入修改。** 不边查边改：A3 改了 token，B1 看到的就是改后的界面，用户在报告里读到的描述会对不上他打开界面看到的样子。全部检查跑在同一个界面状态上，结果才自洽。

九种判拒的完整判据在 [CRITERIA.md](CRITERIA.md)，B2、B3、B4 的方法与派发合同在 [SEMANTIC.md](SEMANTIC.md)。

主要输入是结构化数据，不是截图。**四个来源：**

- **无障碍树快照** — 读界面结构，只含角色与可访问名，不含 class、测试标识、包装元素与内联样式。因此它对前端框架不敏感，同一套方法覆盖原生 DOM、React 与 Web 应用。
- **批量提取的计算样式与布局盒模型数值** — 间距、尺寸、对比度、是否在首屏内、是否被遮挡，全部用数值判断。
- **运行时的 CSS 自定义属性** — 读根元素的计算样式，拿到实际生效的 token 集合。
- **渲染进程控制台** — 供给 A4。

截图只在两种情况下使用，并且**裁到相关区域，不截整屏**：结构化数据判不了的整体视觉印象，以及需要向用户出示证据时。

浏览器动作全部通过 `mmw-ui-qa browser` 驱动。要在 Node 脚本里直接引用浏览器自动化框架时，模块根路径用 `mmw-ui-qa home` 取。可访问性规则引擎那份注入脚本的路径用 `mmw-ui-qa accessibility-source` 取。

## 9. 处置与报告

A 类产出违规项，**直接修改**；B 类产出 finding，**只报告，等用户裁决**。

修改流程、指纹与两级匹配、五个处置标记的去向、报告的五节结构，完整读 [VERDICTS.md](VERDICTS.md)。

## 平台

Mac 侧检查 Electron 渲染层，技能自行启动应用，全流程自动。**Windows 侧不一样**：用户必须在场手动启动一次。去 Windows 之前完整读 [WINDOWS.md](WINDOWS.md)。

## 下一步

| 情况 | 下一步 |
| --- | --- |
| 检查跑完，报告已经交给用户，有要他裁决的条目 | **停**：等他逐条裁决，以及回答第 3 节的「是不是同一件事」 |
| 用户裁决完了 | **自己继续**：按 [VERDICTS.md](VERDICTS.md) 把裁决写进可用性判据，再报一次最终结果 |
| 工作区不干净 | **停**：列出未提交的文件，让用户先提交再重新发起 |
| 用户拒绝建立阈值表、可用性判据或接线文件中的任意一份 | **停**：说明缺哪几份、缺了跑不起来 |
| 用户拒绝建设计系统 | **自己继续**：跳过 A3 与 B1，其余七种照常，报告顶部声明跳过原因 |
| 问卷答完仍拿不到能启动应用的信息 | **停**：说明还缺哪几项，不猜启动方式与环境变量 |
| 判据自检报出 `error` 级 finding | **停**：写出全部 error finding |
| 被 `$mmw:mmw-prototype` 或 `$mmw:mmw-review` 叫起来 | **移交**：把报告交回调用方，由它决定往下走 |
