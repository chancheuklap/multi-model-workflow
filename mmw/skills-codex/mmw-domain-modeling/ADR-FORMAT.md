# ADR 的格式

ADR 住在 `docs/adr/`，按顺序编号：`0001-slug.md`、`0002-slug.md`，依此类推。下一个号用 `mmw domain adr-next` 取。

`docs/adr/` 目录按需建——第一份 ADR 要写时才建。

## 模板

```md
# {这个决定的短标题}

{一到三句：当时的背景是什么、我们决定了什么、为什么。}
```

就这些。一份 ADR 可以只有一段。价值在于记下**有过**这个决定以及**为什么**，不在于把各个小节填满。

## 可选小节

只在真能加分时才加。多数 ADR 用不上。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）—— 决定会被重新审视时有用
- **Considered Options** —— 只在被否掉的那些选项值得记住时才写
- **Consequences** —— 只在有不明显的下游影响需要点明时才写

## 编号

跑 `mmw domain adr-next`，它扫 ADR 目录取最大的号加一，四位零填充。目录不存在或者空的时候给 `0001`。

**这是单条分支的情形。** 几条分支可能同时写 ADR 时，各自加一必定撞号——跑 `$mmw:mmw-wayfinder` 就是这种情形，好几个会话各在自己的分支上解一条 decision ticket 链。这类分支上先写成草稿名：

```
docs/adr/draft-<ticket 编号>-<kebab-标题>.md
```

草稿不占号（`mmw domain adr-next` 只数正式编号）。等这条链合回上一层分支时再统一改成正式编号。单条分支独占的场景不用绕这一道，直接取下一个号。

## 什么时候才提议写 ADR

三条必须同时成立：

1. **难以回退** —— 以后改主意的代价是实打实的
2. **不给上下文会让人意外** —— 将来的读者看着代码会想「他们当初到底为什么要这么做？」
3. **是一次真取舍的结果** —— 当时真有别的选项，你为了具体理由选了这个

一个决定容易回退就跳过——反正你会回退它。不让人意外，就没人会想为什么。当时根本没有别的选择，那除了「我们做了显而易见的那件事」也没什么可记的。

### 什么够格

- **架构形状。** 「我们用 monorepo。」「写模型是事件溯源的，读模型投影进 Postgres。」
- **上下文之间的集成方式。** 「Ordering 和 Billing 之间走领域事件，不走同步 HTTP。」
- **带锁定效应的技术选型。** 数据库、消息总线、鉴权服务商、部署目标。不是每个库都要记——只记那些换掉要花一个季度的。
- **边界与范围的决定。** 「客户数据归 Customer 上下文所有，别的上下文只能按 ID 引用。」明确的「不做什么」跟「做什么」一样值钱。
- **刻意偏离显而易见那条路。** 「我们手写 SQL 不用 ORM，因为 X。」凡是一个正常读者会假设成相反做法的地方都算。这些能拦住下一个工程师去「修好」一件本来就是故意的事。
- **代码里看不见的约束。** 「合规要求让我们不能用 AWS。」「响应时间必须在 200 毫秒以内，因为合作方的接口合同。」
- **被否掉的选项，当否掉的理由不明显时。** 你考虑过 GraphQL、出于微妙的理由选了 REST，记下来——否则半年后又会有人提 GraphQL。
