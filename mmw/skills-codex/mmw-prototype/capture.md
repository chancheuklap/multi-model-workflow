# 保存逐轮结论

用户给出走查意见后，更新 `prototype 产物路径` 下的 `README.md`。这份 `README.md` 就是下游读 prototype 的入口：spec、ticket、plan、审查和实现都只从它出发找内容。

## 1. 记录本轮

每一轮记录以下内容：

- 当前验证问题。
- 本轮可运行资产的精确路径和运行方式。
- 用户原话。
- 根据用户意见完成的修改。
- 本轮验证结果。
- 下一轮问题，或者用户选中的产物路径。
- 整个方向不成立时，记录击穿方向的事实。

用户要求修改时，继续修改同一份 prototype。用户选定结果时，记录选中产物的精确路径。每项记录都写用户原话和实际结论。

## 2. 让 `README.md` 一个人就够用

下游只会读这一份 `README.md`，然后顺着它去找东西。所以每一轮都把下面几项维护成最新的：

- 当前问题和逐轮用户走查结论。
- 选中产物的精确路径；没有时写「无」。
- 落选变体及其形成的否定约束；没有时写「无」。
- 页面每个功能或按钮对应的后端脚本、接口合同或可复用 `module` 路径；没有界面时写「无界面对应」。
- 这一轮已经磨清楚、下游可以直接参考或复用的纯逻辑、后端脚本、接口合同、状态模型或界面 mockup，以及各自的精确路径；没有时写「无」。

**可复用指的是想法，不是工程完备度。** 列进可复用那一项的文件是在 prototype 约束下写出来的：没有测试，错误处理最少。下游把它折进正式代码时按生产标准重写——补测试、补错误处理，不要原样搬文件。在可复用那一项的开头写上这句话，让只读 `README.md` 的下游也看得到。

调试外壳、变体切换器和落选变体留在 prototype 目录里，但不要列进可复用那一项——它们只用来回顾这一轮怎么走过来的。

## 3. 提交持久资产

提交本轮可运行资产和更新后的 `README.md`。`scratch 路径` 下的过程材料不提交。提交之后，只删除本轮 prototype 自己在 `scratch 路径` 下建的文件，其他文件留着——这个目录是几个流程共用的。

## 4. 交回调用方

交回以下内容：

- 当前验证问题和用户走查结论。
- 这份 `README.md` 的精确路径。
- 选中产物的精确路径；没有时写「无」。
- 当前验证事实和否定约束。
- 页面功能或按钮与后端脚本、接口合同或可复用 `module` 的精确对应；没有界面时写「无界面对应」。
- 这一轮已经磨清楚、下游可以直接参考或复用的内容及其精确路径；没有时写「无」。

交回之后就结束。不要替调用方去写 issue 评论、关 ticket、改 map，也不要替它去找用户确认——那些由调用方自己做。
