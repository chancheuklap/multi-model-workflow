把现状查清，产出一份带引用的报告，为后面的方案与设计提供依据。**取证不判定**：只提供证据和出处，方案、路线、设计结论都留给 `mmw-propose` 与 `mmw-design`。

全程只读。几路都查完、逐条亲自验证过，主线程才写入文件。

## 定题目

执行过 `mmw-wayfind` 的，题目清单在 `docs/design/<任务名>/wayfind/map.md` 末尾「交给 mmw-investigate」那一节，照它执行。那些决策文件里已经查证过的事实连同出处直接引用，不重复派发；不够用的作为新题目派出去。没有执行过探路就当场确定题目。

**一个题目一个 `scout`**，几个同时派还是依次派，照 `mmw-dispatch` 的并行判据。范围小到一个点（一个函数、一个已知文件）就自己用 `Read`、`Grep` 查完。

两个方向分开确定题目，题目不混在一起：

| 方向 | 查什么 | 派发时额外交代什么 |
| --- | --- | --- |
| 内部 | 模块边界、接缝、数据流、根因 | 不用额外交代，方法在 `scout` 已安装的 `mmw-evidence` 里 |
| 外部（非必做） | 现有库、已有实现、最佳实践 | 库文档用 context7，其余用 web 检索 |

题目确定后先写入文件：照 [现状报告的骨架](references/investigation.md) 建出 `docs/design/<任务名>/investigation.md`，只填题目那一节，结论留空。**把这一版告诉用户**，等他确认或者修改题目再派发。方向错了后面全部作废。

## 派发与回收

派发的提示词只写这次的工作：查哪个问题、从哪个角度切入。返回什么由 `scout` 已安装的 `mmw-evidence` 规定。

回执收回来之后怎么筛选、怎么亲自验证，读 `mmw-evidence`。

## 收口

亲自验证过的事实回填 `investigation.md`，一个题目一节，缺口与丢弃的内容同时填齐。

写入后告诉用户三样：查了几个题目、报告存放在哪、缺口有几个并逐条列出。缺口里有必须由他决定才能继续的，当场提问。

遇到的本次范围之外的问题记进 `.mmw/sidelines.md`，不一并修改。

**查到中途发现题目本身就问错了**——要决定什么都还表述不准、题目答完也确定不了任何事——告诉用户输入 `/mmw-back 探路`，不要把一份答非所问的报告交下去。

查 bug 收口有两种如实的写法，按实际情况选一种：

- `scout` 返回「没能复现」：把它列出的复现路径转给用户，向他申请下面三样中的一样——一个能复现的环境；一份捕获的产物（HAR、日志转储、core dump、带时间戳的录屏）；在生产环境添加临时埋点的许可。**这个阶段不为了复现去写测试、切换版本**，这里全程只读。三样都得不到而这个 bug 又必须查清，告诉用户这需要单独开一个任务：输入 `/mmw-start fix <那个 bug>`。
- 复现成功但确定不了根因：报告里列出已排除的假设与各自的证据，请用户决定接下来排查哪一条。

## 线下 · 不是技能内容

**取证手艺为什么不在这份里**：探路解一个查证类决策、`mmw-fix` 定一个根因，用的是同一门手艺。写在这个阶段里，另外两处要用就得跨阶段引用。手艺整份住 `mmw-evidence`，三处平级点它的名字，内部谁读哪一份由它自己分。

**来源**：旧插件 `plugin/skills/orchestrate/references/investigate.md`（60 行，骨架、两个方向、亮计划、亲验与两种诚实收口照它）；`investigate-internal.workflow.js` 与 `investigate-external.workflow.js`（272 行，只取取证过滤这条机械规则）。

**没搬的**：两个 workflow 的编排脚本——并行就是连着派几个 `scout`；检索候选的六字段 JSON 传输合同（方法论里没有任何一步指示谁生成那份数据）；`handoff` 引擎调用与结论词；值守档 attended / afk 的分野，改成一律亮给用户等一句。

**题目清单为什么先落盘再念给用户**：它就是报告的第一版，不另写一份只给用户看的清单。批完直接往里填，关了会话也还在。

**待接的断口**：`mmw-propose` 还没说它读的「现状」就是这份 `investigation.md`，填那份技能时接上。
