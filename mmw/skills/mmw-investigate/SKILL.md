把现状查清，产出一份带引用的报告，给 `mmw-design` 扎根。**取证不判定**：只摆证据和出处，不在这里拍方案、选路线、下设计结论。

全程只读。几路查完、合成过，主线程才写盘。

## 定题目

跑过 `mmw-wayfind` 的，题目清单在 `docs/design/<任务名>/wayfind/map.md` 末尾那节，照它走；没跑过就当场定。那些决策文件里已经查证过的事实带着出处直接引用，不重派；不够用就当新题目派。

**一个题目一个 `scout`**，要几个派几个。每个题目写清两样：从哪个角度查、要回答什么。

两个方向分开跑，题目不混：

| 方向 | 查什么 | 怎么交代角度 |
| --- | --- | --- |
| 内部 | 模块边界、接缝、数据流、根因 | 先读 [调查角度](references/angles.md)，把要用的词汇与判据写进给它的活里 |
| 外部（非必做） | 现有库、已有实现、最佳实践 | 库文档优先走 context7，其余用 web 检索 |

只要内部就只派内部那几个，要对比外部方案再派一轮。**窄到一个点**（一个函数、一个已知文件）就自己 `Read`、`Grep` 查完，不派。

派之前把题目清单亮给用户，等他批一句或者改。方向错了白烧。

## 回执

派它的时候要交代清楚回执给四样：一条条事实（一句话，不是判断也不是方案）、每条的出处与信心（高中低）、这个题目的现状小结、没查清的缺口。

**收到先机械过滤**：没出处的、信心标低的，丢掉。丢了什么单独记一行——被丢的往往正是下一轮要补查的。

## 合成与亲验

几路合成一份：跨题去重、把相关的事实串起来、每条结论保住出处。

**写进报告之前逐条亲验。**仓库的结论自己回目标 checkout 用 `Grep`、`Read` 坐实，保留 `文件:行号` 与原始行。外部的承重结论（库的行为、接口合同、规范语义）沿引用链追到第一方来源——官方文档、源码、规范、第一方接口；二手综述只当线索，追不到就降级写「待验」。验不过的不写进报告。

## 收口

报告落进 `docs/design/<任务名>/investigating.md`，目录不存在就建，随设计一起提交。领域文档归 `mmw-design` 维护，这里不碰。

撞到的本次范围外的东西记进 `.mmw/sidelines.md`，不顺手修。

查 bug 的根因有两种诚实收口，别硬编一个根因往下走：复现不了，报告附上已试过的复现路径；复现了但定不到根因，附上已排除的假设与各自的证据。两种各该向用户要什么，写在 [调查角度](references/angles.md) 的查 bug 那节。

## 线下 · 不是技能内容

**角度不引外部技能原文**：上游那三份的取舍与摘录理由写在 [references/angles.md](references/angles.md) 的线下区。

**来源**：旧插件 `plugin/skills/orchestrate/references/investigate.md`（60 行，骨架、两个方向、亮计划、亲验与两种诚实收口照它）；`investigate-internal.workflow.js` 与 `investigate-external.workflow.js`（272 行，只取提示词里的回执四件与取证过滤这条机械规则）；上游 `engineering/research`（12 行，追第一方来源与旧插件互相印证）。

**没搬的**：两个 workflow 的编排脚本——并行就是连着派几个 `scout`；检索候选的六字段 JSON 传输合同（方法论里没有任何一步指示谁生成那份数据）；`handoff` 引擎调用与结论词；值守档 attended / afk 的分野，改成一律亮给用户等一句。

**取证过滤为什么是机械的**：按有没有出处、信心标了什么来筛，不让另一个代理去评判前一个代理的结论。丢弃留痕，不静默吞。

**待接的断口**：`mmw-propose` 还没说它读的「现状」就是这份 `investigating.md`，填那份技能时接上。
