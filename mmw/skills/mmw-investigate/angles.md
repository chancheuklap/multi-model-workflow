# 调查角度

主线程读这份，把要用的词汇与判据写进派给 `scout` 的活里。

**只摆事实，不提改法。**下面这些判据是用来把观察写成一句能落进报告的事实的，不是用来提改造建议的。

## 描述代码结构

术语从头到尾用同一个，别换成「组件」「服务」「API」「边界」——换词就对不上账。

| 词 | 指什么 |
| --- | --- |
| 模块 | 有接口和实现的任何东西：一个函数、一个类、一个包、一条跨层的切片 |
| 接口 | 调用方为了用对它必须知道的全部：类型签名，加上不变量、调用顺序约束、错误模式、必需配置、性能特征 |
| 实现 | 模块内部的代码本体 |
| 接缝 | 能在别处改变行为而不必改这里的位置——接口所在的地方 |
| 适配器 | 坐在接缝上、满足那个接口的具体东西 |
| 深 / 浅 | 深＝大量行为藏在小接口后面；浅＝接口几乎和实现一样复杂 |

三个判据：

- **删除测试**：设想删掉这个模块。复杂度跟着消失，它就是个穿透层；复杂度在 N 个调用方那里重新冒出来，它在挣自己的饭钱。
- **一个适配器是假接缝，两个才是真的**：只有一种实现坐在那儿，这条接缝是设想出来的，不是真有东西在变。
- **依赖是接进来的还是自己造的**：模块在内部 `new` 依赖，它的接口就测不动；依赖从参数进来，接口就是测试面。

## 查 bug 的根因

只读阶段能做到两件事：判断这个 bug 能不能稳定复现，以及把假设收窄。建反馈回路——写失败测试、插桩、跑二分——是落地阶段的活，这里不做。

**先判能不能复现。**没有一个会为这个 bug 变红的信号，盯着代码想原因是白费。非确定性的 bug 不要求干净复现，要的是复现率高到能查：一半的概率能查，百分之一不能。

**能复现**：一次提 3 到 5 个假设并排序，别只提一个——第一个看着像的会把你锚死。每个假设必须可证伪，写成一句预测：「如果是 X 导致的，那么改 Y 会让它消失、改 Z 会让它更严重。」说不出预测的是感觉不是假设，磨尖或者丢掉。排好序先给用户看一眼，他常常一句话就能重排（「我们刚上线过第三条」）。然后在只读范围内逐个排除——用代码、日志、提交历史找反证；排掉的连同证据记进报告。

**复现不了**：停下来说清楚，别接着编假设。列出已经试过的复现路径，向用户要三样里的一样：能复现的环境、一份捕获的产物（HAR、日志转储、core dump、带时间戳的录屏）、或者往生产加临时埋点的许可。
