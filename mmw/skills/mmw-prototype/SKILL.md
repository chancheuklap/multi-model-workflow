开始前，遵守目标仓库 `AGENTS.md` 的领域上下文规则。

原型是**为了回答一个问题而写的能跑的东西**。问题决定它长什么形状。

**它的产物是资产，不是一次性代码**：落在仓库里、随设计一起提交、原地迭代，不另起临时分支重做一版。

## 一轮只回答一个问题

开写之前先把这一轮要回答的那个问题写下来，一句话。判据是**用户走查完能给出一个明确答案**：状态模型那类的答案形如「对」或者「不对，因为退款窗口关闭之后这条路走不通」；界面那类的答案形如「选 B，页头换成 C 的」；数据或者合同那类的答案形如「够用」或者「少一个退款发起人的字段」。「这个设计好不好」得不到明确答案，收不成这个形状先回 `/mmw-grilling` 谈清楚。

要问的有好几个时，排出当前最关键的那个先做，其余等这一轮走查完再开新一轮。

问题产自讨论，不凭空造。

## 选一条 branch

| 这一轮要回答什么 | 走哪条 |
| --- | --- |
| 这套逻辑、状态转移或者数据形状对不对，而且要用户**手动推过**几种情形才判得出来 | [LOGIC.md](LOGIC.md)。做一个双击可运行的自包含 HTML，让非开发者通过 free-play 和 guided walkthrough 推过纸上想不清楚的情形 |
| 它该长什么样 | [UI.md](UI.md)。在同一个路由上给出几个结构截然不同的界面变体，用 URL 查询参数和一个浮动底栏切换 |
| 一份数据长什么样、一个接口的合同是什么、一段转换的输出对不对——**看一眼输出就判得出来** | 不用交互式 HTML 也不用界面变体。做一份**最小的能跑的东西**：一个脚本、一份合同样例、一个测试夹具。跑完把输入和输出并排摆给用户看，规矩见本文“后端那条 branch：不要为了走查而搭壳”一节 |
| **我们要依赖的那个外部系统**实际表现如何：撑得住多少、实际返回什么、几个候选哪个扛得住 | [EVIDENCE.md](EVIDENCE.md)。写探测脚本真实跑一次，先定通过判据再跑，结果记成一份台账 |

前三条验的是我们自己要写的东西，第四条验的是我们要依赖的外部系统。

前三条之间两可、用户又不在场时，按周边代码判——页面或组件走界面，后端模块看用户要不要手动推：要推走逻辑 HTML，不要推走最小脚本——并在 prototype 开头写明这个假设。分不清是自己的东西还是外部系统时，问一句：**这个问题的答案会不会因为换一个供应商、换一个版本就变？** 会，走 [EVIDENCE.md](EVIDENCE.md)。

## 后端那条 branch：不要为了走查而搭壳

问题是「这份数据长这样对不对」「这个接口该收什么返回什么」「这段转换的输出符不符合预期」时，用户要看的是**那份输出本身**，不是一个能按键的界面。给他一份样例 JSON、一段跑完打印结果的脚本、或者一个把预期写成断言的测试夹具。

判据是**用户要不要手动改变状态才判得出来**。要改（先退款再取消，看它拦不拦得住），走逻辑 HTML；不用改（这份订单快照的字段够不够用），做最小脚本。

这条 branch 照样守本技能其余各节的通用规矩、照样落在 prototype 产物路径、照样逐轮记进 `README.md`、照样要用户走查过才算数。它省掉的只是那层壳。

产物放 `logic/` 目录，跟逻辑 HTML 那条 branch 同一个位置。

## 前三条设计 branch 都适用的规矩

1. **不用猜怎么运行。** 逻辑 prototype 是一个可双击打开的 HTML 文件。界面 prototype 和最小脚本使用项目已有的任务入口（`pnpm <名字>`、`python <路径>`、`bun <路径>`）。项目没有任务入口时，把完整命令写在 prototype 目录的 `README.md` 开头。
2. **默认不落库。** 状态放内存。问题本身就是关于数据库的，就接一个临时库，或者一个名字里带 `PROTOTYPE — wipe me` 的本地文件。
3. **不打磨。** 不写测试，错误处理只做到能运行为止，不做与当前问题无关的抽象。HTML 外壳是走查工具；纯逻辑模块是可移植资产，后续 ticket 会把它移入正式 module，再用 TDD 补上生产关卡。
4. **把状态摊开给人看。** 每次操作之后（逻辑原型）或者每次切换变体之后（界面原型），把相关状态整个打出来或者渲染出来，让用户看得见变了什么。
5. **覆盖真实存在的边界，不只演顺利路径。** 逻辑 HTML 那条 branch 覆盖哪些边界见 [LOGIC.md](LOGIC.md)，界面那条 branch 见 [UI.md](UI.md)。最小脚本那条 branch：样例里要有失败、空和边界值，不能只给一份长得最漂亮的。

## 落在哪

调用方必须给出产物目录。从 `/mmw-wayfinder` 来的任务还必须给出当前 decision ticket 的 `issue-<编号>` 子目录。普通非 Wayfinder 任务使用任务 slug 作为产物目录，不加 issue 子目录。

开始之前运行对应命令，把输出分别记为 prototype 产物路径、evidence 产物路径和 scratch 路径：

```bash
mmw artifact path prototype <产物目录> [issue-<编号>]
mmw artifact path evidence <产物目录> [issue-<编号>]
mmw artifact path scratch <产物目录> [issue-<编号>]
```

前三条设计 branch 的持久目录只保存设计合同需要的东西：

```
<prototype 产物路径>/
├── README.md              本轮问题、逐轮用户走查结论、用户选中的路径
├── logic/                 可运行逻辑 prototype 和确认过的可移植逻辑
└── mockup/                完整 UI 变体集
```

过程截图、DOM、console、录屏、临时探测输出和生成中间物默认写入 scratch 路径，不进 Git。只有直接支撑长期决定、且无法用持久 prototype 本身低成本重建的最小证据，才提升到 prototype 产物路径或 evidence 产物路径。每份提升的证据都要在 `README.md` 或结论台账里逐条引用。

**[EVIDENCE.md](EVIDENCE.md) 那条 branch 使用 evidence 产物路径和 scratch 路径**。它仍然要先确认任务 worktree，并在原路径迭代；文件形状、运行记录和完成判据只按 [EVIDENCE.md](EVIDENCE.md)，不套用前三条设计 branch 的 `README.md` 和用户走查合同。

开始写原型之前，先确认当前任务已有正确的 slug 和任务 worktree。没有时按下面的宿主动作建立任务 worktree：

[[mmw-host-action:prepare-task-worktree]]

**原地迭代，不复制版本目录。** 下一轮继续改同一份源码，保留已经确认过的状态、交互和文案。

**Prototype 产物路径不随 spec 一起删。** 它是逻辑决定和视觉合同的 primary source。正式实现只吸收用户已经确认的决定；逻辑 branch 还会移入其中可移植的纯逻辑模块。Scratch 路径随任务清理。

前三条设计 branch 的 `README.md` 顶部写本轮问题。每轮只追加用户走查反馈、结论和用户选中的路径。UI 走查还要列出所有落选或 `superseded` 变体的路径，以及它们形成的明确否定约束；没有则写「无」。每轮都要列出被提升为长期证据的路径；没有则写「无」。修改过程、验证过程和未提升的材料留在 scratch。结论只有三个词：

| 结论 | 什么意思 |
| --- | --- |
| `continue` | 还没定下来，登记下一轮要回答的问题接着做 |
| `accepted` | 用户明确接受了，写清楚选中的是哪几份产物 |
| `superseded` | 验证证明这个方向本身不成立 |

前三条设计 branch 每轮走查完立刻提交：这一轮的可运行源码、`README.md` 和确实提升且已引用的证据放同一个提交，不夹带 scratch 或无关文件。

## 走查是人工审批关卡

把当前产物和运行结果给用户看，记下他的原话或者你的明确假设。**不替用户宣布定稿**，走查没过的时候也不并行往下写正式代码。

派一个 subagent 自问自答，它给的结论不作数。

下表准备移交下一技能时，先读 [`../mmw-start/phase-boundaries.md`](../mmw-start/phase-boundaries.md)，按顺序判断是否留在当前会话。自己继续和因 blocker 停下不触发阶段边界判断。

| 要问的问题收不成能明确回答的形状 | **移交**：`/mmw-grilling`，把它谈清楚再回来 |
| 这个问题读文档、读源码就能答，不用真跑 | **移交**：`/mmw-research` |
