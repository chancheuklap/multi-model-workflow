# 逻辑 prototype

做一个自包含 HTML 文件，让任何人通过按钮驱动状态模型。它回答业务逻辑、状态转移或数据形状的问题。纸上看着合理、必须推过真实情形才判断得出的设计问题走这一条。

问题是“它该长什么样”时，回 [UI.md](UI.md)。只需看一次输出时，回 [SKILL.md](SKILL.md) 的最小脚本分支。

## 1. 把问题写在页面上

页面顶部用一段可见文字写清状态模型和本轮问题。不要只写代码注释。用户稍后独立打开文件时，仍能判断这个 prototype 在验证什么。

一轮只回答 [SKILL.md](SKILL.md) 已登记的那一个问题。

## 2. 把逻辑隔离成可移植模块

实际回答问题的逻辑放进一个独立 `<script>` 块。它使用仓库的语言和领域命名，并保持纯粹：不访问 DOM，不读取按钮，不通过打印控制流程。

按问题选择形状：

- 纯 reducer：动作是离散事件，状态是单个值。
- 状态机：合法动作取决于当前状态。
- 一组纯函数：只有数据变换，没有隐含当前状态。
- 类或模块：逻辑确实持有持续的内部状态。

页面调用逻辑模块。逻辑模块不能反过来调用页面。HTML 外壳是走查工具；纯逻辑模块是 prototype 中不丢弃的部分。实现阶段把用户确认过的 reducer、状态机或纯函数移入正式 module，再按 `/mmw-tdd` 补齐测试和生产集成。

## 3. 生成一个自包含 HTML 文件

文件放在 [SKILL.md](SKILL.md) 通过 `mmw path prototype` 取得的 prototype 产物路径下的 `logic/`。HTML、CSS 和 JavaScript 全部内联。不要使用框架、bundler、服务器或外部依赖。用户双击文件就能运行，也能直接把文件交给不写代码的人。

页面按以下顺序布局：

1. 标题和一句说明。说明复述本轮问题。
2. 当前状态。使用带标签的字段展示全部相关状态，不把原始 JSON 直接丢给用户。每次操作后重新渲染，并在有帮助时说明刚刚改变了什么。
3. Free-play。每种动作一个真实按钮，按钮始终可用。非法动作也允许点击，由模型明确拒绝并说明原因。
4. Guided walkthrough。一个场景一个 tab。每个 tab 说明场景设置和观察重点，并按顺序提供真实动作按钮。

启动任一 guided walkthrough 时，先重置到该场景声明的已知初态。每次重新启动同一场景，必须得到相同起点。

界面使用领域语言，不暴露 reducer、事件枚举或字段缩写。排版保持克制：清楚的层级、足够的间距和一个强调色。不要加入动画和装饰性效果。

## 4. 覆盖真正难判断的场景

场景来自本轮问题和实际领域边界。至少覆盖：

- 正常路径。
- 一个纸上难判断的边界。
- 一次应被拒绝的非法动作。

并发、回滚、空状态和失败状态只在该模型真实存在时加入。不要为了显得完整而制造不存在的场景。

## 5. 交给用户走查

打开 HTML 文件，把 free-play 和每个 guided walkthrough 交给用户。用户需要能独立重置和重跑场景。

[[mmw-host-action:present-ui-review]]

用户说“这不应该发生”或“我以为这里会不同”时，把反馈登记为下一轮问题。需要新动作或新场景时，继续修改同一文件，不复制版本目录。

## 不能要的写法

- 使用框架、bundler 或服务器。逻辑 prototype 必须是一个双击可运行的文件。
- 只有 guided walkthrough，没有 free-play。用户必须能按任意顺序尝试动作。
- 场景只写说明，没有真实按钮。每一步必须实际调用同一逻辑模块。
- 场景不重置初态。无法重复的 walkthrough 不能验证状态模型。
- 逻辑模块访问 DOM。页面是一次性外壳，逻辑必须保持可移植。
- 把 HTML 外壳当成生产页面。后续只移入已经验证的纯逻辑模块。
