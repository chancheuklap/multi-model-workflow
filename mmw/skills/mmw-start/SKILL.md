需求理解到能起个名字就建树，深入的对话放进第一个阶段做。

## 怎么做

1. **拆参数**：第一个词是个阶段名就当起点，其余全是需求；不是就整串都是需求，起点用 `mmw-wayfind`。
2. **从需求提炼任务名**：动作加对象，短横线连写，只用小写字母、数字和短横线（`fix-payment-retry`、`add-oauth-login`）。泛称起不了名——`update`、`refactor`、`task-1` 隔一个月认不出是哪件事。
3. 在主仓库跑插件根的 `scripts/task.sh new <任务名> <起点技能名>`。忽略清单、工作树、`.mmw/task.json`、`.mmw/sidelines.md` 由它一次落齐，输出头四行给你任务名、工作树路径、分叉点、起点。
4. 进到那棵工作树里。这个任务往后每一步都在里面干：状态文件、旁路清单、代码改动都在那里，留在主仓库的话下一份技能读不到状态。
5. 告诉用户三样：任务名、工作树路径、开在哪个阶段加为什么。请他改或者点头。
6. 用户点头，接着读那个阶段的技能；他要换一个，读 `mmw-next`。

---

## 线下 · 不是技能内容

**两份状态文件为什么由脚本注入**：这两份谁都要读写——主线程每个阶段、被派出去的工人都会碰。格式住 `templates/`，每棵工作树里长得一模一样。让主线程照着技能里的样例手抄，抄错一次这棵树就带着错格式跑完全程；改格式还得同时改抄本与所有引用它的技能。

**忽略清单为什么必须在建树之前提交**：工作树若从一个还没忽略 `.mmw/` 的提交分叉，状态文件会以未跟踪身份出现在工人的改动里，验收读 diff 时分不清哪些是工人改的。

**为什么催着建树**：状态文件没地方存之前，聊多少轮都在盘外，关掉会话就没了。

**来源**：`plugin/scripts/prepare.sh`（315 行，建工作树、起名、写状态、从父 HEAD 分叉照它；它第 8 行「路由由 LLM 当场判，不在本脚本」与这里的分工一致）。

**起点为什么是个可选参数而不是一套判断**：探路默认第一格这个默认，对新做一件事成立，对修一个已知的 bug 不成立——那类任务开在探路就得先敲一次跳出去，常见路径走成了例外路径。给参数是零判断：用户给什么脚本写什么，脚本只校验拼写。

**起点为什么排在需求前面**：需求是一长串自然语言，尾巴上再挂一个格名，敲的人和读的人都要先找到那个尾巴。第一个词认不认得出是格名，一眼就分得开。

**为什么不给中文名立一张对应表**：九份格子技能主线程全都装着，每份 description 的头一个词就是那个中文名，认起来不用查表。真写了表，它得在四个入口之间共享，要么复制四份，要么让三份技能跨文件去读第四份。约束只剩一条：九份 description 的头一个词必须是格名且互不重复——这条空转脚本验得了。

**这里为什么不放一张「什么时候从这里起」的判据表**：起点由用户给，不由主线程判，那张表没人读——主线程只需要认出第一个词是不是格名，判据一列它用不上；用户读不到技能正文，他看得见的是补全提示，九个中文名全在那儿。

**没搬的**：入口能力判定那六种治理能力与「须给用户原话当证据」——敲了这个命令就是要用；三十九字段任务档案；`routes.json` 的场景预设——起点是一格的名字，不是一套预设的阶段序列。
