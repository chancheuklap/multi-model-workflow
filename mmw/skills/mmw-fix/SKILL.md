工作树已经建好，`phase` 是 `mmw-fix`，用户要做的事写在 `.mmw/task.json` 的 `note` 里。

这条路上代码由你自己写，不派角色出去。如果发现必须先做设计、把工作拆成几件、写一份计划才动得了，说明它不该走这条路——第 2 步分岔。

## 步骤

1. **先查清楚。**查根因读 `mmw-evidence` 的「主线程：查一个 bug 的根因」，那一份也写了信号造不出来怎么办；查改动面、动了它谁会跟着变，读同一份技能的「主线程：查代码结构」。

   范围窄（就一个函数、一个已知文件）你自己查完。要追的线索有好几条、彼此不依赖，就派 `scout` 去查，怎么派读 `mmw-dispatch`；它交回三节之后，读 `mmw-evidence` 的「主线程：回执收回来之后」。

   这一步不修改产品代码。为造出那个会变红的信号而写的测试和临时脚本不在此列。

2. **查完先分岔。**

   - 确实只是一处小事 → 往下做第 3 步。
   - 是系统性的问题（要重做设计，或者要拆成好几件工作）→ 告诉用户这件事改一处解决不了，然后自己调用 `/mmw-back 探路`。返回之前在 `note` 里写明你查到了什么、为什么要返回。工作树不用重建，已经查到的事实继续沿用。

3. **动手之前告诉用户三样，等他回复再改**：你查到了什么、打算怎么改、影响面到哪里。改之前只停这一次，修改过程中不再回来请示。

4. **改。**查根因时造的那个会变红的信号就是这次的测试，直接用；还没有就先写一条——修 bug 就是按根因写一条复现测试——再用最小的改动把它转绿，然后提交。过程中遇到的、这次范围之外的问题记进 `.mmw/sidelines.md`，不一并修。

5. **请用户输入 `/mmw-review 落地` 发起终审。**终审由他自己发起，你不代为输入。「落地」这两个字要告诉他：发起审查那一份技能按主干阶段名选审法，短路径不在它的名单里，他不点名就选不出来。

6. **终审通过后，请用户输入 `/mmw-next 出包`。**出包那一份技能会带着他跑两轮测试：开发模式下的功能测试，还有安装之后的测试。这个仓库没有安装包可出，就请他输入 `/mmw-next 收尾`。

---

## 线下 · 不是技能内容

**为什么这不是一个入口**：用户只敲 `/mmw-start`，`fix` 写在需求前面，路由由那一份做完。再给它一个斜杠入口，等于要用户先自己判断这件事够不够小——那正是这一份第 1 步查完才知道的事。

**`phase` 存 `mmw-fix` 而不是某个主干阶段**：这条路整程都在这一份底下——查、确认、改、起终审，中间不换阶段。存成落地那一格的话，新会话读到的是「派工人写码」那套，与这条路要干的事对不上。

**修一个 bug 与改一处已知的地方是同一条路**：动作是同一串——先查清、再确认、再最小改动转绿。差别只在第 1 步查的是根因还是改动面，而怎么查整份在 `mmw-evidence` 里，分成两条只是把同一串步骤抄两遍。

**来源**：旧插件 `plugin/skills/orchestrate/references/scenario/bug.md` 与 `small-change.md`（各 88 行，其中三分之二是四份场景共享的引擎锚点块；两条各自专属的只有开头那几行加动手前那一次轻确认）。

**造复现信号那一整套不写在这里**：写失败测试、切旧版本 diff、`git bisect run`、拿脚本请用户按提示操作，这些要动工作树，只有主线程做得了。它们整套住在 `mmw-evidence` 写给主线程的那一份里。查一个 bug 的根因这件事，主线程在 `mmw-investigate` 里也会遇到；搬一份到这里，就是同一套办法两处各存一版。

**没搬的**：场景预设的阶段序列与强制走完；`--entry-capability` 那六种治理能力与原话取证；`mmw task escalate --to develop` 这条升级命令——回上游走 `mmw-back` 就是了，不另立一个动词；值守档与它带来的「afk 也要停这一次」的说法。
