用户敲了这条，就是要改一处已知的地方：不做设计、不切片、不写计划。他要做的其实是一件新东西，请他改敲 `/mmw-start`。

两条路都从取证起步，取证做完、他点过头你才动手；代码你自己写，测试先行，不派 `executor`。

**状态文件已经在了**（新会话读到 `phase` 是 `mmw-fix`）：树早就建好了，跳过下面「开任务」整节，念一遍 `note` 看走的是哪一条，从对应那一节接着干。

## 开任务

1. **认哪一条**：有一个已知的坏行为、根因还没定，是修 bug；改哪、怎么改都已经清楚，是小改动。用户开头点了就照他点的，没点你挑一条，第 3 步一起确认。

2. **起任务名**：动作加对象，短横线连写，只用小写字母、数字和短横线，像 `fix-payment-retry`、`bump-upload-limit`。`update`、`refactor`、`task-1` 这类泛称隔一个月认不出是哪件事。

3. **建树之前把任务名与走哪一条念给用户，等他改或者点头。**这两样建了树就写进分支名与状态文件，再改要拆掉重来。

4. 跑这一句：

   ```bash
   bash "${CLAUDE_PLUGIN_ROOT}/scripts/task.sh" new <任务名> mmw-fix
   ```

   忽略清单、工作树、`.mmw/task.json`、`.mmw/sidelines.md` 由它一次落齐，输出头四行是任务名、工作树路径、分叉点、起点。

5. `EnterWorktree({ path: "<上一步回的工作树路径>" })`。这个任务往后每一步都在那棵树里干：状态、旁路清单、代码改动都在那儿，留在主仓库下一份技能读不到状态。

6. 把用户的需求原话与走的是修 bug 还是小改动，写进 `.mmw/task.json` 的 `note`。走哪一条只有这一句记得住，需求原话也没有别的地方存得下。

7. 往下走对应那一节。

## 修 bug

1. **先定根因。**照 `mmw-evidence` 的「查一个 bug 的根因」那节做：先判这个 bug 能不能稳定复现——没有一个会为它变红的信号，盯着代码想原因是白费；能复现就一次提三到五个可证伪的假设、排序、逐个排除。

   范围窄（一个函数、一个已知文件）你自己查完。要追的线索有好几条且彼此不依赖，才派 `scout`，几个一起派还是串着派照 `mmw-dispatch` 的并行判据；回执照 `mmw-evidence` 的 [回执收回来之后](../mmw-evidence/references/verify.md) 过滤与亲验。

2. **复现不了就停下来向用户要东西**：把试过的复现路径逐条列给他，要三样里的一样——能复现的环境、一份捕获的产物（HAR、日志转储、core dump、带时间戳的录屏）、或者往生产加临时埋点的许可。三样都拿不到就不往下猜。

3. **动手前把三样念给用户，等他回一句你再动**：根因是什么、打算怎么修、影响面到哪。这是这条路上唯一一次停。

4. **修**：先按根因写一条会红的复现测试，再最小改动把它转绿，提交。改动跨好几个文件，先自己写一份计划把活理清再逐条做——不派 `plan-writer`，也不进计划审。

## 小改动

1. **先把要改的地方摸准。**照 `mmw-evidence` 的「查代码结构的时候」那节做，答清两件事：改哪一处、动了它谁会跟着变。这一步只读，不动手。

2. **动手前把两样念给用户，等他回一句你再动**：打算怎么改、影响面到哪。

3. **改**：测试先行，最小改动，提交。

## 发现它不是这条路

根因是设计级缺陷而不是局部 bug，或者这个改动要动设计、要跨好几个模块：先一句话告诉用户这不是改一处能了结的事，请他敲 `/mmw-back 探路`。工作树不重开，已经查到的事实留着接着用。

## 收口

- 撞到的本次范围外的问题你记进 `.mmw/sidelines.md`，不顺手修。
- 改完请用户敲 `/mmw-review 落地` 起终审，审的是这个任务的全部改动。**终审要他自己起**，你不代敲；**要点名落地**，审查的对应关系认的是主干阶段名，`mmw-fix` 不在那张表里。
- 终审过了，告诉用户下一步敲哪一句：有安装包目标是 `/mmw-next 出包`，没有就 `/mmw-next 收尾`。

---

## 线下 · 不是技能内容

**`phase` 存 `mmw-fix` 而不是某个主干阶段**：这条路整程都在这一份底下——取证、确认、改、起终审，中间不换阶段。存成落地那一格的话，新会话读到的是「派工人写码」那套，与这条路要干的事对不上；存成查清现状那一格更远，那一格产的是给设计扎根的报告。

**为什么与 `mmw-start` 分成两份**：两条路从第一步起就不一样，合一份得先摆判据表再分岔，读的人每次先读一半与自己无关的。

**为什么不再往下拆一份 references**：这一份从头到尾一个读者、一趟读完，没有只有一部分运行会走到的分支。拆出去只多一次跳转。

**来源**：建树那几步与 `mmw-start` 同源（`plugin/scripts/prepare.sh`）；两条路的分界与各自的走法来自旧插件 `plugin/skills/orchestrate/references/scenario/bug.md` 与 `small-change.md`（各 88 行，其中三分之二是四份场景共享的引擎锚点块，两条路各自专属的只有开头那几行加动手前那一次轻确认）。

**没搬的**：场景预设的阶段序列与强制走完；`--entry-capability` 那六种治理能力与原话取证；`mmw task escalate --to develop` 这条升级命令——回上游敲 `/mmw-back` 就是了，不另立一个动词；值守档与它带来的「afk 也要停这一次」的说法。
