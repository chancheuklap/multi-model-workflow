你在查一个问题，要的是带出处的事实。**取证不判定**：只摆证据和出处，改法、路线、设计结论不在这一步定。

查不到就说查不到，别拿推测填。

## 查代码结构的时候

下面六个词是全部，指同一样东西时从头到尾用同一个，换词就对不上账。

| 词 | 指什么 |
| --- | --- |
| 模块 | 有接口和实现的任何东西：一个函数、一个类、一个包、一条跨层的切片 |
| 接口 | 调用方为了用对它必须知道的全部：类型签名，加上不变量、调用顺序约束、错误模式、必需配置、性能特征 |
| 实现 | 模块内部的代码本体 |
| 接缝 | 能在别处改变行为而不必改这里的位置——接口所在的地方 |
| 适配器 | 坐在接缝上、满足那个接口的具体东西 |
| 深 / 浅 | 深＝大量行为藏在小接口后面；浅＝接口几乎和实现一样复杂 |

三个判据，用来把看到的东西变成一条说得出出处的事实：

- **删除测试**：设想删掉这个模块。复杂度跟着消失，它就是个穿透层；复杂度在 N 个调用方那里重新冒出来，它在挣自己的饭钱。
- **一个适配器是假接缝，两个才是真的**：只有一种实现坐在那儿，这条接缝是设想出来的，不是真有东西在变。
- **依赖是接进来的还是自己造的**：模块在内部 `new` 依赖，它的接口就测不动；依赖从参数进来，接口就是测试面。

写一个模块的依赖时点明是哪一类，四类是全部：

| 类 | 什么样 |
| --- | --- |
| 进程内 | 纯计算、内存里的状态，不碰 I/O |
| 本地可替身 | 有个本地替身顶得住：PGLite 顶 Postgres、内存文件系统顶磁盘 |
| 远端但自家的 | 自己的服务，隔着一层网络：微服务、内部接口 |
| 真外部 | 管不着的第三方：Stripe、Twilio 这类 |

## 查一个 bug 的根因的时候

### 先造一个会变红的信号

**这一步就是这门手艺本身，剩下的都是机械劳动。**手上有一个会为这个 bug 变红、修好就转绿的信号，你就能找到原因；没有这个信号，盯着代码想原因是白费。力气不成比例地花在这里：使劲想办法，别放弃。

**造这个信号是主线程的活**，`scout` 不做：它改不了文件、切不了版本；而且一个 bug 只需要一个信号，派几个人各造一个是白费。派出去的活是「查某一条线索」，回来的是事实。

主线程手上有自己的工作树，这些都做得到，从轻到重试：

1. 拿 curl 或一段 HTTP 脚本打一个跑着的开发服务器，看它回什么。
2. 用固定输入跑一次命令行，把输出跟已知正确的结果比。
3. 从日志和提交历史里找那条会随 bug 一起出现、修好就消失的记录。
4. 写一条会为这个 bug 变红的测试，或者搭一个一次性的最小环境，把出 bug 那条路径单独跑起来。
5. 存一份抓下来的真实请求或事件，脱开界面回放它。
6. bug 是在两个已知状态之间冒出来的，切到旧版本跑同一个输入、diff 两边的输出；两头都清楚就把「切到状态 X，跑一次，看结果」写成一条命令交给 `git bisect run`。
7. 非得有人点鼠标才出得来的，把 `scripts/hitl-loop.template.sh` 复制一份、改成这次要用户走的步骤，让他跟着提示做，脚本会把他的回答按 `键=值` 打出来给你接着用。人当手，你当脑。

**造出来了就磨它**：跑得更快（缓存准备工作、跳过无关初始化、缩小测试范围）、更尖（断言用户说的那个具体症状，不是「没崩」）、更确定（钉住时间、固定随机种子、隔离文件系统、冻住网络）。三十秒还时灵时不灵的信号跟没有差不多，两秒钟每次结论都一样的信号是另一回事。

**这个 bug 时有时无**：要的不是干净复现，是把复现率拉高到能查。触发一百次、并行跑、加压、缩窄时间窗、往可疑的地方注入 sleep。一半的概率能查，百分之一不能。

**这一步算干完的判据**：你说得出一条命令，而且已经真跑过至少一次，把命令和它的输出一起记下来。这条命令要走的是出 bug 的那条路径、断言的是用户说的那个具体症状（不是「没报错」），每次跑结论一样，几秒钟出结果。那条命令连同输出就是这个 bug 最硬的出处。

### 信号有了，再提假设

一次提 3 到 5 个假设并排序——第一个看着像的会把你锚死。每个假设写成一句可证伪的预测：「如果是 X 导致的，那么改 Y 会让它消失、改 Z 会让它更严重。」说不出预测的是感觉，磨尖它或者丢掉它。然后逐个排除，用代码、日志、提交历史找反证；排掉哪一条、凭什么排掉，都记下来。

**信号始终造不出来**：记下这个 bug 没能复现，把已经试过的每一条路径逐条列出来。没有信号就编假设是这门手艺最要防的事，到此为止。

被派出来查一条线索的 `scout` 手上没有信号也很正常——那不是你的活，照实写进缺口那节交上去。

## 查完了，回什么

只给这三节：

```markdown
## 事实

| 事实 | 出处 | 信心 |
| --- | --- | --- |

## 小结

<这个问题现在是什么样，几句话。>

## 缺口

- <没查清的，和它挡住什么>
```

一条事实一行，是一句陈述而不是判断或建议。出处给 `文件:行号` 或链接，出处给不出来的那条就不写进表里。信心填 高 / 中 / 低：亲眼读到写高，靠推断写中，只是看着像写低。

前面排掉的假设、没能复现这件事，都进事实表；没查清的进缺口那节，连同它挡住了什么。

这三节交上去之后，没出处的和信心低的会被整条丢掉，所以出处越准，这一轮的活留下来得越多。

## 查完之后

前面每一步谁来做都一样，到这里才分。看你是哪一个：

**`scout`**：三节交上去，这一轮就完了。

**主线程**：

- 派了 `scout` 的，他交回来的三节归你筛、归你亲验，两道怎么做在[回执收回来之后](references/verify.md)。
- 小结写的是「没能复现」，把试过的每一条路径给用户看，向他要下面三样里的一样。三样都拿不到就停在这里，不接着猜。
  - 一个能复现的环境
  - 一份捕获的产物：HAR、日志转储、core dump、带时间戳的录屏
  - 往生产环境加临时埋点的许可

做完这些，**读 `.mmw/task.json` 的 `phase`，回那一份技能接着走**——查了一轮下来记不清自己是从哪儿进来的，`phase` 里存的技能名就是答案。亲验过的事实落到哪个文件，由那一份定。

## 线下 · 不是技能内容

**为什么单独一份而不住在某一个阶段里**：探路解一个查证类决策、查清现状答一批题目、`mmw-fix` 定一个根因，用的是同一门手艺。写在其中一处，另外两处要用就得跨文件引用，很快会漂成好几套。

**分岔只有一个，在最后**：怎么查、回哪三节、六个词、假设怎么排，主线程和 `scout` 做的事一模一样，正文从头到尾不提角色。收活与向用户开口是查完之后的事，`scout` 两样都做不了，所以「查完之后」那节才需要问一句你是哪一个。曾经把 `references/verify.md` 的路标写在「回什么」那节末尾——那时候一条回执都还没有，主线程点过去也没东西可筛。

**分流写在这一份里，外面点名字的地方一律不管**：调用方替这一份做内部路由，它内部一改，外面几处全跟着错。

**回哪儿靠 `phase`，不靠这一份点名**：探路、查清现状、`mmw-fix` 三处都会进来，这一份认不出这次是谁调的；主线程查完一轮，会话里已经堆了几十条工具回执，也未必还记得。`phase` 是盘上现成的锚点，读一下就知道回哪一份——不必在这里写「你要是从探路来的就回探路」那种三选一。

**来源**：上游 `vendor/mattpocock-skills/skills/engineering/diagnosing-bugs`——Phase 1 整节（这一步就是手艺本身、造信号的办法、磨它的三个方向、非确定性 bug 提高复现率的手段、一条已经跑过的命令当完成判据、造不出来时向用户要哪三样），加上它 `scripts/hitl-loop.template.sh` 原样搬进本份 `scripts/`；Phase 3 的可证伪假设与一次提 3 到 5 个。上游十种造法里，浏览器脚本与 property/fuzz 循环没单列——前者并进「搭一次性最小环境」，后者在「时有时无的 bug」那段里。`codebase-design` 的 `SKILL.md`（词汇表、深浅、三个判据）与 `DEEPENING.md` 的依赖四类。旧插件两份 investigate workflow 提示词里的回执要求。

**上游把 Phase 1 称作「这份技能本身」，这里照搬这个分量**：先造信号、再提假设的先后不能倒过来，没有信号就编假设是它最要防的事。曾经把这一步写成「判断这个 bug 能不能稳定复现」，主动造成了被动判断，理由是「取证只读做不到」——真正做不到的只有 `scout`，主线程在自己的工作树里什么都动得了。

**造信号那一套要动工作树，为什么还留在这一份**：`scout` 确实做不了，但主线程做得了，而且它在 `mmw-investigate` 与 `mmw-fix` 两处都会遇到同一件事。曾经按「只读做不做得到」把这套办法劈成两半、重的那半搬去 `mmw-fix`，结果主线程要跨两份文件才拼得齐一套办法。整块留在这里，标明是主线程的活，`scout` 读到那一节自己跳过。

**为什么不给 `scout` 开写权限，好让它也能造**：一个 bug 只需要一个信号，派几个人各造一个是白费；`scout` 的结论本来就要主线程逐条亲验，让它改代码得逐行验，比自己写还贵；派发那边还规定每个能写文件的角色单独一棵工作树，并行几个就是几棵树要收拾。派出去的活是「查某一条线索」，回来的是事实。

**没摘的**：`codebase-design` 的深浅示意图与「设计接口时问自己能不能减少方法数」（设计动作）；`DEEPENING.md` 除依赖四类之外的部分——怎么把浅模块合深、接缝纪律、replace-don't-layer 的测试策略（都是重构动作，归 `mmw-design` 与 `mmw-build`）；`DESIGN-IT-TWICE.md` 整份（派几个子代理各设计一版接口再比，是设计动作，归 `mmw-design`）。`diagnosing-bugs` 的 Phase 2 最小化、Phase 4 插桩、Phase 5 修复与回归测试、Phase 6 收尾——都要写盘或反复改，归 `mmw-fix` 与 `mmw-build`。`improve-codebase-architecture` 整份不用：它产出重构建议，撞取证不判定；且它 `disable-model-invocation: true`，子代理调不动。

**三样东西的清单为什么不沉进 `references/`**：只有三行，开一份文件让人跳过去，跳转成本高过它自己。够一份 `references/` 的判据是分量——`verify.md` 是两道工序加一张表。
