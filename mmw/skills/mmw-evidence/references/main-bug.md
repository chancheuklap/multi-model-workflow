# 主线程：查一个 bug 的根因

**谁读**：主线程，这次要定一个坏行为的根因。`scout` 不读这一份——造信号要改文件、切版本，它做不了。

## 先造一个会变红的信号

**这一步就是这门手艺本身，剩下的都是机械劳动。**手上有一个会为这个 bug 变红、修好就转绿的信号，你就能找到原因；没有这个信号，盯着代码想原因是白费。力气不成比例地花在这里：使劲想办法，别放弃。

**这件事你自己做，不派 `scout`**：它改不了文件、切不了版本；而且一个 bug 只需要一个信号，派几个人各造一个是白费。派出去的活是「查某一条线索」，回来的是事实。

你手上有自己的工作树，下面这些都做得到，从轻到重试：

1. 拿 curl 或一段 HTTP 脚本打一个跑着的开发服务器，看它回什么。
2. 用固定输入跑一次命令行，把输出跟已知正确的结果比。
3. 从日志和提交历史里找那条会随 bug 一起出现、修好就消失的记录。
4. 写一条会为这个 bug 变红的测试，或者搭一个一次性的最小环境，把出 bug 那条路径单独跑起来。
5. 存一份抓下来的真实请求或事件，脱开界面回放它。
6. bug 是在两个已知状态之间冒出来的，切到旧版本跑同一个输入、diff 两边的输出；两头都清楚就把「切到状态 X，跑一次，看结果」写成一条命令交给 `git bisect run`。
7. 非得有人点鼠标才出得来的，把 `${CLAUDE_PLUGIN_ROOT}/skills/mmw-evidence/scripts/hitl-loop.template.sh` 复制一份、改成这次要用户走的步骤，让他跟着提示做，脚本会把他的回答按 `键=值` 打出来给你接着用。人当手，你当脑。

**造出来了就磨它**：跑得更快（缓存准备工作、跳过无关初始化、缩小测试范围）、更尖（断言用户说的那个具体症状，不是「没崩」）、更确定（钉住时间、固定随机种子、隔离文件系统、冻住网络）。三十秒还时灵时不灵的信号跟没有差不多，两秒钟每次结论都一样的信号是另一回事。

**这个 bug 时有时无**：要的不是干净复现，是把复现率拉高到能查。触发一百次、并行跑、加压、缩窄时间窗、往可疑的地方注入 sleep。一半的概率能查，百分之一不能。

**这一步算干完的判据**：你说得出一条命令，而且已经真跑过至少一次，把命令和它的输出一起记下来。这条命令要走的是出 bug 的那条路径、断言的是用户说的那个具体症状（不是「没报错」），每次跑结论一样，几秒钟出结果。那条命令连同输出就是这个 bug 最硬的出处。

## 信号有了，再提假设

一次提 3 到 5 个假设并排序——第一个看着像的会把你锚死。每个假设写成一句可证伪的预测：「如果是 X 导致的，那么改 Y 会让它消失、改 Z 会让它更严重。」说不出预测的是感觉，磨尖它或者丢掉它。然后逐个排除，用代码、日志、提交历史找反证；排掉哪一条、凭什么排掉，都记下来。

## 信号始终造不出来

记下这个 bug 没能复现，把已经试过的每一条路径逐条列出来。没有信号就编假设是这门手艺最要防的事，到此为止。

把那份路径清单给用户看，向他要下面三样里的一样：

- 一个能复现的环境
- 一份捕获的产物：HAR、日志转储、core dump、带时间戳的录屏
- 往生产环境加临时埋点的许可

三样都拿不到就停在这里，不接着猜。

## 查完之后

**读 `.mmw/task.json` 的 `phase`，回那一份技能接着走。**查了一轮下来记不清自己是从哪儿进来的，`phase` 里存的技能名就是答案。事实落到哪个文件，由那一份定。
