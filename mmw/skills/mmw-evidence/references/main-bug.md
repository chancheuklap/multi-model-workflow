# 主线程：查一个 bug 的根因

**谁读**：主线程，这次要定一个坏行为的根因。`scout` 不读这一份——造信号要动工作树，只有你动得了。

阶段技能会把你直接送到这里，所以本技能 `SKILL.md` 开头那两条先补上：取证不判定，以及一条事实该怎么记。

## 先造一个会变红的信号

**这一步就是这门手艺本身，剩下的都是机械劳动。**有一个会为这个 bug 变红、修好就转绿的信号，你就能找到原因；没有这个信号，盯着代码推测原因没有意义。时间要不成比例地投入在这里：反复尝试，不要提前放弃。

**这件事你自己做，不派 `scout`**：它没有修改文件的权限，又与你共用这棵工作树，切换版本会把你正在使用的代码一起切走；而且一个 bug 只需要一个信号，派几个角色各造一个是重复劳动。派出去的任务是「查某一条线索」，交回来的是事实。

你有自己的工作树，下面这些都做得到，从轻到重依次尝试：

1. 用 curl 或一段 HTTP 脚本请求一个运行中的开发服务器，看它返回什么。
2. 用固定输入执行一次命令行，把输出与已知正确的结果对比。
3. 从日志和提交历史里找那条随 bug 一起出现、修好就消失的记录。
4. 写一条会为这个 bug 变红的测试，或者搭一个一次性的最小环境，把出 bug 的那条路径单独运行起来。
5. 保存一份抓取到的真实请求或事件，脱离界面回放它。
6. bug 是在两个已知状态之间出现的，切换到旧版本运行同一个输入、对比两边的输出；两端都明确就把「切换到状态 X，执行一次，看结果」写成一条命令交给 `git bisect run`。
7. 必须由人操作界面才能触发的，把 `${CLAUDE_PLUGIN_ROOT}/skills/mmw-evidence/scripts/hitl-loop.template.sh` 复制一份、改成这次要用户执行的步骤，让他跟着提示操作，脚本会把他的回答按 `键=值` 打印出来供你继续使用。用户负责操作，你负责判断。

**信号造出来之后要打磨它**：更快（缓存准备工作、跳过无关初始化、缩小测试范围）、更精确（断言用户描述的那个具体症状，不是「没有崩溃」）、更稳定（固定时间、固定随机种子、隔离文件系统、断开网络）。三十秒还时灵时不灵的信号与没有信号差别不大，两秒钟每次结论都一致的信号才有价值。

**这个 bug 时有时无**：要的不是完全干净的复现，而是把复现率提高到足以调查。触发一百次、并行执行、施加压力、缩小时间窗口、在可疑位置注入 sleep。二分之一的概率可以调查，百分之一不行。

**这一步完成的判据**：你说得出一条命令，而且已经实际执行过至少一次，把命令和它的输出一起记录下来。这条命令要走出 bug 的那条路径、断言用户描述的那个具体症状（不是「没有报错」），每次执行结论一致，几秒钟返回结果。那条命令连同输出就是这个 bug 最可靠的出处。

## 信号有了，再提假设

一次提出 3 到 5 个假设并排序——第一个看起来成立的会把你锚定住。每个假设写成一句可证伪的预测：「如果是 X 导致的，那么改动 Y 会让它消失、改动 Z 会让它更严重。」说不出预测的是直觉，把它表述精确或者放弃它。然后逐个排除，用代码、日志、提交历史寻找反证；排除了哪一条、依据是什么，都记录下来。

## 信号始终造不出来

记录这个 bug 没能复现，把已经尝试过的每一条路径逐条列出。没有信号就编造假设，是这门手艺最需要防止的事，到此为止。

把那份路径清单交给用户，向他申请下面三样中的一样：

- 一个能复现的环境
- 一份捕获的产物：HAR、日志转储、core dump、带时间戳的录屏
- 在生产环境添加临时埋点的许可

三样都得不到就停在这里，不继续推测。

## 查完之后

**读 `.mmw/task.json` 的 `phase`，返回那一份技能继续执行。**调查一轮下来记不清自己是从哪里进来的，`phase` 里存的技能名就是答案。事实写进哪个文件，由那一份技能规定。
