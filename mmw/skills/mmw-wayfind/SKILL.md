这个阶段只产决策，不产交付物、不写码。探的是怎么走到目的地，不是走。产生「已经可以动手了」的冲动就是探路完成的信号，交给下一个阶段。

## 两份文件

都落进 `docs/design/<任务名>/wayfind/`，随分支提交。

**决策地图** `map.md`，是索引，四节：

- **目的地**：一段话写清走到哪算到——交出一份能接手的设计？锁死一个技术选型？把某个模块就地改造完？目的地塑形后面每一个决策。
- **已决**：一个决策一行，结论摘要加文件链接。
- **可解的那批**：挡它的决策都解开了的，现在能领。顶上另记一行正在解哪个，跨会话靠这行接上。
- **迷雾**：知道后面还有事要定、但现在连问题都问不准的。判据是这个问题能不能精确表述出来，不是能不能回答。

细节只住决策文件，地图不复述。

**决策文件** `d-<编号>-<名字>.md`，一决策一份，五部分：问题 / 为什么挡路 / 候选答案与各自的取舍 / 结论 / 证据（`文件:行号` 或链接）。引用它用决策的名字，不裸写编号。

## 起图

1. 命名目的地，写进地图。
2. 当下能精确表述的问题全部建成决策文件，编号从 `d-01` 起。表述不准的留在迷雾区，不硬编成问题。
3. 第二遍连「谁挡谁」，算出可解的那批。

## 每轮

1. 读地图，从可解的那批里领一个。一轮一个。
2. 按它的类型走：

| 类型 | 怎么解 |
| --- | --- |
| 查证 | 派 `scout` 去查，回来的证据回源码亲验。几个可以并行派 |
| 原型 | 做一版给用户看，走 `mmw-prototype` |
| 追问 | 跟用户一问一答解开，一次只问一个，每问附上你的推荐 |

追问是默认那一类。

3. 解开就落盘：结论写进那份决策文件，地图已决区加一行，重算可解的那批。解开的判据是用户确认双方理解一致。
4. 前置解开之后，迷雾里能精确表述的问题转成新决策文件，编号续排，连边。
5. 撞到该做、但不属于这次目的地的事，记进 `.mmw/sidelines.md`，不留在迷雾里。

## 停

可解的那批空了，且剩下的迷雾经用户确认不挡路。把从现在到目的地怎么走写成一句话放进地图顶部，连上下一个阶段该查清的问题清单。

## 线下 · 不是技能内容

**来源**：`plugin/skills/orchestrate/references/wayfind.md`；上游 `mattpocock/skills` 的 `wayfinder`。

**没搬上游的**：整套 issue tracker 承载——地图是打了标签的 issue、决策是子 issue、认领靠自己给自己派单、挡路关系用 tracker 的原生依赖字段。我们的产物是随分支走的 Markdown；「可解的那批」也因此去掉「未认领」这个条件，单主线程没有认领这回事。上游还留了个口子，地图的 Notes 里可写明本次允许顺手做交付物——不要，真要动手敲 `/mmw-next` 跳格。上游的「范围外」单列一区，我们并进已有的 `.mmw/sidelines.md`。

**没搬旧插件的**：`handoff` 引擎调用与三个结论词。
