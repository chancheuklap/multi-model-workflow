发起一轮审查。**审查方法论不在本文**，在 `mmw-reviewer` 技能里。你不读它，也不转述。

## 六道审

| 哪一道 | 什么时候发起 | 几个视角（任务名） | 谁去审 | 是不是关卡 |
| --- | --- | --- | --- | --- |
| ① spec 审 | spec 写完、自检过了，给用户看之前 | 设计内容审、项目对齐审 | 两个视角都派另一个模型 | 不是。findings 连同你的处置一起给用户看参考 |
| ② plan 审 | 全部 plan 写完、主 agent 验证过、跨 plan 合同回填完之后，发起一次 | 覆盖质量审、合规交叉审 | 两个视角都派另一个模型 | 是 |
| ③ 逐份验收 | 一个工人交回它那份活 | 不分视角 | **你自己**，判据见本文「③ 逐份验收」一节 | 是。不过这一关不合并回任务分支 |
| ④ 合同门 | 全部 plan 合并回任务分支之后，一次 | 不分视角 | **你自己**，判据见本文「④ 合同门」一节 | 是 |
| ⑤ final 终审 | 全部 ticket 落地、合同门过了 | 对照终审、独立终审、编码规范审 | 每个视角各派两个模型 | 是 |
| ⑥ 合并集成审 | 几条并行分支要合到一起 | 不分视角，七个角度 | 两个模型各派一个，各走全套 | 是 |

**红线是每一道审至少有一个视角的审查者跟作者不是同一个模型。** 上表「谁去审」那一列按这条红线落成角色名：

| 这一道审的东西谁写的 | 派哪个角色 |
| --- | --- |
| spec、map、调查综合——你自己定稿的 | `reviewer-gpt` |
| plan、代码——工人写的 | `reviewer-claude` |
| 要两个模型各一个的（⑤ final、⑥ 合并集成审） | 两个角色各派一个，同一份 brief |

模型和档位由 `mmw dispatch` 从仓库根的 `.mmw.json` 取，你不指定。

## 1. 确定被审的东西

| 审哪一道 | 钉什么 |
| --- | --- |
| ① | 那份 spec 的路径 |
| ② | plan 目录 `docs/plans/<slug>/` 的路径。**整批发起一次，不逐份发起** |
| ⑤ | 一个固定点，加 `git diff <固定点>...HEAD`（三个点，比的是分叉点）。固定点通常是 `git merge-base HEAD <父分支>` |
| ⑥ | 合并后的 `HEAD`，加各条分支的分叉点 |

用户直接叫你来审、又没说固定点的，问他要。**复审时的固定点不是他第一次说的那个**，见第 8 步。

往下走之前先确认它解析得出来（`git rev-parse`），而且 diff 非空。

## 2. 给每个视角备齐材料

审查者只拿它这个视角判断得上的材料。**多给反而有害**：独立终审那个视角要是拿到 spec 和 plan，它就变成第二个对照终审。

| 任务名 | 这个视角的 Source |
| --- | --- |
| 设计内容审 | 这份 spec、走查过的原型产物（`docs/prototypes/<slug>/`） |
| 项目对齐审 | 这份 spec、走查过的原型产物（`docs/prototypes/<slug>/`），另加领域文档（跑 `mmw domain path` 取落点，多上下文的仓库备这次要碰的那几份子上下文）与这块地方的 ADR |
| 覆盖质量审 | spec（含回填后的 `## Cross-Plan Contract Anchors`）、原型产物、全部 ticket、全部 plan |
| 合规交叉审 | spec（含回填后的 `## Cross-Plan Contract Anchors`）、原型产物、全部 ticket、全部 plan |
| 对照终审 | spec、全部 plan、diff 范围、走查过的原型产物（`docs/prototypes/<slug>/` 里选中的那一版） |
| 独立终审 | **只有 diff 范围** |
| 编码规范审 | diff 范围、仓库自己写下来的编码标准文件；仓库没有就明写「本仓库没有写下来的标准」 |
| 合并集成审 | 各分支的 spec、合并后全貌的 diff 范围、之前的冲突解决记录 |

spec 在哪按这个顺序找：这个分支上的 `docs/specs/<slug>/<slug>.md`；提交信息里引用的 issue（按 `docs/agents/issue-tracker.md` 取）；用户当参数传进来的路径。都找不到就问用户。他说没有，就只保留不要 spec 的两个视角——独立终审和编码规范审——其余视角全部撤掉，并在报告里说明。

**路径一律是被审仓库里的路径。** 派发前逐个确认它们真的存在，缺了当场报错。

## 3. 确认方法论装了

跑 `mmw doctor`，它会告诉你方法论装没装。没装就先跑 `/mmw-dispatching-agents` 旁边的 `install-agent-skills.sh` 装，再派。

## 4. 组装提示词，派发

提示词就四行，**不夹带方法论**：

```
任务名：<上表里的任务名，一字不差>
审什么：<被审对象>
Source：<这个视角的材料，一行一个；没有写「无」>
复审：<上一轮审查记录的路径；首轮写「否」>
```

再加一句告诉它去哪读方法论：跑 `mmw skill-path <角色>` 取路径，有输出就写那个路径，没有输出说明这个宿主自己会把方法论送到位，这句省掉。**同一个视角派给两个角色时，四行内容一模一样**，只有这句路径不同。

写到 `.reviews/<slug>-<哪一道>-<轮次>-<任务名>.prompt.md` 再从那里派（先 `mkdir -p .reviews`，轮次从 1 起）。派发机制按 `/mmw-dispatching-agents`，一条消息里全部发出去，它们并行跑、互不通气。

## 5. findings 存盘

把每个审查者交回的东西**原样**抄进 `.reviews/<slug>-<哪一道>-<轮次>.md`，按任务名分组。不要重写，不要摘要。文件顶部记下固定点的提交号。

审查者交回的是 `needs-redirection` 或 `needs-context`，不是 findings：

| 收到 | 怎么办 |
| --- | --- |
| `needs-redirection` | 停。交给用户重新框定，不要自己改产物绕过去 |
| `needs-context` | 看它缺什么。是你没给全就补齐重派这个视角；是产物里真的没有这份东西，那本身就是一条 finding |

## 6. 逐条判定

先按 `/mmw-verifying-agent-output` 验证每一条的出处，验证不出来的标 `needs-evidence`。

**条目多的时候把取证那一半派出去。** 派法和抽检的规矩在 `/mmw-verifying-agent-output` 的「取证可以派，判定不可以」一节。判定不派——下面那两问和五个处置词全是你的活。

验证过的每条再过两问：

1. **不修会伤到谁、在什么场景？** 说不清影响面的，不能当关键项采信。
2. **这轮花预算修，还是挪出去？**

然后标一个处置词。这五个词写英文，审查记录文件里当机器可扫的标记用：

| 处置 | 含义 | 驱动返工？ |
| --- | --- | --- |
| `accepted` | 成立，且本轮值得修 | 是——唯一能驱动返工的 |
| `rejected` | 不成立，或审查者误读 | 否，写一句理由 |
| `duplicate` | 与另一条重复 | 否，指向保留的那条 |
| `needs-evidence` | 可能成立，但没验证出出处 | 否，补证之前不修不争 |
| `waived` | 可能成立，但过度设计、收益太低或超出本次范围 | 否，理由必填 |

几个审查者报同一件事，合并成一条处置。**同一个视角两个模型都派了的，把两个模型的 findings 并排对**：只有一个模型报出来的重点验证，两个模型同报的可信度高。

搁置的按影响面分成两种：说得清影响面的，开一张 GitHub issue 打 `needs-triage`（标签词汇见 `docs/agents/triage-labels.md`），issue 就是它的审查记录，也是交给用户的通道；纯品味、没有当前用户路径的只写进本次报告，不开 issue。

**搁置项不打断你。** 判成 `waived` 或者开成 issue 的，记下来接着判定其余各条，不要停下来问用户。本文「下一步」一节里标「停」的那些情况仍然要停。

## 7. 报告

按任务名分节呈现，每条 finding 都带着它的处置词，包括被判 `rejected` 的那些。**不要跨视角合并或者重排。**

每个视角末尾给出这个视角报了几条、采信几条，以及这个视角里最严重的那条采信项。不要跨视角评出一个总冠军。最后加一行讲搁置的：搁的是什么、现在由哪张 issue 收着。

⑥ 合并集成审另外要求七个角度各一行结论，原样带上。

## 8. 复审

采信项修好、分支回来时：

- 固定点变成上一轮的 `HEAD`，那一轮的审查记录文件顶部记着它。审查者只看这次修复的 diff。
- 提示词的「复审」那一行填上一轮审查记录文件的路径。
- 已经标成 `rejected`、`duplicate` 或 `waived` 的，没有新证据不许再提。

## ③ 逐份验收：你自己做

一个工人交回它那份活时，你当场亲手验证三关。**三关都过才允许合并回任务分支。**

1. **做漏没有** —— 派给它的那份东西（ticket，有 plan 那一层的话是 plan）每条验收标准真达成了吗。跑验收命令、读 diff，不认「我做完了」。
2. **测试达不达标** —— 工人写的测试它自己说了不算。按 `mmw-tdd/quality-bar.md` 的合入标准逐条验证，加上目标仓库根 `TESTING.md` 补的本仓库事实。不达标就打回重写。
3. **有没有偏离** —— 落地有没有跑偏它上游那份东西的意图、合同、边界。

工人交回的四档怎么读，在 `/mmw-verifying-agent-output`。工人卡在派给它的那份东西与代码互相矛盾上，这件事交给用户。

### 三关不过时的返工升级策略

有一关不过就写修复指令打回，每一轮修复配一次重新验证——只验证这一轮改动碰到的地方，不重走全部三关。轮次按这条曲线走：

| 第几轮 | 派谁 |
| --- | --- |
| 一到三轮 | 再派一个 `worker`。上一轮那份 brief 原样带上，后面接这一轮的修复指令 |
| 四、五轮 | 改派 `worker-high-risk` |
| 第五轮还没过 | 停止返工，由你判定 |

每一轮都是一次新的派发，上下文不继承——所以每一轮的 brief 都要自包含。

第五轮还没过时先判这一关挡不挡验收：测试写法差一点但行为是对的，不挡；行为不对或者合同破了，挡着。两种情况的处置见本文「下一步」一节。**不做第六轮。**

## ④ 合同门：你自己做

全部 plan 合并回任务分支之后跑一次，**只验证一件事**：spec 的 `## Cross-Plan Contract Anchors` 一节里每条跨 plan 合同，在合并后的代码里真兑现了。

- 提供方声明的接口、类型、端点、数据结构真存在——grep 到定义，给出 `文件:行号`。
- 消费方真按那个接口对接，调用点的签名对得上。
- 合同版本号一致；新字段配套的迁移在位；新增的可被外部引用之物入了登记。

**grep 不到行号就不算兑现。** 这一道不做主观代码评审。

上面三样全是机械查找，**合同条数多的时候把取证派出去**：给它合同清单和目标仓库根的绝对路径，让它逐条 grep 定义、抄回 `文件:行号` 加原文，找不到的写「找不到」。派法在 `/mmw-verifying-agent-output` 的「取证可以派，判定不可以」一节。**判「兑现了没有」仍然是你的活**，尤其是「找不到」那几条——它可能只是没搜对名字，你要自己再搜一次才能判成落地漏了。

没有跨 plan 合同（只有一份 plan，或者那一节写明了无），把这件事连同你据以确认的位置一起记下来，不要跳过不写。

## ⑥ 合并集成审：先解冲突，再发起审查

几条并行分支要合到一起时走这一道。**冲突解完才发起审查。**

解冲突五步：

1. **看清现状**：git 历史，以及哪几个文件在冲突。
2. **查清每一处冲突两边各自要做什么**：读提交信息、PR、原始 issue，弄清两边为什么这么改。**按 `/mmw-research` 的内部方向派出去**，一条分支一个 subagent，题目是「这条分支在这几个冲突文件里想做成什么」，交回的是每条分支一段意图。收回来按 `/mmw-verifying-agent-output` 验证。
3. **逐块解**。双方的意图都保住；确实不兼容的，选符合这次合并目标的那一个，并把这个取舍记下来——解完冲突发起审查时要连同各分支的 spec 一起交给审查者。不发明新行为。一定要解出来，不用 `--abort`。
4. **跑这个项目自己的检查**：类型检查、测试、格式化。合并弄坏的当场修。
5. **完成合并**：暂存、提交。在 rebase 的那条路上继续到所有提交都 rebase 完。

合并完成之后回到本文开头的第 1 步到第 8 步发起审查，两个审查者各走全套七个角度。解冲突第 3 步记下的那些取舍，连同各分支的 spec 一起给它们。

## 下一步

| 情况 | 下一步 |
| --- | --- |
| 判定完了，一条 `accepted` 都没有 | **移交**：回到把你叫起来的那个技能，由它决定往下走 |
| 有 `accepted` 的 findings | **移交**：回到调用方，由它把这些打包成一张修复 ticket 派给新工人；修完再回本技能第 8 步复审 |
| 用户直接叫你来审，没有调用方 | **停**：报每个视角各报了几条、采信几条、最严重的是哪一条，让他定这一轮修不修 |
| 第 1 步的固定点解析不出来，或者 diff 是空的 | **停**：说清是哪一种，让用户重新给 |
| 收到 `needs-redirection` | **停**：把审查者说的「哪里可疑、建议怎么重新框定」原样交给用户 |
| 收到 `needs-context`，且缺的东西产物里真的没有 | **自己继续**：把这件事本身记成一条 finding，接着判定其余各个视角 |
| 第 3 步发现方法论没装 | **自己继续**：跑 `/mmw-dispatching-agents` 旁边的 `install-agent-skills.sh` 装好再派，不要改成把方法论粘进提示词 |
| ③ 三关有一关不过，返工还在前五轮内 | **自己继续**：按返工升级策略打回——前三轮派 `worker`，四五轮改派 `worker-high-risk`，每一轮的 brief 自包含。别合并 |
| ③ 返工满五轮还不过，但这一关不挡验收 | **自己继续**：记入待办，开 issue 打 `needs-triage`，别做第六轮 |
| ③ 返工满五轮还不过，而且确实挡着 | **停**：报是哪一关、五轮各自改了什么，交给用户 |
| ④ 有合同 grep 不到行号 | **停**：报是哪条合同、提供方或消费方缺在哪 |
| ⑥ 解冲突时两边意图确实不兼容，而这次合并的目标不足以判 | **停**：报是哪一处、两边各自要做什么，让用户定保哪一个 |
| 同一条 `accepted` 修过两轮还在 | **停**：报这条修了两轮还在，并说出你的判断——是修错了地方，还是当初不该采信 |
