## ③ 逐份验收：你自己做

一个 `worker` 交回它写的代码时，你当场亲手验证三关。**三关都过才允许合并回任务分支。**

1. **做漏没有** —— 派给它的那张 ticket（有 plan 那一层的话，还有那份 plan）每条验收标准真达成了吗。跑验收命令、读 diff，不认「我做完了」。
2. **测试达不达标** —— 它自己说测试写好了不算。按 `mmw-tdd/quality-bar.md` 的合入标准逐条验证，加上目标仓库根 `TESTING.md` 补的本仓库事实。不达标就打回重写。
3. **有没有偏离** —— 落地有没有跑偏 ticket 与 plan 写下的意图、合同、边界。

`worker` 交回的四档怎么读，在 `/mmw-verifying-agent-output`。它卡在 ticket 或 plan 与代码互相矛盾上，这件事交给用户。

### 三关不过时的返工升级策略

有一关不过就写修复指令打回，每一轮修复配一次重新验证——只验证这一轮改动碰到的地方，不重走全部三关。轮次按这条曲线走：

| 第几轮 | 派谁 |
| --- | --- |
| 一到三轮 | 再派一个 `worker`。上一轮 task 的路径与目标保留，后面接这一轮的修复指令 |
| 四、五轮 | 改派 `worker-high-risk` |
| 第五轮还没过 | 停止返工，由你判定 |

每一轮都是一次新的派发，上下文不继承——所以每一轮 task 都要重新写清路径与修复目标。

第五轮还没过时先判这一关挡不挡验收：测试写法差一点但行为是对的，不挡；行为不对或者合同破了，挡着。挡与不挡各自的处置在本文「下一步」一节。**不做第六轮。**

## ④ 合同门：你自己做

每份 plan 对应的代码都合并回任务分支之后跑一次，**只验证一件事**：spec 的 `## Cross-Plan Contract Anchors` 一节里每条跨 plan 合同，在合并后的代码里真兑现了。

- 提供方声明的接口、类型、端点、数据结构真存在——grep 到定义，给出 `文件:行号`。
- 消费方真按那个接口对接，调用点的签名对得上。
- 合同版本号一致；新字段配套的迁移在位；新增的可被外部引用之物入了登记。

**grep 不到行号就不算兑现。** 这一道不做主观代码评审。

上面三样全是机械查找，**合同条数多的时候把取证派出去**：给它合同清单和目标仓库根的绝对路径，让它逐条 grep 定义、抄回 `文件:行号` 加原文，找不到的写「找不到」。派法在 `/mmw-verifying-agent-output` 的「取证可以派，判定不可以」一节。**判「兑现了没有」仍然是你的活**，尤其是「找不到」那几条——它可能只是没搜对名字，你要自己再搜一次才能判成落地漏了。

没有跨 plan 合同（只有一份 plan，或者 spec 的 `## Cross-Plan Contract Anchors` 写明「无跨 plan 共享合同」），把这件事连同你据以确认的位置一起记下来，不要跳过不写。
