你已经决定了要派谁（比如落地一份计划要派 `executor`），这份讲怎么把它跑起来。**派谁、给它什么活，不在这份里**——那是各阶段技能的判断。

**这份是宿主适配层，换一家宿主整份重写。** `roles/` 那六份角色文件不动。

## 一次派发长什么样

以派一个落地工人为例，四步：

**一、打开它的角色文件** `roles/executor.md`，看头部两件事：它的 `model` 是谁家的（决定走下面哪条路），它的 `skills` 列了哪几份技能（这次提示词里要逐个点名让它读）。

**二、写提示词，落成一个文件。** 内容只做路由，不抄方法论：

```
读你已装的 mmw-worker、mmw-task-pack、mmw-testing、mmw-retrieval 这几份 skill，照它们走。
这次的活：落地 docs/plans/<任务名>/plan-2.md。
设计文档 docs/design/<任务名>/<任务名>.md，切片 docs/issues/<任务名>/issue-2.md。
工作树就是当前目录，从 <起点提交> 起算。
```

技能按名字叫就行，不给路径——安装时已经装进被派者那一侧，它自己找得到。**方法论正文一个字都不要复述**：复述就会出现两份说法，改了一处忘了另一处。

**三、派出去。** 模型是 GPT 家的走这条：

```
dispatch.sh run --role executor --cwd <工作树> --prompt <提示词文件>
```

只给角色名、在哪干、这次的活。模型、思考档、能不能写盘、可写边界，脚本自己从角色文件读。**不要自己拼命令行**：参数错一个是白跑一轮，权限参数拼错等于围栏失效。

模型是 Claude 家的（`reviewer-claude`、`scout`）改用宿主自己派子代理的工具，那两份已由插件清单注册，模型与工具白名单由宿主强制执行。

**一律起在后台**：审一轮、落地一份计划都常超过前台等待上限。

**四、它干完了，你验收。** 脚本回三样：会话号、退出码、它自己写的最后一条汇报。

**它的汇报不是信源。** 自己跑测试、自己读改动，再核一次它有没有越界：

```
dispatch.sh check --role executor --cwd <工作树> --since <起点提交>
```

干净回 0，越界回 3 并列出碰了哪些文件。要追问就拿会话号 `resume`，它的上下文还在，不用重讲一遍。

## 为什么分两条路

Claude Code 只能原生派自家模型的子代理。六份角色里模型是 Claude 家的两份走原生，另外四份是 GPT，本宿主派不了，只能在旁边起一个独立进程。

判断规则只有一条：看角色的 `model` 是不是本宿主自家的。

多模型宿主（Cursor、pi、Droid）不存在这个限制——那边六份全是原生角色，这份技能会短得多，派发脚本根本不需要。

## 三条纪律

**并行就是连着起几个。** 三份计划就把第三步敲三遍，各一个工作树。没有别的机制，脚本自己把会话记账分开。

**恢复会话不等于恢复围栏。** 续接时权限参数要跟首派一样，脚本已经处理，前提是你走脚本而不是自己敲。

**验收吃实证。** 跑测试、读改动、看越界检查的结果，三样都做。

## 装的时候是两半

模型专用宿主上这套东西装两处：主线程这一半由本宿主的插件清单装；被派出去那一侧要另装一次，否则它按名字找不到自己的技能。

跑 `scripts/install.sh` 装第二半。装哪几份不用维护名单——六份角色的 `skills` 字段合起来就是它，脚本自己读。`--check` 看装齐没有，`--uninstall` 拆掉。

没装或装漏了，派发脚本开工前会当场停下并指向它。多模型宿主没有「另一半」。
