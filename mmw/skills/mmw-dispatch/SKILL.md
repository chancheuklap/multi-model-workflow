六份角色都往同一个入口投：

| 干什么 | 怎么敲 |
| --- | --- |
| 派一个 | `scripts/dispatch.sh run --role <角色> --cwd <目录> --prompt <文件>` |
| 续接追问 | 同上，`resume` 加 `--session <会话号>` |
| 收工核越界 | 同上，`check` 加 `--since <起点提交>` |

**提示词只写这次的活。**要交代哪几样，读 `roles/<角色>.md` 那行「开工要拿到」，逐项填齐。

送到被派者手里的是四段，脚本按这个顺序拼，你写的那份落在最后：

```
你的角色是 <角色名>。

<角色文件正文：边界、开工要拿到什么、收工回什么>

先读你已装的这几份 skill，照它们走：<角色文件 skills 字段>

## 这次的活

<你写的 --prompt 文件全文>
```

前三段的字全在角色文件里，脚本一个字都不添。模型与沙箱档由脚本按角色文件钉死，不进提示词。

派原生角色时脚本回一个角色名，角色文件由宿主加载；提示词照同样写法写，开头点名它该读的几份技能（名单在角色文件 `skills` 字段）。

**派可写角色前先给它一棵工作树**：从任务分支分叉出 `.mmw/worktrees/<任务名>-<片名>`。验收过了 `git merge --no-ff` 合回任务分支，再清掉那棵树。只读角色不用建，在任务工作树里跑。

**一律起在后台。**并行就是连着起几个，各一棵工作树。

---

## 线下 · 不是技能内容

**这份属于适配层，换一家宿主整份重写。**

**为什么原生角色也要点名**：宿主的角色文件字段只保证被派者拿得到那几份，不保证它去读；无头那一侧连角色文件都看不见。点名是每家宿主都做得到的唯一一件事。

**`preview` 子命令不写进上面的表**：它只打印会送出去的提示词、不派发，用途是让空转脚本验生产路径上那个拼装函数本身，而不是重写一份副本来断言。主线程要知道该交代什么，直接读角色文件更快。

**为什么可写角色各一棵工作树**：派发脚本要求首派时工作树干净，几个可写角色挤同一棵会互相顶掉。

**为什么一律后台**：审一轮、落地一份计划都常超前台等待上限。

### 施工单

- **来源**：`plugin/scripts/worker.sh` 的 `dispatch` / `plan-dispatch` / `resume`、`plugin/scripts/review.sh` 的派发指南
- **保留**：后台起；恢复会话要重钉围栏；提示词纯路由不内联方法论；并行是连着起几个
- **删除**：把派发指南文本生成封进 shell（旧的 253 行大头）；审者分档矩阵；派发前先落盘一份指南再读回来
