派谁、给它什么活，是各阶段技能的判断，不在这份里。这里只讲怎么把它跑起来。

六份角色都往同一个地方投，你不用先判断走哪条路：

| 干什么 | 怎么敲 |
| --- | --- |
| 派一个 | `scripts/dispatch.sh run --role <角色> --cwd <目录> --prompt <文件>` |
| 续接追问 | 同上，`resume` 加 `--session <会话号>` |
| 收工核越界 | 同上，`check` 加 `--since <起点提交>` |

**提示词只写这次的活**：落哪份计划、审什么、读哪几份文档、从哪个提交起算。别的都不用写——让它读哪几份技能、用什么模型、能不能写盘，脚本从角色文件读。不要自己拼命令行。

派原生角色时也照这个写法，在提示词开头点名它该读的几份技能（名单在角色文件的 `skills` 字段）。

**一律起在后台**，审一轮、落地一份计划都常超前台等待上限。并行就是连着起几个，各一个工作树。

派出去之后怎么验收，看那一格自己的技能。

## 线下 · 不是技能内容

以下是建这份文件时的依据与备注：来源、取舍理由、设计成因。填方法论时用，照着干活时不用读。

**这份属于适配层，换一家宿主整份重写。**

**为什么原生角色也要点名**：宿主的角色文件字段只保证被派者拿得到那几份，不保证它去读；无头那一侧连角色文件都看不见。点名是每家宿主都做得到的唯一一件事。

### 施工单

- **来源**：`plugin/scripts/worker.sh` 的 `dispatch` / `plan-dispatch` / `resume`、`plugin/scripts/review.sh` 的派发指南
- **保留**：后台起；恢复会话要重钉围栏；提示词纯路由不内联方法论；并行是连着起几个
- **删除**：把派发指南文本生成封进 shell（旧的 253 行大头）；审者分档矩阵；派发前先落盘一份指南再读回来
