---
name: mmw-integrate
description: 把结果分支集成到当前任务分支。用于合并已完成分支、让未完成分支 rebase 到已推进的目标分支，或处理进行中的 merge 或 rebase 冲突。
---

开始前，遵守目标仓库 `AGENTS.md` 的领域上下文规则。

把几条结果分支集成到当前任务分支。当前任务分支是本轮唯一目标；主 agent 不切换工作目录，也不把结果直接合入仓库的默认分支。

当前已经存在 merge 或 rebase 冲突时，直接进入第 3 步。merge 读 [merging.md](merging.md)，rebase 读 [rebasing.md](rebasing.md)。

## 1. 记录现状

先确认 `mmw task state` 输出以 `bound` 开头，并记录当前任务分支和 `HEAD`。工作区有与集成无关的未提交改动时停下。

每条结果分支记录四项：

| 项目 | 取得方式 |
| --- | --- |
| 分支与报告 HEAD | 使用执行者交回的分支名和 HEAD SHA |
| 基点 | 使用派发时记录并由执行者交回的基点 SHA |
| 完成状态 | 检查 task 验收、主 agent 验证和终审记录 |
| 合同关系 | 检查一条分支是否提供另一条分支消费的数据模型、interface、迁移或序列化格式 |

先运行 `mmw result verify <结果分支> <HEAD SHA> <基点 SHA>`。任何一项与报告不一致时，不集成该分支。

## 2. 确定顺序与路线

| 结果分支状态 | 处理方式 |
| --- | --- |
| 已完成并通过终审 | 合入当前任务分支，读 [merging.md](merging.md) |
| 尚未完成，当前任务分支已经推进 | 在拥有该结果分支的任务中 rebase 到当前任务分支，读 [rebasing.md](rebasing.md) |

已完成的分支按合同依赖排序：提供方先合，消费方后合。没有合同关系时，按终审通过时间排序。顺序确定后逐条推进；如果依赖事实发生变化，停止本轮并重新排序。

## 3. 逐条推进

合入已完成分支时，运行：

```bash
mmw result integrate <结果分支> <HEAD SHA> <基点 SHA>
```

命令使用 `git merge --no-ff`，保留结果分支的提交历史。发生冲突时按 [merging.md](merging.md) 继续，不重新运行集成命令。

未完成分支需要跟上当前任务分支时：

[[mmw-host-action:continue-result-worktree]]

然后按 [rebasing.md](rebasing.md) 操作。该分支完成后交回新的 HEAD SHA；主 agent 重新运行 `mmw result verify`。

冲突处理遵守三条规则：

1. 先读取提交、issue 和 spec，确认双方意图。
2. 逐块保留双方兼容的行为；不兼容时只按本轮已确定的目标取舍。双方 primary source 和既定目标都没有要求的行为不得加入。
3. 每次推进后运行目标项目要求的检查。

冲突解决只组合已有意图，不发明新行为。若必须增加第三种行为才能让代码通过，现有目标不足以决定取舍，按“下一步”停止并交用户判断。

运行 `mmw path review`，把实质取舍写入命令返回目录的 `integration-<YYYY-MM-DD>.md`。同一天第二轮在日期后加序号。每条记录文件位置、双方意图、保留内容和理由。

完成条件：没有进行中的 merge 或 rebase；工作区干净；本轮应合入的分支都出现在当前任务分支历史中。

## 4. 决定是否发起集成审

| 本轮结果 | 处理方式 |
| --- | --- |
| 两条以上结果分支合入当前任务分支 | 发起 ⑥ 合并集成审 |
| 只让一条未完成分支跟上，冲突全部是相邻位置或 import 等机械冲突 | 不发起集成审 |
| rebase 或 merge 中对行为、合同、数据结构、迁移作了取舍 | 发起 ⑥ 合并集成审 |

需要审查时，固定点使用集成前记录的当前任务分支 `HEAD`，并附每条结果分支的基点和取舍记录。

⑥ 合并集成审是集成结果的终审。完成后在审查记录中登记 `终审提交`，不再发起 ⑤ final 终审。

下表准备移交下一技能时，先读 [`../mmw-start/phase-boundaries.md`](../mmw-start/phase-boundaries.md)，按顺序判断是否留在当前会话。自己继续和因 blocker 停下不触发阶段边界判断。

## 下一步

| 情况 | 下一步 |
| --- | --- |
| 集成完成且需要审查 | **移交**：`/mmw-review`，发起 ⑥ 合并集成审 |
| 合并集成审有采信项 | **自己继续**：把全部采信项合成一张修复 ticket，只派一次 `worker`；逐条验证修复和项目检查后登记 `修复提交` 与 `终审提交`，完成集成，不再审 |
| 集成完成且不需要审查 | **停**：报告已合入的分支、仍在工作的分支和当前任务分支 HEAD；按下面的宿主动作处理 worktree |
| 结果分支报告与 Git 状态不一致 | **停**：报告分支名、报告 HEAD、实际 HEAD 和基点 |
| 双方意图不兼容，现有目标不能决定取舍 | **停**：报告文件位置和双方意图，让用户决定 |
| 项目检查因本次集成失败且无法当场修复 | **停**：报告失败命令和引入失败的集成步骤 |
| 用户要求合入一条尚未通过终审的分支 | **停**：说明该分支缺少终审；先让它跟上当前任务分支，或先运行 ⑤ final 终审 |
