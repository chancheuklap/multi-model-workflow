# rebase：把一条没完成的分支挪到最新主线上

别的分支先进了主线，这条还没做完。走这一份让它跟上，跟上之后回它自己的 worktree 接着做。解冲突的三条方法论在 `/mmw-integrate` 第 3 步，这里只写 rebase 自己的机械。

**在这条分支自己的 worktree 里做**，不在主仓库。它没完成，主仓库的主线上不该出现它。

## 开始

```bash
git rebase <主线>
```

rebase 把这条分支相对分叉点的每个提交依次重放到新的基上。**一个提交解一次冲突**，所以一开始 `git status` 报的冲突文件不是全集，后面的提交会报出别的。

## 冲突时哪一边是哪一边

`ours` 是**已经在基上**的那一侧，`theirs` 是**正在被应用进来**的那一侧。这条规则跟 merge 是同一条，但 rebase 的基是主线，被应用的是你自己的提交——落到具体一边就跟 merge 相反：

| 标记 | merge 时指 | rebase 时指 |
| --- | --- | --- |
| `ours`、`<<<<<<< HEAD` 那一段 | 你自己的分支 | **主线** |
| `theirs`、`>>>>>>>` 那一段 | 要合进来的分支 | **你自己正在重放的那个提交** |

`<<<<<<< HEAD` 底下那段是主线的内容，不是你写的。按 merge 的直觉认边会把自己的工作当成外来改动舍掉，而且舍掉不报错。每一块都按本文「冲突时哪一边是哪一边」节内的标记表认一遍。

## 完成

解完当前这个提交的全部冲突块之后：

```bash
git add <解完的文件>
git rebase --continue
```

它会接着重放下一个提交。**重复到它报没有下一个为止**，那时 `git status` 不再显示 rebase 进行中。

**完成用 `git rebase --continue`，不用 `git commit`。** 在 rebase 中途跑 `git commit` 会成功、不报错、不告警，但 rebase 仍在进行中，分支引用一动没动，`HEAD` 停在 detached 状态。看着像做完了，实际这条分支还在原地。

同一处冲突在多个提交上反复出现时，开 rerere 让它重用你已经解过的：

```bash
git config rerere.enabled true
```

它只重用你自己在这个仓库里解过的同样冲突，不会替你做新判断。

## 检查跑在哪

全部提交重放完之后跑一次项目自己的检查。要求这条分支的每个提交都能单独跑通的（后面要按提交二分查问题），改用：

```bash
git rebase <主线> --exec "<项目的检查命令>"
```

它每重放一个提交就跑一次，某个提交上挂了就停在那里。

## 放弃的代价按阶段分

| 什么时候 | 放弃的代价 |
| --- | --- |
| rebase 还没完成（`git status` 显示进行中） | `git rebase --abort` 干净回到 rebase 前，工作区不留残留 |
| rebase 已经完成 | 历史已经重写。回退要从 `git reflog` 找 rebase 前那个提交再 `git reset --hard` 到它，属于会丢工作的动作，先按 Git 纪律确认 |

`/mmw-integrate` 的第 3 步要求解出来。判不出保哪一边时按 `/mmw-integrate` 正文「下一步」表对应行停下交给用户，并告诉他 rebase 正停在中途。

## 跟上之后

这条分支的历史被重写了。已经推到远端的，推送要用 `--force-with-lease`（它在远端被别人推进过时会拒绝，`--force` 不会）。**推送是对外发布的动作，要用户明确同意再推。**

没推过的分支不用管这一节，接着在这个 worktree 里做就是。
