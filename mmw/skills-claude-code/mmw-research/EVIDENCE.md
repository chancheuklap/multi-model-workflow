# 实测取证

本文件由主 agent 执行。

其他 research 回答的是"资料上写的是什么"。这一条回答的是"它在我们的负载、我们的数据、我们的账号下**实际**是什么样"。问题长这样：

- 那个服务撑得住我们的并发吗？
- 这三个候选哪个扛得住？
- 这个第三方接口实际返回什么，跟文档说的一样吗？
- 这个方案的延迟能压到多少？

只在**有一项决定被这条事实卡住**时走本文件。读文档、读源码或者跑一条只读命令就能答的，回 [MAIN.md](MAIN.md) 按普通 research 处理。

要验的是我们自己要写的那套东西成不成立（状态模型、界面、数据形状），这里就走错了，移交 `/mmw-prototype`。

## 1. 立计划

先按 [MAIN.md](MAIN.md) 第 0 节认领入口，再按它第 4 节拼出这次的 research 路径。scratch 路径按 MAIN.md 第 6 节取：调用方传了就用传入的那条，没传就按那一节的规则自己拼。

把计划写成 `<research 路径>/test-plan.md`，四栏：

| 栏 | 写什么 |
| --- | --- |
| 对象 | 测哪几个候选，各是什么版本、什么配置 |
| 口径 | 测什么指标，怎么测，跑几轮，用什么输入 |
| 通过判据 | 什么结果算它通过 |
| 真实环境需求 | 要什么账号、凭证、数据量、网络位置 |

**通过判据必须在跑之前写死。** 跑完再定判据，等于用结果反推结论。

## 2. 动手之前先问用户

下面任何一条成立时，先把要做什么、影响什么、花多少说清楚，等用户明确点头再动：

- 要用真实凭证
- 要连生产环境
- 要在真机上跑
- 会产生费用
- 会写入外部系统的数据

这一条不能跳过，入口是 `wayfinder:research` ticket 时也一样：ticket 免掉的是「要不要保存」的询问，免不掉对外部世界产生真实影响的操作。

## 3. 真实跑

探测脚本、过程截图、完整命令输出和跑出来的中间物，全部落在 `<scratch 路径>/runs/<本轮实测的短名>/`。短名按 `test-plan.md` 里被测的对象或口径取，单个路径段，字符规则同 [MAIN.md](MAIN.md) 第 4 节。这些不进 Git。

需要在浏览器里取证时：

浏览器取证优先用宿主自带的可控浏览器，保存相关状态的截图、DOM 和 console。宿主没有，就用项目已有的 Playwright 或 Puppeteer 入口。需要多轮测量或稳定断言时一律走脚本入口，不用交互式浏览器。改过 viewport 的，留下最后一份证据之后恢复默认。宿主和项目都没有入口时，记录一遍可重复执行的人工步骤——不为这次取证新装浏览器工具。

对象只有一两个时，你自己跑完。

对象有好几个、而且每个对象的探测都是**一条自成一体的只读命令**时，可以一个对象派一个 `investigator` 并行跑。task 按 [MAIN.md](MAIN.md) 第 2 节的四栏写，方向写外部方向，「读」那一栏加上这个对象在 `test-plan.md` 里的那一行。

派之前先对着这条探测确认一遍：它不施加负载、不需要多轮测量、不用真实凭证、不连生产、不花钱、不写外部系统的数据。这六条是 `investigator` 那边的硬边界，碰到任何一条它都会停下来把任务交回给你，白跑一轮。

派一个独立上下文的 `investigator`。它只读，不需要工作目录。
启动：后台执行 `mmw dispatch investigator`。把四栏 task 正文作为命令的标准输入。当前 task 属于 decision ticket 时，加 `--issue <当前 decision ticket 编号>`。命令返回 `mode: host-tool` 时，使用输出中的 `params` 调用对应宿主工具。

互不依赖的实例在同一条消息里一起启动，全部回来之后再汇总。

`investigator` 只交回命令原文和关键输出，不做判断，不写仓库文件。它交回之后，你把完整输出落进 `<scratch 路径>/runs/` 再往下走。

需要真实凭证、需要连生产、会产生费用或者会写入外部系统的探测，**不派 `investigator`**，由你自己在第 2 节拿到用户批准之后跑。

收回结果后，对照命令原文和关键输出打开出处确认。

## 4. 记台账

结论写成 `<research 路径>/report.md`。每一条结论都标出它的证据是哪一档：

| 档 | 是什么 |
| --- | --- |
| 一手实测 | 你自己按 `test-plan.md` 跑出来的。台账里写下精确命令、当时的环境和结果摘要 |
| 官方文档 | 第一方文档或源码写着的 |
| 二手 | 别人的测评、博客、问答 |

**说不出精确命令、说不出当时环境、或者结果没法复验的实测结论，标「待验」**，不能当结论用，也不能交给下游。

被否掉的候选也各留一条：它是什么、为什么否、证据在哪。下游据此知道这条路已经走过了。

台账正文写结论、精确命令、环境、结果摘要和证据出处。长输出不要内联进正文。只有**不能低成本重跑、而且直接支撑某条结论**的原始证据，才从 `scratch 路径` 提升到 `<research 路径>/raw/`；提升之前先去掉密钥、个人数据和与结论无关的内容，并在台账里逐条写清它支撑的是哪条结论。其余的留在 `scratch 路径`，交回结果之前清掉这次自己建的那些。

## 5. 保存与交回

**实测一律保存，不问用户。** 不走 [MAIN.md](MAIN.md) 第 5 节那个询问关卡：那一关问的是"这次查的东西值不值得留下来"，而实测在第 2 节已经让用户点过头、已经付出了真实成本，台账又是这批数字唯一能复验的记录。第 1 节和第 4 节写下的 `test-plan.md` 和 `report.md` 就在 `research 路径` 里，不要再回过头去问该不该建这个目录。

其余按 [MAIN.md](MAIN.md) 第 6、7 节执行。这次的 `README.md` 除了第 6 节要求的内容，还要写清：测了哪几个对象、通过判据是什么、哪些结论是一手实测、哪些标了「待验」。

跑完发现所有候选都没达到通过判据：报告测了哪几个、各自卡在哪条判据上。不要自己放宽判据。

| 情况 | 处理 |
| --- | --- |
| 台账已记完、保存已完成，而且有调用方等待 | 按 [MAIN.md](MAIN.md) 第 7 节交回，并附 `test-plan.md` 的精确路径 |
| 台账已记完、保存已完成，没有调用方等待 | 报告结论、证据档次、「待验」项和保存位置 |
| 实测结果要用户走查一套状态模型或几个界面候选才能继续 | 问要不要做 prototype，带上台账里的相关结论 |
