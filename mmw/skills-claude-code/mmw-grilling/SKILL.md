name: mmw-grilling
description: 用设计树把需求或决定谈成可执行的共同理解。用于新需求或改进尚未谈定，或其他技能遇到未决的产品或设计取舍。
---

用一棵会话内的设计树组织追问。每轮把当前 frontier 上的问题一起交给用户，收到这一轮的全部答案后再重算设计树。问到双方形成**能动手的共同理解**为止。

走主线时，能不能动手不凭感觉判。对照 `/mmw-to-spec` 的内容范围检查覆盖是否完整，但不要提前写 spec。被别的技能叫起来时，以调用方带来的问题是否形成共同理解为准。

## 取上下文

**事实归主 agent，决定归用户。** 在文件、工具、代码或外部资料里查得到的是事实。需要在几个可行方向之间取舍的是决定。不要拿事实问题消耗用户，也不要替用户回答决定问题。

| 上下文 | 何时读取 | 读取范围 | 不读取 | 向下传递 |
| --- | --- | --- | --- | --- |
| 当前实现 | 开问前 | `/mmw-research` 验证的相关代码、seam 和数据流 | 无关模块 | 验证后的事实；已保存且后续需要时再传 research 路径 |
| 领域文档 | 开问前 | `mmw domain path` 返回的相关 leaf | 无关 leaf | canonical 术语和领域约束 |
| ADR | 开问前 | `mmw domain dirs` 返回目录中的相关文件 | 无关 ADR | 当前决定必须遵守的约束 |
| 已有页面或 mockup | 涉及页面决定时 | 全部相关页面 | 无关页面 | 已验证的页面现状 |

主 agent 先直接读取已知入口、相关领域文档和 ADR。现状跨多个模块，而且需要从调用链、数据流或影响面等独立角度系统取证时，调用 `/mmw-research`。等待调查报告时继续建立设计树；只暂停依赖相应事实的叶节点，其余 frontier 可以进入第一轮提问。

需求涉及已有页面、mockup，或者用户必须看见界面才能决定时，等待相关 research 全部交回并完成关键出处验证，再把全部相关页面交给用户：

使用当前宿主已有的浏览器工具打开全部相关页面，并保留给用户走查。交给用户前保存每个相关页面的截图并记录出处。没有可用浏览器工具时，给出一条运行命令、全部页面地址和目标 viewport，等待用户反馈。

页面交给用户后，等待用户完成标记或给出反馈，再提出第一轮问题。

## 同时应用 domain-modeling

`/mmw-grilling` 和 `/mmw-domain-modeling` 默认成对运行。主 agent 在同一段对话中读取并应用 `/mmw-domain-modeling`，不要另开一条独立流程，也不要等追问结束后再补领域建模。

`/mmw-domain-modeling` 负责挑战 glossary、收紧术语、用边界场景检验概念、对照代码、当场更新拥有术语的 leaf，并用完整的三项判据决定是否提议 ADR。产品决定和实现决定留在对话与后续 spec 中，不写进领域 leaf。

## 建立设计树

设计树是本次对话的临时推理结构。它不写入文件、issue、领域文档或图谱，也不成为新的项目状态模型。

- 根节点是这次要谈成的计划、决定或想法。
- 分支表示必须作出的决定及其依赖关系。
- 未解决的叶节点表示还需要用户回答的决定。
- frontier 是依赖已经满足、现在可以回答的全部未解决叶节点。

开问前先根据用户原话、research 结果、领域文档和已有决定画出当前设计树。只保留足以判断依赖和遗漏的内容，不向用户倾倒内部推理过程。

每轮回答后重新计算设计树。新答案可以展开新分支、关闭已有分支，也可以证明原先的依赖关系分错了。依赖关系分错时，重新打开受影响的分支，不要把旧答案当成不可修改的状态。

## 按 frontier 分轮提问

- 默认一次提出当前 frontier 上的全部问题。同一轮的问题之间不能互相依赖。
- 等用户回答完这一轮，再更新设计树并提出下一轮。
- 用户只回答一部分时，保留未回答的问题。不要假装这一轮已经完成。
- 用户可以按编号回答整轮，不必复述问题正文。
- “不知道”、指出问题已经漂出范围、拒绝不合适的选项，或推回一个前提，都是有效回答。把这些回答更新进设计树，不把它们当成漏答。
- 用户明确要求一次只看一个问题时，只改变展示数量。设计树、frontier 和每轮重算的方法不变。
- 不设固定轮数上限。没形成共同理解就继续，不用轮数替代完成判据。
- 没到能动手之前不要开始实现。

每个问题都使用以下格式，并给出推荐答案：

```markdown
**Q1 — <问题标题>**

<问题正文和必要选项>

**推荐答案：** <推荐答案和简短理由>
```

## 对话中出现新的事实问题

问答开始后出现新的事实问题时，单个文件、符号、事实或一条命令能答完的由主 agent 直接查询。需要多个独立角度系统取证时调用 `/mmw-research`。只有依赖这条事实的叶节点暂停，当前 frontier 上的其余问题照常提出。

research 报告交回后，按 `/mmw-verifying-agent-output` 验证会改变问题或结论的关键事实。把验证结果放回设计树，再重新计算 frontier。research 不能替用户作决定。用户选择保存，而且后续 spec 依赖该 research 时，把 research 索引和精确文件路径纳入共同理解。

某条事实必须真实运行一个原型才能知道时，按本文「下一步」移交 `/mmw-prototype` 的 `EVIDENCE.md` 路径。只暂停依赖这条事实的分支。

事实只存在于另一位知识持有者那里，而且当前用户无法代答时，移交 `/to-questionnaire`。Questionnaire 只收集缺失事实，不替当前用户作产品决定。答案回来后放回设计树，重新计算 frontier。

## 完成判据

以下条件全部成立，才可以说已经形成共同理解：

1. 设计树的 frontier 为空。
2. 所有已发现的分支都已经访问，没有靠沉默假设关闭的分支。
3. 没有仍在等待的 research 或实测证据。
4. 走主线时，`/mmw-to-spec` 的内容范围都已有明确答案。这里只检查覆盖，不提前发布 spec。

达到这些条件后，向用户总结问题、约束、决定、取舍和未纳入范围的内容，并等待用户确认这份共同理解。用户纠正任何内容时，重新打开受影响的分支并继续追问。用户确认之后，才能进入发布或实现流程。

这次人工审批关卡只确认 `/mmw-grilling` 形成的共同理解。它不替代 `/mmw-to-spec` 对 spec 定稿的人工审批关卡。

用户要求提前停止时，分别报告已经定下来的内容、仍未解决的内容和仍在等待的事实。不要宣称已经形成完整的共同理解。

## 下一步

| 情况 | 下一步 |
| --- | --- |
| 设计树已经满足完成判据，正在等待用户确认共同理解 | **停**：展示共同理解，等用户确认或纠正 |
| 用户直接叫你来谈一个新需求，并确认了共同理解 | **移交**：`/mmw-to-spec`，由它把这次对话综合成一份 spec |
| 别的技能把你叫起来，用户已经确认调用方问题的共同理解 | **移交**：回到把你叫起来的技能，收尾归调用方 |
| 同一个决定仍定不下来，用户需要看见东西才能判断 | **移交**：`/mmw-prototype`，把这个决定收成一个走查后能得到明确答案的问题；走查完成后回到 `/mmw-grilling`，重新计算设计树 |
| 某个分支依赖一条必须真实运行才知道的事实 | **移交**：`/mmw-prototype` 的 `EVIDENCE.md` 路径；只暂停依赖该事实的分支，其他 frontier 问题照常推进 |
| 某个分支依赖另一位知识持有者掌握的事实，当前用户无法代答 | **移交**：`/to-questionnaire`，答案回来后重新计算设计树 |
| 用户要求在完成判据满足前停止 | **停**：报告已经定下来的内容、仍未解决的内容和仍在等待的事实 |
