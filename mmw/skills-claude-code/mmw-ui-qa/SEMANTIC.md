# 语义层：B2、B3、B4

语义层判断界面想表达的功能、流程与目的是否被实现，**不判断组件是否存在**。

## 两条写死的做法

**保留完整会话历史。** 把已经走过的屏、做过的动作、给过的理由带进后续每一步。不带历史时，重复运行的结果彼此不一致。

**agent 走得通不等于用户走得通。** 任务完成**不**作为通过判据。依据：同一界面，人类评估者找出十个失败点，语言模型多轮合计只找出三个，而语言模型的任务完成率更高。

## 认知走查四问 · B2

每一步问：

1. 用户会不会想要达成正确的那个结果
2. 用户会不会注意到正确的操作是可用的
3. 用户会不会把正确的操作与他想达成的结果联系起来
4. 操作之后，用户会不会看到事情在推进的反馈

**四问中只有第 2 问需要视觉信息。** 它同时用两种输入：结构化的视觉显著度数值（是否在首屏内、尺寸、对比度、是否被遮挡、层叠次序）与一张裁到相关区域的局部截图。第 1、3、4 问只用结构化数据。

## Trunk Test 六问 · B4

假设用户被直接放到当前这一屏，没有任何上文，他能否回答：

1. 这是什么产品
2. 我现在在哪一个界面
3. 这个界面有哪些主要区块
4. 我在这一层有哪些可选的操作
5. 我处在整个流程的什么位置
6. 我怎么回到上一层，或者找到我要的东西

第 6 问是对桌面应用的调整。来源的原始表述问的是「怎么搜索」，那假设界面上有搜索框；桌面工作台不一定有，所以改成问导航与查找能力。其余五问按原表述。

**六问按上面的固定表述提问，不逐个产品改写**，这样不同产品的结果可比。任一问答不出，记一条 B4。

## 困惑分量表 · B3

每一屏单独打分，三档：

| 分档 | 含义 |
| --- | --- |
| 完全不困惑 | 当前该做什么一眼可见 |
| 有点困惑 | 需要停下来读或想一下才知道该做什么 |
| 很困惑 | 读完仍不确定该做什么，或有两个以上看起来都对的选项 |

**「偏高」怎么判**：任何一屏被评为「很困惑」直接记一条 B3；连续两屏被评为「有点困惑」也记一条 B3，指向这一段路径而不是单屏。**单独一屏「有点困惑」不记。**

## 走查任务从哪来

两种来源，要求不同：

- **从 MMW 产物取到的路径。** 必须是用户为达成一个真实目的所走的完整路径，跨多个界面，并且至少包含一条失败路径或边界情况。从产物中取到单个操作时，向上合并到它所属的完整路径，不拆细凑数。
- **范围内没有产物路径时，用全图跳转关系拼出来的路径。** 从主窗口出发到范围内每个界面的最短路径，各拼一条。不要求含失败路径，但**必须在报告中标明是拼的**——它只保证走得到，不保证用户真会这么走，基于它得出的结论要打折看。

第二种保证 B2、B3、B4 在任何范围下都有路可走。**产物完全取不到时也不跳过这三种判拒。**

## 交接：主 agent 走，`designer` 判

**浏览器由主 agent 独占，`designer` 拿不到它。** 两条理由：A 类检查已经占着同一个应用实例，两边同时驱动会互相干扰；`designer` 是独立上下文，它自己开实例就意味着应用状态归零，走到第五步才出现的那个界面它到不了。

**一条完整路径派一个 `designer`，不是一步派一个。** 四问要带完整会话历史。一步一派时每个 `designer` 的上下文都是空的，第 4 问「操作之后用户会不会看到事情在推进」根本判不了——判它需要知道操作之前是什么样。

**主 agent 先把整条路径走完，再一次性交付。** 按路径逐步操作应用，每一步采集下面的数据，全部走完之后把整条路径的数据包一次交出去。

### 路径包

路径级：

| 字段 | 类型 | 内容 |
| --- | --- | --- |
| `产品名` | 字符串 | 本次检查的产品 |
| `路径名` | 字符串 | 这条路径做的事，一句话 |
| `用户目的` | 字符串 | 用户走这条路径想达成什么。第 1 问判的就是它 |
| `来源` | 枚举 | `产物` 或 `拼的` |
| `步骤` | 数组 | 见下，按执行顺序 |

每一步：

| 字段 | 类型 | 内容 |
| --- | --- | --- |
| `序号` | 整数 | 从 1 开始 |
| `界面标识` | 字符串 | 界面全图里的节点标识 |
| `界面标题` | 字符串 | 用户看得到的那个标题 |
| `本步动作` | 字符串 | 这一步做了什么操作。第一步写「到达此界面」 |
| `可操作元素` | 数组 | 每项含 `名称`、`角色`、`是否在首屏内`、`尺寸`、`对比度`、`是否被遮挡`、`层叠次序`。第 2 问用它 |
| `无障碍树快照` | 文本 | 本步执行后的快照 |
| `动作后的变化` | 字符串 | 主 agent 比对动作前后两份快照得出的差异描述。第 4 问用它 |
| `局部截图路径` | 字符串 | 裁到相关区域的那一张。第 2 问用它，其余三问不看 |
| `运行时报错` | 数组 | 本步产生的报错。为空写空数组 |

**截图落临时目录，运行结束删除。** subagent 读不到主 agent 进程里的字节，截图只能走文件。落点用 `mktemp -d` 当场创建的目录，路径随数据包交给 `designer`，本次运行结束时整个目录删掉。这些截图在本次运行之后没有任何消费者，**不是产物，不走产物落点解析**。

`mktemp -d` 失败时继续跑，第 2 问只用结构化的视觉显著度数值判定，并在该条 finding 上标明没有截图。

**会话历史不落文件。** 整条路径的数据包本身就是完整历史，一次进 `designer` 的上下文。它在一次任务内看得到前面每一步，第 4 问因此判得了。

### 派发

四栏表：目标是「认知走查」加这条路径的名字；读是路径包与截图目录；约束是只读、不碰浏览器、不改任何文件；验收是交回下面那份结构化列表。

派一个独立上下文的 `designer`。它只读，不需要工作目录。
启动：后台执行 `mmw dispatch designer`。把四栏 task 正文作为命令的标准输入。当前 task 属于 decision ticket 时，加 `--issue <当前 decision ticket 编号>`。命令返回 `mode: host-tool` 时，使用输出中的 `params` 调用对应宿主工具。

互不依赖的路径在同一条消息里一起启动，全部回来之后再汇总。

### `designer` 交回什么

一份结构化列表，每条含：`判拒`（`B2`、`B3`、`B4` 之一）、`步序号`、`界面标识`、`元素`（判到具体元素时填，否则留空）、`失败的是哪一问`（四问或六问的编号）、`一句话问题`、`理由`。

另交一份困惑分，每步一档，取值是上面那三档之一。**B3 由主 agent 按上面的判定规则从困惑分算出，不由 `designer` 直接报。**

派发返回空、格式对不上或中途失败时，跳过 B2、B3、B4，报告顶部的「本次跳过」写明原因。**不拿主 agent 自己的判断顶替独立上下文的评估。**

### 交回之后

B2、B3、B4 产出的全部内容是 finding 候选。按 `/mmw-verifying-agent-output` 回到当前源码验证每一条的出处。验证不出来的标 `needs-evidence`，不进处置。
