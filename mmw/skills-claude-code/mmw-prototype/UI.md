# 界面原型

生成**几个结构截然不同的界面变体**，用一个浮动底栏在它们之间切换。用户在浏览器里翻看，挑一个，或者从每个里各取一部分。

适合的问题长这样：

- 「这个页面该长什么样？」
- 「定下来之前我想先看几个仪表盘的方案。」
- 「设置页换个布局试试。」

问题是逻辑或状态而不是长什么样，就走错了，回 [LOGIC.md](LOGIC.md)。

## 选一个形态

界面变体**贴着应用其余部分**才走查得准：真实的页头、侧边栏、真实数据、真实密度。

| 形态 | 什么时候用 |
| --- | --- |
| **挂进已有页面**（首选） | 路由已经存在。变体渲染在**同一个路由**上，用 `?variant=` 查询参数切换，原有的取数、参数和鉴权全部保留，只换渲染的那一层。要做的东西还没有页面、但天然属于某个页面里面（仪表盘的一个新区块、设置页的一张新卡片、既有流程里的一步），也算这一种，把变体挂进宿主页面 |
| **新开一个一次性路由** | 要做的东西确实没有任何已有页面装得下：一个全新的顶层界面，或者一个嵌不进任何地方的流程。按项目已有的路由约定建，名字里带上 `prototype` |
| **独立 HTML 稿** | 项目里还没有能承载它的应用——纯后端仓库，或者产品的界面部分尚未存在。直接写在 [SKILL.md](SKILL.md) 通过 `mmw path prototype` 取得的 prototype 产物路径下的 `mockup/`，同样带切换器 |

前两种的变体代码写在项目路由里，走查完成之后才归档（见 [capture.md](capture.md)）。独立 HTML 稿从一开始就在原型目录里。

新开一次性路由之前先确认一遍：真的没有任何已有页面装得下它吗？

三种形态的浮动底栏完全一样。

## 1. 定变体数量

默认 **3 个**，上限 5 个。超过 5 个以后，变体会从结构差异变成噪声，很难再逐个判断。

把这一轮的打算写成一行，放在原型所在位置或者文件顶部注释：

> 「设置页三个变体，挂在已有的 `/settings` 路由上，用 `?variant=` 切换。」

## 2. 一个变体派一个 subagent

一个变体一个 `prototype-worker`，并行。每个变体使用独立 worktree，且只写分配给自己的变体组件。四栏表写明：目标是该结构方向的变体；读是页面语境路径；约束是其他变体方向、独占文件和本文件「3. 每个变体都要过质量门」；验收是可切换、可走查。派发前为每个变体确定唯一、完整的结果分支名，并记录当前任务分支的基点 SHA。

启动：先运行 `mmw task new <结果分支> "<目标栏原文>" --from <基点 SHA>`，使用命令返回的 worktree 绝对路径。把四栏表写入 task 文件，后台执行 `mmw dispatch prototype-worker --task <task 文件绝对路径> --cwd <结果 worktree 绝对路径>`。命令返回 `mode: host-tool` 时，使用输出中的 `params` 调用对应宿主工具。

每个 `prototype-worker` 完成后，逐个收取结果：

该角色完成后，运行 `mmw result verify <结果分支> <HEAD SHA> <基点 SHA>`。命令通过后，从输出取得结果 worktree 路径；在该路径读取报告与 diff，并运行本技能规定的验收。此动作不合入结果分支。

每份 task 给同样的页面语境路径（用途、数据、组件库与样式系统在仓库里的位置），但各自指定一个不同的结构方向和一组不重叠的文件。质量门点名本文件「每个变体都要过质量门」一节，由 `prototype-worker` 自读。

收回的变体按 `/mmw-verifying-agent-output` 逐个验证：真的结构不同吗，真的用了项目的组件库吗，质量门过了吗。两份太像就重做一份，task 里明写「不要用卡片网格」这类排除项。

每个变体通过验证后，集成该变体的结果：

本技能规定的验收全部通过后，运行 `mmw result integrate <结果分支> <HEAD SHA> <基点 SHA>`。命令成功后，结果提交才算进入当前任务分支。

变体自己也需要一个清楚的导出名，例如 `VariantA`、`VariantB`、`VariantC`。

## 3. 每个变体都要过质量门

- 先分清这是营销页、应用页还是两者混合，三者的信息密度和节奏不一样。
- 颜色定义成变量，不散落在各处。
- 不用浏览器默认字体栈。
- 表单标签可见，不靠占位符代替标签。
- 标题贴着它所属的区块，不飘在中间。
- **每个状态都渲染得出来**：目标 viewport、加载中、空、错误、成功、部分完成——这个界面实际存在的那些。空状态要有说明和一个主操作，不是一片空白。
- 可访问性：键盘可达、ARIA 正确、触控目标够大、对比度达标、正文字号不小于项目基线。

下面这些做法一律不要：紫色到靛色的渐变、三列图标圆圈、纯装饰的圆形色块、整页居中、所有圆角一个值、装饰性的波浪和不规则色块、拿 emoji 当设计元素、左边一道彩色竖条的卡片、套话式的大标题区、每个区块等高等距。

项目已经有设计系统的，一律照它做，本节的排版、状态、可访问性和模板感清单只填它没规定的部分。项目没有设计系统、又装了界面设计类技能的，用那个界面设计技能生成和打磨，质量门仍然按本节判。

## 4. 接进切换器

在这个路由上做一个切换组件：

```tsx
// 伪代码——按项目的框架改写
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

挂进已有页面时，保留切换器上方所有原有的取数逻辑，每个变体只换被渲染的那棵子树。

浮动底栏固定在屏幕底部居中，三个部分：

- **左箭头**——切到上一个变体，循环。
- **变体标签**——显示当前变体的键，变体导出了名字就一并显示，例如 `B —— 侧边栏布局`。
- **右箭头**——切到下一个，循环。

行为：

- 点箭头更新 URL 查询参数（用框架自己的路由方法），这样变体可以分享、刷新也不丢。
- 键盘 `←` `→` 同样切换。焦点在输入框、文本域或者可编辑元素里时不要拦截方向键。
- 视觉上跟页面明显区分（高对比药丸形、淡阴影），让人一眼看出它不属于正在走查的那个设计。
- 生产构建里隐藏——用 `process.env.NODE_ENV !== 'production'` 或者等价判断挡住。

切换器做成一个共享组件，三种形态复用同一个。

## 5. 交给用户

把地址和 `?variant=` 的取值给他。他常给的反馈是**「我要 B 的页头配 C 的侧边栏」**，据此再开一轮。

使用当前宿主已有的浏览器工具打开全部相关页面，并保留给用户走查。交给用户前保存每个相关页面的截图并记录出处。没有可用浏览器工具时，给出一条运行命令、全部页面地址和目标 viewport，等待用户反馈。

## 下一步

| 情况 | 下一步 |
| --- | --- |
| 用户选中了某一个变体，不再要求改动 | **自己继续**：读 [capture.md](capture.md)。界面这一侧的回填是把选中变体拆成验收标准和视觉契约，并把全部变体归档进原型目录 |
| 用户要的是几个变体的组合（「B 的页头配 C 的侧边栏」），或者还要改 | **自己继续**：回 [SKILL.md](SKILL.md) 的「一轮只回答一个问题」一节开新一轮，把他要的组合做成一个新变体请他确认。**组合不能直接当选中的那一版回填** |
| 收回的变体有两份太像 | **自己继续**：重派其中一份，task 里明写这次不许用哪个结构 |
| 三个变体都被否，而且用户说不出他要什么方向 | **移交**：`/mmw-grilling`，先把这个界面要解决什么问题谈清楚 |

## 不能要的写法

- **只差颜色或者文案的变体。** 那是微调不是原型。真正的变体在结构上就不一样。
- **变体之间共用太多代码。** 共用一个页头没问题，共用一整套布局就失去意义了——每个变体都要能把布局整个换掉。
- **把变体接到真实的写操作上。** 只读的原型没问题；变体确实要改数据就指向一个桩。
- **把变体代码直接提拔成生产代码。** 回填时按仓库规范重写，见 [capture.md](capture.md)。
