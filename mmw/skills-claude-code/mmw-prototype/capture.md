# 走查过了之后怎么回填

**回填完成之前这一轮不算完。**

## 1. 先把这一轮记完

往 [SKILL.md](SKILL.md) 通过 `mmw path prototype` 取得的 prototype 产物路径下的 `README.md` 追加这一轮用户走查结论。处置词写 `accepted`，并列出**选中的是哪几份产物**（写路径）。UI 走查还要列出所有落选或 `superseded` 变体的路径，以及它们形成的明确否定约束；没有则写「无」。落选的全部 UI 变体留在原地作为 primary source，但不往下传。

过程截图、DOM、console、录屏、临时探测输出和生成中间物留在 scratch 路径。只有长期决定必需的最小证据才提升，并在 `README.md` 里逐条引用。然后把源码、`README.md` 和已引用的提升证据放进同一个提交；不提交 scratch。回填完成后清理当前 scratch 路径。

## 2. 结论写到哪去

看是谁把你叫起来的：

| 谁叫的 | 结论写去哪 |
| --- | --- |
| `/mmw-wayfinder` 的一张 `wayfinder:prototype` ticket | 回 `/mmw-wayfinder`，按 `mmw-wayfinder/walking.md` 第 4 步那六件事记录这次解答；结案评论里留一个指向原型产物的路径。关 ticket、追加 map 索引、写 ADR 都归那一步，不要在这里先做一遍 |
| `/mmw-grilling`，或者用户直接叫你 | 写进这份 spec 的 `Implementation Decisions`；spec 还没建就先留在 `README.md` 里，`/mmw-to-spec` 会来取 |

**每一条回填进去的决定，末尾标注它的原型出处**——第几轮、哪份产物。`/mmw-to-spec` 定稿时要逐条验证：每条需求都得指得到一份原型证据，或者写明它为什么不需要原型。

## 3. 逻辑这一侧怎么回填

自包含 HTML 那条 branch 和最小脚本那条 branch 都走这一节。

- **状态、合法转移、被拒绝的非法转移、schema** 逐条写成文字，每条对应一项能执行的验收。「退款窗口关闭后申请会被拒绝」是一条，它对应一个测试。
- **把验证过的模块形状、状态和转移写进 spec 的实现决定与验收标准。** 正式实现阶段由对应 tracer bullet ticket 把 reducer、状态机或纯函数移入正式 module，并用 TDD 证明行为。
- **HTML 外壳不进生产**，完整保留在 prototype 产物路径下的 `logic/` 里。
- **最小脚本那条 branch**：用户看过并认可的样例、数据形状和合同定义，逐个字段写成验收标准。字段的类型、可空性和取值范围都写出来。样例和脚本继续留在 prototype 产物路径下的 `logic/` 里当出处，不进入生产路径。

## 4. 界面这一侧怎么回填

- **选中变体的每个界面元素、每个状态、每处交互、每句文案，原子级拆成验收标准。** 「空状态显示一句说明加一个『新建订单』按钮」是一条。
- **视觉契约单独写一节**：布局、间距、配色、用到哪些组件，并指向具体的变体文件路径。
- **全部变体归档进 prototype 产物路径下的 `mockup/`**——选中的和落选的都要。
- **正式应用路径里撤干净**：把全部变体和切换器归档到 prototype 产物路径下的 `mockup/`，再从已有页面或一次性路由删除 prototype 接线。Prototype 阶段不把选中变体提前改成生产页面。
- **界面代码在实现阶段重写，不搬运。** 对应 tracer bullet ticket 按仓库规范和视觉合同实现选中方向。

## 5. 冲突了听谁的

回填过程中发现原型跟先前写下的决定对不上，**以用户确认过的那份选中的那一版为准**，反过来改决定文档。

## 6. 材料怎么交给写码的 `worker`

派 `worker` 实现时（见 `/mmw-implement`），task 里给的是**回填后的验收标准和视觉契约**，加上选中资产在仓库里的路径。

不要只给一句“照 prototype 做”。prototype 目录里还包含落选变体和 HTML 外壳。
