# Upstream Skill Fidelity

本技能供在本仓库维护 MMW Plugin 的 agent 使用，不限模型。它规定如何把上游方法准确翻译成中文，再加入经过确认的 MMW 工作流。MMW Plugin 安装后供各宿主 agent 使用的技能源仍在 `mmw/skills/`。

开始前完整读取 `.agents/skills/writing-for-agents/SKILL.md` 和它链接的 `SKILL-MECHANICS.md`。`SKILL-MECHANICS.md` 规定一个技能能不能被别的技能调起来：标了 `disable-model-invocation: true` 的技能只有人能调，任何技能都够不到它。判断一条移交成不成立之前先读它，否则会把一条根本走不通的移交当成正确接线。

上游方法合同与 MMW 工作流合同必须同时成立。当前 MMW 行为不能证明方法保真，上游原文也不能否定有证据支持的 MMW 接线。

当前请求只涉及运行已经安装的 MMW Plugin 时，停止使用本技能，改按已安装的 MMW 技能处理。

## 先判定正在修改哪一层

每次编辑前，先写清本次产物属于哪一层：

| 层 | 使用者 | 位置 | 处理方式 |
| --- | --- | --- | --- |
| 仓库维护方法 | 在本仓库维护 MMW 的 agent | `.agents/skills/`、`AGENTS.md` | 只约束 MMW 的开发和审查 |
| MMW Plugin 发布面 | 安装 MMW 后的各宿主 agent | `mmw/skills/`、`mmw/cli/`（含 `seeds/`）、各宿主 manifest、根 marketplace | 经过批准后才修改，并物化到正式宿主 |
| 候选重构材料 | 用户与维护 agent | 独立候选目录 | 不参与 Plugin 运行，不物化 |
| 上游副本 | 上游版本的只读依据 | `vendor/mattpocock-skills/` | 只读取，不编辑 |

产物层没有判清之前，不创建文件。先问：这条规则是维护者工作时需要，还是安装 Plugin 后的 agent 执行任务时需要？只有后者才能进入 `mmw/skills/`。仓库维护技能不得加入 Plugin manifest、README 技能清单或 `mmw-skill-map.html`。候选材料不得冒充当前技能源。

**候选阶段要改发布面的任何一部分，都把那一部分整份复制进候选区再改，不要就地改。** 技能正文精简之后，原本写在正文里的参数来源和约束常常应该落到 CLI 帮助文本里，所以 CLI 会跟着一起动——`mmw/cli/` 和 `mmw/skills/` 是同一个发布面的两半，不是“技能是候选、CLI 是现役”。已经就地改了才发现越界时，先把改动**完整复制**进候选区、逐字确认没丢，再还原现役文件；不要直接丢弃已经落地的内容重做。

**完成判据：** 每个拟修改文件都已归入一层，使用者和发布影响已经写清。

## 先判定本次是哪种任务

本技能的第 1 到第 9 节是**正向维护**的顺序：从上游出发，翻译、精简、接线、发布。另一种常见任务是**复核别人已经产出的候选**——上游翻译、精简稿和接线候选都已经在候选区，你的工作是判断这批候选能不能用。

复核任务不要从第 1 节重跑一遍全流程。按下表进入：

| 本次任务 | 从哪进入 |
| --- | --- |
| 从上游建立或升级一个技能 | 第 1 节起顺序执行 |
| 复核已有候选，用户没有限定审查对象 | 第 1 节固定版本和文件清单，再进第 4 节；翻译基线和精简稿作为定位依据读，不重做 |
| 复核已有候选，用户明确说只看最终候选、不看过程 | 直接进第 4 节和第 5 节，审查对象是 `candidate/` 里将来会被 agent 打开的每一个文件 |

第三种是合理的，不是偷懒：翻译基线和精简稿都是中间材料，不会有任何 agent 打开它们；将来真正被读到的只有 `candidate/` 的内容。这时判据也随之改变——不是“它跟基线的 diff 对不对”，而是“一个只读到这个文件的 agent 能不能照着执行”。中间材料只在你需要判断某处写法是翻译遗漏还是有意精简时才回头去查。

**完成判据：** 本次属于哪一种、审查对象是哪些文件、判据是什么，都已经写清并与用户的要求一致。

## 1. 固定版本、范围和文件清单

先记录上游版本或提交，再完整列出双方材料：

- 上游 `SKILL.md`、被它引用的全部 `reference`、模板和资产。
- 当前 MMW 技能源的全部文件，包含入口、分支文档和完成判据。
- 当前 MMW 中调用待改技能的技能，以及待改技能调用的下游技能。
- 与接线有关的当前领域文档、ADR、CLI 合同和宿主物化规则。

机械 diff 只负责定位差异。方法效果必须结合完整句子、上下文、步骤顺序和完成判据判断。不得只比较同名文件，也不得因主入口相似而跳过其余文档。

**完成判据：** 上游版本已固定；双方全部相关文件和上下游调用方均已列出；不存在尚未读取的引用。

## 2. 建立术语对照

术语一致性分两项检查，不能合并成一次笼统的“用词检查”。

### 上游术语与中文译名一致

- 有公认中文译名的术语，使用准确、正统的中文译名。
- 没有稳定中文译名的术语，保留上游英文原词。
- 技能名、角色名、命令、字段、标签、状态字面量和代码标识符保留原文。
- `leading word` 等依赖既有模型语义的词，除非存在同样稳定的中文术语，否则保留英文。
- 同一个英文术语只对应一个中文译名。一个中文译名也不能混指多个不同概念。

### MMW 技能之间的术语一致

在 active `mmw/skills/`、相关领域文档、ADR 和 CLI 中搜索同一概念。已有 canonical 术语时沿用；发生冲突时，列出每一种实际用法和对应对象，不能自行挑一个覆盖其他用法。

术语对照至少记录：

| 上游原词 | 采用写法 | 类型 | 依据 | 其他技能中的冲突写法 |
| --- | --- | --- | --- | --- |
| 原始术语 | 正统中文或英文原词 | 方法术语、字面量或代码标识符 | 上游上下文、领域文档或行业惯例 | 没有则写“无” |

不要为了术语审查另建长期 glossary。当前领域文档已经拥有该概念时，长期结论归对应 leaf；候选阶段的临时映射留在审查材料中。

**完成判据：** 每个反复出现或决定执行方式的上游术语只有一种采用写法；跨技能冲突已解决，或者已经作为明确问题交给用户决定。

## 3. 保存逐句翻译基线

在独立候选目录创建逐句翻译。翻译基线只做翻译，不做精简，也不加 MMW 接线。

按上游顺序保留以下内容：

- invocation 方式和入口判据；
- 方法论与解释性文字；
- 每个步骤及其顺序；
- 例子、模板和分支；
- 每一步的完成判据和整个技能的完成判据。

每段标注对应的上游文件和行号。句式可以按中文语法调整，方法效果、信息强度和范围不能变化。原文说“all”“only”“must”时，译文必须保留同等约束。原文保留选择空间时，译文不能擅自收紧。

翻译完成后逐句检查四类问题：遗漏、增写、曲解和术语漂移。重点检查强行翻译英文原词、同一英文词出现多个中文译名、用概括句替代解释性文字、把示例误写成硬性规则。

翻译基线检查通过后，先建立独立提交。该提交不得包含精简、接线或正式技能源修改。

**完成判据：** 上游清单中的每个标题、正文段落、表格、例子和完成判据都有对应译文与出处；四类检查均已完成；该提交只包含翻译基线。

## 4. 逐项审查全部差异

审查对象按“先判定本次是哪种任务”那一节确定：正向维护时是当前 MMW 技能，复核时是候选区里的接线候选。用逐句翻译基线作为对照依据。每个差异单独记录：

| 位置 | 上游原意 | 当前写法 | 对方法效果的影响 | MMW 证据 | 分类 | 处理 |
| --- | --- | --- | --- | --- | --- | --- |
| 精确文件与段落 | 写完整含义 | 写完整含义 | 说明 agent 会怎样不同地执行 | 当前合同或“无” | 下列六类之一 | 保留、恢复或待确认 |

分类只有六种：

1. **直接保留**：翻译准确，不需要修改。
2. **有意精简**：用户已经明确确认，而且不破坏上游方法效果。
3. **MMW 接线**：当前仓库合同支持，而且只负责承载上游方法。
4. **语义漂移**：没有证据支持，或者已经改变步骤、解释、完成判据或执行效果。
5. **待用户决定**：现有证据无法判断，选择会改变方法效果、用户流程或长期工作流。
6. **MMW 自有内容的增删**：上游侧本来就是空的——这块内容是 MMW 自己加的，现在被删掉、被移走或被新加。

第 6 类容易整块漏掉，因为前五类都是拿“上游原意”对“当前写法”比，而 MMW 自有内容在上游侧没有对应物，“删掉它”在那张表里落不进任何一格，看上去也不需要证据。

对每一处 MMW 自有内容的增删，另外做一次**消费者检查**：

| 问 | 不通过时怎么办 |
| --- | --- |
| 它原来承担的那类问题，现在由谁接？ | 没有人接就是一个洞。要么恢复，要么明确写出“这类问题当前 MMW 不接”，不能默认它消失了 |
| 谁在引用它？路径、CLI 子命令、标签、宿主动作、别的技能各查一遍 | 引用还在、被引用方没了，就是悬空引用。删干净，或者恢复被引用方 |
| 候选区的 `README.md` 有没有记下这次增删，以及去向？ | 补记。只写“删除了 X”不够，要写 X 去哪了或者为什么不再需要 |

旧 MMW 技能只能提供候选线索，不能为自身正确性作证。用户的标注明确说明“有意为之”时，必须归入有意精简或 MMW 接线，不得再次作为误译报告。用户尚未确认的推测不得写成既定决定。

每项问题必须在当前待改稿中重新验证。旧技能中曾经存在的问题，不能直接套到新的翻译基线、精简候选或接线候选。

汇报时写完整问题。每项都要说明哪句话不同、原意是什么、当前写法会怎样改变 agent 行为。不得使用“三个章节重复”“路由有问题”这类无法定位和判断的缩写。

**完成判据：** 文件清单中的每个差异都已分类；每个保留项都有方法或 MMW 证据；每个待定项都收敛成一个用户能决定的问题。

## 5. 换成使用者视角再读一遍

前面几节比的都是“候选对不对得上上游和 MMW 合同”。这一节换一个身份：**你是一个刚被调起、只读到这一个文件的 agent，手上还压着大量别的上下文。** 一句话在这个身份下能不能执行，跟它翻译得准不准、有没有合同依据，是两件独立的事——三类最常见的问题在前面那六类里一格都不占，只有换视角才看得见。

逐个文件读，逐句问三件事：

| 问 | 典型病症 | 怎么改 |
| --- | --- | --- |
| 这个词第一次出现时，读者能不能从本文件、或者本文件明确指过去的位置知道它指什么？ | 用了只有维护者知道的内部说法，例如“某某资产索引”“上下文指针”“结案评论”“落盘”“取证材料” | 直接说那个东西是什么：说 `README.md`，不说“资产索引”；说“每张 ticket 关闭前留的那条写结论的评论”，不说“结案评论” |
| 这句话是写给正在执行的 agent，还是写给维护这份文件的人？ | “这些字段只由 X 定义，本文件不重复”“细节见 Y，此处不再展开” | 换成使用者要做的动作：“这一轮记什么、怎么维护、交回什么，全部见 X” |
| 这条命令的每个参数，agent 知不知道值从哪来？ | 只给了命令形状，参数写成占位符，取值来源和取名规则都没说 | 逐个参数写出来源（上游交回的、map 正文里读的、还是自己起的）；有字符规则就写实际规则，并写清命令报错时该改什么 |

判断“读者知不知道”时，标准是**本次这个 agent 的上下文**，不是仓库的整体知识。仓库里别处解释过、你自己读过，都不算数。

**完成判据：** 候选区里每一个将来会被 agent 打开的文件都按这三问读过；每处命中都已改成不依赖外部知识的说法，或者已经在本文件里当场解释。

## 6. 应用有意精简

从逐句翻译基线复制一份精简候选。只应用差异审查中已经由用户确认的有意精简。

精简前先向用户展示每一项拟删除或改写的完整内容、理由和方法影响，然后停止并等待确认。用户确认后再编辑；用户没有确认时不修改精简候选。没有列入确认表的段落保持逐句翻译基线原文。

精简可以删除与 MMW 无关的上游安装说明、宿主假设或已经被当前仓库合同取代的机械细节。精简不能删除形成理解所需的解释、步骤之间的因果关系、例子承担的方法作用或完成判据。

精简完成后单独提交。该提交只包含用户已经确认的精简，不包含 MMW 接线。

**完成判据：** 精简候选相对翻译基线的每处差异都能对应一项用户确认；未确认的上游内容保持不变。

## 7. 增加 MMW 接线

从精简候选复制一份接线候选。接线阶段只增加 MMW 工作流，不再翻译、精简或改写已经确认的上游内容。

每条接线先找到当前依据：领域文档、ADR、CLI 行为、`AGENTS.md` 或另一个 active 技能的输入输出合同。Git 历史只能帮助定位理由，不能替代当前依据。

接线候选中的技能文件必须按照正式技能源中的最终位置书写。候选目录只承载审查材料，不参与技能运行，也不充当相对路径的解析基准。例如，`mmw/skill-rebuilds/grilling/candidate/SKILL.md` 的正文必须按照它最终位于 `mmw/skills/mmw-grilling/SKILL.md` 时所需的相对路径书写。不能为了让引用在 `candidate/` 中成立而写入候选目录专用路径。

验证候选引用时，先把每个候选文件映射到 `mmw/skills/` 中的正式目标位置。相对引用从正式目标文件的父目录解析。引用同一候选技能中的其他文件时，把这些文件视为已经一起放入正式目标目录。候选目录中的引用能够打开，不能证明正式技能源中的引用有效；只有按照正式目标位置解析成功，引用检查才通过。

### 按 agent 的执行时序编排

技能是给 agent 使用的文档。文字出现的顺序必须与 agent 实际判断和执行的顺序一致。

- 需要 agent 理解语境、比较证据或作出判断时，使用完整自然语言写清判断依据、边界和完成判据。
- 操作已经确定、不需要 agent 自行判断时，使用有顺序的编号步骤、条件表、字段清单或命令块。动作写准确、直白、完整，不让 agent 从叙述中推断操作顺序。
- 某个条件在正文中途出现时，把判定和处理动作放在对应步骤旁边。需要暂停、移交或稍后从同一步恢复时，当场写清；不要把它搬到文末。
- 每个文件的 `## 下一步` 只列正文全部执行完成，或者 agent 已经读取到该文件末尾以后，可能采取的下一步。选择当前分支、补齐输入、等待中途确认、进入下一内部步骤和中途失败不属于文末“下一步”。
- 审查 `## 下一步` 时逐行反问：agent 是否已经完成正文，才会遇到这项情况？答案为否时，把该行移回实际发生的步骤。再检查正文的每一种最终结果是否都列出了下一步。

按以下规则接线：

- 把接线放在它承载的上游步骤旁边，保持上游步骤顺序。
- 调用下游技能时，只传递下游所需输入，并保留下游自己的方法论。
- 复用旧 MMW 接线之前，验证它仍符合当前合同，再按术语对照统一用词。
- 只增加当前流程必需的 worktree、tracker、报告验证、领域文档、人工审批关卡、资产和宿主动作。
- 使用当前已有命令、字段、标签、状态和技能名。没有当前依据时，不创建新协议或新术语。
- 共享技能源使用宿主无关的完整语义。宿主差异只进入仓库已有的启动块、宿主动作块、profile、adapter 或 manifest。
- 文档拆分只服务真实的 invocation 分支或阶段边界。共享方法保留一个唯一事实来源。
- 仓库持久状态先写入并提交，再让外部 tracker 宣称该状态完成。
- 路由表和分支表必须有兜底行。全是正面条件的表，落不进任何一行时 agent 没有指示；写清“以上都不是”时怎么办。
- 一个技能既要写清什么时候接手，也要写清什么时候不接手。相邻技能能处理的情况要有一条明确的移交行，否则它会把不属于自己的问题接下来用自己的方法做。

### 逐条对齐移交合同

“上下游输入输出闭合”要真的去对，不能靠通读一遍觉得顺。每一条移交是一份双向合同，两边各读一次，列成一张表：

| 移交 | 交出方实际给出什么 | 接收方实际需要什么 | 对不对得上 |
| --- | --- | --- | --- |

对不上的情况有三种，都要当场修，不要记成“以后再说”：

- **接收方要的东西，交出方在某条分支上不产生。** 例如上游要求交回一个索引文件的路径，而下游有一条捷径分支根本不建那个文件。
- **被引用的那一节写死了时机或前提，跟引用它的地方不成立。** 例如某节开头写“完成验证之后再做”，而另一个流程需要提前用它。
- **交出方少给了一个接收方算不出来的值。** 例如接收方要靠某个目录名算路径，而交出方没把这个值一起交过去。

**只查引用路径能不能解析是不够的**：这三种全都发生在引用完全解析得开的前提下。

如果接线时发现新事实会改变已经确认的方案、方法效果或用户流程，立即停止，报告证据和影响，等用户决定后再继续。不会改变已确认方案的机械修正可以直接完成。

用户没有批准进入 Plugin 发布面时，展示接线候选和逐层验证结果，然后停止。不要进入第 8 节。
