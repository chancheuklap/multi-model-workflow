# Upstream Skill Fidelity

本技能只供 Codex 维护 MMW Plugin 仓库。它规定如何把上游方法准确翻译成中文，再加入经过确认的 MMW 工作流。MMW Plugin 安装后供各宿主 agent 使用的技能源仍在 `mmw/skills/`。

开始前完整读取 `/writing-for-agents`。上游方法合同与 MMW 工作流合同必须同时成立。当前 MMW 行为不能证明方法保真，上游原文也不能否定有证据支持的 MMW 接线。

## 先判定正在修改哪一层

每次编辑前，先写清本次产物属于哪一层：

| 层 | 使用者 | 位置 | 处理方式 |
| --- | --- | --- | --- |
| 仓库维护方法 | 在本仓库维护 MMW 的 Codex | `.agents/skills/`、`AGENTS.md` | 只约束 MMW 的开发和审查 |
| MMW Plugin 技能源 | 安装 MMW 后的各宿主 agent | `mmw/skills/` | 经过批准后才修改，并物化到正式宿主 |
| 候选重构材料 | 用户与 Codex | 独立候选目录 | 不参与 Plugin 运行，不物化 |
| 上游副本 | 上游版本的只读依据 | `vendor/mattpocock-skills/` | 只读取，不编辑 |

产物层没有判清之前，不创建文件。先问：这条规则是维护者工作时需要，还是安装 Plugin 后的 agent 执行任务时需要？只有后者才能进入 `mmw/skills/`。仓库维护技能不得加入 Plugin manifest、README 技能清单或 `mmw-skill-map.html`。候选材料不得冒充当前技能源。

**完成判据：** 每个拟修改文件都已归入一层，使用者和发布影响已经写清。

## 1. 固定版本、范围和文件清单

先记录上游版本或提交，再完整列出双方材料：

- 上游 `SKILL.md`、被它引用的全部 `reference`、模板和资产。
- 当前 MMW 技能源的全部文件，包含入口、分支文档和完成判据。
- 当前 MMW 中调用待改技能的技能，以及待改技能调用的下游技能。
- 与接线有关的当前领域文档、ADR、CLI 合同和宿主物化规则。

机械 diff 只负责定位差异。方法效果必须结合完整句子、上下文、步骤顺序和完成判据判断。不得只比较同名文件，也不得因主入口相似而跳过其余文档。

**完成判据：** 上游版本已固定；双方全部相关文件和上下游调用方均已列出；不存在尚未读取的引用。

## 2. 建立术语对照

术语一致性分两项检查，不能合并成一次笼统的“用词检查”。

### 上游术语与中文译名一致

- 有公认中文译名的术语，使用准确、正统的中文译名。
- 没有稳定中文译名的术语，保留上游英文原词。
- 技能名、角色名、命令、字段、标签、状态字面量和代码标识符保留原文。
- `leading word` 等依赖既有模型语义的词，除非存在同样稳定的中文术语，否则保留英文。
- 同一个英文术语只对应一个中文译名。一个中文译名也不能混指多个不同概念。

### MMW 技能之间的术语一致

在 active `mmw/skills/`、相关领域文档、ADR 和 CLI 中搜索同一概念。已有 canonical 术语时沿用；发生冲突时，列出每一种实际用法和对应对象，不能自行挑一个覆盖其他用法。

术语对照至少记录：

| 上游原词 | 采用写法 | 类型 | 依据 | 其他技能中的冲突写法 |
| --- | --- | --- | --- | --- |
| 原始术语 | 正统中文或英文原词 | 方法术语、字面量或代码标识符 | 上游上下文、领域文档或行业惯例 | 没有则写“无” |

不要为了术语审查另建长期 glossary。当前领域文档已经拥有该概念时，长期结论归对应 leaf；候选阶段的临时映射留在审查材料中。

**完成判据：** 每个反复出现或决定执行方式的上游术语只有一种采用写法；跨技能冲突已解决，或者已经作为明确问题交给用户决定。

## 3. 保存逐句翻译基线

在独立候选目录创建逐句翻译。翻译基线只做翻译，不做精简，也不加 MMW 接线。

按上游顺序保留以下内容：

- invocation 方式和入口判据；
- 方法论与解释性文字；
- 每个步骤及其顺序；
- 例子、模板和分支；
- 每一步的完成判据和整个技能的完成判据。

每段标注对应的上游文件和行号。句式可以按中文语法调整，方法效果、信息强度和范围不能变化。原文说“all”“only”“must”时，译文必须保留同等约束。原文保留选择空间时，译文不能擅自收紧。

翻译完成后逐句检查四类问题：遗漏、增写、曲解和术语漂移。重点检查强行翻译英文原词、同一英文词出现多个中文译名、用概括句替代解释性文字、把示例误写成硬性规则。

翻译基线检查通过后，先建立独立提交。该提交不得包含精简、接线或正式技能源修改。

**完成判据：** 上游清单中的每个标题、正文段落、表格、例子和完成判据都有对应译文与出处；四类检查均已完成；该提交只包含翻译基线。

## 4. 逐项审查全部差异

用逐句翻译基线审查当前 MMW 技能。每个差异单独记录：

| 位置 | 上游原意 | 当前写法 | 对方法效果的影响 | MMW 证据 | 分类 | 处理 |
| --- | --- | --- | --- | --- | --- | --- |
| 精确文件与段落 | 写完整含义 | 写完整含义 | 说明 agent 会怎样不同地执行 | 当前合同或“无” | 下列五类之一 | 保留、恢复或待确认 |

分类只有五种：

1. **直接保留**：翻译准确，不需要修改。
2. **有意精简**：用户已经明确确认，而且不破坏上游方法效果。
3. **MMW 接线**：当前仓库合同支持，而且只负责承载上游方法。
4. **语义漂移**：没有证据支持，或者已经改变步骤、解释、完成判据或执行效果。
5. **待用户决定**：现有证据无法判断，选择会改变方法效果、用户流程或长期工作流。

旧 MMW 技能只能提供候选线索，不能为自身正确性作证。用户的标注明确说明“有意为之”时，必须归入有意精简或 MMW 接线，不得再次作为误译报告。用户尚未确认的推测不得写成既定决定。

每项问题必须在当前待改稿中重新验证。旧技能中曾经存在的问题，不能直接套到新的翻译基线、精简候选或接线候选。

汇报时写完整问题。每项都要说明哪句话不同、原意是什么、当前写法会怎样改变 agent 行为。不得使用“三个章节重复”“路由有问题”这类无法定位和判断的缩写。

**完成判据：** 文件清单中的每个差异都已分类；每个保留项都有方法或 MMW 证据；每个待定项都收敛成一个用户能决定的问题。

## 5. 应用有意精简

从逐句翻译基线复制一份精简候选。只应用差异审查中已经由用户确认的有意精简。

精简前先向用户展示每一项拟删除或改写的完整内容、理由和方法影响。用户确认后再编辑。没有列入确认表的段落保持逐句翻译基线原文。

精简可以删除与 MMW 无关的上游安装说明、宿主假设或已经被当前仓库合同取代的机械细节。精简不能删除形成理解所需的解释、步骤之间的因果关系、例子承担的方法作用或完成判据。

精简完成后单独提交。该提交只包含用户已经确认的精简，不包含 MMW 接线。

**完成判据：** 精简候选相对翻译基线的每处差异都能对应一项用户确认；未确认的上游内容保持不变。

## 6. 增加 MMW 接线

从精简候选复制一份接线候选。接线阶段只增加 MMW 工作流，不再翻译、精简或改写已经确认的上游内容。

每条接线先找到当前依据：领域文档、ADR、CLI 行为、`AGENTS.md` 或另一个 active 技能的输入输出合同。Git 历史只能帮助定位理由，不能替代当前依据。

按以下规则接线：

- 把接线放在它承载的上游步骤旁边，保持上游步骤顺序。
- 调用下游技能时，只传递下游所需输入，并保留下游自己的方法论。
- 复用旧 MMW 接线之前，验证它仍符合当前合同，再按术语对照统一用词。
- 只增加当前流程必需的 worktree、tracker、报告验证、领域文档、人工审批关卡、资产和宿主动作。
- 使用当前已有命令、字段、标签、状态和技能名。没有当前依据时，不创建新协议或新术语。
- 共享技能源使用宿主无关的完整语义。宿主差异只进入仓库已有的启动块、宿主动作块、profile、adapter 或 manifest。
- 文档拆分只服务真实的 invocation 分支或阶段边界。共享方法保留一个唯一事实来源。
- 仓库持久状态先写入并提交，再让外部 tracker 宣称该状态完成。

如果接线时发现新事实会改变已经确认的方案、方法效果或用户流程，先报告证据和影响，等用户决定后再继续。不会改变已确认方案的机械修正可以直接完成。

接线完成后单独提交。正式技能源仍保持不变，直到用户批准接线候选。

**完成判据：** 每条新增内容都有当前依据；上游步骤、解释和完成判据没有被改写；所有上下游输入输出均已闭合；不存在自创协议、状态或术语。

## 7. 批准后进入 Plugin 发布面

用户批准接线候选后，才把候选内容更新到 `mmw/skills/`。此时遵守仓库的宿主物化、README、架构图、版本和提交规则。

不得手改 `mmw/skills-pi/`、`mmw/skills-claude-code/` 或 `mmw/skills-codex/`。共享技能源更新后，通过仓库命令物化全部正式宿主。安装状态、运行时状态和远端发布状态分别验证，不能用静态检查代替。

**完成判据：** 用户已经批准候选；正式技能源与批准内容一致；全部正式宿主产物由当前源生成；各层验证结果分别报告。

## 8. 最终验证

最终验证分六层：

| 层 | 必须证明的事实 |
| --- | --- |
| 翻译 | 没有遗漏、增写、曲解或术语漂移 |
| 方法 | invocation、步骤顺序、解释、例子和完成判据仍产生上游方法效果 |
| 术语 | 上游原词与译名一致；相关 MMW 技能对同一概念使用同一名称 |
| 接线 | 每条 MMW 内容都有当前合同依据；上下游输入输出闭合 |
| 源与产物 | 正式技能源、物化产物和静态检查一致 |
| 运行与发布 | 只报告实际完成的宿主验证、安装或发布，不从前一层推断后一层 |

检查术语时搜索全部 active 技能和相关领域文档。仅统计词频不能证明语义一致；必须打开命中位置判断它们是否指同一概念。

最终汇报说明翻译基线、有意精简、MMW 接线和正式发布面分别发生了什么。不要用一次总 diff 混合四个阶段。

**完成判据：** 六层结论均有当前文件或运行结果支持；没有执行的验证明确写为未验证。

## 下一步

| 情况 | 下一步 |
| --- | --- |
| 上游版本、文件清单或术语映射尚未固定 | **自己继续**：补齐来源、引用和术语对照，不进入翻译 |
| 逐句翻译基线尚未完成 | **自己继续**：完成逐句翻译和四类检查，单独提交基线 |
| 有意精简尚未得到用户确认 | **停**：展示每项完整改动、理由和方法影响 |
| 有意精简已确认，MMW 接线尚未完成 | **自己继续**：只应用确认的精简，再建立接线候选 |
| 新事实会改变已确认方案、方法效果或用户流程 | **停**：展示证据和影响，等待用户决定 |
| 接线候选尚未得到用户批准 | **停**：展示候选与逐层验证，不修改正式技能源 |
| 接线候选已批准 | **自己继续**：更新正式技能源，物化正式宿主并按仓库规则验证 |
| 当前请求只涉及运行已安装的 MMW Plugin | **停**：本技能不适用，按已安装 MMW 技能处理 |
