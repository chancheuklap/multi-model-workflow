# Upstream Skill Fidelity

把上游方法准确翻译成中文，再加入经过确认的 MMW 工作流。

**本技能建立在根 `AGENTS.md` 之上。** 它随本仓库自动加载，MMW 是什么、有哪几个宿主、manifest 和 marketplace 在哪、怎么物化、领域文档和 ADR 用什么命令取、提交前检查在哪，都由它规定。本文出现这些词时按它的定义理解，不另给一份。

开始前完整读取 `writing-for-agents`，包括它链接的 `SKILL-MECHANICS.md`。后者规定一个技能能不能被别的技能调起来：标了 `disable-model-invocation: true` 的技能只有人能调，任何技能都够不到它。判断一条移交成不成立之前先读它，否则会把一条根本走不通的移交当成正确接线。

上游的方法要求和 MMW 的工作流要求必须同时成立。当前 MMW 行为不能证明方法保真，上游原文也不能否定有证据支持的 MMW 接线。

当前请求只涉及运行已经安装的 MMW Plugin 时，停止使用本技能，改按已安装的 MMW 技能处理。

## 先判定正在修改哪一层

| 层 | 使用者 | 位置 | 处理方式 |
| --- | --- | --- | --- |
| 仓库维护方法 | 在本仓库维护 MMW 的 agent | `.agents/skills/`、`AGENTS.md` | 只约束 MMW 的开发和审查 |
| MMW Plugin 发布面 | 安装 MMW 后的各宿主 agent | `mmw/skills-src/`、`mmw/cli/`（含 `seeds/`）、各宿主 manifest、根 marketplace | 经过批准后才修改，并物化到正式宿主 |
| 候选重构材料 | 用户与维护 agent | 候选目录 `mmw/skill-rebuilds/<上游技能名>/` | 不参与 Plugin 运行，不物化 |
| 上游副本 | 上游版本的只读依据 | `vendor/mattpocock-skills/` | 只读取，不编辑 |

层没判清之前不创建文件。先问：这条规则是维护者工作时需要，还是安装 Plugin 后的 agent 执行任务时需要？只有后者能进 `mmw/skills-src/`。仓库维护技能不进各宿主 manifest 的技能清单、根 `README.md` 的「技能系统」一节，或者根 `mmw-skill-map.html`。

**候选阶段要改发布面的任何一部分，都把那一部分整份复制进候选目录再改，不要就地改。** 精简技能正文时，原本写在正文里的参数来源和约束常常应该落到 CLI 帮助文本里，所以 CLI 会跟着一起动——`mmw/cli/` 和 `mmw/skills-src/` 是同一个发布面的两半，只改一半会留下对不上的另一半。已经就地改了才发现越界时，先把改动**完整复制**进候选目录、逐字确认没丢，再还原现役文件。

## 这一轮的边界

**候选目录只装这一轮重建的那个技能自己的文件。** 一个改动的落点如果在别的技能、`mmw/cli/` 或者调用方，它不属于这一轮：把它写成一条 finding 交给用户，由他决定另开一轮。

**问用户之前先把级联算完。** 一个选项要连带改哪些文件、多少处，写进选项本身。用户点头的是你写的那句话，不是它后面的连锁——「把 X 搬去 Y」看起来是一处改动，实际可能强制改名、强制改 CLI、强制改八个调用方。算不出来就先说算不出来，不要问过了才发现。

## 先判定本次是哪种任务

第 1 到第 9 节是**正向维护**的顺序：从上游出发，翻译、精简、接线、发布。另一种常见任务是**复核别人已经产出的候选**——翻译基线、精简稿和接线候选都已经在候选目录，你判断这批候选能不能用。

复核任务不要从第 1 节重跑一遍全流程。按下表进入：

| 本次任务 | 从哪进入 |
| --- | --- |
| 从上游建立或升级一个技能 | 第 1 节起顺序执行 |
| 复核已有候选，用户没有限定审查对象 | 第 1 节固定版本和文件清单，再进第 4 节；翻译基线和精简稿作为定位依据读，不重做 |
| 复核已有候选，用户明确说只看最终候选、不看过程 | 直接进第 4 节和第 5 节，审查对象是 `candidate/` 里将来会被 agent 打开的每一个文件 |

走第三种时判据随之改变：不是「它跟基线的 diff 对不对」，而是「一个只读到这个文件的 agent 能不能照着执行」。翻译基线和精简稿是中间材料，不会有任何 agent 打开它们，只在你需要判断某处写法是翻译遗漏还是有意精简时才回头去查。

## 1. 固定版本、范围和文件清单

候选目录是 `mmw/skill-rebuilds/<上游技能名>/`，本次全部材料都放在它下面。目录里的 `README.md` 是这一轮的台账：上游版本、当前处在哪个阶段、每个文件是干什么的、以及第 4 节要求记的每一处增删和去向，都写进它。`candidate/` 是它下面的子目录，只装第 7 节的接线候选。

先把上游版本或提交写进 `README.md`，再完整列出双方材料：

- 上游 `SKILL.md`、被它引用的全部 `reference`、模板和资产。
- 当前 MMW 技能源的全部文件，包含入口、分支文档和完成判据。
- 当前 MMW 中调用待改技能的技能，以及待改技能调用的下游技能。
- 与接线有关的当前领域文档、ADR、CLI 合同和宿主物化规则。

主入口相似不能作为跳过其余文档的理由。方法效果要结合完整句子、上下文、步骤顺序和完成判据判断，机械 diff 只负责定位。

## 2. 术语

两项检查，不能合并成一次笼统的「用词检查」。

**上游原词与译名一致。** 有公认中文译名的用正统中文译名；没有稳定中文译名的保留英文原词；技能名、角色名、命令、字段、标签、状态字面量和代码标识符保留原文；`leading word` 这类依赖既有模型语义的词保留英文。同一个英文词只对应一种写法，一个中文译名也不混指多个概念。

**MMW 技能之间一致。** 在 `mmw/skills-src/`、相关领域文档、ADR 和 CLI 里搜同一概念（`archive/` 是冻结归档，不算）。**已有 canonical 写法就沿用，即使翻译基线选了别的词**——发布面已经在用的词是事实，翻译基线是候选材料。冲突时列出每一种实际用法和它指的对象，不自行挑一个覆盖其他用法。

不为术语审查另建长期 glossary。长期结论归拥有该概念的领域文档 leaf。

## 3. 保存逐句翻译基线

在候选目录创建逐句翻译。只做翻译，不做精简，不加 MMW 接线。

按上游顺序保留：invocation 方式和入口判据；方法论与解释性文字；每个步骤及其顺序；例子、模板和分支；每一步和整个技能的完成判据。

每段标注对应的上游文件和行号。句式可以按中文语法调整，方法效果、信息强度和范围不能变。原文说「all」「only」「must」时译文保留同等约束；原文保留选择空间时译文不擅自收紧。

逐句检查四类问题：遗漏、增写、曲解、术语漂移。重点看强行翻译英文原词、同一英文词出现多个中文译名、用概括句替代解释性文字、把示例误写成硬性规则。

翻译基线单独提交，该提交不含精简、接线或正式技能源修改。

## 4. 逐项审查全部差异

审查对象按「先判定本次是哪种任务」确定：正向维护时是当前 MMW 技能，复核时是 `candidate/` 里的接线候选。用逐句翻译基线作对照。

每个差异归入六类之一，并写清它会让 agent 怎样不同地执行：

1. **直接保留**：翻译准确。
2. **有意精简**：用户已经明确确认，而且不破坏上游方法效果。
3. **MMW 接线**：当前仓库合同支持，只负责承载上游方法。
4. **语义漂移**：没有证据支持，或者已经改变步骤、解释、完成判据或执行效果。
5. **待用户决定**：现有证据判断不了，而选择会改变方法效果、用户流程或长期工作流。
6. **MMW 自有内容的增删**：上游侧本来就是空的——这块是 MMW 自己加的，现在被删掉、被移走或被新加。

第 6 类最容易整块漏掉：前五类都是拿「上游原意」对「当前写法」比，而 MMW 自有内容在上游侧没有对应物，「删掉它」在这个比法里落不进任何一格，看上去也不需要证据。

对每一处 MMW 自有内容的增删，另做一次**消费者检查**：

| 问 | 不通过时怎么办 |
| --- | --- |
| 它原来承担的那类问题，现在由谁接？ | 没人接就是一个洞。要么恢复，要么明确写出「这类问题当前 MMW 不接」，不能默认它消失了 |
| 谁在引用它？路径、CLI 子命令、标签、宿主动作、别的技能各查一遍 | 引用还在、被引用方没了，就是悬空引用。删干净，或者恢复被引用方 |
| 候选目录的 `README.md` 有没有记下这次增删和去向？ | 补记。只写「删除了 X」不够，要写 X 去哪了或者为什么不再需要 |

**判「有没有人接」要去搜，不能凭印象。** 拿被删内容里的关键词逐个 grep 全仓库，打开每一处命中确认它接的是不是同一件事。零命中就是零命中。

旧 MMW 技能只能提供候选线索，不能为自身正确性作证。用户标注「有意为之」的归入有意精简或 MMW 接线，不再作为误译报告。用户尚未确认的推测不写成既定决定。

每项问题在当前待改稿中重新验证。旧技能里曾经有过的问题，不直接套到新的基线、精简稿或接线候选上。

汇报写完整问题：哪句话不同、原意是什么、当前写法会怎样改变 agent 行为。不用「三个章节重复」「路由有问题」这类定位不了也判断不了的缩写。

## 5. 三问

前面几节比的是「候选对不对得上上游和 MMW 合同」。还有一类问题跟对不对得上无关：一句话翻译得准、有合同依据，一个只读到这个文件的 agent 照样执行不了。

**三问是写的时候的约束，不是写完之后的检查。** 每写一句当场答一遍，这时候改一个词就够了。写完一整份再回头找，你已经处在读不出自己盲点的位置上，只能靠外人告诉你。

先定这个文件的**读者手上保证有什么**，三问都以它为准：

| 文件最终落在 | 读者保证有的 |
| --- | --- |
| `mmw/skills-src/` | 只有 task 给的材料，加目标仓库自己自动加载的 `AGENTS.md` 或 `CLAUDE.md`。本仓库的任何东西都不在内 |
| `.agents/skills/` | 本仓库根 `AGENTS.md`，它随仓库自动加载 |

1. **这个词第一次出现时，读者能不能从这个文件里知道它指什么？** 命中的多是只有维护者知道的内部说法：「资产索引」「上下文指针」「结案评论」「落盘」「取证材料」。当场说清那是什么东西。
2. **把这句话删掉，读者的动作会不会变？** 不会变的就是命中。注意区分两种解释：讲「这一类最容易整块漏掉，因为……」的会改变动作，留着；讲「这份文件为什么这么组织」「这里为什么不写某某」「这条上游规则为什么被删」的不会，那是写给审查你的人看的。
3. **这条命令的每个参数、每个占位符，读者知不知道值从哪来？** 只给形状不给来源就是命中。取名有规则就写实际规则。

第 2 问命中的从产物里拿掉，按下表挑去处：

| 这条理由 | 放哪 |
| --- | --- |
| 只在当时那个决定里有意义，以后没人会回头问 | 删掉 |
| 将来复核这一轮的人要靠它判断某处是有意为之还是漏译 | 候选目录的 `README.md` |
| 只跟这一次改动有关，跟技能的长期形态无关 | 提交信息 |

**一条规则只在一处写死。** 同一个概念在这份材料里出现三种叫法，或者一个词承担三种意思，第 1 问就已经不成立了——第 2 节的术语要求在这里同样管用。**例子不是规则。** 只在例子里出现过的路径形状、命名规则或映射关系，读者会照着例子外推，外推错了是你的问题；规则单独写一句，例子放在规则后面。

### 交出去之前派一次冷读

三问守得再紧，也有一类你看不见：你脑子里压着每句话当初为什么那么写。「本文不重复」在你这儿是一条刚做完的去重决定，在读者那儿是一句没有下文的话。

**一轮一次，在你把候选交给用户之前跑，不是每次编辑之后。** 它是交付前的关卡，不是写不对时的拐杖。冷读报回来的条目多，要修的是你写的时候没带着三问这件事，不是把冷读跑得更勤。

每个将来会被 agent 打开的文件各派一个 subagent：

| | 写什么 |
| --- | --- |
| 给它 | 那一个文件的绝对路径、上表里对应的那行「读者保证有的」、加上面三问 |
| 让它做 | 读这一个文件，报出照着执行不了的每一句。只读这一个文件——不去读它引用的其他文件来补全理解，引用打不开本身就是要报的东西。保证有的那些当作已知，不报。不做对错判断，只报卡在哪 |
| 让它交回 | 逐条给出原句、卡在哪一问、缺的是什么。一条都没有就直说 |

除此之外**只给它这一个文件**。不给上游原文、不给 diff、不给你的设计理由、不给同批的其他文件——给了任何一样，这一遍就失效了。

你手上派不出 subagent 时，把三问、那行「读者保证有的」和文件原文交给用户读。自己再读一遍不算。

## 6. 应用有意精简

从逐句翻译基线复制一份精简候选。只应用差异审查中已经由用户确认的有意精简。

**精简前先向用户展示每一项拟删除或改写的完整内容、理由和方法影响，然后停下等确认。** 用户没确认就不动精简候选，没列入确认表的段落保持翻译基线原文。

精简可以删除与 MMW 无关的上游安装说明、宿主假设，或者已经被当前仓库合同取代的机械细节。精简不能删除形成理解所需的解释、步骤之间的因果关系、例子承担的方法作用或完成判据。

精简单独提交，只含用户已确认的精简，不含 MMW 接线。

## 7. 增加 MMW 接线

从精简候选复制一份接线候选。接线阶段只增加 MMW 工作流，不再翻译、精简或改写已经确认的上游内容。

每条接线先找到当前依据：领域文档、ADR、CLI 行为、`AGENTS.md`，或者 `mmw/skills-src/` 里另一个技能的输入输出合同。Git 历史只能帮助定位理由，不能替代当前依据。

**候选文件按它在 `mmw/skills-src/` 里的最终位置书写，相对引用也从那个位置解析。**

最终目录取 `mmw/skills-src/` 里现役对应技能的**实际目录名**，不要从上游技能名推——`mmw/skills-src/` 下既有 `mmw-grilling` 这样带前缀的，也有 `handoff`、`wizard`、`wait-what` 这样不带的。没有现役对应目录时，先跟用户确认目录名再往下写。

例如 `mmw/skill-rebuilds/grilling/candidate/SKILL.md` 按它最终位于 `mmw/skills-src/mmw-grilling/SKILL.md` 来写。引用同一候选技能里的其他文件时，把它们视为已经一起放进正式目标目录。候选目录里能打开不算数——只有按正式目标位置解析成功，引用检查才通过。

接线规则：

- 把接线放在它承载的上游步骤旁边，保持上游步骤顺序。
- 调用下游技能时只传递下游所需输入，保留下游自己的方法论。
- 复用旧 MMW 接线之前，验证它仍符合当前合同，再按术语统一用词。
- 只增加当前流程必需的 worktree、tracker、报告验证、领域文档、人工审批关卡、资产和宿主动作。
- 使用当前已有的命令、字段、标签、状态和技能名。没有当前依据时不创建新协议或新术语。
- 共享技能源使用宿主无关的完整语义。宿主差异只进入仓库已有的启动块、宿主动作块、profile、adapter 或 manifest。
- 文档拆分只服务真实的 invocation 分支或阶段边界。共享方法保留一个唯一事实来源。
- 仓库持久状态先写入并提交，再让外部 tracker 宣称该状态完成。
- **路由表和分支表必须有兜底行。** 全是正面条件的表，落不进任何一行时 agent 没有指示；写清「以上都不是」时怎么办。
- **一个技能既要写清什么时候接手，也要写清什么时候不接手。** 相邻技能能处理的情况要有一条明确的移交行，否则它会把不属于自己的问题接下来，用自己的方法做。
- 文末 `## 下一步` 只列正文全部执行完成之后可能采取的下一步。选择当前分支、补齐输入、等待中途确认、进入下一内部步骤、中途失败，都不属于文末——它们写在实际发生的那一步旁边。逐行反问：agent 是否已经完成正文才会遇到这项情况？答案为否就搬回去。再检查正文的每一种最终结果是否都列出了下一步。

### 逐条对齐移交合同

「上下游输入输出闭合」要真的去对，不能靠通读一遍觉得顺。每一条移交是一份双向合同，**两边各打开一次**，列成一张表：

| 移交 | 交出方实际给出什么 | 接收方实际需要什么 | 对不对得上 |
| --- | --- | --- | --- |

对不上的有三种，都当场修：

- **接收方要的东西，交出方在某条分支上不产生。** 例如上游要求交回一个索引文件的路径，而下游有一条捷径分支根本不建那个文件。
- **被引用的那一节写死了时机或前提，跟引用它的地方不成立。** 例如某节开头写「完成验证之后再做」，而另一个流程需要提前用它。
- **交出方少给了一个接收方算不出来的值。** 例如接收方要靠某个目录名算路径，而交出方没把这个值一起交过去。

**只查引用路径能不能解析是不够的**：这三种全都发生在引用完全解析得开的前提下。

接线时发现新事实会改变已经确认的方案、方法效果或用户流程，立即停止，报告证据和影响，等用户决定。不改变已确认方案的机械修正直接完成。

接线单独提交。正式技能源保持不变，直到用户批准接线候选。用户没有批准进入发布面时，展示候选和验证结果，然后停止，不进第 8 节。

## 8. 批准后进入 Plugin 发布面

用户批准接线候选后，才把候选内容更新到 `mmw/skills-src/`。

到这里为止本技能不再有额外要求。物化命令、版本号要同步哪几处、架构图和 README 怎么跟、提交前跑什么，全部按 `AGENTS.md` 和根 `TESTING.md` 当时写的执行。

## 9. 汇报

**只写你实际打开过的文件和实际跑过的命令。** 一份「各层都已完成」的清单，跟真的做过之间没有任何区别——你自己分不出来，看的人更分不出来。没跑的写「未验证」。不从上一层推下一层：静态检查绿不代表物化过，物化过不代表在宿主上跑过。

检查术语时打开每一处命中，判断它们指不指同一个概念。词频统计不算。

报「检查通过」之前先确认这次检查真的在检查。按根 `TESTING.md` 自己写的方式跑整段，别改跑法；脚本里有桩或夹具的，先确认它这一次真的生效——桩失活时断言会打到真实环境上给出假结果，比没有这条检查更糟。

翻译基线、有意精简、MMW 接线和正式发布面分别发生了什么，分开写，不用一次总 diff 把四个阶段混在一起。
