# 逻辑原型

一个小的 TUI——终端里的交互界面——让用户手动驱动一套状态模型。问题关于**业务逻辑、状态转移或者数据形状**时走这条——那种纸上看着合理、只有推过真实情形才觉出不对的东西。

适合的问题长这样：

- 「先 X 再 Y 这个边界情形，这套状态机处理得了吗，我不确定。」
- 「这个数据模型真的表达得了……那种情况吗？」
- 「写之前我想先摸摸这个 API 该长什么样。」
- 任何用户想**按按钮、看状态怎么变**的场合。

问题是「它该长什么样」就走错了，回 [UI.md](UI.md)。

## 1. 选语言

用宿主项目在用的那个。项目没有明显的运行时（比如一个纯文档仓库），问用户。

工具链跟着项目现有习惯走，不要为了一个原型引入新的包管理器或者新的运行时。

## 2. 把逻辑隔离成一个可移植模块

真正回答问题的那部分逻辑，放在一个小而纯的接口后面，将来能整块拎出来放进正式代码。外面那层 TUI 是一次性的，**里面这个模块不是**——这是逻辑原型能活过自己这一轮的原因。

状态、转移、schema 和类型形状一律用仓库的语言和业务命名（读 `CONTEXT.md`），这样提升进正式代码时不用改名。

形状按问题选，不按「哪个更好接 TUI」选：

- **一个纯 reducer**——`(state, action) => state`。动作是离散事件、状态是单个值时合适。
- **一台状态机**——把状态和转移显式写出来。「此刻到底哪些动作合法」本身就是问题的一部分时合适。
- **一组纯函数**，作用在一个普通数据类型上。没有隐含的当前状态、只有变换时合适。
- **一个类或模块**，带清楚的方法面。这套逻辑确实自己持有着持续的内部状态时合适。

保持它纯：不做输入输出，不写终端代码，不用打印语句控制流程。TUI 导入它、调用它，反过来不行。

## 3. 覆盖真实存在的状态边界

只演顺利路径的假逻辑不算原型。这套状态模型里实际存在的边界都要能被用户手动走到：成功、失败、空、**被拒绝的非法转移**、并发、回滚。

非法转移尤其要能试：用户按下一个此刻不该合法的动作，程序要明确告诉他被拒绝了、以及为什么，而不是默默什么都不做。「哪些动作此刻不合法」常常就是这一轮真正要判真假的东西。

## 4. 建一个最小的 TUI 把状态摊开

保持它轻：每一拍清屏（`console.clear()`／`print("\033[2J\033[H")`／等价写法），整帧重画。用户任何时候看到的都是一个稳定的画面，不是越滚越长的历史。

每一帧两部分，按这个顺序：

1. **当前状态**，漂亮打印、便于比对（一行一个字段，或者格式化的 JSON）。字段名和小标题用**粗体**，次要信息（时间戳、编号、派生值）用暗色。原生 ANSI 转义就够了——`\x1b[1m` 粗体、`\x1b[2m` 暗色、`\x1b[0m` 复位。项目里已经有样式库才用库。
2. **键盘快捷键**，列在底部：`[a] 添加用户  [d] 删除用户  [t] 时钟前进  [q] 退出`。键位加粗、说明用暗色，或者反过来，怎么读着清楚怎么来。

行为：

1. **初始化状态**——一个内存里的对象或结构体。启动时先画第一帧。
2. **一次读一个按键**（或者一行），分派给一个改状态的处理函数。
3. **每次操作之后整帧重画**——替换，不追加。
4. **循环到退出为止。**

整帧要能放进一屏。

## 5. 交给用户

把运行命令给他，他自己驱动。有价值的时刻是他说「等一下，这不该发生」或者「咦，我以为 X 会是另一样」——那是**想法本身**的缺陷，正是这一轮要找的东西。他要加新动作就加。

## 不能要的写法

- **泛化。** 不要「万一以后要支持 X 呢」。这个原型只回答一个问题。
- **把逻辑和 TUI 糊在一起。** reducer 或者状态机里一旦出现打印、提示、终端转义码，它就拎不出来了。TUI 必须是纯模块外面薄薄一层壳。
