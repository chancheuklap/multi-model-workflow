起一轮审。**审查方法论不在本文**——它在 `mmw-reviewer` 技能里，那是审者读的，你不读也不转述。本文只管编排：哪一道、几路、谁去审、每一路手上给什么。

## 六道审

| 哪一道 | 什么时候起 | 几路（任务名） | 谁去审 | 是不是闸 |
| --- | --- | --- | --- | --- |
| ① spec 审 | spec 写完、自检过了，摆给用户之前 | 设计内容审、项目对齐审 | 两路都派另一家 | 不是。findings 连同你的处置一起摆给用户参考 |
| ② plan 审 | 全部 plan 写完、主线程亲验过、跨 plan 合同回填完之后，起一次 | 覆盖质量审、合规交叉审 | 两路都派另一家 | 是 |
| ③ 逐份验收 | 一个工人交回它那份活 | 不分路 | **你自己**，见下面 | 是。不过这一关不合并回任务分支 |
| ④ 合同门 | 全部 plan 合并回任务分支之后，一次 | 不分路 | **你自己**，见下面 | 是 |
| ⑤ final 终审 | 全部 ticket 落地、合同门过了 | 对照终审、独立终审、编码规范审 | 每一路各派两家 | 是 |
| ⑥ 合并集成审 | 几条并行分支要合到一起 | 不分路，七个角度 | 两家各一个，各走全套 | 是 |

**谁去审由 `docs/agents/models.md` 定，那里也定模型和档位。** 本文不出现型号。红线是每一道审至少有一路审者跟作者不是同一家：spec 是你和用户谈出来的，所以两路都得是另一家；plan 是写计划工人写的，同理；代码是写码工人写的，所以每一路配一个另一家加一个本家，同一路两家的发现互相对账。

## 1. 钉住被审的东西

| 审哪一道 | 钉什么 |
| --- | --- |
| ① | 那份 spec 的路径 |
| ② | plan 目录 `docs/plans/<slug>/` 的路径。**整批一起审，不逐份起**——归属冲突、提供方与消费方对不上、几份 plan 合起来漏了 spec 的某条意图，只有手上同时握着全部 plan 才看得见 |
| ⑤ | 一个固定点，加 `git diff <固定点>...HEAD`（三个点，比的是分叉点）。固定点通常是 `git merge-base HEAD <父分支>` |
| ⑥ | 合并后的 `HEAD`，加各条分支的分叉点 |

用户直接叫你来审、又没说固定点的，问他要。**复审时的固定点不是他第一次说的那个**，见第 8 步。

往下走之前先确认它解析得出来（`git rev-parse`），而且 diff 非空。引用写错或者 diff 是空的，要在这里就失败，不要等审者已经派出去才发现。

## 2. 给每一路备齐材料

审者只拿它这一路判断得上的材料。**多给会坏事**：独立终审那一路要是拿到 spec 和 plan，它就变成第二个对照终审，这一路存在的理由也就没了。

| 任务名 | 这一路的 Source |
| --- | --- |
| 设计内容审 | 这份 spec、走查过的原型产物（`docs/prototypes/<slug>/`） |
| 项目对齐审 | 同上，另加 `CONTEXT.md` 与这块地方的 ADR |
| 覆盖质量审 | spec（含回填后的 `## Cross-Plan Contract Anchors`）、原型产物、全部 ticket、全部 plan |
| 合规交叉审 | 同上 |
| 对照终审 | spec、全部 plan、diff 范围 |
| 独立终审 | **只有 diff 范围** |
| 编码规范审 | diff 范围、仓库自己写下来的编码标准文件；仓库没有就明写「本仓库没有写下来的标准」 |
| 合并集成审 | 各分支的 spec、合并后全貌的 diff 范围、之前的冲突解决记录 |

spec 在哪按这个顺序找：这个分支上的 `docs/specs/<slug>/<slug>.md`；提交信息里引用的 issue（按 `docs/agents/issue-tracker.md` 取）；用户当参数传进来的路径。都找不到就问用户。他说没有，就撤掉需要 spec 的那几路，并在报告里说明。

**路径一律是被审仓库里的路径。** 派发前逐个确认它们真的存在——缺了当场报错，不让审者开工之后才发现。

## 3. 确认方法论装了

无头那一家读的是它自己技能目录里的副本。派之前先确认：

```bash
ls "${CODEX_HOME:-$HOME/.codex}/skills/mmw-reviewer/SKILL.md"
```

不在就先跑 `/mmw-dispatching-agents` 旁边的 `install-agent-skills.sh` 装，再派。会话内那一家不受这个影响，它读插件里的原件。

## 4. 组装提示词，派发

提示词就四行，**不夹带方法论**：

```
任务名：<上表里的任务名，一字不差>
审什么：<被审对象>
Source：<这一路的材料，一行一个；没有写「无」>
复审：<上一轮留痕的路径；首轮写「否」>
```

再加一句告诉它去哪读方法论：无头那一家写它自己技能目录里的路径，会话内那一家写插件里 `mmw-reviewer/SKILL.md` 的绝对路径。**同一路派给两家时，四行内容一模一样**，只有这句路径不同。

写到 `.reviews/<slug>-<哪一道>-<轮次>-<任务名>.prompt.md` 再从那里派（先 `mkdir -p .reviews`，轮次从 1 起）。派发机制按 `/mmw-dispatching-agents`，一条消息里全部发出去，它们并行跑、互不通气。

## 5. findings 落盘

把每个审者交回的东西**原样**抄进 `.reviews/<slug>-<哪一道>-<轮次>.md`，按任务名分组。不要重写，不要摘要。文件顶部记下固定点的提交号。

审者交回的是 `needs-redirection` 或 `needs-context`，不是 findings：

| 收到 | 怎么办 |
| --- | --- |
| `needs-redirection` | 停。它说的是要解决的问题本身可疑，这件事交给用户重新框定，不要自己改产物绕过去 |
| `needs-context` | 看它缺什么。是你没给全就补齐重派这一路；是产物里真的没有这份东西，那本身就是一条 finding |

## 6. 逐条裁判

按 `/mmw-judging-agent-output` 过：自己重新复核每一条的锚，问不修会伤到谁、这一轮该不该花预算修，然后标一个处置词。只有 `accepted` 驱动返工。

**同一路两家都派了的，把两家的 findings 并排对**：只有一家报出来的重点复核，两家同报的可信度高。

## 7. 报告

按任务名分节呈现，每条 finding 都带着它的处置词，包括被判 `rejected` 的那些。**不要跨路合并或者重排。** 一次改动可以过了一路、栽在另一路；分开报，一路才不会遮住另一路。

每一路末尾给出这一路报了几条、采信几条，以及这一路里最严重的那条采信项。不要跨路评出一个总冠军。最后加一行讲搁置的：搁的是什么、现在由哪张 issue 收着。

合并集成审那一路另外要求七个角度各一行结论，原样带上。

## 8. 复审

采信项修好、分支回来时：

- 固定点变成上一轮的 `HEAD`，那一轮的留痕文件顶部记着它。审者只看这次修复的 diff。
- 提示词的「复审」那一行填上一轮留痕文件的路径。审者读到它就知道只验两件事。
- 已经标成 `rejected`、`duplicate` 或 `waived` 的，没有新证据不许再提。
- 同一条 `accepted` 修过两轮还在，停下来——见下一步表。

## ③ 逐份验收：你自己做

一个工人交回它那份活时，你当场亲手核三关。**三关都过才允许合并回任务分支。**

1. **做漏没有** —— 派给它的那份东西（ticket，有 plan 那一层的话是 plan）每条验收标准真达成了吗。跑验收命令、读 diff，不认「我做完了」。
2. **测试达不达标** —— 工人写的测试它自己说了不算。按 `/mmw-tdd` 那份进仓资格线逐条核，加上目标仓库根 `TESTING.md` 补的本仓库事实。不达标就是缺陷，打回重写，别将就。
3. **有没有偏离** —— 落地有没有跑偏它上游那份东西的意图、合同、边界。

有问题写修复指令发回原会话续做，上下文还在工人那里。工人卡在派给它的那份东西与代码互相矛盾上，它报告的是上游的问题，不是它自己的问题，这件事交给用户。

这一关不派审者，因为要的是跑测试读 diff 这种亲手动作，不是第二双眼睛。

## ④ 合同门：你自己做

全部 plan 合并回任务分支之后跑一次，**只核一件事**：spec 的 `## Cross-Plan Contract Anchors` 一节里每条跨 plan 合同，在合并后的代码里真兑现了。那一节是 `/mmw-to-plan` 第 2 步写骨架、第 5 步回填精确字段的，不是 spec 阶段那节 `## Contract Boundaries`——后者讲业务上有哪些边界，前者讲这些边界落到哪一份 plan 头上。

- 提供方声明的接口、类型、端点、数据结构真存在——grep 到定义，给出 `文件:行号`。
- 消费方真按那个接口对接，调用点的签名对得上。
- 合同版本号一致；新字段配套的迁移在位；新增的可被外部引用之物入了登记。

**核不出行号就不算兑现。** 这一道不做主观代码评审，那是终审的活。

没有跨 plan 合同（只有一份 plan，或者那一节写明了无），把这件事连同你据以确认的位置一起记下来，不要跳过不写。

## ⑥ 合并集成审：先解冲突，再起审

几条并行分支要合到一起时走这一道。**冲突解完才起审**——审者判的是合并后的事实，工作区里还留着冲突标记，它看到的就不是最终形态。

解冲突五步：

1. **看清现状**：git 历史，以及哪几个文件在冲突。
2. **查清每一处冲突两边各自要做什么**：读提交信息、PR、原始 issue，弄清两边为什么这么改。
3. **逐块解**。双方的意图都保住；确实不兼容的，选符合这次合并目标的那一个，并把这个取舍记下来——七个角度里的最后一个会审它。不发明新行为。一定要解出来，不用 `--abort`。
4. **跑这个项目自己的检查**：类型检查、测试、格式化。合并弄坏的当场修。
5. **完成合并**：暂存、提交。在 rebase 的一路继续到所有提交都 rebase 完。

然后按第 1 到 8 步起审，两个审者各走全套七个角度。第 3 步记下的那些取舍，连同各分支的 spec 一起给它们。

## 下一步

| 情况 | 下一步 |
| --- | --- |
| 裁判完了，一条 `accepted` 都没有 | **移交**：回到把你叫起来的那个技能，由它决定往下走 |
| 有 `accepted` 的 findings | **移交**：回到调用方，由它把这些打包成一张修复 ticket 派给新工人；修完再回本技能第 8 步复审 |
| 用户直接叫你来审，没有调用方 | **停**：报各路几条、采信几条、最严重的是哪一条，让他定这一轮修不修 |
| 第 1 步的固定点解析不出来，或者 diff 是空的 | **停**：说清是哪一种，让用户重新给。不要带着坏引用往下派审者 |
| 收到 `needs-redirection` | **停**：把审者说的「哪里可疑、建议怎么重新框定」原样交给用户。方向的事不由你替他定 |
| 收到 `needs-context`，且缺的东西产物里真的没有 | **自己继续**：把这件事本身记成一条 finding，接着裁判其余各路 |
| 第 3 步发现方法论没装 | **自己继续**：跑 `install-agent-skills.sh` 装好再派，不要改成把方法论粘进提示词 |
| ③ 三关有一关不过 | **自己继续**：写修复指令发回原会话续做，别合并 |
| ④ 有合同核不出行号 | **停**：报是哪条合同、提供方或消费方缺在哪。这是落地漏了，不是审出来的意见 |
| ⑥ 解冲突时两边意图确实不兼容，而这次合并的目标不足以判 | **停**：报是哪一处、两边各自要做什么，让用户定保哪一个 |
| 同一条 `accepted` 修过两轮还在 | **停**：报这条修了两轮还在，并说出你的判断——是修错了地方，还是当初不该采信 |
