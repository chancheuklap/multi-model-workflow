# 合并集成审

**谁读**：任务名是「合并集成审」的审者。**两个审者同读这一份，各自把七个角度全部走一遍**，不像别处那样分两路。七个角度是一张检查清单，不是两种对立的看法，分走就变成各查一半；两家各走全套，重叠的部分正好互为交叉验证。

这一路审的不是某一份 plan 落得对不对，也不是某一条分支的意图闭没闭环——那些各分支自己的终审已经过了。这一路审的是**几条并行分支合到一起之后，系统整体还对不对**。它们各自都对，不等于合起来对。

材料里应该有各分支的 spec、合并后的全貌、以及之前解冲突的记录。自己跑 `git diff <base>..HEAD` 看合并后的样子。

## 七个角度，逐条给结论

1. **组合行为**：全部分支合在一起，产出的是各份 spec 描述的正确行为吗。各自对不等于组合对，盯交互、顺序、依赖。
2. **合同一致**：跨分支的数据模型、接口、数据库结构、序列化格式、登记表一致吗。一个分支提供的合同，被另一个正确消费了吗。
3. **迁移完整**：多个分支的数据迁移合并后顺序对吗；有没有漏（这条改了模型，那条没配套迁移）；回滚安全吗。
4. **状态一致**：跨分支对同一份共享状态、缓存、全局配置的假设一致吗；并发访问安全吗。
5. **模块引用**：合并后有没有循环引用；依赖版本一致吗。
6. **回归**：合完之后既有功能完好吗。跑完整测试套件，报结果。
7. **冲突修复质量**：之前解过冲突的，修得正确、完整吗；有没有引入新问题。

## 校准

**不信各分支自己终审的结论**——独立验组合行为。判断基于合并后的代码事实，不基于各分支独立审出来的结论。

只标会导致实际问题的 finding，每条带证据。单个分支内部的代码质量已经在它自己的终审里覆盖过了，不重复审；措辞、命名、风格不算 finding。

## 交回时多给一段

除了共用纪律要求的 findings 和证据表，另外给一段：上面七个角度**各一行结论加证据**。走完了没发现问题的角度也要写那一行，写「已确认」加你据以确认的东西。
