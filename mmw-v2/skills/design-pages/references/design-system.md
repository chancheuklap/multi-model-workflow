# design system — Claude Design builds it from running code, before any page is drawn

The design system exists before the first page is written. Its source is code that already runs, never a reverse extraction of a rendered product. It is a Claude Design design system in full, as **What Claude Design requires** lists, with the rules of **What MMW adds** on top.

## Which code

- **A new product, or a remake that changes the look** — the prototype's winning variant; on a wayfinder map, the winners the state list gathers (the `prototype` skill's `UI.md` step 6). After the product ships, later changes take the product code as the source.
- **An existing product that keeps its current look** — the style variables and shared components (button, badge, banner, dialog, and the like) already in the product. Extracted values are reviewed before they become the standard; current defects are not copied in as rules. Skip this entry when a design system already exists and those shared components have not changed.

A remake is a new interface that does **not** keep the old look. An interface that keeps the old look is the existing-product case, even if the rest of the product is being rewritten.

## What Claude Design requires

Taken from Claude Design's own design-system instructions and the built-in Classical system (checked 2026-09-21). A design system missing any of these shows gaps in Claude Design itself: an empty Design System tab, no components for pages to mount, nothing to start a page from.

- `styles.css` at the root, made of `@import` lines only. It reaches the token files (custom properties on `:root`: base values and semantic aliases), the `@font-face` rules, and the component stylesheets. The font files those rules name ship with it.
- `readme.md`: the product and its sources; CONTENT FUNDAMENTALS (how copy is written); VISUAL FOUNDATIONS (colour, type, spacing, backgrounds, motion, hover and press states, borders, shadows, radii, cards); ICONOGRAPHY; an index of the files, components and UI kits; and "Intentional additions", every component the source does not define, with its reason.
- Foundation cards: small HTML files whose first line is `<!-- @dsCard group="…" viewport="700x<height>" name="…" subtitle="…" -->`, each linking `styles.css`. Twelve to twenty or more, split by sub-concept. The Design System tab shows every tagged file.
- Components: `<Name>.jsx` with a named export (React only), `<Name>.d.ts` with the props, `<Name>.prompt.md` with what, when and a usage example; one `@dsCard` card per directory that mounts them from `_ds_bundle.js`. The inventory is the source's, complete: every family it defines, none it does not.
- UI kits: one directory per product surface under `ui_kits/`, an interactive `index.html` recreating the real screens from the components, tagged `@dsCard`. A screen that seeds new pages carries `<!-- @startingPoint section="…" subtitle="…" viewport="WxH" -->` as the first line of its own HTML file.
- Assets copied from the source, never drawn; an icon set the source loads from a CDN is named, not redrawn.
- `SKILL.md`, the design system as an agent skill for download.
- `_ds_bundle.js`, `_ds_manifest.json` and `_adherence.oxlintrc.json` are generated by Claude Design's compiler and never written by hand. That compiler runs only inside Claude Design: files written from outside through MCP or the design-sync tool leave both unchanged (checked 2026-09-21).

## What MMW adds

1. **A component renders the source's own DOM**: the same elements, class names and nesting the source code produces, styled by the source's own CSS rules in a stylesheet `styles.css` imports. A design page built from components and the product built from the same code then compare element to element under the story judge.
2. **A component takes a `data-ui` prop**, sets it on its root, and sets `<data-ui>.<part>` on each part the brief lists for it. A page gives each component its `data-ui` id; the component stamps its own parts.
3. **A UI kit per surface of the winner** (a region of the state list), and one `@startingPoint` screen per region, so edit pages starts each `Component · ` page from it rather than drawing it again.
4. **Values copied exactly** (pixels, colours, line heights), font files copied from the source, never substituted.

## Which path

**React code.** Ask the user to start the design-sync command that ships with Claude Code (its description limits it to a React design system; its product is `_ds_bundle.js`). For React code this skill calls none of that command's tools itself. Then run step 3 below.

**Anything else** (Jinja templates, a plain JavaScript prototype). Claude Design builds it, because its compiler runs only there:

1. Fill [template-design-system-brief.md](template-design-system-brief.md) from the code and save it as `design-system-brief.md` in the leaf directory that holds the state list. The component inventory is the one part to get exhaustively right: every shared piece of markup the code renders more than once, with its file and its parts.
2. The user attaches the codebase in Claude Design (the GitHub repository, or the local folder), opens "Set up your design system" for a new one or the design system's "Remix" for an existing one, and pastes the brief.
3. Check the result through MCP: `list_files` on the design system with `depth: -1`, then `read_file` of `_ds_manifest.json`. Every inventory family has a component; the foundation cards number at least twelve; each `ui_kits/<surface>/` has its `index.html` and one `@startingPoint` screen per region; the manifest lists the fonts; `readme.md` has each heading **What Claude Design requires** names; `SKILL.md` exists. Each miss is one line; hand the list to the user to paste into the same Claude Design chat, and check again. Done when nothing is missing.
4. The user switches the design system's "Published" toggle on (Settings > Design systems). Its id is the UUID after `/design/p/` in its link; [edit pages](edit-pages.md) binds the project with it.

This happens once per product. The repository keeps the brief, not a second copy of the design system: from then on the design system in Claude Design is the source, and each page project carries the `_ds/` copy [edit pages](edit-pages.md) makes.

## After the values change

Change the source code first, then Remix the design system with a brief naming the changed files, and check again as step 3 says. A page project's `_ds/` copy does not follow: copy the changed files into it again (edit pages, **Create the project** step 4), then [pull](pull.md).

`_adherence.oxlintrc.json` is not a check this skill runs: the agent inside Claude Design has no linter, and those rules do not reach CSS in a `.dc.html` `<style>` block.
