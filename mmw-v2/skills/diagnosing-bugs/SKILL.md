# Diagnosing Bugs

一套对付难以定位的 bug 的纪律。跳过某个 Phase 要给出明确理由。

探索代码时读 `CONTEXT.md`（如果有），先对相关模块建立清楚的心智模型，并且读一遍你要碰的这块地方的 ADR。

## Phase 1 —— 造一个反馈 loop

**这是本技能的核心。** 其余都是机械动作。手上有一个 **tight** 的通过／失败信号——一个会因为*这个* bug 变 red 的信号——你就一定能找到原因；二分、验假设、埋点，全都是在消费这个信号。手上没有，盯着代码看再久也无济于事。

在这里花不成比例的力气。**主动尝试，换角度，不要放弃。**

### 怎么造出来——大致按这个顺序试

1. **失败的测试**，放在任何一个够得到这个 bug 的 seam 上——单元、集成、e2e 都行。
2. **curl / HTTP 脚本**，打一个跑着的 dev server。
3. **CLI 调用**，喂一份 fixture 输入，把 stdout 和一份已知正确的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动界面，对 DOM／console／网络下断言。
5. **回放抓下来的 trace。** 把一次真实的网络请求／载荷／事件日志存到磁盘，隔离出来在那条代码路径上回放。
6. **一次性 harness。** 起一个最小子集（一个服务，依赖打桩），用一次函数调用就走到出 bug 的那条路径。
7. **属性／模糊测试循环。** bug 表现为「有时候输出不对」，就跑 1000 个随机输入，找那个失败形态。
8. **二分 harness。** bug 是在两个已知状态之间（提交、数据集、版本）出现的，就把「在状态 X 启动、检查、重复」自动化，让 `git bisect run` 跑得起来。
9. **对照循环。** 同一份输入分别过旧版本和新版本（或者两套配置），diff 输出。
10. **HITL bash 脚本。** 最后手段。必须有人点鼠标时，用 `scripts/hitl-loop.template.sh` 去驱动*那个人*，让循环仍然有结构。抓下来的输出回流给你。

把对的反馈 loop 造出来，这个 bug 就修好了九成。

### 把 loop 收紧

把这个 loop 当产品对待。手上有了*一个* loop 之后，把它**收紧**：

- 能更快吗？（缓存初始化、跳过无关的启动、把测试范围收窄。）
- 信号能更锐吗？（对准那个具体症状下断言，而不是「没崩」。）
- 能更确定吗？（钉住时间、给 RNG 播种、隔离文件系统、冻结网络。）

一个 30 秒还会抖的 loop 比没有 loop 好不了多少；一个 2 秒的确定性 loop 是 **tight** 的——它是调试效率的分水岭。

### 非确定性的 bug

目标不是一个干净的复现，而是**更高的复现率**。触发条件循环 100 次、并行跑、加压、把时间窗收窄、注入 sleep。50% 概率出现的 bug 是能调的，1% 不能——把复现率一直往上抬，抬到能调为止。

### 确实造不出 loop 的时候

停下来，明说。列出你试过什么。然后向用户要：(a) 能复现它的那个环境的访问权，(b) 一份抓下来的产物（HAR 文件、日志转储、core dump、带时间戳的录屏），或者 (c) 往生产环境加临时埋点的许可。**没有 loop 就不要往下提假设。**

### 完成判据 —— 一个会变 red 的 tight loop

Phase 1 完成的标志是这个 loop 既 **tight** 又 **red-capable**：你能说出**一条命令**——一个脚本路径、一次测试调用、一条 curl——而且你**已经至少跑过它一次**（把调用和它的输出原样贴出来），并且它：

- [ ] **red-capable** —— 它走的是真正出 bug 的那条代码路径，断言的是**用户说的那个确切症状**，所以它会因为这个 bug 变 red、修好之后变绿。不是「跑起来没报错」——它必须能*抓到这个具体的 bug*。
- [ ] **确定** —— 每次跑结论一样（会抖的 bug：按上面的做法，钉住一个高复现率）。
- [ ] **快** —— 以秒计，不是以分钟计。
- [ ] **agent 能跑** —— 你能无人值守地跑它；要人参与就只经由 `scripts/hitl-loop.template.sh`。

发现自己在这条命令还不存在的时候就开始读代码建理论，**停下——直接跳到假设正是本技能要防的那个失败**。没有 red-capable 的命令，就没有 Phase 2。

## Phase 2 —— 复现 + 最小化

跑那个 loop。看着它变 red——bug 出现了。

确认：

- [ ] 这个 loop 产出的是**用户**描述的那个失败形态，不是旁边碰巧出现的另一个失败。定位错 bug 就会修错东西。
- [ ] 这个失败多跑几次都能复现（非确定性的 bug：复现率高到足以对着它调）。
- [ ] 你已经把那个确切症状记下来（报错信息、错误输出、慢了多少），后面的 Phase 要靠它验证这次修复真的对上了。

### 最小化

变 red 之后，把 repro 缩到**还能变 red 的最小情形**。输入、调用方、配置、数据、步骤，**一次去掉一样**，每去掉一次重跑一遍 loop——只留对这个失败承重的部分。

这么做的收益：最小 repro 把 Phase 3 的假设空间缩小（剩下可疑的活动部件更少），并且它会在 Phase 5 变成那个干净的回归测试。

**剩下的每一样都是承重的**——去掉任何一样 loop 就变绿——这时候算完成。

复现**和**最小化都完成之前不要往下走。

## Phase 3 —— 提假设

在验证任何一条之前，先生成 **3 到 5 条排好序的假设**。只生成一条会让你锁死在第一个看起来合理的想法上。

每条假设都必须**可证伪**：把它做出的预测写出来。

> 格式：「如果 <X> 是原因，那么 <改动 Y> 会让 bug 消失／<改动 Z> 会让它更严重。」

预测写不出来，这条假设就只是直觉——丢掉，或者把它写得更精确。

**验证之前把排好序的清单给用户看。** 他常常有领域知识能当场重排（「我们刚给第 3 条那块发过版」），或者知道哪些他已经排除过。这个检查点成本很低，省下的时间很多。不要停在这里等——用户 AFK 就照你的排序往下走。

## Phase 4 —— 埋点

每一个探针都要对应 Phase 3 里的某一条具体预测。**一次只改一个变量。**

工具优先级：

1. **调试器／REPL 检查**，只要环境支持。一个断点抵得上十条日志。
2. **定点日志**，放在能区分开各条假设的边界上。
3. 不要「全都打日志然后 grep」。

**每条调试日志都打标记**，用一个唯一前缀，例如 `[DEBUG-a4f2]`。这样最后清理就是一次 grep。没打标记的会残留，打了标记的会被清掉。

埋点由你自己动手，不派工人。这些日志在 Phase 5 开始前全部删掉，一行都不进最终 diff，所以它们不会让你成为这次修复的作者。

**性能分支。** 性能回退的问题，日志通常是错的工具。改成：先建立一条基线测量（计时 harness、`performance.now()`、profiler、查询计划），然后二分。先测量，后修复。

## Phase 5 —— 修复 + 回归测试

**修复这一步派 Codex 无头工人做，你不自己写。** 你在前四个 Phase 里拿到了工人拿不到的东西——一个 red 的 loop、最小化的 repro、验证过的那条假设。把这些交给它。你自己不写代码，才有资格裁判后面审出来的 findings（`docs/agents/models.md`）。

回归测试**写在修复之前**——前提是存在一个 **correct seam**。

correct seam 是指：测试在调用点上跑的是**真实的 bug 形态**。手上唯一能用的 seam 太浅（bug 要多个调用方才出现，测试却只有单个调用方；单元测试复现不了触发这个 bug 的那条链），放在那里的回归测试给的是虚假信心。

**没有 correct seam，这件事本身就是发现。** 把它记下来。代码架构挡着，这个 bug 锁不住。留给下一个 Phase。

有 correct seam 的话：

1. **先把工作区清干净。** grep `[DEBUG-` 前缀，把 Phase 4 的埋点全删掉。工人要在可写 sandbox 里跑，工作区不干净你就分不清哪些改动是它的（`dispatching-agents`）。
2. 按 `dispatching-agents` 派一个工人，简报从文件和你已经跑过的内容里取，包含：

   | 给它什么 | 内容 |
   | --- | --- |
   | 复现命令 | 命令本身，加上你跑它时看到的输出原文 |
   | 最小化的 repro | 场景，以及每一样为什么是承重的 |
   | 那条假设 | 被验证的那条，以及验证它的那次观测 |
   | seam | 测试放在哪一层、断言什么——这条由你定，工人问不到人 |
   | 纪律 | `worker-brief.md` 与 TDD 全文，取法见 `implement` 第 3 步 |

3. 工人要跑的循环是：在那个 seam 上把最小化 repro 变成一个失败的测试，看它红，写修复，看它绿。

它交回来之后按 `judging-agent-output` 验收：自己把那个测试跑一遍，读它的 diff，再拿 Phase 1 的 loop 对着**原始的、没最小化的**场景跑一次。

## Phase 6 —— 清理 + 复盘

宣布完成之前必须满足：

- [ ] 原始的复现不再复现（重跑 Phase 1 的 loop）
- [ ] 回归测试通过（或者没有 seam 这件事已经写下来）
- [ ] `[DEBUG-...]` 埋点全部不在了（grep 那个前缀确认）
- [ ] 一次性原型已删除（或者挪到一个明确标出来的调试位置）
- [ ] 结果证明成立的那条假设写进了工人那次提交的信息里，或者由你追加一条评论——好让下一个人从中学到东西

**然后问：什么本来能防住这个 bug？** 答案要是牵涉架构改动（没有好的测试 seam、调用方互相缠绕、藏着的耦合），就带着具体情况移交 `/improve-codebase-architecture`。这个建议在修复落地**之后**给，不在之前——你现在掌握的信息比开工时多。
