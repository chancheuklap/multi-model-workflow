代码已经落地，终审过了。这一步把设计文档搬到它的长期落点，再把工作区收干净。

**Wiki 是这份 spec 之后唯一的真相源。** 完整约定在 `docs/agents/wiki.md`——命名、一页放什么、导航怎么生成、三条核验，全在那里，本文不复述。这里写的是这次收尾按什么顺序做。

## 前置条件

四件事必须满足，缺一件就停下说清是哪一件。

| 检查 | 怎么查 |
| --- | --- |
| 你在任务 worktree 里 | `git rev-parse --show-toplevel` 以 `.worktrees/<slug>` 结尾 |
| 终审跑过，采信的 findings 都修完并复审通过 | `.reviews/` 里有终审报告；采信项各自有对应的修复提交 |
| 工作区干净 | `git status --porcelain` 是空的 |
| Wiki 已初始化 | 按 `docs/agents/wiki.md` 的检测命令查。没初始化就停，只能由用户去仓库的 `/wiki` 页手建一页 |

没有 spec 的任务不走这一步。诊断一个 bug 修完就结束，没有要归档的设计文档。

## 1. 取 Wiki 的工作副本

按 `docs/agents/wiki.md` 的落点那一节 clone 或 pull 到 `.worktrees/.wiki/`。

## 2. 写这一页

文件名 `Spec-<slug>.md`，五段的内容按约定那份文件里的表格写。

内容从这个分支上取：`docs/specs/<slug>/` 的定稿进 spec 正文，`docs/plans/<slug>/` 的每一份进计划章节，一张 ticket 一节。

落地信息这一段写父 spec issue 的链接、这条任务分支的名字、归档日期。**合并的 PR 这时候通常还不存在**——分支要等用户批准才合，所以先写分支名，合并之后再补。

相关决定那一段只放指回仓库 `docs/adr/` 的完整链接，绝不把 ADR 复制进来。

slug 相同的那一页已经存在，就是同一份 spec 的演进：覆盖它，在页尾追加一条修订记录。

## 3. 重新生成两个导航文件

`Home.md` 和 `_Sidebar.md` 每次写入后都要重新生成，跟这一页一起提交。

条目从 `.worktrees/.wiki/` 下现有的 `Spec-*.md` 全量取，不要只往旧文件上追加一行——别的会话可能也归档过，追加会漏掉它们。每一页的一句话和落地日期从它自己的抬头和落地信息那两段读。

## 4. 摆给用户，等他点头

**推送到 Wiki 是出站动作。** 把 `git -C .worktrees/.wiki diff` 给他看，等他明确同意再推。

## 5. 推送，核验

推送之后跑约定那份文件里的三条核验。**三条全过才允许往下走**，任何一条不过就停下报告——本地文档一删就没有第二份了。

## 6. 删本地文档，提交

三条核验全过之后，在任务分支上删掉 `docs/specs/<slug>/` 与 `docs/plans/<slug>/` 并提交。主线因此不留 spec 和计划文档，不会随项目演进变成过时残留。

**`docs/prototypes/<slug>/` 不删。** 那里面的逻辑模块会被搬进正式代码，界面变体是视觉契约的出处；删掉它，下一个人只能重新验一遍。

## 下一步

| 情况 | 下一步 |
| --- | --- |
| 六步都做完 | **停**：用业务语言交代现在什么能用了、什么证明它能用、这份 spec 归档到了哪一页、什么搁置了搁到哪里。分支可以合并了，合并和清理 worktree 由用户批准 |
| 第 4 步用户不同意推送 | **停**：问清他要改哪里，改完重走第 2 步 |
| 第 5 步三条核验有一条不过 | **停**：报是哪一条、看到的是什么。**不要删本地文档**，也不要重推一遍指望它自己好 |
| Wiki 还没初始化 | **停**：告诉用户去仓库的 `/wiki` 页建一页任意内容。没有 API 能替他建，不要试着绕 |
| 终审还没跑，或者还有采信的 findings 没修完 | **停**：说清缺哪一样。回 `/mmw-implement` 第 7 步起终审，或者按 `/mmw-review` 第 8 步复审 |
