### Make a small change

**The user checks this change directly.**

This playbook builds and delivers a change small enough that the user will check it directly, with no spec, no tickets and no night. This path has none of what a ticket brings: no criteria a script runs, no reviewer in a session of its own, no closed ticket as the record. So what this session misses reaches the user, unless a reader who did not write the change finds it first. The temptation is to call the change too small for that reader; run **Get a second reading** however small it is.

1. **Write it test-first.** Run the `tdd` skill in this session, to build a concrete behaviour test-first without a spec or tickets. The code you write follows `references/code-writing-rules.md`. A test that would still pass with the change undone gives the user's check nothing to stand on (**principle-test-behavior-not-implementation**).
   Done when every behaviour the change adds or alters has a test at a seam the user confirmed, and each of those tests failed before its code was written and passes now.
2. **Run the checks.** Run type checks and single test files regularly while you work. At the end, run only the tests the repository names for the code this change touches; a full suite runs only when `shared.md` rule 15 allows it. Read what each run ran: a run that collected no test, or none that reach the changed code, has checked nothing (**principle-silence-is-never-a-pass**).
   Done when, on the final code, the repository's type checks and the tests it names for this change pass, and each run's output shows it ran tests that reach the changed code.
3. **Get a second reading.** Start one general-purpose subagent in one message, with a brief filled from `references/subagent-brief.md` that keeps its read-only sentence, and wait for it. Fill `{TASK}` with the commit this change started from and this question: which parts of the change from that commit to the working tree are wrong, missing, or more than the request in `{MATERIAL}` asks for, and at which file and line is each? Paste the user's request into `{MATERIAL}` word for word, since the subagent cannot read this conversation; ask in `{RETURN_FORMAT}` for one line per finding with its file, line and reason, and set `{WORD_LIMIT}` to 400. Do not tell it which parts you believe are right: the user would then check a change only you have judged (**principle-a-second-reader-judges**). Check each finding against the code before you act on it: fix what holds, and keep what does not for the Reply with your reason. On a host that cannot start a subagent, tell the user to open a new session and give it the same brief, and list the second reading in the Reply as not done until that session's answer comes back. Reading the change again in this session is not a second reading.
   Done when the subagent has returned and each of its findings is fixed or kept for the Reply with a reason, or, on a host that cannot start a subagent, the user has the brief and the Reply lists the second reading as not done.
4. **Deliver.** Run **Deliver a change**.
   Done when the change is committed, or the user has heard each step of its delivery that remains.

**Reply:** what changed; how it was verified, naming the checks and tests that ran; why each new file or dependency was needed; what the user should check; and, while the second reading is still with a new session, that it is not done.
