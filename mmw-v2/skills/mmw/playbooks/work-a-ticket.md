### Work a ticket

**You own this ticket's branch until its closeout. The orchestrator lands it.**

A dispatched worker's session has nobody watching; an adopted one may have the user present, and mode `## Autonomy` says which applies. The reviewer judges the branch from the ticket and your decisions comment, and the user reads your closing comment in the morning, cold, with none of this session's context. The temptation in a ticket is to make it close: to loosen what it was told to follow, or to call a round done because the tests you wrote are green. Green is what a recorded run of the ticket's criteria says, never the tests you wrote. A ticket handed back with its reason on it is a good result; a ticket closed on a bent check is a defect that lands under a green mark.

Commands of this skill's `bash scripts/dispatch.sh` and `python3 scripts/ticket_state.py` are named bare below.

**Entry.**
- **Started by `start`.** The start prompt names **Claim**. Read the file its `Data:` names first: it holds the installed paths and the Memory indexes.
- **Adopted ticket.** You picked the ticket up yourself; no `start` is behind you. Run `bash scripts/dispatch.sh adopt <n>` first: it records you as the ticket's worker and makes sure a relay watches the ticket. Without it no event names your session, so your reviewer's report would wake nobody, and `start <n> reviewer` would refuse. Run it from the ticket's worktree on branch `issue-<n>`, before claiming; outside a night add `--into <base branch>`. Exit 2 adopted nothing; its stderr names what to fix. Exit 0 prints `<session> · Data: <file>`: read that file before claiming, since, like the file a start prompt names, it holds the installed paths and the Memory indexes.
- **Woken.** Go to the step the wake's pointer names, after mode `## Re-entry`.
- **Compacted, or unsure.** **Where you are.**

**Where you are.** Run `dispatch.sh where <n>` and go to the step it prints.

#### Steps

1. **Claim.** First claim the ticket: `ticket_state.py <n> --claim`. On `NOT_READY`, stop: the reason is already on the ticket. The branch may already carry the commits of an earlier worker of this ticket whose session ended, among them a `wip(#<n>): uncommitted work of …` commit holding what it left uncommitted. They are this ticket's work: carry on from them.
   Done when `--claim` exits 0.
2. **Read yourself in.** Read yourself in, until you know what this ticket delivers, what it must not contradict, and the words the repository uses for them: the ticket in full, comments included, and its own open children (the `verify-ticket` skill's `python3 scripts/issue_tree.py <n> --root ticket` prints each child with its state), as a supplement to **What to build** (whether you do them goes under `Decisions I made on my own`); then every item under its **Read first**, each through to its conclusion: the part of a research file that answers its question, an ADR's decision in the untitled paragraph under its title, a design package pulled into the repository, a prototype's leaf `README.md` read to its verdict. `#### Reading yourself in` says how to read a baseline among them, then the spec, the glossary and the Memory records.
   Done when you can name what this ticket delivers, what it must not contradict and the repository's word for each, and every item under **Read first** has been read to its conclusion.
3. **Write the code.** Read the `tdd` skill's `SKILL.md` and follow it where possible, at pre-agreed seams. Working from a ticket, the seams under test are the ones its `## Seam` section names. Where an acceptance criterion's `CHECK:` names a test case, that case is your first red test: run it before writing the code it covers and read why it fails. Red that comes from a missing file, an import error or a typo in the case name proves nothing; the test counts as red only when it fails because the behaviour is absent. No later step does this for you: the claim-time baseline ran before the test existed, and the review reads tests without running them. `#### While writing code`, `#### While the product runs` and `#### Unattended outlets` hold until the closeout. Once done, commit your work to the current branch.
   Done when every point under **What to build** is implemented and committed, and each test case a `CHECK:` names went red for the absent behaviour before its code was written.
4. **Integrate and run every criterion.** Integrate `origin/<base branch>` first: `dispatch.sh integrate <n>`, from this ticket's worktree. `#### Integrating` says what each exit asks of you, 0 included. Then run every criterion: `ticket_state.py <n> --run-and-record-criteria`. Exit 3: no product slot was free and nothing ran; end your turn, and on the `#<n> worker.queued` wake, ack it and run the same command again. Whatever wakes you, first do what mode `## Re-entry` says: a wake can cut short a command you were running, and that section runs it again before anything else; the ack in the sentence before is the one that section asks for. How many rounds a criterion gets is your judgement: keep fixing while a fix is in sight, and when none is, give it the line `ABANDON: AC<n> failed <what each round tried>`, which **Draft the closing comment** puts in the closing-comment draft, and carry on with the rest; the closeout counts no rounds, so that line is the whole record of the trying. The kinds of `ABANDON` line are in `#### ABANDON kinds`.
   Done when `ticket_state.py <n> --run-and-record-criteria` has recorded a run of your own after the integration.
5. **Post the decisions.** Post the decisions comment, once: `ticket_state.py <n> --decisions <file>`. The file is two sections, each opened by its `## ` heading: `## Decisions I made on my own`, with every line written so far, one per line, in the shape the closing comment uses; and `## Outside Owns`, with the `Outside Owns:` line of your newest run (its `ticket.checked` event, run `self`), followed by one sentence per file saying which criterion could not pass without it; `None` when that line is `None`. It is posted here, before the reviewer starts, so the review judges every line of it, and once: the review's fix round adds nothing to it, and the closing comment carries the final version.
   Done when `--decisions` exits 0.
6. **Get reviewed.** Start the reviewer: `dispatch.sh start <n> reviewer`, then end your turn (**principle-a-second-reader-judges**, **principle-agents-are-woken-not-polled**). You are woken with `#<n> reviewer.reported` once its report is on the ticket. On that wake, first do what mode `## Re-entry` says: a wake can cut short a command you were running, and that section runs it again before anything else; the ack in the next sentence is the one that section asks for. Then read the report, the comment on the ticket that carries that event (`dispatch.sh result <n> reviewer` prints the event with the two commits it read), and `dispatch.sh ack <n> reviewer.reported`. Start exits 2: when its stderr says to start again, run it once more; any other exit 2, or a second one, is a pipeline fault: open the `fault` child as `#### Opening a child` says, then stop. One reviewer per round; after `reviewer.lost`, start another. Then work its findings as `#### The review round` says.
   Done when the review report is on the ticket (a session's state never is), each in-ticket finding is fixed or `refuted:`, and each out-of-ticket finding still true has its `finding` child.
7. **Run every criterion one final time.** Run every criterion one final time: `ticket_state.py <n> --run-and-record-criteria --reverify --actor worker`. It runs after the last step that writes a commit, including the review fix, and includes criteria earlier runs already ticked. If anything still fails, write `ABANDON: AC<n> failed` for each failure; the closeout will be `HANDOFF REQUIRED`, and you carry on with **Audit against the ticket**. This final run gets no fix round.
   Done when the final run is on the ticket at `HEAD`.
8. **Audit against the ticket.** (judgement) Read the ticket once more against the branch, the way the user will read your closing comment. Each point under **What to build** holds in the product, not only in a test, and each baseline under **Read first** is followed where it applies (**principle-prove-it-works**). A point that does not hold is said in the closing comment; nothing is committed after the final run. Write what this reading found as one sentence on the `Audited against the ticket:` line of the closing-comment draft, when **Draft the closing comment** fills it.
   Done when you can name, for each point and each baseline, where the branch follows it or the line of the closing comment that says it does not.
9. **Tell the touched tickets.** Tell the tickets whose files you changed: `ticket_state.py <n> --touched`.
   Done when `--touched` exits 0.
10. **Draft the closing comment.** Cut loose what only a person can settle, then write the closing-comment draft. A criterion that waits only on one sentence from a person: write `ABANDON: AC<n> decision <question, options, and the default if nobody answers>` **and** run `ticket_state.py <n> --open-child decision <file>`, then keep working the rest; the ticket does not stop. Then `ticket_state.py <n> --closing-draft`, which prints the path it wrote as `DRAFT: wrote <path>`; give that run no path of your own. Fill every `<fill>`: `skipped:` as `[X], add when [Y]`; each review finding as `fixed <commit>` or `refuted: <what actually happens at path:line>`; each criterion under `Green before work:` with the landed ticket that did that work, or with the fact that this `CHECK` cannot see this ticket's behaviour (then also a `contract` child); `Decisions I made on my own` with every line written so far. Put each `ABANDON:` line under its criterion.
    Done when the closing-comment draft has no `<fill>` left.
11. **Close out.** Close the ticket: `ticket_state.py <n> --closeout <draft>`. Never close the ticket or swap its labels yourself: a hook blocks the command. Open no pull request: the orchestrator lands the ticket once it is closed, and running `land` from this session would stop it. When the repository's own checks fail and the failing check covers code an incoming ticket of your integration changed, the failure is the merge's: use the `resolving-merge-conflicts` skill.
    Done when `--closeout` exits 0.

#### Reading yourself in

A baseline in **Read first** is anything there that records a settled conclusion, and it is a contract, not a reference. A design package is copied exactly; a prototype is rewritten to production standard, keeping the shape its verdict settled on.

Follow **Parent** to the spec: read its Problem Statement and Solution, the few lines that say who uses this and why, then only the Implementation Decisions sections the ticket names, plus its Testing Decisions and Out of Scope, not the whole spec. Where the ticket is silent, choose what serves the person the Problem Statement names. Then the domain glossary (the root `CONTEXT.md`, or the `CONTEXT.md` of each context `CONTEXT-MAP.md` lists that this ticket touches): where it has a term for the thing you name, use that term.

When **Read first** lists a screen contract, read the `ui-acceptance` skill's `references/writing-ui-code.md`. Open the Memory records `#### Memory while working` names.

#### Memory while working

The `Data:` file carries two Memory indexes, one line per record (`id`, `title`, its first line as `applies`, `space`). Before working, open every record whose title or `applies` line bears on this ticket; skip the rest. A record is a clue: check it against the repository before you act on it (**principle-clues-are-not-evidence**).

When a command or tool behaves in a way that the ticket, repository authority, and the records you opened do not explain, search the current task with the exact error, command, and component before trying a workaround; if that has no answer, search repository and approved toolbox experience. How to open, search, save and correct a record is the `memory-records` skill.

#### While writing code

- The baseline is the contract (**principle-the-baseline-is-a-contract**). A baseline is a decision someone already paid for: a user's answer, a prototype that won, a page they signed off. Rewriting it from memory, or improving it, reopens that decision where nobody who made it can see; a `contract` child reopens it where they can. Copy the values, wording, states and interface shapes of every baseline in **Read first** from it rather than writing them again from memory. When something this ticket was told to follow does not hold, whether a baseline under **Read first**, a spec section named by **Parent**, or an acceptance criterion lacks a state, field, interaction or case or contradicts another such source, keep going and run `ticket_state.py <n> --open-child contract <file>`. The child quotes what does not hold and states what in that same source still holds and must be preserved. When the rest of the ticket depends on the answer, end your turn: the child wakes the orchestrator, which corrects the source and resumes you, or leaves the question to the user. A wrong `CHECK` is a `contract` child too: name the acceptance criterion, quote what is wrong, and state what it should be. Once a batch is published, only its orchestrator or the user edits a spec, ticket body or acceptance criterion. Never quietly change a baseline, never quietly add around one. A check that will not pass is answered by fixing the code or abandoning the criterion, never by bending the baseline, the harness or the test (**principle-silence-is-never-a-pass**). The checks exist so the user can trust a closed ticket without reading its code. An honest `HANDOFF REQUIRED` costs them one look in the morning; a false `ALL MET` lands broken behaviour under a green mark, and every ticket built on this one inherits it.
- Read `references/code-writing-rules.md` before the first line of code; its rules bind every change on this branch, the review's fix round included.
- Run typechecking regularly, single test files regularly, and, once at the end, the tests the repository's own instructions name for what this ticket changed; `--closeout` runs the repository's `checks` itself.
- Verify your work however you like; scratch scripts and quick checks need not be kept. Commit tests only where the ticket asks for them or this repository already keeps tests for this kind of change, sized like the neighboring test files: roughly one focused test per stated behavior. This is about extras only: implement every behavior the ticket asks for, completely.
- Before adding a file, a dependency or a configuration entry, write under **Decisions I made on my own** why the existing one is not enough.
- Whatever you simplify, keep intact: security, error handling that prevents data loss, accessibility, and anything the ticket explicitly asks for: **What to build**, every acceptance criterion, the baseline, the interface under **Seam**.
- For a file outside **Owns**: change it when a criterion cannot pass otherwise, and it lands under `Outside Owns:` in the closing comment; when the change is merely convenient, leave it and run `ticket_state.py <n> --open-child deferred <file>`. A file owned by a ticket that can run beside this one (neither blocks the other, directly or down a chain) is never changed from here, whatever needs it: run `ticket_state.py <n> --open-child contract <file>`, because one file has one writer at a time and the cut missed an edge (**principle-separate-before-serializing-shared-state**).
- A dispatched worker never runs the `design-pages` skill. A page that has to be drawn again is a `contract` child naming it, for a session whose host has the Claude Design tools.

#### While the product runs

Mode `## Non-negotiables` sends you to the `ui-acceptance` skill's `## Five rules while the product is running` before you start, reach or stop the product. When those rules have you report the ticket blocked (a human step, an unreachable product, a fault in the pipeline itself), open a `fault` child as `#### Opening a child` says, and stop.

#### Unattended outlets

Your line for a decision nobody is there to make goes under **Decisions I made on my own**. A question whose answer would change what the ticket delivers gets `ticket_state.py <n> --open-child decision <file>` instead, and the rest of the work carries on. Write each line for the reviewer, who judges it, and for the user, who reads it in the morning without your context: a choice a user would notice in the product (a label, a default, what a page shows or hides) is the one most worth a line.

Copy each `skip:` line of your todolist under **Decisions I made on my own** too, with the skipped step's title after `skip:`: the closeout checks every step under `#### Steps` for a trace or a `skip:` line naming it. A principle that changed a decision is named on that decision's line.

#### Integrating

Exit 0 is a clean merge, or nothing to merge; a clean merge prints its incoming tickets. After a clean merge of `origin/<base branch>`, identify each ticket represented by its new first-parent merge commits, then read its ticket and closeout evidence before changing the combined behavior. Exit 3 leaves a conflicted merge in the tree: do what its stderr says, and note each trade-off under `Decisions I made on my own`. The incoming side is closed tickets whose criteria the closing pass's `reverify` runs again on the base branch, so a resolution that drops their behaviour reopens their ticket hours later, and after a bounce no reviewer sees this merge. Where theirs and yours cannot both hold, the cut missed an edge: keep what landed and run `ticket_state.py <n> --open-child contract <file>` naming both tickets. Exit 2 names the condition that prevented integration; a pipeline failure becomes a `fault` child, then stop. Never rebase, abort or push from this integration command.

#### ABANDON kinds

Three `ABANDON` kinds, and the machine branches on each. `failed`: it ran and did not pass, after as many rounds in **Integrate and run every criterion** as you judged worth spending, or still failing after the review fix or final run; the reason says what each round tried. `stuck`: it will not start, or cannot be done within the task: a `CHECK` that will not run, a missing credential or device; the reason names the routes tried or points at the child that records them. A human step or an unreachable product while the product runs is not `stuck`: `#### While the product runs` routes it. `decision`: both options are legal and neither the ticket nor the spec says; write the question, the options, and the default when nobody answers; a UI difference never goes here: it is a `contract` child. Any `failed` or `stuck` turns the whole ticket into `HANDOFF REQUIRED`; `decision` does not: its child is already open, and the rest all passing is still `ALL MET`.

#### Opening a child

`ticket_state.py <n> --open-child <kind> <file>` takes a kind and a file whose first line is the child's title and whose rest is its body; it opens the child under this ticket and records it there. Which kind it is: the `verify-ticket` skill's `references/child-issues.md`. The child's readers have not seen your session, so the body stands on its own.

A fault in the pipeline itself (the pipeline's own scripts, a hook, or `.mmw/target.json`): `ticket_state.py <n> --open-child fault <file>`, whose body is the command you ran and the output you saw, then stop (**principle-report-faults-through-the-pipeline**).

#### The review round

The in-ticket round is first: fix the in-ticket findings once, under the code-writing rules that governed the first write, and run **Integrate and run every criterion** again. This round is the `tdd` skill's refactoring pass: restructure here, not under the next red. An in-ticket finding you do not fix is answered `refuted:`, which says you checked and the bad outcome does not happen at the cited location. Write what disproves this specific claim. A true fact about nearby code that does not disprove the claim does not count. Then, for each out-of-ticket review finding whose body the in-ticket round has not made untrue, run `ticket_state.py <n> --open-child finding <file>`.

A `## Manifest notes` line needs no answer from you: no fix, no `refuted:` row, no child.

#### When the orchestrator resumes you

`dispatch.sh resume` hands you the orchestrator's message as it wrote it. Do what it says, then run `dispatch.sh where <n>` and carry on at the step it prints.

#### After the closeout of an adopted ticket

A ticket you adopted outside a night, where `adopt` started a relay with you as the session it wakes, has no orchestrator to land it: you are woken with `#<n> ticket.passed` or `#<n> ticket.returned`; `bash scripts/dispatch.sh ack <n> <that event>`, then tell the user the ticket is closed and that `bash scripts/dispatch.sh land <n>` merges it and stops that relay. Do not run `land` from this worker session: it stops every session the ticket's events name, including this one.

#### When something else wakes you

On a ticket you adopted, you are also the orchestrator of its watch, so the relay, the watchdog and the turn guard wake you with what they would send an orchestrator. A `child.opened` of kind `contract`, `fault` or `decision` is the echo of a child you opened: run `dispatch.sh where <n>` and carry on at the step it prints. A `ticket.refused` carries a `reason`: with the user present, tell them what it says; with nobody there, write it as a line under `Decisions I made on my own`. A `worker.lost` means the watchdog took this session for stopped: run `dispatch.sh where <n>`, carry on at the step it prints, and put the `worker.lost` line into the closing comment. A `relay.recovered` asks nothing more of you. A message that `dispatch.sh resume` hands you is handled as `#### When the orchestrator resumes you` says. A `watchdog:` line that wakes you is not acked: tell the user what it says, since no orchestrator watches this ticket and this session cannot resume itself. An `MMW turn guard:` line names the commands to run: do what it says.

**Reply:** the closing comment `--closeout` posted. With the user present, also give them the ticket's number, the first line of that comment, and each `ABANDON: … decision` line that waits on them.
