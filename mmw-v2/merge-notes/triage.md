# triage

源目录：`mmw-v2/upstream/skills/engineering/triage/`

## 逐段意图

### SKILL.md

| 段落 | 我们的意图 |
| --- | --- |
| 开头「must **start** with this disclaimer」 | 改成放 issue comment 最后一行。原来的理由是 issue comment 的 first line 曾是 landing pipeline 的 protocol slot；mmw #315 之后程序只读 comment 末尾的 `<!-- mmw {...} -->` 事件块、不读 first line，但 first line 仍是人在票上扫一眼读到的那一行（`status` 的 `note` 列、night summary 都抄它），免责声明占了它，这张票在哪一步就没人看得出来。正文只写「放末行」，不附理由（旧理由里的 `protocol slot` 已过时）。上游改这句 → 收上游的措辞，位置留在末行 |
| `references/pipeline-issues.md`，`## Reference docs` 里指向它的一条，与 `## Triage a specific issue or PR` 开头指向它的一句 | 我们加的，放在上游文件旁边的一份 reference：本仓 landing pipeline 自己产出的 issue——worker 开的 `mmw:child`，以及最新结果是 `ticket.returned` 或 `ticket.bounced` 的 `mmw:ticket`——由 `## Triage a specific issue or PR` 开头那一句按 label 送过去（`gh issue view` 就显示 label，判这个条件不必多读什么），外来 issue 不读它。那一句放在第 1 步之前，因为从「Show what needs attention」挑出来的与维护者直接点名的 issue 都经过这里。理由：分支材料不压在上游占多数的正文里，外来 issue 的 triage 少读约 350 词。它的 `## A ticket handed back` 一节：`needs-triage` 不只承接外来 issue，还承接本仓 agent 没做完的 `ticket.returned` 与合并时被退回的 `ticket.bounced`。前者读 `ticket.checked`、`reviewer.reported`；后者读尝试建立合并的 `origin/<base branch>` commit（`commit`）、`into`、开工后已落地的兄弟票，以及事件里的 `files` 或 `commands`。两者都不按 reporter 的步骤复现、不查 `.out-of-scope/`，而是从已留下的证据推荐四个 outcome。上游若自己写了这两条支路 → 收上游，删掉我们这一节 |
| `references/pipeline-issues.md` 开头的按来源清单（原 `## Gather context`） | 我们加的：一个 child 的类型和父票写在它正文第一行（``A `<kind>` child of #<n>.``），不必再查 `gh issue view <m>` 的 `parent:` 行或 `gh api repos/{owner}/{repo}/issues/<m> --jq .parent_issue_url`（REST 对象没有 `parent` 字段）；父是 ticket 时读那张票的事件轨迹（`ticket.checked`、`reviewer.reported`），理由已并入开头段落，不再单独成节。`SKILL.md` 第 1 步因此回到上游原文。上游改 Gather context → 收上游措辞，按来源清单不动 |
| `references/pipeline-issues.md` 判断表的 `New work in this batch` 一行 | 不在句子里写票有几节：这一行说「模板里每一节都填」、指 `to-tickets` 的 `<issue-template>`。理由是节数由 `to-tickets/SKILL.md` 的 `<issue-template>` 一处定，抄进散文就是一份会过期而无人发现的副本，本仓 `CONTEXT.md` 把 `七节`、`八节` 列在 `<issue-template>` 的 `_Avoid_` 上就是这个原因 |
| `references/pipeline-issues.md` 的 `## ready-for-agent` | 我们加的：判定一个流水线的 child 该由 agent 做，同时回答在哪做，按表里的三去向改挂或转移（另一张票 / spec / 转到 toolbox 仓）。去 spec 的那一行走 `dispatch` 技能的 `route <ticket> <m> became-ticket <m>`（`<ticket>` 是 `child.opened` 记着 `<m>` 的那张票；spec 取自那条事件，不读当前的树，所以这条命令可以重跑），因为变成 ticket 要同时换分类 label（`mmw:child` → `mmw:ticket`）、改挂到 spec、并在原票上记一条 `child.closed`（mmw #315 第 6 节：label 管 board 怎么读这一层，父链管脚本怎么找 spec，出身留在原票的事件里）。这张 issue 本身是 pipeline 退回的 ticket 时，把 `needs-triage` 换成 `ready-for-agent`，它的 spec 下一次 `advance` 放掉 pipeline 的认领（`ticket.returned`、`ticket.bounced` 结束所有 hold，`status.py` 的 `advance_plan` 打出 `RELEASE`），blocker 都落地后打出 `DISPATCH` 再派一个 worker。外来 issue 判为 `ready-for-agent` 之后怎样进 landing pipeline，写在 `mmw` 技能的 **Triage an issue**，不在这份技能里 |
| 第 4 步 `Grill (if needed)` | host 中立：上游写「call the Skill tool twice」，这个工具名只在一家 host 上存在；改成读 `grilling` 与 `domain-modeling` 两份技能的 `SKILL.md`。共同理由见 [README.md](README.md#host-中立)，写法见 `mmw` 技能的 `references/skill-set-rules.md` `### Paths and host neutrality` 与 `### Hand-offs`。上游改这一步 → 收上游措辞，工具名仍换成读两份 `SKILL.md` |
| 第 5 步 `**Apply the outcome:**` 标题行，与删掉的 `needs-triage: apply the role` 一条 | 注明 the four outcomes 是 `needs-info` / `ready-for-agent` / `ready-for-human` / `wontfix`，留在 `needs-triage` 不算 outcome，上游那条 `needs-triage` 一并删掉。`CONTEXT.md` 与 `docs/agents/triage-labels.md` 都写「one of the four outcomes」，而上游这一节下面列了五条，读者数不出是哪四个。「`needs-info`、`ready-for-human` 和 `wontfix` 不移动 child」这句只对流水线的 child 有意义，挪到 `references/pipeline-issues.md` 的 `## ready-for-agent`，写成只有 `ready-for-agent` 会移动 child；`SKILL.md` 第 5 步不再重复这句。上游改这一节 → 收上游的条目，「四个」这个数与 `needs-triage` 不算出口这句保留 |
| 第 5 步 `Apply the outcome` 末尾 `A child whose default was right …` 一段 | 我们加的：worker 开的 child 默认已经对了、或修复已在 base 分支上时，经 `dispatch` 技能的 `dispatch.sh route <ticket> <child> fixed` 或 `stale <invalid\|fixed-elsewhere>` 关闭，让它的票记下这条路线；`wontfix` 表示没人会做，不表示已经做了。理由：triage 对这类 child 要有一个固定出口，而不是当场修掉。上游改这一步 → 收上游的条目，这一段保留 |
